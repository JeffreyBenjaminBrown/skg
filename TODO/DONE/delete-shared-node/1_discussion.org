#+title: Deleting a node referenced from someone else's data

* Executive summary
The requested behavior is compatible with the existing data model:

- A user may delete a node they own.
- The delete may clean references recorded in sources that user owns.
- It must neither rewrite nor require a rewrite of references recorded in
  sources they do not own.
- A surviving raw reference to the deleted ID is a real, durable graph
  state, not a failed transaction.

The existing 'Phantom::Unknown' is already the right representation for
that state.  It means precisely that a stored reference names an ID that
cannot currently be resolved.  The phantom itself should remain inert;
the relationship represented by its position should be editable when
that relationship belongs to the current user.

The main semantic decision is whether an unchanged Unknown line
preserves its relationship until the user explicitly removes it.  I
recommend that it does.  Otherwise an unrelated save silently destroys
the dangling relationship and prevents it from reconnecting if the
missing node later becomes available again.

** DONE 2. Does an unchanged Unknown preserve the relationship?
- [recommended] Yes.  It remains until its relationship owner deletes
  the Unknown line (or otherwise edits that collection).
- No.  Any definitive save of the relationship owner silently drops all
  visible Unknown members.

The recommended round-trip contract is:

1. Rendering a raw unresolved member produces an Unknown headline at the
   member's position.
2. Saving that headline unchanged contributes the exact raw ID back to
   the owner's collection, but contributes no node definition.
3. Deleting the headline removes that raw ID from the collection.
4. If the ID becomes resolvable before it is removed, the next render
   shows the real node again.

This makes the Unknown load-bearing only as relationship membership.  It
does not make the phantom itself saveable.

'traverse.rs' ignores every phantom, and 'content_members()' collects
only affected Active children.  Consequently a buffer containing an
Unknown can save without an error, but the containing node's next
definitive save omits the dangling ID.  The existing round-trip test
checks only that the save reports no error; it does not check whether the
relationship survived.

*** some context
The short distinction is epistemic:

- Deleted says: this view contained a real, materialized node, and the
  save that is being rerendered just deleted it.
- Unknown says: this position asks for an ID, but the renderer can find
  no current record for that ID and has no last-seen node to use.

Both are absent from the current graph.  That is why 'No longer exists in
the graph.' does not distinguish Deleted from Unknown.

'Phantom::Deleted' is created under these particular conditions:

1. The post-save rerender receives 'deleted_by_this_save_pids', built
   directly from the 'DeleteNode' instructions in that completed save.
   A deletion visible only in Git history uses 'Phantom::Diff', not
   Deleted.
2. A view occurrence with one of those PIDs already exists as a
   definitive Active vognode when its breadth-first completion visit
   begins.  'mutate_activeNode_to_deletednode' converts that existing
   occurrence in place.
3. Because the occurrence was real moments earlier, Deleted keeps its
   ID, former node home source, last-rendered title and body, and existing
   view children.  Its children can then be preserved as independent
   branches.

It is not the generic result of a failed lookup.  A fresh render has an
empty 'deleted_by_this_save_pids' set and therefore never creates a
Deleted merely because a file is absent.  Inactive placeholders are not
converted, because doing so would leak that hidden data vanished.
Indefinitive Active occurrences are clobbered before the conversion
check, so the in-place conversion specifically preserves a definitive,
materialized occurrence.  A Deleted can subsequently survive another
buffer parse/rerender, but it emits no save instruction and contributes
no parent membership.  A childless Deleted is pruned unless it is a view
root; one with children remains to hold the saved view subtree.

'Phantom::Unknown' is created under these particular conditions:

1. Rendering or completing a requested position has a raw ID to draw.
2. Lookup cannot resolve that ID to a current node/source in the in-Rust
   graph, filesystem, or applicable fallback.
3. There is no current-save transition carrying last-seen Active-node
   data for that newly created position.

Today those positions include a dangling content member, a requested
root or backpath target that cannot be found, and an Unknown already
parsed from a buffer.  Under the decisions in this document they will
also include unresolved PartnerCol members.  Unknown carries only the
raw ID: it does not claim that the target ever existed, why it is absent,
where it lived, or what its text was.  Content reconciliation retains an
Unknown while the raw parent relationship still names its ID; if that
membership disappears, it becomes a dead scaffold and is pruned.  The
new round-trip rule from decision 2 will make that retained Unknown
load-bearing for the relationship, while it remains inert as a node.

The reported case exposes an overlap rather than two naturally disjoint
states.  Immediately after deleting node N:

- an open Cheese view already has N as a materialized Active child;
- Cheese's non-owned raw relationship to N survives; and
- the post-save context knows that this save deleted N.

Current ordering retains the existing child for the raw membership, then
converts it to Deleted when the child is visited.  If it is a leaf, the
prune pass may remove it altogether.  After a restart, there is no
current-save deletion set or last-seen Active node, so the same surviving
raw relationship produces Unknown.  Thus the present UI can show
Deleted, nothing, and later Unknown for the same durable relationship.

Decision 5 is really a precedence decision for that overlap:

- If durable relationship state wins, a surviving raw membership is
  shown as Unknown immediately.  Deleted is reserved for a last-seen
  occurrence that has no surviving backing relationship.  This is my
  recommendation because it makes the row immediately editable under
  the Unknown rules and agrees with a fresh render.
- If last-seen transition information wins, the open view may show the
  richer Deleted temporarily and become Unknown only after a fresh
  render.  Then Deleted must either become relationship-aware and
  load-bearing, or the UI must accept that this temporary row cannot be
  used to remove the surviving relationship.
- A third option is to invent a combined Deleted-and-still-referenced
  state, but that adds another phantom distinction and still cannot be
  reconstructed after restart without persistent tombstones.

Reminder: you want to edit the 'No longer exists in the graph.' comment
on 'Phantom::Deleted' after deciding the precedence above.

* Confirmed cause of the failed deletion
'apply_delete_propagation_cleanup' in 'server/save.rs' performs two
passes:

1. It uses the inverse indexes for contains, subscribes, hides, and
   overrides to find every node that refers to a deleted PID.  It
   synthesizes a full 'SaveNode' for each referencer not already in the
   save.
2. It removes the deleted node's primary and extra IDs from all four
   outbound lists of every 'SaveNode'.

That is why the current all-owned deletion test expects every neighbor
to be rewritten.  The algorithm has no source-ownership boundary.

The save handler runs normal buffer validation first, then adds these
collateral saves.  The synthesized save of Cheese therefore did not go
through the earlier foreign-edit/fork classification.  Later, the
filesystem preflight correctly refuses to write a telescope whose home
or proposed sections are non-owned.  The transaction fails before any
files change.

The preflight is doing the right thing.  The delete-propagation pass is
asking it to do the wrong thing.

* DONE Proposed authorization rule
** it
Deletion cleanup may mutate a referencer only when its retained

The loader makes this a node-level decision.  When raw owned and
non-owned files collide on one PID, it retains the complete owned
telescope and ignores every non-owned same-PID file before folding.  A
retained 'NodeComplete' is therefore all-owned or wholly foreign; it
cannot mix relationship members recorded in the current user's sections
with members recorded in another user's sections.  Its home source
reliably classifies which case it is.

The implementation wrinkle is consequently smaller than first reported:
the global inverse indexes contain both owned and wholly foreign
referencers, while 'apply_delete_propagation_cleanup' currently turns all
of them into synthetic ordinary 'SaveNode' values.  It should synthesize
and strip only owned referencers.  The normal writer's refusal to write a
foreign telescope remains unchanged.

The deletion itself can remain as it is: filesystem deletion already
iterates configured sources and removes files only from owned sources.

** elaboration on the wrinkle
*** it
A 'NodeComplete' is the folded, effective view of one retained privacy
telescope.  One user's telescope may span that user's public and private
repositories, and its relationship members retain those per-edge
recording sources.  It may therefore contain, for example:

#+begin_example
contains = [A recorded at my-public, B recorded at my-private]
#+end_example

It may not combine 'my-source' with 'other-user'.  If configured raw sources
contain both an owned and non-owned file with the same PID,
'retain_owned_sections_when_pid_collides' keeps all owned sections,
discards all non-owned sections from semantic loading, and reports
'IgnoredForeignPidCollision'.  A normal fork likewise has a new PID and
does not extend the foreign node's telescope.

The cross-owner wrinkle is in discovery, not telescope writing.
The in-Rust inverse indexes cover every retained node in the config,
including Cheese's wholly foreign node.  When an owned target is deleted,
the current cleanup sees Cheese among the referencers and creates a full
synthetic 'SaveNode' for it.  Phase 2 removes the target ID from that
pending folded value.  Only afterward does filesystem preflight observe
that the entire telescope is foreign and refuse it.

The intended fix does not need a new section-patching writer.  Before
synthesizing a cleanup save, classify the referencer by its retained
home/source and skip it unless 'config.user_owns_source' is true.  Keep
phase 2's deleted-ID stripping for owned synthetic saves and owned saves
already supplied by the user's buffer.  A defensive ownership check at
that phase boundary can ensure a future caller cannot reintroduce the
same bug.

Tests should pin the premise as well as the outcome: an owned telescope
may span several owned sources; an owned/non-owned same-PID collision
loads only the owned telescope and warns; a wholly foreign referencer is
not scheduled for cleanup; and the owned target deletion succeeds while
the foreign bytes and raw reference remain unchanged.

*** DONE please define/elaborate
**** current cleanup
'Current cleanup' means 'apply_delete_propagation_cleanup' in
'server/save.rs'.  It receives the pending 'DefineNode' batch and an
in-Rust graph snapshot after the user's buffer has already passed normal
save validation but before filesystem preflight.

It has two phases.  First it collects every deleted primary PID, expands
that set with the deleted nodes' known extra IDs, and consults the four
inverse indexes to find nodes that contain, subscribe to, hide, or
override a deleted PID.  For every referencer not already saved or itself
deleted, it copies the referencer's current 'NodeRust' into a complete
synthetic 'SaveNode'.  Before this task, that copy is intended as a
no-op; its purpose is to put otherwise-unmentioned neighbors into the
pending write batch.

Second, it walks every 'SaveNode' in the batch -- both those synthesized
neighbors and saves originating from the buffer -- and strips deleted
IDs from the four outbound relationship fields.  The resulting batch
then goes through ordinary telescope preflight and writing.

The bug is entirely in the first phase's missing ownership filter.  Its
inverse scan finds Cheese correctly, but Cheese should never have been
turned into a save instruction.

**** removes IDs from that folded value
The 'folded value' is the in-memory 'NodeComplete' inside a pending
'SaveNode', not a raw '.skg' section and not the graph already being
mutated.  It represents the effective result of folding the retained
telescope.  Its list elements are 'MemberAtSource' values, so each member
still says which one of that telescope's source sections records it.

For 'contains', cleanup calls 'retain' and drops every element whose raw
'member' is in the deleted-ID set.  The helper for the other three fields
does the equivalent while preserving their 'MSV' specified/unspecified
shape.  This removes both the ID and its recording-source tag from the
prospective complete value.  The ordinary writer later unfolds that
value into the telescope's per-source files.

For an owned referencer this is the desired collateral rewrite.  For
Cheese it constructs a prospective foreign rewrite, which preflight
properly rejects.  Skipping the foreign synthetic 'SaveNode' leaves
Cheese's folded graph value and raw files untouched, so its reference can
become Unknown after the target disappears.

**** synthetic saves
In this document, a *synthetic cleanup save* is a 'SaveNode' that the
server adds to the current pending save batch even though the user's
buffer expressed no edit to that node.  'Synthetic' describes the
instruction's origin, not its durability or validity.

For delete propagation, the server finds an otherwise-unmentioned
referencer in an inverse index, copies its current 'NodeRust' into a
'NodeComplete', wraps that in 'DefineNode::Save', and appends it to the
batch.  At the moment it is created, the instruction describes the node
unchanged.  Phase 2 then removes the deleted IDs from its outbound lists,
turning it into the collateral rewrite that cleans the referencer.

It is not:

- a second user-visible save operation;
- a dry run or hypothetical value;
- a special filesystem write path; or
- any arbitrary server-generated 'SaveNode', such as a fork clone or a
  merge preservation node.

Once added, it goes through the same batch preflight and ordinary
telescope writer as a buffer-originated 'SaveNode'.  That last fact is
why synthesizing one for Cheese causes the observed failure.

In the actual plan I will prefer the unambiguous phrase
'cleanup-generated SaveNode', while recognizing 'synthetic cleanup save'
as the shorter term used in this discussion.

* Missing machinery
** Unknown save extraction

exact stored member ID to the owning collection without producing a node

content and writable PartnerCols.

The exact stored ID matters: a referencer may name an extra ID rather

**** Codex response
Agreed.  The wire metadata field is 'referenceSource'; the Rust field can
follow the local naming convention as 'reference_source'.  Its value is
the source section recording the relationship represented by this
Unknown occurrence, never the missing target's home.

It should be load-bearing and validated when an Unknown round-trips a
structured relationship, because it determines which section is
preserved or edited.  It can be optional for an Unknown root or another
placement that has no structured relationship provenance.  Per the
withdrawn source-herald request above, merely carrying
'referenceSource' does not present it as the Unknown node's source.

** Herald wording
The current Unknown herald says 'Parent references unknown node.'  That
fits content but not an Unknown root reached through a text link or a
PartnerCol member.  A safe generic label is 'Reference to unknown node.'
Relationship-aware wording is possible if provenance is deliberately
exposed to the herald layer.

** Authorization and atomicity
- Deleting an owned target succeeds when both an owned node and a
  non-owned Cheese node refer to it.
- The owned relationship is removed.
- Cheese's file is byte-for-byte unchanged and still contains the raw ID.
- The target is removed only from owned sources.
- No foreign file is prepared, written, or deleted.
- A failure in preflight still changes nothing.

** Unknown lifecycle
- A fresh view of Cheese renders the surviving raw ID as
  'Phantom::Unknown'.
- An already-open Cheese view converges to the same result after delete.
- Saving Cheese's relationship owner with the Unknown untouched
  preserves the exact raw ID.
- Deleting the Unknown line and saving removes only that relationship.
- If the target becomes resolvable again before removal, the relationship
  resolves to the real node.
- A dangling extra ID follows the same rules without being rewritten to
  a primary ID.
