* Purpose

Implement the decisions recorded in '1_discussion.org' and the subsequent
inline discussion in '2-0_plan.org'.  This document supersedes the operative
plan in '2-0_plan.org'; that file remains the discussion history and should not
be used as implementation instructions where the two differ.

The completed feature has these user-visible results:

- A user can delete a node they own even when a retained foreign telescope
  still refers to it.
- Delete propagation removes references only from retained telescopes owned by
  the current user.  It neither writes nor requires a write to foreign data.
- A surviving unresolved member of 'contains', 'subscribes_to',
  'hides_from_its_subscriptions', or 'overrides_view_of' renders as
  'Phantom::Unknown'.
- An Unknown remains inert as a node but behaves like its raw ID as a member of
  an editable structured relationship.  Leaving it in place preserves the
  relationship; omitting it removes the relationship; moving, copying, and
  ordering it have the same meanings as for a known member.
- 'HiddenOutsideOfSubscribeeCol' becomes an editable derived filter.  Users can
  add and remove hides there.  An added member which belongs inside a
  subscribee is saved, displayed in 'HiddenInSubscribeeCol', and accompanied
  by an explanatory success warning.
- 'skg-delete-references-to-absent-node' removes an Unknown's exact raw ID from
  all four structured relationship fields in every retained owned telescope.
  It reports textual Org links before confirmation but never rewrites them.
- An already-open view and a fresh view agree: if a raw relationship survives
  deletion, its missing member is Unknown immediately.  'Phantom::Deleted' is
  reserved for a last-seen occurrence without a surviving backing
  relationship.
- Relationship-source metadata has separate fact and request branches for
  known nodes, Unknowns, and aliases.  Copying a rendered fact cannot
  accidentally resource an edge.

* Semantic model

** A retained telescope has one ownership classification

A retained 'NodeComplete' or 'NodeRust' represents one telescope.  It may span
several sources belonging to the same user.  It does not mix this user's
sections with another user's sections.

If owned and foreign raw files collide on a PID, loading retains the complete
owned telescope, ignores all foreign same-PID files, and reports the existing
'IgnoredForeignPidCollision' warning.  A normal fork has a fresh PID.  Thus
'node.source', the retained home source, is sufficient to classify the whole
telescope with 'config.user_owns_source(&node.source)'.

This ownership boundary controls writes.  The global graph may discover a
foreign referencer, and a view may display its relationship, but neither fact
authorizes a 'SaveNode' for it.

** Relationship vocabulary

Use these terms consistently:

- /relationship owner/ is the node whose outbound field stores the member;
- /member/ is the ID or alias value stored in that field;
- /home source/ is a node's home, qualified as the owner's home or member's
  home when both are in scope; and
- /relationship source/ is the source section which stores one relationship
  member.  Its wire leaf is 'relSource'.

An Unknown has no known home source.  It can still depict a relationship with
a known relationship source.  Do not introduce 'referenceSource' or
'reference_source'; those names belong only to the superseded design in the
discussion history.

** Unknown is a raw relationship value, not a node edit handle

'Phantom::Unknown' continues to mean only that a raw ID has no current graph
record.  It has no title, body, home, owner, tombstone facts, or node-level
write behavior.

At a structured relationship position, the Unknown's raw ID is load-bearing
membership data:

- an unchanged occurrence retains the destination's current exact stored
  member and source;
- omission from an owned, definitive, editable collection removes that member;
- a new occurrence creates a relationship to the exact raw ID;
- a copy leaves the origin unchanged and creates the destination membership;
- a move removes an editable origin only because it was omitted there, then
  creates the destination membership;
- ordered relationships use its buffer order exactly as they do for known
  members; and
- the occurrence emits no node definition, deletion, merge, fork, title/body,
  or node-source instruction.

The Unknown carries no origin provenance.  Its current tree ancestry supplies
the requested destination owner and relation.  Current graph/disk state
supplies an existing destination member's sticky source.  A new destination
uses its ordinary source rule.  This permits a root or backpath Unknown to be
copied into an owned relationship and permits an informed user to author an
arbitrary absent raw ID.  Such an edit changes only the relationship owner's
data.

Do not add a special stale-edge proof for Unknown.  A stale definitive buffer
can already recreate a known relationship.  A general buffer/graph revision
scheme, if wanted, is separate work.

** Raw identity is preserved

Use one comparison key wherever relationship members are deduplicated,
matched, partitioned, or woven:

#+begin_example
#[derive(Clone, Debug, Eq, Hash, PartialEq)]
enum RelationshipMemberKey {
  ResolvedPid(ID),
  UnresolvedRawId(ID),
}
#+end_example

Construct 'ResolvedPid' when 'graph.pid_of(raw_id)' succeeds and
'UnresolvedRawId' otherwise.  This preserves primary/extra-ID equivalence while
a node exists and exact raw equality after it disappears.

The key is for comparison only.  Never replace the stored raw ID in a
'MemberAtSource<ID>' during a no-op round-trip.  In particular, an unresolved
extra ID must not be rewritten to a remembered or guessed primary PID.  When a
line which was rendered Unknown becomes resolvable before save, allow the
relationship edit and render it as Active afterward; retain its exact raw ID
unless an existing, explicit repository rule already says otherwise.

** Display and edit gates are separate

For an outbound structured member recorded at relationship source S:

| S active | member resolves | member home active | display behavior |
|----------+-----------------+--------------------+------------------|
| no       | either          | either             | omit it and preserve it from disk |
| yes      | no              | not applicable     | display Unknown using the raw ID |
| yes      | yes             | no                 | omit target data and preserve it from disk |
| yes      | yes             | yes                | display the normal current-node form |

The relationship source controls whether an unresolved member is visible.  A
missing member has no home to consult, and displaying its already-stored raw ID
does not reveal title/body or home data.

Ownership controls editability separately.  A foreign relationship can be
visible in the deleting user's already-open view and converge to Unknown, but
that occurrence is read-only.  Under the relationship owner's config, the
same definitive owned relationship can be edited.

** Writable and read-only surfaces

The four outbound fields use these user-facing surfaces:

| stored field | relationship owner | writable dangling-member surface |
|--------------+--------------------+------------------------------------|
| 'contains' | the direct parent node | direct content child |
| 'subscribes_to' | the subscriber | 'SubscribeeCol' member |
| 'overrides_view_of' | the overrider | 'OverriddenCol' member |
| 'hides_from_its_subscriptions' | the subscriber | 'HiddenOutsideOfSubscribeeCol' member when classified outside |

'SubscriberCol', 'OverriderCol', 'HiderCol', and 'HiddenCol' remain read-only
inverse surfaces.  'HiddenInSubscribeeCol' remains a read-only derived filter.
Inbound views do not invent unresolved members after TypeDB loses the missing
node's relation instance.  Durable dangling membership comes from raw outbound
lists, never from TypeDB.

Textual Org links are title/body text, not structured relationship members.
Normal deletion and collection saves do not rewrite them.

** Same-session deletion precedence

After a save deletes a node, inspect the post-save raw relationship goal before
applying the generic Active-to-Deleted conversion:

- if a raw membership at this position survives and the member no longer
  resolves, normalize the occurrence to Unknown immediately;
- if no backing relationship survives, retain the existing last-seen
  'Phantom::Deleted' behavior, including its scaffold and pruning rules; and
- make post-save, fresh-render, and post-restart output agree.

The normalization may preserve the view wrapper's focus/fold state and may
retain descendant display context by making those descendants independent.
It must discard title, body, source, and other claims an Unknown cannot make.

* Relationship-source fact and request contract

This refactor is a prerequisite for Unknown editing.  Apply it uniformly to
ordinary Active occurrences, aliases, and Unknown occurrences wherever source
editing is supported.

** Use the same leaf in two unambiguous branches

The already-true display fact remains 'relSource'.  For an Active node it stays
inside 'viewStats':

#+begin_example
(skg (node ...
           (viewStats (relSource CURRENT))))
#+end_example

It heralds as '~CURRENT'.  It says where the relationship represented by this
position is currently stored.  It has no write force.

A source change is represented only by a relationship-source variant of the
existing 'editRequest' branch:

#+begin_example
(skg (node ...
           (viewStats (relSource CURRENT))
           (editRequest (relSource REQUESTED))))
#+end_example

It heralds as 'request:~REQUESTED'.  Before save both forms may coexist.  Only
the 'editRequest.relSource' value feeds explicit-source validation and
lowering.  The fact and request are still unambiguous because their parent
forms differ.

Keep the alias display form at its existing top-level location and add its
request beside it:

#+begin_example
(skg alias
     (relSource CURRENT)
     (editRequest (relSource REQUESTED)))
#+end_example

Represent the same position metadata inside an Unknown's own form:

#+begin_example
(skg (unknown
       (id RAW-ID)
       (viewStats (relSource CURRENT))
       (editRequest (relSource REQUESTED))))
#+end_example

Both optional forms are absent on an ordinary Unknown at the applicable
default with no pending request:

#+begin_example
(skg (unknown (id RAW-ID)))
#+end_example

Do not emit or accept 'referenceSource'.  Do not add another spelling for
the relationship-source edit request.

** The display fact is output-only save input

Parsing must retain the displayed 'relSource' long enough to round-trip and
herald the buffer, but save extraction must ignore it as an instruction.  If a
user edits, deletes, or copies the fact, the next successful rerender recomputes
it from the graph.  Do not tamper-fail a copy merely because its displayed fact
describes the old position.

An existing destination edge remains sticky even if its copied or edited
display fact is wrong.  A new destination edge derives its default.  Thus a
normal copied headline does not transplant its old edge's relationship source.

If a headline also contains a pending
'(editRequest (relSource REQUESTED))', copying the headline copies that
deliberate request.  Validate and apply it at the new destination.  This
distinction is the reason the fact and request branches must remain separate.

After a successful save, graph-derived rerendering emits no request branch and
recomputes the display fact.  After validation or write failure, the client
buffer remains untouched and the pending request remains available for
correction.

** Compute displayed facts with the applicable default

Continue suppressing the display fact when the current relationship source
equals the applicable default.  Emit it only for an off-default edge.

For a known member, use the existing relationship-default policy based on the
relationship owner's and member's homes, including the established owned-to-
foreign rule.  For an unresolved member, the fallback default is the
relationship owner's home.  For direct content that is the parent's home; for
an outbound PartnerCol it is the col anchor's home.  It is not the scaffold's
source, and it is not a guessed home for the missing node.

Alias default remains the alias owner's home.  Hides remain the existing
exception: 'hide_source' derives their source, and known and Unknown hide rows
have no explicit relationship-source request.

Centralize this default calculation enough that rendering, the source-info
request, save validation, and tests cannot drift.  Do not force callers with an
unresolved member to fabricate a member home.

Extend 'Qual::Alias' with a separate 'rel_source_request'.  Its existing

** Validate request eligibility at save

The parser accepts enough shape to produce good validation errors; tree and
graph validation decide whether a request is meaningful.  Require:

- a genuine binding relationship at the occurrence, not a root, backpath,
  independent parked node, or unrelated scaffold;
- an owned, definitive relationship owner;
- one of content, subscribes, overrides, or alias membership;
- a configured requested source owned by the current user;
- conformance with the existing default privacy floor; and
- no conflicting request for the same final owner/relation/member.

Reject requests on hide positions and read-only/inbound positions.  Validate
against the same pre-save graph snapshot used for membership merging.  If the
member begins resolving between render and save, use the now-known default for
validation and render it normally after success.

** Relationship-source regression checkpoint

Before layering dangling-reference behavior on top, prove all of the following:

- saving an untouched rendered off-default known edge does not resource it;
- copying a known headline with only the display fact creates a destination
  edge at its sticky/default source, not the copied source;
- a pending request changes the source and disappears after success;
- a failed save leaves the request in the user's buffer;
- copying a pending request applies it at the destination after validation;
- aliases obey the same fact/request distinction;
- existing delete and merge requests retain their wire round-trip and
  validation behavior;
- a relationship-source request on an indefinitive member is accepted when
  its relationship owner is definitive and owned;
- repeated or multi-valued 'editRequest' forms and delete/merge/source
  conflicts are rejected without last-one-wins behavior;
- recursive source changes and node-source-move assistance inspect requests,
  not facts; and
- no parser, lowering, or documentation path describes a display fact as save
  intent.

No.  On reconsideration, your argument wins: putting it in the existing
'editRequest' branch is cleaner than adding a relationship-specific request
container.

I had treated 'editRequest' as a node-edit namespace because its current wire
grammar lives inside '(node ...)', its Rust value is stored in
'IndefOrDef::Definitive', and its only variants are 'Delete' and 'NodeMerge'.
But those are facts about the present implementation, not a persuasive
semantic boundary.  As you point out, merge already changes more than the
single carrier node.  The coherent meaning of 'editRequest' is “a requested
graph mutation anchored at this view occurrence.”  Changing the source of the
binding relationship fits that meaning.

The proposed wire forms should therefore be:

#+begin_example
(skg (node ...
           (viewStats (relSource CURRENT))
           (editRequest (relSource REQUESTED))))

(skg (unknown
       (id RAW-ID)
       (viewStats (relSource CURRENT))
       (editRequest (relSource REQUESTED))))

(skg alias
     (relSource CURRENT)
     (editRequest (relSource REQUESTED)))
#+end_example

The displayed fact remains '~CURRENT'; the request should still herald as
'request:~REQUESTED'.  The parent form, not a different leaf name,
distinguishes observation from intent.

This requires generalizing the parser and in-memory placement of
'editRequest' so Alias and Unknown can carry the relationship-source variant.
That work is not additional complexity caused by choosing 'editRequest': any
separate-container design would also have to add request storage and grammar
to all three carriers.  Internally the current 'EditRequest' enum becomes the
node-specific 'NodeEditRequest'; the occurrence's separate
'rel_source_request' field and a parsing-only discriminated value carry the
relationship-source case even though both share one wire container.

The existing singular request also gives a useful rule.  A carrier cannot
simultaneously request delete or merge and request a new source for its binding
relationship.  Those combinations are meaningless or contradictory and
should be rejected rather than ordered.  The single-edge setter refuses a
headline which already requests delete or merge.  The recursive setter
preflights its eligible subtree and aborts before making any metadata change if
it finds such a conflict.  Neither setter may overwrite the node edit request.
“No override” removes only the '(relSource ...)' edit request and never touches
the displayed fact.

Thus a relationship-specific container does not earn a separate namespace
merely because the edit belongs to an edge.  A separate branch would become
worthwhile only if Skg developed several relationship-specific requests which
legitimately coexist with node edit requests and needed their own collection
semantics.  This task does not provide such a case.  Jeff accepted this
conclusion, and the operative plan now uses 'editRequest' throughout.

alias fact locations limits wire churn.  Parser, serializer, herald, command,
and save tests enforce identical semantics despite those grammar locations.
