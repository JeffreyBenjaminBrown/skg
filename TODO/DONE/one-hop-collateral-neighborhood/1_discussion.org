* vision : Updates should apply to a collateral buffer's one-hop neighborhood.
Collateral buffer updates should use a one-hop neighborhood
of each collateral (but not the saved) buffer.
(This problem is already noted in TODO/problems.org, I think --
definitely somewhere besides TODO.org.)
The saved buffer data checked should (probably already does)
include the union of the saved buffer's IDs before and after save.
The one-hop neighborhood of the collateral buffers
need, I think, only include what the collateral buffer included
before the save, because any new nodes that buffer gains
will have been new nodes saved in the saved buffer,
and their heralds will be redrawn from scratch.

** Architecture: keep the old collateral membership, but examine both graph snapshots
   I agree that selection should start with the collateral view's existing

*** Counterexample: adding an incoming edge
    Another buffer displays B. Saving A adds A.contains = [B], where A
    was not previously adjacent to B. B's old graph neighborhood does not
    contain A, yet B's container count must change. A can be either an
    existing node or a newly created one. Removing the edge gives the
    converse example: the post-save neighborhood no longer contains A.
*** Recommended selection rule
    Let C be the active IDs in an existing collateral view, W the nodes
    written or deleted by the save, and N_before / N_after the one-hop
    neighbors in the corresponding graph snapshots. Select that view if:

    #+begin_example
    W intersects (C union N_before(C) union N_after(C)).
    #+end_example

    Include C itself, so ordinary title/body edits still propagate.
    Exclude the saved view from this selection; it already rerenders.
    This is a rule for one-hop dependencies, not a proof that every
    possible rendering dependency is covered.
*** The explanation about newly displayed nodes is too restrictive
    A collateral view can gain an already-existing graph node. For
    example, adding an existing B to A.contains can expose B and B's
    existing descendants when A's collateral view is completed. Those
    descendants need not occur in the saved buffer. The stronger reason
    no second selection pass is needed is that, once selected, the whole
    view completes and computes its stats from the post-save graph.
** Architecture: use the save's actual effects, not all IDs appearing in its buffer
   'find_collateral_view_uris' in [[file:../../server/update_buffer.rs][update_buffer.rs]] currently uses
   Save/Delete IDs from 'define_nodes'. It does not use a union of the
   saved buffer's old and new IDs. The handler adds delete cleanup,
   approved fork clones, and merge definitions before calling it.

   I recommend retaining an effects-based set W and ensuring it covers
   all final writes, deletions, and source changes, including generated
   operations. A buffer-membership union can both refresh unnecessarily
   for unchanged nodes and miss effects outside the submitted view.
   Old and new identity resolution still matters: retain deleted IDs,
   resolve extra IDs in the appropriate snapshot, and account for merges
   that turn an old PID into an extra ID of another node.
*** Keep view membership separate from graph dependencies
    Do not put neighbor IDs into 'ViewState.pids'. Its current invariant
    is the IDs of active nodes actually in the view. Compute the
    neighborhood separately, initially on demand, using the captured old
    runtime and the published new runtime. This avoids introducing a
    dependency cache that becomes stale whenever an unseen neighbor changes.
*** Decide whether the asymmetry is semantic or an implementation requirement
    With adjacency defined in both directions, intersecting W with each
    view's neighborhood is equivalent to intersecting each view's IDs
    with W plus W's old/new neighbors, provided identities are normalized
    consistently. The latter can compute an affected-ID set once per save.
    I recommend allowing either implementation; neither entails recursively
    expanding both sides or changing how the saved view renders.

****** Define overlap using the save's effects and the dirty view's dependencies
I recommend rejecting when an affected-ID set computed from W
intersects another dirty view's relevant IDs. That uses the same
mostly one-hop relation as collateral selection. Intersecting two
expanded neighborhoods is more conservative: A and B could both
link to X without either buffer depending on the other's edits.
We need not block that case merely because X is a common neighbor.

However, the server's registered view is insufficient for this
check. A dirty buffer may have acquired an existing node, link,
or override marker since its last render. The client must report
which buffers are dirty and provide their current dependency
information, in addition to the registered baseline. Include IDs
removed by local edits as well as newly referenced ones. A missing
or unparseable dependency description must cause a conservative
refusal, not be treated as an empty set.

Perform the check against the prepared candidate before disk
writes, graph publication, or index updates. Return the conflicting
buffer names/URIs and useful shared IDs so the refusal is actionable.
Sending only dirty URIs would protect current replacement targets,
but would miss dependencies introduced by unsaved edits.
****** Keep the dirty-buffer check valid while applying the save
Capture dirty-buffer state while the client's initial locks are
held. Keep those dirty buffers locked through the terminal response,
even when they pass the conflict check, so their checked dependencies
cannot change mid-save. The early narrowing can still free unrelated
clean views. This slightly qualifies the earlier "exact collateral
set" lock contract: locks also protect the conflict check's inputs.

This is safety within the dependency model we define. A mostly
one-hop neighborhood alone is not a proof against every stale-save
case, especially placeholders or dependencies not represented by
active IDs. A complete guarantee would also require baseline/version
validation of what a save reads or overwrites. We should not describe
the overlap check as solving that broader problem without the audit.

*** Let's take a full override neighborhood.
So one hop along the other relationships,
but extend the neighborhood along the override axis
for as far as it can go monotonically.

Override is a very rare relationship, and not a bushy one --
most chains will be length 1 -- so this is affordable.

What I mean by monotone is:
Given a view V, we extend first in the overriderward direction
as far as possible to get V',
and then we extend V in the overriddenward direction to get V'',
and then we union V' and V''.
Stated differently, while extending along one direction,
we don't double back into the other direction.

In the code then we should call this an "update-relevant neighborhood",
and define that in the glossary.
**** Codex: adopt monotone override reachability, with two boundaries made explicit
     Agreed on the name 'update-relevant neighborhood' and on documenting
     it in the glossary when implementing. For each graph snapshot and
     seed set S, I read your rule as:

     #+begin_example
     M(S) = S
            union ordinary one-hop neighbors of S in either direction
            union all overriderward nodes reachable from S
            union all overriddenward nodes reachable from S.
     #+end_example

     "Ordinary" here means the four non-override relations. The two
     override walks start separately from S; neither starts from the
     other's result. Compute M_before(W) and M_after(W) separately and
     union them. Do not walk a graph made by unioning old and new edges:
     that could invent a path present in neither snapshot.
***** Do not silently compose ordinary hops with override walks
      The formula above does not follow an ordinary edge and then an
      override chain, or the reverse. Those mixed paths are a broader
      neighborhood. I recommend the literal separate union above, with
      mixed paths explicitly excluded from the glossary definition.
      If the intent is to extend override chains from every ordinary
      neighbor too, that needs a different formula; doing that in only
      one order would also invalidate the symmetry argument above.
***** Traverse branches and guard cycles even if ordinary usage is a short chain
      I agree that short, rare chains make this practical. But
      [[file:../../server/dbs/in_rust_graph/override_invariants.rs][the invariants]] restrict user-owned overriders; a node can override
      multiple targets, and foreign override facts do not have the same
      monogamy/cycle guarantees. Our accepted ungated neighborhood
      includes those facts, so the traversal must handle branching.

      Use a separate visited set for each direction and traverse every
      reachable branch. Sharing the visited set between directions could
      suppress a necessary traversal. No depth cap or silent truncation:
      visited sets ensure termination, and cost is proportional to the
      override subgraph actually reached. Use relation accessors rather
      than 'resolve_override', which deliberately applies ownership and
      visibility rules for choosing a displayed substitute.

      This extends selection. It does not by itself establish that every
      already-substituted node reconciles correctly after an intermediate
      override edge changes; implementation tests should check the resulting
      displayed node as well as whether its view was selected.
** Acceptance cases that should constrain implementation
*** Both edge addition and removal update a view showing only the other endpoint
    Include creation/deletion of the edge-owning node, and each relation
    type. Neither endpoint needs to be displayed in the other buffer.
*** Identity and metadata changes reach affected views
    Cover extra-ID references, merge acquirees, source moves, and a
    text-only edit that changes a neighbor's surprising-link herald.
*** Newly exposed existing nodes render correctly in one completion pass
    Add an existing subtree through a saved relationship; check its
    freshly displayed descendants and heralds without another save.
*** Lock coverage holds throughout the message sequence
    Test a view that shares no old saved-view PID but becomes collateral,
    and a newly introduced relationship absent from the old neighborhood.
    Check that rejected/failed saves and confirmation responses unlock.
*** The boundary stays narrow and safe
    Preserve direct-overlap and search-view refreshes, avoid selecting an
    unrelated view, and retain active-source/text-release restrictions.
