* Quasi-duplication: "Repo '...' not found in config" across ~9 sites (fixed 2026-11-22)
  The plan asked to consolidate the duplicated "repo not found"
  error into one 'RepoValidationError'. The recon found the
  duplication is wider than the three sites named (server/util.rs,
  dbs/filesystem/multiple_nodes.rs x2, plus copies in not_nodes.rs,
  git_ops/read_repo.rs, diff_analysis/snapshot.rs) -- ~9 literals of
  the same format string -- across three carrier types (io::Error,
  Result<_, String>, BufferValidationError). A clean consolidation
  needs an enum with both an ID-less 'NotInConfig(RepoName)' shape
  (the fs layer has no node id) and ID-bearing shapes, plus
  From-impls bridging to io::Error / Box<dyn Error>. I added typed
  fork-specific errors (ForkRepoUnresolved / ForkAlreadyExists /
  ForkRepoInactive on BufferValidationError) but DEFERRED the broad
  string consolidation -- it is a nice-to-have touching fs/git/diff
  layers, out of proportion to the fork work. Worth doing on its own.
  Fixed: 'SkgConfig::skgrepo_or_err' ('server/types/misc.rs') holds
  the message; the eight call sites in 'util.rs', 'git_ops/' and
  'dbs/filesystem/multiple_nodes.rs' call it. The typed error enum
  was not built. 'server/test_utils.rs' keeps its own copy, for a
  'get_mut'.
* A whole redraw rewrote every folded headline line of the live buffer (noted 2026-11-19; fixed 2026-11-19)
  Found measuring slow forks. When a save's answer, or any redraw,
  replaces the whole buffer ('skg-replace-buffer-with-new-content',
  as a fork's approving save often does),
  'skg-remove-folded-metadata' strips the 'folded' atom from each
  headline line in place, each rewrite running every modification
  hook (heralds' folder refresh, the org-element cache, link
  annotations), and then unfolds and refolds the buffer. In batch
  Emacs, on a 2,500-line view with 550 hidden headlines (the size of
  Jeff's view rooted at 7642d4d5), that is about 0.5 s of a fork's
  approved save; interactively it is likely more. Planned fix, as for
  the outbound snapshot ('skg--buffer-snapshot-with-save-metadata'):
  read the fold and focus atoms from the text, strip them from the
  string before inserting it, then fold by what was read.
  Fixed so: 'skg-replace-buffer-with-new-content' inserts the stripped
  form of the text in one piece and folds by the atoms the stripping
  removed ('skg--stripped-text-and-atom-headlines',
  'skg-fold-headlines-by-atoms'). It also no longer leaves a space
  after the metadata of a title-less headline that had an atom.
* A buffer that shows a forker as claiming nothing can undo a fork another view made (noted 2026-11-16; fixed 2026-11-16)
  Fixed by the review of every-mirror plan 2 (its probes 36 and 37):
  every view the refresh draws gives each member of a forks folder the
  claim the graph gives it ('claim_forks_folder_members_as_the_graph_does',
  'server/refresh/visit.rs'; 'docs/forks.org', "Claims in a redrawn
  view"), since a buffer the server redraws holds no gesture still to
  be saved. So a stale view another client saves, the view saved, and
  every collateral view show a forker the note now forks claiming, and
  can edit the note. The save-side patch that gave a forker made a
  forkee its claim in the saved view alone
  ('claim_forkers_the_save_makes_forkees') is gone.
  Still possible, and not the server's to tell apart from a
  detachment: text the client sends back itself. Undoing past a save
  and saving the old text again (plan 2 slice 6 found it: the
  pre-save text of N's view, where T claimed nothing, sent after the
  save that made T a mutual) ends the fork, as any detachment does;
  its baseline is the redrawn view, so the stale check sees an edit,
  not a stale buffer. The entry as it stood:
    Found by every-mirror plan 1 slice 6 (its record, "Unfinished"). In
    the forks folder a member that claims nothing is a forker the note
    does not fork. If another view makes the note fork it (a mutual), and
    this buffer still shows it claiming nothing, the clients read it as a
    pending detachment, and saving this buffer stops the fork. Whether the
    collateral rerender reaches this buffer first in every case is not
    checked. The cause is in 'mark_claims' ('server/refresh/visit.rs'):
    under an editable parent a child that claims nothing stays, since that
    is how a detachment the user wrote survives a refresh; nothing tells a
    member drawn claiming nothing because it was forker-only from one the
    user detached. (A related case, a content occurrence re-pointed to
    another mirror keeping the forks folder of the note it showed before,
    was fixed by the review of every-mirror plan 1: a re-pointed
    occurrence's folders are drawn afresh, 'redraw_folders'.)

   lets a viewnode stand in for a different graphnode than the one

* A redraw the user did not ask for undoes the folds changed since the last save (2026-11-13; fixed 2026-11-13)
  A view's fold state reaches the server only as the 'folded' and
  'bodyFolded' atoms of a save. A rerender after another writer's
  change ('rerender-view') or a save's collateral redraw of another
  view draws the folds of that view's last save, so any headline the
  user folded or unfolded since then reverts. Seen live on a scratch
  server, Emacs client: a headline folded after opening the view was
  unfolded by the redraw that followed a '.skg' change on disk.
  Fixed in the clients: before such a redraw replaces the buffer,
  each headline's fold state is recorded by viewnode ID, and decides
  the fold atoms of the new text, a headline's 'folded' by its new
  parent's state and its 'bodyFolded' by its own
  ('skg--content-with-fold-atoms', Neovim's 'content_with_fold_atoms');
  the server's atoms stand where the deciding headline is new.
