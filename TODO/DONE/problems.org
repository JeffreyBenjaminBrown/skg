* Architecture note: "drawn in place of another node" is override-specific data (noted 2026-06-10; fixed 2026-11-16)
  Fixed in every-mirror plan 1, slice 8: the part is '(inPlaceOf N)',
  the field 'in_place_of' on the occurrence, named for what it says (a
  viewnode drawn in place of another node), not for overrides. No reason
  enum was added: mirror substitution is still its one consumer. The
  entry as it stood:
   Override substitution (TODO/DONE/full-schema/
   11_override-rendering-and-navigation.org, executed 2026-06-11)
   lets a viewnode stand in for a different graphnode than the one
   whose ID it carries: the buffer draws overrider R where the
   container's contains list says N. The representation is
   'ViewNodeStats.overridesHere : Option<ID>' (and a parallel field
   on 'InactiveNode', for substitutes a skgrepo-set switch retains),
   carrying the original's ID -- data, not the earlier-planned
   bool-plus-convention, which was rejected 2026-06-11 because
   inverting the resolution at save time is ambiguous when one
   overrider stands for two members of the same parent. Save
   extraction, the content distinctness validators and the content
   reconciler's orderkey all read it through 'collected_id ()'.

   The name is override-specific. If a second substitution-like
   feature ever appears (redirects, merge previews, etc.), do not
   add a second marker field beside it; generalize this one (e.g.
   rename to 'drawn_in_place_of', adding a reason enum if consumers
   need distinguishing). Deferred until that second consumer exists
   (Jeff, 2026-06-10).

  Fixed in every-mirror plan 1, slice 5, when 'subscribesTo' and
  'overrides' became 'forks': 'find_related_nodes' now panics on an
  unknown (relation, input role, output role) triple, naming it. The
  entry as it stood:
  'find_related_nodes' in 'server/dbs/in_rust_graph/query.rs' takes
  the relation and roles as strings, and an unknown combination
  returns an empty set (the '_ => {}' arm). Renaming a relation left
  test calls passing a stale name, which showed up only as a confusing

  unknown triple) would make such mistakes loud.
* Override invariants are validated by two divergent implementations (noted during override-chains planning; obsolete 2026-11-16)
  Obsolete since every-mirror plan 1, slice 3: monogamy and the owned
  cycle check are gone, and the startup check and the save's check
  now run one per-note function ('violations_of_note' in
  'server/dbs/in_rust_graph/override_invariants.rs') over the whole
  graph and over the save's affected notes, so they cannot disagree.
  The entry as it stood:
   Monogamy (and, once
   [[../override-chains/1_plan.org][the override-chains plan]] lands,
   cycle-freedom) is checked in BOTH 'validate_override_invariants' (a
   full O(V) scan) and 'validate_touched_override_invariants' (an
   incremental O(touched) scan), in
   server/dbs/in_rust_graph/override_invariants.rs. They already hand-roll
   the same "follow owned overrider relationships, resolving extra-ids via
   'pid_of'" logic twice; adding cycle detection duplicates it a third and
   fourth time. A divergence (e.g. one resolves extra-ids, the other
   forgets) would let bad data through the fast save path and only catch it
   at the next rebuild. Opportunity: extract one shared primitive (e.g.
   'user_owned_override_cycle_through(pid)', or have the validators reuse
   'resolve_override''s seen-set/=cycle_detected=) so the save-time and
   init/rebuild gates cannot disagree. Pre-existing (monogamy is already
   duplicated); surfaced while planning override chains.
* A redraw the user did not ask for undoes the folds changed since the last save (2026-11-13; fixed 2026-11-13)
  A view's fold state reaches the server only as the 'folded' and
  'bodyFolded' atoms of a save. A rerender after another writer's
  change ('rerender-view') or a save's collateral redraw of another
  view draws the folds of that view's last save, so any headline the
  user folded or unfolded since then reverts. Seen live on a scratch
  server, Emacs client: a headline folded after opening the view was
  unfolded by the redraw that followed a '.skg' change on disk.
  Fixed in the clients: before such a redraw replaces the buffer,
  each headline's fold state is recorded by viewnode ID, and decides
  the fold atoms of the new text, a headline's 'folded' by its new
  parent's state and its 'bodyFolded' by its own
  ('skg--content-with-fold-atoms', Neovim's 'content_with_fold_atoms');
  the server's atoms stand where the deciding headline is new.
