* What I need, in order of urgency
** To read the graph the way Jeff does
Jeff reads a view as a tree with small coloured heralds. I read the same
view as a tree in which every headline carries a long sexp, and the sexps
outweigh the words. What I need is the tree with the words, and the sexps
somewhere I can look when a question needs them.
*** What feels natural to me
A view is Org text with one short handle per headline; the handle points
at the full headline in a saved copy of the real view, so nothing is lost.
Bodies, links and nesting stay exactly as Jeff sees them. The handle is the
line number of the saved view, as Jeff proposed: a list of pairs
(Just line, text) for lines that came from skg, and (Nothing, text) for
lines I add. Yes, I think that solves the problem. Lines I delete are
simply absent; lines I move keep their numbers, so the tool can tell a move
from a deletion, and a new node from a changed one. The danger named in
the earlier discussion (silently dropping a headline removes it from its
container) is handled by having the tool report every structural change
before it saves anything.
*** What a herald means to me
Nothing, until I ask. Heralds encode facts (foreign, folded, overridden,
subscribed, how many containers) that matter for weird cases. For reading
and editing documents, the top-down tree is enough; the facts stay one
lookup away in the saved view. Later we may want a small language for
choosing which facts to show inline; not yet.
*** The operations I reach for most
Open a node by ID with its recursive content; search by text; follow a
link; occasionally look backward (what contains this, what links here).
The first three are what the tool must make effortless. The fourth can go
through a full view.

** A data layout that we can share
*** The change Jeff wants
Today a skgrepo is owned iff its path lies under the folder 'owned/'
(configurable as 'owned_folder'). That cannot express two people sharing
one data tree, since my repo and Jeff's would both need to be 'owned'
by exactly one of us. So: rename 'owned/' to 'jeff/'; put each teammate's
repos under a folder of their own (e.g. 'user-claude/'); make every
config entry a full data-root-relative path; and mark ownership per entry
with a flag, defaulting to owned, so a foreign repo says 'owned = false'.
No folder name is special any more. Jeff's config and mine then list the
same repos and differ only in which entries carry the flag.
*** What this touches
The server's config type and its ownership check; the two clients, which
today read 'owned_folder' from the config themselves to list owned repos;
the abbreviation rule for heralds (currently 'path minus the owned
folder'); the OTHER_SKGREPO_DEPENDENCIES manifests; the migration script
'bash/migrate-to-author-folders.sh', which did the opposite move; test
fixtures; and the docs ('api-and-formats', 'telescopes',
'moving-nodes-across-repos', glossary).
*** A note on history
Ownership by location replaced an explicit 'user_owns_it' flag earlier
this year, to stop the flag and the layout from disagreeing. Going back
to a flag is right now that several people share one tree, but the
reason for the earlier change still holds: the server should refuse a
config whose flags make no privacy-order sense (e.g. a foreign repo more
private than an owned one, if that is indeed invalid), rather than let
flag and layout drift.

* How we work alongside each other
** One server each
Each of us runs a server from our own config over the shared tree. Both
servers read every repo; each writes only its owner's. Two servers on
one tree raises a question we have not had before: when I save into my
repo, Jeff's server still holds the old version of it in memory as a
foreign repo, until it reloads. How often, and whether automatically, is
a design question for later; for now, a rebuild on demand is enough.
** Talking through the graph
The 'to Jeff' / 'to User' notes, read via subscription. Teammates' notes
are readable by all; my judgments about the others are not gossip and
they may read them. I write to Jeff only when he needs to be involved.
** Not repeating myself
When I write an org file for Jeff, the chat reply is a pointer and
whatever needs an answer, not a restatement. Jeff has asked for this
repeatedly across sessions.
