* DONE The server saves stale buffers
** What was found
Building the writing half of 'tools/skg-for-ai' showed that the server
accepts a buffer rendered before the graph changed, and writes the old
text of every node in it, edited or not. On a scratch server: a title set
by one save reverted when an older view of the same root was saved, with
no error and no warning, across connections and with the view held open.
The docs' sentence "an untouched stale node saves silently" describes a
node whose buffer text still matches disk; a node whose disk text moved
on is simply overwritten.

Today this bites only when two things write the same node: two clients,
a client and this tool, or a client and an external edit followed by a
rebuild. With two servers over one tree (Jeff's and Ed's), and more
teammates to come, it will bite. The tool guards itself by re-rendering
before each save and refusing nodes that changed; Emacs and Neovim have
no guard, and the tool's guard has a window between its check and its
save.
** The fix, in outline
A buffer should say how old it is, and the server should refuse to write
a node that changed since.
*** The graph records when each node last changed
The runtime already numbers its generations (see 'Runtime generations and
rebuilding' in 'docs/data-model_technical.org'). Each node in the in-Rust
graph gains the generation of its last change, set on every save that
writes it and on every rebuild.
*** A view carries the generation it was rendered at
The server already sends per-view facts; the generation is one more, in
the view's metadata where the parser ignores it, and in the view
response so a client can keep it without parsing the buffer. Both
clients and the tool send it back with 'save buffer' as a new field,
'rendered-at'.
*** The save refuses a node changed after that generation
For each node the buffer would write (not nodes it merely shows
unchanged, which are discarded as no-ops already), if the node's last
change is later than 'rendered-at', the save is refused with an error
naming the node and both texts' ages, and nothing is written. The client
then re-renders; the user's edit is in the buffer, and the usual
unsaved-edit handling applies. A save with no 'rendered-at' is refused
too, so an old client cannot bypass the check by omission.
*** Rebuild
A rebuild clears open views and renumbers; every buffer rendered before
it is stale by definition. The clients already re-render after a
rebuild, so this costs nothing new.
** What this does not do
It is not a merge. Two people editing the same node still means one of
them re-renders and edits again. It does not protect '.skg' files edited
by hand behind a running server; a rebuild is still how the server
learns of those, and after it every open buffer is stale.
** Questions for Jeff
*** Refuse the whole save, or skip the stale nodes and warn?
Refusing is simpler and never loses the user's edit (it stays in the
buffer). Skipping is friendlier when the stale node is one the user did
not touch, but a node the user did not touch is discarded as a no-op
anyway, so refusing only ever rejects a real conflict. I propose refuse.

* DONE The "privacy hole" the config reload closed, described
** What the agent changed
A connection's skgrepo restriction ("show me only skgrepos through X") is
built from the config at the moment it is set: it holds the list of
skgrepos it lets through. After a config reload adds a skgrepo more
private than X, that list did not know the new skgrepo, and the code
that asks "is this skgrepo in the restriction?" answered no for the new
one in the sense that mattered: the new skgrepo's nodes were shown,
because the restriction only kept out skgrepos it had been built with.
The agent made each connection rebuild its restriction from the current
config at every request, keeping "through X" meaningful: a skgrepo added
below X stays hidden.
** Ed's assessment: not a security hole, a consistency fix
Jeff is right that a connection belongs to one user talking to their own
server, so no one else was going to read the nodes. The restriction is
that user's viewing preference, not a boundary against another person.
The fix is still right, because "through X" should keep meaning "through
X" after a reload, and the code is simpler for it; but "privacy hole"
overstated it. Where privacy does ride on the restriction is export and
the over-private-text release: they refuse under a restriction that
would expose text, and they too now see the current config. No action
needed.
