***** Jeff : Ed's answer: not polling, and cheap
On Linux the kernel offers 'inotify': a program registers interest in a
directory, then sleeps on a file descriptor; the kernel wakes it with an
event (created, modified, deleted, renamed) whenever something touches
that directory. No polling: zero cost while nothing changes, and a few
microseconds per event. One watch per directory, so one per skgrepo;
the kernel caps watches per user in the tens of thousands, far above
our needs. macOS (FSEvents) and Windows (ReadDirectoryChangesW) do the
same; the Rust crate 'notify' wraps all three and falls back to polling
only on network filesystems, where no kernel can tell. Our data root is
a Docker bind mount on the same Linux kernel, so events from your
editor outside the container reach a server inside it.

The cost that matters is not watching but reacting: a 'git pull' of a
hundred files produces a hundred events, and the server must not rebuild
a hundred times. The usual answer is to debounce, gathering events until
the directory has been quiet for, say, half a second, then integrating
the whole batch once. A file still being written shows up as a size
change; the quiet period handles that too.
