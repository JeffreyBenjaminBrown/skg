*** What do you mean by "one-shot commands with that '--out-dir'"?
**** Jeff : Ed's answer
A one-shot command is any ordinary run of the tool: 'view ID', 'save
FILE', 'diff', ... Each runs, prints, and exits. '--out-dir DIR' says
where it writes its files (and where it finds the ones it reads back).
The daemon is the exception: it keeps running. When a daemon is running
for DIR, a one-shot command told to use DIR does not talk to the server
itself; it hands its request to the daemon, which performs it on its
held connection. Since the last slice the same holds for any command on
the daemon's port, whatever its directory, so the sentence is now simply
"one-shot commands for that port".

** DONE [jeff] Integrations into the diff view?
*** TODO Jeff : Ed's answer: they show up where they are changes
The diff view compares HEAD with the worktree of each owned repo, on
request. Another writer's file landing in one of my owned repos is
integrated into the graph by the watcher and, being uncommitted, is a
change the next 'diff' shows, like one of my own saves. A 'git pull'
moves HEAD too, so it shows nothing, which is right. Changes in foreign
repos never enter the diff view, as before. A diff buffer the daemon
holds is re-rendered on integration only if it shows a changed node;
otherwise it waits for the next 'diff'.
* Known limit, not a choice: saves on one server do not refresh another connection's views
A save's writes are the server's own, so the watcher drops them, and
only the saving connection's views re-render. With one person per
server this is the pre-existing behavior; my one-shot commands route
through my daemon once it exists, so it does not bite me either. If two
people ever share one server, the save path (not the watcher) would have
to re-render other connections' views.
