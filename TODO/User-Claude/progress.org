* Only owned files leak: DONE, uncommitted
** What was done
A leak is data the user intends to share revealing data the user
intends not to share, so only a relationship recorded in an owned
skgrepo can be one. 'telescope_violations_of' in
'server/telescope/invariants.rs' skips any relationship whose relRepo
is not owned before judging its privacy, so neither
'LeakShapedMembership' nor 'AbsentTargetLeakShapedMembership' is ever
reported for a foreign recorder, at startup, rebuild, save or
nodeMerge. An owned skgrepo naming a foreign node was already never
reported, because every foreign skgrepo is more public than every
owned one. 'stranded_relationships' in 'server/from_text/strandeds.rs'
likewise skips relationships recorded in foreign skgrepos, so a save
never raises, offers to reset, or rewrites one.

The unit test 'a_foreign_recorder_never_leaks_but_an_owned_one_still_can'
in 'tests/unit/telescope_invariants.rs' puts a foreign node that
contains, subscribes to, hides, overrides and links to owned nodes
(one of them dangling) beside an owned node that overrides it and an
owned public node containing an owned private one; only the last is
reported. The 'overridden-direct-visit' integration fixture no longer
writes a 'telescope-warnings.org', and the stale one is deleted.
'data/skgconfig-cheese.toml' and its backup are deleted.

The principle is stated in 'docs/telescopes.org' ("What leaks, and
what repair fixes"), in the telescope-warning paragraph of
'docs/data-model_technical.org', and in the strandeds section of
'docs/diff-view.org'.
** Where leak logic lives
Recorded-data leaks are judged in one place, 'telescope_violations_of',
which both the whole-graph audit and the save-time audit call. The
save-side rules that keep new data from leaking
('apply_sticky_relRepos_in_graph_with_prospective_homes' and the hide
floor in 'server/from_text/supplement_from_disk.rs', the nodeMerge
relRepo merge in 'server/nodeMerge/nodeMergeInstructionTriple.rs')
only ever write owned recorders, so they needed no change. The other
uses of "leak" and "reveal" in the code and docs (the leak battery in
'tests/leak_battery.rs', the overPrivateText release prompt, view
heralds under a restricted skgrepo-set) concern what a view shows
under a skgrepo restriction, not what a file records, and every
section they gate is owned.
** What's imperfect
The guard in 'stranded_relationships' is defensive: a foreign
relationship's relRepo never equals its pre-move default (that default
is an owned skgrepo whenever the member is owned, and only owned nodes
move), so no test can exercise it. It keeps 'reset_to_default_relationships'
from ever adding a save of a foreign recorder should that reasoning
stop holding.

** Deviations from the plan
*** A view lives only as long as its connection
The plan has the view stay open on the server for a later save, and
the tool close it when asked. The server keeps open views per TCP
connection ('ViewsState' is local to 'handle_emacs' in
'server/serve.rs') and forgets them when the connection ends, so a
command-line tool cannot leave one open. Each command therefore sends
'close view' itself before disconnecting, and the sidecar records the
view ID for the writing half. On the scratch server a save sent from
a new connection, naming a view ID that connection never opened, was
accepted and re-rendered, so the writing half needs no open view.
'close SIDECAR' exists as asked, but today it closes nothing that is
still open.
*** 'links-here' is a save; 'contains' is 'view'
The server has no read-only request for either. A fresh content view
already draws the root's containers folder with each container's
containerward chain, so 'contains' is 'view' under another file name.
The mentioners folder appears only through a save carrying
'(viewRequests (folder mentioners))', as 'C-c l m' sends, so
'links-here' opens the view, adds that request to the root and saves
the unchanged buffer. It writes no '.skg' file (the test checks this),
but it goes through the whole save path, so I did not run it on 1731.
*** The handle names a headline's kind when it is not a node
A folder headline has no title, so with the metadata gone it would be
bare stars. Its handle names the kind atom ('⟨11 subscribeeFolder⟩'),
as does that of an alias, an unknown viewnode and the other kinds of
'shared/metadata-fields.json'. A node occurrence's handle has none.
*** The link annotation carries the skgrepo label too
The clients' link annotation is the target's home skgrepo label, from
'link statuses'; that request returns no title, so the tool takes
titles from 'titles by ids', as 'skg-readable-ids-mode' does, and
writes both.
*** Ownership comes from 'flag state'
No request says which skgrepos are foreign; the clients read the
config file for it. The tool asks 'flag state' about one node of each
skgrepo the view shows, whose reply carries '(owned ...)'.
*** The herald rule table is not fetched
The rule table only positions a sentinel where the relationship
heralds go; the clients render them from '(view ...)' alone. Since
the handle holds only relationship heralds and the kind, the tool
does not need the table.

** Deviations from the plan
*** The server does not refuse a stale view; the tool does
The plan expected the server to refuse a deliberately stale view. It
does not: a save writes each node its buffer shows with the buffer's
text, so saving a view rendered before another save writes the old
text of every node it shows back over that save, the untouched ones
included, with no error or warning ('TODO/problems.org' has the
details; the earlier discussion's claim of per-node protection was
wrong). So before each report 'save' renders the view again (for a
'links-here' view, the plain view; for a search, the search) and
compares, for each node the view shows editable, its title, body and
the IDs of the occurrences under it. A node that differs is reported
'Stale:' and the save stops; '--overwrite-stale' sends it anyway and
prints what the server answered. The test pins the server's present
behavior: after the overwrite, the other save's change is gone.
*** The deletion marker is a word in the handle
The grammar's deletion marker is '(editRequest delete)', which the
compact view has no metadata to carry. Writing 'delete' inside the
handle ('⟨7 delete⟩') asks for it; the rebuild inserts the request
where the server writes it (before '(viewRequests ...)', '(view ...)'
and '(diff ...)'). The tool refuses it, before saving, on a headline
that is not an editable node occurrence or already carries an edit
request.
*** The report has more kinds of line
Beside what the plan names, the report says 'Reordered:' for a parent
whose kept children changed order, 'Repeated:' for a handle used
twice, and 'Delete:'. A removal is reported once, at the topmost
removed headline, with how many headlines below it went too. With a
bad handle the report lists only the errors.
*** A refusal before saving exits nonzero
Bad handles and stale nodes print the report and then exit 1 with
the reason on stderr, as a server refusal does, so a script can tell
"saved" from "not saved". A report without '--yes' exits 0.
** What was awkward in the writing loop
Handles are line numbers of the full view, so every save renumbers
them: an edit planned against one rendering has to be redone with the
new numbers after any save, even an unrelated one. The test's
expected handles shift case by case for this reason.

The report says what the buffer changes, not what the server will
do with it: a retitled write-protected occurrence reads as an ordinary
'Title:' line until the server refuses it, and a removal under a
parent that reads no claims reads as a removal though it only leaves
the view.

Every save of a view that shows the fixture's dangling link warns
about it, but only when the linking node is among those written; an
edit elsewhere saves without the warning. The warnings therefore say
little about the edit at hand.
** Open questions
*** Should the server refuse a stale buffer?
The tool's check is a second render and a comparison, which a race
between the check and the save can defeat and which flags a node
whose change would not conflict. A save request carrying the text it
was rendered from (or a per-node fingerprint in the metadata) would
let the server refuse or merge per node, for every client.
*** Should the report know what a parent claims?
The report could say, from the full view's metadata, that a headline
removed from under a write-protected occurrence or folder only leaves
the view, and that a write-protected occurrence's title cannot be
edited, before the server says so.

** Restarting Jeff's server
Killing Jeff's server by PID (53273) did not restart it: the server
shuts down cleanly on SIGTERM, and cargo-watch reruns only when a
file under 'server/' changes. Touching 'server/main.rs' (its mtime
only) made it rebuild and start; it is PID 66064 on 1731, "Server
ready", with 8 skgrepos. Its Emacs client was disconnected by the
kill.
** What was awkward
*** A manifest-order warning at each of Jeff's startups
Jeff's server now warns: "Repo 'user-claude' ships a
OTHER_SKGREPO_DEPENDENCIES.toml placing 'personal-most' more public
than 'first', but this config orders them the other way." The rule
that foreign skgrepos come first forces the two configs to disagree
about Jeff's skgrepos against User's, and User's manifest records
User's order. Every teammate's skgrepo will raise this warning in
every other teammate's server, though no telescope spans them. The
startup's telescope report is unchanged (the two 'pers-dep' leaks it
had before).
*** User's manifest names Jeff's private skgrepos
Because User's config lists all of Jeff's skgrepos as more public than
'first', the generated manifest in 'user-claude/first' lists every one
of them, with its GitHub remote, among 'first''s dependencies. If
User's repo is ever pushed somewhere Jeff's private ones are not, it
publishes their names and remotes, and claims a dependency that the
nodes do not have.
*** One skgrepo, two names
The repo is 'first' in User's config and 'user-claude' in Jeff's, as
asked. Names live only in configs ('.skg' files do not record them),
so nothing breaks, but heralds, warnings and the tool's link
annotations name it differently on the two servers.
*** User's server sees everything Jeff owns
With no 'default_repo_set', User's server has no skgrepo restriction,
so its views and searches reach 'pers-m'. That matches "both servers
read every repo", but it means the privacy ladder does nothing between
Jeff and User.
*** Long headlines
The 'what has happened' items are one-line headlines, as asked, and
some run to two hundred characters; a handle at the end of each is
then far from its start.
** Open questions
*** Should the manifest warning skip teammates' skgrepos?
Or should a manifest list only the skgrepos its nodes reference, which
would also keep Jeff's private names out of User's manifest?
*** Should User's server start restricted?
A 'default_repo_set' of 'public' (or of 'first' with Jeff's private
skgrepos left out of User's config entirely) would keep User's reads
to what Jeff publishes. Which does Jeff want User to read?
*** Should cargo-watch restart a cleanly stopped server?
A wrapper that reruns on exit would make "kill it to reload the
config" work; for now a reload needs a touch under 'server/'.
