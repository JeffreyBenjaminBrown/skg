* Ownership becomes a per-repo flag: DONE, uncommitted
** What was done
A '[[repos]]' entry is owned unless it says 'foreign = true'
('SkgrepoToml.foreign'). 'owned_folder' is gone from 'SkgConfig' and
rejected like 'user_owns_it', whose message now names the flag. The
loader refuses a config in which a foreign repo is not strictly more
public than every owned one, naming both
('validate_foreign_skgrepos_more_public_than_owned' in
'server/dbs/filesystem/not_nodes.rs'). 'derive_ownership_and_labels'
became 'derive_default_abbreviations': an owned repo with a defaulted
name abbreviates to its path below the data root minus the first
component. Three tests in 'tests/repo_path_validation.rs' cover the
flag and the abbreviation, the refusal, and the retired key.

Emacs, Neovim and 'data/bash/lib.sh' read the flag. The new
'bash/migrate-to-foreign-flag.sh' replaces
'bash/migrate-to-author-folders.sh'. The docs the plan names, the
verify skill and 'example-data/' (now 'me/' plus a foreign
'fred/public' listed first) follow the new layout.

In 'data/': 'owned/' is now 'jeff/', all three configs were migrated,
'data/mr-cheese/' is deleted (its 'private' repo had four uncommitted
changes, which are gone with it), and the 'Mr Cheese' entry is out of
'skgconfig-jeff.toml', which 'skgconfig.toml' links to. The main
server restarted on the new config ("Server ready"); its telescope
warnings went from 16 to 2.
** Deviations from the plan
*** Fixtures were reordered as well as flagged
Nearly every test config with a foreign repo listed it last, which
the new check refuses. Each one now lists its foreign repos first,
with 'foreign = true'. That includes the inline configs in Rust tests
and the integration 'run-test.sh' files. All suites pass on the new
order. Configs that were entirely foreign by location
('link-annotations', 'subscribee_heralds') got the flag so they keep
their meaning.
*** The privacy order now includes unnamed repos
'skgrepo_order_from_toml' used to skip an entry without 'name', so
such a repo was missing from the privacy order and counted as
infinitely private. The new check would have refused every unnamed
foreign repo for that reason, so an unnamed entry is now ordered
under its path, matching how it is named.
*** The migration script decides idempotency from three signs
A config gets rewritten if it sets 'owned_folder', if some path lies
under the owned folder, or if that folder still exists. A config that
owned nothing, run after the folder was renamed, looks the same as an
already-migrated config where everything is owned. The script warns
in that case. It also warns when the result lists a foreign repo after
an owned one, and it keeps a 'default_repo_set' that names a moved
unnamed repo pointing at it. Because of the first rule I ran it on
'skgconfig-cheese.toml' first, before the folder was renamed.
** What's imperfect

fixture, where the foreign 'Cheese' overrides an owned node. The test
passes, but the server now writes a 'telescope-warnings.org' there.
The same thing will happen when User's repo, foreign to Jeff, links
to Jeff's public nodes.
*** Generated files in tracked fixtures changed
Running the integration suite regenerated the
'OTHER_SKGREPO_DEPENDENCIES.toml' manifests and the

* Only owned files leak: DONE, uncommitted
** What was done
A leak is data the user intends to share revealing data the user
intends not to share, so only a relationship recorded in an owned
skgrepo can be one. 'telescope_violations_of' in
'server/telescope/invariants.rs' skips any relationship whose relRepo
is not owned before judging its privacy, so neither
'LeakShapedMembership' nor 'AbsentTargetLeakShapedMembership' is ever
reported for a foreign recorder, at startup, rebuild, save or
nodeMerge. An owned skgrepo naming a foreign node was already never
reported, because every foreign skgrepo is more public than every
owned one. 'stranded_relationships' in 'server/from_text/strandeds.rs'
likewise skips relationships recorded in foreign skgrepos, so a save
never raises, offers to reset, or rewrites one.

The unit test 'a_foreign_recorder_never_leaks_but_an_owned_one_still_can'
in 'tests/unit/telescope_invariants.rs' puts a foreign node that
contains, subscribes to, hides, overrides and links to owned nodes
(one of them dangling) beside an owned node that overrides it and an
owned public node containing an owned private one; only the last is
reported. The 'overridden-direct-visit' integration fixture no longer
writes a 'telescope-warnings.org', and the stale one is deleted.
'data/skgconfig-cheese.toml' and its backup are deleted.

The principle is stated in 'docs/telescopes.org' ("What leaks, and
what repair fixes"), in the telescope-warning paragraph of
'docs/data-model_technical.org', and in the strandeds section of
'docs/diff-view.org'.
** Where leak logic lives
Recorded-data leaks are judged in one place, 'telescope_violations_of',
which both the whole-graph audit and the save-time audit call. The
save-side rules that keep new data from leaking
('apply_sticky_relRepos_in_graph_with_prospective_homes' and the hide
floor in 'server/from_text/supplement_from_disk.rs', the nodeMerge
relRepo merge in 'server/nodeMerge/nodeMergeInstructionTriple.rs')
only ever write owned recorders, so they needed no change. The other
uses of "leak" and "reveal" in the code and docs (the leak battery in
'tests/leak_battery.rs', the overPrivateText release prompt, view
heralds under a restricted skgrepo-set) concern what a view shows
under a skgrepo restriction, not what a file records, and every
section they gate is owned.
** What's imperfect
The guard in 'stranded_relationships' is defensive: a foreign
relationship's relRepo never equals its pre-move default (that default
is an owned skgrepo whenever the member is owned, and only owned nodes
move), so no test can exercise it. It keeps 'reset_to_default_relationships'
from ever adding a save of a foreign recorder should that reasoning
stop holding.
* tools/skg-for-ai, reading: DONE, uncommitted
** What was done
'tools/skg-for-ai/skg_for_ai.py' (standard library only) talks to a
running server and, for a view, writes 'BASE.full.org' (the server's
text, unchanged), 'BASE.compact.org' and the sidecar 'BASE.view.json'
(view ID, request, port, the server's errors and warnings). The
compact view keeps every line in order; a headline loses its metadata
and gains a handle '⟨N KIND HERALDS⟩' at its end, N its line in the
full view; every '[[id:...]]' link, in titles and bodies, is followed
by '⟦→ TITLE ⌂:LABEL⟧', '⟦✗ missing⟧' or '⟦✗ restricted⟧'. A summary
of Org comment lines precedes the tree unless '--no-summary' is given.
The commands are 'view', 'search', 'links-here', 'contains' and
'close'; the port is 'SKG_PORT' or '--port'. 'README.org' beside it is
written for anyone.

The relationship heralds mirror 'render_rel_facts' in
'nvim/lua/skg/heralds.lua', styles dropped, reading the letters and
their order from 'shared/relations.json'. The test checks them
against the 32 cases of 'tests/shared/herald-rendering-cases.txt'
whose text is only relationship and property tokens, the cases both
clients' tests read.

'python3 tools/skg-for-ai/test_skg_for_ai.py' passes. It copies
'tools/skg-for-ai/test-fixture/' (a foreign 'fred' listed first, an
owned 'main', a folded node, a node with two containers, a
subscription, a dangling link and a link into the foreign repo) to a
temporary data root, starts a server on port 1793, runs four commands
and compares each compact view, summary included, with
'tools/skg-for-ai/test-expected/'. It also checks each handle's line
number, and that no '.skg' file changed. 'cargo check --all-targets'
is clean; no Rust, client or doc outside 'tools/skg-for-ai/' changed.

The live run on 1731 used 'view' on 703f5a82-d948-431f-985c-4db8132bc504,
'search AI team' and 'close', plus the read-only lookups the tool
makes ('link statuses', 'titles by ids', 'flag state').
** Deviations from the plan
*** A view lives only as long as its connection
The plan has the view stay open on the server for a later save, and
the tool close it when asked. The server keeps open views per TCP
connection ('ViewsState' is local to 'handle_emacs' in
'server/serve.rs') and forgets them when the connection ends, so a
command-line tool cannot leave one open. Each command therefore sends
'close view' itself before disconnecting, and the sidecar records the
view ID for the writing half. On the scratch server a save sent from
a new connection, naming a view ID that connection never opened, was
accepted and re-rendered, so the writing half needs no open view.
'close SIDECAR' exists as asked, but today it closes nothing that is
still open.
*** 'links-here' is a save; 'contains' is 'view'
The server has no read-only request for either. A fresh content view
already draws the root's containers folder with each container's
containerward chain, so 'contains' is 'view' under another file name.
The mentioners folder appears only through a save carrying
'(viewRequests (folder mentioners))', as 'C-c l m' sends, so
'links-here' opens the view, adds that request to the root and saves
the unchanged buffer. It writes no '.skg' file (the test checks this),
but it goes through the whole save path, so I did not run it on 1731.
*** The handle names a headline's kind when it is not a node
A folder headline has no title, so with the metadata gone it would be
bare stars. Its handle names the kind atom ('⟨11 subscribeeFolder⟩'),
as does that of an alias, an unknown viewnode and the other kinds of
'shared/metadata-fields.json'. A node occurrence's handle has none.
*** The link annotation carries the skgrepo label too
The clients' link annotation is the target's home skgrepo label, from
'link statuses'; that request returns no title, so the tool takes
titles from 'titles by ids', as 'skg-readable-ids-mode' does, and
writes both.
*** Ownership comes from 'flag state'
No request says which skgrepos are foreign; the clients read the
config file for it. The tool asks 'flag state' about one node of each
skgrepo the view shows, whose reply carries '(owned ...)'.
*** The herald rule table is not fetched
The rule table only positions a sentinel where the relationship
heralds go; the clients render them from '(view ...)' alone. Since
the handle holds only relationship heralds and the kind, the tool
does not need the table.
*** The summary has a few more lines
Beside the counts the plan names, it names the full file and view ID,
counts the headlines by kind and the node occurrences per skgrepo
with their ownership, and counts the server's errors and warnings. "Has
other containers" is computed as a 'contains' in-side larger than its
ancestor flags, and is written "Contained elsewhere too".
** Reading the live view
The compact view of "AI team for Skg" is 277 lines against the full
view's 269 long ones, and it reads as a document: the words dominate
and each handle is short. The link annotations helped most: "[[id:
...][here]]⟦→ AI team for Skg ⌂:public⟧" said at once that a body

not.

Folded headlines are invisible in the compact view except in the
summary's count. In 'search AI team' (736 headlines, 182 folded) the
hits are the level-1 headlines and everything under them is collapsed

Nothing tells me whether a node shows all its content. A 'C6' with six

** Open questions
*** A read-only request for backward views
Should the single-root view request accept view requests, such as
'(folder mentioners)', so that "what links here" needs no save? Then
'links-here' could run against any server without going through the
save path, and 'contains' could ask for the containers folder alone.
*** Ownership over the protocol
Should 'herald rules' (or another request) report each skgrepo's
ownership beside its label? Both clients and this tool each find it
another way.
*** Saving a view another connection opened
A save naming a view ID its connection never opened is accepted. Is
that intended, and does the save's stale-view protection still hold
for a buffer rendered on another connection? The writing half depends
on the answer.
*** Quieter handles
Should the handle omit a side that the occurrence's birth fully
explains (the bare 'aC' of ordinary content, which the clients style
low), or the whole token when nothing else remains? It would be the
tool's first departure from the clients' text.
*** What 'contains' should show
Should 'contains ID' write only the root and its containers folder,
rather than the whole content view? For a large node the containers
are lost below its content. The compact-view rule that every line of
the full view appears would then hold for a narrower full view.
* A 'repos' request, the unknown-ID view, one protocol client: DONE, uncommitted
** The 'repos' request
'((request . "repos"))' answers '((response-type repos) (restriction
"NAME") (repos ((name "N") (path "P") (abbreviation "A") (owned
"true")) ...))': every configured skgrepo in privacy order, and the
connection's skgrepo restriction. The handler is
'server/serve/handlers/repos.rs', its unit tests 'tests/unit/repos.rs';
the API doc has a "Repos" section after "Flag state". The tool's
summary takes ownership from it instead of asking 'flag state' about
one node per skgrepo.

The config loader makes every skgrepo path absolute and keeps no copy
of the path as written, so the response gives a path below the data
root relative to it and any other absolutely. A config that writes an
absolute path below the data root is therefore reported relative.
Keeping the written path would mean a new field on 'Skgrepo', which
some 86 constructors build.
** Viewing an unknown ID
The empty view is the intended behavior: an unknown viewnode stands
for an ID its viewparent's list names, no list names a root, so the ID
rule makes the root a tombstone and the refresh prunes it. The API
doc's "Single-root content view from ID" now says so, and that a
skgrepo restriction refuses such a request instead. The verify
skill's probe says what to expect. The server is unchanged.
** One protocol client
'.claude/skills/verify/skg_client.py' is deleted, and the skill's
"Speaking the protocol" calls the tool. The tool gained 'raw REQUEST'
(prints every response until the server is quiet for three seconds),
'raw REQUEST --saved-buffer FILE' (sends FILE as a save's body and
reads to the terminal response; the skill's 'save' mode needed a
home, and the task named only view, search, raw and import), and
'import INPUT_DIR REPO' (preview and apply on one connection, a blank
host root if asked; '--preview-only' cancels instead). Its test now
also runs 'raw' on 'repos' and an 'import' against the scratch server.
The README says plainly that the tool may save and import, as any
client may.
