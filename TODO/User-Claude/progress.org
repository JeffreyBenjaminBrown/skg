* Only owned files leak: DONE, uncommitted
** What was done
A leak is data the user intends to share revealing data the user
intends not to share, so only a relationship recorded in an owned
skgrepo can be one. 'telescope_violations_of' in
'server/telescope/invariants.rs' skips any relationship whose relRepo
is not owned before judging its privacy, so neither
'LeakShapedMembership' nor 'AbsentTargetLeakShapedMembership' is ever
reported for a foreign recorder, at startup, rebuild, save or
nodeMerge. An owned skgrepo naming a foreign node was already never
reported, because every foreign skgrepo is more public than every
owned one. 'stranded_relationships' in 'server/from_text/strandeds.rs'
likewise skips relationships recorded in foreign skgrepos, so a save
never raises, offers to reset, or rewrites one.

The unit test 'a_foreign_recorder_never_leaks_but_an_owned_one_still_can'
in 'tests/unit/telescope_invariants.rs' puts a foreign node that
contains, subscribes to, hides, overrides and links to owned nodes
(one of them dangling) beside an owned node that overrides it and an
owned public node containing an owned private one; only the last is
reported. The 'overridden-direct-visit' integration fixture no longer
writes a 'telescope-warnings.org', and the stale one is deleted.
'data/skgconfig-cheese.toml' and its backup are deleted.

The principle is stated in 'docs/telescopes.org' ("What leaks, and
what repair fixes"), in the telescope-warning paragraph of
'docs/data-model_technical.org', and in the strandeds section of
'docs/diff-view.org'.
** Where leak logic lives
Recorded-data leaks are judged in one place, 'telescope_violations_of',
which both the whole-graph audit and the save-time audit call. The
save-side rules that keep new data from leaking
('apply_sticky_relRepos_in_graph_with_prospective_homes' and the hide

relRepo merge in 'server/nodeMerge/nodeMergeInstructionTriple.rs')

'tests/leak_battery.rs', the overPrivateText release prompt, view

under a skgrepo restriction, not what a file records, and every

** Deviations from the plan
*** A view lives only as long as its connection
The plan has the view stay open on the server for a later save, and
the tool close it when asked. The server keeps open views per TCP
connection ('ViewsState' is local to 'handle_emacs' in
'server/serve.rs') and forgets them when the connection ends, so a
command-line tool cannot leave one open. Each command therefore sends

view ID for the writing half. On the scratch server a save sent from

accepted and re-rendered, so the writing half needs no open view.
'close SIDECAR' exists as asked, but today it closes nothing that is
still open.
*** 'links-here' is a save; 'contains' is 'view'
The server has no read-only request for either. A fresh content view
already draws the root's containers folder with each container's
containerward chain, so 'contains' is 'view' under another file name.
The mentioners folder appears only through a save carrying
'(viewRequests (folder mentioners))', as 'C-c l m' sends, so
'links-here' opens the view, adds that request to the root and saves
the unchanged buffer. It writes no '.skg' file (the test checks this),
but it goes through the whole save path, so I did not run it on 1731.
*** The handle names a headline's kind when it is not a node
A folder headline has no title, so with the metadata gone it would be
bare stars. Its handle names the kind atom ('⟨11 subscribeeFolder⟩'),

'shared/metadata-fields.json'. A node occurrence's handle has none.
*** The link annotation carries the skgrepo label too
The clients' link annotation is the target's home skgrepo label, from
'link statuses'; that request returns no title, so the tool takes
titles from 'titles by ids', as 'skg-readable-ids-mode' does, and

** Deviations from the plan
*** The server does not refuse a stale view; the tool does
The plan expected the server to refuse a deliberately stale view. It
does not: a save writes each node its buffer shows with the buffer's
text, so saving a view rendered before another save writes the old
text of every node it shows back over that save, the untouched ones
included, with no error or warning ('TODO/problems.org' has the
details; the earlier discussion's claim of per-node protection was
wrong). So before each report 'save' renders the view again (for a
'links-here' view, the plain view; for a search, the search) and
compares, for each node the view shows editable, its title, body and
the IDs of the occurrences under it. A node that differs is reported
'Stale:' and the save stops; '--overwrite-stale' sends it anyway and
prints what the server answered. The test pins the server's present
behavior: after the overwrite, the other save's change is gone.
*** The deletion marker is a word in the handle
The grammar's deletion marker is '(editRequest delete)', which the
compact view has no metadata to carry. Writing 'delete' inside the
handle ('⟨7 delete⟩') asks for it; the rebuild inserts the request
where the server writes it (before '(viewRequests ...)', '(view ...)'
and '(diff ...)'). The tool refuses it, before saving, on a headline
that is not an editable node occurrence or already carries an edit
request.
*** The report has more kinds of line
Beside what the plan names, the report says 'Reordered:' for a parent
whose kept children changed order, 'Repeated:' for a handle used
twice, and 'Delete:'. A removal is reported once, at the topmost
removed headline, with how many headlines below it went too. With a
bad handle the report lists only the errors.
*** A refusal before saving exits nonzero
Bad handles and stale nodes print the report and then exit 1 with
the reason on stderr, as a server refusal does, so a script can tell
"saved" from "not saved". A report without '--yes' exits 0.
** What was awkward in the writing loop
Handles are line numbers of the full view, so every save renumbers
them: an edit planned against one rendering has to be redone with the
new numbers after any save, even an unrelated one. The test's
expected handles shift case by case for this reason.

The report says what the buffer changes, not what the server will
do with it: a retitled write-protected occurrence reads as an ordinary
'Title:' line until the server refuses it, and a removal under a
parent that reads no claims reads as a removal though it only leaves
the view.

Every save of a view that shows the fixture's dangling link warns
about it, but only when the linking node is among those written; an
edit elsewhere saves without the warning. The warnings therefore say
little about the edit at hand.

'titles_probably_reworded' and 'title_similarity', over
'normalized_title_words' and 'crude_stem'. A new headline and a
removed one with different titles are probably the same statement when

pair either of whose headlines is already paired; each pair keeps the
other removed headlines its new headline resembles, which the question
names. Each pair is a 'Question:' line after the change lines:
"Question: removed ⟨ID⟩ 'X' / new 'Y' (line N): probably the same
statement reworded; keep its ID?", plus "Its title also resembles ..."
when there are others.
*** The answers

and '--all-new' (each is a new node), mutually exclusive, both needing

** Deviations
*** The stemmer is a little less crude than asked

*** The ratio is loose on short titles

** What was done
*** The command
'skg_for_ai.py daemon --out-dir DIR [--port P]' ('SkgForAiDaemon' in
'tools/skg-for-ai/skg_for_ai.py') opens one connection
('DaemonConnection', a subclass of 'SkgConnection'), logs the
server's startup warnings, and listens on 'DIR/skg-for-ai.sock'. The
socket is bound under a temporary name from inside DIR and renamed, so
it exists only once it listens, and a long DIR path does not hit the
Unix-socket path limit (clients connect from inside DIR too). It runs
in the foreground until 'daemon --stop --out-dir DIR', SIGTERM or
SIGINT, then closes every held view (marking each sidecar closed), its
connection and its socket. A socket that refuses connection is a dead
daemon's: commands then run on their own, and the next daemon removes
it and logs so; a socket that answers refuses a second daemon. A lost
server connection (closed, or a response cut off) stops the daemon,
since the server forgot its views.
*** Routing
'main' parses the command line, then 'exit_code_of_command_sent_to_daemon'
looks for a socket in the command's folder: '--out-dir' for the view
commands and 'new', the sidecar's folder for 'save', 'integrate' and
'close'. It sends '{argv, cwd}' as JSON, half-closes, and prints the
daemon's '{stdout, stderr, exit_code}'. The daemon runs the same
'run_command' in the sender's cwd with stdout and stderr captured, one
command at a time. 'connect_to_server' hands a command the daemon's
connection when its port is the daemon's; a routed command takes the
daemon's port unless its argv names '--port'. 'raw', 'import' and
'commit' have no folder and never route.
*** Held views
'write_view_files' asks the connection whether it holds what it
writes; the daemon's holds everything written into DIR, so the
sidecar says '"closed": false', and 'release_view' skips the 'close
view' a one-shot command sends. A view ID maps to one base name: a
later view under the same ID releases the earlier files (sidecar
closed, a save of them then runs on its own connection,
'connection_for_saved_view'), and a later view written over the same
files closes the earlier view ID (a second 'diff'). Asking a held
view ID again gets '(switch-to-view ID)' from the server, so
'fetch_single_root_view' first closes a held one. Saves through the
daemon are ordinary held-view saves; the diff-view buffer kind is
still sent, and the server keeps the registered kind. An unheld save
on the daemon's connection (after 'close') registers the view again,
and the daemon holds it again.
*** Rerenders and the log
'read_message' hands unprompted messages to
'handle_unprompted_message' and every other message to
'observe_message'. On the daemon's connection both queue
('waiting_messages'): 'repo-files-integrated', and every
'collateral-view' and 'rerender-view' with the cause in force when it
was read. Between commands the daemon selects on the server socket
and its listener, and drains the queue: for 'repo-files-integrated'
it logs each warning and sends "rerender all views" excluding every
held view but the clean ones named (as the clients do); each
rerendered view is written over its three files and logged with what
changed, node by node (new, gone, title/body/metadata), compared with
the old full view. The rerenders a command's own save brought are
written before the command's answer is sent, and those of views the
command wrote itself are dropped. A compact view with unsaved edits
is never overwritten ('kept BASE'), and the compact file is read
again just before writing, so an edit made meanwhile is kept too.
'save-result' and 'rerender-done' warnings are logged as read. Log
events: started, holding, released, closed, saved, saved new root,
integrated, re-rendered, kept, warning, error, stopped.

*** Forking
'predicted_forks' reads the edit as the server's

(see Deviations), and 'fork' beside any other edit is an error, as

** Deviations
*** An edit of a write-protected foreign node does not fork it
The brief has an edit of a write-protected (☮) foreign occurrence
trigger the fork confirmation. The server refuses it ("Write-protected
occurrence differs from the graph ... request this one editable (C-c s
d)"), as 'docs/forks.org' says: step one is making the node editable.
So the tool stops at such an edit in content with an error saying how
to go on, and gained the word 'editable' (C-c s d, one of "the rest")
for it. A foreign node in an owned node's content is editable in a
fresh view, and a placed one after its placing save, so the common
case (the live one) needs no extra step. Doing the two saves
automatically was rejected: when the occurrence becomes editable the
server draws its content (and an omitted body), which the edit made
against the write-protected rendering lacks, so re-applying the edit
would remove children and empty bodies.
*** The confirmation is printed on '--yes', and approved at once
A save without '--yes' sends nothing, so it cannot show the server's
confirmation: sending a save to see whether it forks would write when
it does not. The report predicts the fork instead ('Fork:', 'Fork
into:'), and '--yes' prints the server's confirmation and approves
it. The guard: an original the report did not predict stops the
approval, and nothing is written.
*** The live forking edit is a body line
Not the suggested child headline: a body line is a real change (the
server compares title, body and contents) that adds no node, and puts
no non-message among the messages the inbox will collect.
*** The 1731 view does not show the clone under 'inboxes'
It shows Jeff's 'to Ed', heralded '1S 1O'. Override substitution
applies to owned overriders only ('substitute_overriders'), and 'ed'
is foreign to Jeff, so this is the server's rule, not a delay. The
clone itself is in Jeff's graph.
*** Subscribing, overriding and hiding are not gaps
The plan expected them as gaps. 'forest subscribesTo ID' and 'forest
overrides ID' draw editable folders, and a '⟨node:ID⟩' placed there
joins the relation (checked on the fixture; the override case was
first refused by the server's monogamy rule for 'overridden-id', and
then succeeded on 'fred-aside-id'); removing an unintegrated child
under a subscribee as such hides it. The test covers subscribing and
hiding; the README says all three.
*** Fork prediction stays in content position
A first version predicted a fork for a child removed under an
editable subscribee as such, which the server saves as a hide; the
prediction (and the write-protected error) now covers only roots and
the children of node occurrences.
** What's imperfect
*** The prediction is local
It mirrors the server's comparison from the two files; a fork it
misses stops the approval, and one it predicts that the server does
not make (an edit that equals the graph) just saves.
*** The placed title comes from the search index

The approving save runs on whichever connection sent the first one,
