* Outcome

Implement the decisions in '1_discussion.org' as one coherent feature:

- A user can delete a node they own even when a foreign retained
  telescope still refers to it.
- Delete propagation cleans structured references only in retained
  telescopes owned by the current user.  A foreign telescope is never
  scheduled for a collateral write.
- Each surviving unresolved member of 'contains', 'subscribes_to',
  'hides_from_its_subscriptions', or 'overrides_view_of' can render as
  'Phantom::Unknown'.  An unchanged Unknown preserves the exact raw
  relationship member; removing the Unknown from an editable collection
  removes that relationship.
- An Unknown has the same collection-membership gestures as an Active member:
  it can be reordered where the relationship is ordered, and it can be moved
  or copied into another owned, definitive, editable structured collection.
  A new destination relationship receives its source from that destination's
  ordinary source rule; the copied 'referenceSource' is provenance, not the
  requested source of the new edge.
- 'HiddenOutsideOfSubscribeeCol' is an editable derived collection.  Its
  additions and removals edit the subscriber's hides.  A newly added hide
  that belongs inside a subscribee moves there after save and produces a
  success warning.
- 'skg-delete-references-to-absent-node' removes one unresolved raw ID from
  all four structured relationship fields in every retained owned telescope,
  including inactive owned sources.  It reports but never rewrites textual
  Org links.
- An already-open view converges immediately to Unknown wherever a surviving
  raw relationship still backs the position.  'Phantom::Deleted' is reserved
  for a last-seen occurrence with no surviving backing relationship.

This is an execution plan, not another decision document.  The choices in
'1_discussion.org' are settled and should not be reopened during
implementation unless the existing code proves one of the stated invariants
false.

* Semantic contract

** Ownership is decided at the retained-telescope boundary

A retained 'NodeComplete'/'NodeRust' represents one telescope.  It may span
multiple sources owned by the same user, but it does not mix owned and foreign
sections.  Same-PID owned/foreign collisions are normalized during loading:
the owned telescope wins and the foreign files are ignored with the existing
'IgnoredForeignPidCollision' warning.  A normal fork has a fresh PID.

Therefore:

- Classify a referencer by its retained home, 'node.source'.
- 'config.user_owns_source(&node.source)' is the authorization boundary for a
  cleanup-generated 'SaveNode'.
- Never add a foreign referencer to the pending write batch.
- Defensively do not strip deleted IDs from a foreign 'SaveNode' if one reaches
  delete propagation through a future call path.
- Keep the ordinary filesystem writer's foreign-write refusal unchanged.  It
  remains a last line of defense, not the primary filter.

** Unknown is inert as a node and load-bearing as a relationship member

'Phantom::Unknown' does not define, own, delete, rename, source, or save a
node.  At a structured relationship position it does represent one exact raw
member of an owner's collection.

The round-trip is:

- Rendering an unresolved raw member produces an Unknown at that member's
  position.
- The Unknown carries the raw ID and the source section that records the edge.
- Saving it unchanged contributes that exact raw ID/source pair back to the
  containing relationship, but emits no node definition.
- Reordering it among visible peers has the same effect as reordering an Active
  member: 'contains' and 'subscribes_to' retain the submitted order, while the
  already-unordered hides and overrides relationships ignore textual reorder.
- Placing a copy in another owned, definitive, editable relationship creates a
  new relationship to the same raw ID without creating the missing node.  The
  new relationship uses its destination's ordinary source derivation.  The
  original relationship survives unless its occurrence is also omitted from
  an editable definitive collection, in which case the gesture is a move.
- Removing it from a writable relationship surface omits that pair and removes
  the relationship.
- If its ID becomes resolvable before removal, the next render produces the
  real node.

Do not canonicalize an unresolved ID.  It might be an extra ID of the deleted
node, and the graph no longer contains the information needed to map it to the
former primary PID.

** Home source and reference source are different facts

Use these terms consistently in types, comments, errors, tests, and docs:

- /Home source/ is the home of the referenced node.  An Unknown has no known
  home source.
- /Reference source/ is the telescope section that records the relationship
  member.  On the wire this is 'referenceSource'; in Rust it is
  'reference_source'.
- Existing 'relSource' metadata expresses a user's source-placement request for
  a resolvable edge.  It is not interchangeable with 'referenceSource'.

'referenceSource' is provenance and validation input.  In its rendered
position it is the source of that relationship.  After the user copies or
moves the occurrence elsewhere but before save, it still identifies the
relationship from which the occurrence was rendered; it does not choose or
authorize the new destination relationship's source.  It must be consumed
without being displayed as the Unknown node's source herald.

** Visibility and editability use different gates

For a raw structured member recorded at edge source S:

| Edge S active? | Node resolves? | Home source active? | Rendering                                     |
|----------------+----------------+---------------------+-----------------------------------------------|
| no             | either         | either              | preserve from disk; omit from the buffer      |
| yes            | no             | n/a                 | render Unknown with 'referenceSource=S'       |
| yes            | yes            | no                  | preserve from disk; omit target data          |
| yes            | yes            | yes                 | render the existing Active/Diff/Inactive form |

The edge source controls whether an unresolved relationship is visible.  The
referenced node's home source cannot be consulted when there is no node.  This exposes no
target title, body, or home; the raw ID and edge section are already facts of
the visible relationship.

Ownership separately controls writeability.  A foreign edge may be displayed
in the deleting user's already-open view, but it remains inert there.  When the
same telescope is viewed under its owner's config, its definitive owner makes
the collection editable and the Unknown can be removed.  This separation is
required to satisfy both same-session convergence and the ownership boundary.

** Relationship surfaces

| Stored field | Owning view node | Editable surface for dangling member |
|--------------+------------------+--------------------------------------|
| 'contains' | parent node | direct content child |
| 'subscribes_to' | subscriber | member of 'SubscribeeCol' |
| 'overrides_view_of' | overrider | member of 'OverriddenCol' |
| 'hides_from_its_subscriptions' | subscriber | member of 'HiddenOutsideOfSubscribeeCol' when outside; membership can derive into 'HiddenInSubscribeeCol' after save |

Inbound collections such as 'SubscriberCol', 'OverriderCol', 'HiderCol', and
'HiddenCol' stay read-only.  'HiddenInSubscribeeCol' stays a read-only derived
filter.  Textual Org links stay ordinary title/body text and are outside the
structured round-trip.

** Same-session precedence

When a deletion and a surviving raw reference overlap, durable relationship
state wins:

- Surviving raw membership plus absent target becomes Unknown immediately.
- No surviving raw membership permits the existing last-seen Active occurrence
  to become 'Phantom::Deleted' and then follow the existing scaffold/pruning
  rules.
- A fresh render, post-save rerender, and post-restart render must agree.

* Shared implementation vocabulary and data shapes

Introduce explicit types rather than continuing to overload
'(ID, Option<SourceName>)'.  Here an /intent/ is the save extractor's
intermediate description of the relationship membership asserted by the
buffer.  It has not yet been lowered into 'MemberAtSource' values or a
'SaveNode'.  The exact module can follow local ownership, but the concepts must
remain distinct:

#+begin_example
#[derive(Clone, Debug, Eq, PartialEq)]
pub enum RelationshipSourceChoice {
  Derive,
  Explicit(SourceName),
}

#[derive(Clone, Debug, Eq, PartialEq)]
pub enum StructuredMemberIntent {
  Node {
    id: ID,
    source_choice: RelationshipSourceChoice,
  },
  RenderedUnknownReference {
    raw_id: ID,
    reference_source: SourceName,
  },
}
#+end_example

The cases mean:

- 'Node' represents an ordinary Active member.  'Derive' means it has no
  'relSource', so the current sticky-else-default algorithm chooses the edge
  source.  'Explicit' carries a user-authored 'relSource' and retains the
  existing floor/config/ownership validation.
- 'RenderedUnknownReference' represents an Unknown rendered from an existing
  relationship.  Its raw ID/reference-source pair must exactly match at least
  one retained raw outbound relationship in the current graph.  The source is
  evidence for the rendered occurrence, not a source choice for its current
  destination.  Reconciliation preserves the destination's existing exact
  member when it already has the same relationship-member key; otherwise it
  creates a new member with the destination's ordinary derived source.
  Omitting the occurrence from its original editable definitive collection
  removes that original relationship.

Use a shared identity helper wherever resolved and unresolved relationship
members are compared:

#+begin_example
enum RelationshipMemberKey {
  ResolvedPid(ID),
  UnresolvedRawId(ID),
}
#+end_example

Construct 'ResolvedPid' when 'graph.pid_of(raw_id)' succeeds and
'UnresolvedRawId' otherwise.  This provides PID equivalence for primary/extra
IDs while targets exist, and exact raw-ID equality after they disappear.  Use
it for deduplication, set difference, reconciliation matching, and the hide
inside/outside partition.  Do not replace the raw ID stored in
'MemberAtSource'; the key is for comparison only.

Rendering also needs an explicit relationship-member reality rather than an
empty Active fallback.  Extend the existing content and PartnerCol goal/child
types, or introduce a shared equivalent, with at least:

#+begin_example
enum RelationshipMemberReality {
  Real { pid: ID, home_source: SourceName, title: String },
  // Keep the existing Diff/Inactive cases where that pipeline needs them.
  Unknown { raw_id: ID, reference_source: SourceName },
}
#+end_example

Every display goal must retain both the raw stored ID and its reference source,
even when a resolved PID is also available.

** Command contract

The command is runnable only with point on an Unknown headline.  It operates on
the full raw ID from metadata, never a readable/truncated display ID.

It scans every retained owned telescope represented in the configured graph,
regardless of the active source set and regardless of which views are open.  It
removes the exact raw ID from:

- 'contains';
- 'subscribes_to';
- 'hides_from_its_subscriptions';
- 'overrides_view_of'.

It does not remove a primary-ID equivalent, another extra ID, or a now-known
canonical PID.  It does not edit foreign telescopes.  It does not rewrite
titles or bodies.

Before mutation, compute one deterministic preview containing:

- every owned node/telescope that would be rewritten, with PID, title, home,
  relationship kind, and each reference-source section involved;
- every matching textual Org ID link in each owned node's effective title/body,
  with PID, title, home, 'title' or 'body line N', link label, and occurrence
  count/location sufficient to find it.

Use 'types/textlinks.rs::textlinks_from_text' for semantic matching, with a
small location-aware wrapper over the same syntax/regex so line numbers and
labels agree with the established parser.  'NodeRust.textlinks_to' can cheaply

  and textual-link list;
- only after the buffer exists, ask whether to proceed;
- decline performs no mutation;
- approval retries with the opaque approved-preview value supplied by the
  server.

not invent a general confirmation for this task.  The ordinary result still
reports the structural changes.  A preview containing textual links but no
structured rewrites still gets the warning/confirmation; approval then yields
a successful structural no-op and leaves all text untouched.

** DONE Separate Unknown visibility from relationship editability

converge to Unknown immediately.  I chose separate display and write gates

** DONE Scan effective node text rather than every raw telescope section for links

The command plan scans each retained owned 'NodeRust' node's effective title
and body for textual links.  It does not separately parse every raw owned
telescope-section file whose lower-priority title/body text is currently shadowed

The alternative is a filesystem-level scan of every retained owned section.
That is more literally a search of all of the user's data and would find a
link that is dormant now but could become effective after a later telescope
change.  It also requires the preview to identify source section and file

effective-node scan because the in-Rust graph is the command's mutation

choice in the plan about which I have the least confidence.

The plan has both clients reject the command before sending it when any
registered Skg view has unsaved edits.  The command rerenders every open view
after its global mutation, so proceeding would otherwise overwrite unrelated
buffer work.

The alternatives were to rerender only views known to contain the raw ID, or

The former risks stale views because removing subscriptions and overrides can
change reachability beyond the visible Unknown occurrence.  The latter is a
substantial concurrent-edit design of its own.  I chose the conservative
global refusal, accepting that users may need to save or discard unrelated

** DONE Bypass text-release confirmation only for the post-command rerender

The plan uses the normal rerender preparation and streaming machinery after a

The alternative was to construct a simulated post-command graph, prepare and
authorize every rerender against it before touching disk, and then commit only
after approval.  That preserves one uniform privacy gate but requires the
rerender stack to accept an alternate graph snapshot and makes the operation's
confirmation state substantially more complex.  I chose the documented narrow
bypass; it must not be generalized to arbitrary mutations.

*** DONE please define vocabulary
**** text release
/Text release/ is the privacy decision about allowing a node's title or body,
in contrast to relationship-valued fields such as 'contains', to cross an
output boundary.

A telescope can have its home in one source while folding selects its title or
body from a source below home in the privacy ladder.  Skg calls that telescope
/overPrivateText/.  Holding the folded text inside the server is not a release.
A /text release/ occurs when that selected title/body text, or information
derived from it, is allowed to cross an output boundary: for example, when it
is sent to a client in a view or title lookup, used to return search matches,
or written by export.

'server/serve/handlers/text_release.rs' implements the shared decision.  It
canonicalizes candidate IDs to PIDs, checks whether their retained
'NodeRust.overPrivateText_telescope' flag is true, and returns 'Allow',
'AllowWithWarning', or 'Challenge'.  Source-set 'all' permits release with a
warning.  A restricted source set requires request-local approval for the
exact affected PIDs; search instead obtains an include/exclude choice before
querying, because revealing which PIDs matched could itself reveal protected
text.  Approval to release text is neither permission to rewrite a telescope
nor permission to Hoist its title/body text to home.

Thus “bypass text-release confirmation” in this section means bypassing the
usual call that asks whether a prepared rerender may send overPrivateText title/body text
to the client.  It does not mean bypassing source-set membership, filesystem
authorization, or the textual-link confirmation belonging to this command.

**** the restricted-source overPrivateText-telescope challenge
The /restricted-source overPrivateText-telescope challenge/ is the protocol/UI
form of a 'TextReleaseDecision::Challenge'.  It occurs when the active source
set is not 'all', a proposed response involves at least one overPrivateText telescope, and the
current request lacks the required release approval.

The server sends an 'overPrivateText-telescope-confirmation' response containing the
operation name, a prompt, and normally the canonical PIDs requiring approval,
but none of their protected title/body text.  The client asks the user and, on
approval, retries the operation with those exact PIDs in
'allow-overPrivateText-telescopes'.  The approval belongs only to that retry.  For an
ordinary prepared rerender, the server challenges before streaming any view
text or changing the open-view registry.  Search is the special case: its
challenge names no PIDs and asks include versus exclude before the query, so
even the identity of a matching overPrivateText telescope is not disclosed prematurely.

The concern raised here is ordering.  If the new cleanup command first commits
its relationship removals and then calls the generic rerender authorization,
the challenge can occur after disk and graph mutation.  Declining would leave
the mutation committed while withholding the refreshed views.  The plan
therefore proposes a narrow no-challenge rerender path for this command, based
on the claim that removing edges to a freshly verified absent ID cannot reveal
any new real node's title or body.  The architectural alternative described
above is to prepare and authorize rerenders against a simulated post-command
graph before committing.

***** Three coherent designs

****** Keep 'referenceSource' destination-relative

Under the strict original meaning, 'referenceSource' always names the edge at
the Unknown's current position.  A copied line necessarily has a stale value,
so the save must reject it unless some editor command rewrites or removes the
atom while copying.  That is a poor fit for an Org buffer, where ordinary text
movement is supposed to be the editing interface.  It does not meet the
copy-like-a-known-Vognode requirement without special client behavior.

****** Carry a complete origin relationship

The Unknown could instead carry something like 'origin_owner',
'origin_relation', and 'origin_reference_source'.  Together with the raw ID,
those fields identify the exact old edge after the line moves.  The server
would use them only to prove that the copied occurrence came from that edge;
the new ancestry would still name the destination, and the destination's
ordinary rule would still choose its source.  Rerender would replace the
metadata with the new edge as origin.

This is precise, but it adds substantial hidden wire state merely to prove the
origin of a value the user is allowed to put in their own relationship.  It
also makes a copy fail if the origin disappears concurrently, and it continues
to distinguish relationship-backed Unknowns from root/backpath Unknowns even
though both carry a usable raw ID.

****** Do not serialize relationship provenance on Unknown

'PhantomUnknown' can remain just '{ id }'.  At save, ancestry supplies the
destination owner and relation.  The current retained graph then supplies all
the source information actually needed.

If the destination already contains that unresolved raw ID, its current
'MemberAtSource' supplies the exact source to preserve.  If it does not, the
line is a new destination member and the ordinary new-edge rule derives the
source.  If the line was omitted from an editable origin collection, that
origin's current raw list and edge sources tell the source-set-aware merge what
to remove.  Inactive members can still be preserved because visibility is
computed from each disk member's source, not from metadata on submitted
headlines.

This makes movement and copying exactly destination-relative, like the rest of
the Org editing model.  It also permits a root/backpath Unknown to be copied
into an owned relationship and permits a sufficiently knowledgeable user to
write an Unknown headline for an arbitrary absent raw ID.  The latter changes
only a relationship the user owns; it neither creates nor edits the absent
node.

The cost is losing the narrow optimistic-concurrency check: if an edge is
deleted elsewhere while an old buffer still contains its Unknown, saving that
buffer can recreate the edge at its normal derived source.  Known members can
already be resurrected by stale definitive buffers, so solving that generally
would call for a buffer/graph revision check rather than special provenance on
Unknown alone.

***** My recommendation

I now recommend the third design: do not add 'referenceSource' to
'PhantomUnknown' or the wire format.  The current graph already stores the
reference source in 'MemberAtSource', and the Unknown's current ancestry already
identifies the only relationship the save is being asked to edit.  Treating the
Unknown as a raw relationship value makes copying natural and avoids turning a
display occurrence into a partially specified edge handle.

If you want proof that every structured Unknown was rendered from a particular
existing relationship, I recommend the complete-origin design instead.  The
one-field traveling-provenance compromise in the current amendment is the
least crisp of the three: it neither keeps 'referenceSource' destination-local
nor identifies the origin edge completely.

***** Yes: if we carry the relationship source, it should be 'relSource'

Yes, with one qualification: this means abandoning the proposed
/provenance-proof/ role of 'referenceSource'.  It would reuse 'relSource' with
the same read/write meaning it already has for a known Vognode occurrence.

On render, 'relSource' reports an existing edge source only when that source is
off the edge's normal default.  On save, its presence is an explicit request
for the relationship at the headline's /current/ position to use that source;
its absence means sticky source for an existing destination edge and derived
source for a new one.  It never identifies an origin relationship.

That behavior composes naturally with text copying.  If an Unknown is copied
with no 'relSource', its new relationship derives a source.  If it carries an
off-default 'relSource', the copy carries the same explicit source preference,
which is then checked against the new destination's ownership and privacy
floor.  That is what already happens when a known Vognode headline carrying
'relSource' is copied.  The original relationship is independently retained or
removed according to whether its original definitive collection still
contains the line.

For an unresolved target, the existing new-edge default is the relationship
owner's home, so render can decide whether an edge is off-default without
knowing a target home.  An unchanged destination edge with no atom still keeps
its actual source through the sticky lookup in the current graph.  Therefore
we do not need to emit 'relSource' merely to remember every edge's section.

Hides remain the existing exception.  Skg does not support explicit

its explaining subscriptions.  An existing Unknown hide can still keep its

'hide_source', exactly like a known hide.

So my refined recommendation is: do not introduce 'referenceSource'; allow an
optional ordinary 'relSource' on Unknown in precisely the relationship
positions where known members already support it.  Keep only the Unknown's raw
ID otherwise.  This sacrifices the special Unknown-only provenance check and
allows an absent raw ID to be added to an owned relationship, as described
above.  If that provenance check is a requirement, merely renaming the field
would be wrong: we would need the complete origin relationship instead.

*** Codex response

Yes.  That is the cleaner model, and it resolves the copying problem.

Your memory matches the general metadata architecture, but not the current
'relSource' implementation.  Today the server renders the already-true fact as
'(node (viewStats (relSource S)))'.  The client command then edits that very
same atom, the parser stores it in 'ViewNodeStats.rel_source', and save
extraction interprets it as an explicit source request.  Its herald is simply
'~S'.  There is currently no separate relationship-source request and no
'request:~S' herald.

'viewRequests' is presently reserved for requests to construct extra views
such as cols, paths, and definitive views.  'editRequest' presently contains
node deletion and node merge.  Thus Skg has request branches, as you remember,
but relationship-source editing was implemented as an exception that makes a
rendered fact double as a setter.

**** The separation you describe

The displayed fact should remain something like
'(viewStats (relSource CURRENT))' and should produce '~CURRENT'.  It says only
where the binding relationship at this position is currently stored.  Save
extraction should not treat that display fact as an instruction.  If it is
stale, deleted, edited by hand, or copied under another container, rerender can
recompute it from the graph.

A distinct request branch should carry '(relSource REQUESTED)' and produce a
visibly prospective herald such as 'request:~REQUESTED'.  Only that occurrence
of the token should feed the explicit-source side channel and its ownership and
privacy-floor checks.  After a successful save, the request disappears and
rerender recomputes the display fact.  Before save, current and requested
sources can coexist, so the buffer can truthfully show both “~old” and
“request:~new.”

The same leaf token in two different parent forms is appropriate: both facts
name the relationship-source aspect, while the parent form determines whether
the value is observed or requested.  The exact request-container name remains
a vocabulary choice.  I would not put it in 'viewRequests', whose established
meaning is view construction.  A relationship-specific edit-request form is
conceptually cleaner than making it another node edit, because the source
belongs to the edge represented by this occurrence, not to the represented
node.

**** Consequence for copying

Copying an ordinary or Unknown headline also copies its display
'(viewStats (relSource OLD))', but that atom has no write force.  At the new
position the destination relationship either keeps its current stored source
or, if new, derives its default.  Rerender replaces or removes the copied
display atom accordingly.

If the headline also carries an explicit pending relationship-source request,
copying it copies that request.  Applying the request at the new position is
reasonable because it is visibly marked as prospective user intent, and it is
validated against the new destination.  A normal copy with no pending request
does not accidentally transplant the old edge's source.

This is more coherent than either 'referenceSource' proposal.  No origin
provenance is needed, and 'relSource' never has to mean “the source of some
other edge from which this line may have come.”

**** Unknown and ordinary Vognode parity

Agreed: the rules should be the same.  A structured Unknown participates in
the same relationship-position metadata as an ordinary Vognode.  It needs an
optional displayed 'relSource' only when the current edge is off its applicable
default, and it accepts a source-change request only in positions where an
ordinary member accepts one.  A root, backpath, independent occurrence, or
read-only relationship position has no settable binding edge.

For an Unknown, the missing target has no known home, so the existing default
rule falls back to the /relationship owner's home/.  For direct content that
is the parent's home; for an outbound PartnerCol it is the col owner's home,
not literally the scaffold headline.  Thus an Unknown edge stored at the
owner's home needs no displayed atom, while an edge stored more privately does.
An unchanged atom-free edge still preserves its actual source through the
ordinary sticky lookup.

Hides are not an Unknown exception.  Known and Unknown hides alike currently
have no explicit 'relSource' setter because 'hide_source' derives their source
from the subscriber and explaining subscriptions.  The HiddenOutside and
HiddenIn positions should therefore follow that same existing rule.

**** Scope revealed by this decision

This is not merely a naming correction inside the dangling-reference work.  It
requires splitting the existing 'relSource' fact-and-request mechanism for all
ordinary Vognodes and aliases too, changing the setter commands, parser,
heralds, save extraction, request cleanup, docs, and tests.  I agree that it
should be done if this is the intended metadata invariant; otherwise Unknown
would be forced to imitate an existing conflation that already makes copied
known headlines carry accidental source-setting force.

I have left the operative plan unchanged, as requested.  Once you close this
discussion, the plan should replace 'referenceSource' with the shared displayed
'relSource', add the distinct relationship-source request path, and apply that
fact/request split uniformly to known nodes, Unknowns, and aliases wherever
relationship-source editing is supported.
