*** 'write-protected leaf'
This is a write-protected viewnode
  without its body or content

** where to show/edit the commit-status of each kind of edit
*** alias changes
New and deleted aliases have a commit status.
Their commit status propagates up to the aliases folder they belong to.

Alias changes to graphnode X are shown under an "its aliases" viewchild of X.
A deleted alias is just an alias node marked Removed.
A new alias is just an alias marked New.
All other aliases are also shown, but without a Removed or New.

Each deleted and each added alias is separately commit-cycled.
Each edit begins in the TODO state.
If any of them are TODO, the whole aliases collection is also TODO.
If not, but any of them is ONGOING, the whole aliases collection is ONGOING.
If they are all DONE, the whole is also DONE.
The user does not control the whole collection's commit status,
just the individual aliases.
*** new IDs
New IDs are shown under an "its IDs" viewchild of X,
alongside the other IDs. The PID is first. The new ones are heralded "new".

If the user is not okay with an extra ID, they ran a merger they regret.
An automatic way to unwind the merger would be nice but seems not critical.

New IDs have a commit status.

** "commitment status"
Some things in the edit report need a "commitment status"
that the user can cycle between TODO, DOING, and DONE.
*** elaboration | motivation
TODO and ONGOING are both just prompts for the user.
Indeed maybe the user should be able to define other labels.

But DONE is a special label,
because (although the meaning of DONE is up to the user)
the user aims to mark all edits DONE,
knowing that once all are so marked
they can feel safe committing all changes to all repositories.
*** Changes to atoms and changes to relationships require separate commitment statuses.
Suppose A and B both contain C, and C is deleted.
The user wants to separately OK each of
- the deletion of C
- the deletion of (A contains C)
- the deletion of (B contains C)

**** The commitment status on an atom facilitates avoiding duplicate work.
For instance, two containers may have both lost a contains relationship
to the same node, because it was deleted.
That node will be represented by a 'resurrected deletion'
under both containers.
Once the user has determined that they are OK that it was deleted,
they can mark either deletion DONE,
and the other will show as DONE, too.
This way they don't have to redetermine,
when they come to the second container,
whether it is okay that that thing was deleted.
**** Commitment status propgagates across representations of the same object.
To cycle the diff work status of any graphnode,
deleted or present,
causes every representation of that graphnode
to show the same diff work status.
