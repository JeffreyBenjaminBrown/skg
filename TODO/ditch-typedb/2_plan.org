* Accepted decisions

1. Keep Tantivy.  It is a derived search index, not graph authority.
2. A request or operation captures one explicit immutable runtime/graph
   snapshot and threads it through all helpers.  There is no hidden global
   graph fallback.
3. At every server startup, read all =.skg= files once, build and validate the
   graph from those nodes, and rebuild Tantivy from that same node vector.
   Delete the marker/incremental startup fork.
4. Delete the scheduled graph-vs-TypeDB audit.  Keep pre-write/startup
   validation and pure tests of the graph's internal indexes.
5. Retired config keys =db_name=, =delete_on_quit=, and =auto_audit_daily=
   produce one clear migration error.  They are not silently ignored and are
   not retained as no-op compatibility fields.
6. Rename the user command to *rebuild ephemeral data stores*.  Explain in
   =docs/COMMANDS.org= and the Neovim counterpart that the graph and Tantivy
   are reconstructible, while =.skg= files are authoritative.
7. Delete =schema.tql= after every enduring invariant has a Rust validator,
   test, or technical-documentation home.
8. Rename =docs/data-model.org= to =docs/data-model_friendly.org=.  Add

   semantic meaning, graph constraint, and graph index.
9. Use two distinct green checkpoints: first remove =typedb-driver= while
   preserving async public shapes; then make graph-only paths synchronous.
10. Stop using TypeDB in this repository.  Record cleanup of the external

* Authority and target architecture

The authority chain after the refactor is:

#+begin_example
.skg files + skgconfig.toml
          |
          | full read / validation at startup or explicit rebuild
          v
immutable RuntimeGeneration
  - Arc<SkgConfig>
  - Arc<InRustGraph>
  - TantivyIndex for the same generation
          |
          +--> request captures one Arc and uses it throughout
          +--> save publishes a new graph generation under one writer gate
          +--> Tantivy background queue updates the captured index in FIFO order
#+end_example

There must be one shared publication handle per =SkgEnv= family, not copied
config/index fields in each connection clone.  A concrete target shape is:

#+begin_src rust
struct RuntimeGeneration {
  config: Arc<SkgConfig>,
  graph: Arc<InRustGraph>,
  tantivy_index: TantivyIndex,
  generation: u64,
}

struct SharedRuntime {
  current: ArcSwap<RuntimeGeneration>,
  mutation_gate: /* one shared, runtime-compatible mutex */,
}

#[derive(Clone)]
struct SkgEnv {
  runtime: Arc<SharedRuntime>,
}
#+end_src

Names may change to fit the codebase.  The semantic requirements may not:

- cloning =SkgEnv= shares publication state and the mutation gate;
- one operation calls =load_full= once and retains that =Arc=;
- helpers receive that captured generation or graph explicitly;
- ordinary saves publish a new graph with the same config and Tantivy handle;
- live rebuild constructs and validates an entire replacement generation
  before one atomic publication visible to all connections;
- a failed rebuild leaves the old generation and open views untouched;
- successful rebuild clears open views only after publication;
- replacement Tantivy construction must not destroy files still used by the
  published generation.  Build into a sibling generation directory, publish
  it only after success, and retire old generation directories at a safe
  point (at least on next process startup).  Do not recreate the old
  wipe-under-live-readers behavior.

The mutation gate is environment-owned rather than process-global.  Select the
simplest mutex whose guard is safe for the actual executor and for the phase-1
async call chain; this is an implementation detail, not a reason to borrow the
failed partial-reload branch.  No graph-dependent validation, filesystem
mutation, graph publication, or Tantivy enqueue for another mutation may
interleave inside it.

* Non-negotiable semantic invariants

** Snapshot consistency

- A single operation never mixes graph generations.
- No production helper calls =snapshot_global= or consults a singleton.
- Background work captures the exact generation/index it is intended to use.

** Authority and recovery

- =.skg= files are authoritative for nodes and relationships.
- =skgconfig.toml= is authoritative for configured sources and paths.
- The in-memory graph and Tantivy are entirely reconstructible.
- Never delete an existing TypeDB data directory as part of this migration.
  It is obsolete derived data, but retaining it through the initial soak gives
  Jeff a cheap manual rollback reference; removal is a later explicit cleanup.
- A crash after a successful disk write but before derived publication is
  repaired by restart/rebuild; no derived store is treated as proof that disk
  state committed.

** Mutation serialization and order

Every save, merge, delete, source move, migration that rewrites nodes, and
manual rebuild uses the same mutation gate.  For a normal mutation:

1. Capture the current generation while holding the gate.
2. Parse and simulate the whole change against that graph.
3. Run every fallible semantic validation before the first disk write.
4. Write/remove the authoritative files.
5. Construct and atomically publish the resulting graph generation.
6. Compute the Tantivy delta/context metadata from that same result and enqueue
   it in FIFO order before releasing the gate.

If a later implementation discovers a fallible step after disk mutation, move
or precompute it before disk mutation, or explicitly document and test the
startup-recovery behavior.  Do not add rollback machinery casually.

** Reader performance

- Readers remain lock-free: they load an immutable =Arc= snapshot.
- Only writers take the mutation gate.
- Do not replace the graph with a large shared =RwLock=.

** Identity

- A primary ID wins over an identical extra ID.
- Primary IDs are unique; extra IDs resolve to at most one primary node; and a
  primary/extra namespace collision is either rejected or resolved by the
  documented primary-wins rule at every call site.
- Dangling relationship member IDs and their recorded sources remain raw and
  round-trippable; lack of a target node does not erase them.

** Relationship semantics and privacy

- All nine relationship roles retain their present meanings, direction, and
  endpoint typing.
- Stored outbound order is preserved.
- Inbound results derived from indexes are sorted deterministically before
  presentation or comparison.
- Every edge retains both the member ID and the source recorded on that member.
- Visibility requires both gates: the edge's recorded source must be active,
  and a resolved target node's home source must be active.
- Source-set filtering happens while traversing the graph, not only while
  rendering results.  Hidden edges must not affect path length, first-fork
  selection, ancestry topology, context statistics, or subscription topology.
- The existing render/insertion gate remains as defense in depth.

** Graph constraints

Rust must own every useful constraint formerly suggested by =schema.tql= plus
the constraints that TypeDB never enforced:

- identity uniqueness and primary/extra resolution rules;
- one configured home source per complete node;
- well-formed typed binary relationships and known roles;
- correct relationship-member source provenance;
- raw dangling members preserved without manufacturing nodes;
- override monogamy, permitted orientation, and cycle rejection;
- telescope constraints and source visibility rules;
- exact agreement between forward node data and every inverse graph index.

The constraint audit must label each condition as a hard error, warning, or
type-system guarantee.  Avoid accidentally turning tolerated dangling edges
or privacy warnings into startup-fatal errors.

* Scope boundaries

In scope:

- graph reads, traversal, stats, source lookup, save/merge/delete/source-move;
- startup and explicit derived-store rebuild;
- TypeDB-dependent test fixtures and behavior tests;
- TypeDB driver, schema, audit, tools, scripts, config, protocol names, client
  commands, and current documentation;
- synchronous cleanup of graph-only call chains after the driver-free gate.

Out of scope:

- redesigning the =.skg= file format;
- removing Tantivy or changing search semantics except where graph authority
  replaces ID/source fallback;
- recovering or copying code from the post-divergence partial-reload branch;
- rebuilding the external container image/repository in this initiative;
- rewriting historical notes merely because they truthfully mention TypeDB;
- broad test-regrouping or performance work not justified by this cutover.

** TODO 1.1 Introduce one shared mutation gate

migration that finishes by rebuilding does not recursively acquire the same

* Failure and escalation rules

The pre-plan is settled, so most implementation discoveries should be resolved
locally and recorded.  Ask Jeff only if evidence requires changing an accepted
semantic decision or expanding authority/scope.  Examples:

- preserving behavior would require keeping a second authoritative graph
  store;

  availability contract;

- a test reveals ambiguous intended privacy/relationship semantics not
  resolved by =1_discussion.org= and existing behavior; or
- external environment work becomes necessary to prove this repository at
  all, rather than merely being a later cleanup.

A hard implementation problem, a broad caller cascade, or higher-than-expected
token use is not itself a reason to weaken correctness or stop.  Read more,
raise test scope, use the main model, or delegate a bounded task as needed, and
record why in the ledger.
