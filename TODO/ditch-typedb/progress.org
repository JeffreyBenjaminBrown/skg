** Lock-order map

- The shared =Arc<tokio::sync::Mutex<()>>= lives in =SkgEnv=, so all cloned
  per-connection environments share it.  New construction sites create one
  gate per independent test environment.
- Normal save/merge: mutation gate -> captured/current graph and override
  validation -> filesystem -> graph publication -> foreground TypeDB (until
  Phase 7) -> Tantivy enqueue or merge writer -> release gate.
- Rebuild: mutation gate -> wait for queued Tantivy writes -> candidate
  disk/config/graph validation -> TypeDB/Tantivy rebuild -> graph publication
  -> release gate.  The background Tantivy worker takes only its writer lock,
  never the mutation gate, so this order cannot form a queue/gate cycle.
- Standalone save, merge, absent-reference cleanup, and rebuild all enter the
  same gate.  Internal =*_with_hoist_approval= helpers do not reacquire it;
  the combined save path therefore holds one guard across its ordinary and
  node-merge portions.
  The TCP save handler now acquires before save-plan construction (whose disk
  reads would otherwise permit two serialized writes based on the same old
  files), and releases immediately after publication, before rerendering.
