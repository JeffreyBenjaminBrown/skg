* DONE The short answer

  The runtime is right. The vocabulary is wrong. But the wrong
  vocabulary is not cosmetic: it has already misled at least two
  readers on record, and it concealed one real nondeterminism bug
  whose blast radius includes the privacy level at which edges get
  written.

  So: no data is being corrupted today, no legitimate telescope is
  rejected today, and nothing here is an emergency. But I would not
  file it as "just a rename" either. There are four live defects
  behind the misleading name, and one root cause that the privacy
  telescope plan explicitly predicted and asked to be prevented.

  Since the first draft, two things changed. Your rule -- the text
  always lives in the most public section -- turns out to be an
  invariant the save path ALREADY enforces but never names, and
  adopting it makes the 'source_from_disk' fix simpler, not harder
  ([[*ONGOING 4. Fix 'source_from_disk', and pin the home to the most public section][item 4]]). And the TypeDB experiment came back split: one
  flavor of a real id conflict dies inside TypeDB before the readable
  report can run, the other passes TypeDB silently ([[*DONE Open question, now settled: does TypeDB reject a conflict first?][the experiment]]).

* DONE What I verified: the check itself is correct

  'check_for_duplicate_ids_across_sources'
  (server/dbs/filesystem/multiple_nodes.rs:144) does NOT flag
  telescopes. It groups every claimant of every id and reports only
  ids whose claimants have MORE THAN ONE DISTINCT PID:

  #+begin_src rust
    let distinct_pids : HashSet<&ID> =
      owners . iter() . map ( |(pid, _)| pid ) . collect();
    distinct_pids . len() > 1
  #+end_src

  Sections of one telescope share a pid, so they can never trip it.
  Its own doc comment (line 136) says so in as many words.

  I checked every call site. All nine pass POST-FOLD nodes -- one
  NodeComplete per telescope, never one per file:

  - server/main.rs:140 (from 'initialize_dbs')
  - server/save.rs:132 (TypeDB-rebuild fallback)
  - server/nodeMerge.rs:87 and :116 (rebuild fallbacks)
  - server/serve/handlers/rebuild_dbs.rs:63
  - tools/bench-audit.rs, tools/probe-audit.rs,
    tools/top-contents.rs, tools/bench-context-inmemory.rs,
    tools/top-contentward-descendants.rs

  And the tests pin the telescope case as LEGAL, explicitly:
  tests/multi_source_loading.rs:178-186 writes the same pid into two
  sources, asserts they fold into one node, and asserts the check
  passes ("a telescope is not an id conflict").

  The surrounding subsystems are already telescope-aware too:
  diff analysis reports only the two-pid violation
  (server/diff_analysis/diff.rs:116-118), api-and-formats.md:170-176

  Conclusion: there is no code path on which a privacy telescope is
  treated as invalid.

** DONE Live defect: the report throws away the only actionable data

   'check_for_duplicate_ids_across_sources' collects claimants as
   '(pid, home)' pairs and then maps the pid away before reporting:

   #+begin_src rust
     . map ( |(id, owners)|
             (id, owners . into_iter()
                  . map ( |(_, src)| src ) . collect()) )
   #+end_src

   'report_duplicate_ids' therefore receives 'ID -> Vec<SourceName>'.
   Post-telescope the sources are the USELESS half. The violation is
   "two nodes claim this id"; the two pids are what you need to open
   and repair. Worse, both claimants can live in ONE source (nothing
   about the violation is cross-source any more), in which case the
   report prints that source twice:

     - ID 'contested' in sources: public, public

   That is the entire diagnostic the user gets. The experiment below
   sharpens this: for one flavor of conflict TypeDB's own error is
   what you actually see, and it names the contested VALUE but neither
   claimant -- so the pids are missing from both diagnostics.

** DONE Live defect: the report file is never deleted

   'report_duplicate_ids' is only reached when the set is non-empty
   (line 166 returns early otherwise), so nothing ever removes
   'initialization-error_duplicate-ids.org' after a clean boot.

   Contrast 'report_telescope_violations'
   (server/telescope/invariants.rs:132-142), which explicitly removes
   its stale report "so the file's presence is meaningful". This is
   the same defect problems.org already files against
   'initialization-error_unreadable-skg-files.org' -- but the
   duplicate-ids file is the dangerous one, because a stale copy
   written by a pre-telescope binary names id/source pairs that are
   now perfectly healthy. Someone acting on it would "repair" a valid
   telescope by deleting a section.

** DONE Live defect: at init the check runs after the databases are built

   server/main.rs:130-144 calls 'initialize_dbs' first and checks
   afterward. 'full_init' (server/dbs/init.rs:280-324) populates
   TypeDB (line 309) and Tantivy (line 318), each with its own
   'std::process::exit (1)' on failure.

   I have now confirmed by experiment what this costs; see
   [[*DONE Open question, now settled: does TypeDB reject a conflict first?][the experiment]]. Short version: for an extra_id/extra_id
   conflict TypeDB errors first and the readable report never runs;
   for a pid/extra_id conflict TypeDB accepts silently and the Rust
   check is the only thing that catches it -- after both databases
   have already been filled with the ambiguous data.

   Note the internal contrast: 'rebuild_dbs_in_place'
   (server/serve/handlers/rebuild_dbs.rs:58-76) gets the order right --
   read files, check ids, THEN wipe and repopulate. Init does not.

** DONE Live defect, and the weighty one: 'source_from_disk'

   server/types/phantom.rs:106-116:

   #+begin_src rust
     pub fn source_from_disk (
       id     : &ID,
       config : &SkgConfig,
     ) -> Option<SourceName> {
       let filename : String = format!( "{}.skg", id . 0 );
       for (source_name, source_config) in &config . sources {
         let path : PathBuf =
           PathBuf::from( &source_config . path ) . join (&filename);
         if path . exists() {
           return Some( source_name . clone() ); }}
       None }
   #+end_src

   It iterates 'config.sources', which is a 'HashMap', and returns the
   FIRST directory holding a file with that name.

   Pre-telescope there was at most one such directory, so iteration
   order was irrelevant. Post-telescope, any node with a privatized
   edge has two or more section files -- this is the normal shape, not
   an edge case -- and this function returns an ARBITRARY one, chosen
   by 'HashMap' iteration order, which Rust randomizes per process.

   It also breaks the rule stated at server/types/misc.rs:191-201,
   where 'source_order' is marked LOAD-BEARING and the comment ends
   "No other code may compare source positions." This code compares
   source positions by declining to.

   Every consumer reads the returned SourceName as the node's HOME:

   - server/from_text/supplement_from_disk.rs:275 -- 'home_of' feeds
     'default_floor_for', which computes the sticky-else-default LEVEL
     of a relationship edge. A wrong home means a wrong default
     privacy floor for a new edge, and once written the level is
     sticky.
   - server/from_text/weave.rs:42 -- 'member_is_visible' decides
     whether a disk member counts as visible during a save. Wrong in
     one direction, a member the user deleted is retained; wrong in
     the other, a member they never saw is dropped.
   - server/to_org/complete/partner_col/mod.rs:162, :352, :449,
     server/update_buffer/reconcile/content.rs:249,
     server/update_buffer/reconcile/partner_col.rs:62,
     server/to_org/complete/partner_col/goal_list.rs:358 -- rendering,
     where a wrong home means a wrong source herald.
   - server/types/env.rs:60, :97 -- the last rung of 'find_source'.

   *How exposed is it today.* It is the LAST fallback. The in-Rust
   graph answers first and knows every node loaded at init, so in a
   healthy running server this fires only for ids the global snapshot
   does not know. In harnesses where 'snapshot_global ()' returns None
   it fires always -- but the one fixture set with genuine
   multi-section telescopes on disk (tests/leak_battery/fixtures, N.skg
   and S.skg in two sources) installs the global handle, so no test
   is flaking on this now.

   So: latent, not currently firing. But it is nondeterministic by
   construction and it sits on the path that decides how public a
   relationship gets written. That is the one place in this codebase
   where "arbitrary" is least acceptable.

** DONE Root cause: the type the plan asked for was never built

   'source_from_disk' is precisely the regression that
   4_discussion.org:754-761 predicted and proposed to prevent by
   making "several files, one node" a TYPE rather than a condition.
   Because grouping stayed an anonymous HashMap, nothing forced
   'source_from_disk' to answer the question "which of this node's
   several sections do you mean?" -- so it silently kept answering the
   pre-telescope question.

   This is why I would not treat the rename as the fix. The rename
   stops the bleeding; the type is what stops the next one.

*** DONE The rule, and what I found checking it

    THE RULE (yours): a node's text always lives in its most public
    section. So the home is THE MOST PUBLIC SECTION, full stop --
    not, as today, "the most public section bearing a title". A
    titleless section above the title is then a violation to report,
    not a shape to search past.

    What I verified: the save path ALREADY enforces this for owned
    data, without naming it. 'apply_sticky_levels'
    (server/from_text/supplement_from_disk.rs) clamps every level to
    at least the owner's home --

    #+begin_src rust
      config . more_private_of (unclamped, owner_home . clone ())
    #+end_src

    -- for ordered relations (line 302), for hides (line 376), and
    for aliases (line 391). Its own comment there calls a
    more-public section "the 'extends on the other side' junk
    shape". So no owned section written by the current save path can
    be more public than the home.

    Your rule is therefore not a new constraint. It is an existing
    one that was never named, never validated on read, and never
    relied on. That is exactly the pattern this whole document is
    about, so I think naming it is worth more than the code change.

   In server/main.rs, the check runs on nodes 'initialize_dbs' has

* DONE Open question, now settled: does TypeDB reject a conflict first?

  You asked me to find out. I ran it.

** DONE Method

   Started a TypeDB server, created a scratch database, and defined
   the relevant slice of schema.tql verbatim: 'attribute id',
   'entity node owns id @key', 'entity extra_id owns id @key',
   'relation has_extra_id', plus 'source' / 'has_source'. Then issued
   the same two queries 'create_node' and 'insert_extra_ids'
   (server/dbs/typedb/nodes.rs:155-205) issue, one node per
   transaction, committed separately -- mirroring
   'create_one_node_in_own_tx'.

   Both scratch databases were deleted and the server stopped
   afterward; TypeDB was not running when I started and is not
   running now.

** DONE Result A: extra_id vs extra_id -- TypeDB REJECTS

   Two nodes with distinct pids ('pid-a', 'pid-b') each claiming
   extra_id 'contested'. The SECOND node's insert fails -- at query
   execution, not even at commit:

     [CNT9] Constraint '@unique' has been violated: there is a
     conflict for value '"contested"'.
     Caused: [DVL9] Instance ... of type 'extra_id' has a key
     constraint violation for attribute ownership of 'id', since it
     is not the unique owner of attribute '"contested"'.

   So 'tx.query(...)' returns Err, 'create_one_node_in_own_tx'
   propagates, 'create_all_nodes' returns Err, and 'full_init'
   dies at init.rs:309-313 with "Failed to populate TypeDB: ..."
   and 'exit (1)'. 'check_for_duplicate_ids_across_sources' never
   runs. Confirmed as hypothesized.

   Two aggravations I had not anticipated. The error names the
   contested VALUE but neither claimant, so it is strictly less
   useful than the report it preempts -- and 'create_all_nodes' uses
   'buffer_unordered', so WHICH of the two nodes fails is itself
   nondeterministic.

** DONE Result B: pid vs extra_id -- TypeDB ACCEPTS, silently

   Node 'pid-c' with extra_id 'pid-d', then a separate node whose
   pid IS 'pid-d'. Both commit cleanly. '@key' uniqueness is per
   owner type, and 'node' and 'extra_id' are different types, so
   nothing stops one id from being a node's key and another node's
   extra id at once. Confirmed as hypothesized.

   The consequence is worse than "the check catches it late". While
   that state exists, id resolution is genuinely ambiguous and the
   layers disagree: 'pid_and_source_from_id'
   (server/dbs/typedb/search.rs:209-221) matches on an 'or' over
   "node has id X" and "extra_id has id X", so it returns TWO rows;
   the in-Rust graph's 'pid_of' (in_rust_graph.rs:144-149) checks
   'nodes . contains_key' FIRST and returns one. Production never
   runs in that state today only because init exits afterward -- but
   it builds both databases from it first.

** DONE What should skg-migrate-to-telescopes do about title placement?

   'skg-migrate-to-telescopes' today raises every owned edge's
   privacy to at least its default level and rebuilds the databases
   (docs/telescopes.md, "What leaks, and what migration fixes"). It
   says nothing about where titles sit.

   With the rule adopted, migration could also repair title
   placement, and there are two opposite repairs for the same shape.
   Given an owned titleless section MORE PUBLIC than the title:

   - HOIST: move the title (and body) up into the more public
     section. Makes the node's text as public as its most public
     section already is.
   - COLLAPSE: fold that section's contents down into the titled one
     and delete the now-empty file. Keeps the node's text as private
     as it was.

   These have opposite privacy consequences, and the tool cannot
   guess which you meant -- HOIST publishes text that was private,
   which is the one direction a migration should never take
   unasked. My instinct is that migration should COLLAPSE (it never
   publicizes anything, matching the rest of the migration's
   direction of travel) and that HOIST should exist only as a
   deliberate per-node gesture, if at all. But this is a product
   call about your data, not a code call, so I am asking rather than
   assuming.

   A third possibility: migration REPORTS these and repairs
   nothing, on the grounds that a shape this rare deserves a human
   look. That is the most conservative option and I would not argue
   against it.
