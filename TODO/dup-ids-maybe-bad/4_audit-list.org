#+title: The one-ID-one-file audit list

  TODO/DONE/privacy-telescope/4_discussion.org asked for this and
  never got it:

    Unlike adding a =NodeRelation= variant (exhaustive matches), the
    "an ID has exactly one file/source" assumption hides in ordinary
    code ... A written audit list of these sites, checked off during
    implementation, is the only protection; budget for it explicitly.

  Its absence is why 'source_from_disk' survived the telescope work
  unnoticed. This is that list, checked off. It names the sites the
  discussion predicted, plus the ones found since.

  STATUS values:
  - RESOLVED :: the site now asks a telescope-shaped question.
  - BY CONSTRUCTION :: the site never assumed one file; recorded so
    the next reader need not re-derive that.
  - STILL ASSUMED :: open. (None as of this writing.)

* Sites the discussion predicted

** RESOLVED init's duplicate check
   'error_unless_each_id_names_one_node'
   (server/dbs/filesystem/multiple_nodes.rs). Narrowed to "one id
   claimed by two DISTINCT pids" during the telescope work, but kept
   the old name and messages until now, which is how it went on
   reading as a check against telescopes. Renamed, remessaged, and
   moved ahead of database population.

** RESOLVED the daily audit
   'server/dbs/in_rust_graph/audit.rs' compares each pid's
   'node.source' in the in-Rust graph against TypeDB's 'has_source'.
   Both are the HOME, one per node -- TypeDB never held per-section
   rows (schema.tql: 'has_source ... @card(1)', and edges are stored
   unleveled). So the comparison is telescope-correct as written.

** RESOLVED diff analysis's duplicate bucket
   'duplicate_id_reports' (server/diff_analysis/diff.rs) reports only
   an id claimed by two distinct pids; endpoints are compared as whole
   telescopes (sections grouped by pid and folded). Done during the
   telescope work; api-and-formats.md says so explicitly.

** RESOLVED source_from_disk
   Now 'home_from_disk' (server/types/phantom.rs). It walked
   'config.sources', a HashMap, and returned the first directory
   holding '<pid>.skg' -- an arbitrary section, chosen by an order
   Rust randomizes per process, for any node with more than one.
   Consumers read it as the HOME, including the computation of a new
   edge's default privacy level. Walks 'ordered_sources' now.

   This is the site the audit list was supposed to catch.

** RESOLVED pid_and_source
   'InRustGraph::pid_and_source' reads 'node.source', which the fold
   sets. Ambiguous while the home was "the most public TITLED
   section" (a titleless section above it was silently skipped);
   unambiguous now that the home is the most public section, full
   stop.

** BY CONSTRUCTION get-file-path
   'path_from_pid_and_source' (server/util.rs) takes the source as an
   argument, so it never guesses which section is meant -- the caller
   must say. Nothing to fix; the type already asks the right question.

** RESOLVED delete-propagation
   'delete_all_nodes_from_fs' (server/dbs/filesystem/multiple_nodes.rs)
   sweeps every OWNED level for the pid, so deleting a node deletes
   its whole telescope. Done during the telescope work.

** RESOLVED stage-moves
   Redefined during the telescope work around TITLE presence rather
   than file presence: a node moved iff its title vanished from
   exactly one source and appeared in exactly one other. Titleless
   section creations and deletions are re-levelings of individual
   relationships, and stage as ordinary edits.

* Sites found since

** RESOLVED deleted_ids_to_source
   server/serve/handlers/save_buffer.rs. Maps a deleted node's id to
   its source by walking 'source_diffs' (a HashMap) and letting the
   last writer win. Deleting a node deletes every owned section, so
   one id routinely appears as deleted in several sources at once,
   and the reported home was chosen by hash order. Walks the privacy
   order now, keeping the most public.

** RESOLVED write_nodecomplete_telescope's ownership claim
   server/dbs/filesystem/one_node.rs. Its doc comment promised
   foreign sections are never written; the write loop checked
   nothing (only the delete sweep did), so the promise lived in the
   callers. With the home definitionally the most public section, a
   foreign home is conceivable, so
   'error_unless_home_is_writable' enforces it at the writer.

** RESOLVED the fold's own home search
   'fold_sections' (server/telescope/fold.rs) searched for the most
   public section BEARING A TITLE. That is the two-notions-of-home
   problem in miniature, and every read path wanting the home had to
   repeat or approximate the search. The home is now the most public
   section; a title below it is 'FoldWarning::TitleBelowHome'.

** RESOLVED pid_and_source_from_id's disjunction
   server/dbs/typedb/search.rs. Not a one-file assumption but the
   same shape: an 'or' over "node has id X" and "extra_id has id X",
   taking whichever row came first, so a database in which one id is
   both answered differently from the in-Rust graph. Prefers the node
   branch now, matching 'pid_of'.

* The structural fix

  Each entry above was a function that could answer a one-file
  question about a many-file node without anything forcing it to say
  which section it meant. Grouping the same-pid files ended in an
  anonymous 'HashMap<ID, Vec<(SourceName, NodeFS)>>'.

  It ends in a 'Telescope' now (server/telescope/types.rs), which is
  what 4_discussion.org asked for:

    Making "several files, one node" a type, not a condition, is what
    keeps the scattered-assumption sweep from regressing later: new
    code meets =Accordion=, not a surprising second file.

  A 'Telescope' knows its sections are in privacy order and that its
  home is the first of them. A function that wants one section has to
  choose one.

  This list should still be extended, not retired: a type prevents
  the shape from being invisible, not from being written.

* August 2026 follow-up: disk selection and response boundaries

  This is a new pass prompted by the work planned in [[./7_plan.org]].
  The July entries above remain the historical one-ID-one-file audit;
  they are not being rewritten as if they had covered the later
  owned-pid normalization and text-release questions.

** Disk-selection inventory

   The shared rule now runs before a telescope can become semantic
   data: if a PID has at least one owned section, retain the complete
   owned telescope and ignore every same-PID non-owned section; if it
   has no owned section, retain the wholly foreign telescope. Ignored
   files are warned about deterministically and left untouched. In
   particular they cannot contribute title, body, aliases,
   relationships, extra IDs, or ID-conflict claims.

   Checked consumers:

   - RESOLVED bulk live-disk reads:
     'read_all_skg_files_from_sources_collecting_violations' normalizes
     each same-PID group before constructing/folding a 'Telescope'.
     Initialization, rebuild, and export inherit that boundary.
   - RESOLVED one-PID reads: 'telescope_from_disk' applies the same
     normalization before construction. Save preflight, Hoist rereads,
     and single-node filesystem callers inherit it.
   - RESOLVED home lookup: 'home_from_disk' chooses the most-public
     RETAINED section after normalization, never a raw map entry.
   - RESOLVED git snapshots: 'diff_analysis/snapshot.rs' normalizes
     same-PID blobs independently at each endpoint before folding or
     computing extra-ID claims. Both worktree/index reads and tree/blob
     snapshots use the rule.
   - BY CONSTRUCTION output writers receive checked, private
     'Telescope'/'PreparedTelescopeWrite' values. Their fields cannot be
     replaced with unchecked raw section vectors, and the batch
     ownership preflight proves every destination writable before the
     first mutation.

** Text-response inventory

   The positive inventory -- endpoints that can return a title, body,
   alias, or view text -- is checked at its final response boundary:

   - RESOLVED direct content views and override-choice menus
     ('single_root_view');
   - RESOLVED text search before its Tantivy query, with the explicit
     include/exclude choice carried through asynchronous enrichment;
   - RESOLVED readable-ID title lookup ('titles_by_ids'), including
     titles recovered from git diffs;
   - RESOLVED org export, both the interactive server endpoint and the
     noninteractive CLI flag;
   - RESOLVED diff analysis: restricted sets are refused, while 'all'
     reports add the warning when their snapshots contain overPrivateText nodes;
   - RESOLVED rerender-all, source-set switching, and diff-mode
     toggling: all output is staged in memory, authorized, and only then
     installed/streamed; a challenge is followed by an empty rerender
     stream to unwind client locks;
   - RESOLVED save-result and collateral rerenders: the save can already
     be committed, but text and open-view registry mutations remain
     staged until the response is authorized.

   A restricted direct response uses exact PID approval and carries no
   authority into a later request. Search is deliberately different: it
   asks include/exclude before matching and its challenge contains no
   PIDs, because matching identities are themselves unreleased. The
   reserved source-set 'all' releases overPrivateText text with the same warning.

   Negative inventory -- initialized endpoints that do not return graph
   title/body text -- needs no text-release challenge: verify/close/shutdown,
   list/current source-set, edge-source-info, get-file-path, herald rules,
   rebuild, strip-body-whitespace, and stage-moves. Their replies contain
   status, source/path metadata, presentation rules, or a staging script,
   not protected title/body text. Save lock messages and the Hoist and
   release decisions are text-free too. Fork confirmation can contain
   node text, but Hoist preflight precedes it, so an overPrivateText disk input cannot
   reach that response without its exact publication approval. The
   pre-initialization busy signal contains only server status.

   RESULT: no text-output path found in this audit knowingly bypasses
   the central policy. Interactive clients retry with narrowly scoped
   authority; maintenance paths fail closed, and the export CLI requires
   its explicit inclusion flag.
