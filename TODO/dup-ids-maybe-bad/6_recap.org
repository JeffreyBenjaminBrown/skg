* What prompted the branch

  The phrase "duplicate IDs across sources" had become dangerously
  backwards after privacy telescopes were introduced.

  A privacy telescope is one logical node represented by same-pid '.skg'
  sections at several privacy levels. Therefore the same pid appearing in
  several sources is normal and is the feature.

  The actual error is an ID CONFLICT: one id, whether a primary id or an
  extra id, is claimed by two DIFFERENT pids. Such a conflict need not span
  sources at all.

  The existing check already made that distinction correctly, but its
  name, messages, report filename, tests, and surrounding comments said
  "duplicate IDs across sources". That had misled two readers and left a
  stale generated report in real data describing nine healthy telescopes
  as errors.

  The investigation then found a real bug hidden by the same old mental
  model: 'source_from_disk' walked 'config.sources', a randomized HashMap,
  and returned the first source containing '<pid>.skg'. That was harmless
  when one pid meant one file. With telescopes it returned an arbitrary
  section, while every caller interpreted the answer as the node's HOME.
  Some callers use that home to choose the privacy floor at which a new
  relationship is written, so this was latent nondeterminism on a
  privacy-sensitive path.

  The deeper goal consequently became more than a rename:

  - separate the valid telescope shape from a two-node ID conflict;
  - make HOME mean one deterministic thing everywhere;
  - surface malformed telescope shapes without bricking a pull;
  - reject unsafe writes;
  - move ID-conflict detection ahead of database population;
  - represent "several files, one node" with a named type so the old
    one-file assumption is harder to repeat;
  - audit the known sites where that assumption might survive.

  The full reasoning, including the TypeDB experiment, is in
  [[./1_discussion.org]].

* What is done

** The vocabulary now says what the code means

   'check_for_duplicate_ids_across_sources' became
   'error_unless_each_id_names_one_node'. User-facing messages and the
   generated report consistently say "id(s) claimed by more than one
   node". The report is now
   'initialization-error_ids-claimed-by-two-nodes.org', and each conflict
   names its claimant pids as well as their homes.

   The important negative fact remains tested: same-pid sections in two
   sources fold into one telescope and are not an ID conflict.

** Stale generated reports are removed

   A clean run removes the new ID-conflict report and
   'initialization-error_unreadable-skg-files.org', matching the existing
   behavior of 'telescope-warnings.org'. Therefore the presence of any of
   the current report filenames describes the most recent run.

   One deliberate exception is the RETIRED filename
   'data/initialization-error_duplicate-ids.org'. The new code neither
   writes nor removes that old name. See "Data cleanup" below.

** Home selection is deterministic

   'home_from_disk' walks 'SkgConfig::ordered_sources' from most public to
   most private and returns the first existing section. The fold uses the
   same definition: the first, most-public section is the home, whether or
   not it contains the title.

   A title below home is no longer silently searched past. It produces a
   'TitleBelowHome' fold warning; no title anywhere remains a hard load
   error, unchanged from before this branch.

** Load-time warnings reach the user-visible report

   The new
   'read_all_skg_files_from_sources_collecting_violations' returns fold
   warnings and foreign-overlay warnings to init/rebuild. They are merged
   with graph-level telescope invariants and written to
   'telescope-warnings.org'. This generalized the plan slightly: every
   'FoldWarning' is reported, not only the two newly interesting shapes.

** Full initialization rejects ID conflicts before populating databases

   This matters because the TypeDB experiment found two different failure
   modes:

   - two 'extra_id' entities claiming the same value make TypeDB fail first
     with a raw uniqueness error that names neither claimant;
   - one node's pid equaling another node's extra id is accepted by TypeDB,
     even though id resolution becomes ambiguous.

   Full init now runs the readable Rust check before writing either TypeDB
   or Tantivy. Rebuild already had the safe ordering. The incremental path
   caveat remains below.

** Unsafe text placement is refused at write time

   The writer refuses a node whose home is foreign, rather than dropping
   the title or trying to modify a foreign home. It also refuses a write
   that would put the folded title into an already-existing titleless home,
   because that would silently publish text from a more-private section.

   This is the safe interim REFUSE policy. It is intentionally not an
   automatic repair.

** The two id resolvers agree in degraded state

   A pid/extra-id collision is now refused before normal startup, but if a
   database somehow contains one, 'pid_and_source_from_id' prefers the row
   whose primary id is the queried id. That matches 'InRustGraph::pid_of'
   instead of accepting TypeDB row order as an answer.

** The obsolete migration is out of the live product

   'skg-migrate-to-telescopes' was a one-user, one-time migration and had
   already served its purpose. Its code is preserved in the graveyard with
   resurrection notes; the live protocol/client/docs no longer advertise
   it. Per-edge repair now points to 'skg-set-relationship-source'.

** The load boundary has a 'Telescope' value and an audit artifact

   Same-pid files are grouped into 'Telescope { pid, sections }' before
   folding, replacing anonymous vectors at the main load sites. The type
   supplies home/extra-id/misc helpers and makes the many-file shape
   visible to callers.

   [[./4_audit-list.org]] records every one-ID-one-file assumption checked
   during the arc. It marks none still assumed and found the separate
   'deleted_ids_to_source' HashMap-order bug, which was fixed.

*** DONE (C to J)

'Fold' and 'unfold' are the two directions between disk and memory:

- To fold is to read all of one node's section files and combine them into
  one in-memory node. For example, U/u.pid.skg plus R/u.pid.skg become one
  'NodeComplete' for u.
- To unfold is the reverse operation used when saving: take that one
  in-memory node and split its data by privacy source, producing the
  section contents to write back to U/u.pid.skg, R/u.pid.skg, and so on.

A 'levelled member' is one item that carries both its value and the source
where it belongs. In the Rust type 'PrivaciedMember<T>', 'member' is the
value -- for example, child x's ID in u's contains list, or an alias string
-- and 'level' is a source name such as U, R, or F. During unfold, level R
means "put this item in u's R section."

'Survive' was vague shorthand and I should not have used it. I meant that,
after buffer parsing, supplementation from disk, sticky/default level
resolution, and validation, the item still has level F when the writer
starts. Nothing dropped it, moved it to an owned level, or rejected the
save. The problematic sequence is therefore:

1. u is an owned node whose home is U.
2. One of u's members reaches the writer tagged 'level = F'.
3. Unfold places that member in the proposed F section of u.
4. The current writer checks that U is owned, but not that F is owned, and
   attempts to write F/u.pid.skg.

The proposed all-output preflight rejects at step 4 before writing any
section.

Before any filesystem write, 'buffer_to_validated_saveplan' validates the

the write phase is not entered.

On the load side, the named type makes the operation look roughly like:

  'fold_telescope(Telescope) -> NodeComplete'

Even before we strengthen its private fields and constructor, the type
communicates that the input is one pid's complete collection of sections,

The save side currently looks roughly like:

  'unfold_node(UnfoldInput) -> Vec<(SourceName, SectionSlices)>'

That return value is only a generic vector. Its type does not say that the
sources are configured, unique, ordered, or owned; that the first section
is home; or even which pid the collection belongs to. The writer supplies
the pid and other file fields separately and trusts the vector's shape.

'fold(unfold(x)) == x' names the round-trip law we want: take a valid
in-memory node x, split it into telescope sections, then fold those
sections again, and recover the same effective node (allowing only

The invariant I would put in the type is narrow: a 'Telescope' is a
nonempty collection of sections for one pid, with each source configured,
no source repeated, and the sections strictly ordered from most public to
most private according to this 'SkgConfig'. If a value exists, 'home()' is
therefore unambiguously its first section. Content problems such as
'TitleBelowHome' and dangling anchors remain fold violations; the
constructor should not conflate those with structural ordering.

Concretely:

1. Make both fields (PID and sections) private.
   Expose 'pid()', 'home()', 'sections()' as an
   immutable slice if inspection is needed, and a crate-private consuming
   'into_parts()' for the fold. Do not expose a mutable section vector or
   permit struct literals outside 'telescope::types'. This makes it
   impossible for later code to reorder or append sections behind the
   type's back.

2. Add a checked constructor along the lines of
   'Telescope::try_new(pid, sections, config)'. It returns a typed error,
   rather than panicking, if a section's embedded 'NodeFS.pid' differs
   from the telescope pid, a source is absent from the config, a source is
   duplicated, the order is not strictly increasing, or the vector is
   empty.

3. Stop using an empty 'Telescope' to mean "not found". The single-node
   disk reader should return 'Option<Telescope>' internally and translate
   'None' into its existing NotFound result. That lets nonemptiness be a
   real type invariant rather than a comment that most consumers must
   remember.

4. Route all four current construction sites through the constructor: the
   one-node disk reader, bulk initialization's grouped-section fold, the
   normal diff snapshot fold, and the diff snapshot's titleless fallback.
   The latter two need 'SkgConfig' threaded into their grouping helpers;
   they currently discard it before constructing the value. The titleless
   retry would construct a fresh checked telescope after changing only the
   first section's placeholder title.

5. Compute source positions once per construction (or once per load) from
   'ordered_sources', then scan sections once. That makes validation
   O(S + k), for S configured sources and k sections. My earlier shorthand
   "O(k)" assumed this position lookup. Calling the current
   'source_position' afresh for every section would instead do avoidable
   repeated scans and clones, O(kS), though the absolute numbers would
   still be small.

6. Add constructor tests that accept a valid telescope and reject: reversed
   order, duplicate source, unknown source, mixed pid, and empty input.
   Existing fold tests then continue to establish semantic behavior. A
   focused disk-reader test should show that a missing pid still reports
   NotFound after the 'Option' change.

This closes the present encapsulation hole with a small surface change:
there are only four struct-literal construction sites, and external code
does not currently read 'sections' directly. It does not solve the other
debt noted just above -- 'unfold_node' still returns a bare vector. A later
step could make unfold produce a checked telescope-shaped output too, but
I would keep that separate from this load-side invariant change.
