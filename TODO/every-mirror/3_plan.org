* Open questions for Jeff
** Q1. Several mirrors in the skgrepo that decides
*** Settled by Jeff (2026-11-16): the note itself; any remaining tie however is convenient
"the note itself. And where it's still ambiguous -- say, my skgrepo R
holds F and G which both fork Q from another repo, and we have to
decide how to show Q -- pick arbitrarily in whatever way is
convenient." So the provisional rules hold; the later tie rules may be
simplified if that is easier, as long as the choice is deterministic.
Slice 1. Decision D says which skgrepo decides: the perspective's, or
else the first the config lists that holds a mirror. It does not say
which mirror stands when that skgrepo holds several (two forks of one
note in one skgrepo, which plan 1 made legal, or an owned chain D forks
C forks N kept in one skgrepo). Today 'first_ranked_mirrors' and
'mirror_shown_among' ('server/dbs/in_rust_graph/mirrors.rs') break such
a tie by plan 1's rules: one mirror alone there; else the only one
none of the others forks (so the chain shows D in N's place); else N
itself; else the nearest, then the least pid.
*** Provisional
N itself, when N is homed in that skgrepo; else the only one there
that none of the others forks; else the nearest to N along forks, then
the least pid. Rule 2 and rule 3 trade places: a fresh view of N,
whose perspective is N's home skgrepo (decision D), must show N itself
('docs/glossary.org', "override substitution" now "mirror
substitution": "A view opened on one node always shows the requested
node itself"), and roots now substitute under every perspective
(behavior 1). The cost: an owned chain kept in one skgrepo shows N,
not D, wherever the perspective is that skgrepo; D stands where N's
skgrepo is not the perspective's and D's is first.
** Q2. The order within a flat forks folder
*** Settled by Jeff (2026-11-16): as provisional
Slice 2. Decision A orders the folder "first what it forks, then what
forks it, then the rest of the family, nearest first"; decision D puts
"the other mirrors ... in its forks folder in config order". The first
group is the note's own 'forks' list, whose order the user edits there
today ('Goal::ordered_then_unordered' in 'server/refresh/goal.rs': an
ordered head the save writes back, an unordered tail kept as the view
has it).
*** Provisional
The notes it forks in its list's order (editable, as today); then the
forker-only members, by the declaration order of their home skgrepos;
then the indirect members, nearest first, and among equals by the
declaration order of their homes, then pid. Both tails are ordered
now (the refresh moves a member there), since the order is the
graph's and the config's, not the user's.

* Vocabulary
Checked against 'docs/glossary.org' and the code at 0d2d650e
('coding-advice/names.org', "Check a plan's words before the run").
** perspective (redefined)
A view's perspective is a skgrepo, the view's own once the user
chooses one (C-c v o), or, until then, each top-level tree's root's
home skgrepo ("root homes"). It decides which mirror stands in a note's
place. Today it is an owner ('Perspective::Owner (SkgrepoOwner)') or
each tree's root's author ('Perspective::RootAuthors').
** a perspective's skgrepo list (redefined)
The perspective's skgrepo first, then every skgrepo in the config's
declaration order ('SkgConfig::skgrepos_in_declaration_order'), whose
owned entries run most public first. Today
'SkgConfig::perspective_skgrepo_list' puts an owner's skgrepos first,
most private first.
** root homes (coined)
The default perspective: each top-level tree from its root's home
skgrepo, the root standing for its '(inPlaceOf N)' else itself (as
'perspective_owner_of_tree_containing' finds the root today). The
wire's name for it: "root homes".
** flat forks folder
The forks folder ('Folder::Forks', atom 'forksFolder') as decision A
makes it: every mirror of its note under the skgrepo restriction, each
once, the note itself and those it hides excepted.
** direct member, indirect member (coined)
A *direct member* of N's forks folder is a fork partner of N (N forks
it, or it forks N; a mutual both). An *indirect member* is a mirror of
N joined to N only through other mirrors. An indirect member claims
nothing, as a forker-only member does (decision B).
** member as such, forker as such
Unchanged: a member as such is a warranted member of a forks folder; a
forkee as such claims, a forker as such claims nothing
('docs/glossary.org'). Since an indirect member claims nothing too, the
code's claim-based "forker as such" ('note_of_forker_as_such',
'LocalContext::ForkerAsSuchPosition', 'MemberAsSuch::Forker') holds of
it. Where the difference matters (the hidden-by folder, messages), the
code asks the graph; the glossary's entry says a forker as such is a
forker-only or an indirect member, and the messages say "a member that
claims nothing" where either may be meant.
** integrated, integrated elsewhere (redefined, coined)
A note's content is *integrated* by the user when an owned note
contains it, by a record the skgrepo restriction shows (decision C:
"my graph" is every note in the user's owned skgrepos), or when the
note whose forks folder shows the member contains it. Today
"integrates" means "the note contains or hides"
('less_what_the_note_integrates', 'server/refresh/goal.rs'). The
folder of what a member's content holds that the user integrated
elsewhere: 'Folder::IntegratedElsewhere' (atom
'integratedElsewhereFolder', coined).
** what a member shows (redefined)
A member as such M of N's forks folder shows M's content less what N
hides, less what N contains, less what any owned note contains
(decision C). '(unintegrated COUNT)' counts it, as today.

* Agreed behavior
** Jeff's decisions (2026-11-16)
*** A. Flat forks folders
"if a forks b, then b will show under a's forks, and then a will show
under b's forks. That's silly. Since forking is now transitive, we
don't need to restate them like that. Nothing in a forks folder should
itself contain a forks folder, unless the user specifically requests
one there."
*** B. Indirect mirrors
A mirror joined to the note only through others is treated as a
member claiming nothing, as a forker-only member is: deleting it hides
it; cutting from it makes the note fork it; its content shows what the
note neither contains nor hides; no K herald toward the note. Every
member of the forks folder explains a hide alike ('fork_partners_shown'
should mean the folder's members).
*** C. Hides by integration
"If I move your a to my x or under my y, there is no need to create a
hide relationship. Skg can determine that it should hide my view of a
under my view of your x by recognizing that a is integrated into my
graph: it is contained by some node in my graph. The hide relationship
is only needed if I delete your a from under your x, without making
one of mine contain it. Under your x I should see up to [two] kinds of
hide-related folders now: Things I have hidden, and things I have
integrated into my graph." "My graph" is every note in the user's
owned skgrepos, as the skgrepo restriction shows them. The folder of
what is integrated is write-protected, each member carrying a
containers folder showing where the user keeps it, and stands before
the hidden folder.
*** D. Perspective is a skgrepo
"it has to be skgrepos, not authors, because what if I have two forks
of something, one private and one public? I have to be able to choose
either. The forks-as-such can be ordered and deduplicated according to
their order in my skgconfig, but the chosen perspective is special."
"Every buffer should have a 'user perspective', which is some skgrepo.
Usually you see things from your own POV because you open buffers from
your own graph. But if you open a buffer from someone else's, you
should see it from theirs, until you request a different POV." With
perspective S, a note's mirror in S stands in its place; with none in
S, the mirror in the skgrepo the config lists first; the other mirrors
are in its forks folder. A fresh view's perspective is its root note's
home skgrepo. C-c v o cycles through the skgrepos that hold a mirror of
something in the view. The config's own order stands, so after the
chosen skgrepo a public fork outranks a private one.
*** E. Out of scope
Label wording, the migration and the server switch, 'TODO/problems.org'
entries not named here.

** 1. The perspective is a skgrepo (decision D)
*** What decides it today
'Perspective' ('server/types/views_state.rs') is 'RootAuthors' or
'Owner (SkgrepoOwner)'; 'perspective_owner_of_tree_containing'
('mirrors.rs') gives the owner a tree is drawn from: the view's owner,
or the owner of the tree's root's original's home skgrepo.
'mirror_shown' ranks a note's mirrors by
'SkgConfig::perspective_skgrepo_list' ('server/types/misc.rs': the
owner's skgrepos most private first, then the rest in declaration
order) and breaks ties by 'first_ranked_mirrors'. 'substitute_roots'
('server/refresh/visit.rs') shows a root raw under 'RootAuthors' and
substitutes it under an owner's perspective; 'substitute_mirrors'
substitutes content children of an editable occurrence under either.
*** What it should be
- 'Perspective' should be 'RootHomes' or 'Skgrepo (SkgrepoName)'.
  'perspective_owner_of_tree_containing' becomes
  'perspective_skgrepo_of_tree_containing': the view's skgrepo, or the
  home skgrepo of the tree's root's original (its '(inPlaceOf N)',
  else itself); where that root is no occurrence of a node the graph
  knows, the config's first owned skgrepo in declaration order.
- The skgrepo list of a perspective S: S, then every other skgrepo in
  declaration order ("Vocabulary"). 'SkgConfig::perspective_skgrepo_list'
  takes a skgrepo, not an owner.
- The mirror shown for N: the first skgrepo of that list holding a
  mirror of N decides, its tie broken as Q1 says. The owner of the
  skgrepo plays no part; so 'SkgrepoOwner' leaves the substitution.
- Roots: 'substitute_roots' treats a root as any substitution position
  under both perspectives. Under 'RootHomes' a single-root view shows
  its root itself (by Q1's first rule), as every fresh view does; a
  search buffer's hits each stand in their own home skgrepo, so each
  shows as itself, as today.
- The cycle (C-c v o, 'perspective_to_show' in
  'server/serve/handlers/perspective.rs'): 'RootHomes' first, then the
  skgrepos home to a visible mirror of an original at a substitution
  position ('candidate_owners' becomes 'candidate_skgrepos';
  'original_at_substitution_position' unchanged), in declaration order
  ('perspective_rank'); a skgrepo whose drawing equals the root homes'
  is passed over, as today an owner's is ('in_the_cycle'), so that no
  press changes nothing. "Something in the view" is read as an original
  where substitution acts: a mirror of anything else draws nothing
  differently.
- The wire: '(perspective . NAME)' in "set perspective", its answer and
  the save, where NAME is "root homes" or "skgrepo S" (S any configured
  skgrepo, owned or foreign; 'Perspective::wire_name' and
  'from_wire_name'). "root authors", "user" and "owner of NAME" are
  refused as unknown names (no legacy reading). A save with no
  '(perspective ...)' means "root homes", as it means "root authors"
  today ('perspective_from_save_request', 'save_buffer.rs').
- Messages ('perspective_name', 'name_of_owners_perspective'): "the
  perspective of S" (S's skgrepo label, 'herald_label'), and for the
  default "each root's home skgrepo (S1, S2)". Wording provisional
  (decision E).
- Everything that asks an owner of a tree today asks its skgrepo:
  'inPlaceOf_part_errors' ('validate_tree.rs', its refusal naming the
  mirror shown), 'forks_the_view_will_not_show' ('fork.rs', which also
  warns for a fork of a root in a view switched to a skgrepo where the
  clone is not shown: today it skips roots, since a root fork re-roots
  the view, but under a skgrepo perspective the re-rooted clone is
  substituted like any root), the fork confirmation's perspective
  words, 'perspective_name', 'candidate_skgrepos'.
- The search's suppression ('suppressed_result_gnids', 'text_search.rs')
  ranks the hits that are mirrors of one another by the user's own
  list: the config's first owned skgrepo, then declaration order
  ('hit_standing_among' through 'first_ranked_mirrors' with that
  skgrepo); it suppresses the others only when the one standing is
  owned, as today. So among owned hits a public one stands over a
  private one, where today the private one does.
- The search buffer is drawn under 'RootHomes' ('draw_search_buffer'),
  where it is drawn under 'RootAuthors' today.
*** The clients and the AI tool
- Emacs: 'skg-perspective' holds nil (root homes) or "skgrepo S";
  'skg--set-perspective' treats "root homes" as nil; the mode line
  shows the server's name once switched; 'skg-cycle-perspective' (C-c
  v o) and its handler unchanged but for their docstrings
  ('elisp/skg-buffer.el', 'elisp/skg-request-perspective.el',
  'elisp/skg-request-save.el', 'elisp/skg-request-text-search.el').
- Neovim: the same in 'nvim/lua/skg/buffer.lua',
  'nvim/lua/skg/perspective.lua', 'nvim/lua/skg/save.lua'.
- The AI tool ('tools/skg-for-ai/skg_for_ai.py'): 'DEFAULT_PERSPECTIVE'
  is "root homes"; the 'perspective' command takes "next", "root
  homes" or "skgrepo S"; the sidecar key 'perspective' keeps its name
  and holds the new names; a sidecar with an old value ("user", "owner
  of NAME") is read as the default, as one without the key is
  ('perspective_of_sidecar'). On 2026-11-16, 1133 of the saved
  sidecars under 'data/claude/views/' held the older key
  'overrides_followed' and none held 'perspective'; all read as the
  default.

** 2. Flat forks folders (decisions A and B)
*** What decides it today
'forks_folder_goal' ('server/refresh/goal.rs') holds N's forkees (its
list, ordered, claimable) then its forker-only members
('forker_only_members': the notes forking N that N neither forks nor
hides), unordered. 'add_default_folders' ('visit.rs') gives every
editable occurrence carrying an editable-view request its forks
folder, a member as such included, so each editable member shows its
own forks folder, N in it. The search buffer ('draw_search_buffer',
'text_search.rs') draws each hit's forks folder, then asks notes on a
shortest fork path for their own forks folders until every suppressed
mirror of the hit stands ('request_forks_folders_toward_suppressed_hits',
'fork_path_parents', 'fork_partner_it_stands_among',
'fold_nested_forks_folders').
*** What it should be
- The goal: N's forkees in list order (claimable); then its
  forker-only members; then its indirect members, every other mirror
  of N ('mirrors_of', 'mirrors.rs') that N does not hide; each tail
  ordered as Q2 says. None claimable but the forkees. A mirror reached
  only through a note N hides is still a member: the hide leaves out
  that note alone.
- An indirect member, as decision B says: drawn as a forker-only
  member is (claiming nothing, warranted by the goal, a member as such
  with its containers folder, editable under an editable N as the
  budget allows); no birth facts (its roles toward N are none:
  'birth_facts_of_fork_roles'); its relationship heralds name no
  ancestor 2 on the 'forks' sides, so no =K= toward the note (they come
  from the graph); its relRepo fact none, a relRepo request on it
  refused as on any member claiming nothing
  ('is_forks_folder_member_claiming_nothing'). Its content shows what a
  member shows. The folder of what a forker hides of the note
  ('Folder::HiddenByForker', 'hidden_by_forker') is drawn under a
  member claiming nothing only when it forks N: an indirect member's
  hides do not apply to N's content.
- No member of a forks folder draws a forks folder unasked:
  'add_default_folders' adds 'Folder::Forks' to an occurrence only when
  it is no member as such ('note_of_member_as_such'). A request (C-c l
  f, '(folder forks)') still draws one there. A forks folder already
  standing under a member in a buffer stays, as the refresh keeps what
  a buffer holds (a view request's folder cannot be told from an
  unasked one once drawn).
- 'fork_partners_shown' ('goal.rs') means the folder's members: the
  forkees, the forker-only and the indirect members. So their content
  explains a hide alike: the hidden-outside folder
  ('hidden_outside_of_fork_partners'), the hide inference from
  removals ('infer_hides_from_contains_removals'), the hidden-outside
  edits ('apply_hiddenoutside_edits'), the nodeMerge
  ('gnids_shown_through_fork_partners') and the hide report
  ('hide_report_lines') read it. The private function of the same name
  in 'mirrors.rs' (a note's visible direct partners, for the walk) is
  renamed 'visible_fork_relationships_of', so that one name means one
  thing. The hide floor ('hide_skgrepo', its "partners on record")
  keeps its wider set, as plan 2 decided.
- Deleting an indirect member hides it, as deleting a forker-only
  member does: 'resolve_forks_folder_removals' ('resolve_visibility.rs')
  reads every mirror of N the folder no longer shows, not only N's
  forkers.
- A cut from an indirect member makes N fork it and hides the child
  as a cut from a forker as such does ('resolve_forker_visibility'),
  which reads what the view drew under the member by
  'are_fork_partners' today: for an indirect member that answer is
  false, and it would read all of the member's content as shown, so a
  child the view never drew would count as cut. It asks instead
  whether the member is a mirror of N under the restriction
  ('is_mirror_of').
- The search buffer: one forks folder under a hit, flat as any, holding
  every suppressed mirror of the hit; the nesting machinery goes
  ('request_forks_folders_toward_suppressed_hits', 'fork_path_parents',
  'fork_partner_it_stands_among', 'fold_nested_forks_folders'), and
  'draw_search_buffer' refreshes once.
- Heralds: none new. A forkee shows =bK=, a forker-only member =Kb=, a
  mutual =bKb=, an indirect member neither 'b' flag ('docs/heralds.org',
  "Ancestor flags and floors").

** 3. Hides by integration (decision C)
*** What decides it today
What a member as such shows is its content less what N contains or
hides ('less_what_the_note_integrates' and 'unintegrated_content_gnids',
'goal.rs', through 'content_goal_gnids', which the stats pass counts
from too). A cut from a forkee as such hides each content child the
buffer no longer shows unless N contains it after the save (the
forkee-visibility step in 'resolve_visibility'); a cut from a forker
as such reads what the view drew, then hides the cut unless N contains
it after the save ('resolve_forker_visibility'); a child removed from
N's contains that a fork partner contains is hidden unless N contains
it after the save ('infer_hides_from_contains_removals').
*** What it should be
- What a member shows ("Vocabulary"): less N's hides, less N's
  contains, less what any owned note contains, each by records the
  skgrepo restriction shows. The owned containers are read from the
  graph's containment relmap ('inbound_pids_for_relation_gated' with
  'NodeRelation::Contains'), each container's home owned
  ('SkgConfig::skgrepo_is_owned'). N's own contains is subtracted even
  when N is foreign: what N already holds is integrated into N.
- The integrated-elsewhere folder, under an editable member as such
  ('add_default_folders'), first among the member's folders, before
  the hidden-in folder: M's content (visible records) that an owned
  note or N contains, less N's hides, in M's list order. Write-protected,
  drawn when nonempty, its members folded
  ('Walk::folders_whose_drawn_members_are_folded'), each member
  carrying a containers folder (folded, omitting view-ancestors, as a
  forks-folder member's does: 'add_containers_folder_under_forks_folder_member'),
  which shows where the user keeps it among its containers. Its members
  carry no chain directly. Birth facts '(contains in 2)'. Label
  provisional: "☮ It contains these, and you keep them elsewhere."
- A child both hidden by N and integrated stands in the hidden-in
  folder only: the hide is the explicit record, and that folder is
  where moving it out removes it.
- Existing hides that integration makes redundant are kept, harmless:
  each still stands in the hidden-in folder under the member that
  contains it, and nowhere else; moving it out unhides it, and it then
  stands in the integrated-elsewhere folder. No save removes such a
  hide by itself.
- Cuts: the forkee-visibility step reads a child as cut only if the
  view drew it (a content child of the forkee that N neither hid nor
  integrated before the save, by the graph), and hides a cut child
  only if no owned note contains it after the save; the
  forker-visibility step likewise (it already reads what the view
  drew; its "integrated" set gains the owned containers), and still
  makes N fork the forker or indirect member; the inference from
  removals hides only what no owned note contains after the save.
  "After the save": a note this save writes, by its contains as the
  save leaves it ('note_contains_after_save' and its kin in
  'lower.rs'); any other, by the graph.
- The hidden-outside folder is unchanged: N's hides that no member of
  its forks folder contains.
- The hide report ('hide_report.rs') says, for a child removed and not
  hidden because another owned note keeps it, which one ("but 'Y'
  keeps it", as it says today "but this save places it under 'E'").
- nodeMerge ('gnids_shown_through_fork_partners') reads what a member
  shows by the new rule (unrestricted, as now).
