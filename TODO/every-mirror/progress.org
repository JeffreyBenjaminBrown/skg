*** Deviations from the plan's "how"
**** Logs under 'tests/results/every-mirror/slice1-plan1/'
As the launch brief said, not the plan's 'every-mirror-1/slice1/'.
**** A refused section leaves its whole telescope unchanged
The plan leaves a refused file unchanged. The tool also leaves every
other section of that pid unchanged, and lists them: how the refused
section's relations pair with the others' is unknown, so migrating
them alone could append an override another section subscribes to.
**** More refusals than the plan names
Besides a flow-style list and an October 2026 key, a file is refused
if it holds a key twice, an old key beside its new one ('subscribesTo'
and 'forks', 'hidesFromSubs' and 'hides'), an anchor in 'overrides',
or keys to migrate but no readable 'pid'. Each would otherwise be
migrated into something the server misreads.
**** An existing 'forks' list pairs like 'subscribesTo'
So that a rerun after fixing a refused file, when other sections of
its pid were migrated in an earlier run, still drops an override that
a migrated section records.
**** 'HidesFromSubs' marks are renamed 'Hides'
The plan has the tool drop only marks of 'SubscribesTo' and
'Overrides'. Q10 renames 'NodeRelation::HidesFromSubs' to
'NodeRelation::Hides' in slice 7, after which a mark naming
'HidesFromSubs' would make the whole marks file unreadable (the
pitfall "The processed marks file is all or nothing"). The tool runs
after the plan, so it renames them; a relationship's fingerprint does
not include the relation name, so a renamed mark stays valid. Slice 7
must keep the variant's serialized name 'Hides' (serde's default).
**** The README's counts are recounted
The plan's table (jeff/public: 32 paired, 4 subscribe-only;
claude/public: 99 paired) was taken earlier on 2026-11-16. At 08:20
UTC the copies held more, since forks were made this morning:
Jeff's 49 paired, 4 subscribe-only, 0 override-only, 53 files changed;

*** What "forks" means here, until slice 5
The rules ('SelfFork', 'ForkeeContained', 'ForkerContained') read a
note's 'subscribesTo' and its 'overrides' alike ('FORK_RELATIONS' in
'server/dbs/in_rust_graph/override_invariants.rs'): slice 5 makes
every subscription and every override one 'forks' relationship, so a
rule over 'overrides' alone would admit now, from a subscription,
what the migrated data would then refuse at startup. Slice 5 replaces
the two-element constant with 'NodeRelation::Forks' and drops the
"(subscribes to or overrides)" in the messages.

The fork operation's guard (Q6) reads 'MIRROR_RELATION' (today
'overrides'): it asks whether the user already owns a mirror-making
fork of the note, which today is what the operation itself writes, and
slice 5 switches it with the mirrors in one place. A note of the
user's that only subscribes to N does not trip it until then.

*** Deviations from the plan's "how"
**** "No owned note contains it": the member itself excepted
Read literally, an owned member as such would integrate all its own
content (it contains it), and no cut from it could ever hide. So the
owned notes that integrate a child of member M are the owned notes
but M ('owned_notes_containing', its 'excepted'). Two members that
both contain a child, one of them owned, therefore differ: under the
foreign one the child is kept (by the owned one), under the owned one
it shows, unless another owned note keeps it too. The removal
inference ('infer_hides_from_contains_removals') follows: a child
removed from N is hidden only where some partner containing it would
show it after the save, that is, where no owned note but that partner
contains it then. The nodeMerge ('gnids_shown_through_fork_partners')
excepts the partner likewise.
**** "An owned note": its home owned, shown, its record shown
An owned note counts when its home skgrepo is owned, the skgrepo
restriction shows it, and shows its record of the child (the graph's
gated containment relmap). A note the save writes counts by its
contains as the save leaves them ('ContainsAfterSave', built by
'LoweredNodeIntents::contains_after_save' and, in the hide report, from
the plan); a note it deletes does not count; any other note, by the
graph. IDs are compared resolved, with no mirror substitution: a note
holding a fork of the child does not keep the child.
**** Placements run before the visibility loops
A child placed under a member as such joins its content
('add_children_placed_under_member_as_such'); that ran inside each
signal's loop. So that a child moved from one member into an owned
member in one save counts as kept whichever signal comes first, the
placements now run as one pass ('add_children_placed_under_members_as_such')
after the removal inference and before the two visibility loops.
**** The conflict check skips what was kept elsewhere
'validate_no_overlapping_forkee_hiderel_conflicts' compares, child by
child, what each forkee shows. A child one owned forkee keeps is
drawn under the other forkee's folder of what is kept elsewhere, not
as its content; read as "hide it" there, an unchanged save would have
been refused. A child kept elsewhere before the save, by the graph,
now says nothing there.
**** The diff view's content goal keeps the old rule
The plan: every rule here does nothing in the diff view. Since the
diff view draws no integrated-elsewhere folder, a member there keeps
what the user keeps elsewhere among its content
('less_what_the_note_integrates' takes 'kept_elsewhere_counts', false
there). The stats pass, which does not know the mode, counts
'(unintegrated N)' by the new rule in both (see "Unfinished").
**** An unwarranted member of the new folder vanishes
Unlike the hidden-in folder's members, which stay marked ⊥ in a
redrawn buffer, a member of the integrated-elsewhere folder that the
user no longer keeps elsewhere (removed from y, or kept out by a
narrowing) vanishes from it ('leaves_its_write_protected_folder'),
since the folder is derived each time from where the user keeps it;
the child is drawn among the member's content instead.
**** The folder's parties
'compound_folder_parties' gives the new folder the hidden-in folder's
places: its container is the member (its viewparent), its "hider" N
(three up), whose hides it leaves out. Its birth fact is
'(contains in 2)', its relRepo fact none.

"Hides nothing: 'R' left 'S', but 'Y' keeps it." names every owned
note but S keeping R after the save ("'Y' and 'Z' keep it"; "'Y'
keeps 'M', which it stands for" for a mirror). It is said only for a
removal from S's content, as the plan says: a cut from a member that
hides nothing because an owned note keeps the child prints no line,
as no line is printed today for a cut whose child S contains.
