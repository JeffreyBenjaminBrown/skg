*** Deviations from the plan's "how"
**** Logs under 'tests/results/every-mirror/slice1-plan1/'
As the launch brief said, not the plan's 'every-mirror-1/slice1/'.
**** A refused section leaves its whole telescope unchanged
The plan leaves a refused file unchanged. The tool also leaves every
other section of that pid unchanged, and lists them: how the refused
section's relations pair with the others' is unknown, so migrating
them alone could append an override another section subscribes to.
**** More refusals than the plan names
Besides a flow-style list and an October 2026 key, a file is refused
if it holds a key twice, an old key beside its new one ('subscribesTo'
and 'forks', 'hidesFromSubs' and 'hides'), an anchor in 'overrides',
or keys to migrate but no readable 'pid'. Each would otherwise be
migrated into something the server misreads.
**** An existing 'forks' list pairs like 'subscribesTo'
So that a rerun after fixing a refused file, when other sections of
its pid were migrated in an earlier run, still drops an override that
a migrated section records.
**** 'HidesFromSubs' marks are renamed 'Hides'
The plan has the tool drop only marks of 'SubscribesTo' and
'Overrides'. Q10 renames 'NodeRelation::HidesFromSubs' to
'NodeRelation::Hides' in slice 7, after which a mark naming
'HidesFromSubs' would make the whole marks file unreadable (the
pitfall "The processed marks file is all or nothing"). The tool runs
after the plan, so it renames them; a relationship's fingerprint does
not include the relation name, so a renamed mark stays valid. Slice 7
must keep the variant's serialized name 'Hides' (serde's default).
**** The README's counts are recounted
The plan's table (jeff/public: 32 paired, 4 subscribe-only;
claude/public: 99 paired) was taken earlier on 2026-11-16. At 08:20
UTC the copies held more, since forks were made this morning:
Jeff's 49 paired, 4 subscribe-only, 0 override-only, 53 files changed;
Claude's 103 paired, 0, 0, 103 files; 7 and 3 'hidesFromSubs' keys.
The README gives both rows and says the counts grow with each fork.

*** Deviations from the plan's "how"
**** Logs under 'tests/results/every-mirror/slice2-plan1/'
As the launch brief said.
**** The invariants module walks owned overriders itself
The plan keeps the invariants in force here but removes the resolver
they walked with. 'override_invariants.rs' got a small private walk
of owned overriders (the old resolver's, under the user, ungated) for
'OwnedOverrideCycle'; slice 3 deletes it with that violation.
**** Names renamed now
'override_follower_of_tree_containing' was renamed here, since the
plan says "renamed if Q8 renames the perspective" and Q8 does. The
substitution's functions in 'visit.rs' took mirror names (Q8 names
'substitute_mirrors') since they were rewritten. 'OverridesFollowed',
the wire names and '(overridesHere N)' are untouched (slice 8).
**** Ties where no original is given
'member_it_stands_for' has a set of members, not a list (the union of
several subscribees' contents), so "then the first in the list"
became "then the least ID". The search's grouping of hits has no
original N for Q3's rules 3 and 4: a tie left after rules 1 and 2
goes to the least pid. Reading "as if N were each hit in turn" with
rule 3 would leave a tied owned mutual pair both shown, against the
plan's "shows one hit, not none".
**** The fork warning sees the clone
'forks_the_view_will_not_show' runs on the graph before the save,
which lacks the clone, so it ranks the original's mirrors with the
clone added ('mirror_shown_once_cloned'), and takes the skgrepo
restriction as a new argument. Its message now says which
perspective draws the place ("your perspective", "the perspective of
the owner of 'X'") and what it shows there ("the original", or
another mirror by title).
**** The shown mirror's birth fact for a mutual pair
Where the mirror shown reaches N both ways (mutual forks), it gets
'(overrides out)'; the plan names no side for that case.
**** 'candidate_owners' takes the original's own author too
"The owners of every visible mirror" includes the original itself;
a candidate whose drawing equals the root authors' is dropped by the
cycle anyway.
**** Docs beyond the plan's list
'docs/sharing-model.org' (the paragraph saying the shown node is the
end of the owned chain) and 'docs/forks.org' (named by the plan)
were reworded; the glossary's "clone, and the fork operation" got
"from your perspective".
