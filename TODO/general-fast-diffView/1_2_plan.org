* Scope
The start script takes the config path as its argument and
keeps everything it writes in a folder beside that config; the
server writes its logs into a per-run subfolder of that folder;
the clients and the docs point there. Not in scope: the server's
log contents, the rerun loop, 'windows/container/' scripts
(they get one doc line), the redraw delta (plan 1_3).

* Vocabulary
"CONFIG" is the config file's path as the start script was given
it, e.g. 'data/skgconfig.toml'.
"The run folder" is 'CONFIG.running/', a sibling of the config:
'data/skgconfig.toml.running/'.
"A start" is one invocation of 'bash/start-servers.sh'. It may
span several "server runs": each time the rerun loop (or
cargo-watch) starts the server binary is one server run.
"START" is a UTC timestamp 'YYYY-MM-DDTHH-MM-SSZ', hyphens
only, so that it is a valid file name on every filesystem.
"The script log" is what the start script's children print:
the rerun loop's output, and cargo-watch's with hot reload.
"The server logs" are 'server-to-user.log' and, when the config
says 'timing_log = true', 'server.jsonl', which the server
writes itself.
"Isolated instance": a server on a scratch config and a free
port, '.claude/skills/verify/SKILL.md'.

* Agreed behavior
** The start script's argument
'bash/start-servers.sh [CONFIG] [--deb] [--hot-reload]'. The
first argument that does not start with '--' is CONFIG; a second
such argument is an error. Omitted, CONFIG is
'data/skgconfig.toml'. The environment variable 'SKG_CONFIG' is
removed, not aliased. Any unknown option: a usage line to stderr
and exit 2, before anything is written.
** The run folder
The script creates 'CONFIG.running/' (mkdir -p) before it
writes anything. It no longer creates '<data root>/logs/'.
** The stop script
'CONFIG.running/stop-servers.sh', with the same one-line body
('kill -TERM -PGID') as today's 'bash/stop-servers.sh', rewritten
at every start. The script no longer writes
'bash/stop-servers.sh' and does not delete it either: the
untracked file there is the stop command of Jeff's live server
until he restarts (Pitfalls).
Its startup messages name the new path.
** The script log
'CONFIG.running/start-servers.START.log', START the start's own
time, created at the start; both modes append the rerun loop's
or cargo-watch's output there. The old 'logs/cargo-watch.log' is
not written anymore and not deleted.
** The two mode functions
'run_skg_rerunning_on_exit' becomes
'run_skg_without_hot_reload', and 'run_skg_under_cargo_watch'
becomes 'run_skg_with_hot_reload'.
** What stays in the script
The config preflight and its red error; 'compile_emacs_client';
'kill_stale_skg' with its patterns scoped by the config path
(CONFIG as given, exactly as the command lines carry it); the
free-port check; the INT/TERM trap; the two modes' behavior.
** The server's logs go to a run subfolder
'SkgConfig::logs_dir' ('server/types/misc.rs:312') returns
'CONFIG.running/START/' where CONFIG is 'config_path' and START
is the server process's own start time, decided once per process
and the same at every call, including after a config reload
(the reload keeps the same 'config_path'; the folder must not
move mid-run). 'main.rs:430-432' creates it as it creates the
old folder today. Nothing else about the log files changes: the
same two file names, the same layers, 'timing_log' gating
'server.jsonl'. 'check-config' creates no folder. So each server
run has its own folder, and a reader sees at a glance how many
runs there were and when each began.
** Messages that name the log location
The busy-initializing message ('main.rs:213-217') already prints
the real folder, so it stays correct. The Emacs client's two
messages ('skg-client.el:77' and ':128-140') and the Neovim
client's (':75-88' of 'nvim/lua/skg/client.lua') will name the
run folder from the client's config file path ('skg-config-file',
'config.config_file()'): "CONFIG.running/: the newest folder
there holds server-to-user.log; the start-servers.*.log files
beside it hold the start script's output". They name no
timestamp, since they cannot know it.
** The docs follow
'docs/setup.org:90' and 'docs/api-and-formats.org:1291' name the
stop script's new path; 'api-and-formats.org:1725' and
':1887-1888' the run subfolder; the troubleshooting doc that
says where "Server ready." appears
('docs/troubleshooting/build-artifacts-corrupted-by-power-loss.org:136');
'docs/usage.org' where it shows 'cargo run --
data/skgconfig.toml' gains the one clause that the server
writes its logs to 'CONFIG.running/START/';
'.claude/skills/verify/SKILL.md' recipe says where an isolated
instance's logs land and that its stop script, when started by
the start script, is in its own run folder.
'docs/glossary.org' gains "run folder" beside "hot
reload". 'windows/README.org' or the Windows docs get one line
saying the server's logs moved, if they name the old place
(grep 'logs' under 'windows/'); the container scripts there are

** The profiling tools follow
'tools/introspect/profile-with-org-report/run.sh:94-95, :167' and

* Pitfalls the slices must respect
** Jeff's live server still runs under cargo-watch on this tree
At planning time (14:13 UTC) 'ps' shows cargo-watch watching
'server/' for 'data/skgconfig.toml'. Slices 1 to 3 touch no file
under 'server/' (not even a 'touch'). Slice 4 edits the server
and is launched only after Jeff has restarted his server with
the new script (no hot reload) or has said the restarts do not
matter; the orchestrator checks 'ps' before launching it. Never
run the start script or any stop script against
'data/skgconfig.toml'; scratch configs only, each with its own
free port above 1760 ('ss -tln').
** 'bash/stop-servers.sh' is Jeff's; leave the file alone
It is untracked and holds 'kill -TERM -485475'-style line for
his live server. Slice 1 stops generating it and must not
delete it or run it. Scratch instances are stopped with their
own 'SCRATCH.running/stop-servers.sh'. The one-time runners of
plan 1_1 used 'set -m' to give a scratch start its own process
group ('tests/results/plan-1_1/slice1/'); the container has no
'setsid'.
** The reload path keeps the run folder
The rebuild command reloads the config ('load_config' is called
again with the same 'config_path'; grep its callers). If
'logs_dir' were recomputed from a fresh timestamp there, the
busy signal and any later reader would name a folder the
appenders never write to. Decide START once per process (a
process-wide 'OnceLock' or a value fixed in 'main.rs' and
stored) and derive the folder from it.
** The config structs built by hand need the new state
'SkgConfig' literals at 'misc.rs:539' and ':562' (test and
default constructors) must still build; so must every test that
constructs a config ('cargo check --all-targets' finds them).
** START must be a legal file name everywhere
No colons (Windows). Use 'date -u +%Y-%m-%dT%H-%M-%SZ' in bash
and the equivalent in Rust.
** The clients may know only the config's directory
'skg-config-file' ('elisp/skg-config.el:16') and
'config.config_file()' ('client.lua:36-38, :75') give the path;
when either returns nil the message falls back to naming
'CONFIG.running/' with CONFIG unknown, in words, not to the old
'logs/' path.
** Suites
'bash/emacs-tests.sh' (elisp; run alone), 'bash/nvim-tests.sh'
(Neovim is installed here), 'bash/nextest.sh' or 'cargo nextest
run' (Rust), 'bash/integration-tests.sh' (both clients against a
server; the server's startup message changes, so slice 4 runs
it), 'tools/skg-for-ai' has its own tests which assert server
behavior (read its README for the command; slice 4 runs them
too). Serialize full suites; two at once collide on temp paths
and the Tantivy writer. Logs under 'tests/results/plan-1_2/
sliceN/', untracked.
** No shellcheck
'bash -n' is the syntax check.
