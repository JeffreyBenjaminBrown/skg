* Styles (phases 2 to 6)
** DONE Style directives on the wire are capitalized
The served rule table writes a style as its name in capitals (CRUCIAL,

** DONE The lens engines skip empty INTERC slots
An INTERC used to emit its separator beside an empty slot, so a
one-slot match read '3{' -- a rule kept for a contains herald that no

would read "text changed  ✗" (two spaces). Both lens engines now skip
an empty slot and its separator; their tests say so.

**** Claude says: yes; which name should the chain get?
***** What a graft is
A path request '(path ROLE)' (e.g. 'skg-show-paths-through-mentioners')
draws, under the origin, the node playing ROLE toward it, then that
node's partner in the same role, and so on. Each node it adds is a
graft: it sits where it does because of the path, not because its
parent contains it, so it carries 'affectsParent false' and the birth
'(birth backpath ROLE)'. The glossary does not define it.
***** The divergent names
The chain is a "path" in the commands, the wire's '(path ROLE)' and
'RelationRole' docs; a "backpath" in the engine
('server/to_org/expand/backpath.rs'), 'Birth::Backpath' and the birth
atom; and a "...ward ancestry" ('containerward', 'mentionerward') in
module names, tests and some docs. ("Org ancestry", the outline above a
headline, is a different thing and keeps its name.) "Graft" names one
node of the chain, and is the only word for that.
***** My recommendation
Call the chain a "path" everywhere: 'Birth::Path', '(birth path ROLE)',
"the path engine" in 'to_org/expand/path.rs', and "a containerward
path" rather than "containerward ancestry". Keep "graft" for one node
of a path, and define both in the glossary. It is a rename like phase 1:
code, wire, both clients, tests and docs. Shall I do it?
****** DONE [jeff]
It's not always a path. Often it's a tree or a forest.
I think the general terms should be 'single-relation tree'
and 'single-relation forest'. Except that doesn't imply directedness --
we're only traversing the relation in one direction.
Is there a good word for that? "Flow", maybe?
******* DONE Claude says: "role tree" carries the direction
******** You're right that it branches
The header of 'server/to_org/expand/backpath.rs' already says so: the
"path" follows a node's single partner in the role until a node has
several, then includes that first layer of branches. So it is a tree,
rooted at the origin.
******** A role, unlike a relation, is directed
Following the container role from a node only ever goes one way, so
"single-role tree" says what "single-relation tree" can't. Shorter:
"role tree". The existing '-ward' adjectives name particular ones:
"a containerward tree", "a mentionerward tree". It is always one tree,
rooted at the origin; it would be a forest only without its root.
******** Against "flow"
In graph theory a flow is a quantity assigned to edges (network flow),
and in prose it suggests movement. Other candidates I considered:
"reach" (direction, but names a set, not a shape), "lineage" (directed
and branching, but implies ancestry, which fits only containerward),
and "arborescence" (exactly a directed rooted tree, but obscure).
******** The proposal
"Role tree" for the chain, "graft" for one of its nodes, '-ward'
adjectives for particular role trees. In code and on the wire:
'Birth::RoleTree', '(birth roleTree ROLE)', the request
'(roleTree ROLE)' replacing '(path ROLE)', 'to_org/expand/role_tree.rs',
and commands like 'skg-show-mentionerward-tree' replacing
'skg-show-paths-through-mentioners'. Shall I do it, or would you name
it differently?
********* DONE [jeff]

********** DONE Claude says: "graft" is better, and "role" can go
*********** "Branch" already means a node with all its descendants
'docs/vocabulary.org' defines it so ("A branch is just a node together
with all its descendents"), on containment: "When a node contains other
nodes, we can say it branches". In a role tree, a node's descendants are
the rest of the tree beyond it, so "a role branch" would name a node
together with everything grafted below it, not the one node. And it
would echo containment, which is just what a graft is not: a graft is in
the view because of the role, not because its parent contains it.
*********** "Graft" alone is enough
Only role trees make grafts, so "role graft" repeats itself. "A graft"
is one node of a role tree; "the grafts" are all of them but the root.
*********** So the proposal stands
"Role tree", "graft", and '-ward' adjectives for particular role
trees, carried through code, wire, commands and the glossary as
described above. Say go and I'll do it.
