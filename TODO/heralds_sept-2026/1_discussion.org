* Codex's response — 2026-09-21
The proposed ratios would make the heralds easier to read. I especially
like giving the numerator a consistent meaning: something within the
total that deserves attention. There are a few semantic choices to settle,
though, and the motivation for the link-source overlay rests on behavior
that the current code no longer has.

** Following a link currently visits the exact node
'skg-goto' sends the selected ID to the single-root-view handler, which
opens that node itself. Override substitution can occur in the content
drawn beneath it. Finding an O herald at your destination therefore does
not mean that following the link redirected you.

This is explicit in [[file:../../elisp/skg-id-search.el::(defun skg-goto][skg-goto]],
[[file:../../server/serve/handlers/single_root_view.rs][the request handler]], and
[[file:../../docs/override.org::*Direct visits are exact][the override guide]].

*** Same-source overrides are allowed, and I would keep them
The [[file:../../server/dbs/in_rust_graph/override_invariants.rs][override invariants]]
limit owned overriders per target and prohibit owned cycles; they do not
require different endpoint sources. The
[[file:../../server/dbs/in_rust_graph/override_resolution.rs][resolver]] checks ownership
and visibility, without requiring a source change.

A useful example is a revised public note superseding an older public
note whose ID and text remain valuable for old references. Another is a
private override relationship between two public notes: relationship
source and node source are independent. Sources organize ownership and
visibility; they need not define which notes can supersede one another.

*** The overlay is useful as provenance, independently of overrides
I would define its suffix as the home source of the link's literal target,
using the same abbreviation and green styling as node sources. Here
"source" means a configured source, not an inbound linking node.

Make it a buffer-local toggle covering links in titles and bodies. Its
annotations should be display-only, survive view refresh while enabled,
and update after link edits and source-set changes. Unknown or inactive
targets need an explicit unavailable state; a failed lookup must not look
like a known source. Resolve extra IDs to their node before looking up
the source. Batch lookups against the graph rather than issue one request
per link or depend on the asynchronously updated search index.

I would implement this if you want provenance at a glance. I would defer
it if its only purpose is to detect link-following redirection.

*** Define the counted objects before implementing the statistic
S should count distinct inbound nodes, not link occurrences or configured
sources. T should count distinct target nodes, resolving extra IDs and
respecting the active source set. Multiple links to one target then
contribute one to T. Count the literal graph relationships, without
following override chains.

For "multiple links" in the interesting-source predicate, I recommend
multiple distinct targets as well. Repeating a link to the same note
would not alone make an otherwise empty source interesting. If you mean
multiple textual occurrences instead, that is a meaningful alternative
to decide explicitly. In either case, count each interesting source only
once when it satisfies more than one condition.

T is useful even when links can be counted by hand: bodies can be folded,
links can repeat, and some targets can be outside the active source set.
With these semantics it is not necessarily the number of visible link
labels. Unresolved targets need a separate policy; I would exclude them
from the resolved-node total and expose their failure separately.

**** The new I cannot be obtained by adding the old subcounts
[[file:../../server/dbs/in_rust_graph/stats.rs::fn link_split][link_split]] currently
counts sources with content separately from bodyless, contentless sources
whose link labels differ from their titles. Body text and multiple targets
are not the requested union of those old categories. The interesting
predicate must change in the server, and outbound link counts must be
added to the semantic payload: it currently sends only outbound ancestor
flags for links.

The predicate should inspect content visible in the active source set.
The current content test uses the raw 'contains' list, which can let an
inactive relationship influence the statistic. I recorded that concrete
issue in [[file:../problems.org::*Link interestingness inspects inactive content relationships (2026-09-21)][problems.org]].

** Subscribee content: the numerator belongs to the occurrence
For a subscribee B under subscriber A, I recommend defining the numerator
as B's visible direct content minus what A visibly hides or directly
contains. This follows the existing
[[file:../../server/update_buffer/reconcile/content.rs::fn content_goal_list][content-goal calculation]].
Hidden content is already dealt with and should not count as unintegrated.
The denominator is all B's visible direct content, including that hidden
or integrated subset. Thus 'C2/8' becomes 'C8' when the remaining two are
dealt with.

*** Keep this contextual count out of graph-wide node statistics
The same B can have different unintegrated counts under two subscribers.
Compute the numerator from the same membership rules used to populate
that occurrence, resolving extra IDs and applying relationship and node
visibility consistently. Do not count rendered child viewnodes: folds, display
budgets, folders and placeholders can make those differ from membership.

Keep the inbound contains side intact: a full token might be '2C3/8'.
If total content is zero, omit the outbound side; retain C if the inbound
side still has something to say. Outside the subscribee-as-such context,
retain the ordinary content count.

**** One semantic edge deserves an explicit decision
The existing subtraction compares node identities after extra-ID
resolution. It does not equate a node with its overrider. I would preserve
that definition here. Treating "I contain an override of this child" as
integration would change subscription behavior, not just its herald.

*** What is 'actual substitution at this occurrence'?

**** Codex: the parent names N, but this viewnode shows R
Suppose a container P contains a public note N, and your note R overrides
N. When viewing P, Skg can draw R in the position occupied by P's stored
reference to N. That particular viewnode is a substituted occurrence: its
title/body and node edits concern R, while its membership in P still
represents N. Saving it does not silently change P's reference to R.

Visiting R directly shows the same note R, with the same override
relationship, but no substitution occurred at that root. Visiting N
directly shows N. Thus "R overrides N" is a graph fact; "this R viewnode is
standing in for N" is a fact about a particular position in a view.

The latter is what 'overridesHere' records. Currently it makes O a birth
relation, but O is also a birth relation when R appears in an override
folder or path. The old O style therefore says "overrides explains why
this viewnode appears", which is broader than "this viewnode replaced another".

I recommend a distinct marker only on substituted viewnodes, with an
explanation such as "Showing R in place of N; edits affect R; the
container still refers to N." If preserving the existing birth cue is
enough for you, we can omit that extra marker, but those two designs
provide different amounts of information.
