* The processes involved
** Runtime generations
The server's graph state moves through numbered 'runtime
generations'. Each graph mutation (a save, a reload of files
changed on disk, a body-whitespace strip, a rebuild) builds a new
graph and swaps it in as the next generation: the previous number
plus one ('SharedRuntime::swap_in' in 'server/types/env.rs').

A server starts at the microseconds since the Unix epoch, so a
buffer drawn by an earlier server process is always older than
anything the current one has. Your numbers decode that way: the
server started at about Tue 3 Nov 2026 15:31:26 UTC.
** Last-change generations
The in-Rust graph records, for every node, the generation at
which it last changed ('LastChangeGenerations' in
'server/dbs/in_rust_graph/last_change_generations.rs'). A node
untouched since startup dates from startup. A mutation notes each
node it wrote, and the swap-in stamps them with the new
generation. A deleted node keeps its entry, so an old buffer
cannot quietly recreate it.

What counts as a write is wide. A save writes every node whose
file changes, and that includes a node whose relationship records
move between repos even though its title and body stay the same.
** A buffer's 'rendered-at'
Every view response carries the generation it was drawn at. The
Emacs client keeps it in the buffer-local 'skg-rendered-at'
('elisp/skg-buffer.el') and sends it back with every save, as
'(rendered-at . "N")'.

A buffer's rendered-at advances only when that buffer is redrawn.
After a save, the server redraws the saved view and the
'collateral' views, which are the open views that show a node the
save changed. A view that shows none of those nodes keeps its old
rendered-at. Its text is still accurate, but its date is not
current.
** The stale-save check
Before a save writes anything or asks for any confirmation, it
runs 'stale_write_errors'
('server/serve/handlers/save_staleness.rs'). It collects the
nodes the save would write:
- the nodeInstructions the buffer's text yields, after dropping
  the ones identical to the graph;
- for each nodeMerge, both the acquirer and the acquiree.

If any of them last changed at a generation later than the
buffer's rendered-at, the whole save is refused, with one error
per node. The reasoning: the buffer's text of that node predates
the change, so writing it would silently undo the change.
** How a save carries out a merge request
A merge request, '(editRequest (merge ACQUIREE))' on the
acquirer's headline, is set by 'skg-set-merge-request' (C-c s m).
The save turns each request into a 'NodeMerge' triple
('nodeMerge_from_acquirer_and_acquiree' in
'server/nodeMerge/nodeMergeInstructionTriple.rs'):
- a 'text preserver', a new node titled "MERGED: " plus the
  acquiree's title, holding the acquiree's body;
- the 'updated acquirer', which gains the acquiree's IDs,
  contents, aliases and subscriptions, with relRepos kept (the
  more private repo wins on a shared member);
- a delete of the acquiree.

The save builds all three from both nodes as the graph and the
disk hold them at save time. They are not built from the buffer.
That matters below.

*** What made the merge case go wrong
Two things had to hold at once. The check covered a node whose
written content does not come from the buffer's text. And a
change to that node did not redraw the buffer, so the buffer's
date fell behind.

For most writes the second condition cannot hold. Apart from
merge nodes, everything the check covers is a node the buffer
shows, and a change to a shown node makes the buffer collateral,
so it is redrawn. If the buffer has unsaved edits, the save that
would change the node is refused instead, as a conflict with that
dirty view. The writes a save derives from the graph (delete
propagation, Hoist repairs, fork clones and the rest) are not
checked at all.
*** The mirror: a dirty buffer's merge request blocks other saves
Before any save, the server refuses it if it would affect an open
view that has unsaved edits ('dirty_view_conflicts' in
'server/serve/handlers/save_dependencies/mod.rs'). Among a dirty
view's dependencies it counts the target of every merge request
in its text, which is to say the acquiree.

So had you set the merge request on singularity before saving
event horizon, the event-horizon save would have been refused as
a conflict with the singularity buffer. That refusal protects
nothing either, for the same reason: the merge will read the

***** The experiment
I ran an isolated server on scratch data. The data had a root
containing 'A old' (body "a body old") and 'B'. In one buffer I
retitled A to 'A new', changed its body to "a body new", added
'(editRequest (merge b))' to A, and saved.

itself happened: B's ID is now one of A's extra IDs, and 'MERGED:

***** Why
A save runs in two phases ('prepare_save_under_mutation_gate' in
'server/save.rs'). Phase one writes the buffer's ordinary edits,
including the edits to A. Phase two writes the merge.

But the merge was computed before phase one, from the graph and
files as they stood before the save
('nodeMerge_instructions_from_pairs', called from
'server/from_text.rs'). So phase two writes a version of A that
predates the buffer's edits, over the version phase one just
wrote.

By the same reading, though I did not run it, the acquiree's
edits are lost the same way when the buffer shows the acquiree
and edits it. The text preserver gets the acquiree's title and
body from before the save.
***** What this means for the stale check
At the moment the merge-specific check on the acquirer protects
nothing, for the same reason as the acquiree. Whatever the buffer
says about the acquirer, the merge writes the graph's version.

Once this bug is fixed, the buffer's text of the acquirer will be
written. But it will be written through its ordinary
nodeInstruction, which the ordinary rule already checks whenever
the buffer edits it. So the merge-specific entry for the acquirer
is redundant either way. I now recommend that the stale check
cover only the nodeInstructions and drop both merge nodes.
***** Two ways to fix the lost edits
The first way is to build the merge on top of the buffer's
edits. This is the behavior a user expects. It is not a
one-line change, because the merge reads bodies from disk
('graphnode_by_gnid'), and the disk does not have phase one's
edits yet. The merge would
have to read A and B from phase one's nodeInstructions where they
exist, and from the disk only where they do not.

The second way is to refuse a save that both edits a merge node
and merges it, saying "save your edits to A first, then merge".
There is a precedent, 'CannotMoveAndMergeSimultaneously'. It is
small and safe, but it costs the user an extra save.

I'd do the second now and the first if refusals become annoying.
The first is what you would want eventually.
