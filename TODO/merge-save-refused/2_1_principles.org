* Claude says: the short answer
The plan's rules are right, but it states them as a list of
cases. Three of its four slices follow from one principle, and
that principle is the one you reached for: a graphnode's last
change matters only to a buffer that holds a viewnode of it.
Stated that way, slice 2 is not special treatment of merges. The
current code treats merges specially, and slice 2 removes that.

Two things in the plan are genuinely ad hoc, in the sense you
mean.

Slice 1 is a bandaid by its own admission. The root cause is that
the merge is computed from the graph as it stood before the save,
and the root fix is to compute it after phase one. I size that
fix below; it is one agent slice, not a rewrite.

The stale check's correctness depends on where in the save
handler it runs, not on what it is given. The plan's whole
pitfalls section is about that ordering. That fragility has a
structural cause, which I name below.

Beyond the plan, there is a deeper alternative that makes "stale"
mean what it says: compare the buffer's copy of each graphnode
with the graph, instead of comparing generation numbers. The
client already holds the text that would make this possible. It
would subsume slices 2 and 4 and also remove the restart and
rebuild rules, which make every buffer stale whether or not
anything it shows changed. It costs a protocol change in both
clients, so I do not recommend folding it into this plan, but it
is the real answer to "could it be more principled," and I lay it
out so you can decide.
* Claude says: your intuition, made precise
** The principle
A save writes some graphnodes. For each written graphnode, the
content either is a viewnode, the copy the buffer took when it
was rendered, or is computed from the graph and disk at save
time. Only a copy can be older than the graph, so only a copy can
undo a change the user never saw. So the stale check should cover
exactly the writes whose content is a render-time copy.

Your phrasing was "anything that would be read from disk does not
need a warning, but anything in a buffer might." That is this
principle. The one refinement is that a delete also belongs on
the checked side, though it reads nothing: deleting a graphnode
discards its current state, and the user decided to delete it on
the strength of an older state. The common thread is loss. The
check guards against a save discarding graph state newer than
what the buffer showed.
** How each kind of write falls under it
*** The buffer's nodeInstructions, after the noop filter
A copy, and checked. The noop filter already drops a graphnode
the buffer shows as the graph now has it, which is the principle
applied to unedited graphnodes.
*** The buffer's deletes
A loss, and checked.
*** A merge's two graphnodes
Computed from the graph at save time, and lossless: the
acquiree's title and body go to the text preserver, its contents,
aliases and subscriptions go to the acquirer. Nothing newer than
the buffer is discarded. Not checked. This is slice 2.
*** Derived writes
Delete propagation, strandeds resets, restore requests, Hoist
repairs and fork clones are computed from the current graph and
disk. Not checked, as today.
*** The whitespace strip
A strip changes a body in a way no save can undo, because every
save trims trailing whitespace from each line it parses
('divide_into_viewNodeLineCols', line 198 of 'uninterpreted.rs').
A change no save can lose is not a change the check needs to know
about. This is slice 4.
** What the plan should say
The module comment of 'save_staleness.rs' already states the
principle, almost word for word, and then lists the merge
graphnodes as an exception to it. The plan should say that slice
2 removes a contradiction, not that it adds a merge rule. One
sentence in the plan's "Agreed behavior" and in the docs
paragraph would do it: "The check covers a write whose content is
the buffer's render-time copy of the graphnode; a merge's writes
are computed from the graph at save time, so they are not
checked."

The same sentence covers the dirty-view change. A dirty view
depends on a graphnode when it holds a viewnode of it that a
later save would write. A merge request names a graphnode without
holding a viewnode of it. The PITFALL about links is the same
principle again, and the plan rightly leaves it out of scope, but
it should name it as a known deviation from this principle rather
than an unrelated issue.

later refused as stale, or would undo S. So V depends on

** Slice 4 bends the meaning of 'last change'
After slice 4, a graphnode's last-change generation means "the
last change a save could undo," not "the last change." That is
consistent with the loss principle above, and I would keep it,
but the plan should say the principle so the exception reads as a
consequence.

One factual correction. The discussion and the strip module's
comment say the graph stores no body text, so a strip leaves the
graph unchanged. That is false: 'GraphnodeInRust' has a 'body'
field ('server/types/nodes/rust.rs', line 20), and the strip
rebuilds the graph from the stripped graphnodes. The strip does
change the graph. The stale refusal still only bites when the
user then edits a stripped graphnode, because an unedited one is
filtered as a noop: the parser trims the same whitespace, so the
buffer's copy equals the stripped graphnode. Slice 4
stands, but its rationale in the plan should be the loss
principle, not the body claim, and the strip module's comment
should be fixed in passing.

The other principled framing would be that a strip is a mutation
like a save and should redraw the views that show the stripped
graphnodes. That redraw would change nothing visible, so slice 4
is the cheaper consistent choice.
** A gap the principle exposes: implicit forks
When the buffer edits a foreign graphnode N, N's own save is
dropped from the nodeInstructions and the edit becomes a clone C
built from the buffer's text of N ('validate_and_filter_foreign_
instructions', and the comment at 'server/from_text.rs' line
229). So N never reaches the stale check. If N changed after the
render (a reload of files changed on disk, say, since the server
watches foreign repos too), C is built from a stale copy of N and
the override silently diverges from what the user thought they
were editing.

By the loss principle this is milder than the other cases:
nothing is overwritten. By the copy principle it belongs in the
check: C's content is a render-time copy of N. The fix is small,
because a 'ForkSpec' carries 'original_gnid': chain the fork
specs' originals into 'written_pids' in 'stale_write_errors'. It
would be a natural addition to slice 2, which is already changing
that function's inputs.

* DONE Claude says: the deeper alternative, content not clocks
** The idea
The generation mechanism is a proxy. The question it answers is
"was N written after this buffer was drawn?" The question we care
about is "is the buffer's copy of N what the graph holds now?"
The client already holds the text that answers the second
question directly: 'skg-clean-baseline' ('elisp/skg-buffer.el',
line 162), captured at every render and every redraw
('skg-replace-buffer-with-new-content' recaptures it), and
already sent in the save envelope for every dirty other view.
Neovim mirrors it ('skg_clean_baseline' in 'nvim/lua/skg/').

If the saved buffer's own baseline rode along too, the server
could parse it the way it parses dirty views today
('dependencies_from_text' already runs 'org_to_viewforest' on
baselines), supplement it from disk as the save path does, and
for each graphnode the buffer writes compare the baseline's
viewnode with the graph's current graphnode using
'buffernode_differs_from_disknode', the noop filter's own
comparison. The rule becomes one sentence: a graphnode is stale
iff saving the baseline would not be a noop for it.
** What falls out of it
*** Merges
The baseline holds no copy of the acquiree, so there is nothing
to compare, so a merge is never stale. Slice 2 without a rule
about merges.
*** The whitespace strip
The parser trims trailing whitespace from the baseline too, so a
stripped graphnode compares equal. Slice 4 is unnecessary, and
'last change' can keep its honest meaning, or go away.
*** Restarts and rebuilds
Today a restart or a rebuild makes every earlier buffer stale for
every graphnode it writes, and the rebuild tells the user to
close all views. The discussion calls this deliberate, and it is,
but only because generations cannot tell a file that changed
while the server was down from one that did not. A content
comparison tells them apart, so a buffer survives a restart
unless something it shows actually changed.
*** The cases the check already gets right
A graphnode deleted after the render: the baseline has it, the
graph does not, so it differs, and the save is refused. A
graphnode the buffer creates: no baseline copy, never stale. A
graphnode changed and changed back: equal, not stale, which is
correct and which generations get wrong.
*** The error message
It can show what changed, by diffing the baseline's copy against
the graph's graphnode, instead of saying "3 graph changes later."
That is better than slice 3's message.
*** What could be removed
'rendered-at' in the save request, 'RenderedAt', the stamping in
'SharedRuntime::swap_in', 'LastChangeGenerations', and the
'runtime generation' request a client sends for a new empty view
would no longer be needed by the stale check. I did not check
whether anything else depends on the generation numbers the view
responses carry, so I claim only that the check would not.
** What it costs
*** A protocol change in both clients
The saved buffer's half of the envelope gains the baseline, in
the same 'present' or 'unavailable' form the other views use.
Emacs and Neovim both change, as do the client tests that build
save requests.
*** A decision for an unavailable baseline
A view without a baseline today refuses to be a dirty other view
("has no verified clean baseline"). For the saved buffer the same
rule would be: if the baseline is unavailable and the buffer
writes an existing graphnode, refuse and point at the recovery
command. A new empty view writes only new graphnodes, so it
passes.
*** Server work per save
One more parse and supplementation, of a buffer-sized text. Every
dirty other view already costs this on every save, so the cost is
known and small.
*** Subtleties I checked
Supplementation fills a field the buffer leaves unspecified from
the current graph. Applied to the baseline as well, such a field
compares equal, which is right: the buffer does not write it.
Under a skgrepo restriction 'preserve_invisible_members' weaves
the hidden members into both texts the same way. The folded and
focused atoms are added to the current snapshot at save time, not
to the baseline, and the parser ignores them in any case.
*** Size
Server, two clients, and the rewrite of
'tests/save_stale_buffers.rs' around baselines instead of
rendered-at. Larger than the whole current plan.
** My recommendation
Not in this plan. Slices 2, 3 and 4 are cheap and right under
either mechanism, and the plan should proceed with the principle
stated. Record the content comparison as its own discussion, to
be taken up when the restart or rebuild rule next costs you a
buffer, or when a false positive appears that the principle does
not explain. If you would rather go straight to it, slices 2, 3
and 4 become its first steps and are not wasted.

its buffers, because every buffer was stale by generation. With
content comparison a buffer rendered before a rebuild is stale

server would keep them and rerender the clean ones. That is a
change to the rebuild handler and both clients' rebuild
commands. A restart improves without any change: the new server
does not hold the old views, and their saves pass or fail on
content.
