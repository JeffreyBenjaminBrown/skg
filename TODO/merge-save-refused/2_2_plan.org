* The principle
A save's write of a graphnode has one of two sources: a copy the
buffer took when it was rendered (a viewnode), or the graph as it
stands at save time. Only a copy can be older than the graph, and
only a write from a copy, or a delete, can discard graph state
the user never saw. So the stale check asks, for each graphnode
the buffer writes or deletes, whether the buffer's copy of it
still matches the graph. The buffer's copy is in its baseline:
the text the server last drew for it, which the client keeps.
The check compares the baseline's viewnode of the graphnode with
the graph's current graphnode. No clock, no generation number.
A merge is built from the graph at save time, so it is never
stale. A strip changes nothing a baseline shows after parsing, so
it never makes a buffer stale. A server restart or a rebuild
makes nothing stale by itself.
* Scope
** In scope
- A merge will be built from the graph as phase one leaves it, so
  a save that merges a graphnode and also changes it will keep
  both. A save that deletes a merge node will be refused (slice
  1).
- The saved buffer's baseline will ride with every save, from all
  three clients (slice 2).
- The server will decide staleness by comparing the baseline with
  the graph, and the generation machinery will go: 'rendered-at'
  in requests and responses, the 'runtime generation' request,
  and 'LastChangeGenerations' (slice 3).
- The stale error will say what changed, using the diff view's
  node-comparison functions (slice 3).
- A merge request will be no dirty-view dependency, and neither
  will a link (slice 4).
- The server will record the skgrepo restriction each view was
  last rendered under, and refuse a save of a view whose
  restriction has since changed (slice 5).
- Open views will survive a rebuild; the clients will rerender
  them instead of closing them (slice 6).
** Out of scope
- A rendered diff-view buffer of a stale save. Slice 3 reuses the
  diff view's comparison functions for text only; a rendered
  buffer is the later generalization Jeff intends for merge
  conflicts.
- Refusing a merge request whose acquiree ID is an extra ID.
- A graphnode the buffer writes without holding a baseline
  viewnode of it (pasted in by ID, or put into a new empty view).
  Nothing can be compared, so it is not checked; the docs say so.
- Giving each NodeInstruction a provenance (see
  'TODO/problems.org').
- The dirty-view conflict check itself. It stays as it is except
  for what slice 4 removes from its dependencies.
* Vocabulary
- 'baseline' of a buffer: its text as the server last drew it,
  before any edit. Emacs keeps it in 'skg-clean-baseline'
  ('elisp/skg-buffer.el'), Neovim in 'vim.b.skg_clean_baseline',
  the AI tool in its sidecar's 'content'. Each recaptures it on
  every render and redraw. A new empty view's baseline is the
  text the client creates it with.
- 'the baseline's writes': the Save instructions that saving the
  baseline would produce: parsed, supplemented and noop-filtered
  exactly as the saved text is. A baseline viewnode equal to the
  graph's graphnode is dropped by the noop filter; one that
  differs, or whose graphnode the graph lacks, survives.
- 'the buffer's writes': the nodeInstructions the saved text
  yields after the noop filter, plus the originals of its fork
  clones ('ForkSpec::original_gnid').
- 'stale graphnode': one the buffer writes or deletes that is
  also among the baseline's writes. Its copy in the buffer no
  longer matches the graph.
- 'merge request', 'acquirer', 'acquiree', 'merge pair', 'merge
  nodes', 'NodeMerge', 'phase one', 'phase two', 'derived
  writes': as the deleted '2_plan.org' defined them, repeated here. A
  merge request is '(editRequest (merge ID))' on a headline; the
  headline's graphnode is the acquirer, the named one the
  acquiree. A merge pair is the acquirer's pid and the acquiree's
  pid: since slice 1, 'from_text.rs' resolves the ID as written
  (possibly an extra ID) to its pid before the pair enters the
  'SavePlan' as 'nodeMerge_pairs'. A
  NodeMerge is the triple a pair becomes: text preserver, updated
  acquirer, delete of the acquiree. Phase one applies the
  ordinary nodeInstructions and phase two the NodeMerges, in
  'prepare_save_under_mutation_gate' ('server/save.rs').
- 'dirty view': an open view with unsaved edits, sent with a save
  as a 'ClientViewSnapshot'.
- 'runtime generation': the server's internal counter of graph
  swap-ins ('RuntimeGeneration' in 'server/types/env.rs'). It
  stays; only its use for staleness goes.
* Agreed behavior
** A merge will be built on the save's own edits
The NodeMerge triples will be built inside
'prepare_save_under_mutation_gate', from phase one's candidate
graph ('graph_after_save'), and no longer in
'buffer_to_validated_saveplan_with_fork_skgrepos_in_graph'.
'SavePlan' will carry the merge pairs instead of the triples. So
the updated acquirer will carry the buffer's edits to the
acquirer, the text preserver will carry the buffer's edits to
the acquiree, and the merged contents will reflect the save's
deletes.
** A save that deletes a merge node will be refused
A save whose buffer deletes the acquirer or the acquiree of one
of its merge pairs will be refused before anything is written,
with a new 'BufferValidationError' variant,
'CannotDeleteAndMergeSimultaneously', carrying the graphnode's
pid and whether it is the acquirer or the acquiree, checked
beside 'CannotMoveAndMergeSimultaneously' in
'server/from_text.rs', all IDs as pids. Only the buffer's own
deletes will count, not delete propagation. Its org form will
read:
#+begin_example
  A node this save would merge is also deleted by it:
  - Title: B
  - ID: b
  - It is the acquiree of a merge request in this buffer.
  - Remove either the deletion or the merge request, then save.
#+end_example
For an acquirer, the third line will say "the acquirer".
** The save envelope will carry the baseline
The envelope's 'saved-buffer' will be joined by a mandatory
'(baseline "TEXT")'. A request without it will be refused with a
message naming the field, as a request without 'rendered-at' is
today, and nothing will be saved. There will be no 'unavailable'
form for the saved buffer: every view a client can save has a
baseline, and a new empty view's will be its initial text.
** Staleness will be decided by content
Before any confirmation is asked and before anything is written,
the server will parse the baseline through the same path as the
saved text up to the noop filter ('org_to_viewforest' with
'IdResolution::ThroughGraph', then
'extract_nonmergeSavePlan_locally_in_graph', under the
connection's current skgrepo restriction, skipping the
validators between them) and take the pids of its Save
instructions: the baseline's writes. Every graphnode the buffer
writes or deletes whose pid is among them will be stale, and the
whole save will be refused with one error per stale graphnode. A
baseline that fails to parse or to extract will refuse the save
too, with a message that says so and points at the recovery
command, as a dirty view's unparsable baseline does today.

So a merge request will never be stale; a graphnode the buffer
shows unchanged is not written and so will never be stale; a
graphnode deleted after the render will be stale, because the
baseline's copy survives the noop filter when the graph lacks
the graphnode; a strip will be invisible, because the parser
trims what the strip trimmed; a restart or a rebuild will make
nothing stale by itself.
** The generation machinery will go
Removed: '(rendered-at . "N")' from the save request;
'(rendered-at "N")' from every view response ('content-view',
'search-results', 'diff-view', 'save-result', 'collateral-view',
'rerender-view'); the 'runtime generation' request and its
handler; 'RenderedAt', 'rendered_at_from_request' and
'rendered_at_entry'; 'LastChangeGenerations', its field on
'InRustGraph', every 'note_written' and the stamping in
'SharedRuntime::swap_in'; the clients' storage of rendered-at
and the new empty view's request for a generation; the tool's
sidecar 'rendered_at'. 'RuntimeGeneration::generation' will stay
for the reload notices, the rerender pass and the Tantivy
rebuild.
** The stale error will say what changed
The error's org form will read:
#+begin_example
  A node this save would write changed after the buffer was rendered:
  - Title: event horizon
  - ID: e03f8bfd-...
  - Changed since this buffer was rendered: the title (then "event
    horizon", now "event horizons"); the body; the content (gained
    743fd40c-..., lost none); the home skgrepo (then public, now
    personal-ish).
  - The body's changed lines, then against now:
    - a line the graph no longer has
    + a line the graph gained
  - Saving would undo that change. Archive your edits if you need
    them (M-x skg-show-unsaved-changes in Emacs,
    :SkgShowUnsavedChanges in Neovim), reopen a fresh view, and
    reapply them there.
#+end_example
- The first line will stay exactly as it is now; client tests and
  two Rust tests match on it.
- The "Changed since" line will list only the aspects that
  differ, from the diff view's own comparison:
  'node_changes_between' ('server/graph_straddle/union_walk.rs')
  for title, body, aliases, extra IDs, flags and home skgrepo,
  and 'interleaved_diff_without_reorders' ('server/types/
  list.rs') for the content list. Title and home skgrepo will
  show both values; lists what was gained and lost, by ID.
  Aliases, IDs, flags, subscriptions, hides and overrides will be
  named when they changed.
- A changed body will be followed by its line diff, baseline
  against graph, by 'interleaved_diff_without_reorders' over
  lines: each lost line prefixed "- ", each gained line "+ ",
  unchanged lines omitted, at most 40 lines each way, then "...
  and N more". So the user will hold two diffs from one base:
  theirs, which 'skg-show-unsaved-changes' writes, and the
  graph's, in the error.
- The error will not report: aspects that did not change;
  graphnodes the buffer does not write or delete, however they
  changed; the user's own edits; any viewnode of the baseline
  that the noop filter dropped.
- If the graph no longer has the graphnode, the title line will
  be omitted and the third line will read "It was deleted after
  this buffer was rendered."
- The one-line 'Display' form in 'server/types/errors.rs' will
  carry the title and the names of the changed aspects.
** Neither a merge request nor a link will be a dependency
'dependencies_from_viewforest' will stop adding a merge request's
target, and 'dependencies_from_text' will stop adding the links
of the text. A dirty view will depend on the graphnodes it holds
viewnodes of: occurrences, gnid-only viewnodes, ghosts, ID
property members, and the overrides an occurrence shows. The
collateral-redraw neighborhood ('update_relevant_neighborhood')
will keep its links; a redundant redraw of a clean view costs
nothing.
** A view will remember the restriction it was rendered under
'ViewState' will gain the skgrepo restriction the view was last
rendered under, set wherever a view is registered or rerendered.
A save of a view the connection holds will be refused, before the
stale check, when that restriction's 'skgrepos' set differs from
the connection's current one: "This view was rendered under a
different skgrepo restriction (then: main, private; now: main).
Rerender it, or archive its edits and reopen it." The clients
already refuse to switch the restriction while a view has
unsaved edits; this will make the server independent of that
courtesy, and will cover a rebuild that reconciles the
connection's restriction with a changed config.
** Views will survive a rebuild
'rebuild_session_lifetime_stores_in_place' will stop clearing
'open_views'. It will still drop the graph straddle. On a
successful rebuild each client, instead of telling the user to
close the views, will send 'rerender all views', which redraws
every view without unsaved edits and names the ones it skipped.
A dirty view will keep its baseline and be compared at its save
like any other. A view showing a graphnode of a skgrepo the
reloaded config no longer names will be redrawn with that
graphnode as the refresh shows an unknown one.
** What stays as it is
- The dirty-view conflict check, apart from slice 4.
- The move-and-merge refusal.
- The Hoist confirmation for an acquiree whose text sits below
  its home, and its repair save.
- The whitespace strip's rewriting of files and refresh of the
  graph and the index; only its dating goes, with
  'LastChangeGenerations'.
- A clean view is still redrawn after any save that changes a
  graphnode it shows, and after a reload of files changed on
  disk.
- The reload notice's 'generation' field and the rerender pass's
  use of the generation.
- The recovery command and its document ('skg-show-unsaved-
  changes', ':SkgShowUnsavedChanges').
- The fork confirmation, the delete-from, strandeds and Hoist
  confirmations, and the order they are asked in.

** What else consumed the triples before phase one
Each of these takes the triples today and must take the pairs,
or the triples from the 'PreparedSave', after slice 1:

  ('server/from_text/validate.rs') runs the foreign policy over
  the triples' nodeInstructions so that a merge touching a
  foreign graphnode is refused, never forked. On pairs: refuse
  when the acquirer or the acquiree is foreign, with the same

  telescope_hoist.rs') adds the triples' saved pids and the

  ('server/nodeMerge.rs') calls 'candidates_from_disk' with the

prepared. With the triple built from phase one's candidate, the
text preserver copies the acquiree as the repair left it.
** IDs are compared as pids
A merge pair holds two pids (since slice 1). A 'DeleteNode'
carries a gnid. 'ForkSpec::original_gnid' is a gnid. The
baseline's and the buffer's Save instructions carry pids after
supplementation. Resolve every gnid through
'graph . pid_else_raw_id' before comparing.
** The baseline is parsed as the saved text is, minus the plan
'extract_nonmergeSavePlan_locally_in_graph' ('server/from_text/
local_fieldintent_collection/mod.rs', line 60) takes a
'ViewForest', not text: parse the baseline first with
'org_to_viewforest (text, IdResolution::ThroughGraph (graph))'
as 'buffer_to_validated_saveplan_with_fork_skgrepos_in_graph'
does, skip the validators that follow it there, and call the
extraction with the same graph, config and restriction as the
save. It supplements from the in-Rust graph
('supplement_from_disk.rs' reads the graph, not disk) and
noop-filters. Keep only the pids of the 'node_instructions'
Saves of the 'NonmergeSavePlan' it returns; its skgrepo moves,
flag targets, merge pairs, notice candidates and warnings are
ignored. It runs before 'validate_and_filter_foreign_
instructions', so the baseline's foreign graphnodes stay in its
Saves, which is what makes a fork clone's original checkable.
'org_to_viewforest' with 'ThroughGraph' supplies IDs to new
headlines; a baseline has none, and any it got would be unused.
