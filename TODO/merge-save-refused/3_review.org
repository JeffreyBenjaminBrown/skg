#+title: Plan 2_2 reviewed: stale saves decided by content
* Verdict
The plan did what it set out to do, in seven slices and about
two and a half hours of agent time. The stale-save check now
compares the buffer's baseline with the graph instead of
comparing clock numbers; a merge is built on the save's own
edits; every trace of 'rendered-at' and the runtime-generation
request is gone from the server, both editors and the AI tool;
a dirty view depends on what it shows; a view remembers the
restriction it was drawn under; views survive a rebuild. The
suites were green after every slice, with the one failure that
predates the plan ('import-md-and-org', both clients).

The probes found one regression the suites did not: after a
nodeMerge of two siblings, their container's file lists both
IDs, which now name one graphnode, and the content comparison
read that as a change under every view of the container. The
generation check had let such a save through, and the save
cleaned the duplicate. Slice 7 fixes it by comparing the
baseline's copy with the graphnode as a view reads it back,
members resolved to pids and deduplicated. Slice 7 also applies
the vocabulary review's ten cheap findings.

Two behaviors deserve your decision (section "Decide"): whether
an untouched but outdated copy in a buffer should refuse the
save or be skipped, and whether the dirty-view check's remaining
link over-matching should go.

***** TODO Claude says: it does; two reasons for text anyway
****** The server does hold the tree
Every view the connection holds has its viewforest in 'ViewState'
('server/types/views_state.rs'), replaced at every redraw
('update_view', called from the rerender pass and the rerender
stream). The baseline's writes are computed by
'extract_nonmergeSavePlan_locally_in_graph', which takes a
'ViewForest', so for a held view the server could feed it the
stored tree and skip the parse of the text. The parse costs a
few milliseconds in release, tens in debug.
****** Reason one: views the server does not hold
The server forgets every view at a restart. The client keeps its
buffers and their baselines, so after a restart a save is still
checked against what was drawn; that was one of the gains of
plan 2_2. With the server's tree as the only baseline, a buffer
that outlives the server would have no baseline, and its save
would be either unchecked or refused until redrawn.
****** Reason two: the server's tree can be ahead of the buffer
A save whose redraw is withheld by the text-release challenge
registers the saved view as the save left it, while the client's
buffer still shows the text from before the save
('withhold_save_rerender' in 'server/rerender_pass.rs': "the
saved view is registered as this save left it, sending nothing
of it"). Until the user approves the rerender, the server's tree
and the buffer differ, and a baseline taken from the tree would
describe a text the user has not seen. The client's text is what
the user actually saw, so it is the right base.
****** What I would do
Keep the text as the baseline the client sends, and let the
server, when it holds the view and the stored tree renders to
that same text, use the tree and skip the parse. That is an
optimization with a cheap equality check, not a change of
meaning, and I would not do it until the parse shows up in a
timing. A hash in place of the text would shrink the envelope
but needs the full text as a fallback for the two cases above,
so it adds a path rather than removing one.

* What the user sees differently
** By decision
- A save that edits a merge node and merges it keeps both; a
  save that deletes a merge node and merges it is refused.
- A stale save's error names what changed, with the body's
  changed lines; no generation numbers anywhere.
- A merge request, a whitespace strip, a restart or a rebuild no
  longer makes a buffer stale; a node changed and changed back
  does not either.
- A dirty view whose only tie to a saved node is a merge request
  or a link no longer blocks the save (but see "Decide" for the
  other direction of links).
- After a rebuild the clients redraw every view without unsaved
  edits instead of telling the user to close them.
- A save of a view rendered under another restriction is refused
  by the server, not only prevented by the client.
** By accident
- A graphnode pasted into a view by ID, or into a new empty
  view, is no longer checked for staleness: the buffer holds no
  baseline copy of it. Decided in the discussion and documented,
  but a protection the generation proxy gave in one case.
- The container of merged siblings refused every save until
  slice 7 (above).
- Following a link to a node that is a root of an open diff-view
  buffer lands in that buffer. This was always so; the rebuild's
  forgetting of views had hidden it in one test.

* Decide
** DONE An untouched outdated copy: refuse, or skip?
Today a buffer that shows A as it was, while A changed in the
graph, is refused as stale when it saves, even if the user
edited only B. The noop filter compares A's copy with the graph,
finds a difference, and counts it as a write. This was so before
the plan too. The baseline makes a finer rule possible: when the
buffer's copy of A equals the baseline's copy, the user did not
touch A, and the save could leave A out instead of refusing,
redrawing the view with A's new state afterwards. That is the
three-way rule "base equals mine, take theirs". It would be a
few lines in 'stale_write_errors' and the noop filter's caller,
and the error would then fire only for a graphnode the user
edited that changed under them, which is the case the remedy
text describes. I would do it.
