* Setup

scratch dir, ran it on port 1763 with three skgrepos: 'main'
and 'priv' owned, 'theirs' foreign. Seed in 'main': r contains

* Findings
** One defect: a dirty view is redrawn as collateral (probe 7)
Slice 2 split the two matches, but 'collateral_viewforest_ids'
('save_dependencies/mod.rs') does not skip dirty views. Before
slice 2 a dirty view in the neighborhood always refused the
save, so it could never be a collateral target. Now a dirty
view linked to the save passes the check and is still in the
full neighborhood, so the server sends it a 'collateral-view'.
Both clients' 'apply-streamed-view-update' replace the buffer
without looking at its modified flag, so the user's unsaved
edits there would be lost. The plan and the docs say "a dirty
view is never redrawn".

* 7. Dirty view linked to the saved node: differs
** Part 1: no conflict, as the plan says, but L is redrawn

** Part 2: link save succeeds, as the plan says, but r redrawn

Response: no errors; x.skg has the link; but a
'collateral-view' for content-view:r arrived (the log: "save

** Part 3: edit of A refused, as the plan says
Response: "this save conflicts with unsaved dependencies in
content-view:r ... Conflicts: content-view:r [a, r]"; content
nil; a.skg unchanged.
** Why it matters
The keep-set lists the dirty view, so the client keeps it
locked; then the collateral-view handler unlocks it and
replaces its text, and the unsaved edits are silently gone.
The fix belongs in the server ('collateral_viewforest_ids'
skipping the envelope's dirty view IDs), in both clients
(skip a modified buffer), or both.
