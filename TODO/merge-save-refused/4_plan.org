* Vocabulary
- 'baseline', 'stale', 'the baseline's writes', 'the buffer's
  writes', 'merge node', 'merge pair', 'dirty view': as
  'docs/glossary.org' defines them since plan 2_2.
- 'the buffer's copy' of a graphnode: the supplemented Save
  instruction the saved text yields for it, after the noop
  filter ('nonmerge_nodeInstructions' in the save handler).
- 'the baseline's copy': the supplemented Save instruction the
  baseline yields for it ('baseline_writes' in
  'server/serve/handlers/save_staleness.rs').
- 'untouched': a graphnode is untouched by a buffer when the
  buffer's copy and the baseline's copy are equal, compared as
  'baseline_writes' compares a copy with the graph (lists by
  distinct pid, body as a view reads it back). The user did not
  edit it; the buffer merely still shows what the server drew.
- 'outdated': a graphnode whose baseline copy differs from the
  graph. Stale, as the glossary has it, is outdated and written
  or deleted by the buffer.
- 'the collateral neighborhood': the IDs
  'update_relevant_neighborhood' ('server/dbs/in_rust_graph/
  relation_accessors.rs') returns for a save's touched IDs: one
  hop over contains, linksTo, subscribesTo and hidesFromSubs in
  both directions, plus the override walks.
- 'a buffer of the diff view': an open view whose 'ViewState'
  has 'diffView_buffer_kind' set ('server/types/views_state.rs').
* Agreed behavior
** An untouched outdated graphnode will be left out of the save
Today a buffer that still shows A as the server drew it, while A
changed in the graph, is refused as stale when it saves, even if
the user edited only B: the noop filter compares A's copy with
the graph, finds a difference, and counts it as a write. After
slice 1 the save will drop the Save instruction of every
graphnode that is outdated and untouched, write the rest, and
redraw the view, which then shows A as the graph has it. The
stale refusal will fire only for an outdated graphnode the
buffer edited or deletes. A delete is never untouched: deleting
is an edit. A fork clone's original is never untouched: an
unchanged foreign graphnode makes no fork. The error's text does
not change. What the save response says: a warning per dropped
graphnode, "Left as the graph has it: TITLE (ID), which changed
after this buffer was rendered and which this buffer did not
edit.", so the user learns why the redraw differs from what they
saw. The warning does not report graphnodes the buffer edited,
graphnodes that did not change, or graphnodes the noop filter
dropped.
** The dirty-view check will not match through links
'dirty_view_conflicts' ('server/serve/handlers/
save_dependencies/mod.rs') matches each dirty view's dependencies
against the save's touched IDs and their collateral neighborhood
in the before and after graphs. After slice 2 that match will use
a neighborhood computed without the link relation, in both
directions, so a dirty view of L, where L links to the saved A,
no longer conflicts with A's save, and a dirty view showing A no
longer conflicts with a save that only adds a link to A. The
collateral redraw of clean views ('collateral_viewforest_ids')
keeps the full neighborhood: a clean view showing A's mentioner
folder is still redrawn when X gains a link to A. A dirty view
showing that folder is not redrawn, as no dirty view is, and
writes nothing of it; its folder is refreshed at its next
redraw.
** A view request will not switch to a buffer of the diff view
'handle_single_root_view_request' ('server/serve/handlers/
single_root_view.rs') answers '((switch-to-view "ID"))' when the
requested graphnode is a root of an open view, through
'content_viewforest_id_for_root_gnid' ('views_state.rs'). After
slice 3 that lookup will skip every open view whose
'diffView_buffer_kind' is set, so a request for a graphnode that
is a root only of diff-view buffers renders a content view, and
a request for one that is also a root of a content view switches
to that content view, as today.
** What stays as it is
- The stale refusal and its text, for an edited or deleted
  outdated graphnode.
- The noop filter on the saved text, and what the save writes
  for every graphnode the user edited.
- The collateral redraw: which clean views a save redraws.
- A dirty view's dependencies as slice 4 of plan 2_2 left them:
  the graphnodes it holds viewnodes of.
- The switch to an open content view whose root is requested.
- The diff view's own four buffers, their roots and their
  registration.
* Pitfalls the slices must respect
** Where the buffer's copies and the baseline's copies meet
'stale_write_errors' ('save_staleness.rs', line 58) computes
'baseline_writes' (a map from pid to the baseline's supplemented
copy) and 'buffer_written_pids', and emits one error per pid in
both. The buffer's copies are the Save instructions in
'nonmerge_nodeInstructions' at the call site in 'save_buffer.rs'
(near line 897), supplemented and noop-filtered by
'extract_nonmergeSavePlan_locally_in_graph' exactly as the
baseline's are. Compare a buffer copy with a baseline copy by
'buffernode_differs_from_disknode' after
'with_relationships_by_distinct_pid' on both
('save_staleness.rs', line 144), and after trimming both bodies
as 'graphnode_as_read_back_from_a_view' (line 126) trims the
graph's; factor that canonicalization into one function the
three comparisons share.
** What the handler does with a dropped Save
'nonmerge_nodeInstructions' is a 'Vec<NodeInstruction>' the
handler mutates in place through the rest of the pipeline
(restore requests, delete propagation, strandeds, Hoist, forks).
Remove the untouched outdated Saves right after the stale check,
before anything reads the vector again, so that delete propagation
and the Hoist classification never see them. A 'SkgrepoMove' in
'skgrepo_moves' for a dropped graphnode cannot exist: a move
changes the copy's home skgrepo, so the graphnode is not
untouched. The save's warnings travel in 'parse_warnings' and the
'SaveResponse'; add the new warnings beside the strandeds
warnings ('strandeds_warnings'), which reach the response the
same way.
** Only the stale check knows the baseline's copies
'baseline_writes' is private to 'save_staleness.rs'. Give
'stale_write_errors' a richer result (errors, the untouched
outdated pids with their titles for the warning) rather than
exposing the map; keep the function's one call site.
** The neighborhood has one definition and two readers
'update_relevant_neighborhood' ('relation_accessors.rs', line
234) is called twice, both in 'SaveAffectedIds::from_prepared'
('save_dependencies/mod.rs', lines 29 and 31), for the before and
after graphs. 'matching_identity' (same file) reads the two sets
for both the collateral redraw ('collateral_viewforest_ids') and
the dirty-view check ('dirty_view_conflicts'). Parameterize the
neighborhood by its list of ordinary relations (the four today;
the override walks stay in both), keep the existing signature as
the full version, and give 'SaveAffectedIds' a second pair of
sets without 'LinksTo' and a second matcher that
'dirty_view_conflicts' uses. Do not copy the walk.
** Which views are buffers of the diff view
'ViewforestId' has two variants, 'ContentView' and 'SearchView'
('views_state.rs', line 22); a buffer of the diff view is a
'ContentView' whose 'ViewState::diffView_buffer_kind' is 'Some'
('register_diffView_view', line 176, sets it after
'register_view'). 'content_viewforest_id_for_root_gnid' (line
141) filters by the variant only, which is why it finds
diff-view buffers. 'root_gnids' maps every root ID, primary and
extra, to the view IDs; the lookup must consult 'self.views' for
the kind.

Slice 6 of plan 2_2 made the integration test 'diff-view' (both
clients) close its diff-view buffers before asking for a view of
a root they hold, because the request switched to them. After
slice 3 that closing is unnecessary; remove it and let the test
exercise the new behavior (a content view of 'r' opens beside
the diff-view buffers).

** TODO Slice 4: the runtime generation starts at the epoch again
Plan 2_2's slice 3 made a server start its runtime generation at
0 ('server/types/env.rs', near line 80, 'generation : 0'); before
it, a server started at the microseconds since the Unix epoch
(the removed 'startup_generation' in that file, see commit
d6ea5ccc), which the staleness check needed and nothing else.
Jeff wants the epoch start back: a generation in the server's log
then places itself in time, at no cost. So 'SharedRuntime' will
start at the microseconds since the Unix epoch again, and each
swap-in will still add one. Nothing reads the number for
staleness. Check for a test that asserts the start at 0 (grep
for "generation" under 'tests/' and 'server/', around the swap-in
and the reload notice) and adapt it; update the comment at the
start value and 'docs/data-model_technical.org' ("Runtime
generations and rebuilding") where it says what the number is.
Run 'bash/nextest.sh'. One commit.
