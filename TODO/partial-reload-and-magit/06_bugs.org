** Result
There are three branch regressions in this story, with three separate causes.
I implemented the natural fixes for all three.  The duplicate-telescope
warning is real data, not a fourth regression.  The old herald-table claim is

** Regression 1: the blocking pause and the herald timeout
*** Cause
The branch added every selected path outcome to the =verify connection=
response.  This corpus currently has 29,973 direct =.skg= files.  For every
one, =verify_connection_response= serialized the pathname, a 64-hex-character
BLAKE3 digest, graph generation, index state, and Tantivy generation.  That
made a ping into a multi-megabyte response which Rust had to construct and
Emacs had to receive, decode, and parse on its UI thread.  In the captured run
the verification request occupied 3.15 seconds.

Neither client used this data.  Emacs copied =path-outcomes= into
=skg--server-store-state=, which has no readers.  Neovim copied it into
=config.store_state=, whose path outcomes likewise have no readers.  The
server's selected path manifest remains authoritative and is used internally;
there is no reason to duplicate it over the handshake wire.

The timestamps also explain the misleading herald message.  Client init
queued verification, then =skg-herald-rules-ensure= made three one-second
waits.  Because this branch serializes requests, all three herald requests sat
behind verification and all three waits expired.  They reached Rust together
immediately after verification completed and succeeded, which is why heralds
could work despite the message saying their table was empty.
*** Fix
I removed =path-outcomes= from the verification response and from both
clients' unused caches.  The response still carries the small information the
clients consume: source inventory, telescope warnings, pending recovery
incidents, graph generation, and store health.

This removes the new cause of the UI pause and keeps the normal handshake well
inside the existing herald wait.  I did not redesign the preexisting herald
retry protocol; an independently wedged server could still make its old false
timeout claim.  That is deliberately outside these branch regressions.
** Regression 2: hot reload caused a full-corpus sweep and leaked connections
*** Cause
Two lifecycle mistakes combined with the branch's new exact sweep:

1. =skg-reload= unloaded =skg-state=.  Unloading made
   =skg-rust-tcp-proc= void without closing the Emacs process.  The following
   =skg-client-init= therefore opened a new connection while the server kept
   the forgotten old one.  The live server had five established Emacs-side
   connections after repeated reproductions.
2. The verification handler called =skg-start-reload-observation=, which
   always removed and recreated even-live file watches and unconditionally
   scheduled a full sweep.

The full sweep is exact and expensive by design:
=changed_paths_since_selected= calls =selected_path_digest_manifest=, which
enumerates and reads all 29,973 files and computes a BLAKE3 digest for each.
It ran as an ordinary serialized =reload paths= request.  This accounts for
the roughly 40.5 seconds between the full-sweep request and the next queued
foreground request in the captured run.  Emacs itself could process unrelated
input, but no SKG request on that connection could pass the sweep.
*** Fix
I made hot reload preserve =skg-state= and re-evaluate it plainly.  This keeps
the live process, request records, length-prefix state, and monotonic request
number while refreshing the functions and struct accessors.  Reload now
refuses to run while a foreground request is active, rather than tearing its
handlers out mid-flight.  I also plainly re-evaluate the stateful reload and
worktree-guard modules, so their live watch/advice state survives but edits to
their functions actually take effect.

=skg-start-reload-observation= is now idempotent when every installed watch is
valid.  The TCP sentinel still removes all watches on a real disconnect; a
subsequent real connection therefore installs fresh watches and requests the
mandatory gap-covering sweep.  A stopped/invalid watcher does the same.  Only
the no-gap hot-reload case skips it.

Together, these changes make the documented reload snippet reuse its existing
TCP connection and existing valid watches.  It neither leaks a server
connection nor launches a full-corpus sweep.

** Regression 3: a numeric visit sequence was mistaken for a missing field

*** Fix
The key/value extractor now accepts any scalar atom supported by the existing
=atom_to_string= helper: string, integer, or float.  The visit handler then
parses that text as =u64= as intended.  Nonintegral and negative values still
fail validation.
** Architectural choice left for Jeff
The plan says full sweeps belong in a low-priority observation worker and that
foreground save/search preempts them.  The implementation does not yet have
that worker: a true connection, watcher-gap, explicit-manual, or batch-end

=handle_reload_paths_request=.  The hot-reload fix removes the accidental

1. Accept the rare real-gap pause for now.  Exact recovery stays simple; the

** Yes: give requested views a fast lane, with one important qualification
That is the right shape.  I would make the observation work queue
reprioritizable, and a foreground view request would promote the source paths
that can affect the requested view ahead of the sweep cursor.  The unit to
promote should be a normalized =.skg= source path (or telescope), rather than a
node: one source can define several IDs, and one telescope can contain several
sources.

For a view we already know, the fast lane can include:

- every source presently selected for an ID in its viewforest;
- all possible source paths for those primary IDs; and
- the requested root's possible paths, even if that root is not presently in
  the graph.

If one of those paths changed, its reload transaction and the view's rerender
should also jump ahead of ordinary sweep work.  The background scan can then
resume where it left off.  The worker must yield rather than merely share the
same FIFO TCP request queue; otherwise it has only moved the existing pause to
a different function.

The qualification is that scanning the paths in the old view does not prove
the new view complete.  An as-yet-unscanned file elsewhere can add or remove an
incoming link, containment edge, subscription/override/hide relationship, or
an extra ID that changes the requested view.  A requested ID newly introduced
as an extra ID is especially unknowable from its filename.  Only the completed
exact sweep can certify that no such source exists.

I therefore recommend this user-visible contract:

1. A view request preempts the scanner and is answered immediately from the
   selected graph.
2. Its known source paths enter the observation fast lane, and any resulting
   view replacement is offered automatically.
3. Until the exact sweep completes, the client shows a small
   "reconciliation pending" indication; completion removes it and applies any
   final collateral replacement.

Waiting for the fast-lane paths before the first display is also possible, but
it adds latency without buying a correctness guarantee.  Silently presenting
the answer as fully current would be worse.  Unless Jeff prefers the blocking
variant, I propose the immediate-display contract above.

The worker itself should own only observation: exact enumeration, byte
hashing, priority/deduplication, cancellation epochs, and a resumable full-sweep
cursor.  It should not mutate the graph, own view state, or talk on a client
connection.  It returns observations to the serialized graph-transition path;
that path still constructs a stable transaction and lets the owning connection
handle dirty-buffer conflicts.  I think this division follows the existing
invariants closely enough to be the natural implementation, but the
reconciliation UI contract above is an architectural choice, so I am stopping
for Jeff's response before building it.
** Yes, there are other orphaned intentions
I compared the plan's promises with the current coordinator, reconnect,
collateral-refresh, and Git-presentation code.  The missing observation worker
is the largest one, but it is not alone.  I found four material clusters, plus
one old intention that I think should stay abandoned.
*** Request coordination and disconnect cleanup are incomplete
The plan gives each request its terminal handler, locks, cleanup guard, and
incident ownership.  The actual request record contains only an ID, incident
ID, and response handlers; submission is ordinary FIFO.  There is no priority
between interactive and observation work and no replacement/coalescing of
unsent observation requests.

More seriously, the TCP sentinel clears the coordinator without synthesizing
terminal failures for queued and in-flight requests.  Thus their cleanup
callbacks do not run.  In particular, a disconnected reload observation can
leave =skg--reload-observation-in-flight= true indefinitely.  That is a real
lifecycle bug, not just an unrealized optimization, and it is prerequisite
work for a worker which must survive preemption and disconnects.

The plan also reserves generic =Error= frames for envelope/connection failure.
Several expected endpoint failures still use them instead of request-specific
terminal replies.  Finally, committed-but-unpresented reload incidents are
thread-local to a connection and are explicitly discarded when its thread
exits; the planned process-owned incident registry was not built.
*** Reconnect does not reattach surviving views
The plan says the next handshake reports each surviving buffer's base graph
generation, token, and dirty status, so the server can reattach clean and dirty
stale buffers.  The current verification request carries none of that, and a
new connection begins with empty =ViewsState=.  Emacs buffers survive a real
reconnect, but the server has forgotten them.

Relatedly, the planned no-client case---observe and commit safe graph changes,
then retain presentation debt for the next client---does not exist as such.
The server retains a reconciliation generation, but not the view/incident
state needed to discharge all of that debt after reconnect.
*** The collateral scheduler has its engine but not all of its contract
The MRU queue, one-at-a-time rendering, cancellation epoch, and
generation/revision checks exist.  These promised pieces do not:

- A queued buffer is not marked visibly stale.  The stale flag is set only
  after an offer reaches a buffer that is already modified; edit/save does not
  reject once and promote the queued refresh as the plan specifies.
- The server parses the collateral =client-token= but deliberately ignores it,
  so the exact token check in the design is not enforced.
- A background scalar challenge is only warned about and rejected by both
  clients; there is no approval-and-retry path.
- A search view retains its query, but ordinary collateral repair completes
  the old result forest rather than rerunning membership and ranking against
  the corresponding new Tantivy generation.  The special cyclic-root repair
  reruns searches; general graph changes do not appear to do so.

These are narrower than the missing observer, but the stale-before-edit rule
and query rerun are correctness/user-data issues rather than polish.
*** Git presentation observation is not yet durable coordination
The Magit hook and explicit presentation-observation request exist.  Its
signature and pending work live in a connection-local scheduler, however, not
in the planned durable/process-owned observation state.  It consequently lacks
the same reconnect, failure, priority, and coalescing guarantees.  This should
probably share the new coordinator rather than grow another special queue.
*** The client-side acknowledged-manifest cache is an obsolete intention
The plan says both clients mirror acknowledged path outcomes and pending
failures.  The old verification reply did transmit the entire path-outcome
map, but neither client ever read it; that was the large handshake payload I
removed.  The server is already authoritative, successful reloads wait for the
exact Tantivy generation, and incident IDs can represent unresolved work.

I do not recommend resurrecting a multi-megabyte client mirror merely to make
the progress document literally true.  The new observation coordinator should
keep that state process-side and expose only compact status/incident data.  We
should update the plan/progress wording when its replacement lands.

** Short answer
This is a real simplification, and I prefer it to the fast lane.  It lets us
drop view-prioritized observation and makes a commanded pull's normal path
conflict-free: begin only when every view is clean, prevent edits, pull,
reconcile, refresh every surviving view, and only then unlock.

It does not quite let us drop the background observation worker if both of
these remain requirements:

- missed watcher events are eventually found by an exact sweep; and
- queries remain usable while that potentially 40-second sweep runs.

Today the sweep is a synchronous request on the one interactive connection,
so it blocks every query behind it.  We can, however, reduce the worker to a
much simpler process-owned observer/maintenance job.  It need not promote view
paths, mediate ordinary edits, or mutate connection-owned view state.  It
enumerates and hashes paths, retains the pending generations, and hands one
stable change set back to the serialized transition.  File notifications can
continue to provide the cheap immediate indication that work is pending.

If it is acceptable for all queries to pause during every exact sweep, then we
can omit that worker.  That is the actual trade: the editing restriction alone
does not unblock the TCP request loop.
** Pull and full rebuild have different query-safety properties
A pull only changes disk.  Until reconciliation, queries can consistently use
the old selected graph and indexes.  New query/view buffers must be born
edit-locked and join the final refresh census, but read-only querying is safe.
A query which straddles the final graph transition should finish against one
pinned generation or be retried, never combine graph and TypeDB data from two
generations.

The current full rebuild is different.  It deletes and recreates the live
TypeDB database and the live Tantivy directory in place.  Concurrent queries
can therefore see a missing or half-populated database; putting that function
on a worker thread does not make it safe.

There are two honest choices:

1. Initially make full rebuild an exclusive maintenance operation: no editing
   and no queries until it finishes.  Pull plus partial reconciliation still
   permits queries throughout.  This is my recommendation.
2. Build TypeDB and Tantivy under shadow generation names and atomically swap
   the server's store handle after both are ready.  Then queries can remain on
   the old generation during a rebuild.  That is a useful design, but it is a
   separate and substantial store-lifecycle project.

Thus I would not promise "query as much as you want during rebuild" in the
first implementation.  It is safe during pull, observation, and an ordinary
partial transition; a destructive repair rebuild should visibly enter
exclusive maintenance.
** Corner cases the rule needs to cover
*** A pending disk change can prevent a dirty view from being saved cleanly
Suppose an external writer changes a telescope while a related view is dirty.
We correctly postpone incorporating the disk change.  The user then tries to
clean the view by saving it.  The current save path does not compare every
would-be-written path with the graph-selected manifest before writing, so it
can overwrite the external bytes which are still pending.

Every save therefore needs a disk-generation precondition on its complete
prepared write/delete set.  If those paths still match the selected manifest,
the save can finish and reduce the dirty census.  If any drifted, ordinary save
must write nothing and enter an explicit base/local/disk resolution.  There is
no policy which simultaneously says "never incorporate while any view is
dirty", "never discard either side", and "ordinary save can always make the
view clean"; an overlap requires a deliberate conflict-resolution exception
or requires the user to discard one side.  I recommend retaining the existing
three-way conflict UI for this exceptional case.
*** Once pending work is known, letting clean views become dirty defeats convergence
The cleanest state machine is a draining state:

1. An out-of-band candidate arrives.  Skg reports pending reconciliation.
2. Views already dirty remain editable so the user can finish them, subject to
   the disk-generation save check above.
3. Every currently clean view, every view as it becomes clean, and every newly
   queried view is edit-locked.  Hence no new dirty view can join the census.
4. Once the last dirty view is clean and no save/request is still finishing,
   Skg schedules (rather than nests inside the save handler) one prompt.
5. Approval starts reconciliation under the same lock.  Successful refresh of
   all views ends the incident and unlocks them.

This extends Jeff's no-new-edits rule from the pull itself to the short period
in which already-dirty views drain.  Without it, a different view can become
dirty just as the last old one becomes clean, and the prompt races forever.
*** "Not now" needs defined semantics
If the user declines the prompt and all views become ordinarily editable
again, the system immediately returns to the save collision and stale-base
problems above.  The simplest meaning of "not now" is therefore: retain the
pending incident and leave Skg in read/query-only mode.  A manual
=skg-reconcile-pending-changes= command later performs a partial reload of the
retained changed paths (plus an exact fence), refreshes, and unlocks.

If Jeff wants "not now, but let me keep editing", we can support it, but it
needs the disk-generation save guard and conflict workflow on every intervening
save.  That is less simple.  Also, the manual operation is a /partial reload/,
not a database rebuild; naming it that way will keep the destructive repair
command distinct.
*** A pull can fail after changing some repositories
Cancellation, authentication failure, a merge conflict, or failure in a later
repository does not mean the worktree is unchanged.  The client must close its
batch bracket in an unwind/finalizer, then reconcile whatever actually changed
before unlocking.  A failed pull whose disk cannot be legally loaded leaves
the views locked with an actionable report; it must not unlock merely because
the Git subprocess exited.

Moving the command into the client means the client owns this lifecycle.  The
Git processes should still be asynchronous so Emacs/Neovim can answer queries
and display password/conflict output.  The operation has to preserve the
current script's partial-success behavior rather than treating the repo loop as
atomic.
*** The edit lock must be a state, not a one-time pass over buffers
The existing save lock covers only buffers which exist when it is installed.
During a query-enabled pull the user can open new views, so a process-local
maintenance epoch must cause view constructors to lock those too.  Pure
navigation, opening views/searches, copying text, and closing views remain
allowed.  Commands which sound query-like but edit metadata and auto-save
(such as requesting a collection in the current view) are writes and must be
refused.

Modified raw buffers visiting configured =.skg= files also belong in the
preflight.  Git does not know about their unsaved editor contents; a pull can
replace their on-disk files and a later ordinary file save can silently put the
old text back.  Such buffers must be clean before a commanded pull and locked
against saving for its duration.  Counting only =skg-view-uri= buffers misses
them today.
*** The end of reconciliation needs a fence, not merely an empty queue
Watcher delivery can lag.  A file can also change after the full manifest was
enumerated but before views unlock.  The maintenance epoch therefore needs a
monotonic observation fence: the final selected manifest must equal an exact
post-batch observation, and no newer watcher generation may be pending.  A
writer which never becomes quiescent should leave a visible pending/locked
state rather than cause a busy retry loop.

Additions, deletions, atomic renames, config/source changes, and Git
presentation-only changes must all advance the relevant generation.  The last
one may require only rerendering diff-mode views, but it is still part of the
"safe to unlock" decision.
*** Disconnect and multiple-client cases become more important, not less
The current sentinel unlocks all buffers and forgets request callbacks.  If a
connection drops during a pull, that behavior would defeat the safety rule at
exactly the dangerous moment.  The maintenance/pending epoch must be
process-owned; reconnect verification must rediscover it, reattach surviving
views, and restore their lock before editing is enabled.  If the editor itself
dies, the next client must reconcile the possibly changed disk before enabling
writes.

The design assumes one interactive client, but the server currently accepts
more than one connection.  A server-issued maintenance lease must either prove
there is only one verified interactive client or collect/lock all of them.
Client-only checking in Emacs is not enough when Neovim can also issue rebuild
and save requests.  Shell/control connections do not count as interactive
clients, but all state-mutating endpoints should require or respect the
process-wide epoch.
*** Failure and authorization are terminal states too
Invalid YAML, ownership/ID conflicts, telescope scalar-release questions,
TypeDB failure, and failed Tantivy indexing can prevent reconciliation after
the disk has changed.  Only a fully acknowledged graph/TypeDB/Tantivy
generation plus completed view presentation permits unlock.  Otherwise the
incident remains visible and read/query-only, with explicit repair, recovery,
or authorization commands.  A full rebuild which fails after deleting the old
TypeDB is especially unable to return to queryable normal mode.
** What this removes, and what remains
This change removes the proposed view fast lane.  It also removes dirty-view
conflicts from the /commanded pull/rebuild happy path/, and makes
"stale-before-first-edit" unnecessary for views created during maintenance:
they are simply locked until refreshed.

It does not remove:

- total request termination and disconnect cleanup;
- the process-owned pending-incident/maintenance state and reconnect census;
- a pure observation job, unless we accept blocking queries during exact
  scans or weaken missed-event recovery;
- generation-safe search reruns and client-token checks;
- the collateral scheduler for ordinary saves, which can still affect other
  open views; or
- durable/coalesced Git presentation observation.

The observer is nevertheless much smaller than the one I previously
described: no view-path priority, no edit preemption, and no attempt to make a
partially scanned graph display-current.  It only discovers exact disk state
without monopolizing the interactive connection.
** Revised implementation order
I propose:

1. make request/disconnect cleanup total and add the process-wide maintenance
   epoch/lease;
2. add a complete save write-set versus disk-generation precondition;
3. implement the client-owned asynchronous pull command and the clean/draining
   locks, including raw =.skg= buffers and newly opened views;
4. move exact observation into the simple server-owned job, then apply one
   fenced partial transition and refresh before unlock;
5. reattach pending maintenance and views on reconnect; and
6. finish the independent collateral/search/token and Git-presentation holes.

For the first version I recommend (a) live queries during pull and partial
reconciliation, (b) exclusive full rebuild, (c) no new edits once pending work
is known, and (d) "not now" means remain read/query-only until the manual
partial-reconciliation command runs.  If Jeff agrees with those four precise
meanings, the architecture is settled enough to implement without silently
choosing among the corner cases.

** Verdict: yes, with a qualification
Yes.  This requires less machinery than the draining design, provided an
interrupted dirty buffer stops being a live Skg view.  After its evidence is
durably archived, it should become a read-only recovery artifact which the
server no longer regards as open.  The user can inspect it and its undo
history, but cannot save it back through Skg; a newly queried view represents
the post-rebuild graph.

That boundary is what makes the idea simple.  If the old dirty buffer keeps its
live =view-uri= and is expected eventually to rejoin the graph, we still need
base generations, conflict state, reattachment, token checks, and careful
collateral scheduling, and most of the simplification disappears.
** What becomes simpler
We can delete the proposed "wait for all dirty views to drain" protocol and
its difficult case where a pending disk change prevents the last dirty view
from saving.  A user-commanded pull or rebuild can instead do this:

1. freeze the set of current views;
2. durably archive every dirty one's last server text, current raw text, and
   their ordinary diff;
3. retire and lock those dirty views, and edit-lock the clean ones;
4. perform the maintenance operation; and
5. refresh the clean live views before unlocking them.

No unsaved text is fed into an uncertain merge, and no rebuild has to wait for
the user.  A crash after step 2 still leaves ordinary files from which to
recover.  This also sharply reduces the reconnect problem for dirty views:
their safety no longer depends on reconstructing volatile client/server view
state.

The archive itself is modest, auditable client work.  An ordinary unified diff
between =last-fetched.org= and =unsaved-changes.org= is a good choice: it
records exactly what changed locally without pretending Skg understands the
user's intent.  Folding is normally overlay/visibility state and is compatible
with a text lock.  Undo/redo while otherwise read-only needs small custom
wrappers in both clients, but it is bounded work; the on-disk snapshot remains
the durable authority even while undo changes what the retired buffer shows.
** My pushback is about user cost, not technical soundness
A conflict is not always inevitable.  A dirty view may be wholly unrelated to
the paths changed by a pull, and the present impact analysis can sometimes
prove that and preserve the edit session untouched.  The conservative archive
rule interrupts /every/ dirty view.  It trades a complicated rare conflict
workflow for a simple but more frequent manual recovery workflow.

The raw diff is familiar, but recovery may still be more awkward than a normal
source-file merge.  One rendered view can contain edits to several nodes,
generated collections, repeated appearances, and Skg metadata; its directory
being named for the original root does not mean all changes belong to that
root.  After the graph changes, hunks may need to be interpreted and reapplied
rather than patched mechanically.

I think that trade is reasonable for explicit, comparatively rare maintenance
commands which the user knowingly starts.  I would push back against silently
archiving active work whenever any watcher event arrives.  For an unsolicited
out-of-band change, Skg should report what it detected and ask before it
interrupts dirty views.  If such interruptions become common, the simpler
implementation will have made ordinary use materially harder.
** It does not remove all of the earlier work
The archive rule removes the draining state, the view fast lane, and most
dirty-view reattachment/conflict machinery from the maintenance path.  It does
not remove:

- exact observation and its worker if queries must remain responsive during a
  long sweep;
- the current full rebuild's inability to serve safe concurrent queries while
  it destroys and recreates the live TypeDB/Tantivy stores;
- process-owned maintenance state, total disconnect cleanup, and a final
  watcher-generation fence;
- locking views opened during maintenance and refreshing clean live views;
- generation-safe search reruns, collateral handling for ordinary saves, and
  Git-presentation observation; or
- a save-side disk-generation precondition, because an unseen external write
  can still race an ordinary save before any maintenance command begins.

It also does not by itself cover a modified raw buffer visiting an actual
=.skg= file.  Such a buffer has no "last received from server" rendering and
can overwrite pulled bytes later.  It needs either its own disk-based archive
variant or a refusal to begin maintenance until it is clean.

This is a smaller and more failure-tolerant design than my previous proposal.
Its new persistence and read-only-buffer code is substantially cheaper than
the draining/conflict/rejoin state machine it replaces.  It does not eliminate
the observation worker or the independent coordinator holes, but it reduces
the hardest client-side portion of the project.

**** Glossary
***** The /selected generation/, =G0=,
  is the one coherent graph + TypeDB +
  Tantivy state which Skg currently answers queries from and permits views to
  save against.
***** The /observed candidate/, =Gdisk=,
  is the coherent graph obtained by reading
  and folding the changed disk.  It has been validated but has not been made
  selected.
***** /Pending disk work/ means that =Gdisk= exists and differs semantically from
  =G0=, but the user declined the proposed maintenance for now.  Queries still
  use =G0=; disk already contains the bytes behind =Gdisk=.
***** A /save proposal/, =S=,
  is the semantic edit parsed from one live view,
  before it writes anything.
***** The save's /prepared write set/
  is the complete list of files it would
  create, replace, move, or delete, with their required before-digests and
  exact proposed after-bytes.  Preparing it has no side effects.
***** A /colliding save/
  is one which might overwrite, misinterpret, or invalidate
  pending disk work.  “The filenames differ” is not enough to prove the
  absence of a collision: a new extra ID, source selection, relationship, or
  global uniqueness violation can connect otherwise different files.
***** A /disjoint save/
  is a much stronger claim: applying =S= before =Gdisk= and
  applying it after =Gdisk= have both been validated and produce the same
  canonical final graph and disk manifest, without overwriting an externally
  changed byte.  In other words, the two changes commute.
***** /Reconciliation/
  is selecting the pending disk work through the maintenance
  protocol: archive first, build/validate the candidate stores, classify
  views, and then refresh, preserve, or retire them.
**** What declining looks like
Suppose Skg is serving =G0=.  Someone changes node =A= on disk; observation
constructs =Gdisk= and predicts which dirty views would be retired.  Skg asks,
and the user chooses “not now.”  Nothing is rolled back on disk.  Instead:

1. =G0= remains the selected query/save base.
2. A persistent status says that external semantic changes are pending and
   identifies the candidate/incident.
3. Existing views remain editable.  New views and searches come from =G0= and
   carry the same pending/stale notice.
4. An explicit command can show the changed nodes and can run reconciliation
   later.

The only dangerous operation in that interval is save: it would write from an
old graph into a disk that already represents a different graph.

**** The simple save policy
Allow editing, but reject every Skg save while pending disk work exists.  The
rejection writes nothing and offers the reconciliation command.  Undo, redo,
navigation, queries, and more editing continue normally against =G0=.

This is easy to state and test, and it cannot destroy the external bytes.  Its
cost is that “not now” postpones every save, even a save of an obviously
unrelated node, until the user accepts reconciliation.

**** What “server-proven disjoint saves” would actually require
Suppose disk changed =A= and the user edits =B=.  Before allowing the save,
the server would have to hold both =G0= and =Gdisk= and do all of this without
writing:

1. prepare =S= from the view and its =G0= base;
2. verify that none of =S='s files would replace bytes changed in =Gdisk=;
3. apply and validate =S= speculatively to =Gdisk=, catching global ID,
   source, override, relationship, and telescope interactions;
4. also compute =G0 + S= and prove that later adding the pending disk change
   yields the same canonical graph as =Gdisk + S=; and
5. at the commit fence, recheck that real disk still has the exact candidate
   digests, then atomically advance both the selected branch to =G0 + S= and
   the pending branch to =Gdisk + S=.

If any proof or fence fails, the save writes nothing.  For example, changing
=A.skg= externally and saving =B.skg= is still colliding if the new =A= claims
an extra ID which the edited =B= also claims, or if =B='s edit refers to a
version of =A= which the external change removed.  A pathname intersection
test would miss both cases.

This dual-generation, commuting-transition machinery is possible, but it is
substantially more architecture than my earlier short phrase suggested.  The
existing save-side disk-digest check supplies only the commit fence; it does
not supply the two speculative graphs or the commutativity proof.

**** Codex's revised recommendation

semantic disk candidate is pending.  That is the natural complement of “not

The UI should put “reconcile pending disk changes” directly in the save error,

We can add proven-disjoint saves later if pending intervals prove frequent

*** DONE What does 'proves a new semantic disk generation' mean?
**** Codex clarifies
It means more than noticing a changed mtime, and less than committing the
change to the live stores.

First the observer obtains a stable, exact disk candidate: path names and
BLAKE3 digests identify the bytes it read, watcher generations fence the scan,
and any relevant event which arrives during the scan makes it incorporate or
reread that path before closing the candidate.  It then parses all changed
sources, applies the normal privacy/source-selection and telescope-folding
rules, and validates the result as one candidate =NodeComplete= graph.

It compares that candidate graph with selected =G0= by canonical primary ID,
using choice 3's semantic equality.  There is a “new semantic disk
generation” only if the candidate has at least one added, deleted, or modified
semantic node.  For example:

- touching a file, changing whitespace which parses identically, or observing
  Skg's own already-selected save advances the acknowledged byte manifest but
  does not create a semantic generation and does not prompt;
- changing a node's text, source provenance, extra IDs, or authored
  relationships does create one; and
- invalid or unfoldable disk proves neither.  It produces an invalid-disk
  report/pending condition and is never offered as a valid =Gdisk= to select.

“Proves” therefore means “the exact bytes were stably observed, successfully
folded and validated, and their semantic graph differs from =G0=.”  It does
not mean the candidate is already authoritative.  Until the user accepts
maintenance, it remains the pending =Gdisk= defined in choice 17.  A later
watch event can supersede it and requires the same proof again before the
prompt is updated.

** DONE 19. What if Git or rebuilding fails?
Failure must be classified by whether disk or stores may already have changed,
not by the subprocess exit code.  Once that possibility exists, optimistic
unlocking can turn a recoverable failed pull into an unnoticed overwrite.

Recommendation:

- Archive failure: do not start the operation.
- Cancellation before the first external/store mutation: release all buffers;
  retain the incident as =maintenance-aborted= evidence.
- Pull failure after any repo may have changed: observe actual final disk,
  classify it, and reconcile or report it exactly as a successful pull would.
- Invalid/unfoldable disk: there is no trustworthy G1 or orthogonality proof,
  so retain the old stores, conservatively retire the snapshotted dirty views,
  keep clean views locked, and offer disk repair/recovery.  Do not call the
  operation reconciled.
- Store/index failure after selection begins: keep the incident and whichever
  last-good stores remain; unlock only when one complete graph/TypeDB/Tantivy
  generation has been re-established.

One alternative in the invalid-disk case is to abort and release the old dirty
views because the graph did not change.  I do not recommend it after a pull:
disk has changed and a later save can destroy the evidence.

*** DONE what is 'maintenance'?
**** Codex clarifies
/Maintenance/ is shorthand in this tree for the fenced protocol used by an
operation which selects disk state not produced by the current Skg save.  It
is not ordinary software upkeep and it is not every Skg command.

It includes an explicit pull, explicit partial reload, explicit full database
rebuild, accepted out-of-band reconciliation, watcher-gap/full-sweep repair,
and a configuration/source-set replacement which selects a different disk
graph.  It excludes ordinary view/search requests, normal Skg saves, editor
code hot-reload, and mere Magit/Neogit display refresh.

The /maintenance interval/ begins when the server installs the maintenance
epoch and clients have applied its archive/lock instructions, before the
first external mutation or store replacement.  It ends only with a terminal
outcome: either one coherent generation has been selected and every affected
buffer has been refreshed, preserved, or retired, or the operation has
aborted and the protocol has explicitly decided which old state and locks are
safe to restore.  Observation may happen before that interval in order to
decide whether unsolicited work is worth asking about.

Thus “prevent raw =.skg= saves during maintenance” means only during that
bounded epoch, not throughout a long user-declined pending interval.  In the
pending interval, a raw file's ordinary save instead needs its own exact
on-disk conflict check; the broader unresolved choice 20 is whether the first
version should support that or simply refuse to start explicit maintenance
while such a raw file buffer is modified.
