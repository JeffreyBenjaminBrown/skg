#+title: Partial reload: architecture review and alternatives
#+date: 2026-09-06
#+author: Astra, with two bounded Sol reviews

* My assessment

Your suspicion is substantially right: there is a simpler architecture worth
considering. The problem is not that you failed to learn CAP. The branch grew
from partial reload into a durable protocol coordinating the graph, two
derived databases, Git, editor buffers, recovery archives, and presentation.
It makes successful completion depend on a large collection of acknowledgments
and independently changing state. Some central guarantees remain incomplete.

I would favor one owner for state changes, immutable snapshots for reads, and
a smaller maintenance contract. My preferred longer-term direction is to make
the existing in-Rust graph the sole authority for live graph queries, paired
with a specific Tantivy search snapshot, and remove TypeDB from that
correctness boundary. A less disruptive alternative retains both databases
and permits an explicit pause while selecting and settling a reload.

I would not begin with STM, a language rewrite, or a new incremental-query
framework. I also would not promise that deleting a particular number of lines
will solve this. Significant deletion looks plausible; preserving every
current lifecycle and recovery promise would retain substantial complexity.

This is an assessment and a comparison of proposals, not an implementation
plan. No program code, tests, data, running servers, or Git state were changed.
The other document change records the findings in [[file:../problems.org][TODO/problems.org]].

* One user, one interactive client

All recommendations here assume your intended model: one user and exactly
one interactive editor connection per server process. Emacs and Neovim are
alternative implementations of that client. They are not concurrent users.

The implementation has an explicit admission guard:
[[file:../../server/runtime/mod.rs::181][InteractiveConnectionSlot::try_attach]] refuses another interactive
connection until the existing guard is dropped. The plans also expressly
reject secondary read-only clients and hypothetical multi-user machinery
([[file:07_plan.org::311][single interactive connection]], [[file:07_plan.org::1820][your clarification]]).
I found no reason to design for multiple simultaneous users.

One user still creates concurrency: the observer, index worker, background
renderer, socket handler, Git child process, and editor callbacks can overlap.
Those overlaps, and recovery after either process dies, explain the relevant
coordination problem. They do not require a multi-user architecture.

* Where the architecture becomes expensive

** Completing a graph change also requires completing an editor ceremony

The current path is approximately:

#+begin_example
allocate incident and epoch
  -> freeze and census editor buffers
  -> publish initial archive and verify it
  -> authorize Git / observe final disk
  -> publish recovery evidence
  -> update TypeDB and Tantivy and select the graph
  -> classify every enrolled view
  -> authorize protected text where necessary
  -> apply or retire views and acknowledge each
  -> transfer evidence and finalize the archive
  -> send exact unlock inventory
  -> acknowledge terminal delivery
  -> return to idle and observe again
#+end_example

Much of the danger is in interactions between these stages. A new view may
arrive after the original archive but before finalization. A report may become
modified because a Git process writes output. A response may have been applied
even though its ACK was lost. An old render may finish during source changes.

The [[file:07_plan.org::1870][late addition for views born during maintenance]] is especially revealing.
Supporting those views required provisional server enrollment by ViewUri,
binding to a later client buffer ID, two related censuses, more presentation
classification, and a barrier against finalization overtaking enrollment.
This is a real consequence of that promise. It is also an expensive promise
for a single-user application, and a good candidate for reconsideration.

Graph validity, preserving authored work, making every view current, and
finishing a human-readable report are different obligations. The current
protocol couples them into a global period of restricted operation. Some
coupling is necessary; the strongest all-buffers/all-receipts coupling is a
product choice, not a theorem.

An alternative is to let each buffer regain authority once its own disposition
is safe. A buffer awaiting an application ACK remains unsavable; it need not
keep unrelated, already reconciled buffers locked. Report finalization could
continue after selection if the complete recovery evidence is already durable
and retained server-side. That explicitly relaxes today's requirement for a
fully finalized client archive before global unlock; it must not relax the
initial dirty-work archive before risky mutation. This separation is compatible
with either proposed storage architecture, but is an additional product choice.

** Having a coordinator does not give it exclusive ownership

[[file:07_plan.org::1030][The plan]] correctly calls for a typed transition function and one authority.
The implementation nevertheless exposes a public mutex-protected coordinator
to several producers, and uses both strict and best-effort persistence paths.
Likewise, session state, candidate retention, generation selection, graph
writes, and index completion have separate synchronization mechanisms.

One actor, in the ordinary programming sense, means one event loop owns these
decisions. Workers may hash files or render from immutable input; they return
results as messages. They do not independently mutate or persist authority.
The owner can reject an obsolete result without sharing its mutable state.
That is more specific, and stronger, than adding another coordinator mutex.

The many IDs in the plan are not all redundant: a request, an incident, a graph
version, and an editor application really have different lifetimes. Randomly
merging their counters would conceal races. The opportunity is to remove
unnecessary overlapping lifetimes and authorities, then retain the identities
that the smaller protocol actually needs.

It does not mean doing every expensive calculation on one thread. Nor does
it make Git or the editor part of an atomic memory operation. Durable effects
still need explicit intent and completion records, with recovery for the gap.

** Three selected stores create work that the data model may no longer need

The [[file:../../server/dbs/in_rust_graph.rs::87][in-Rust graph]] already stores nodes, outgoing relationships, inverse
relationships, and extra-ID resolution using persistent collections.
[[file:../../server/types/nodes/rust.rs::14][NodeRust]] includes titles, bodies, aliases, provenance-bearing relationships,
and miscellaneous properties.

Several supposedly TypeDB-facing reads already return from that graph in
production: [[file:../../server/dbs/typedb/search.rs::23][container and relation lookup]] and
[[file:../../server/dbs/typedb/ancestry.rs::46][containerward ancestry]] are concrete examples. Their TypeDB paths largely
serve environments that did not initialize the graph, including older tests.
This is strong evidence for simplifying TypeDB's role, although it is not a
complete proof that every TypeDB dependency can be removed unchanged.

Today, [[file:../../server/maintenance/selection.rs::456][candidate selection]] drains readers, applies stores, waits for the exact
index generation, and checks coherence before publishing. The runtime
snapshot pins the graph, but it contains database handles; it is not by itself
an immutable snapshot of every fact those handles can later read. The gate
does important work. Replacing it safely requires changing the read boundary,
not merely deleting locks.

Global graph lookups and live-disk fallbacks also weaken that boundary.
For example, [[file:../../server/types/env.rs::51][find_source]] can discover a node from current disk after failing
to find it in the selected graph. That is convenient for certain diff paths,
but ordinary selected-graph queries should not silently consult unselected
data. Explicit snapshot parameters and separately named Git/disk evidence
queries would make the distinction reviewable.

** The worst observed delay was recovery serialization

The [[file:08_single-node-reload-performance.org][performance investigation]] is useful counterevidence to a blanket
criticism of incremental database updates. It attributes the roughly
40-second delay to repeatedly serializing and validating two complete graph
snapshots as YAML. In that recorded run the TypeDB update was about 13 ms and
Tantivy work about 148 ms.

The compact evidence format has already fixed that particular pathology.
The recorded real-corpus title-change reload took about 2.7 seconds afterward.
These are the branch's recorded measurements, not new measurements by me.

The remaining evidence design still writes a full baseline per incident.
That is an intentional cost of independently recoverable incidents, explicitly
accepted in the performance discussion. Sharing immutable baselines could
reduce it, but adds retention and deletion rules. It should be considered
separately from repairing lifecycle races.

* Concrete findings in the current code

These findings come from source inspection and independent cross-checking.
I did not run new crash experiments or the integration suite. The first two
are specific code defects with identifiable failure sequences, rather than
general concerns about concurrency.

** A delayed observer can overwrite newer durable maintenance state

[[file:../../server/runtime/maintenance.rs::177][persist_maintenance_state]] copies the coordinator while holding its mutex,
then releases the mutex before writing. The foreground
[[file:../../server/runtime/maintenance.rs::204][transition_maintenance]] holds that mutex through its own journal write.
The [[file:../../server/maintenance/journal.rs::78][journal publisher]] writes a unique temporary file and unconditionally
renames it onto active.yaml; there is no version check or common write lock.

A possible execution is:

1. Observer copies old state, then is delayed.
2. Foreground records and durably publishes a newer archive/selection/ACK state.
3. Observer resumes and renames its old state over the new journal.
4. A restart loads the old state.

Atomic rename prevents a torn file. It does not prevent an obsolete writer
from winning. The [[file:../../server/maintenance/observation.rs::629][observer]] and
[[file:../../server/serve/maintenance_connection.rs::118][disconnect path]] both use this looser publication route. This is a direct
example of why exclusive state ownership would help.

** Restart does not restore the selected generation recorded by maintenance

Startup initializes stores from current disk before constructing the runtime
([[file:../../server/main.rs::150][main startup]], [[file:../../server/dbs/init.rs::259][environment construction]]).
[[file:../../server/types/store_state.rs::95][SelectedStoreState::initial]] resets graph generation and manifest revision
to 1. [[file:../../server/runtime/mod.rs::76][ServerRuntime::new]] then loads the maintenance coordinator journal without
restoring that journal's selected snapshot or generation.

Suppose a real transition reached G1, recorded generation 2 or later, and the
process died before its remaining clean-view presentation completed. The
journal still names that generation, but startup supplies generation 1.
[[file:../../server/serve/handlers/maintenance_protocol.rs::923][Presentation staging]] explicitly rejects that mismatch.

The evidence codec can reconstruct G0/G1 semantic maps. I found no startup
consumer connecting those maps to restored store authority. The
[[file:../../server/serve/handlers/client_census.rs::356][reconnect census]] restores an initial-archive cache for preselection cases;
that does not repair post-selection graph identity. If current disk has also
changed, assigning the old generation number would be wrong anyway: recovery
must prove or reconstruct the corresponding content.

Thus the strong restart promise in [[file:07_plan.org::1505][the plan]] is not established by merely
retaining a checksummed journal and a reconstructible evidence file. This also
explains why codec round-trip tests can pass while actual restart remains
incomplete.

** Exact save checks do not exclude an uncontrolled external writer

[[file:../../server/save.rs::161][The save path]] validates the prepared before-digests and subsequently
[[file:../../server/save.rs::736][applies ordinary file writes/deletions]]. An outside process can change a
target between those operations. Even the apply method's additional read
only tests whether bytes already equal the proposed result; it is not an
atomic conditional replacement against the expected old bytes.

This is a limitation of the guarantee, not evidence that your usual pull
workflow always races. The checks are useful and catch drift already present
when checked. They cannot support the unrestricted claim in
[[file:07_plan.org::738][the save-fence exit condition]] that no unselected external byte can be
overwritten. A Rust lock, STM transaction, or watcher debounce cannot lock out
an unrelated editor or Git command.

Every proposal needs an explicit rule here: cooperative exclusion for known
writers, external editing only during a documented non-saving interval, or
acceptance that arbitrary simultaneous writes are detected only best-effort.
A private transactional canonical store with import/export is another option,
but changes the plaintext-worktree contract. Repeating checks forever does
not create a filesystem transaction.

Ordinary multi-file saves also still use direct writes without a durable
batch journal at this boundary. A crash can leave a truncated file or a prefix
of a multi-file operation. This is a pre-existing weakness exposed by the
review, not a claim that partial reload introduced it. Rebuilding caches from
disk cannot recreate bytes that never safely reached disk.

** Observation still does whole-corpus work and can wait indefinitely for quiet

[[file:../../server/maintenance/observation.rs::622][run_observation]] deduplicates its path list but calls observe_complete_disk
for ordinary notifications. The explicit targeted reload path does less work;
the general watcher path does not yet realize the planned incremental queue.

The [[file:../../server/maintenance/observation.rs::247][worker's debounce loop]] repeatedly waits for another signal with a fresh
175 ms timeout, with no maximum batch age. A stream of notifications spaced
less than 175 ms apart can postpone processing, including maintenance jobs
already in the batch. This is a source-derived starvation case, not a newly
measured occurrence. The work is off the socket thread, which is an important
improvement, but it is not the bounded/cooperatively cancellable observer
described in [[file:07_plan.org::389][the plan]].

* Why passing tests did not end the whack-a-mole

The [[file:09_happy-path-integ-test.org][two-person sharing scenario]] is valuable. It exercises actual Git pulls,
forking, reciprocal subscriptions, view survival, warnings, and elapsed unlock
time. It caught a real generated-report problem and a real disagreement
between save defaults and disclosure warnings. The latter was a semantic
specification problem, not a race.

But the test makes most operations happen in a safe serial order:

- [[file:../../tests/integration/partial-reload-happy-path/run-test.sh::99][The runner]] waits for Server ready before launching the editor.
- [[file:../../tests/integration/partial-reload-happy-path/test-emacs.el::228][Initialization]] completes verification before commands run.
- [[file:../../tests/integration/partial-reload-happy-path/test-emacs.el::188][Each pull helper]] waits for both unlock and complete incident termination
  before issuing the next view command.
- Each person/phase uses a fresh editor/server lifetime; it does not preserve
  a long-lived editor through an interrupted server operation.
- It exercises pull, not the explicit targeted-reload selector.

These are sensible choices for a readable behavioral test. They also exclude
the interleavings behind several later bugs. The existing
[[file:../../tests/integration/maintenance-rebuild/test-emacs.el::116][rebuild test]] does cover a view born during blocked maintenance and eventual
retry/unlock. It does not establish crash recovery at the journal boundaries.

The [[file:07_plan.org::1519][plan required]] systematic disconnect/restart tests at those boundaries.
The checked-in integration coverage I found does not provide that matrix.
Recent reconnect repairs have focused client unit tests and recorded manual
live checks, which are useful but narrower evidence.

There is also a counterproductive acceptance rule in
[[file:../../bash/all-tests.sh::223][all-tests.sh]]: failed integration tests are retried, and a successful retry
can produce [[file:../../bash/all-tests.sh::299][an overall pass]]. Logs retain the first failure, but for concurrency
acceptance that failure is itself evidence. A retry should help diagnose
instability, rather than erase it from the success criterion.

The lesson is not to add thousands more assertions around individual message
handlers. Test the real ownership boundaries: delay a worker result, lose an
ACK, restart after durable publication, issue a command before census
completion, or create a buffer immediately before finalization. A small
deterministic schedule can reveal what many ordinary successful runs cannot.

* Proposals and their tradeoffs

These alternatives concern two partly independent decisions: how much editor
activity maintenance permits, and how many stores live queries depend on.
Changing a database alone does not eliminate the editor lifecycle protocol.

| Alternative                                                    | Main benefit                                       | Main cost                                                 | My assessment                                    |
|----------------------------------------------------------------+----------------------------------------------------+-----------------------------------------------------------+--------------------------------------------------|
| One owner, finite maintenance barrier, keep current stores     | Fewer lifecycle interleavings; smaller disruption  | Defer new editable views                                  | Best conservative option                         |
| One owner, immutable Rust graph plus pinned Tantivy searcher   | Remove a live database and cross-store read gate   | Audit/replace remaining TypeDB and global/live-disk reads | Preferred architectural direction                |
| SQLite graph projection and FTS in one database                | Built-in atomicity for graph and search projection | Query/search migration and filesystem boundary remain     | Credible alternative, needs comparative evidence |
| Private versioned canonical store; worktrees are import/export | Stronger durable commit boundary                   | Changes everyday plaintext/Git semantics                  | Consider only if that product change is wanted   |

** One owner and a finite maintenance barrier, keeping existing stores

Use a single state owner for saves, maintenance decisions, journal publication,
and acknowledgment acceptance. Keep the pure candidate builder and existing
store update machinery. Background work returns immutable results tagged with
the base that authorized it.

Close admission to new authoritative views before the initial locked census.
Drain already admitted requests, secure the required dirty-work archive before
Git or destructive work, and settle that fixed inventory. Later requests to
create editable views wait until the barrier ends. Existing text stays readable.
During long Git/observation work, queries could still return temporary read-only
snapshot results that carry no live save authority and need no maintenance
settlement; obtaining an editable view would require reopening after the barrier.
Those are buffers in the same sole editor, not secondary client connections.
This is a deliberate change in query-result behavior. The even simpler variant
queues every graph command during maintenance, but slow Git authentication
makes that restriction unpleasant.

This deliberately relaxes the current promise that new authoritative views
may be created throughout maintenance. It avoids
the moving enrollment target that caused the late two-census design.
It can retain dirty orthogonal views and native undo protection.

Advantages: substantial existing code remains useful; the serial state owner
has one journal writer; reasoning and fault injection become simpler; TypeDB
semantics and Tantivy search behavior stay intact.

Costs: editable-view creation waits, and the barrier must have a clear
failure/authorization UI. Git, archive work, or database work can lengthen it;
only small local reloads should be expected to make that pause brief.
The existing three-store recovery obligations remain. Preserving every exact
current promise would reduce this option's simplification considerably.

** One selected Rust graph and a pinned Tantivy searcher

Here the published read unit would conceptually be:

#+begin_example
Selected snapshot
  graph + exact manifest + config/source identity + query context
  a specific Tantivy Searcher built for that same graph

one writer: candidate -> validated graph/index pair -> publish snapshot
readers: hold that snapshot until their query is finished
editor: local drafts and view bases, with explicit safe refresh/retirement
#+end_example

Tantivy already provides immutable search snapshots. Its
[[https://github.com/quickwit-oss/tantivy/blob/main/ARCHITECTURE.md][architecture documentation]] explains that a held Searcher keeps a consistent
segment snapshot across subsequent commits and merges. That supports this
proposal; publishing the correct graph/searcher pair is still Skg's job.
A cloned IndexReader that later supplies a new Searcher is not equivalent.

The writer builds the next graph and index state, obtains its corresponding
searcher, and publishes the pair only when both are ready. Existing queries
retain the previous pair. Index failure leaves that previous pair selected
and blocks any operation requiring the unfinished change; reconstruction is
from a named immutable graph. A full index replacement must retain resources
needed by old readers until they finish.

TypeDB could be removed from live query/write correctness, or retained only
as an explicitly optional export/audit tool if it has a separate useful role.
All ordinary graph reads must use the supplied snapshot, including a lookup
that finds nothing. No fallback may turn that absence into a read of newer
disk or process-global graph state.

Advantages: much of the graph machinery exists already; no separate TypeDB
service is required for ordinary use; old queries can finish without waiting
for an in-place database transition; one published graph/search pair replaces
several coordination obligations. No new language or graph-query engine is
needed.

Costs: remaining TypeDB uses need a real dependency audit and behavioral
comparison. The existing global-handle shortcuts must be removed from pinned
paths. Long-lived snapshots retain memory/index resources, so request
lifetimes must stay bounded. Search must wait for the correct index before a
new pair becomes visible; that cost should be measured, not hidden by stale
results. Crash recovery and ordinary filesystem-save durability still need
an explicit durable boundary.

I favor combining this direction with the finite maintenance barrier above.
The two changes solve different sources of complexity. Neither requires
automatically rerunning searches or discarding dirty editor text.

*** DONE (jeff) for searches requested mid-maintenance
we can just ask the user, 'use the current (stale) index or wait for the updated one'?

Response: yes. That is a good user-facing policy, provided the choice is explicit
in the result and does not silently create editable authority from stale data.
"Use current index" can return a coherent, read-only result from the last
published graph/search snapshot, visibly marked as possibly stale. "Wait" can
remain pending until the next validated graph/search pair is published. The
wait should be cancellable, and neither choice should automatically rerun or
silently replace an existing search result. If the user later requests an
editable view, that request still follows the maintenance barrier and the
view-base checks.

** SQLite as one transactional graph-and-search projection

Store nodes, relationships, source provenance, ordering, and FTS in a single
SQLite database, and apply one candidate in one transaction. Normal readers
use one database snapshot. SQLite's
[[https://www.sqlite.org/isolation.html][isolation documentation]] describes serialized writes and snapshot reads in
WAL mode. Those are a good fit for a single-user application with background
read work.

This could replace TypeDB and Tantivy together, rather than add a fourth
authoritative representation. An in-memory graph, if retained, must be a
versioned derivative of the same committed state, not a separately advancing
authority. SQLite on the container's local filesystem can be exposed through
the existing server; the editor need not share a database file.

Advantages: database commit/crash mechanics and graph/search atomicity move
into a mature storage engine; fewer services and custom cache-recovery paths;
relational constraints and queries may make some invariants easier to express.

Costs: this is a larger rewrite than using the graph already present.
Skg depends on ordered relations, telescope provenance, aliases, dangling
references, override traversal, custom ranking, and per-token regex/operator
search. An ordinary SQL schema with indiscriminate foreign keys or a default
FTS query is not behaviorally equivalent. [[https://www.sqlite.org/fts5.html][FTS5]] supplies full-text indexing,
but its external-content mode still requires keeping the content table and
index synchronized; both should be updated in the same transaction.

Crucially, a SQLite transaction does not include Git, arbitrary .skg file
writes, or editor undo. If .skg remains canonical, SQLite is a transactional
projection of a selected disk snapshot and the external-write boundary stays.
If SQLite becomes canonical, .skg becomes an import/export working copy.
Those are different product decisions, not interchangeable implementation
details. I would not choose this migration without a small comparative
demonstration of the actual graph and search semantics.

** A private versioned canonical store, with Git worktrees as exchange surfaces

Persist immutable node/file versions and publish one durable root describing
the selected generation. Git operations modify a working copy; validated
imports become new selected versions. Old versions remain available for
recovery, with checkpoints or shared content-addressed objects instead of a
complete independent baseline per incident.

Advantages: selecting a generation has a clear durable commit point; recovery
need not infer authority from mutable worktree contents; unchanged data can
be shared; external imports cannot partially become live graph state.

Costs: the worktree is no longer the sole live authority. Out-of-band edits
need an explicit import/conflict policy, and exports need failure recovery.
Retention, private data, garbage collection, and multi-repository publication
remain real work. Hidden commits in public source repositories would also
create an undesirable coupling between recovery and publication; a private
state store would need a clear separation.

This may be a good architecture for a different desired workflow. It is not
a cheap way to preserve every existing plaintext/Git expectation.


* What to keep, and what could go

I would preserve these behavioral requirements and their tests:

- load/fold/unfold semantics, privacy/source ownership, ID and override rules;
- additions, deletions, alias redirection, and byte-only semantic no-ops;
- partial selection agreeing with a full reference fold of the selected
  baseline plus the targeted replacement bytes;
- no external mutation before required authored-work preservation;
- dirty text/undo surviving interruption and recovery;
- no stale response overwriting newly authored text;
- each query reading one coherent generation;
- no automatic rerun of search membership/ranking;
- the real two-person fork/pull/reciprocal-subscription scenario;
- bounded latency on a representative corpus, separately from tiny fixtures.

Pure parsers, validators, source normalization, semantic deltas, conservative
impact helpers, archive/undo adapters, and useful Git evidence code can survive
a coordinator replacement.

Tests prescribing the current number of ACKs, intermediate phase labels,
provisional enrollment protocol, or multi-store rollback sequence should not
dictate a replacement architecture. Preserve the property they protect; adapt
or replace the mechanism-specific test. Tests that use TypeDB merely because
the global graph was never initialized should not force TypeDB to remain a
production dependency.

If the smaller contract is accepted, likely deletion candidates include
continuously growing maintenance enrollment, duplicated orchestration in
clients and handlers, separate authoritative persistence paths, TypeDB cache
coordination, and reconstruction plumbing made unnecessary by a single read
authority. This is a conditional opportunity, not an audited deletion list.

I would resist throwing away the tests or specs wholesale. I would equally
resist treating the current specs as immutable: they contain precisely the
expensive promises under review, and some sections contradict one another.
For example, [[file:../../api-and-formats.md::792][the old fatal-reload section]] says legal subsets are selected when some
input is invalid, whereas [[file:07_plan.org::527][the later contract]] rejects the candidate as a whole.
The API's shell pull description also survives even though
[[file:../../data/bash/pull-all.sh][the script]] now refuses to pull. Retention needs a deliberate behavioral
baseline, not indiscriminate preservation of every written sentence.

* CAP, STM, relational algebra, and formal methods

** CAP is useful background, but not the missing prerequisite

[[https://www.cs.princeton.edu/courses/archive/spr22/cos418/papers/cap.pdf][Gilbert and Lynch's CAP result]] concerns the inability to guarantee both
atomic consistency and availability under network partitions in its model.
It is not a rule that three local stores force you to sacrifice one of three
desirable properties, nor does its availability definition mean a four-second
UI latency target.

Skg already permits peers' Git clones to lag. A local server and its editor
can disconnect, but you do not need both to independently accept conflicting
authoritative graph writes. Preserving a local draft is different from
committing that draft while the server is unreachable.

The more useful concepts for this decision are: one writer; immutable read
snapshots; atomic publication; crash durability; idempotent replay; and the
difference between observing an effect and proving it never happened. Learn
CAP if it interests you, but I would not delay this decision to study it.

** STM addresses shared memory, not this entire transaction

STM could make a set of in-process memory changes composable. The classic
[[https://cs.brown.edu/people/mph/HarrisMPJH05/stm.pdf][Composable Memory Transactions]] paper explicitly separates that problem
from storage/database interaction and explains why retryable transactions
cannot freely perform irrevocable I/O.

A retried memory transaction cannot undo a Git pull, retract text already
displayed by an editor, or restore a file whose write was interrupted. You
would still need the durable effect protocol. With one intended graph writer,
exclusive ownership is a simpler starting point than introducing transactional
memory to manage competing writers you do not need.

** Relational algebra helps graph semantics, not acknowledgment timing

A relation-and-delta formulation can clarify what changes when an edge is
added, removed, hidden, or redirected. It can support a slow reference model
for checking the optimized in-Rust graph. That is useful regardless of the
storage engine.

It does not decide who owns a buffer after disconnect, whether an ACK was
durably recorded, or whether Git is still changing a file. Moreover, Skg's
ordered members and source-sensitive folds require more than unordered set
algebra. The current displayed-ID impact rule is a conservative product

implementation tests; it is not a proof that the filesystem or protocol
adapter implements the model correctly.

This can happen on an ordinary I/O error as well as a crash. Returning an
error does not undo writes which have already succeeded.

***** Even a single file needs a deliberate replacement strategy

The current =std::fs::write= call writes to the destination itself; it does
not first prepare a complete replacement file and atomically rename it into
place. An interrupted write can therefore leave a truncated destination.
Writing a temporary file and renaming it would address that individual-file
replacement problem, but a sequence of such renames would still not make a
multi-file save atomic. Surviving power loss also requires explicit durable
write ordering, beyond atomic visibility of a rename.

***** What the graph/search publication guarantee actually covers

Publishing one immutable graph/search pair keeps Skg readers from seeing half
of that pair. It does not combine all the source-file writes into the same
atomic operation. Likewise, serializing Skg's writers prevents them from
running over one another; it does not roll back a failed filesystem save.

***** What the recommended journal would add

Before changing source files, persist the intended batch and the data needed
to recover it. Record completion only after the required writes are durable.
After an interruption, Skg can identify which operation was in progress and
finish or reconcile it under the defined recovery policy, rather than treating
the mixed files as a completed save. If another writer has changed them in
the meantime, recovery must report that conflict instead of overwriting it
blindly.

That is why I recommend including recoverable ordinary saves here. It is a
missing guarantee in the current implementation, not something the proposed
TypeDB removal would newly break. Your question leaves the scope choice open;
I have not treated it as accepting either alternative.

**** Codex: prevent Skg saves from writing while coordinated Git work runs

"Exclude Skg saves" means temporarily disallow executing a Skg save while a
Git or other file-changing operation coordinated by Skg is running against
its sources. For example, while a Skg-initiated pull is changing the worktree,
a view save cannot also write those =.skg= files. The coordinator keeps that
restriction until observation and graph/search publication have completed;
then each safe buffer can resume under the accepted rule above.

The restriction applies to writes. The last coherent graph can remain
available for read-only queries, and buffer editability follows the separate
maintenance rules. Whether a save command during that interval is refused or
queued is the UI question above; either way, it cannot write during the
excluded interval.

Skg can enforce this ordering for operations it coordinates. An unrelated
shell command or editor can still write the files without consulting Skg.
The recommendation therefore also states a limitation: exact checks can catch
an outside change already present when checked, but cannot guarantee against
an outside write that races with the subsequent replacement. The alternative
asks external writers to participate in a common locking protocol.

*** Alternative: require every supported writer to participate in exclusion

Provide an explicit external-edit bracket or shared locking protocol and
require shell/editor integrations to honor it. The guarantee applies to those
cooperative writers; arbitrary programs remain outside it. This adds workflow
requirements even with one user.
