* Single-node reload performance investigation

** Result

The roughly 40-second pause was not the one-node reload, TypeDB, Tantivy, view
classification, or the ordinary filesystem observer.  It was the server's
pre-mutation recovery-evidence publication.  Every version-2 maintenance
incident serialized the complete 29,973-node graph twice, as =g0_nodes= and
=g1_nodes= inside a human-readable YAML envelope, even when one title changed.
The publisher then parsed and serialized that 53 MiB envelope repeatedly to
prove its checksums.

There was no small, semantics-neutral deletion which would make this properly
fast.  The accepted representation change is implemented and validated below.

I stopped the live development server while benchmarking.  Its active incident
=00dd1e20-3eec-42f9-8ba6-46a1ce58ab48= had already published =ARCHIVE-READY=,
so the stop itself did not discard recovery evidence.  Once the user confirmed
that these were disposable experiments and no legacy reader was wanted, the
two version-2 client archives and the exact old process-state directory were
removed before starting the version-3 server.

** DONE Implementation and validation

The server now writes evidence format version 3 as two machine-level files:

- a small =header.yaml= containing incident/config/generation identities,
  checksums, classifications, warnings and the human-artifact inventory; and
- a zstd-level-3 compressed CBOR =recovery.cbor.zst= containing one complete
  canonical G0 semantic-node/path baseline plus reversible before/after
  node/path deltas.

Applying the checked deltas reconstructs complete G1 node and path maps.  The
reader rejects duplicate deltas, false =before= values, mismatched primary IDs,
inconsistent classifications, trailing CBOR bytes, decompression length
mismatches, checksum changes, unsafe paths and undeclared files.  There is no
version-2 reader.

Publication serializes and compresses the recovery value once, durably writes
each file, rereads each exact byte sequence once, and atomically renames the
completed directory.  It no longer parses and reserializes a corpus-sized YAML
document before selection.  The process caches the validated small header and
artifact inventory.  Client-archive transfer rechecks the small header, the
compressed recovery checksum and each transferred artifact, but does not
decompress or deserialize the recovery corpus.

** Why the bundle is so large and slow

=MaintenanceEvidenceBundle= currently contains all of these at once:

- the complete =G0= path manifest;
- the complete =G1= path manifest;
- every semantic node in =G0=;
- every semantic node in =G1=;
- the transition delta;
- before/after semantic evidence for every changed node; and
- separately written human-facing changed-node artifacts.

For a title-only partial reload, nearly all of the first four collections are
duplicate unchanged data.  YAML magnifies their size.  The normal publisher
serializes the payload to hash it, serializes the containing envelope, writes
and fsyncs it, parses and reserializes the temporary publication to validate
it, renames it, then parses and reserializes the final publication again.  The
later client-evidence request repeats the last full load.  These operations
explain both the 40-second pre-selection delay and the 13-second finalization
delay.

The full snapshots were added to meet the plan's stronger rule: before the
first store mutation, durable evidence should be sufficient to reconstruct a
complete =G0= or =G1= after a crash.  Although the current restart path does
not yet consume =g0_nodes= or =g1_nodes= for reconstruction, simply removing
them would weaken that intended guarantee rather than merely optimize code.

** DONE Choice 1: keep self-contained G0/G1 recovery? (accepted: yes)

*** Option A -- Keep the strong recovery guarantee (recommended)

Make each incident independently sufficient to reconstruct either complete
generation even if the worktree changes again and the derived stores are found
partly updated after a crash.  This preserves the plan's intended failure
semantics.

*** Option B -- Retain only changed-node/path evidence

The incident would contain before/after records for the changed telescopes and
would rely on the worktree, Git, or still-healthy stores for all unchanged
nodes.  A one-title incident would be tiny and very fast, but the archive would
no longer be a self-contained source for complete store reconstruction.  I do
not recommend accepting that loss merely to obtain acceptable latency: the
recommended representation should eliminate the 40-second delay while keeping
the stronger recovery guarantee.

** DONE Choice 2: representation if the strong guarantee stays

*** Option A -- Version 3: one compact baseline plus reversible delta (recommended)

Replace the monolithic =bundle.yaml= with:

- a small, inspectable header containing identities, generations, checksums,
  change classifications and artifact inventory;
- one versioned, compressed binary recovery payload containing a complete
  canonical =G0= baseline; and
- a reversible before/after node and path delta from which =G1= is derived.

This preserves both complete generations without storing every unchanged node
twice.  Human-readable per-changed-node README, semantic YAML, diff, source
outcome and raw-byte artifacts remain unchanged.  Only the large machine
recovery payload stops pretending to be a document for people to read.

Publication should serialize the recovery DTO once, hash the exact stored
bytes, write/fsync them once, reread their bytes once to verify the checksum,
and rename the completed directory.  The normal in-process path should retain
the already-validated small header and client artifact inventory, so serving
the final client archive does not parse the recovery payload.  A restarted
server parses it only when recovery actually needs it.

All current incidents are disposable development data, so version 3 can replace
version 2 outright.  A format/size regression should assert that a one-node
transition does not write two corpus-sized node collections, and a recovery
round-trip should derive byte-identical semantic =G0= and =G1= maps.

This is my recommendation.  It attacks the scaling error, preserves the
recovery promise, keeps the human evidence human-readable, replaces the
40-second publication path, and removes the later 13-second full parse from the
ordinary client-transfer path.

**** How this addresses the 40-second phase

The current 39.476-second publication is approximately three corpus-sized YAML
validation cycles, each comparable to the independently measured 13.417-second
load.  Version 3 removes all three from the pre-mutation path.  I prototyped its
large recovery payload against the same 29,973-node real corpus:

| version-3 prototype stage                  | measured wall time | bytes     |
|--------------------------------------------+--------------------+-----------|
| construct one complete canonical G0 DTO    | 79.8 ms            |           |
| serialize it as binary                     | 81.0 ms            | 12,669,612 |
| compress it with zstd level 3              | 197.4 ms           | 5,163,761 |
| durable write and exact checksum reread    | 145.4 ms           | 5,163,761 |
| total pre-mutation recovery-payload work   | 503.6 ms           |           |
| decompress and deserialize during recovery | 191.1 ms           |           |

The diagnostic prototype and temporary dependency were removed after the
measurement.  It was run in the same unoptimized development profile as the
40-second benchmark.  It used =bincode= only to measure the representation's
cost; that experiment does not by itself choose the permanent wire/storage
encoding, which should have an explicit stable version contract.  A real
implementation adds a small header, one-node delta and human artifacts, but
none scales like another complete graph.

Combined with the measured 0.662-second candidate construction and sub-0.2-
second store/view transition, the corresponding title-change path should be
around 1.5 seconds rather than 40 seconds.  The implementation should enforce
a generous real-corpus ceiling (for example, three seconds in the development
profile) so the representation is not accepted merely because it is faster
than the current pathological one.

***** Codex agrees

Agreed.  I had treated retained development evidence as if it were user data,
which would impose permanent reader complexity for no benefit.  Before testing
the new writer, remove the current test journal, server evidence and client
archives through their safe scoped cleanup paths.  Implement only the new
format; do not add a version-2 reader.

*** Option B -- Keep version-2 YAML, remove repeated validation passes

The publisher can reuse the envelope it just built, verify exact bytes instead
of immediately reparsing them twice, and cache the parsed client-artifact
inventory.  That should remove most of the repeated 13-second passes and is a
small change, but the first YAML serialization still scales with two complete
graphs and every incident still consumes roughly 53 MiB.  It is a reasonable
stopgap, not a satisfactory fix.

*** Option C -- Share content-addressed generation snapshots across incidents

Persist each complete generation snapshot once and let incidents reference a
checksummed baseline plus their reversible delta.  Repeated one-node reloads
would be extremely cheap after the first snapshot.  This is attractive if
retained incidents are common, but it adds reference counting, garbage
collection, cross-incident ownership and deletion-policy questions.  I would
consider it a later storage optimization after the self-contained version-3
format works.

This is the main alternative if even the measured half-second evidence
publication is too expensive.  A complete snapshot could be prepared after
startup or after the preceding generation is selected, outside the next
interactive reload.  The incident would then durably reference that immutable
snapshot and write only its small reversible delta.  It preserves the strong
recovery guarantee and moves nearly all corpus-sized work off the interactive
path, at the cost of the lifecycle complexity above.

** DONE Choice 3: should the observer queue be changed in this repair?

Recommendation: no.  The plan still promises chunked cancellation and path
coalescing which the current observer does not fully implement, and that debt
should remain visible.  It is not the cause of this incident: on the real
corpus a complete equality observation took 1.230 seconds and the exact
one-target candidate took 0.662 seconds.  Combining queue surgery with the
evidence-format migration would enlarge the proof surface without addressing
the measured 40-second stage.

** DONE Proposed scope after the choices are settled

If the recommendations above are accepted, the implementation should:

1. define a portable version-3 header, compressed recovery DTO and reversible
   node/path delta;
2. prove reconstruction of complete =G0= and =G1= from that representation;
3. publish and checksum each byte sequence once, with exact durable rereads;
4. retain the small transfer inventory in memory and avoid loading the recovery
   payload during ordinary evidence transfer;
5. remove the disposable version-2 development incidents and implement no
   legacy reader;
6. add focused corruption, crash-boundary, replay, size-scaling and real-corpus
   latency tests; and
7. repeat the real one-title workflow and record stage timings and retained
   bytes here before calling the repair complete.
