* partial rebuild : happy path integration test
Suppose there are two users named China-Scholar and Economist.
China-Scholar startrs with a node called China that contains the node Chinese Economics.
Economist starts with a node called Economics.
(Both users only have public data.)
Each has a separate config, appropriate to their data, that includes the other's data.

First, Economist is using the server (one client at a time).
Economist forks Chinese Economics, changes the title to Economics of China,
makes it the first content node of Economics,
and pushes those changes to the remote (both remotes are on disk,
in a subfolder of the folder that hosts this integration test).

Economist disconnects.
China-Scholar connects, opens their China node,
and pulls new changes into their graph.
The test measures how long before the China buffer is unlocked.
The test notes a failure (but continues to execute and collect any more failures)
if it takes longer than 4 seconds.

CS visits their version of Chinese Economics.
In the resulting view, CS should see that it now has a subscriber.
CS subscribes back.

CS disconnects. E connects, opens their Economics node,
and pulls new changes.
Again measure the time to unfreeze, and fail if more than 4 seconds.
(Also log it, whatever it is,
because I hope even 4 seconds is much slower than necessary.)

E visits their Economics of China node in a new buffer.
The buffer should reveal that it now has a subscriber.

If anything returns warnings, those should be collected as failures too.

* Implementation

The integration test lives in
=tests/integration/partial-reload-happy-path/=.  It constructs two bare Git
remotes below a temporary =work-*= subdirectory of the test directory and four
clones: each user's owned clone and their stale clone of the other user's
remote.  The two configs use separate data roots, ownership boundaries,
Tantivy indexes and TypeDB database names.  Three separate server/Emacs
lifetimes drive the Economist, China-Scholar, and Economist-again phases, so
the disconnects and stale pulls are real rather than simulated in memory.

The Emacs driver performs the fork, chooses =economist-public= for the clone,
adds it as Economics's first (and only) content node, commits and pushes;
opens China before pulling; visits the original Chinese Economics with
override substitution bypassed; verifies and reciprocates the subscription;
commits and pushes; then opens Economics before the final pull and verifies the
new inbound subscription in a fresh view of Economics of China.

Failures are appended to one file shared by the three Emacs processes.  A
failure does not make a phase stop unless the missing prerequisite makes the
rest of that phase impossible, and a failed phase does not prevent the later
server/client phases from running.  The driver captures response warning
lists, =display-warning= calls, structured startup telescope warnings, and
non-signaling =SKG request failed:= messages.  The runner also treats every
Rust =WARN= log record as a failure.  It prints all collected failures only
after the final phase.

** What “pull to unlock” means in the test

The monotonic-ish Emacs =float-time= clock starts immediately before
=skg-pull-all=.  The test requires that the already-open target buffer is
observed with its maintenance overlay, records the first instant after that
overlay disappears, and then continues waiting for the maintenance incident
to terminate before proceeding.  Thus it measures the user's whole wait from
invoking pull until that buffer becomes editable, not merely the server's
partial-reload computation.  Both pulls have the corrected four-second limit,
and both exact durations are always written to =timings.log= and printed.

* Critical details not fixed by the scenario

** ONGOING Reciprocal cross-source edges cannot all follow one strict privacy order

This is the important specification tension.  Forking creates edges from the
Economist clone to China-Scholar's original, and “subscribes back” creates an
edge in the opposite direction.  With two distinct sources in a strict linear
privacy order, one of those directions necessarily records an edge in the
earlier source that names a node homed in the later source.  Reversing the
source order only changes which direction gets the leak-shaped-member warning.

The test therefore follows the document literally: it creates the reciprocal
edge and fails on the resulting warning.  Making this a genuinely warning-free
happy path requires a later product choice: exempt this deliberately shared
public/public shape, represent equally public sources, change the collaboration
gesture or data layout, or declare this particular warning expected.  The test
does not silently choose among those architectural options.

** DONE “First” currently means “only”

Economics starts without content, so the clone's position is asserted to be
the first content position but there is no second member against which to
prove ordering.  Add a pre-existing Economics child if relative ordering is a
behavior this scenario is intended to protect.

* Jeff thinks
For any relationship from P to R, even if P is more public than R,
if P is owned and R is not owned, then the relationship should default
to being at P's publicity level. The user can make it more private if they want.

This applies not just to subscriptions but to any relationship,
even containment.

* Codex thinks: yes; make the disclosure rule belong to P

I agree with the rule for a direct relationship asserted by P.  If I publish P
and choose to make it contain, subscribe to, override, or link to R, then I
have chosen to publish the fact that P names R.  R being less public does not
make that assertion accidental.  Defaulting the relationship to P's home is
the least surprising behavior; moving it to one of P's more-private owned
sources should remain available as an explicit choice.

This is, importantly, already the save default for the three independently
stored, writable node relations: =contains=, =subscribes_to=, and
=overrides_view_of=.  =SkgConfig::relationship_default_source= returns P's
home when P is owned and R is foreign, and =apply_sticky_sources= uses it for
all three.  The test's reciprocal subscription was therefore written exactly
where the save rule intended it to go.

The contradiction is in the telescope warning invariant.  It currently asks
only whether the relationship's source precedes R's home.  It does not ask
whether that source is the intentional default for an owned P pointing to a
foreign R.  Thus a legal save creates a shape which the warning code
immediately calls leak-shaped.  I think that is plainly the wrong result.

** The rule must continue to make sense on the receiver's machine

There is a wrinkle beyond merely calling
=relationship_default_source(P-home, R-home)= from the warning validator.
Ownership is local to a config.  On China-Scholar's machine, Chinese Economics
is owned and Economics of China is foreign.  On Economist's machine those
facts reverse.  If Economist recomputes China-Scholar's original default using
Economist's local ownership, the warning reappears even though
China-Scholar's save was legal.

I recommend this division of responsibility:

- At save time, continue using the writer's ownership knowledge.  A new
  owned-P to foreign-R edge defaults to P's home.  A relationship between two
  owned nodes can retain the stricter current rule, because that writer can
  place the relationship at the more-private endpoint's level.

- At load or pull time, do not call a relationship leak-shaped merely because
  its member is homed later than its owner.  A foreign repository can contain
  the result of a perfectly legal save made by that repository's owner, and a
  receiver cannot reconstruct the writer's ownership facts from the current
  config.  An edge recorded at P's home (or a more-private section of P's
  telescope) is a disclosure by P's publisher and should be accepted as such.

This gives the rule a stable meaning after sharing: the writer chooses how
public P's assertion is; receivers do not reinterpret that choice according
to who happens to own R locally.  The cost is that the loader can no longer
diagnose every hand-authored “public P names private R” as suspicious.  I
think that cost follows necessarily from the desired rule: on disk, an
intentional public reference and the supposedly suspicious reference are the
same fact.  Save-time validation can still prevent unintended owned-to-owned
disclosures where the server actually knows both ownership facts.

Under that interpretation, the reciprocal-subscription warning in this test
should disappear, and the warning assertion should stay strict rather than
special-casing the test.

** One relationship deserves an explicit footnote: hides

=textlinks_to= already lives in P's title/body and has no independently
selectable relationship source, so it naturally follows P's publicity.

=hides_from_its_subscriptions= is different.  Its present source floor also
depends on the subscription which explains the hide.  Otherwise a public hide
could reveal that a deliberately private subscription exists.  My preference
is to retain that explaining-subscription floor: it is derived privacy, not
the ordinary “P openly names R” case.  Everything you specifically named --
including containment -- follows your rule, while a hide does not become more
public than the subscription that gives it meaning.

If “any relationship” is meant literally to include hides despite that
inference, that is the remaining substantive choice.  I would recommend the
exception above unless you want an explicit public hide to count as permission
to reveal its supporting subscription too.
