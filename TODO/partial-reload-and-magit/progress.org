what's done and went well; changes to the plan's envisioned order;

* Component 4 (recovery) -- NOT STARTED; assessed, no stumper
The three-=oops-N_*=-branch recovery (plan Component 4) is the remaining
work. The one flagged risk -- rendering a telescope from an in-memory
graph snapshot to its on-disk BYTES without writing to disk -- is
FACTORABLE, not a stumper: =write_nodecomplete_telescope= (=one_node.rs=)
already does =unfold_node= -> =nodefs_from_section= -> =node_fs.to_yaml()=
-> path; factoring that into a =Vec<(path, yaml)>= producer (leaving the
=fs::write= to the caller) gives exactly the bytes git2 blob-building
needs. Everything else is new but understood: git2 0.18 plumbing
(blob/treebuilder/commit/reference, no checkout), =repo.state()= /
=head_detached()= precondition guards (added fresh), a per-connection
=PendingIncident= (=g_pre=, =g_post=, touched set, base commits), and a
second "reload recover" request offered/confirmed like the fork flow.
No git-writing code exists in the server yet, so this is all additive.

* changes to the plan's envisioned order
- Within Component 1, the plan's batch "scoped duplicate-ID check" (plan
  1.4 step 6) is NOT implemented; only the override-invariant batch guard
  is. Duplicate-IDs remain caught by a full rebuild, not by a scoped
  reload. Tracked under "imperfect" below.
- Built in the order Components 1 -> 2 -> 3 (server core, mutex, Emacs)
  as planned; Component 4 (recovery) is the remaining phase.

* what's imperfect about what's done
- Override-invariant rejection is coarse: a violation rejects the WHOLE
  reload batch (all touched telescopes keep last-good), not just the
  offending one. Safe, but blunt. (Planned as acceptable.)
- Scoped duplicate-ID detection on reload is not implemented yet (see
  above). A reload that introduces a cross-source duplicate ID would be
  applied; a subsequent full rebuild would catch it.
- Collateral re-render has no dedicated open-view integration test: the
  parity tests register no views, so the re-render path early-returns in
  them. It reuses the heavily-tested save collateral path, but a reload
  test that registers a view and asserts a streamed CollateralView is
  still owed.
- Component 3 (elisp) is byte-compiled but not runtime-verified (no live
  Emacs/magit/server here). The change-detection scans all =.skg= files
  on each magit refresh via mtime (cheap); if a large tree lags, upgrade
  to hashing only mtime-changed files.

* choices determining the future
- Reload's store commit reuses =apply_define_nodes_to_stores= directly
  (never =update_graph_minus_nodeMerges=). This is the mechanism that
  keeps reload from writing any =.skg= file. Any future change to the
  save pipeline must preserve that this function, with write_fs=false,
  performs no filesystem writes.
- =reload_touched_telescopes= is async and pub, so tests can =.await= it
  and the handler =block_on=s it. The recovery work (Component 4) will
  add a =pending_incident= parameter here and to the dispatch arm.
- The write mutex is a tokio async mutex acquired under
  =block_on=-per-connection-thread. If the server ever moves to a shared
  multithreaded async runtime, revisit that the guard is not held across
  a point that could deadlock the runtime.
