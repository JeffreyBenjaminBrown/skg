* Dead-link warnings miss targets deleted by the same save (2026-09-13)
  =dead_link_warnings= regards every ID present in the pre-save graph as
  live. Therefore, when one buffer both saves a text link and deletes that
  link's target, the final graph contains a dead link but no warning is
  emitted. Computing final ID existence must account for Save, Delete,
  fork, and nodeMerge outcomes together; merely subtracting Delete intents
  would mishandle IDs retained by a merge.

** The unreadable-files report names the SOURCE FOLDER, not the file
   This is the big one: it is the difference between a 30-second fix
   and a manual scan of 54,566 files.
   'read_skg_sections_from_folder'
   (server/dbs/filesystem/multiple_nodes.rs:203) calls
   'read_nodecomplete (&path) ?' and lets '?' propagate the serde error
   with the path DROPPED. The caller (same file, line 39-44) then
   records 'source . path . display ()' -- the folder -- into a tuple
   slot whose own comment (line 24) says "// filename". So the report
   reads:
     * /home/ubuntu/host/data/owned/personal-proc
     ** pers-p
     *** Error: missing field `pid`
   naming a directory of 2,937 files. Worse, the folder read aborts at
   the FIRST bad file, so "Found 1 unreadable file(s)" actually means
   "1 unreadable *folder*" -- with 2 bad files you still get 1, and
   fixing one just reveals the next on the following boot.
   Suggested fix: at line 203, '. map_err' the error to attach
   'path . display ()' before propagating; and either collect per-file
   errors instead of aborting the folder, or rename the count to say
   "source" so it stops lying.
** A titleless single-section node makes the whole server unbootable
   After the empty file got a valid 'pid', init failed again, further
   in, with "Telescope '...' has no home: no section carries a title."
   (multiple_nodes.rs:133). One contentless node -- no title, body,
   contains, or aliases, referenced only as the first child of
   'doing' -- blocks the entire database from loading, and this failure
   path writes NO report file at all (unlike the unreadable-file path),
   just a bare ERROR line. The two failure modes for the same broken
   file are reported inconsistently.
   Note this shape is reachable in normal use: a crash between "create
   node" and "write its title" leaves it behind, and a node whose only
   section is titleless is otherwise legal on disk (its titled siblings
   in owned/public are what make the pattern valid).
   Suggested fix: degrade "no home" from a boot-blocking error to a
   warning in telescope-warnings.org -- quarantine or synthesize a
   placeholder for that one telescope and load the other 54,565 files.
   Refusing to boot the whole graph over one empty node is
   disproportionate, and it is precisely when you can least afford to
   lose the tool (you cannot inspect or delete the offending node
   through the UI, because the UI will not start).

** skg--rel-at-point misclassifies some positions
   It classifies "activeNode child of an activeNode parent" as the
   parent-contains-child edge, without checking:
   - 'birth': a backpath graft (e.g. '(birth backpath container)')
     represents the INVERTED relation -- the child contains the
     parent -- so the command queries and offers to set a
     nonexistent parent->child contains edge;
   - 'parentIs': a parked (independent) child is not a member of the
     parent's collection, so the written '(relSource ...)' atom is
     inert (extraction only reads the atom off collected members);
   - the parent's definitiveness: under a write-protected parent the
     contains list is not collected, so the atom is inert there too.
   Inert atoms are harmless to the data but lie to the user: the
   command reports "Save to apply" and the save applies nothing.
   (The recursive walker added 2026-07-22,
   'skg--set-relSource-recursive-walk', checks parentIs and
   parent definitiveness; the single-edge command still does not.)
  Context: Jeff's machine overheated and cut power mid-'cargo build',
  truncating 3 of 501 rlibs in target/. Servers then refused to start,
  permanently and identically, on unchanged code and unchanged data.
  Fixed by 'cargo clean -p skg -p tantivy -p typedb-driver'. Written up
  in docs/troubleshooting/build-artifacts-corrupted-by-power-loss.org.

** The git_diff_view test matcher ignores bare metadata atoms
   'assert_buffer_contains' (tests/git_diff_view/common.rs) matches
   each expected line by star depth, title, and PARENTHESIZED
   metadata fragments only ('extract_metadata_fragments'). Bare
   atoms -- 'folded', 'focused', 'writeProtected', 'bodyFolded' -- are
   invisible to it, in both directions: an expected atom missing
   from the actual line, or a stray atom appearing in it, cannot
   fail these tests. Found 2026-07-08 while adding the
   begin-folded rule for hidden cols: a probe atom inserted into an
   expected line still passed. Regressions in fold/focus/writeProtected
   marking on diff views are therefore unpinned by that suite
   (tests elsewhere, e.g. tests/hidden_from_subscriptions.rs, use
   exact assert_eq! and do pin them). Suggested fix: also compare
   the bare-atom sets of the two lines in 'line_matches'.
** Subscribee-as-such hides may misfire under a restricted source-set
   The signal loop in 'resolve_visibility'
   (server/from_text/local_instruction_collection/resolve_visibility.rs)
   infers hides as: subscribee's disk contains, minus the children the
   buffer shows, minus the subscriber's post-save contains. Under a
   RESTRICTED source-set, rendering omits a subscribee's
   inactive-source members from the view, so they are absent from the
   signal's 'visible' list for a reason other than deletion -- yet the
   loop would infer hides for them, silently writing
   hides_from_its_subscriptions entries for members the user never
   saw. The new sibling pass 'infer_hides_from_contains_removals'
   guards exactly this with 'member_is_visible'; the older signal loop
   does not. Narrow trigger (needs a definitive subscribee-as-such
   saved under a restricted set, with the subscribee containing
   inactive-source members); not fixed in the fork-fixes arc because
   it is prior, separate behavior. Suggested fix: apply the same
   member_is_visible filter to that loop's 'inferred_hides'.

* Problems found during herald overhaul research
** (mostly fixed) Save validation and extraction use different edit-request surfaces
   The save extraction path uses 'collect_savenode_candidates' to define
   which view positions can produce save/merge instructions. Some
   validation still walks the whole viewforest directly, especially
   merge validation and contradictory instruction collection.

   That can make validation and execution disagree for edit metadata
   placed under display/scaffold positions: validation may see it even
   when extraction ignores it, or vice versa if the candidate policy
   changes. The cleaner fix is probably to validate write-intent
   metadata through the same candidate/role policy used by extraction,
   and explicitly reject edit requests outside that surface.

   Mostly fixed 2026-06-10 by local instruction collection: extraction
   now recurses into every position, so a definitive node's self-edits
   (including edit requests) are honored wherever validation can see
   them. The residual gap is positions where edit requests are
   deliberately ignored rather than rejected: a Delete or nodeMerge
   request on a subscribee-as-such is silently dropped, which validation
   could instead flag.
* Problems found during the staged/unstaged diff axis refactor
** (dormant) 'mk_removed_child_viewnode' hardcodes unstaged=Minus axes
   Dormant as of 2026-06-12: 'mk_removed_child_viewnode' now lives in
   server/to_org/expand/unused_but_nice.rs ("Held for someday, not
   currently wired in"), so the bug is unreachable in the current
   renderer. NOT closed: the per-stage-sign fix must land before that
   module is ever revived.

   When a parent .skg file is deleted, its children are loaded from
   git HEAD and rendered as phantoms. Both existence and membership
   axes are hardcoded as 'staged: None, unstaged: Some(Minus)',
   which misattributes already-staged parent-deletions to the

   side. Additionally, for a deleted-parent scenario the child's
   membership axis should probably mirror the parent's existence
   axis (if parent removed staged, children are 'removed from
   contains' staged too), which is a bit more nuanced than the pure
   contains_diff lookup used in phantom_axes.

   Found while writing docker-unification-strategies.org.

   'start_skg_with_restart' runs broad process kills:
   - 'pkill -f "cargo watch.*skg"'
   - cleanup runs 'pkill -f "cargo watch.*skg"' and
     'pkill -f "cargo run --bin skg"'

* Problems found during the org-export feature (2026-06-13)
** heading-anchor links rely on heading-text uniqueness
   Deep links use org's =[[./file.org::*Heading][label]]= search,
   which matches the FIRST headline with that text. When two
   DISTINCT nodes in one exported file have the same title, links to
   the second resolve to the first. The exporter emits one warning
   per such collision, but org has no per-node anchor available
   without property drawers (which we omit, since exported files
   must not require org-roam). Headings are rendered as the title's
   plain-label form (links collapsed to labels), so a heading's text
   always equals the anchor used to link to it -- the earlier
   heading-vs-anchor divergence is gone.
** a literal bracket in a title can break a deep link
   Anchors and labels are interpolated verbatim into
   =[[*anchor][label]]=. A title containing a literal =]= (e.g.
   "Notes [draft]") yields a malformed org link. The textlink regex
   keeps labels free of =][=, but a title is arbitrary user text.
   Rare; not escaped. Robust fix would require org link-syntax
   escaping of anchors/labels.

** PhantomUnknown is rendered but silently omitted from content saves
   Content reconciliation can render a raw unresolved 'contains' member
   as '(skg (unknown (id ...)))'. Save traversal then ignores the phantom
   and 'content_members()' collects only affected Active children. Thus
   an unchanged definitive save can remove the dangling membership even
   though the Unknown remains visibly present in the submitted buffer.

   The existing test
   tests/dangling_reference_renders_unknown_node.rs proves only that such
   a buffer saves without an error; it never reloads the parent to check
   whether the member survived. This needs an explicit round-trip
   contract and a test of the resulting relationship, not merely the
   response's error list.
** Outbound PartnerCols discard unresolved raw members
   The outbound accessors in
   server/dbs/in_rust_graph/relation_accessors.rs enumerate relationship
   members through 'filter_map(pid_of)'. A raw subscribe, override, or
   hide member therefore disappears before PartnerCol rendering whenever
   its target is unresolved. The initial renderer's nominal fallback
   produces empty Active child data rather than 'Phantom::Unknown', and
   the rerender path can instead fail because no member relSource exists.

   Consequently the UI has no coherent representation from which an
   owner could remove most non-content dangling relationships. These
   paths need raw-ID-aware enumeration and a true Unknown case if the
   deletion policy covers all four structured outbound fields.
