***** DONE jeff : when would a vanished node's occurrence become a tombstone?
****** DONE Claude says: nearly always, in a content view
A vanished node's occurrence becomes a tombstone whenever no
list its parent's goal reads still names any of the node's
IDs. After a deletion through skg that is the usual case: the
save's strip pass ('apply_delete_propagation_cleanup',
'server/save.rs') removes the node's pid and its extra IDs from
the four outbound lists of every owned node that referenced
it, so no owned list names it afterwards. The occurrence
becomes an unknown instead only when a list the deletion may
not rewrite still names it: a foreign skgrepo's list, which
delete propagation deliberately leaves alone, or data edited
outside skg. In the diff view the answer differs: until the
deletion is committed, HEAD has the node, so the occurrence is
a ghost; after the commit it is a tombstone there too. A
childless tombstone is pruned, so most vanished nodes simply
disappear from a content view.

*** DONE jeff : please elaborate on
"The parser no longer checks 'restoreRel' against '(rel removed)'; the save checks the position"
What was happening before, and what happens now?
**** DONE Claude says: one gate, moved from parser to save
A 'restoreRel' request, '(editRequest restoreRel)', asks the
next save to re-add a relationship that the worktree dropped
since HEAD: a node's membership in its container's list, or a
partner folder member's relationship to the folder's node. It
belongs only on a headline standing for such a removed
relationship, which the diff view marks '(diff (rel removed))'.
Before slice 5 that gate stood twice. The parser refused a
'restoreRel' on any headline not carrying '(rel removed)'
('check_where_the_edit_request_sits' at 96f0ff20, matching
the parsed change fact 'Existence::Removed'), and the save then
checked where the headline stood ('restoreRel_stands_where_it_
may', 'local.rs'), since a removed member and a folder member
are told apart by their parents. Slice 5 made the parser skip
'(diff ...)' wholesale, so it can no longer see '(rel removed)';
it now accepts a 'restoreRel' on any occurrence, refusing it
only on a ghost or a non-occurrence. The save's position check
stayed and became the only gate: the headline must be a
partner folder member, or a child claiming no membership (the
declared 'noClaim', or a parent that reads no claims) under an
occurrence outside the containerward chain. A request on a
claiming member, or on a root, is refused there now, with the
message the parser used to give. A request that passes but
names no relationship HEAD records is dropped with a warning
('restore_requests.rs'), as before. Both clients' commands
still require '(diff (rel removed))' at point before they
write the request, so a user reaches the save's refusal only
by editing the metadata by hand.

*** DONE jeff : define "pending detachment"
**** DONE Claude says: a noClaim child the graph still warrants
A pending detachment is a child under an editable parent that
the user marked 'noClaim' and that the truth still warrants:
the parent's list still holds it, and the next save will take
it out. 'docs/data-model_technical.org' names it ("a child the
user marked noClaim to detach it is warranted and claims
nothing (a pending detachment, herald 'detach')"), and both
clients compute it ('skg--pending-detachment-p' in

'nvim/lua/skg/readiness.lua'): the headline carries 'noClaim',
its '(view ...)' has neither 'noWarrant' nor 'ghostWarrant', its
'(diff ...)' has no '(rel removed)', and its parent is editable.
It is the mirror of a note: a note claims and is unwarranted; a
pending detachment is warranted and claims nothing. The term
is one I coined in the plan: '02_jeff_de-novo.org' spoke of
"a user's detachment" being "pending" (your question "what's a
user's detachment?"), and the plan's slice 6 named the state

**** DONE Claude says: the defect, term by term
A node is what the graph holds: a file in a skgrepo, named by
its gnid, its graph node ID. An occurrence is a headline in a
buffer that stands for a node; a node may have several
occurrences, in one buffer or in many. An occurrence is
editable when a save reads its text and its children as the
node's, and write-protected ('writeProtected' in its
metadata) when a save ignores them; a buffer may hold at
most one editable occurrence of a node. The viewparent of a
headline is the headline above it. Under an editable
occurrence, a child headline claims membership when the save
will read it as a member of its viewparent's list, and the
bare atom 'noClaim' says it does not; without the atom it
claims. A child is warranted when the graph already relates
it to its viewparent as its position implies, here when the
parent's contains list names it; the refresh recomputes that
at every pass and writes 'noWarrant' in '(view ...)' when it
does not hold. Under an editable parent at rest the two
agree: what claims is warranted. They differ only for what
the user changed since the last save: a new child claims and
is not yet warranted, and a child the user marked 'noClaim'
is warranted and claims nothing, which the docs call a
pending detachment, since the next save will take it out of
the list.

Validation refuses two claiming children that stand for one
node under one parent (its message says that non-ignored
content children must be unique), so when a buffer shows two
occurrences of one node side by side under one parent, which
I call twins here, all but one carry 'noClaim'.
The refresh runs a fixed sequence of steps at each parent.
Its second step, 'merge_siblings' in
'server/refresh/ladder.rs', unifies twins: the first in
