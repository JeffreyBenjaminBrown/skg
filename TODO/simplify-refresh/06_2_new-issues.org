****** Claude says: nearly; it is in the plan as slice 9
Your rule is in the plan in two parts, and the plan grew a
slice for the second.

The first part, pruning. An editable folder that is empty is
pruned at the tail when the restriction emptied it: its goal
had members before the restriction's omission and none after.
A folder that would be empty under any restriction stays,
since the user can add to it, and an emptied folder drawn on
request shows, empty, in that one refresh. The refresh applies
this from the goal alone; the goal computers already omit
restricted members before any rung sees the list, and the rule
only needs them to say that they omitted something. So no
caller tells the refresh anything for pruning; the caller's
policy carries only the two silenced buffer corrections. This
replaced my first draft, which had the caller say "a narrowing
follows". One consequence: a folder requested under a
restriction that hides all of it shows once and goes at the
next refresh; answering such a request with a message instead
is a one-line change if you prefer it.

The second part, the Restricted vognode, reverses one decision
of the de novo discussion, where you said of the old restricted
placeholder "Yes, disappear it!", and it is a better rule than
the one we took. The old placeholder carried nothing, not even
the gnid, and lingered where its node had been; what you
describe is a goal member: it stands exactly where a section
the user may see names a node the user may not see, and it
carries that section's gnid and nothing else. The visible file
already holds that gnid, so showing it reveals nothing the
visible data does not, with one exception you should weigh: a
viewer learns that the gnid resolves to a node in a restricted
skgrepo rather than to nothing, which the visible data does not
say. [JEFF: Yeah that's fine.]

An unknown would hide even that; you asked for
"restricted", and the plan takes it. What the rule covers,
base by base: every relation, since the goal computers decide
visibility in one place by the record's relRepo and the
member's home ('weave.rs' states it: a member is visible when
both are unrestricted), and the change splits that into
"omitted" (the record is restricted) and "Restricted" (the
record is visible, the node is not); the write-protected
folders, whose records live in the other node's file, where a
restricted node's record is a restricted file and is omitted;
a restricted occurrence under a visible record, which becomes
a Restricted vognode in place, keeping its vnid, fold state and
children, and an occurrence again when the restriction widens;
a restricted occurrence under a restricted record, which is
entombstoned as today, since the record itself may not be
shown; the diff view, where a restricted node is never a ghost
(a ghost would show HEAD's title) and the Restricted vognode
may carry the visible record's change facts; the save, where a
Restricted vognode claims as an unknown does, so a save keeps
the record, and deleting its line removes a record the user
could see, which today's weave of invisible members did not
allow and now allows for visible records only; and the hides,
where a Restricted member in the hidden-outside folder means
the folder shows every visible hide, so slice 1's save rule
("replaceable only when the folder could show the member")
widens in slice 9 to count a Restricted member as shown. What
it does not cover, and the plan decides: text typed on a
Restricted line is refused as on an unknown; it carries no
stats, since counts would reveal; the atom is 'restricted', a
new spelling beside the retired 'restrictedNode', which the
parser goes on refusing by name; and a restricted node's
aliases and properties, which live in its own file, are not
shown anywhere. The relRepo-move question is answered below
and left out of the plan.

On your first paragraph: relRepo moves are not confined to
content. The request '(editRequest (relRepo R))' is honored on
a content member, an alias member, and a member of the two
editable partner folders, the subscribee and the overridden
folder, where the save's writer is the folder's viewparent
('relRepo_request_is_collected' in 'validate_tree.rs'). It is
refused on a member of the hidden-outside folder, with the
message "HiddenOutsideOfSubscribee membership is editable, but
hide relRepos are derived" ('traverse.rs'): hides are inferred
by the save from the subscriber's content removals and from
the subscribee-as-such's visible content
('resolve_visibility.rs'), and their relRepo follows the
config's default for the two nodes' homes; I did not trace
where that default is applied. The write-protected folders
(containers, mentioners, subscriber, overrider, hider, and the
direct hidden folder, which exists and is write-protected,
editable only through the subscribee folder) take no request
from their side. So the extension you ask about is one
relation, the hide, and it is a design question rather than a
mechanism: what the home of an inferred hide should be when
the user moves it, and whether a moved hide stays moved when
the save next infers hides. That is a feature beyond this
plan; I would take it up as its own item after the run.

*** DONE jeff : what are these "corrections"?
**** DONE Claude says: what the refresh reports it changed
A correction is what a refresh reports it changed in a buffer
because the buffer contradicted the truth; the glossary's
entry "corrections" defines it, and 'CorrectionKind' in
'server/refresh/corrections.rs' lists the six kinds with the
message each shows: a goal item drawn that no headline stood
for ("Drew what the graph says belongs here."); a headline
entombstoned because it can stand where it is for nothing; a
claiming child marked 'noClaim' because the graph does not
relate it to its parent; duplicate viewnode siblings merged
into one; a headline re-kinded, as the graph has it; an edit
request dropped because the headline's new kind has no slot
for it. Each names its headline by vnid and title. The save
and rerender responses carry every refreshed view's
corrections, tagged with the view ID, and both clients append
them to the server-warnings buffer ("*SKG Server Warnings*" in
Emacs) under a headline per view. The word is from the de
novo discussion, where the refresh's output was settled as
the buffer plus its corrections. This issue concerns two of
the six that today fire for things that are not the buffer's
fault: after your own save deletes a node, your other open
views report its occurrences entombstoned; after you widen
the skgrepo restriction, the members it reveals are reported
as drawn. Decide 10 of the review settled that neither is a
correction, and the issue is only how the refresh learns it:
from its caller, since the refresh itself is stateless.
