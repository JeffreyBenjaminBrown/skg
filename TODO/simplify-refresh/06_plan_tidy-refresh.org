* Words this plan uses
The glossary ('docs/glossary.org') defines the refresh and its
vocabulary: occurrence, ghost, unknown, tombstone, folder,
property member, change viewnode, claims membership and
'noClaim', is warranted and 'noWarrant', the goal, the extent,
the tail, the buffer corrections, the diff view, the
readiness marks and requests. The words below are new in this
plan, or change with it.
** duplicate viewnode siblings, viewnode merge
Duplicate viewnode siblings are siblings standing for one gnid
under one parent. The refresh's second rung merges them into
one viewnode: a viewnode merge, distinct from a nodeMerge,
which joins two graphnodes. The glossary's entry "merge of
siblings" is retitled "viewnode merge" and defines both; no
one "survives" the merge, and the word "survivor" goes. The
two terms are coined by this plan and the glossary says so.
** change leaf
A change leaf is one aspect of one change the diff view
tracks, the unit the readiness store marks: a node's existence
or properties, or a relationship's existence ('LeafKey' in
'server/diff_view/change_leaves.rs'). Two headlines can name
one leaf.
** orphan
An orphan is a node that no list contains. The word has one
precedent in the user docs ('docs/COMMANDS.org', "the old node
might become an orphan") and none in the glossary, which this
plan gives it.
** detach, attach
Under a parent that reads claims, to detach a child is to
write 'noClaim' on it, so that the next save takes it out of
the parent's list; to attach it is to remove the atom, so that
the next save puts it in. Both are commands in both clients
after slice 4, and both are gestures on the declared claim; no
request is involved. "Detach" said of the tree ("the refresh
never detaches a child") is retired in prose: the refresh
"never removes a child".
** restricted, record
A node the skgrepo restriction keeps out of view is restricted,
and so is its occurrence. "Hidden" is reserved for
hides-from-subscriptions; the presence answer's middle word is
'GnidPresence::Restricted'. A record is a relationship as one
node's file states it, in one skgrepo's section; a record is
restricted when that section's skgrepo is. A member of a goal
is visible when its record and its home are both unrestricted.
** Restricted vognode
The vognode that stands where a visible record names a
restricted node: kind atom 'restricted', 'Vognode::Restricted'
in code, herald "restricted". It is a goal member and carries
the record's gnid. The retired placeholder of the same name,
which carried no gnid and stood for nothing, is not revived,
and the parser goes on refusing its spelling 'restrictedNode'.
** claiming
A child that claims membership is a claiming child. The save's
old word for it, "non-ignored", goes from messages, names and
comments.
** buffer correction
A buffer correction is a change the refresh made to what a
buffer said because the buffer was wrong about the graph; the
term is "buffer corrections", never bare "buffer corrections", in
prose, docs and the server's names (slice 2). Two things are
not buffer corrections and are not reported: a tombstone the
refresh leaves where the saving user's own save deleted the
node, and a member the refresh draws because the skgrepo
restriction was widened. The definition is in the glossary and
in 'server/refresh/buffer_corrections.rs'.
** the search's one phase
After slice 6 a text search answers with one message carrying
the enriched buffer. The words "phase 1", "phase 2",
"enrichment thread", "request-snapshot", "snapshot response"
and "stream guard" name things that no longer exist, and go.
"Enrichment" stays for what the search draws under each hit.
** the switch's entombstone-and-prune phase
The first phase of a skgrepo-set switch's rerender, in which
'convert_and_prune_for_skgrepo_switch'
('server/update_buffer/skgrepo_switch.rs') entombstones every
occurrence of a node the new restriction keeps out and every
unknown it excludes, and prunes childless tombstones, before
the refresh runs on the same view. The code calls it a
"prepass", a word this plan retires: the hook parameter named
'prepass' in 'server/serve/rerender_stream.rs' goes with its
only user (slice 1), and the comment in
'server/import_org_roam/parse.rs' that says "pre-pass" says
instead which phase it means (slice 2).
** RefreshMode, the rungs, visit.rs
'CompletionMode' becomes 'RefreshMode' (slice 8). The
refresh's ordered steps at one parent are its rungs; the word
"ladder" is reserved for the privacy ladder, and the file that
holds the rungs and the visit is 'server/refresh/visit.rs'.
** How to say it in messages
A user-visible message says "claiming" and never "non-ignored",
"viewnode merge" and never "merge" bare, "occurrence" and never
"node" for the kind, "orphan" for a node nothing contains, and
"restricted" for the restriction's sense.

* Agreed behavior
What the code does when the plan is complete. Behavior not
mentioned here is unchanged.
** The viewnode merge (slice 0)
Duplicate viewnode siblings merge into one viewnode. The result
has a fresh vnid, minted by the tail as for any viewnode that
lacks one; it is folded only if every sibling was folded, and
its body is folded only if every sibling's was; it is focused
if any sibling was; it is editable if any sibling was, with the
one exception the code keeps today (a node and its shown
overrider stand for one gnid, and the result takes the
editability only when no other occurrence of the node in the
buffer already holds it); it claims membership if any sibling
did; it carries the union of the siblings' view requests, and
the edit request and relationship request of whichever sibling
carried one (at most one does, since a node edit request lives
only on the editable occurrence and validation lets only one
position carry a relationship request); it holds every
sibling's children in sibling order, each marked 'noClaim'
unless the goal warrants it under the result, as today. The
warrant is recomputed at the next rung, as today. The "merged"
buffer correction names the result's vnid.
** Contradictory readiness requests refuse the save (slice 0)
Validation refuses a save in which two headlines name one
change leaf with contradictory readiness requests, one
'(ready ...)' and one '(unready ...)' naming the same leaf. The
refusal names the leaf and the vnids of both headlines. The
check runs per leaf over the whole buffer, beside the deletion
check of 'contradictory_instructions.rs'. Two requests that
agree are consumed as today.
** What is not a buffer correction (slice 1)
The refresh reports no 'Entombstoned' buffer correction for a
headline standing for a node that the save being rerendered
deleted,
and no 'Reinstated' buffer correction when the rerender follows a
widening of the skgrepo restriction. The refresh learns both
from its caller: the save's rerender passes the gnids the save
deleted, and the skgrepo-set switch passes that the restriction
changed. Every other buffer correction is reported as today.
** The orphan warning (slice 1)
A headline typed under a parent that reads no claims (a
write-protected occurrence, a ghost, a tombstone, a
write-protected folder) is still saved as a node, as today, and
the save-result's warnings gain one line per such node: that it
was created as an orphan, which nothing contains, naming the
headline. The clients show it where they show save warnings.
** Nested tombstones stay (slice 1)
A tombstone whose only children are tombstones is kept as the
model has it; nothing collapses them. The prune rule's doc
comment says that nested tombstones after a deletion are by
design, that collapsing them was considered and rejected
because it could confuse the user, and the technical data
model's tombstone paragraph says the same in one sentence.
** The ghost-tombstone request goes (slice 1)
The view request '(viewRequests tombstone)' on a ghost, the
Emacs commands 'skg-request-ghost-tombstone' (C-c r t) and
'skg-request-buffer-ghosts-tombstone' (C-c r T), and their
Neovim twins (<localleader>rt, rT) are removed, with their
parser rule, herald ("req:tombstone"), editor field, tests and
docs. In the diff view a ghost is a pending change, shown until
it is restored or committed. The tombstone kind itself, and the
'tombstone' atom as a kind, stay.
** Under a skgrepo restriction (slices 1 and 9)
The refresh, not a phase of the skgrepo-set switch's own,
brings a view under the restriction: it entombstones the
occurrences the restriction keeps out, draws no restricted
member, prunes childless tombstones, and prunes the folders
the restriction empties. 'convert_and_prune_for_skgrepo_switch'
and the hook that ran it before the refresh are deleted. A
switched buffer looks as it does today, except where the
Restricted vognode stands.
*** a folder the restriction empties is pruned
An editable folder that is empty is pruned at the tail when
the restriction emptied it: its goal had members before the
restriction's omission and none after. A folder that would be
empty under any restriction stays, since the user can add to
it, and so does an emptied folder in the one refresh that
draws it on the user's request. The refresh applies the rule
from the goal alone; no caller tells it. A folder holding a
Restricted vognode is not empty.
*** the Restricted vognode
A vognode of a new kind, written '(skg restricted (gnid X)
[(skgRepos (relRepo R))] [noClaim] [(editRequest ...)])',
stands where a visible record names a restricted node. It
carries the record's gnid and relRepo and nothing of the node:
no title, no body, no home skgrepo, no stats. Its herald is
"restricted" in the message style; its headline carries no
text, and text typed on its line is refused as on an unknown's.
The ID rule answers it after "present" and before the ghost
question: a gnid the truth says is restricted, named by the
parent's goal, is Restricted; a restricted node is never a
ghost. An occurrence of a node the restriction newly keeps out
becomes Restricted in place when its record is visible, keeping
its vnid, fold state and children, and an occurrence again
when the restriction widens; under a restricted record it is
entombstoned. The goal computers keep a member whose record is
visible and whose home is restricted, marked so, and omit only
members whose record is restricted. A Restricted vognode claims
membership as an unknown does: a save keeps its gnid in the
list, and deleting its line removes the record; the save's
weave of invisible members restores only records the buffer
could not show. It carries the visible record's change facts
in the diff view and takes a relRepo request and a readiness
request as an unknown does. Both clients render it from the
served herald table and offer its fields from
'shared/metadata-fields.json'.
*** a save never unhides what it could not show
A hide is replaceable only when the folder as drawn could show
its member: its record is unrestricted and its member is
either unrestricted or shown as a Restricted vognode. A
hidden-outside folder saved under a restriction leaves every
other hide in 'hidesFromSubs' as it finds it. Today the save
judges by the record's relRepo alone, and an empty folder
deletes a hide ('06_1_prepass-experiment.org').
*** the order of the two slices
Slice 1 fixes the save, adds the emptied-folder rule and
deletes the switch's phase; until slice 9 adds the Restricted
vognode, a member with a visible record and a restricted home
is omitted as today, so a folder it alone would fill is
emptied and pruned, and no hide of it is replaceable. Slice 9
then adds the kind and the goal's distinction, and the rules
above hold in full.
** The stats pass is linear (slice 1)
The tail's derived facts no longer scan a recorder's whole
contains list once per child. The relRepo of each child's
relationship is looked up in a map built once per recorder, so
that a view of N children costs O(N). The synthetic case the
probes report timed (4,000 children, 3.7 s in a debug build)
takes well under a second after the slice, measured and
recorded in 'progress.org'.
** The detach and attach commands (slice 4)
Emacs 'skg-detach' (C-c s t) writes 'noClaim' on the headline
at point and 'skg-attach' (C-c s a) removes it; Neovim ':Skg
Detach' (<localleader>st) and ':Skg Attach' (<localleader>sa)
do the same. Both refuse, with a message, a headline whose
parent does not read claims, since no child claims there; attach
on a claiming child, and detach on a non-claiming one, say so
and change nothing. Neither saves. The heralds are unchanged:
after detach the headline shows "detach" until the save, then
⊥; after attach it keeps its ⊥ until the save. The metadata
editor still offers 'noClaim'.
** The search answers in one phase (slice 6)
A text search request is answered by one 'search-results'
message whose content is the enriched buffer: the hits, each a
write-protected occurrence with its node's title, its containers
folder with each member's containerward chain, the override
folders when they have members, everything under a hit folded
as today, and, for a hit found through an alias, its alias
folder holding the node's aliases, unfolded. No
'search-enrichment', 'request-snapshot' or 'snapshot response'
message exists; the clients hold no stream guard and set no
read-only period for a search; closing a search view needs no
abandonment of an enrichment. The 'overPrivateText' challenge
and its retry are unchanged. 'docs/api-and-formats.org', "Text
search", describes the one reply and carries this note: the
enrichment is a refresh of a stub built from the hits, the same
code every view is drawn with; the two-phase protocol it
replaced showed the hits a tenth to a quarter of a second
earlier for a search of hundreds of hits and was removed for
its complexity ('bench-search-enrichment.org' beside this plan
holds the measurements). The search takes no hit cap and no
node budget; the refresh's budget exists and the stub could be
given one, which is left unmade.
** A hit found through an alias (slice 6)
A hit shows its node's title. When a match was an alias, the
hit holds its alias folder, drawn by the refresh from the graph
with all of the node's aliases, left unfolded so that the
matching alias is seen; the hit of a node matched by its title
alone holds no alias folder unless the user asks for one.
** The logs of a plan run (slice 5)
'bash/all-tests.sh' wipes 'tests/results/' at its start except
subdirectories named for a plan ('tests/results/06/' and the
like), which a run's agents own. 'tests/USAGE.md' says so.
** The test harness's temporary directories (slice 5)
Each test's temporary fixture directory is unique to its
process, and cleanup waits for the Tantivy writer before
removing it, retrying once on "Directory not empty"; the flake
recorded in 'TODO/problems.org' does not recur over ten full

* Pitfalls the slices must respect
** the claim is read in four places
The save reads claims in 'local_fieldintent_collection/
traverse.rs'; 'write_protected_edits.rs' and
'is_in_containerward_chain' read them for their own rules; both
clients' readiness walks key on the atom. A change to what
'noClaim' means touches all four. This plan changes none of
them; the detach and attach commands only write the atom.
** validation guarantees one claiming duplicate
'nonignored_children_have_distinct_gnids'
('server/from_text/buffer_to_viewnodes/local.rs') refuses two
claiming children of one parent that stand for one gnid, so
duplicate viewnode siblings carry at most one claim. Slice 0's
"claims if any did" relies on it; slice 2 renames it.
** the readiness store keys by leaf, not by headline
'ReadinessStore::marks' is a map from 'LeafKey' to a
fingerprint ('server/diff_view/readiness_store.rs'). A new
vnid loses no mark, and two duplicates' stored marks cannot
disagree; only requests within one buffer can, which is what
slice 0's check refuses. Requests are collected and applied in
buffer order by 'consume_readiness_requests'
('server/diff_view/readiness_requests.rs'); today the later
one wins silently.
** the tail mints vnids
'finish' in 'server/refresh/tail.rs' gives a vnid to every
viewnode that lacks one. A merge that wants a fresh vnid clears
the result's vnid and lets the tail mint it; nothing else keys
on a vnid across refreshes (fold state rides in the metadata;
the clients restore point by the focused headline; the
buffer corrections name headlines by vnid at report time).
** the goal computers omit restricted members before the rungs
'omit_restricted_members' ('server/update_buffer/reconcile/
mod.rs') and 'omit_hidden' ('server/refresh/goal.rs') drop
restricted members from a goal before any rung reads it, so
nothing downstream can tell an emptied folder from an empty
one unless the goal says it omitted something, and nothing
can tell a restricted node under a visible record from one
under a restricted record. The emptied-folder rule needs the
first bit on 'Goal'; the Restricted vognode needs the omission
split by its cause, the record or the node.
** the save weaves invisible members back
'preserve_invisible_members' ('traverse.rs') and 'weave.rs'
restore to a saved list every member the buffer could not
show, at its disk position; 'weave.rs' lines 57 to 62 state
the visibility test (the record's relRepo and the member's
home both unrestricted). With the Restricted vognode the weave
restores only records the buffer could not show.
** the buffer corrections are recorded during the walk
'Walk::corrections' ('server/refresh/mod.rs') records each
buffer correction as the rung makes it; the tail fills in
vnids. A policy that silences some buffer corrections is
applied where they are recorded, by kind and gnid, not by
filtering messages afterwards, so that the fixpoint tests,
which demand no buffer corrections on a second refresh, keep
their meaning.
** the save knows what it deleted
'SaveAffectedIds::from_prepared' ('server/serve/handlers/
save_buffer.rs') holds the save's affected gnids, among them
the deleted ones, before the rerender runs. The rerender
context ('RerenderAfterSaveContext', 'server/update_buffer.rs')
is the one place to carry them to the refresh. The skgrepo-set
switch rerenders through 'prepare_rerender_views_where'
('server/serve/rerender_stream.rs') and knows the old and new
restriction.
** the two-phase search spans server, clients and tests
Its footprint, by file: 'server/serve.rs' (the idle loop's look
into the slot, under a 100 ms read timeout that also serves
other purposes and stays), 'server/serve/protocol.rs' (the
"snapshot response" request), 'server/serve/handlers/
text_search.rs' ('SearchEnrichmentPayload',
'spawn_enrichment_thread', 'abandon_search_enrichment',
'cancel_search_enrichment', 'enrich_search_viewforest'),
'server/serve/handlers/skgrepo_sets.rs' and
'server/serve/rerender_stream.rs' (callers of the abandonment),
'elisp/skg-request-text-search.el', 'skg-request-save.el',
'skg-buffer.el', 'skg-recovery.el', 'nvim/lua/skg/search.lua',
'save.lua', 'lock.lua', 'buffer.lua', 'recovery.lua', the tests
'tests/search_enrichment_terminal.rs', 'tests/grouped_repos.rs',
'tests/repo_sets.rs', 'tests/hidden_nodes.rs',
'tests/viewnode_id_stability.rs', 'tests/integration/
search-enrichment/', 'tests/integration/valid_and_invalid_saves/
test-emacs.el', 'tests/nvim/search_spec.lua', 'save_spec.lua',
'tests/elisp/test-skg-search-dirty-state.el', and the docs
'api-and-formats.org', 'glossary.org',
'nvim-client-deviations.org'. Slice 6 visits every one; a grep
for the retired names is its last check.
** the enrichment renders twice today
'text_search.rs' lines 389-403 discard the refresh's text and
render again after excluding 'overPrivateText' nodes, so those
tombstones skip the tail's prune (readability report item 14,
duplication item 10). Slice 6 excludes before the refresh and
renders once.
** the search stub's override folders
'stub_root_of_hit' adds an override folder when
'override_relatives' finds pids, but the refresh fills it from
'partnerFolder_members_in_graph', by member keys; the two can
disagree on a gnid on disk but not in the graph (duplication
item 10). Slice 6 tests the folder with the folder's own goal
function, as 'add_default_folders' does.
** the herald table has a conformance test
'tests/unit/heralds.rs' checks the rule table against the
atoms the server emits and the atoms the clients compute.
Removing the "req:tombstone" rule (slice 1) and nothing else
keeps it green; removing an atom the server still emits does
not.
** the metadata fields table has a conformance test
'tests/metadata_fields_table.rs' checks
'shared/metadata-fields.json' against the parser. The ghost's
'tombstone' view request leaves both in slice 1.
** both clients lens the served table
Neither client computes a warrant or a herald of its own but
the three the heralds doc names ('(repoBoundary LABEL)',
'pendingDetachment', the changed folder); the detach and
attach commands need no herald work.
** the fixpoint tests
'run_in' ('tests/refresh/mod.rs') refreshes twice and demands
an identical result and no buffer corrections the second
time; the sweeps in 'tests/idempotence.rs' do the same over the
fixtures. A change to the merge, the buffer corrections or the
tail runs them first.
** the rendering cases
'tests/shared/herald-rendering-cases.txt' is read by both
clients' test suites; a case added for the relRepo request
(slice 4) must pass in both, and the Emacs fix is what makes it
pass there.
** the runner
'bash/run-plan-slices.sh' is wired to this plan; see "Running
it".
