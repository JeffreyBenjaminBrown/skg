#+title: Review of plan 06: tidy the refresh, run 2026-10-26

* Verdict
The plan did what it set out to do. Eleven slices in four and a
half hours, every suite green at every slice's end but the one
failure older than the plan, eight entries of the problems file
closed, the refresh's parts in one place under 'server/refresh/',
both clients aligned around a shared table and two shared case
files, the search answering in one message, the Restricted
vognode and the detach and attach commands in, and the test
flake found at its cause and gone. The probes passed seven of
ten behaviors end to end, and the fixpoint held after every
gesture, the nodeMerge and the switch included. Four of the
agents found and fixed a bug of their own or of the code before
committing (the 'show_overrider' order, the restore tests'
denominator, the Restricted children's claims, the flake's real
cause), which the plan's instruction to confirm traced claims
by tests earned.
What needs work is the restriction, which the probes drove
harder than anything before: a narrowing then a widening loses
the views whose roots it kept out, the diff view under a
narrower set shows a deleted private node's title and omits
Restricted members, and an alias recorded in a restricted
section shows regardless. Two of the three predate the plan.
Beside them: Neovim's buffer writers misplace requests and
append a delete the server refuses (confirmed by a spec), a
requested hidden folder holding a dangling hide refuses the
save, and a headline under a tombstone is refused where the
plan said it was saved. The structural debt the plan left is
the Restricted vognode as a twin of the unknown, which two
reports rank first. Decide items 1 to 4 are the corrective
slice; 5 to 14 are the next tidy.

* What the user sees differently
** By decision
Duplicate viewnode siblings merge into one headline that keeps
the claim, unfolds if any was unfolded, and gets a fresh vnid.
A save with contradictory readiness requests on one change leaf
is refused, naming both headlines. Your own deletions and a
skgrepo-set switch no longer fill the warnings buffer with
buffer corrections. A headline typed under a parent that reads
no claims is saved as before and the save says so: "created an
orphan". The ghost-tombstone commands (C-c r t, C-c r T and
the Neovim twins) are gone; a ghost stays until restored or
committed. A skgrepo-set switch leaves an emptied editable
folder in place, empty, and it fills again when the set
widens; where a visible record names a restricted node, a
Restricted vognode stands, showing "restricted" and the gnid,
and the save keeps every hide it could not show. Detach
(C-c s t) and attach (C-c s a) exist. A text search answers
with one message holding the enriched buffer: no early list of
hits, no read-only period, no second repaint; a hit found by an
alias shows the node's title with its alias folder open. The
metadata editor shows readiness requests and orders a
headline's parts as the server does. The per-view headline in
the warnings buffer says "Buffer corrections", and startup
warnings go under their own headline rather than erasing it.
The relRepo request's herald reads "request:~NAME" in both
clients. A rerender of a view with thousands of children is
twenty times faster. Hand-edited metadata that breaks the
grammar is refused with the part named, which the docs now
say.
** By accident, or unforeseen
A search during a save is no longer refused (slice 6): it
behaves as a content-view request does. Neovim's skgrepo
inheritance walk treats metadata naming no kind as a node, as
Emacs did (slice 4). The editor can open a headline carrying
'(ready)' (slice 7). The search's overridden folder shows an
unknown for an override target on disk but not in the graph
(slice 6). A requested hidden folder holding a dangling hide
may be refused at save (slice 9, filed, unconfirmed).

***** DONE problem
A buffer correction is a message the refresh reports when it
changed what a buffer said because the buffer disagreed with
the graph: a member drawn that no headline stood for, a
headline entombstoned, a child marked 'noClaim', duplicate
siblings merged, a headline re-kinded, an edit request

clients show them in the warnings buffer.

Not every change the
refresh makes is the buffer's fault, so the refresh is told
what to keep quiet about. Today it is told two ways.
- The first
  is a value the caller passes into the refresh, a struct named
  'BufferCorrectionPolicy', holding the set of gnids the save
  being rerendered deleted (so that their tombstones in the
  saver's other views are not reported) and a flag saying the
  rerender follows a skgrepo-set switch (so that what the switch
  draws, entombstones or re-kinds is not reported); the refresh
  consults it as it records each correction.
- The second way is
  no value at all: four callers that draw a buffer nobody will
  read corrections of (a fresh content view, a search buffer,
  the diff view's first draw, the integrate request) pass the
  struct that reports everything and then throw the corrections
  away.
