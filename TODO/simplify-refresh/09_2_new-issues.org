** DONE The delete's propagation into a restricted recorder
*** the problem
When a save carries a delete request ('C-c <backspace>',
'skg-delete'), the server deletes the graphnode and then
rewrites every file that recorded a relationship to it, so that
no file names the deleted ID. Under a skgrepo restriction some
of those recorders may have their record in a section the
restriction keeps out. Today the server rewrites those sections
too, against the principle that a write never touches what the
skgrepo restriction hides. The report offered two fixes: refuse
the delete whenever a restricted record names the graphnode, or
leave such a record as it is.

***** Claude says: noted; the plan's slice 2 now says so
****** the flow
A save that carries a delete request under a skgrepo
restriction, where a record the restriction keeps out names the
graphnode, stops before writing with a confirmation response,
as a save stops today for strandeds or a telescope hoist. The
response says how many records in restricted sections name the
graphnode, and nothing else of them. The client asks "Delete
from: (c)ancel, (v)isible records only, (a)ll owned records";
cancel sends nothing; the other two re-issue the save with a
field '(delete-from . "visible")' or '(delete-from . "all")',
which is never cached. Under "visible" the restricted records
stay as they are (the plan's earlier choice, now one of the
three); under "all" the server rewrites them too, as today,
with your leave.
****** what the user learns
The offer tells the user that some restricted record names the
graphnode, which a silent choice would not have; you chose that
knowingly.
*** the plan's choice
Leave the record as it is. The deleted ID then stays in the
restricted recorder's list, and where that recorder is shown
under a connection that can see the record, the ID appears as
an unknown viewnode, which 'C-c d a'
('skg-delete-references-to-absent-node'; '<localleader>da') can
remove under an unrestricted connection. A refusal would have
told the user that a restricted recorder exists.

** DONE AGREED : The hiddenFolder a save prunes is not drawn again
*** the problem
Under a skgrepo restriction a requested hiddenFolder shows only
the hides whose records the restriction shows. If a save removes
the last of those, the folder is left empty and the refresh
removes it, with the request that drew it. A later skgrepo
widening, which would show the remaining hides, draws no
hiddenFolder, since nothing asks for one; the API doc's "a
skgrepo widening reveals members and folders" holds for folders
still present, not for one that was removed. The probes'
report lists this as its finding 4c.
*** the plan's choice
Left filed, by the judgment you gave on Decide 11 for the
restricted root's folders: a user who wants the folder asks for
it again with 'C-c l h'.
