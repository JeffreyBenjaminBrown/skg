#+title: Benchmark: text search and its enrichment, old vs new
* Summary
In both builds the server asks for the snapshot about 100 ms
after it sends the results. That wait is the idle poll in the
connection loop: 'read_line' times out after 100 ms, and only
then does the loop look in the enrichment slot. So the wait
does not depend on the enrichment thread in either build.
** Old build: the thread's work was hidden
The old thread needed 24 ms (286 hits) or 52 ms (724 hits).
That fit inside the 100 ms wait, so the client never saw it.
** New build: the enrichment itself is slower
The thread does nothing, but the stub refresh that replaced
'render_enriched_search_buffer.rs' takes longer than the old
hand drawing: 86 vs 79 ms for title-only, and 209 vs 177 ms
for title+body.
** Phase 1 is a little slower in the new build
31 vs 27 ms title-only, 61 vs 56 ms title+body. The spread
between runs is about as large as that difference.
** Most of the time to an enriched buffer is the poll
From request to enriched buffer took about 222 ms (new) and
208 ms (old) title-only, and 374 vs 337 ms title+body.
About 100 ms of each is the poll wait.

* How the numbers were taken
** Driver script
'bash/bench-search-enrichment.py', copied from the session's
scratchpad so that the benchmark can be rerun.
** One connection per search
Run with 'python3 -I bench_search.py PORT RUNS'. Each search
opens its own TCP connection and sends the request line. It
reads LP messages and stamps each one with a time once its
last byte has arrived. It answers request-snapshot with the
phase 1 content, unchanged, and stops at search-enrichment.
It tells message types apart by searching the sexp text.
** Timer boundaries
- t1 starts just before the request is sent.
- t2b starts just before the snapshot response (line and
  body) is sent. So it includes sending 56 to 120 KB over
  loopback.
** Warm-up
Each server first got one warm-up pass (1 run of each kind),
then the 5 measured runs, all in one process. Warm-up times
were close to the measured ones. The first title-only phase 1
on a fresh server was slower: about 57 ms new, 34 ms old.
** Startup time
Wall time from starting the binary to "Server ready." first
appearing in its log, polled every 50 ms. Each build was
measured once, on a fresh copy with no index. A single sample
does not show which build starts faster.
** Order
Run one after the other, never at the same time: NEW first,
then OLD. Each server was killed by its recorded PID, and its
port was confirmed free afterwards.
* What went wrong, and what I did not measure
** Nothing failed
- Every search produced exactly three messages, in order:
  search-results, request-snapshot, search-enrichment.
- Every enrichment carried content.
- Every request-snapshot named the terms that were sent.
- Neither server log contained an error or a panic.
** Not measured
- Emacs-side rendering and parsing.
- Release builds.
- Repeated startups.
- The overPrivateText path, because it never came up.
- Searches other than "something".
** Enriched content differs slightly between builds
The new build's enriched content is about 5 percent larger
in bytes, with the same number of lines. I did not compare
the two contents, to avoid printing private data.
** Cleanup
The worktree, the old target directory and both data copies
were deleted. Only the driver, the launcher, the server logs
and the output files remain in the scratchpad bench folder.
