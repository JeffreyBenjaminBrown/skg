** how to read this
In all of the following, hopefully (i.e. if I haven't screwed up),
angle brackets wrap descriptors,
and quotation marks wrap special herald text.

Sometimes I'll say gnode and vnode (graphnode and viewnode) here,
because it's important to bear in mind the distinction:
A gnode can be represented by a vnode,
but not every vnode represents a gnode;
a vnode might instead represent an aspect of a gnode.
Child and parent is meaningless in the graph,
but meaningful in a viewforest.

Sometimes I'll talk about a vnode's gnode.
When I do that I mean the gnode that a vnode represents.
(If the vnode is a folder, or anything but a vognode,
then I'm probably accidentally talking nonsense.)
Similarly, maybe I'll talk about a gnode's vnode(s);
that would be all the vnodes that represent the gnode.
** problems and motivation
*** Changes must be committed to all skgrepos at once.
Magit is already not a great graph interface.
But it's particualarly terrible when changes span repos.
One problem the total diff view will solve is that
it will let the user see all changes at once.
*** A user needs to be able to mark changed aspects of a node commit-ready.
In the diff, a node might come up in multiple different places.
The user (me) has in the past needed to see all those spots
before deciding whether a node is ready to commit.
This required manual note-taking in some side channel; painful.
The user should therefore be able to represent commit-readiness
in skg, and granularly: not just that the whole node is ready,
but that some aspect (its aliases, say) is ready.

If two vnodes V and V' represent the same gnode G,
and the user marks one of them commit-ready,
the other should be updated to show the same thing.
Stated declaratively rather than procedurally,
commit-readiness is a property of gnodes, not vnodes.

It is also a property of *aspects* of gnodes,
such as a gnode's list of aliases.
The same logic (share it across vnodes)
applies to two folders representing
the same aspect of the same gnode.

*** folder the content
The special treatment of content relationships is
problematic for marking changes commit-ready.

The changes to other aspects of a gnode -- its aliases, say,
or even its containers (once non-content trees are folderable)
-- can be collected under a folder.
Its contents, though, are presented as immediate children.
There is thus no content folder that one can mark 'done'
after verifying that the content relationships are commit-ready.

Skg therefore needs two equivalent ways of presenting content:
As immediate children, or under a "content folder",
which would bear the herald text "its content" in the system font.
**** [Claude] the most invasive prerequisite, and three ways to do it
'contains' is the one list that save extraction reads from a node's
direct children; 'content_members' in [[file:../../server/from_text/local_fieldintent_collection/traverse.rs][traverse.rs]] does that
reading. Many other sites also look for content directly under the
vognode: the content reconciler, the editable draw rule and its
cascade, the node budget, the collected IDs of override substitution,
the hidden-in-subscribee filter, the ancestry checks, 'org_to_text',
the parser, and the client's subtree walkers ('skg-set-repo-recursive',
'skg-git-add-if-new-recursive', 'skg-delete-recursive'). Any second
shape for content would have to be honored at every one of those
sites. I see three ways to get what you want.
***** A1: an optional folder (your proposal, literally)
A1 adds a 'PartnerFolder::Content' kind, with the 'EditableSet' policy
and the contains relation's second role as its member role, and the
folder is either present or absent under a node. The save rule would
be: when a node has a content folder, its direct vognode children must
be non-members ('affectsParent false'), and the folder's members
define 'contains'. Every consumer would learn to look through the
folder. The code would carry two shapes everywhere, forever.
***** A2: always foldered internally, two serializations
A2 gives every vognode a content folder in the viewforest, always. The
renderer writes the folder as a headline only when the folder is
flagged explicit, and the parser inserts an implicit folder under
every vognode whose text lacks one. Internally the code then has one
shape; the two shapes exist only at the text boundary. The leak sits
at the edges: an implicit folder must not count as an ancestor
generation, must not take focus or fold state, and must not appear in
error messages. A2 touches fewer sites than A1, but each site is
subtler.
***** B: no content folder; a changeset marker carries the aggregate
The TDV needs the content folder for three things: a place to mark
the whole content list ready, a place for the aggregate ∃ and ~
heralds, and a way to order the content among the rightward folders
ahead of the leftward ones. B keeps the content as direct children and
gives the first two things to one changeset marker instead. A
changeset marker is a childless non-vognode line that stands for a set
of changes recorded in its parent's files and carries their derived
commit-readiness; the term is yours, from "changed a relationship's
skgrepo". You settled the shape of this one in your reply below: a
non-vognode child labelled "its content changed", drawn beside the
folders, which carries the aggregate heralds and is the headline the
user marks. (I first proposed carrying the aggregate on the vognode's
own headline; your changeset marker is better, because it leaves the
vognode's heralds as they are.) Only the ordering is lost: the content
members stay after every folder, because the reconciler parks
non-vognode children first. B is the cheapest option by far, and it
changes nothing in save extraction.
***** my opinion
B gets the TDV built soonest, and it touches nothing load-bearing. A2
is the right end state if you ever want foldered content as a general
view feature, and it is cleaner than A1 because the code keeps one
shape. I would start with B and schedule A2 as its own project, with
the content test matrix run in both presentations, unless the
ordering argument matters more to you than the delay.

**** 1. a graph pair: the before-graph, built from a git snapshot
This tool is the foundation, and it is cheap, because both halves
exist. The diff report already reads every '.skg' blob at HEAD (or at
the index) into a 'GraphSnapshot' of composed telescopes;
'read_graph_snapshot' in [[file:../../server/diff_report/git_snapshot.rs][server/diff_report/git_snapshot.rs]] does that reading, and a
cache keyed by the HEAD commit id keeps it from repeating the work.
'InRustGraph::from_graphnodes' in [[file:../../server/dbs/in_rust_graph.rs][server/dbs/in_rust_graph.rs]] builds a graph,
with all of its recorderward relmaps, from a list of Graphnodes.
Gluing those two together gives exactly the "two inRustGraphs" you
propose under "deleted a gnode". I will call the result a graph pair:
#+begin_example
  struct GraphPair { before : Arc<InRustGraph>, after : Arc<InRustGraph> }
#+end_example
Here 'before' is the graph built from the last commits, and 'after'
is the live graph. On top of the pair, a small API answers questions
about the union of the two graphs. I will call that API the union
walk:
#+begin_example
  enum Presence { Both, OnlyBefore, OnlyAfter }
  node_presence (id)   -> Option<Presence>
  node_changes  (id)   -> text? aliases± extraIds± flags± home (old, new)?
  partners (id, role)  -> Vec<(ID, Presence, relRepo before?, relRepo after?)>
  changed_pids ()      -> { rightward : HashSet<ID>, leftward : HashSet<ID> }
#+end_example
'Presence' says whether a node or a relationship exists in both
graphs, only in the before-graph, or only in the after-graph.
'partners' walks the UNION of the two graphs, so one call reaches a
removed container, a deleted node's former content and a new
relationship alike, and it tags each one with its presence. The
containerward tracing in the PCSVF, the diffed containerward forests,
the diffed partner folders and the alias and ID folders all reduce to
this API.
***** why not extend today's 'SkgrepoDiff'
Today's diff view works per file and per stage. (A stage is one of
git's two halves: the staged half compares HEAD to the index, and the
unstaged half compares the index to the worktree.)
'compute_diff_for_skgrepo' yields, for each changed file, one
'NodeChanges' per stage, and the renderer first reconciles the
worktree view and then patches diff facts onto it, in
'process_unrestrictedVognode_diff'. Three things make that the wrong
base for the TDV. First, it cannot answer containerward questions
about the old graph, because no recorderward relmaps exist for HEAD;
that is why removed containers today need an "inverse scan" over
every changed file. Second, it compares members by ID only, and so it
drops relRepo (see item 2). Third, the per-stage split doubles every
rule; the reorder-as-remove-plus-add bug in [[file:../diff-render-roundtrip.org][TODO/diff-render-roundtrip.org]] was a
symptom. A pair of graphs answers all of these questions uniformly.
The staged/unstaged distinction is the one thing the pair does NOT
give for free, and you decided to drop it: the TDV compares HEAD with
the worktree only, and the index never enters.
***** lifetime and cost
The server would build the before-graph when a TDV is opened, keep it
in the view's state while the TDV stays open, and rebuild it when
HEAD moves; the snapshot cache key already detects that move. On the
28k-node dataset the HEAD read is the slow part, and it is already
cached; the graph build is a linear pass. The memory cost is one more
graph while a TDV is open.
**** 2. relationship diffs that see relRepo
'compare_graphnodes' in [[file:../../server/git_ops/diff.rs][server/git_ops/diff.rs]] diffs 'members_of (contains)',
which is a list of IDs, so a relationship whose only change is its
relRepo is invisible to today's diff view. The diff report's
'relationship_diffs_for_pid' likewise compares sets of IDs. Your
"changed a relationship's skgrepo" needs a comparison at the level of

and it is equally cheap.

**** 8. a save rule for diff views: reconcile, at each node's visit
A TDV is saved like any other view: the save writes the graph edits,
and the collateral images of the touched nodes update as they do
today. Then the TDV buffer itself is reconciled, not rebuilt. The
pattern exists already: at each vognode's visit in the completion
pass ([[file:../../server/update_buffer/complete.rs][server/update_buffer/complete.rs]]), 'process_unrestrictedVognode_diff' recomputes
that node's diff facts from the diff data and adds or removes its
diff-only children. The TDV generalizes that visit: the node's
presence and change facts come from the graph pair, its changeset markers and
change folders are added when a change appears and removed when a
change disappears, its phantoms are re-derived, and its readiness
heralds are refreshed from the store. The roots and the editability of
the buffer stay as the saved buffer has them, so the user's
arrangement survives. One thing reconciliation cannot do is draw a
change that lies outside the buffer, such as a change that a merge or
a deletion causes in a node the buffer never showed. The save
response therefore counts the changes the buffer does not show,
reports that count, and suggests reopening the view. The old diff view's lesson
still stands: whatever the server renders must re-parse and save
cleanly, as the round-trip test in tests/git_diff_view/roundtrip/
checks.

**** 10. every herald's tier in the shared styles file
Your herald-coloring note asked for this. Today [[file:../../shared/herald-styles.json][shared/herald-styles.json]] defines
the ten styles, the relationship-herald tiers and the view faces, and
both clients build their faces from it at load time. But the tiers of
the non-relationship heralds ('☮', 'B', '⊥', '⟳', the labels, the

[[file:../../server/heralds.rs][server/heralds.rs]], as the 'HeraldStyle' argument of each rule, and a

You chose one source of truth over a conformance check, so this item
makes the file the only place that names a tier. The file gains a
'node_heralds' table that maps each styled atom of the rule table to
a style name: 'writeProtected', 'omittedBody', the false case of
'affectsParent', 'cycle', 'restrictedNode', the diff atoms, the
request atoms, 'relRepo', 'homeRepoHerald' and the folder labels. The
server embeds the file at compile time with 'include_str!' and parses
it once, so it needs no runtime path; the clients can read the file
from disk only because they live inside the repo. The rule table then
looks each tier up by atom name, and the 'HeraldStyle' enum goes
away, because the served rule sexp already carries style names, which
the clients map to faces. The conformance test gives way to an
internal check that every tier named anywhere in the file is one of
the file's own styles; that check can run both as a test and at
startup. The glyphs stay in Rust, because they are part of the view's

*** overarching goal : build a total diff view (TDV)
**** in brief
The total diff view will show all aspects (except order)
that have changed in the graph,
with enough context to understand them,
and a minimum of extraneous context.
(I'm saying "total" to distinguish it from the two extant
lesser implementations, the diff-view and the diff-report.)
It will let the user mark aspects of gnodes,
as well as whole gnodes, commit-ready.
**** "pruned change-spanning viewforest" (PCSVF)
A pruned change-spanning viewforest is built when the user
requests the total diff view.
The total diff view's purpose is to show all changes,
and all the context necessary to understand them,
with a minimum of other stuff.

Let C be the set of changes:
Each gnode that was changed, including new and deleted gnodes.
We trace each c in C containerward to find
the set R of "pseudo-root(s)" that contain it.
WHen tracing containerward to compute R,
we stop at any node that is multi-contained --
this is the sense in which the roots are pseudo.
Oh and also anything that is part of a cycle.
Tantivy already does something like this to define search rank.

If any r in R is within the contentward tree
from some other r' in R, then the view from r' will contain
the view from r. We should therefore define a second set D,
the 'deduplicated pseudo-roots' of the view,
which is R minus all such redundant values r.

From D we will build a contentward viewforest.
Each d in D will be a root of the viewforest.

In order to minimize unnecessary context, we
prune branches from the viewforest that would show no changes.
To compute the pruned view,
we build a set U of nodes to unfold contentward.
U starts with the union of R and C.
We then augment it by tracing each c in C contentward to R,
and adding every node from that path to U.

Once we know U, we can unfold the view contentward from D.
Every node reached contentward from D that is in U,
we draw writable. Every other node, we draw write-protected.

Every node in C, we draw not just writable,
but with its content foldered.
The other nodes in U do not need their content foldered.
However, by modifying a node (the total diff view can be saved,
just like any other skg view) the user can move that node
into the changed set C. When they do so,
the view should be redrawn to folder that node's content.

Even though this "total diff view"
is constructed using only the content relation,
it will still reveal changes to other relationships.
Each node that was changed will be drawn with
subscribee, overridden and hidden folders,
in the way already used for ordinary contentward views.
The only difference is that those folders will now
have diff heralds indicating new, deleted and modified nodes,
as described below.

The change-forest is the tree of everything commit-readiness can be
asked about, built from the graph pair and independent of any view;
it is distinct from the viewforest, which draws some of it. Its roots
are the changed graphnodes. Under each graphnode come its changed

changeset marker or a node is ready iff every one of its leaves that CAN be

propagation code and no invalidation code.

*** [Claude] yes: the report goes, and its vanished-node investigation becomes its own request
You asked in the terminal whether the vanished-node investigation
offers something uniquely valuable. It does, in one case. It is the
only feature that looks past HEAD into git history: for an ID that
some node lists but that no node answers to, it walks each skgrepo's
first-parent history and reports the commit where the file was last
present, the commit it vanished at, its title and relation lists then,
and every node that referred to it then, or that the ID was never
present at all. The TDV covers a node deleted since HEAD (it becomes a
historical phantom with its old text and content), but a reference
that already dangled at HEAD is invisible to both graphs of the pair,
and only the investigation can say whether it is a typo or a deleted
node, and what it was. The duplicate-ID bucket adds nothing, because
load, save and the before-graph build all run the same validation.

So slice 9 now retires the whole diff report (handler, renderer,
buckets, client commands, docs and tests), keeps 'vanished.rs' moved
into 'server/git_ops/', and gives it a request of its own, "investigate
unknown node", with a command in each client that takes the ID at
point from an unknown phantom; the delete-references preview names
that command. The plan describes it under "Investigating an unknown
node" and in slice 9.
