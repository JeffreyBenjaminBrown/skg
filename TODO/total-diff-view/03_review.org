** DONE Folding is lost on save
A context node's body refolds at every save, and the containerward
trees under changed-folder members are redrawn, so folding inside them
is lost too. After a commit, open TDV buffers are redrawn from scratch
rather than reconciled, so a fully committed buffer comes back empty,
and all its folding goes. (slices 6, 7, 8)
*** [Jeff] This cannot stand.
It's too much work, reconstructing the fold structure one was using
after every save. We need reconciliation. I imagine there are a lot
of decisions to be made about how to do that, which is why the agents
skipped it. Let's you and I handle them.
**** [Claude] agreed; here is what breaks, and the decisions
Folding already round-trips in ordinary views: before a save the
client writes '(folded)' and 'bodyFolded' into each headline's
metadata, the server parses them into the viewnode's 'folded' and
'body_folded' fields, reconciliation keeps the viewnode objects, and
the rendered buffer carries the facts back, so the client refolds.
The TDV loses folding in three places, and each is a specific bug
rather than a missing design: 'process_unrestrictedVognode_changes'
sets 'body_folded' on every visit, so a context body the user opened
refolds; 'attach_continuations_under_pair_folder_members' detaches
the continuation under each changed-folder member and redraws it, so
the new viewnodes have no fold state; and after a commit
'redraw_tdv_views' rebuilds each buffer from scratch, because a plain
reconcile keeps the roots and so could never empty a buffer. The
decisions below fix all three.
***** DONE Decision: the server never changes the fold state of an existing viewnode
Defaults apply only when a viewnode is created: a context node's body
starts folded, a container folder starts folded, everything else
starts open. After that the user's folding is law, even when a
context node becomes a changed node (its body stays as the user left
it). I see no case for the server refolding anything; the plan
assumes this.
***** DONE Decision: continuations are reconciled, not redrawn
The containerward trees and role trees under a changed folder's
members are reconciled like the folder's own members: existing
viewnodes are matched by (parent, skgid, kind), kept with their fold
state, and re-walked; nodes that vanished are removed; new ones are
appended. This reuses the goal-list reconciler the folders already
use. The cheap alternative, redraw and then copy fold flags across by
matching paths, gives the same visible result with less code but two
passes over every tree; I prefer the reconcile, and the plan assumes
it, with the copy as the fallback if the reconcile turns out to be
invasive.

The connection holds one graph pair: the before-graph, read from HEAD,
and the after-graph, which is the live graph. After a save the live
graph is a new object, so the pair's after-graph is stale.

temporary context and, by design ("which it does not replace", in
'rerender_all_views.rs'), never copies the refreshed pair back.

more, which costs one full comparison of them. Slice 7 copies the
refreshed pair back, as the save path does.
