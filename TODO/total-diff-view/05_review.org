* Decide: four small limitations worth fixing
** DONE Write-protecting the only editable instance of a changed node is silently undone
'skg-set-write-protected' (C-c s w; Neovim 'sw') puts 'writeProtected'
in a headline's metadata, and the save applies it. In an ordinary view
the node then stays write-protected there. In a TDV buffer, the save's
rerender runs the pre-pass before completion, and a node of U with no
editable occurrence left gets its BFS-first content occurrence made
editable again, often the very headline the user just marked. Nothing
tells the user. A node of U never has two editable occurrences, so
write-protecting one always removes the only one.

I would refuse the save with an explanation, as the other save
validations do, since letting it through would hide a change from the
view whose purpose is to show every change. The rule, checked on the
server after the saved buffer is parsed, since only the server knows U
and the stored view: a node of U that had an editable occurrence in
the stored view, has none in the saved buffer, still has that
occurrence in it, and carries no editable-view request on any
occurrence, refuses the save, naming the node and saying to request
another instance editable instead. The request clause keeps the
legitimate move (write-protect V, request W in the same save)
allowed. The cheaper alternative is to accept the save, let the
pre-pass re-promote, and send a completion warning that says so.
*** [Jeff] agreed, let's refuse
**** [Claude] into the follow-up plan
The refusal rule as written above, checked on the server after the
saved buffer is parsed, with the request clause that keeps a move of
editability allowed.
** DONE A request on a node of U does nothing, where the normal way would move or unfold editability
'visit_normal_node' removes 'ViewRequest::Editable' from any node of
U at its visit, and nothing follows. The agents read the plan's "a
node of U takes none of it" as "drop the request", which also keeps a
stale request from lingering in the headline's metadata. That makes
two things impossible that an ordinary view allows.

Moving editability. If V and W both show graphnode G, with V
editable, a request on W makes W editable and write-protects V: the
draw rule yields a default-editable occurrence to a requested one, and
defers only to another occurrence requested in the same completion
('apply_editable_draw_rule'). On the next rerender W stays editable,
because only an editable occurrence claims its ID in the editable map
('make_writeProtected_if_repeat_then_extend_editable_map'); a
write-protected first occurrence does not. In a TDV the request on W
is dropped, so G can be edited only at the occurrence the pre-pass
chose.

Unfolding. A request on an already-editable node hands the request to
its content children, so it means "unfold this subtree editable,
within the node limit". A node of U is editable with its members
outside U as write-protected leaves, so that is exactly what a user
would want from a request there; today they must request each member.

I would make a request on a node of U take the ordinary path: the
draw rule, which moves editability as above, then the cascade, with
the budget charged only for children outside U, since the node's own
expansion is the TDV's and free. One branch in 'visit_normal_node' and
two tests in 'tests/pcsvf/fresh_sets.rs': editability moves from V to
W and stays there across a save; a request on a node of U unfolds its
members within the limit. The pre-pass is unaffected, since it acts
only when a node of U has no editable occurrence at all. The plan's
pitfall "anything made editable must be the BFS-first occurrence" was
overstated, for the reason above; it did no harm, but a later plan
should not repeat it.
** DONE A changed node drawn only inside a folder counts as shown
The agents flagged this themselves (slice 5, "imperfect"). "Drawn" is
computed by 'nodes_drawn_in_viewforest', which counts every
unrestricted vognode in the buffer, including members of partner
folders. So a node of D whose only occurrence is, say, a container in
a container folder is not appended as a root, and the pre-pass (which
rightly considers only content occurrences) never makes it editable;
its change is not drawn, yet the unshown count does not count it. The
same function feeds that count. I would define "drawn" as "has an
editable occurrence, or is a historical phantom in content position",
and use that in both places; a change's decorations and gestures exist
only at an editable occurrence, so this is what "shown" has meant all
along. The pre-pass runs before completion and the new-roots step
after it, so an origin with a content occurrence is editable by then
and is not appended, while one with only folder occurrences is. Every
node of the fresh U is then reached: the top of its walk is an origin
that is either editable or appended, and each node below is drawn by
the editable node above it. It is a
small change in 'server/pcsvf.rs', with one test in
'tests/pcsvf/fresh_sets.rs'. The plan's wording ("no viewnode in the
buffer draws") invited the agents' reading, so this is a plan
correction, not a fault of theirs.

however it came to be, counts as drawn.

** The pre-pass makes only content occurrences editable
A folder member, a removed member and a historical phantom's old

** Unmarking asks before touching more than one leaf
The clients count the leaves a gesture would unmark by the axes of the
requests it writes (a member's '(node rel)' counts as two; a request
naming 'all' always counts as more than one), gather every request
first, and write all or nothing. In Emacs the prompt reads "Continue?
(yes or no)", since 'yes-or-no-p' appends its own suffix; Neovim shows
the agreed text and wants the typed word "yes" (slice 4).

* Sound: gap fills and corrections, no action needed
** A rebuild of the stores also empties the git snapshot cache
Dropping the straddle alone would not have made the next TDV request
read what the rebuild read: the before-graph's cache is keyed by the
owned skgrepos' HEAD commits, and the foreign skgrepos it holds were
read from their worktrees, so a foreign file edited before the rebuild
would have come back stale and entered C. The rebuild now empties that
cache too (slice 7). Only a rebuild that succeeds drops the straddle.

'PreparedRerenders' carries the refreshed straddle and

* The follow-up work, as decided here
Six items, small enough for one plan:
1. A save that write-protects the only editable instance of a node of
   U, without requesting another instance, is refused with an
   explanation (server-side rule above).
2. A request on a node of U takes the ordinary path: the draw rule
   moves editability, the cascade unfolds, the budget is charged only
   for children outside U.
3. "Drawn", for the unshown count and the new-roots step, means "has
   an editable occurrence, or is a historical phantom in content
   position". A node of U shown only write-protected gets one of those
   instances made editable, where it stands; a root is appended only
   for an origin with no instance at all (your decision in
   conversation, 2026-10-19).
4. 'tests/yaml-corpus/' is deleted.
5. 'collect_grandchild_aliases_for_viewnode' is deleted.
6. 'rand' leaves 'Cargo.toml'.

* Suggested first dogfood
1. Open the TDV on a worktree with a few uncommitted edits. Fold a
   context body, a change folder and a headline inside a
   containerward tree; save the buffer unchanged; everything should
   stay as you left it, and the buffer should be byte-identical.
2. In another buffer, edit a node the TDV shows only as a
   write-protected leaf, and save it. The TDV should rerender with
   that node editable and its change drawn, and the readiness summary
   should not count it as unshown.
3. Edit a node under no root of the TDV (a different content origin).
   On save, a new root should appear at the end.
4. Put an editable-view request on a write-protected member outside U
   and save; it should expand recursively until the node limit, and
   stay editable on the next save.
5. Mark a few leaves ready, then unmark a node recursively: the
   warning should appear, and "no" should change nothing.
6. Stage and commit. The roots should remain, as plain context, with
   their decorations gone; a deleted node's root should stand as a
   deleted phantom.
7. Rebuild the session-lifetime stores and reopen the TDV; nothing
   foreign should appear in C.
