** Scope
Six changes, three to the total diff view (TDV) and three deletions:
a save that would leave a changed node with no editable instance is
refused; an editable-view request behaves the same in every view,
which takes two old save rules away; a change counts as shown only
where it is editable; the YAML corpus check, a dead alias collector
and an unused dependency go.

** Vocabulary
The terms this plan relies on, one line each; 'docs/glossary.org' has
more.
- The TDV (total diff view) is up to four buffers that show the
  graph's uncommitted changes, HEAD against the worktree. The graph
  straddle ('GraphStraddle { before, after }') is what it compares.
- The sets of a buffer's PCSVF: C is the changed nodes, R the content
  origins the containerward walk reaches from C, D the deduplicated
  origins (the buffer's first roots), U the nodes to unfold
  contentward (C, R and the walks). The fresh sets are those
  recomputed from the refreshed straddle at a rerender
  ('pcsvf_sets_of_buffer'). The TDV's rule is that a node of U is
  editable at some occurrence, with its whole content list drawn.
- An occurrence of a graphnode is a viewnode that stands for it. A
  buffer has at most one editable occurrence of a node. A content
  occurrence is a root or a member of an unrestricted vognode's
  content; a folder occurrence is a member of a partner folder.
  Members of the subscribee and overridden folders can be editable
  ('FolderPolicy::EditableSet'); members of the other partner folders
  are write-protected by policy.
- The pre-pass ('make_freshU_editable_at_first_occurrences',
  'server/pcsvf.rs') runs before view completion of a TDV buffer and,
  for every node of the fresh U that has no editable occurrence, makes
  one occurrence editable: today the first content occurrence in level
  order, and none if the node has only folder occurrences. It never
  touches a node that has an editable occurrence.
- An editable-view request ('ViewRequest::Editable', the client's
  'editableView' metadata; 'skg-set-editable', C-c s d) asks for a
  write-protected occurrence to become the editable one. The draw rule
  ('apply_editable_draw_rule') grants it, write-protecting a
  default-editable occurrence elsewhere with its content subtree
  ('writeProtect_content_subtree'), and defers only to an occurrence
  that another request made editable in the same completion; the
  request then passes to the node's content children (the cascade),
  and the node budget ('initial_node_limit', charged once per
  expansion) bounds how far that goes. In a TDV the budget is charged
  only for request-driven expansions of nodes outside U. The save
  validates requests in 'validate_editable_view_requests'
  ('server/from_text/buffer_to_viewnodes/validate_tree.rs'), which
  today refuses a request on an editable node, a request on a node with
  content children, and two requests for the same node in one buffer;
  slice 2 deletes the first two rules and keeps the third.
- 'skg-set-write-protected' (C-c s w; Neovim 'sw') puts
  'writeProtected' in a headline's metadata; the save applies it. The
  server checks a saved buffer's write-protected occurrences against
  its last rendering in 'errors_and_normalize_new_writeProtected_occurrences'
  ('server/from_text/write_protected_edits.rs'), which returns
  'BufferValidationError's; any error refuses the save.
- "Drawn" (or "shown"), of a change: counted by
  'nodes_drawn_in_viewforest' ('server/pcsvf.rs'), which feeds the
  readiness summary's unshown count ('buffer_readiness_summary') and
  the new-roots step ('contentOrigins_missing_from_buffer').

* Agreed behavior
** A save may not leave a changed node without an editable instance
In a TDV buffer, a node of U always has an editable occurrence. A save
of a TDV buffer that write-protects the node's only editable
occurrence, and requests no other occurrence of the node editable, is
refused, with the other buffer validation errors, by a message that
names the node and says what to do instead:
"In a total diff view every changed node stays editable somewhere.
<title> (<id>) would have no editable instance left; to edit it
elsewhere, request another instance editable (C-c s d) instead of
write-protecting this one." The Neovim message names its binding. The
same save with an editable-view request on another occurrence of the
node is allowed: that is how editability moves. Ordinary views are
unaffected.
** An editable-view request behaves the same in every view, and two save rules go
A save no longer refuses an editable-view request because the node is
editable, nor because the node has content children. The one rule
that stays is that a buffer carries at most one editable-view request
per node (the other kinds of view request are not its concern). So, in
every view: a request on a write-protected occurrence makes it the
editable one, and the occurrence that was editable by default is
write-protected with its content subtree, which stays drawn; a request
on that write-protected occurrence later moves editability back, and
its drawn children are reconciled, not redrawn; a request on an
already editable node passes to its content children (the cascade), so
it means "unfold this subtree editable, within the node budget". The
children a user types under a write-protected occurrence in the same
save as a request are still refused, by the validator of edits to
write-protected occurrences, which is where that protection has lived
all along.

In a TDV the request takes this same path, and the node budget is
charged only for the expansion of a node outside U; a node of U is
never charged, whether the TDV's rule or a request made it editable.
So a request on an editable node of U makes its members outside U
editable, within the budget, and its members in U pass the request on.
The pre-pass is unchanged; it acts only when a node of U has no
editable occurrence at all.
** A change is shown where its node is editable
'nodes_drawn_in_viewforest' counts a node as drawn when the buffer has
an editable occurrence of it, wherever that sits (a content occurrence
or an editable folder member), or a historical phantom of it in
content position (under the buffer root or an unrestricted vognode).
A node of U that has occurrences but no editable one gets one of them
made editable by the pre-pass, where it stands: its first content
occurrence in level order if it has one, else its first folder
occurrence. An editable folder member stays editable at the folder's
later visits, whatever the folder's policy, and draws its content list
as the members of the subscribee folder already do. A root is appended
only for an origin of the fresh D with no occurrence at all; the
standing roots stay excluded from the appending, as today. So after a
rerender every node of the fresh U that has an occurrence is editable
somewhere.

* Pitfalls the slices must respect
** the draw rule write-protects the prior occurrence's whole subtree
'writeProtect_content_subtree' write-protects the default-editable
occurrence and every editable node under it, and removes them from
the editable map. In a TDV those may be nodes of U. They get their
editable occurrences back in the same completion: the newly editable
occurrence draws its content list, a created member registers afresh
in the map and is editable, and 'tag_content_members' leaves a member
of U editable. The test in slice 2 must show that every node of U
under the moved subtree is editable after the save, and again after a
save that changes nothing.
** the pre-pass runs before completion
It cannot see the draw rule write-protect an occurrence during
completion, and it must not undo that afterwards: a request is the
user's choice of occurrence. Slice 2 does not change the pre-pass;
slice 1 changes only which occurrence it picks.
** write-protected-set folders re-protect their members
A member of a container, mentioner, subscriber, overrider, hider,
hidden or acquired folder is drawn write-protected ('FolderPolicy::WriteProtectedSet'),
and the fixes run's log says an occurrence made editable there "would
not last", so some step at the folder's visit or the member's own
visit write-protects it again. Slice 1 finds that step and, in a TDV,
exempts a member that is already editable; members a visit creates are
write-protected as today.
** 'tag_content_members' leaves requests in place
Since the fixes plan it write-protects only a member outside U that
the visit created, and it never strips 'ViewRequest::Editable'. The
request reaches the member's own visit, where the draw rule consumes
it.
** typed children under a write-protected node are already refused
'errors_and_normalize_new_writeProtected_occurrences' compares each
write-protected occurrence of the saved buffer with the one at the
same parent path in the last rendering, and reports a changed content
list as an edit to a write-protected occurrence; children typed under
a write-protected occurrence the last rendering lacked are made
non-members. That is the protection the deleted "content children"
rule was for, and it stays. A write-protected occurrence whose drawn
children are unchanged (as after editability moved away from it) is
not an edit, so a request on it now passes.
** the validator matches occurrences by parent path and ID
'errors_and_normalize_new_writeProtected_occurrences' pairs each
write-protected occurrence of the saved buffer with the one at the
same parent path and ID in the server's last rendering. The new rule
needs the complement: a node whose last rendering had an editable
occurrence and whose saved buffer has none. The last rendering is the
stored viewforest ('views_state.open_views.viewid_to_view'), and the
buffer is a TDV buffer when 'tdv_buffer_of_view' says so; U comes from
the connection's straddle ('ViewsState::graph_straddle', refreshed by
'current_graph_straddle_in_slot') for that buffer.
** 'nodes_drawn_in_viewforest' runs after completion
Both callers use it after the buffer is completed, so an occurrence
the pre-pass or a request made editable counts. A deleted phantom
standing as a root is excluded from appending by the standing roots,
not by this function.
