* Decide: one bug worth a small follow-up
** TODO Write-protecting a drawn occurrence while requesting editability at another draws its children twice
The gesture: in a TDV buffer, n is drawn editable under x and
write-protected under y; the user puts 'writeProtected' on n under x
(C-c s w) and an editable-view request on n under y (C-c s d), and
saves. Slice 3 allows this save, rightly: it moves editability. But
the result shows n's children a and b twice under x. Two causes meet.

The first is in the save validator of write-protected occurrences
('errors_and_normalize_new_writeProtected_occurrences'). It pairs
each write-protected occurrence of the saved buffer with a
write-protected occurrence at the same path in the last rendering.
n under x was editable in the last rendering, so nothing pairs, the
occurrence counts as new, and its drawn children are made non-members
('make_direct_unrestricted_children_independent'), as if the user had
typed them under a write-protected headline. In an ordinary view that
is the whole effect: the children a and b turn into non-members under
n, which is already wrong, since they are n's real content. It only
went unnoticed because the gesture was rare.

The second is the editable-occurrences step (the step that, before
completion, makes sure every node of U has an editable occurrence).
Before completion, n has no editable occurrence (the one under x is
now write-protected, the one under y only carries a request), so the
step makes the first content occurrence, n under x, editable again.
Completion then draws n's
content list there, a and b as members, beside the two non-members
the validator left. The request on n under y then moves editability
there and write-protects n under x with everything under it, four
children where there were two.

The fix is two small changes:
(1) In the validator, an occurrence that
was editable at the same path in the last rendering and is
write-protected now is the same occurrence, not a new one; its
children stay members (the server's own move of editability keeps
them that way, through 'writeProtect_content_subtree'). (2) In the
editable-occurrences step, a node that has an occurrence carrying an
editable-view request is skipped, since the request will make that
occurrence editable; the user's choice should win over the default.

The first change alone ends the duplication; the second stops the
step from making n under x editable only for the request to
write-protect it again in the same completion. Tests:
the gesture in a TDV yields a and b once, as members, under a
write-protected n under x; the same gesture in an ordinary content
view keeps a and b as members. A plan for this is a page; say so and I
will write it.

**** DONE Why do we need to know if an occurrence is "the same" as one before saving?
***** [Claude] to tell drawn children from typed children
When a save arrives with a write-protected headline that has children
under it, the server has to decide what those children are. If the
server itself drew them there, as the node's content, they are
members and should stay so. If the user typed them under a
write-protected headline, they cannot become its content (a
write-protected occurrence accepts no edits), so the save turns them
into non-members rather than lose them. The buffer alone does not say
which; the server's last rendering of that buffer does. So the
validator looks for the same occurrence in the last rendering, by its
node and its path from the buffer root, and compares the two. If it
finds a counterpart whose children match, the children were drawn by
the server, and they stay members. If it finds a counterpart whose
children differ, the user has edited a write-protected occurrence,
and the save is refused. If it finds no counterpart, the occurrence
is new, the user typed its children, and the save makes them
non-members.

The bug is that it looks for counterparts only among the last
rendering's write-protected occurrences. An occurrence the user has
just write-protected by hand was editable in the last rendering, so
it finds no counterpart, treats the occurrence as new, and demotes
children the server drew. The fix widens the search to previously
editable occurrences at the same path; nothing else about the check
changes.
