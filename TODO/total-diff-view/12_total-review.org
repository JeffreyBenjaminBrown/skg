* How this was made
Five Opus 5.5 subagents each read the 104 commits between the merge
base with 'main' (68ceef04) and HEAD, one question group each, and

the rest. I read all five in full; you need not.

* The verdict in short
The core survived and is sound: the straddle, the change-forest, the
readiness store, the strand analysis, stage-and-commit, fold
preservation and the write-protect requests were each built once and
kept. Of the 22,613 lines the effort added, about 1,610 (7%) were
later rewritten for substance and 560 for renames; 21 of the 104
commits were reversals. Most of the substantive reversals trace to
three causes: a design the executing agent chose and you rejected
(about 530 lines), a requirement you changed with new information
(about 380), and a requirement the plan got wrong (about 280). Three
wrong beliefs of mine about the existing code cost one stopped run
and three rounds of the editability discussion.

What the effort left behind that needs work is not behavior but
shape: the TDV has no module of its own and sends readers to
superseded plans; a handful of terms mean two things ("drawn",
"leaf", "fresh", "origin") and one thing has five names (a home
move); the same removed relationship is encoded two ways; and the
glossary and API doc are stale in the places the effort added to
without rewriting. All of that is a housekeeping plan, not a redesign.

***** [Claude] the three drawings, and what a removed folder member is
First the term: there is no "removed folder". A removed folder member
is a member of a partner folder (a subscribee, a container, ...) whose
relationship exists only in the before-graph: a subscription you
dropped since HEAD, say. The diff view draws it in the folder so that
you can see the removal, with the fact '(diff rel-)'.

The three drawings of the before/after union:
1. Content under an editable node. The content list of the after-graph
   is reconciled first, as in any view. Then, for each member that
   only the before-graph lists, the per-visit step computes where it
   stood by the longest common subsequence of the two lists and
   inserts it there as a non-member marked 'rel-'
   ('reconcile_removed_content_members', 'phantom_insertion_plan'). A
   removed member therefore keeps its old place.
2. Partner folders. The folder's goal list over the straddle is the
   after-graph's members in their order, with the before-only members
   appended at the end ('GraphStraddle::partners'), each marked 'rel-';
   under a write-protected-set folder they are drawn as members, under
   an editable-set folder as non-members (the encoding split of the
   item above). A removed member therefore goes last.
3. The alias, ID and flags folders. Their entries are not nodes, so
   the per-visit step computes a signed union over the LCS of the two
   lists and draws a removed entry as its own kind ('RemovedAlias',
   'RemovedID') at the LCS position.
So content keeps the old position, folders push removals to the end,
and property folders interleave by LCS. The old diff view interleaved
folders by LCS too; the diff view dropped that. Either make folders
interleave again (the LCS code exists in 'changes.rs') or state the
difference in the glossary; I would do the former, since a removal
shown in place is what the content drawing already taught the user.

***** ONGOING [Claude] the two reconcilers
'complete_relevant_children' ('server/update_buffer/util.rs') is the
older, generic one. It takes a parent, a predicate that says which of
its children are "relevant" (for a content list, the members; for a
folder, its members), a way to read each relevant child's key, a goal
list of keys computed from the graph, and a constructor for a missing
key. It partitions the children into relevant and irrelevant, detaches
duplicates among the relevant, offers each stale relevant child (one
whose key is not in the goal list) to a callback that may keep it as
a non-member ("demote a branch rather than discard the user's
subtree") or let it be detached, creates children for the keys that
no child matches, and reorders: irrelevant children first, then the
relevant ones in goal-list order. It returns a summary of what it
created, kept as non-member, and detached, which the folder code
turns into repair warnings. Context: it runs at every editable node's
visit for the content list, and at every folder's visit, in every
kind of view.

'reconcile_children_with_fresh_drawing' ('server/to_org/render/fresh_drawing.rs')
is the diff view's. It takes a parent, a scratch tree (the fresh
drawing of what the parent's change viewnodes should be), a predicate
for the children it manages (the change viewnodes: old text, markers,
change folders, removed members, historical phantoms), and a
predicate for which matched children to descend into. For each child
of the fresh parent it finds the managed child with the same match
key (kind, or kind plus node, or kind plus entry), copies the fresh
facts onto it keeping its fold state, recurses where asked, and
otherwise copies the fresh subtree in; every managed child that
nothing matched is detached, never kept. It returns the kept and
created children in the fresh drawing's order and leaves their
placement among the other children to the caller. Context: it runs
at every editable node's visit in a diff-view buffer, after the
generic one has reconciled the content list, and at a historical
phantom's visit.

The two differ where it matters: the older one keeps a stale child
as the user's own (a subtree the user built under a member that is
no longer content), the newer one drops a stale child because every
child it manages was drawn by the server and the fresh drawing is
the truth. Merging them would force one rule on both. A comment at
the visit, saying which runs when and why they differ, is the right
fix.

2. Descent. The older touches a parent's direct children only. The
   newer, where it descends, treats every keyed viewnode of the

   child's facts to that child's own visit.

older one obeys: a reconciler detaches only what it drew, and what
the user added survives. Concretely:
- Descent: within a descended subtree, a vognode that is not a
  managed kind and carries no '(diff ...)' fact is the user's and is
  left where it stands. That settles the phantom's content and the
  acquired folder.
- Staleness: a stale managed viewnode with a child of the user's
  under it gets the older reconciler's treatment, lifted into one
  function both call: a vognode survives as a plain non-member
  occurrence of its node, with its diff facts cleared; a property or
  a folder is deadened, so that the orphan pass keeps its children;
  a stale viewnode with nothing of the user's under it is detached,
  as today.
- The member role tree is the one place these rules cannot reach:
  its unchanged nodes carry no diff fact, and the role a graft was
  born with ('Birth::RoleGraft') is not written into the buffer, so
  after a save the server cannot tell a graft from the user's note.
  The proper fix writes the role into the metadata and parses it
  back, which costs the serializer and the parser a field and asks
  both clients to carry the atom through a save; the cheap one
  redraws a member's role tree only when the member has none yet,
  which leaves a role tree stale after later edits. I recommend the
  proper one. Say which.

***** TODO [Claude] cargo's two builds
Cargo builds a Rust program in one of two profiles. The dev profile,
which 'cargo run' and 'cargo build' use by default, compiles fast, with
no optimization and with debug checks on; it is for development. The
release profile ('cargo run --release', 'cargo build --release')
optimizes the code, which takes minutes to compile and runs three to
four times faster here. 'bash/start-servers.sh' starts the server with
'cargo watch -x "run ..."', so you have been running the dev build.
Passing '--release' inside that quoted command ('cargo watch -x "run
--release ..."') runs the optimized build and keeps the
rebuild-on-save loop; the first build is slower and every later one
only recompiles what changed. A flag on the script to choose would do.
