* DONE [Claude] Is detaching important?
Yes, in four places; elsewhere the code already converts. This
document answers the question you asked under "S1" in
'16_review.org': "I'm thinking let's just never detach. Not even
in the old reconciler. Is there any situation in which detaching
is critical?" It rests on two read-only surveys of the server,
the tests, the docs and the git history, and on three throwaway
runs that exercised the cases a reading could not settle. Section
"Evidence" says which claims were run and which were only read.

The short answer. The server detaches a viewnode in eight sites.
Four of them are critical: a reconciler that never detached would
leak private structure, would read a stale alias or ID back into
the graph, would have the save refuse the buffer over a
duplicate, and would keep showing content a subscriber asked to
hide. In the other four sites "never detach" is possible, and in
most of them the code converts already: a stale viewnode with
anything under it becomes a non-member or a dead viewnode, a
deleted node a deleted phantom, a restricted node an anonymous
placeholder. What "never detach" would add there is clutter that
nothing ever removes, a budget drain, and a change to sixteen
tests and two docs. The runs also found two bugs that have
nothing to do with the question and are recorded in
'TODO/problems.org': a folder member kept for a note under it is
duplicated when its membership returns, and a deleted private
node keeps its text after a restricting switch. The
simplification I recommend instead is one rule, stated in one
place, with one predicate for both reconcilers; it is at the end.

* Terms
** most of them
A buffer shows a tree of headlines. The server keeps that tree as
the buffer's viewforest, whose nodes are viewnodes. A viewnode
that stands for a node of the graph is an occurrence of that
node; it is editable or write-protected. An occurrence under
another occurrence is a member of it when the parent's content
list holds it ('affectsParent' true) and a non-member otherwise
('(affectsParent false)', herald '⊥'): a non-member is shown
there but the save does not read it into the parent's list. A
folder is a viewnode that lists the nodes in one relationship
with the node it is drawn under (its viewparent): "These contain
it", "It subscribes to these", the alias folder, the ID folder,
the flags folder. A folder's members are its entries. A role
graft is an occurrence the server draws in a role tree, born
'RoleGraft'. A phantom stands for a node the buffer cannot show
as itself: deleted (a node a save deleted), unknown (an ID that
resolves to nothing), historical (the diff view's image of a node
HEAD has and the worktree lacks). A dead viewnode is a viewnode
kept only because something of the user's stands under it; its
herald reads "DELETED". A restricted vognode is the anonymous
placeholder for a node of a restricted skgrepo; it has no title
and no body. A change viewnode is one the diff view adds to show
a change: a removed member, a historical phantom, a changeset
marker, an old text.

A reconciler is the pass that, at a viewnode's visit, makes its
children match the model, what should stand there now. It creates
what the model has and the children lack, keeps a child the model
still has (updating its kind and facts in place), and decides
what to do with a stale child, one it manages that the model no
longer has, and with a duplicate, a second child with a key a
sibling has. To detach a child is to remove it and its subtree
from the viewforest. To convert it is to keep it under a kind the
buffer can show truthfully: a non-member, a dead viewnode, a
deleted phantom, a restricted vognode.

A child's key is what a reconciler matches it by: for an
occurrence of a graph node (a member, a removed member, a folder
member, a historical phantom) the node's ID as the live graph
resolves it, so that an occurrence shown by an extra ID still
matches its node; for an entry of a property folder the entry
itself, the alias text or the ID string; for any other viewnode
its kind, since a parent holds at most one old text, one marker
of a kind and one folder of a kind. Within one parent each key
appears at most once; the older reconciler calls the same thing
the goal item's key.

Two reconcilers run. The older one, 'complete_managed_children'
in 'server/update_buffer/util.rs', runs in every view, for
content lists and for every folder. The diff view's,
'reconcile_children_with_shallowModelSubtree' in
'server/diff_view/shallow_model_subtree.rs', runs for the change
viewnodes under a vognode, for the member role trees under a
changed folder's members, and for the old content of a historical
phantom. Both ask one question of a stale child before detaching
it: does something of the user's stand below it? The older one
answers "any child does", since it creates its children without
subtrees. The diff view's asks 'is_the_users_viewnode': an
unrestricted vognode born 'Unremarkable', unsigned, and not a
member of the folder it stands in.

** What a "key" is
A key is what a reconciler matches children by. Each child of a
viewnode has one. The reconciler pairs an existing child with the
model's child that has the same key. A child whose key has no
match in the model is stale. A second child with a key a sibling
already has is a duplicate.

What the key is depends on what the child stands for.
*** An occurrence of a graph node
A member, a removed member, a folder member or a historical
phantom has as its key the node's ID, as the live graph resolves
it, so that an occurrence shown by an extra ID still matches its
node.
*** An entry of a property folder
An alias, an ID or a flag has as its key the entry itself: the
alias text or the ID string.
*** Any other viewnode
An old text, a changeset marker of one kind or a folder of one
kind has as its key its kind, since a parent holds at most one of
each.
*** The rule the duplicate detach enforces
Within one parent each key appears at most once. The older
reconciler calls the same thing the goal item's key.
* Where the server detaches today
Each subheadline is one site. "Leaf" means a viewnode with no
children.

Nothing else removes a viewnode. Hoist writes disk; nodeMerge
rewrites viewnodes in place; delete-node converts to a deleted
phantom; "delete references to absent node" rewrites disk and
rerenders; the pruned change view's sets are graph sets and
remove no viewnode; a restricted vognode is never removed by an
ordinary rerender.

**** [Claude] agreed, with one line drawn
Identity comes from the vid; the warrant comes from the graph. A
reconciler answers two questions about a child. Which viewnode is
this? And does the graph still warrant it here, as what? Today
one key answers both, and badly for the first: two occurrences of
one node under one parent are indistinguishable, so the second is
detached with its subtree. A vid answers the first question
completely. It cannot answer the second, because the model a
reconciler builds comes fresh from the graph and has no vids;
whether an alias entry, a member or a marker should still stand
is a fact about the graph, looked up by the node's ID, the alias
text or the kind. So the keys stay as the lookup from a graph
item to the child that stands for it, but they stop deciding
ownership: today a reconciler infers "mine" from shape (birth,
sign, flag, kind), and the first throwaway run showed that
inference reading drawn content as yours. With vids the server
records, at creation, which reconciler made each viewnode, and
"mine" is a lookup. That record is what retires
'is_the_users_viewnode', 'holds_the_users' and
'detach_the_servers_below', and it ends the bug run 3 saw where a
kept stale graft loses its birth and reads as yours forever.

The scheme, with your later note: lowercase letters and digits,
so two characters cover 1,296 viewnodes and a third is almost
never needed; assigned at creation, never reused within the
buffer's life; '(vid xx)' on every headline, folders and
properties included. Nothing identifies a viewnode today: an
ego_tree 'NodeId' tracks buffer position after a parse, and every
state that survives a save rides in an atom ('folded',
'affectsParent', 'writeProtected', 'birth roleGraft', the diff
facts). So the vid rides the same way: the printer writes it, the
parser reads it, and the server keeps per view a table from vid
to what it knows (owner, graph key, birth). A headline without a
vid is one you typed; it gets one at the next render. Two
headlines with one vid (a copy) keep it on the first in buffer
order and give the second a fresh one. A vid that moved is a
move, so fold state and facts follow it.

What it costs. The parser treats an unknown atom as a hard error,
so the atom needs parser and printer support, a 'vac' herald rule
and the regenerated rules fixture; the clients need nothing,
since both hide the whole '(skg ...)' sexp and look atoms up by
name. The real cost is the tests: 1,541 '(skg' literals in the
Rust tests, 488 in the Emacs tests, 437 in the Neovim tests and
about 200 in the integration tests. Many are parser inputs, which
need no vid; the expected-output literals change, unless the
comparison helpers strip '(vid ...)' before comparing, as
'assert_metadata_eq!' already ignores atom order. I would add
that stripping and print the atom last in the form, so that
substring asserts like "(node (id x) " keep matching. The round-
trip tests hold as long as a parsed vid is preserved, which is
the design.

* What "never detach" would mean at each site
Each subsection takes one site, says what the kept viewnode would
have to become, and what the code downstream does with it. The
evidence is the surveys unless a run is named.
** a1, a stale content leaf: possible, with costs
A stale member that is a leaf would become a non-member, as a
stale branch does today. The parser accepts a non-member under a
vognode. Three things change. The leftover takes an editable
claim: the completion orders non-members ahead of members and
gives editability to the first occurrence in level order, so a
stale '⊥' copy can make the real member write-protected (the run
saw the kept x "still editable"). The leftover spends budget: an
editable non-member extends its content and is charged, so
leftovers push later nodes into write-protection. And the
leftover reads as the user's to every later pass, so nothing ever
removes it; only you can, by deleting the line (run 2, case C:
the deletion sticks and no file changes). Two tests assert the
leaf goes: the collateral break-cycle integration test ("because
complete_managed_children discards children not in the parent's
goal_list") and your 2026-06-04 ruling that "a stale LEAF is
deleted uniformly -- including a user-added extra leaf under an
editable subscribee (no carve-out)", pinned by two tests in
'tests/hidden_from_subscriptions.rs' that end "should be deleted,
not preserved".
** a1, a stale folder leaf: possible, with a trap
Keeping it is possible in a write-protected folder. A stale
member of a partner folder is a node that no longer stands in the
folder's relationship. Kept as a non-member it passes the parser
and the write-protected checks, which exclude non-members. The
trap: the folder's distinctness check at save,
'partnerFolder_children_have_distinct_skgids', counts every
unrestricted child, members or not. If the membership later
returns, the goal has the key again; whether the kept non-member
is adopted back ('mark_goal_children_as_folder_members') or a
second member is created beside it decides whether the next save
is refused. The third throwaway run exercises exactly this (case
F, below). The regression test
'tests/collateral_subscribee_staleness.rs' exists because a
collateral subscribee folder once kept stale members, and the fix
was to drop them.
** a1, a stale entry of an alias, ID or flags folder: critical
These folders are save inputs: the save reads the node's aliases,
IDs and flags from them. A stale alias entry kept as it is would
be read back, and the alias removed elsewhere would be re-added
at the next save of this buffer. A dead viewnode is not an
escape: the parser rejects a dead viewnode inside every folder
kind. The one save-inert form that exists is the diff view's
'removedAlias' and 'removedID', which "Saving reads no alias from
it and does not count it among the node's IDs". So a stale
property entry must be detached, or converted to a kind the save
ignores, which ordinary views do not have today.
** a2, a member leaf under an orphaned folder: same as a1
The folder's viewparent became a phantom, a restricted vognode or
a dead viewnode; the folder is deadened and its member leaves go.
Kept, they would be non-members under a dead folder, which the
parser accepts.
** b, duplicates in content: possible only in one form
Keeping them is possible only as write-protected non-members. Run
2 settled this (cases A, A2, B, B2). Two member children with one
ID under an editable parent refuse the save:
"UnrestrictedVognode's non-ignored content children must be
unique (no two sharing the same ID)", and, when both are
editable, "Multiple occurrences of node ID are editable". A copy
marked write-protected alone is still refused; a copy marked
non-member alone is refused as a second editable occurrence; a
copy marked both is accepted, with no warning and no file change,
and the rerender moves it ahead of the members. So a reconciler
that kept a duplicate would have to set both flags, and the kept
copy would then sort first.
** b, duplicates in a folder: critical
The folder's distinctness check counts every unrestricted child,
so a duplicate in a write-protected or hidden folder cannot be
kept in any form the save accepts; the validator would have to
change to count members only, as the content check does.
** c1 and c2, the diff view's spent change viewnodes: possible
Keeping them is possible, at a price in clutter. After a commit
every change is history. A changeset marker, an old text, a
changed folder and a historical phantom whose node is in neither
graph would become dead viewnodes, each reading "DELETED", or
would keep their facts, which are then false ('~-' on a
relationship both graphs have). Five tests assert that none of
'(diff ', 'changed)', 'changesetMarker', 'oldText', 'historical',
'homeSkgrepoMove' and '(ready' remains after a commit; two
integration tests assert the same. The first throwaway run showed
what already stays: a removed member with drawn content survives
the commit as a parked non-member, because the predicate reads
its drawn content as the user's; a deleted root stays as a
deleted phantom, by design ("the user should still see a deleted
root").
** d, the skgrepo-set switch: critical
When the restriction narrows, unrestricted vognodes of a now
restricted skgrepo are converted to restricted vognodes, which
show nothing but the atom 'restrictedNode', and restricted leaves
are pruned. Keeping the leaves would leak that a hidden member
exists, where it stands and how many there are, which a fresh
render under the same restriction withholds; the code already
treats "would leak that a hidden node vanished" as a reason not
to flip a restricted node to a deleted placeholder. The same
holds for a content member whose membership is recorded in a
restricted skgrepo while both nodes are public ("the private
reading-list case"): a stale leaf there, kept as a titled '⊥'
under its container, would reveal the private membership. The
third run tests a related leak (case G).
** e, the prune of empty containers: clutter only
A childless dead viewnode, deleted phantom, write-protected
partner folder or hidden folder is removed after every
completion. Kept, each is a line reading "DELETED" or an empty
folder; the parser accepts them. One test calls an empty
write-protected folder "just noise" and asserts its removal.
** f, ID folders outside the diff view: a side finding
It is a side finding, not a policy. Every rerender outside the
diff view removes every ID folder, since only the diff view draws
one. The parser lets a non-member sit under an ID folder, so a
note you park there in a diff-view buffer would be lost if that
buffer were ever rerendered as an ordinary view; this is a
leftover to fix, not a detach to keep.
** The hidden content of a subscribee: critical
Your 2026-06-04 ruling named one more case where a stale member
"must be REMOVED, not demoted (else a node stays wrongly

hides belongs in the "It contains these, but the subscribing
ancestor hides them" folder and nowhere else. Kept under the
subscribee as a non-member, it would show what the subscriber
asked not to see.

*** [Claude] the simplest rule
Convert what you own, then prune dead leaves. In one sentence: a
reconciler never detaches; a child it owns that the graph no
longer warrants is converted, and after every completion a
postorder prune detaches dead leaves.

Spelled out, with each word defined. A reconciler owns the
children it created; with vids that is a record, and until then
the managed predicates stand in. The graph warrants a child when
the model built from the graph has an item with the child's key;
a second child with the same key is unwarranted, and the copy
kept is the writable one, else the first. To convert is to make a
vognode leaf and every non-vognode a dead viewnode, and a vognode
with a subtree a write-protected non-member, which keeps its
title and ID, extends nothing, holds no claim and can be adopted
back when its membership returns. The prune is the existing
'prune_self_deletable_when_empty': postorder, so a chain of dead
leaves collapses in one completion, before the buffer is
rendered; it never prunes a root.

What follows from it. Privacy needs no exception: a restricted
leaf dies and is pruned at once, and a restricted subtree is the
anonymous placeholder, as today. The alias, ID and flags folders
need none: a stale entry is a leaf, dies and is pruned before the
save could read it. Duplicates need none: the extra copy dies if
a leaf and is otherwise a write-protected non-member, the one
form the save accepts. Hidden content under a subscribee dies if
a leaf; with a subtree it would be a titled non-member, so if
hiding must be strict that one case deadens the vognode instead,
and its title goes. Nothing asks whether a viewnode is yours:
what you typed is owned by no reconciler, so it is never
converted, and it holds its ancestors alive; everything the
server made and no longer warrants collapses to the nearest live
thing.

What goes: 'is_the_users_viewnode', 'holds_the_users',
'detach_the_servers_below', the two branches of
