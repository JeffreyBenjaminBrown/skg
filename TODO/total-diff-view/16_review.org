**** [Claude] three signs for the node, two for the relationship
The mixing you suspect is real. A node's headline can carry one
node sign and one relationship sign. The node sign says what
happened to the node: '∃+' (new since HEAD), '∃-' (deleted) or
'M' (it exists in both graphs and records a leaf beyond its
existence: its text, a property, a content relationship). The
relationship sign says what happened to the relationship between
the node and the node it hangs under: '~+' (new) or '~-'
(removed). So "the other two signs" are '∃+' and '∃-'. They
cannot be confused with 'M' on one headline, since a node is new,
deleted or modified and never two of those: a new or deleted node
records only its existence leaf. But you are right that one slot
holds two kinds of fact. Your "aha!" item below proposes
separating them; my evaluation is there.
** A removed member is editable

**** [Claude] it works, with a surprise in the order
Editing the membership flag is the clean undo. Pasting C's id
under B ('C-c o n') writes a write-protected occurrence, because
a writable occurrence of C, the removed member, is already in the
buffer ('skg--insert-node-from-entry' in
'elisp/skg-id-search.el'; Neovim's 'linkstack.lua' does the
same). The save accepts it: the one-editable-occurrence check
counts only editable occurrences, the distinct-children check
counts only members, and B's new content list is read from its
member children, so B contains C again.

The rerender then holds two children of B standing for C, both
members now ('align_content_members_with_straddle' makes a
removed member whose relationship is back a member). The content
reconciler keeps the first in buffer order and detaches the other
with its subtree ('complete_managed_children' in
'server/update_buffer/util.rs': "Duplicates are redundant: always
detach"). Pasted below the removed member, the paste is detached,
and the removed member, now a plain member, keeps C's content and
stays editable; pasted above it, the editable removed member and
everything under it are detached and the write-protected paste
survives. So the gesture works, and which copy survives depends
on where you pasted.

The clean undo is one edit of the removed member: open its
metadata ('C-c v m'), cycle 'affectsParent' from "false" to "true
(default)" ('S-<right>') and apply, or delete the '(affectsParent
false)' atom by hand. The save then lists C in B's content, and
the rerender keeps the one occurrence. No test covers either
route, and no command does the flag edit in one key. I recommend
two things for the next plan: a command on a removed member that
restores the relationship (the flag edit, under 'C-c s' beside
the other membership commands), documented beside C-c r u; and
the duplicate rule preferring an editable occurrence over a
write-protected one, so the paste works whatever the order.

****** [Claude] yes, in folders too, by a request
The save acts on the request; the flag edit works only where the
container is editable. The name is good. Two facts decide the
design. The flag edit works wherever the container's occurrence

request, '(restoreRequest)', as the last part of the headline's

******** [Claude] the code never asks for an ancestor
It reads the folder's kind, and the folder in your picture is a
filter folder the diff view signs nothing in. Terms first. A
folder's viewparent is the node the folder is drawn under (the
glossary's word; the code calls it the folder's anchor). A
partner folder of one kind lists the nodes in one relationship
with its viewparent, and the kind fixes the direction: "These
contain it" lists the containers of the viewparent, "It
subscribes to these" the subscribees of the viewparent. The
relationship a member stands in is therefore defined by the
folder's kind and the folder's viewparent, never by the member's
nearest vognode ancestor. The save computes it that way already
for a readiness request: 'relationship_to_viewparent'
('server/diff_view/readiness_requests.rs') returns the relation,
the recorder and the member, and the restore request would call
the same function. "Nearest ancestor-partner" is my phrase from
above as much as yours; the plan would say "the folder's
viewparent" instead.

Your picture is the one place where two relationships meet. The
folder under E inside R's subscribees, "It contains these, but
the subscribing ancestor hides them", lists E's content that R
hides; its members stand in two relationships at once, E contains
C and R hides C, and R is four generations up. The code treats
it, and the similar "The subscriber ancestor hides these, but
subscribes to nothing that contains them", as filter folders:

content. So the danger does not arise, and the plan would say so

folder member concerns the relationship, of the folder's kind,
between the member and the folder's viewparent; the filter
folders carry none. One trap for the plan's agents: several
parameters named 'recorder_pid' hold the folder's viewparent,
which for a containers folder is not the recorder; they should be

****** [Claude] the older reconciler's rule
The older reconciler keeps any stale child that has children. The
older reconciler rebuilds a folder's members from the folder's
goal list at the folder's visit. A managed child whose node the
goal list no longer names is stale. That reconciler never looks
below the children it manages, since it created them without
subtrees; so it reads any child of a stale child as something you
added, and keeps such a stale child rather than detach it: an

that rule and asks its predicate instead. That difference is what
the glossary entry should state. It is also the root of a doubt I
