The review's "converts" misled you; nothing is deadened. The

**** DONE [Claude] what skips, and how stable the vids are
The skipping is the server's, in 'take_next_vid'
('server/types/views_state.rs'). It draws the next counter value
as a base-36 string, and if Rust's float parser accepts that
string it draws again. Over the alphabet of digits and lowercase
letters that drops the all-digit strings ('05', '10'), the forms
digits-e-digits ('1e5'), and 'inf', 'nan' and 'infinity'. The
reason is the readers. An agent ran all three: the Rust sexp
crate, Emacs's 'read' and the Neovim parser each turn '05' into
the number 5 and '1e5' into 100000, so a vid spelled that way
would come back from the client respelled. 'inf' and 'nan' matter
to the Rust reader alone, and would first come up at counters
24,171 and 30,191. Two characters give 1,296 strings, of which
the 100 all-digit ones are skipped, so 1,196 vids; the first is
'0a' and the first three-character one is '10a'.

Your rule holds, and a throwaway test ran it. Over a content view
with ten viewnodes: a typed child saved gets the old maximum plus
one, and every other vid is kept; a folder request, a role-tree
request and the rerender-all request keep every vid and give
fresh ones only to what they add; deleting a subtree retires its
vids, and the next new child does not reuse them, since the
counter never decreases. A copy of a headline keeps the vid on
the copy that comes first in buffer order and gives the other a
fresh one.

***** [Claude] what it holds, and why one entry is enough
The diff view's before-graph is HEAD's graph. To build it the
server reads every owned skgrepo's files as they stand at HEAD,
out of git, parses them, and composes a snapshot; at 20,000 nodes
that read costs about a tenth of a second per skgrepo. The cache,

snapshot keyed by the HEAD it came from, so that when the
straddle has to be built again for the same HEAD, as when you
close the last diff view and later open one, the git read is
skipped and only the graph is rebuilt from the snapshot. Nothing
removes an entry but the rebuild of the session's stores, so a
long session that commits often holds one snapshot per HEAD it
has seen, each the whole parsed content of your owned skgrepos,
though only the current HEAD's is ever used again. Evicting all
but the current one costs nothing and bounds the memory to one
snapshot.
