* Vocabulary
Every term below is used in the plan, and each gets a glossary entry in
slice 9.

** TDV, PCSVF
The TDV is the total diff view: four buffers that show every change
in the owned skgrepos since the last commits, with the context needed
to understand them. The PCSVF ("pruned change-spanning viewforest";
type 'PCSVF', functions 'pcsvf_...') is the viewforest that the "all
changes" buffer draws, and the merges and skgrepo-changes buffers draw
PCSVFs over subsets of the changes.

** graph pair, before-graph, after-graph, union walk, presence
The graph pair is 'GraphPair { before, after }': the before-graph is an
'InRustGraph' built from each skgrepo's HEAD; the after-graph is the
live graph. The union walk is the API over the pair that answers
questions about the union of the two graphs; each node and each
relationship it reports carries a presence: 'Both', 'OnlyBefore' or
'OnlyAfter'.

** C, R, U, D, content origin
C is the set of changed graphnodes (rightward and leftward changes;
see "the PCSVF"). R is the set of content origins reached from C by
walking containerward: a content origin is a node with no container, a
multiply-contained node, or a member of a rootlike cycle (the stop rule
of 'server/prominence.rs'; "origin" in code, "content origin" wherever
the term is introduced and in user-facing text). U is the set of nodes
to unfold: R, C and every node on a containerward path from a c in C
to an origin. D is R minus the origins that another kept origin reaches
containerward inside U.

** change-forest, change-forest leaf
The change-forest is the tree of everything commit-readiness can be
asked about, built from the graph pair, independent of any view
(type 'ChangeForest'). Its roots are the changed graphnodes; under each
come its changed aspects; its leaves, the change-forest leaves, are the
individual changes a user marks.

** mark, fingerprint, readiness, derived commit-readiness aggregate
A mark says that one change-forest leaf is commit-ready. It is stored
with a fingerprint of the change it approved, and a mark whose
fingerprint no longer matches counts as absent. An aggregate (a folder,
a changeset marker, a node, a file, the whole changeset) is ready iff
every one of its leaves that CAN be ready is ready; that derived value
is its derived commit-readiness aggregate, or "its readiness" where
the context is clear.

** changeset marker
A changeset marker is a childless property viewnode
('Property::ChangesetMarker') that stands for a set of changes
recorded in its parent's files and carries their derived readiness.
Three kinds exist: the content changeset marker ("its content
changed"), the relRepo changeset marker ("some content relationships
changed skgrepo") and the order-only marker ("order-only change",
which is always ready).

** readiness summary, gesture, readiness request
The readiness summary is the line the client shows after every save of
a TDV buffer: "12 of 14 changed files are ready", or "COMMIT READY.
All 14 of 14 changed files are ready." A gesture is a client command
that writes readiness requests on one or many headlines; a readiness
request is a metadata form that the save consumes to set or clear
marks.

** in, out, "(this file)", "(other files)"
A relationship is out from its recorder (the node whose file records
it) and in to its member. A folder of out-relationships is labelled
"... (this file)"; a folder of in-relationships is labelled "... (other
files)". Changeset markers carry no suffix.

** unknown node, dangling ID
An unknown node is an ID that some node's contains, subscribesTo,
hidesFromSubs or overrides list names but that no node of the graph
answers to, as primary or extra ID; such an ID is dangling. A view
draws it as an unknown phantom ("Parent references unknown node").

* Agreed behavior
** One command, four buffers
One client command ('skg-diff-view' in Emacs, ':SkgDiffView' or the
Lua equivalent in Neovim) opens up to four buffers, in the order below,
and skips any that would be empty. The client sends one request per
buffer; the server answers each with a buffer or with an empty reply,
which the client does not open. Each buffer is an ordinary registered
view ('OpenViews', a client-generated view id), so saves and collateral
rerenders reach it.
*** "diff-view: all changes"
It draws the PCSVF over all of C.
*** "diff-view: merges"
It draws a PCSVF over the nodes involved in nodeMerges: for each
deleted pid that a surviving node lists as an extra ID, the acquiree,
the acquirer and the acquiree's text preserver.
*** "diff-view: skgrepo changes"
It draws a PCSVF over the nodes whose home skgrepo changed.
*** "diff-view: order-only changes"
It is a flat list of the nodes whose file changed but whose
change-forest has no leaf (the only change is the order of a list),
each with an order-only marker under it.

** Refusals
The request is refused unless the skgrepo restriction is 'all' (the
refusal text the old diff-mode toggle used), and if any owned skgrepo
is not a gitrepo or has no HEAD commit. A merge commit at HEAD is not
a reason to refuse (slice 0 removes that refusal). Foreign skgrepos
are excluded from C, from the change-forest and from readiness; the
readiness summary reports their changed-file count.

** No stages
The TDV compares HEAD with the worktree. The index never enters: the
graph pair's before endpoint is HEAD, the atoms carry no stage, and
the stage-and-commit command stages everything before it commits. The
old view's per-stage machinery goes with the old view (slice 9).

** The PCSVF
*** C
C is the union of the rightward set (every node with a change recorded
in its own files: text, aliases, extra IDs, flags, home skgrepo; any
member of its contains, subscribesTo, overrides or hidesFromSubs lists;
any relRepo of those; and every new or deleted node) and the leftward
set (every node whose set of containers, mentioners, subscribers,
overriders or hiders changed). Both come from the union walk. Order
changes do not put a node in C.
*** R, U, D
R: from each c in C walk containerward through the union graph until a
content origin; collect the origins. Reuse the stop rule of
'find_roots_and_multiply_contained' and 'extend_regions_for_cycles'
('server/prominence.rs'), lifted to run over the union walk's
'partners' rather than 'contained_by'. A changed node that is itself an
origin is its own root. U is R, C and every node on those walks. D:
process R sorted by ID; from each r walk containerward within U; if the
walk reaches an origin that is still kept, discard r. This tie-break
keeps exactly one of two origins on a shared cycle.
*** Unfolding
Unfold contentward from each d in D over the union graph. A node in U
is editable, and its content list is drawn WHOLE, with each member
tagged by its node presence and its relationship presence; members in U
unfold further, members outside U are write-protected leaves. A node in
C also gets its change folders and changeset markers (below). Nodes in
U but not in C are context: editable, bodies folded ('body_folded').
Nodes in C have bodies open. No editable node in a TDV gets the
ordinary default partner folders; folders appear only where something
changed. The first occurrence the BFS reaches is editable, the rest
write-protected (today's rule). The node budget is off for a TDV; the
depth bound 'max_roleTree_depth' applies only to the containerward
forests under container folders. A TDV has no size cap.
*** Non-root origins
A multiply-contained origin at the top level gets a container folder
holding its whole containerward forest (the diffed full containerward
tree), drawn folded.

** What each kind of change looks like
Every label below is a herald rule on a metadata atom (slice 5 and the
heralds table in "wire format"). In every list, a removed member sits
where 'phantom_insertion_plan' places it (immediately before the next
surviving member of the old order); membership is decided by set
difference, and the LCS only positions removed members, so a reorder
never shows.
*** text
A changed title or body adds an old-text property viewnode under the
node: "old title and body" (headline = old title, body = old body),
"old title" or "old body", and under it a "body diff" property viewnode
whose body is the line diff. The text change is one leaf; its ✓ sits
on the old-text headline.
*** content
No content folder. The content members are direct children; a member
carries ∃+ / ∃- for its node's presence and ~+ / ~- for its
relationship's presence, each a separate leaf with its own ✓. The
content changeset marker "its content changed" sits before the
members and aggregates only the ~ leaves.
*** containers, mentioners, subscribers, overriders, hiders (in-folders)
A changed in-set adds a write-protected set folder labelled "its
containers changed (other files)" (likewise mentioners, subscribers,
overriders, hiders). Its members are the partners in either graph,
tagged by presence. Under each member hangs the role-tree engine's
continuation over the union graph: under a container member, the full
containerward tree; under a mentioner, subscriber, overrider or hider
member, the role tree of that role plus a full containerward tree
under each graft. 'PartnerFolder::Container' and
'PartnerFolder::Mentioner' are new kinds (slice 3); Subscriber,
Overrider and Hider exist.
*** subscribees, overridden, hidden (out-folders)
The existing 'Subscribee', 'Overridden' and 'Hidden' folders, drawn
only when their membership changed, labelled "its subscribees changed
(this file)" and so on, with members tagged by presence and the same
continuation under each changed member. The folder kinds do not
change; the label is a herald rule on the folder's diff state.
*** aliases, IDs
The existing alias and ID folders, filled from the diff in list order
(a removed entry where the LCS puts it), labelled "its aliases changed
(this file)" and "its IDs changed (this file)"; each entry carries +
or - and is a leaf.
*** flags
The flags folder, drawn only when a flag changed, each changed flag a
leaf.
*** home skgrepo
One property viewnode under the node, "⌂ -old +new", one leaf. In the
skgrepo-changes buffer the same fact is also drawn in the vognode's
heralds as "-old +new". When the nearest moved vognode ancestor moved
the same way, the node also carries the herald 'Δ⌂=a' (the ancestor
letter in place of 'a'), in the 'nonstandard' style.
*** relRepo of a relationship
Under the member whose relationship moved: the property viewnode
"relationship moved from X to Y", with the skgrepo names in the normal
style; one leaf, keyed by the relationship, so the same move seen from
the other end is the same mark. The relRepo changeset marker "some
content relationships changed skgrepo" sits under the recorder, drawn
only when some content relationship's relRepo changed. Mentions are
excluded.
*** deleted node
A historical phantom ('Phantom::Historical'): write-protected, with the
before-graph's title and body, drawn under each former container (even
deleted ones) as a ~- member, and with its old content beneath it as
~- members, recursing into deleted members. Its existence is one leaf
(∃-). If it was an acquiree, it gets a derived, save-inert folder "it
was acquired by" holding the acquirer; the acquirer gets "it acquired".
*** new node
Drawn as an ordinary editable node with ∃+ on its node axis; its
existence is one leaf.
*** added IDs
The IDs folder in the all-changes buffer, as above; the merges buffer
shows the same event. One store entry serves both.

** Readiness
*** marks
The store holds marks only for change-forest leaves. A leaf key is one
of: (pid, Existence), (pid, Text), (pid, Home), (pid, Alias(text)),
(pid, ExtraId(id)), (pid, Flag(name)), (relation, recorder, member,
Existence), (relation, recorder, member, RelRepo). A relationship leaf
lives under its recorder. The value is the fingerprint: a hash of the
leaf's before and after values. A mark whose fingerprint does not match
the current change is absent; nothing signals that an earlier version
was approved, and a commit lapses every mark.
*** aggregates
Readiness of a folder, a changeset marker, a node, a file, a buffer or
the changeset is derived over the leaves that can be ready; an
unchanged member has no leaf and is never asked. The content changeset
marker aggregates only ~ leaves; a member's ∃ leaf belongs to the
member's own file. The relRepo changeset marker aggregates the relRepo
leaves of the recorder's content relationships.
*** gestures
One command, 'skg-cycle-commit-ready' in Emacs and its Neovim twin,
bound in the view keymaps (not S-left/S-right). On a leaf it toggles
that leaf's mark; on a content member with two leaves it asks which
axis unless only one applies; on an aggregate it writes requests on its
leaves one level down, and with the prefix argument recursively, as a
client-side walk that writes one request per headline (the pattern of
'skg-set-relRepo-recursive'). A second command,
'skg-mark-gnode-skgrepo-changes-commitReady', marks a node's home-move
leaf, and with the prefix argument every descendant whose move has the
same (old, new) pair. Both work on write-protected occurrences.
*** persistence
The store is server-side and keyed as above. It is written to
'<data_root>/readiness-marks.json' after every change and read at
startup; a missing or unreadable file means an empty store.
*** the summary and the commit
After every save of a TDV buffer the save response carries the
readiness summary, and the client shows it: "12 of 14 changed files
are ready", or "COMMIT READY. All 14 of 14 changed files are ready."
Files whose only change is order count as ready. The summary adds the
unshown-change count (below) and the foreign skgrepos' changed-file
count. One command, 'skg-stage-and-commit', prompts once for a commit
message and asks the server to stage everything and commit, in every
owned skgrepo that has changes, with that message. When the summary is
not complete the client asks for confirmation, and only the typed word
"yes" proceeds.

** Saving a TDV buffer
A TDV buffer saves like any view. Afterwards the buffer is reconciled,
not rebuilt: at each vognode's visit in view completion, its presence
and change facts are recomputed from the graph pair, its changeset
markers and change folders are added or removed, its phantoms
re-derived, and its readiness heralds refreshed from the store. The
roots and editability stay as the saved buffer has them. The save
response also counts the changes that the fresh change set contains
and the buffer does not show, reports that count in the summary, and
suggests reopening the view when it is nonzero.

** Moving a node between skgrepos: the server decides what the move strands
This replaces the client-side analysis in 'skg-request-relRepo-info.el'
and its Neovim counterpart. The client writes only the new home. At
save, for each home move, the server finds every relationship touching
the moved node, of every relation and in both directions, in view or
not, whose relRepo the sticky-else-default rule would leave stranded.
Inbound relationships of a privatizing move are raised automatically to
the new home, and the save's warnings say so. Every other stranded
relationship is listed in a confirmation response (the fork
confirmation and the overPrivateText-telescope confirmation are the
precedents), and the approving re-save carries the chosen relationships
back, after which the server re-levels them, rewrites the telescopes of
the nodes that record them, and rerenders the views that show them
through the collateral machinery.

** Investigating an unknown node
A request "investigate unknown node" takes an ID. If the ID resolves to
a node of the live graph, the response says so. Otherwise the server
walks each skgrepo's first-parent git history from HEAD and reports,
as org text: the most recent commit whose tree held the ID's file, the
commit it vanished at, its title then, its own relation lists then, and
every node of that tree that referred to it, links included; or that
the ID was never present in any skgrepo's history. The logic is the
existing 'server/diff_report/vanished.rs', unchanged in substance. Each
client has a command, 'skg-investigate-unknown-node' and its Neovim
twin, that takes the ID from the headline at point when that headline
is an unknown phantom and prompts for it otherwise, and shows the org
text in a read-only buffer. The delete-references-to-absent-node
preview ends with one line naming this command.

** Wire format
*** atoms
**** presence
'(diff ATOMS)' sits on a vognode, a phantom or a property leaf, with
ATOMS from 'node+ node- rel+ rel-'. It replaces '(staged ...)' and
'(unstaged ...)'.
**** readiness, displayed
'(ready AXES)' is a display fact: '(ready node rel)', '(ready rel)',
'(ready node)'; '(ready)' on a single-axis leaf; absent when nothing
is ready. An aggregate carries the same form, derived.
**** readiness, requested
'(readyRequest AXES)' and '(unreadyRequest AXES)' are requests, in
their own field ('readiness_request', beside 'relRepo_request'), so
that they ride with a merge or delete request. 'all' as the axis is
the one-level gesture on an aggregate.
**** the new viewnodes
'(oldText)', '(bodyDiff)', '(homeMove OLD NEW)', '(relRepoMove OLD
NEW)', '(movedLikeAncestor GEN)', '(changesetMarker KIND)' and
'(historical)' mark the new property viewnodes and the phantom.
**** folders
'(containerFolder)' and '(mentionerFolder)' name the new folder kinds.
A '(changed)' fact on any folder drawn because of a change is what the
label rule turns into "its X changed (this file)" or "(other files)".
**** notInGit
The existing 'notInGit' stays until the old view goes, then goes.
*** heralds and styles
∃+ ∃- ~+ ~- for the four diff atoms (nonstandard); on an alias or ID
leaf the same atoms render as + and -. ✓ (go) after each ready axis:
'∃+✓ ~+✓'. ✗ is retired. 'Δ⌂=a' (nonstandard) for movedLikeAncestor.
"⌂ -old +new" with skgrepo names in normal. Labels in message. Property
counts in the new 'boring' style. The style 'yucky' is renamed 'ugly'
everywhere. Tiers: '☮' crucial, '⊥' crucial, 'ĥ' crucial, 'B' high,
'⟳' medium, the birth letter low; relationship-herald tiers otherwise
as the shared file has them today.
*** requests and responses
Request type "total diff view" with '(buffer . "all changes")',
'"merges"', '"skgrepo changes"' or '"order-only changes"' and a
'view-id'; response "total-diff-view" carrying a content view or
'(empty . t)'. Request "stage and commit" with '(message . "...")' and
optionally '(confirmed . t)'; response "stage-and-commit" carrying
either the per-skgrepo commit results, or, when the readiness summary
is incomplete and 'confirmed' is absent, the summary alone with
'(needs-confirmation . t)' and no change made.
Request "investigate unknown node" with '(id . "ID")'; response
"investigate-unknown-node" with '((content "ORG") (errors (...))
(warnings (...)))'. The save response gains a '(readiness-summary ...)'
field. The requests "git diff mode toggle" and "diff report" are
removed.

** Slice 2: the graph pair and relRepo-aware diffs
*** module
New module 'server/graph_pair/' with 'GraphPair { before : Arc<InRustGraph>,

** Slice 6: readiness in the view, saving a TDV, the summary
