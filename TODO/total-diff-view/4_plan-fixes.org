** Vocabulary
The terms this plan relies on, one line each; 'docs/glossary.org' has
more.
- The TDV (total diff view) is up to four buffers (all changes,
  merges, skgrepo changes, order-only changes) that show the graph's
  uncommitted changes, HEAD against the worktree.
- The graph pair, called the graph straddle after slice 0
  ('GraphStraddle { before, after }'), is what the TDV compares: the
  before-graph is read from HEAD, the after-graph is the live graph. A
  straddle stands with one foot in the committed graph and one in the
  live graph. Each node and relationship it reports carries a
  presence: both, only-before or only-after.
- The PCSVF (pruned change-spanning viewforest) is what the
  all-changes buffer draws, defined by four sets. C is the changed
  nodes. R is the content origins reached from C by the containerward
  walk; the walk follows single containers only, so a node with no
  container, or with two or more, is an origin, and a rootlike cycle
  contributes one origin, chosen by ID
  ('climb_containerward_to_cycle_via', 'kept_origins'). D is the
  deduplicated content origins, the roots the buffer opens with. U is
  the nodes to unfold contentward: C, R and every node on the walks. A
  node of U is drawn editable at its first occurrence with its whole
  content list; a member outside U is a write-protected leaf. The
  merges and skgrepo-changes buffers draw PCSVFs over subsets of C
  ('pcsvf_sets_of_buffer'); the order-only buffer draws a flat list.
- Where a set's name appears inside a snake_case function name, it is
  one camelCased token ('contentOrigins', 'freshU'), so that it reads
  as a single noun: 'append_contentOrigins_to_buffer', not
  'append_content_origins_to_buffer'.
- The fresh sets are the sets recomputed from the refreshed straddle
  at a rerender ('GraphPair::pcsvf_sets_of_buffer' computes them once
  per straddle). A buffer's standing roots are the roots it has when a
  rerender begins.
- A change-forest leaf is one atomic change to a node (its title, its
  body, one relationship, its home skgrepo, and so on). A mark is the
  user's statement that a leaf is commit-ready; readiness is the state
  of the marks; a gesture is a client command that marks or unmarks.
- A changeset marker is a one-line viewnode that summarizes a node's
  small changes (kinds: content, relRepo, order-only). A historical
  phantom is the TDV's image of a node that HEAD has and the worktree
  lacks. A removed member is a content member drawn write-protected
  with presence only-before. A continuation is the containerward tree
  or role tree drawn under a member of a changed folder.
- Change viewnodes are the viewnodes the TDV draws for a node beyond
  its ordinary content: old-text properties, home moves, relRepo
  moves, changeset markers, change folders and their members,
  continuations, historical phantoms, and removed members.
- View completion is the level-order walk ('complete_viewforest') that
  brings a viewforest up to date with the graph. In a TDV it runs with
  'tdv_drawing' set, and each editable node's visit ends in
  'process_unrestrictedVognode_changes', the per-visit TDV step. The
  node budget is a per-completion counter that starts at
  'initial_node_limit'; an ordinary view checks it before expanding an
  editable node and charges one per expansion; a TDV skips the check
  today.

* Agreed behavior
** Folding survives, because nothing that exists is recreated
The server never changes the fold state ('folded', 'body_folded') of a
viewnode that already exists. Defaults apply only when a viewnode is
created: a context node's body starts folded, a container folder
starts folded, everything else starts open. A context node that later
becomes a changed node keeps whatever fold state the user gave it.

Every change viewnode is reconciled, never detached and redrawn. At a
node's visit, each existing child is matched to what the fresh drawing
would produce. The match key for a viewnode that stands for a
graphnode is (parent, skgid), where the parent is the particular
viewnode it sits under; within one parent a graphnode appears at most
once, so the key is unique. Its kind is a fact updated in place: a
deleted phantom whose node the straddle holds as only-before becomes
the historical phantom, a historical phantom whose node is back
becomes a live member, a live member becomes a removed member and
back, each keeping its viewnode and its fold state, with its children
then reconciled by the same rule. The match key for a viewnode that
stands for no graphnode (an old text, a home move, each marker kind,
each folder kind) is (parent, kind). A matched viewnode is kept and
its facts updated; an unmatched existing one is detached; what the
fresh drawing produces and nothing matches is created. A removed
member or historical phantom is matched and kept too, and only
repositioned to its LCS slot. "Produced by the fresh drawing" is
defined over the union of the two graphs: a node only in the
before-graph is still produced, as a historical phantom or a
write-protected rel- member; a viewnode is detached only when the
relationship it stands for is in neither graph any more.
'redraw_deleted_phantoms_as_historical' is deleted; the matching
covers it.

Continuations under a changed folder's members are reconciled the same
way, through the goal-list reconciler, which gains presence-tagged
goal items so that a removed member or a historical phantom is a
first-class goal entry; the restore-then-redraw pair for folders
('restore_removed_members_of_pair_folder',
'redraw_removed_members_of_pair_folder') goes.

Roots linger: a root stays until the user closes the buffer, whatever
happens to the changes under it. A commit is an ordinary rerender
under these rules: after it, the roots stand as plain context with
their decorations gone; 'redraw_tdv_views' is deleted. No buffer is
ever sent empty because of a commit.

** Removed alias and ID entries
A removed alias is drawn as 'Property::RemovedAlias { text }' and a
removed extra ID as 'Property::RemovedID { skgid }', both save-inert by
kind: the alias reader never reads them and the ID check never counts
them. They sit in list order where the LCS puts them, carry the '-'
herald and the '(diff rel-)' presence fact as display, and carry their
readiness leaf and requests as the live entries do. No save code reads
a presence fact any more.

** Partial staging is gone
'skg-git-add-if-new-recursive', its preview, 'skg-stage-moves', and
their Neovim twins are deleted, with their server support, tests,
bindings and documentation. The magit navigation commands and the
"titles by ids" git fallback stay. Both COMMANDS files already explain
why partial commits are dangerous.

** Unmarking warns
Every readiness gesture toggles: it unmarks when the thing at point is
ready, else it marks, and a recursive form applies that one direction
to every matching descendant. When a gesture would unmark more than
one leaf, it first asks, with a typed answer ('yes-or-no-p' in Emacs,
an input that must equal "yes" in Neovim): "Unmarking this node
commit-ready will unmark every contributing decision. You might
discard a lot of hard-won information. Continue (yes/no)?". An unmark
of a single leaf proceeds silently. This applies to
'skg-cycle-commit-ready' and to 'skg-mark-gnode-skgrepo-changes-commitReady',
which thereby gains unmarking.

** The view follows its fresh sets after a save
A TDV buffer keeps the rule it was drawn by, "a node of U is editable
at its first occurrence, with its whole content list", as U changes.
After any rerender the writable viewnodes are those of the fresh U
plus whatever was already writable: nothing writable is ever
write-protected again, and this drawing is never bounded by the node
budget.
*** new editable occurrences
Before completion of a TDV buffer, for every node of the fresh U with
no editable occurrence in the buffer, the server sets 'editability' to
editable on the node's BFS-first occurrence, directly, with the body
read from the live graph as a freshly drawn editable viewnode has it.
It does NOT use 'ViewRequest::Editable'. Completion then draws that
occurrence's content list: members of the fresh U editable and
expanded, the rest as write-protected leaves, and so on down to the
change, so a node of U with no occurrence at all is reached through
the node above it on its walk. The unshown count keeps counting nodes
of C with no occurrence after completion.
*** new roots
After completion, the origins of the fresh D that no viewnode in the
buffer draws are appended at the end, in ID order, as stubs drawn as
'stub_viewforest_of_roots' draws a root (a historical phantom when the
after-graph lacks the node; a folded container folder when the node
has several containers), and completed. Before that, the
deduplication of the fresh R runs with the buffer's standing roots
pinned as kept, so that a change to a rootlike cycle's membership
never appends a second root for a cycle that already stands. A new
root is the origin the walk reaches, never the changed node itself.
*** a user's editable-view request cascades, within the node budget
In a TDV buffer, 'ViewRequest::Editable' on a write-protected
occurrence behaves as in an ordinary view: the occurrence becomes
editable (or defers to an existing editable occurrence), its content
list is drawn, and the request passes to its content children, each of
which repeats this when visited. The node budget bounds these
request-driven expansions and nothing else: a node of U is never
charged against it. The request adds no default partner folders,
because a TDV draws none. Nodes made editable this way stay editable
at later rerenders, as anything already writable does.

** The merges buffer draws acquirees and acquirers only
C of the merges buffer is each acquiree and its acquirer. The text
preserver is no longer sought; it appears as a new member (∃+) in the
acquirer's content.

** The straddle is dropped on a store rebuild, and written back after a rerender-all
The "rebuild session-lifetime stores" request sets the connection's
cached straddle to None, so the next TDV request rebuilds both halves
from the same disk state as the rebuilt live graph. A rerender-all (an
absent-reference cleanup, the skgrepo switch) writes the straddle it
refreshed back to the connection, as a save does.

** Empty strings on the wire
Every response the server serializes prints an empty string atom as
'""'. Non-empty atoms print as the 'sexp' crate prints them today,
because the server relies on a non-empty 'Atom::S' printing as a bare
symbol. The clients' workaround that reads a bare '(content)' as an
empty view is removed.

** Tree moves detach first
Every move of an existing viewnode within a tree goes through one
module of helpers that detach the node first and do nothing when it is
already in place. No code calls ego-tree's 'prepend_id', 'append_id',
'insert_id_before' or 'insert_id_after' directly on a node that may
already be in the tree.

** Dependencies are current
Every dependency is at its latest version, and 'serde_yaml', which is
deprecated, is replaced by a maintained crate whose output on every
'.skg' file is byte-identical, or the plan stops to ask. The
dependency plan that slice 10 points to states the rest.

* Pitfalls in view completion that the slices must respect
These were found by reading 'server/update_buffer/complete.rs',
'server/update_buffer/reconcile/content.rs',
'server/update_buffer/reconcile/partner_folder.rs',
'server/to_org/render/changes.rs', 'server/pcsvf.rs' and
'server/update_buffer.rs'.
** the per-visit step is destructive today
'process_unrestrictedVognode_changes' begins with
'remove_change_viewnodes', which detaches every old text, home move,
changeset marker, "it acquired" folder, historical phantom (with its
subtree) and removed member, and 'tag_content_members' detaches relRepo
moves; only partner folders are reused ('child_folder_or_new'). It
also sets 'body_folded' from C at every visit, which is why context
bodies refold. Slice 1 replaces all of this with matching.
** the content reconciler runs first and reorders
'expand_true_content_at_unrestrictedVognode' runs before the TDV step
and ends with 'order_children_as_non_vognodes_then_ignored_then_content',
which moves removed members (affectsParent false) ahead of the content.
The TDV step must reposition kept removed members to their LCS slots
after it, every time, by moving them (slice 9's helpers), not by
recreating them.
** the generic goal-list reconciler knows only live members
'reconcile_partnerFolder_children_against_goal_list' matches children
to skgids and treats a demoted member or a historical phantom as
stale, which is why the folders needed the restore/redraw pair. Slice 1
teaches it presence-tagged goal items instead.
** 'tag_content_members' demotes at every visit and never promotes
At each visit of an editable node it write-protects every content
member outside U, including one that was editable, and strips any
'ViewRequest::Editable' from it, before the member itself is visited.
Three consequences. A member that U has grown to include stays
write-protected, and nothing is ever drawn under a write-protected
node ('clobberWriteProtectedViewnode' only resyncs title and home;
children already there survive, which continuations under
write-protected folder members rely on). A commit, which shrinks U,
would write-protect the lingering context. And a user's request on a
member outside U is a no-op, as are the requests the cascade puts on
children. Slice 5 narrows the function to members this visit created
and lets requests through.
** a requested node skips the budget and gains folders
'apply_editable_draw_rule' makes a requested node editable and
'attach_cascade_dvrs_to_affected_content' hands the request to its
content children; the node budget is what bounds this in an ordinary
view, and 'visit_normal_node' skips the budget check in a TDV.
'maybe_add_default_partnerFolder_branches' also runs for a requested
node ('had_dvr'), and a TDV draws no default folders. Slice 5 restores
the check for requested nodes outside U and skips the folders. No
slice uses the request to make a node of U editable.
** editability is recomputed from a fresh 'EditableMap' every rerender
BFS-first occurrence wins. Anything a slice makes editable must be the
first occurrence of its node in BFS order, or the map will
write-protect it again.
** a root with several containers has a container folder
'stub_viewforest_of_roots' gives a multiply-contained root a folded
container folder, which completion fills with its containers in either
graph. A root that slice 5 appends gets the same.
** fold state travels only on viewnodes the client saw
The client writes '(folded)' and 'bodyFolded' before saving; the
parser puts them on the viewnodes. A viewnode the server creates is
open. No client change is needed for folding.
