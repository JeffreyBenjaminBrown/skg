* Client incident retention and status selection
** Existing server interface
'pending-incidents' supplies incident ID, maintenance epoch and phase for every
incident whose terminal outcome is not acknowledged. 'maintenance status' accepts
an explicit incident ID and epoch, returning its retained report independently
of the currently active graph transition. No parallel server ledger is needed.
** Next client boundary
Retain incident-local recovery and report state when another incident becomes
active. Keep the current active pointer as an adapter while adding explicit
selection by incident identity. An older report is historical operation data;
it must not overwrite versioned global current-state metadata or release another
incident's buffer restrictions.
** Counterexample
Retain unsettled incident A, allocate B, and request A's status. A's archive,
census and report state must remain available; B remains the active workflow.
** Deferred workflow boundary
A callback retains its incident identity when scheduled, including callbacks it
schedules in turn. Running A while B is current uses a temporary incident scope,
retains A's latest record on exit and restores B even after an error. Allocating
B alone is no evidence that A's report or restrictions have been discharged.
Global handshake state and pending offers must not follow historical A status.
The focused counterexample runs A's queued settlement and its continuation after
B becomes current, then verifies both the resulting A facts and untouched B.
** Reconnect consumer
The compact handshake state describes the current graph transaction. An idle
handshake can still list A in 'pending-incidents'; that is not abandonment of A.
A new active epoch B must preserve A's restrictions and frozen census. After the
connection census, resume named pending incidents independently. Census staleness
must respect actual remaining per-buffer restrictions, including historical ones,
rather than deriving protection solely from one global active phase.
