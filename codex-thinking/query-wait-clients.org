* Query waits for both clients

This note narrows the remaining search wait contract from [[file:../TODO/partial-reload-and-magit/11_plan_simplify-cohere.org::513][Plan 11]] and the settled maintenance choice in [[file:../TODO/partial-reload-and-magit/10_architecture-review.org::945][Plan 10]]. It covers the Emacs and Neovim adapters and the server wire boundary. A pending wait owns a recipe and an outcome identity; it does not own a Tantivy Searcher, a graph lease, an editor callback, or a time based expiry.

** Current entry points

Emacs starts a search in [[file:../elisp/skg-request-text-search.el::skg--request-text-search][skg--request-text-search]]. It sends text search with terms, the three search axes, the ugly telescope choice, the view URI, and requested view authority. The search-results handler creates or selects a registered search buffer, while search-enrichment later validates the server session, view URI, buffer ID, graph and presentation bases, source set, server revision, and application token before replacing clean text. The snapshot continuation is deliberately tied to the active transport request by [[file:../elisp/skg-request-text-search.el::skg--handle-snapshot-request][skg--handle-snapshot-request]].

Neovim has the parallel entry points in [[file:../nvim/lua/skg/search.lua::M.request_text_search][M.request_text_search]], [[file:../nvim/lua/skg/search.lua::M.display_search_phase1][M.display_search_phase1]], [[file:../nvim/lua/skg/search.lua::M.display_search_enrichment][M.display_search_enrichment]], and [[file:../nvim/lua/skg/search.lua::M.handle_snapshot_request][M.handle_snapshot_request]]. Both adapters dispatch ordinary frames by connection local request-id. The server's [[file:../server/serve/util.rs::begin_request_context][request context]] and the client request records make that ID unsuitable as durable wait identity. The existing server text search handler acquires RuntimeQueryLease and performs the Tantivy query immediately, so a pending branch must be reached before that handler or through a separate wait request.

** Stable wait identity and recipe

The durable field is query-operation-id. The client generates it once for the user's wait and resends it unchanged after a lost response or reconnect. Transport request-id remains fresh for every wire request. The server treats a repeated accept, status, cancel, or applied acknowledgement carrying the same query-operation-id as an idempotent operation and returns its recorded state. No response may use request-id as the operation identity.

The accepted recipe is an explicit canonical query value. For current text search it contains kind text-search, terms, regex, body, operators, ugly telescope inclusion, and the selected source-set. Future query context belongs in the same value, including roots, visibility, and selection rules, so replay never silently adopts a newer interactive source-set or view context. A recipe digest may be echoed for consistency checks, but it cannot replace the recipe needed for recovery.

The wait target is an incident-id, maintenance-epoch, and required-outcome tuple. The required outcome is graph-publication, meaning the coherent graph and matching search publication for that incident, including the no-change result. The target is satisfied by an explicit published or no-change outcome; it is never inferred from a larger graph generation, an unrelated save, or a later incident. The selected graph-generation, manifest-revision, and owner-publication-revision are recorded when the outcome becomes ready.

** Proposed messages

The client sends query-wait with query-operation-id, incident-id, maintenance-epoch, required-outcome, recipe, and a destination descriptor. The destination descriptor carries client-buffer-id, view-uri, server-session-id, application-token, graph-generation, presentation-generation, server-revision, source-set, and a clean-or-placeholder state. The response is query-wait-status with status pending, ready, completed, cancelled, superseded, or failed, and echoes query-operation-id, incident-id, maintenance-epoch, and the exact outcome fields. Acceptance is a terminal transport response with terminal-status accepted; pending is the durable operation state and must not hold the request queue or a Searcher.

The client sends query-wait-status after verified handshake and census, with the same query-operation-id, target, recipe digest, and the current destination descriptor. The server reads only its journaled wait state and replies with query-wait-status. A pending reply remains pending. A ready reply names the exact selected graph, manifest, and owner publication revision. A completed reply is the recorded delivery outcome. An unknown or unrecoverable operation is an explicit failed status; it must not be rerun against current G2.

When the target becomes ready, the owner obtains one immutable graph/search lease, runs the recipe, and emits the unsolicited query-wait-result frame carrying query-operation-id, the selected snapshot identity, and mandatory view-write-authority. The query may run immediately after a no-change outcome. It must not run while the wait is pending. The client acknowledges successful, exact installation with query-wait-applied, carrying query-operation-id, result digest, destination identity, and resulting application token. Enrichment and its apply-collateral operation keep their existing operation-id and additionally echo query-operation-id; those two identities remain independent. A repeated result push is harmless because the applied acknowledgement is idempotent and delivery is bound to the same selected snapshot.

The client sends query-wait-cancel with query-operation-id and the target. Cancellation is explicit and idempotent. Supersession is another explicit terminal outcome, carrying the superseding query-operation-id. Neither cancellation nor supersession is a timeout. The server may compact completed records only after it has durably retained enough terminal metadata to answer a duplicate or reconnect request, and such compaction must be reported as unrecoverable rather than silently deleting user intent. A recoverable failed run may be retried explicitly through the server's status or retry contract; an ordinary result push never triggers an automatic duplicate query.

** Destination and base validation

The result frame must echo query-operation-id, view URI, client buffer ID, server session ID, selected graph-generation, selected manifest or server revision, presentation-generation, source-set, expected client application-token, and resulting client application-token. Before applying content, each editor verifies the current server session, the operation ID and recipe attached to the destination, the URI and buffer ID mapping, clean or placeholder state, every supplied base field, and the expected application token. A missing, dirty, edited, or mismatched destination leaves the outcome available and produces a visible destination-rejected state. It never overwrites an edited result and never creates a second buffer merely because a duplicate result arrived.

An accepted wait may use a read-only placeholder whose application token and empty base are explicitly recorded. If the placeholder disappears, resume can return ready or completed without a destination; the client keeps the durable outcome and lets the next explicit status or run bind a newly verified destination. Waiting results are read-only even when publication opens new editable view admission. Reopening an existing result is a separate explicit client action and does not mutate the wait outcome.

** Reconnect and replay

Each editor keeps a small durable pending-wait record keyed by query-operation-id. It contains the target, canonical recipe, destination identity and base, and local delivery state. On a new server session the record is not attached to an old request record and no callback is revived. After handshake and the maintenance census complete, the client submits one query-wait-status request per record using the new transport request-id and current server-session-id. The server's journal is authoritative for pending, ready, and terminal state; the client recipe is checked against the journaled digest.

A delayed response from an earlier session cannot change the destination or global authority. A current-session query-wait-result can be consumed exactly once and acknowledged with query-wait-applied. A duplicate result is harmless because delivery is keyed by query-operation-id and the destination token. A no-change completion follows the same path as publication and does not wait for a nonexistent newer generation. A disconnected pending wait remains pending without expiry until completion, explicit cancellation, explicit supersession, or an explicit unrecoverable failure.

** Boundary with incident evidence

The incident journal needs only the durable query-operation-id, target tuple, canonical recipe or its recoverable representation, selected publication identity, terminal status, and delivery idempotency record. It must not retain a live Searcher, candidate lease, editor callback, or destination pointer. The evidence/report path can expose the incident's published or no-change outcome to status recovery, while missing old evidence remains an explicit blocked or failed recovery result. It must never substitute the current graph or report-only selected values.

This shape lets the existing search-results and search-enrichment handlers remain the result presentation path in both editors. The new client work is a wait record, the current-snapshot versus wait choice, four small request/response handlers, and the shared base validator; it does not require a second search buffer model or a live query object during maintenance.
