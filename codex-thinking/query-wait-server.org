* Durable server query waits (Plan 11)

The settled contract in [[file:../TODO/partial-reload-and-magit/11_plan_simplify-cohere.org::Searches may use the selected snapshot or wait for reconciliation][plan 11]] makes a wait an explicit request for a named maintenance outcome. It survives disconnect and reconnect, has no time based expiration, and is completed by that outcome rather than by observing a larger graph counter. Document 10's settled choices require the current coherent snapshot option, a cancellable wait option, visible generation and freshness metadata, and no automatic rerun or replacement of an existing result.

The current server has no durable query wait. [[file:../server/serve/handlers/text_search.rs::handle_text_search_request][handle_text_search_request]] consumes a process local [[file:../server/runtime/mod.rs::RuntimeQueryLease][RuntimeQueryLease]], runs Tantivy immediately, registers a view, and starts enrichment in a connection local slot guarded by an atomic cancellation flag. [[file:../server/serve.rs::handle_connection][handle_connection]] only drains that slot during its socket idle loop. [[file:../server/runtime/interactive_session.rs::QueuedServerEvent][QueuedServerEvent]] is also process memory. The [[file:../server/maintenance/journal.rs::MaintenanceJournalStore][maintenance journal]] persists coordinator state but does not retain query recipes, destinations, or result delivery records. A disconnect therefore loses an unfinished search continuation, and a restart cannot recover it.

The durable record should be a private versioned QueryWaitRecord keyed by a client generated query operation UUID, separate from the connection request ID. It should retain the normalized search recipe (terms, regex, body, operators, ugly telescope choice, and source set identity), the requested maintenance incident and epoch, an explicit outcome identity, and a destination identity consisting of the requested search view URI and client buffer identity when one exists. The target must name the maintenance operation or incident outcome and its durable completion marker; an expected graph generation alone is insufficient because no change can complete without advancing that counter and an unrelated save must not satisfy a reload wait. The record may retain the config and source interpretation fingerprints needed to validate the eventual selected snapshot, but it must not retain a graph, a Tantivy Searcher, an editor callback, or a live socket.

The state machine needs pending, blocked, ready, delivered, cancelled, superseded, and failed states. Pending means the named outcome has not completed. Blocked is recoverable and carries a stable reason such as unresolved archive, source/config interpretation, publication, or missing target snapshot; it remains visible until an explicit retry or the blocking condition is resolved. A no change reconciliation is a successful target outcome and transitions to ready even though graph generation is unchanged. Cancellation transitions an undelivered pending or blocked record to cancelled. A newer explicit wait for the same destination may supersede the older operation and names the successor. Query or privacy failure after the target is ready is failed with its exact reason. Ready is entered only after the explicit query has run against the target selected snapshot and its result has been durably staged; delivery and its ACK are separate facts. Duplicate delivery or ACK is idempotent by operation UUID and result digest.

The server should extend the existing text search request with an explicit query policy, either current or wait. A wait request carries a client query operation UUID, a normalized wait target such as incident ID, maintenance epoch, outcome kind, and outcome operation identity, plus the recipe and destination. The immediate response is a terminal query-wait acknowledgement with state pending or blocked, so the serial connection remains available for status and cancellation. When the owner records the target outcome, it runs the recipe against that outcome's selected immutable graph/search pair, drops the Searcher after bounded query work, persists the result and generation/manifest/source-set freshness metadata, and queues a server push such as 'query-wait-result' carrying the same operation UUID. A separate 'query-wait-status' request retrieves pending or staged state, and 'cancel-query-wait' names the operation UUID. A result ACK names the operation UUID and result digest. The result push must contain 'view-uri', content, graph generation, manifest revision, and explicit current/stale/pending reconciliation metadata; it must never silently replace an independently edited destination.

The reconnect handshake or completed client census should expose only a compact list of outstanding query operation IDs, states, target outcome labels, and destination identities. The client can issue authenticated status requests for the recipe or staged result. A client which restarted and no longer has the destination receives recoverable status and may explicitly rerun into a fresh 'search:recovery:UUID' view; the server must not create an editor buffer or revive an old callback. The client admission finish seam should install the query wait server-push handler before ordinary requests are admitted, retain the operation UUID outside a transient request handler, ACK a result only after installing the exact content once, and preserve a pending or staged operation across reconnect. The server must replay a pending or ready record by operation UUID without producing a second logical result.

The publication race needs a fail closed boundary. In one process the wait may acquire the target read unit only after the owner marks the named outcome complete, while later publications retain resources until the bounded query ends. Across a crash, a staged result is replayable without a Searcher. If the target outcome is durable but its result was not staged and the target read unit is no longer reconstructible after restart, the record becomes blocked with an explicit target snapshot unavailable reason; it must not be rerun against newer G2 or current disk under the old target identity. If the target read unit is still the current validated publication, startup may execute the recipe once and stage the result. This preserves the no silent rerun rule without adding a serialized graph cache solely for query waits.

Terms, source-set details, destinations, and staged result content are potentially private graph data. Store them under the existing restrictive maintenance state boundary, exclude them from ordinary logs and unsolicited handshake text, and expose only operation IDs and coarse states until an authenticated status or result delivery. Privacy filtering and ugly telescope choice remain part of the recipe and are evaluated before Tantivy matching; a wait must never disclose matching PIDs merely because it is pending. The eventual query uses only the selected published unit's graph, manifest, config/source interpretation, and matching Searcher, including negative lookups; it never reads live disk or a process global Searcher while waiting.

The narrow implementation split is a durable query-wait journal and typed state transitions beside the maintenance journal, owner messages that register, cancel, supersede, and settle waits on named maintenance outcomes, and a bounded executor that starts only after publication. The TCP adapter then adds the policy and status/cancel/ACK wire frames and reconnect replay. The Emacs and Neovim admission-finish work only needs the shared operation/result contract, push registration before census completion, exact destination checks, and idempotent ACK/replay handling. Existing immediate text search and its snapshot based enrichment can remain a separate current-snapshot path until the durable wait result path is integrated.

** Publication and ranking recovery boundary
The historical graph alone does not prove historical ranking. Ordinary updates
retain cyclic-root bits from the last explicit full pass, so recomputing roots
on G1 after restart can alter the requested search order. The live incident
semantic snapshot therefore retains these small ranking inputs too. Durable
query execution must record the target's config and ranking facts with its
resolved publication before the incident selection outcome is acknowledged.
Resolve already accepted waits in the same owner publication that records the
incident's successful selection. This removes the crash gap between target
completion and retaining the facts needed to reconstruct its matching index.

Result text belongs in a private verified artifact published before the owner
records result readiness. Repeated observer journal publications should copy
only its metadata. Redelivery reads that artifact and rechecks current source
authorization; it never reruns the query or adopts a newer source-set silently.

** Exact configuration encoding
'SkgConfig' is a user-file deserializer: it deliberately skips runtime paths
and derives ownership separately. Its ordinary YAML round trip therefore does
not reconstruct a historical query interpretation. Use a private versioned
wrapper retaining config text plus ordered source entries, configured paths,
directory identities and skipped runtime paths; restore those explicit facts
without reading current disk. A round-trip test with foreign and owned sources
and distinct configured/canonical paths must preserve exact SkgConfig equality.
The owner stores this small encoding and cyclic-root IDs with the incident
selection proposal; query execution and index construction remain worker work.

** Resume staged bytes before rerendering
Search rendering can generate fresh view identities, and equal-score matches
currently have no stable tie ordering. Crash recovery must therefore discover
an already published operation artifact before running its recipe again. The
artifact contains a versioned payload with exact recipe, target, content and
warnings. The journal retains separate artifact and content digests; a verified
orphan artifact can finish readiness after a crash between rename and owner
publication. Temporary staging files are not a published result. This preserves
one result's bytes without changing ordinary search ordering in this slice.
