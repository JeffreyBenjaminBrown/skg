* Start here
Read this file and [[file:to-save-tokens.org][the default token-conservation advice]] once at the
start of a task. Then use the reading guide below for the work actually in
scope. Do not reread unchanged advice for every follow-up in the same task.
Do not load the whole folder or 'maybe-obsolete/' as routine onboarding.

* How to work
** Conserve tokens
Before a tool call, identify the unresolved question it will settle. Work one
narrow, tested slice at a time; use focused reads and tests; do not duplicate
an investigation that another agent owns.
** Follow the requested scope
A request for a review, diagnosis, discussion, or plan ends with that
deliverable; it does not authorize implementing the proposed changes.
When asked to implement, continue through the agreed work and verification.
The detailed execution and stop rules are in [[file:when-to-stop.org]].
** Edit conservatively
Do not alter Git configuration, credentials, index, branches, or commits
unless explicitly asked. Do not gratuitously rename things or add legacy
compatibility code. Preserve relevant comments and follow the existing local
style when modifying code. The code is authoritative when documentation and
code differ.

Do not change or commit git state unless explicitly asked.
If asked to commit, I probably meant to ask for granular commits
that will make the history easy to spelunk, rather than one mega-commit.
Use verbose, understandable names as described in [[file:names.org]].
** Push back when needed
Call out requests that are vague, contradictory, inefficient, unnecessary, or
overly complex rather than silently guessing at a bad interpretation.
* Project essentials
Skg is a local knowledge-graph editor. Its canonical data is in plaintext
'.skg' files; the 'in-Rust graph' and Tantivy are derived stores.
The Rust server is in
'server/', with Emacs Lisp and Neovim clients in 'elisp/' and 'nvim/'. A
server retains one interactive user and admits one interactive client at a
time.

* How to communicate and maintain knowledge with me
For a response longer than a couple of paragraphs, prefer an Org file in the
repository and link to it. Note that an org file uniformly of depth 2,
with bullets inside the bodies, is a weird LLM smell.
The natural way knowledge divides is as a tree of verying depth,
with complex parts being more bushy. And bullets defeat the purpose of org,
so prefer headlines -- those let me (Jeff) respond granularly.
Use single apostrophes around code references in Org, not double
apostrophes; dense double-apostrophe wrappers can stall Org's parser.

Report discovered bugs, specification deviations, important inefficiencies,
or architectural opportunities in 'TODO/problems.org'.
