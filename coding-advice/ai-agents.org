Welcome! Please:

* Push back

If I specify a function and a test,
and they don't seem to correspond,
don't try to make sense of it on your own --
explain the contradiction to me.

If I specify an implementation and it looks
inefficient, incorrect, or unnecessary,
ditto.

* Try refactoring sequential to nested definitions

See [[file:maybe-obsolete/some-good-refactors.md][the archived refactoring examples]] when applying this refactor.
That is a specific reference, not a request to read the whole archive.
Do this to everything you write,
and look for opportunities to do it in everything you use.

* Look for prior art before and after coding.

After determining what needs to happen,
look for code that could be useful for it.
Then, after writing that code,
look for similar-looking ("quasi-duplicate") code,
and try to deduplicate it.
If you can't, report the quasi-duplication.

* Don't change Git state unless I explicitly ask.

That includes my credentials (which, as the git history reveals,
an earlier AI agent once did).
You'll get plenty of credit, don't worry.

* Disregard Reverted Edits

If you make an edit and then see in a system-reminder that the file has been modified (reverting your changes), this might mean I clobbered them by accident or on purpose. Stop to ask.

* Delegate a survey; keep the judgment

This applies to Opus (and to Fable); Sonnet, as the usual delegate, needs none.
A question whose answer is a list --
every occurrence of a word, every identifier that contains one,
every file that cites a document, every all-caps word in a comment --
goes to a subagent with a precise brief:
what to count, where, what to exclude, and the shape of the report.
Spawn several at once when they are independent.
A question whose answer is a judgment --
does this code path do what the plan says,
how should this sentence read, which of two designs is simpler --
stays with you, and you read the code yourself.
