* Key Project Context

This is the **skg** project - a knowledge graph manipulation system with:
- **Rust server** (`server/`) handling the in-memory graph and Tantivy index
- **Emacs client** (`elisp/`) providing org-mode interface
- **YAML data storage** in `.skg` files
- **TCP communication** between components:
  - Port 1730 (default): Rust-Emacs API communication (configurable)

* Formatting Rules

When writing or modifying code:
- **Type signatures**: Name, each argument, and return type on separate lines
- **Variable definitions**: Type signature required, newline after equals sign
- **Function order**: Callers before callees within same module
- **Whitespace**: Honestly, hard to describe, but try to follow the precedents you find in the code. My (this is Jeff speaking) goal is readability.
- **Bracket grouping**: Adjacent punctuation grouped `(( ))` not `(())`
- **Comments**: Inside code blocks they apply to, preserve existing comments
- **No empty lines** in function definitions unless necessary for comment clarity.
- **Don't reformat existing code** - only apply rules to new/modified code

* Testing Dependencies

`bash/all-tests.sh --no-sound` manages the server instances needed by the
integration tests. Rust tests do not require an external database service.
Config files such as `data/skgconfig.toml` select distinct TCP ports, source
folders, and Tantivy folders for concurrently running Skg instances.

* Running Tests

There are three ways to test the code:

1. **Emacs Lisp tests**: `bash/emacs-tests.sh`
   - Runs all automated Emacs tests in `tests/elisp/`
   - Uses Emacs batch mode with ERT (Emacs Lisp Regression Testing)
   - Some tests require `cargo run` to be running

2. **Rust unit/integration tests**: `cargo nextest run`
   - Runs Rust tests in parallel
   - Uses service-free graph fixtures and isolated Tantivy directories

3. **Integration tests**: `bash/integration-tests.sh`
   - Runs end-to-end tests that exercise both Rust and Emacs components
   - Tests run in parallel with isolated configurations
   - The integration runner starts and stops isolated Skg servers
   - Individual tests located in `tests/integration/*/run-test.sh`

* The save-buffer pipeline

  The canonical definition of step 5, "local instruction
  collection", lives in 'glossary.md'; this section lists the
  surrounding stages and links there rather than re-explaining
  extraction.

  The central pipeline. When Emacs saves a buffer, the server:

  1. Parses buffer text -> ViewNode tree ('org_to_uninterpreted_nodes')
  2. Enriches with missing IDs/sources ('add_missing_info_to_forest')
     - New nodes get UUIDs; sourceless nodes inherit parent's source
  3. Validates tree structure ('find_buffer_errors_for_saving')
  4. Converts to placed types ('maybePlaced_to_placed_tree')
  5. Extracts save intents via local instruction collection
     ('extract_nonmergeSavePlan_locally' in
     'server/from_text/local_instruction_collection/'): one pure DFS
     preorder in which each buffer position reads only itself and its
     direct children plus a downward-flowing 'LocalContext', emitting
     per-field intents into a map keyed by PID. Downstream stages
     consume the map, in order: text-claim validation, lowering to
     NodeIntents, visibility resolution (subscribee-as-such signals
     -> subscriber hides/unhides), disk supplementation, the noop
     filter.
  6. Validates foreign nodes ('validate_and_filter_foreign_instructions')
  7. Builds nodeMerge instructions from the same map's
     (acquirer, acquiree) pairs ('nodeMerge_instructions_from_pairs')
  8. Updates graph ('update_graph_minus_nodeMerges'):
     validate first, write authoritative files, publish one graph generation,
     then enqueue the Tantivy delta
  9. Re-renders saved view and collateral views ('update_views_after_save')

  Key entry point: 'handle_save_buffer_request' in server/serve/handlers/save_buffer.rs.
  Key data flow: buffer text -> MpViewnode -> ViewNode -> CollectedIntents -> NodeIntent -> DefineNode (Save|Delete) -> filesystem/graph/Tantivy.

* Source (SourceName)

  Source is a SourceName (String wrapper) identifying which configured directory holds a node's .skg file. It is:
  - NOT serialized in .skg files — inferred from file location at load time
  - Stored in the complete in-Rust node and in Tantivy as a search field
  - Used by 'path_from_pid_and_source' to compute file paths: source.path / pid.skg
  - Governed by user_owns_it flag: foreign sources are read-only

  All graph relationships (contains, subscribes_to, etc.) reference nodes by ID, not by source. Source is purely about where the .skg file lives on disk.

* Relationships and the view system

  Graph relationships (all ID-based, source-independent):
  - contains: parent -> child ordering (Vec<ID>, order matters)
  - subscribes: subscriber -> subscribee (forking foreign data)
  - hides_from_its_subscriptions: filtering within subscriptions
  - overrides_view_of: an overrider node is drawn in place of the
    overridden node wherever it would appear as recursive content
    (override substitution; see glossary.md and docs/sharing-model.md)
  - textlinks_to: org-roam style [[id:...]] hyperlinks

  The view system is ephemeral scaffolding rebuilt every save:
  - ActiveNode: corresponds to an NodeComplete, can be Definitive (editable) or Indefinitive (read-only)
  - Scaffold: display-only nodes; the relation collections are
    PartnerCols (subscribeeCol, subscriberCol, overriddenCol, ...),
    plus AliasCol, IDCol, etc. (see glossary.md, "PartnerCol")
  - 'complete_viewforest' (server/update_buffer/complete.rs) is one
    level-order BFS used for both de novo views and post-save
    rerendering; per-collection reconcilers add and reconcile the
    scaffolds. (The older two-DFS-pass 'complete_viewtree' is gone;
    see TODO/DONE/local-view-update/plan_v2.org.)

* Recovery and source of truth

  The filesystem (`.skg` files plus `skgconfig.toml`) is authoritative. The
  immutable in-Rust graph and Tantivy index are derived from one full read at
  startup. The `rebuild ephemeral data stores` request constructs and
  validates a replacement graph/index generation before publishing it
  atomically. A restart repairs any crash after a successful file write but
  before derived publication.
