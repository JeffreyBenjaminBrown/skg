* Use short atomic functions, but long names

Try to provide a collection of atomic, readable functions, none of them too complex. On the other hand, when naming variables and functions, err on the long side -- the more understandable, the better.

* Avoid gratuitous renaming

Don't rename variables, let alone functions, without a good reason.
A lot of thought has gone into most of those names.
* mixing camel-case and snake-case in one name is helpful

Also I mix camelcase and snake case,
so that compound words like _inRustGraph_ can look like one token,
because that can make names much clearer. For instance
(continuing that example) if a function name includes _in_rust_graph_,
those three words look like an adjective phrase, when in fact they form a noun.
Sometimes it is similarly clarifying to camel-case
adjective or verb phrases into a single underscore-bracketed token.
* Some words are never used bare
Each of these names several things, so code and prose always say which.
The glossary ('docs/glossary.org') defines each kind.
- merge: nodeMerge or instructionMerge.
- snapshot: graph snapshot, git snapshot or buffer snapshot.
- index: search index, git index or graph index. Beside HEAD and
  worktree, git's index needs no qualifier.
- commit: git-commit, skgsave-commit or tantivy-commit. Where git is
  plain from context (HEAD, a merge commit, a git2 call), bare
  "commit" means a git-commit.
- generation: runtime generation ('RuntimeGeneration') or buffer
  generation (the clients' per-buffer request counter).
