* Use short atomic functions, but long names

Try to provide a collection of atomic, readable functions, none of them too complex. On the other hand, when naming variables and functions, err on the long side -- the more understandable, the better.

* Avoid gratuitous renaming

Don't rename variables, let alone functions, without a good reason.
A lot of thought has gone into most of those names.
* mixing camel-case and snake-case in one name is helpful

Also I mix camelcase and snake case,
so that compound words like _inRustGraph_ can look like one token,
because that can make names much clearer. For instance
(continuing that example) if a function name includes _in_rust_graph_,
those three words look like an adjective phrase, when in fact they form a noun.
Sometimes it is similarly clarifying to camel-case
adjective or verb phrases into a single underscore-bracketed token.
* Some words are never used bare
Each of these names several things, so code and prose always say which.
The glossary ('docs/glossary.org') defines each kind.
- merge: nodeMerge or instructionMerge.
- snapshot: graph snapshot, git snapshot or buffer snapshot.
- index: search index, git index or graph index. Beside HEAD and
  worktree, git's index needs no qualifier.
- commit: git-commit, skgsave-commit or tantivy-commit. Where git is
  plain from context (HEAD, a merge commit, a git2 call), bare
  "commit" means a git-commit.
- generation: runtime generation ('RuntimeGeneration'), buffer
  generation (the clients' per-buffer request counter), or ancestor
  generation (how far up the view an ancestor is: 1 = viewparent). A
  bare "generation" of a tree, counting down from its root, is fine.
- facts: change facts, a viewnode's '(diff ...)' parts (the three
  kinds of change, the leaves, the readiness).
- marker: changeset marker (a property viewnode standing for a set
  of changes) or commit-readiness marker (the '(ready ...)' part and
  its herald).
* Do not ask the reader to learn a distinction that does not exist outside skg
Two ordinary words that are near-synonyms outside skg must not be
given different technical meanings inside it. Outside skg, "unfold"
and "expand" are roughly equivalent, and nothing makes one of them
more pertinent to org folding than the other; so skg must not say
"unfold" for the org fold state and "expand" for drawing more of the
viewforest and expect a reader to keep them apart. When two things
need distinct names, make the names different in a way the reader
can see: a qualifier that says which thing is meant ("org-fold",
"viewforest-unfold"; in a longer symbol, 'orgFold' and
'viewforestUnfold'), not a pair of plain synonyms with a private
convention attached. The same applies to "fresh" versus "current",
"drawn" versus "shown", and any other pair whose difference a
newcomer could not guess.
* Please report any synonyms you encounter.
There's no need to go specifically looking for them,
but if you encounter them in the course of whatever you're doing,
please let me know. This includes plans in which I invent a new name
for something that already has an established one.
