* user-facing skg commands
** C-x C-s : skg-save
Each time you save, your view is rebuilt.
This is because you can put 'requests' into your view,
in which you request more data,
such as a node's ancestors, or the nodes that link to it.
Since views can overlap, saving one open view can change another.
You may edit several views at once, but if your first edit to a view
would dirty it while another view already has unsaved edits, Emacs
pauses that edit and asks; yes makes the edit, no cancels it. On save, Skg checks the other dirty
views' last clean text and current text against every graph identity the
prepared save can affect. A conflict is a hard refusal before any write;
the error names the views and IDs. Missing or malformed baseline data is
also refused conservatively. There is no "save anyway" choice.

If the current files for anything being saved select a title or body
from below that node's home, Skg stops before every write and offers
*Hoist* or *Abort*. Hoist publishes the selected text at home, removes
lower title/body copies, and preserves lower relationships and aliases;
the exact approved PIDs are reread and rechecked as one batch before the
save proceeds. Abort leaves every file byte-for-byte unchanged. Scripts
and maintenance writers have no prompt and refuse this repair.

That disk-publication choice is separate from displaying the result. If
a successful save under a restricted repo-set would rerender text from
an overPrivateText telescope, Skg asks for a second, request-scoped approval. Decline
leaves the save committed but sends no new view text and changes no
open-view registry entry.
** M-x skg-show-unsaved-changes : archive edits for manual recovery
Prompts for a local Org file, writes a detached recovery document, opens
it, and reports its actual path. The document contains context, lossless
JSON strings for the clean baseline and current text, and a readable
unified diff. It does not save graph data, close or clean the source view,
or register the archive as a live view.

When a save is refused, archive the relevant dirty views, close those live
views, save the remaining view, reopen fresh views, and manually reapply
the intended edits. Do not save an entire stale archived snapshot over the
newer graph. If dirty search results were enriched, the archive labels that
the diff also includes enrichment presentation and is not a semantic patch
of user intent alone.

** C-c f : text search
The 'f' is for 'find'.
*** how search works
**** the search ranking rules
"Rooty" nodes (roots, cycle members,
mentioned nodes, and nodes that had an org-roam ID before import)
are bumped in the ranking via their context-origin multiplier.
**** how search treats Skg repo restrictions
If the repo-set is restricted, if the search index contains any overPrivateText
telescope (one whose selected title or body lies below home), Skg asks
whether to include or exclude overPrivateText telescopes before running the query.
Exclude filters them in Tantivy before matching; Include is permission
for this search only. Under repo-set =all= they are included without a
prompt and the result carries a warning.
*** C-c f RET : skg-search
Text search across titles and aliases, returning every
matching node.

A node with the =NoSearchMatching= flag will not be found
(will not be a "hit") through
its title, aliases, or body in any search mode. It may still appear as graph
context around another hit and can still be opened by ID. This is a
decluttering preference, not privacy or access control. For example, a packing
list can mention “shaver” without that packing list itself matching a search
for shaver.

Prompts for search terms. All search axes take their conservative
defaults: no per-token regex, titles only (no body), no Tantivy
phrase and operator syntax.

Run 'skg-goto' (below) from one of the links in the search
results to open the view from that node.
*** C-c f i   : skg-search-interactive
Same as skg-search, but after the search terms it prompts:

: Type a character for each search option: (r)egex, (b)ody, (t)antivy syntax, (h)elp:

Type one character for each option you want, in any order,
then RET. An empty answer uses the same conservative defaults
as =skg-search=. Unrecognized characters are ignored. Typing
=h= opens this documentation (unfolded, with point on this
headline) and abandons the search.

- =r= (*regex*) — per-token regex instead of phrase search.
  Bypasses the query parser; each whitespace-separated piece
  is handed to Tantivy's 'RegexQuery'.
- =b= (*body*) — also search the body field (titles are
  always searched).
- =t= (*tantivy syntax*) — Tantivy phrase and operator syntax
  (AND/OR/NOT/+/-). In non-regex mode this passes through
  Tantivy's QueryParser (phrase quotes, grouping, field: all
  work; intra-word operator chars get escaped so =foo:bar=
  remains findable). In regex mode, AND / OR / NOT / +foo /
  -bar combine the per-piece RegexQueries at the document
  level, with conventional precedence and grouping by
  stand-alone parens; phrase syntax does not apply there. See
  the regex=true section below.
**** Query syntax with default axes (phrase/operators=false, regex=false)
Queries are literal. The query string is split on whitespace,
and any word containing a Tantivy operator character
(=+ - & | ! ( ) { } [ ] ^ " ~ * ? : \=) or the bare keyword
=AND= / =OR= / =NOT= is wrapped as a phrase so its contents
are searched literally. Words without specials pass through.
- *OR between words*. "dog cat" matches titles containing
  either word; a title with both outranks one with only one.
- *Literal special characters*. A title like "C++ tips",
  "[draft] plan", or "cat:dog" is findable by typing its
  literal text.
**** Query syntax with phrase/operators=true
The query is handed to Tantivy's QueryParser, with one
heuristic adjustment: any operator character sitting strictly
inside a word (with word chars on both sides, scanning
through consecutive operators within the same token) is
backslash-escaped. So =foo:bar= stays findable as a literal,
but =AND= / =OR= / =+foo= / =-bar= / ="fox in socks"= /
=(dog OR cat)= keep their operator meaning.

Known imperfection: the heuristic can't distinguish a
configured field name from a user word, so
=title_or_alias:dog= gets its =:= escaped too. Field-
qualified queries need manual =\:= in operators mode.
**** Query syntax with regex=true
The query is split on whitespace and each piece is handed to
'tantivy::query::RegexQuery' as its own pattern. Matches are
against *tokens*, not raw text: the indexer lowercases and
splits on whitespace, so no stored token ever contains a
space. That's why splitting is the only way multi-word regex
queries return anything. Patterns like =histor.*= work for
prefix search ('history', 'historical'), and =polit.* scien.*=
combines two such prefix searches. Combine with body=true to
also search body fields.

The regex *flavor is Rust's* (the =regex= crate), not Emacs's.
The inversion that bites Emacs users: bare parens =(...)= group
and bare pipe =|= alternates, while =\(= and =\)= are LITERAL
parens. =(cat|dog).*= is one valid piece; the Emacs-style
=\(cat\|dog\).*= would match only tokens containing literal
parens and pipes. A pattern must match the WHOLE token
(anchored), and tokens are lowercase.

The *=*= gotcha*: in regex =*= means "zero or more of the
previous character", NOT "any characters" (that's =.*=). So
=sci*= matches the tokens =sc=, =sci=, =scii=, … — not
"anything starting with sci". Use =sci.*= for that.

With operators=false, pieces are OR'd (SHOULD-combined)
like the non-regex default.

With phrase/operators=true (the wire flag is still
=operators=true=), the query is parsed as a boolean expression
over the pieces:
- Keywords: =AND=, =OR=, =NOT= (consumed, never matched as
  patterns). Bare adjacency between pieces means OR.
- Precedence is conventional: =NOT= binds tightest, then =AND=,
  then =OR=. So =poli.* AND sci.* OR fish.*= means
  "(poli.* AND sci.*) OR fish.*".
- *Grouping*: a paren is an operator-grouping token if and only
  if it stands ALONE between whitespace. =( poli.* AND sci.* )
  OR fish.*= groups; =poli.* AND ( sci.* OR fish.* )= overrides
  precedence. A paren ATTACHED to a pattern is regex syntax
  inside that piece, so =(cat|dog).*= still works. Groups nest.
- =NOT piece= (or the prefix =-piece=) excludes its piece
  within the enclosing group; =+piece= requires it even in an
  OR group. A group holding ONLY exclusions matches nothing
  (there is no positive clause to anchor it).
- Malformed operator syntax — a lone unbalanced paren, a
  dangling =AND= / =OR=, an empty query — is rejected with an
  explanatory error rather than silently reinterpreted.
Examples:
- =poli.* AND sci.*= — documents whose tokens include one
  matching =poli.*= AND one matching =sci.*=.
- =poli.* NOT bio.*= — documents matching =poli.*= and NOT
  any token matching =bio.*=.
- =+poli.* -bio.*= — same as above, without the keywords.
- =( poli.* AND sci.* ) OR fish.*= — the grouped conjunction,
  or anything with a token matching =fish.*=.
**** Caveats
- Each alias is indexed as its own document, so a query can
  match on an alias even when the title doesn't mention the
  searched word. The returned node is still the aliased one.
- Results are ranked by BM25 times a context-origin factor
  (Root 100×, CycleMember ~32×, Mentioned 10×, HadID 10×,
  MultiContained ~3.2×, everything else 1×). A weaker text
  match on a root can outrank a stronger match on a leaf,
  but every match is returned — search is never filtered by
  graph role.
- Regex distance is tokenwise: a pattern never spans
  whitespace, because we split the query on whitespace before
  handing the pieces to RegexQuery. A true whole-title regex
  (one pattern that matches across spaces) would need a
  separate non-tokenized =raw_title= field. Not done yet.

Scans the git status of every configured Skg repo and finds each

** C-c s : setting node properties
*** first some vocab: 'definitive' and 'write-protected'
A view of a node can be definitive or write-protected.
Typically the first place in the buffer that depicts a node
is the definitive view of it. So that other views of that node
cannot contradict it, they are 'write-protected': Edits to them
cannot affect the node they depict. They are also truncated --
that is, shown without content --
in order to prevent the view from becoming redundant and huge.
*** PITFALL: Don't make something 'definitive' by directly editing its metadata.
Instead, use skg-set-definitive, below.
That's because Skg has to make other instances of it
(in this same buffer -- and maybe in the future other buffers too)
write-protected. That's because a buffer can only be saved
if it has at most one definitive instance of a node.
Otherwise, two definitive nodes could contradict each other.

This same caveat does not apply to making a node write-protected.
While there does exist a command for that (skg-set-write-protected)
you can also 'do it yourself'
by visiting a metadata buffer for the node (skg-view-metadata).
*** C-c s d : skg-set-definitive
If you want to see the definitive view of that node
from a place where it is currently shown in a write-protected form,
call this function. It will make the current definitive view
(if it exists) write-protected, and then draw a definitive view here.

*** C-c s r : skg-set-relRepo
Sets the relRepo of the relationship instance the headline at
point represents -- =contains= for a content child, the folder's
relation for a writable PartnerFolder member, or the alias membership
for an alias headline. An Unknown placeholder in one of those writable
positions is supported too: it carries only its raw relationship member ID,
never a node edit. (Formerly
=skg-privatize-relationship=; renamed because the gesture now moves
privacy in both directions, see
=BUG-and-fix_make-edge-more-public.org=.)

For a node-to-node edge, the command asks the server for its default
relRepo and current relRepo (the
"relRepo info" endpoint), then prompts -- with both
tab-completion and S-left/S-right cycling, like the other Skg repo
dialogs -- over the Skg repos at least as private as the default (more
public ones could leak an endpoint's ID and would be rejected at
save), plus a no-override choice. The minibuffer starts pre-filled
with a pending request when it is offerable, else the current relRepo
or default, so RET keeps the most specific available choice. If the server cannot resolve the edge
(e.g. a node not yet saved), every Skg repo is offered and the save's
floor check backstops. For an alias, its default is its owner's home
and the current relRepo is read directly from the alias metadata, so
no synthetic graph edge or broader endpoint is needed.

For an edge from an owned owner to a foreign member, the default is
the owner's home regardless of privacy order. That choice deliberately
shares the foreign ID and relationship with readers of the owned
Skg repo; Skg never offers the foreign Skg repo as a write destination.

Choosing a Skg repo writes an =(editRequest (relRepo REPO))= metadata
request. This
both raises privacy above the default and lowers it back down to
(never below) the default -- the way to publicize an edge stuck at
an old, more private Skg repo after its endpoint's home moved. An edge
sitting more private than its default is marked with a red =~NAME= herald
immediately before the ⌂ Skg repo herald; once saved at its default,
request and display herald disappear.

The no-override choice removes the request, which means "no opinion":
a saved edge keeps its saved Skg repo (sticky). It does NOT reset the
edge to its default -- to reach the default, choose it.

Refuses with an error when point is on a member of a write-protected folder
(subscriberFolder, overriderFolder, hiderFolder, hiddenFolder,
hiddenInSubscribeeFolder, hiddenOutsideOfSubscribeeFolder): the
relationship belongs to the other end there, so setting its Skg repo
from this side would be meaningless. Also refuses on a root
headline, which represents no edge.

The command only edits the node's metadata in the current buffer.
Save the view afterward to apply the change.

Note that the name 'skg-set-relRepo' is somewhat misleading.
Normally, by 'relationship' we mean
'a relationship between two nodes in the graph'.
But for this command we need to broaden the definition to
'a relationship from what this viewnode represents
(which might be an alias) to what its parent represents (a node in the graph)'.

With a prefix argument (=C-u C-c s r=) it instead runs
'skg-set-relRepo-recursive', described next.
*** C-c s R : skg-set-relRepo-recursive
Like 'skg-set-relRepo', but applied throughout the
subtree at point (the node at point's own edge to its view-parent
included). Also reachable as =C-u C-c s r=.

It first presents an org-menu asking what kind of relationships to
the view-parent should qualify: the schema's five node-node
relations are the level-1 headlines, and each level-2 headline is a
role the view-CHILD would play in that relation toward its
view-parent. Only three roles are settable from the child's
position -- =contained= (ordinary content), =subscribee= (a
subscribeeFolder member) and =overridden= (an overriddenFolder member);
RET on any other role explains why its edge cannot be set from
there (write-protected folders belong to the other end; links carry no
independent Skg repo; hide Skg repos are derived at save). RET picks a
role; q aborts.

It then prompts for a Skg repo over the whole ladder, plus the
no-override choice, which instead REMOVES existing Skg repo requests
throughout the subtree. Unlike the single-edge command, no
per-edge default is fetched -- the subtree's edges have different
defaults -- so every Skg repo is offered and the save's floor check
validates each edge (an offered Skg repo more public than some edge's
default makes the save fail, naming that edge).

The walk applies to, and recurses on, only viewchildren that affect
their viewparents: affectsParent=true activeNodes, through the two
writable folders. It prunes below write-protected nodes and
subscribee-as-such members (their org-children's edges are not
collected at save), and prunes write-protected folders and other non-vognodes
entirely.

This is the gesture for republicizing a subtree's relationship
edges after 'skg-set-repo-recursive' moved its nodes to a more
public Skg repo: the sticky rule keeps each edge at its old, more
private Skg repo, so the contains edges stay behind until explicitly
moved to the new default (see
=MAYBE-BUG_recursive-move-to-more-public-leaves-relations-private.org=).

The command only edits metadata in the current buffer.
Save the view afterward to apply the changes.

** C-c {i|u|o} : IDs, links and the linkstack
*** some background
**** IDs are mostly invisible, but good to know about.
Every node has an ID,
which you can see if you disable skg-view-heralds-mode.
Every link also has an ID and a label,
but all you see when you look at the ID is the label,
unless you disable org-mode (say, by switching to text-mode).
You should never need to see IDs explicitly.
**** The linkstack
is, like it sounds, a stack of links.
A stack is just a list that you interact with,
mostly from one side, the 'top':
You can 'push' something onto the top of the stack,
and you can 'pop' something off of the top of the stack.
But you can also jump to a view of your entire stack,
using (copying, pasting, deleting) it
without any restrictions on order.
*** C-c i n : skg-id-next
Makes the cursor hop among two kinds of IDs:
The ID associated with a node in the view,
and the ID associated with a link in a node's title.
Every node has an ID,
but a title can include multiple or no links.
*** C-c i p : skg-id-prev
See skg-id-next, above.
*** the stack of links/ids

**** C-c O i : skg-pop-id
Like skg-paste-id,
but also removes the node from the stack.
**** C-c o l : skg-paste-link
Inserts, at the cursor, a link to the node

**** C-c O l : skg-pop-link
Like skg-paste-link,
but also removes the node from the stack.

This is the easiest way to give a node multiple containers --

Inserts, at the cursor, a write-protected view

** import and export
*** skg-import-md-and-org : additive mixed-document import
:PROPERTIES:
:CUSTOM_ID: import-md-and-org
:END:
**** ordinary usage
Run =M-x skg-import-md-and-org= with the server running. Choose an absolute
directory in the server/container filesystem and an existing owned Skg repo.
That Skg repo determines where every new node will be written. The importer scans
exact =.md= and =.org= files recursively, skips symlinks and =.git=, and
leaves the originals untouched.

Review the preview of files, generated =.org= export paths, and warnings,
then explicitly approve or decline. Approval applies only to that preview;
another run requires a new one.

The operation creates file-root and heading nodes,
which correspond 1-to-1 to sections of the imported data.
A document whose only top-level heading has nothing before it
is that heading, so the heading is its file root;
otherwise the file root is titled after the document.
It also creates two kinds of nodes that do not so correspond:
- a single import-record node with links to all file roots,
  so you can see everything you just imported in one place.
  The import result buffer links to it; follow the link with =C-c g RET=.
- an export marker under each root,
  so you can export back to the same path if you want.
  But this is dangerous -- see "Re-export is dangerous" below.

The importer does not merge into existing nodes,
copy attachments, synchronize later edits, or automatically export.

Only document structure, selected metadata, links, and named Markdown
footnotes are interpreted. Other Markdown/Org markup remains readable text,
not a full format conversion. Unresolved links and unsupported constructs
are left in place with warnings.

Only links to =.md= and =.org= files are resolved, or warned about.
A link to any other file (source code, an image, a folder) keeps pointing
where it did, written as an Org link, without a warning.

**** Re-export is dangerous.
Subsequent Org export is for reading, not
a round-trip backup: it does not preserve Markdown syntax or all Skg graph
semantics. Exporting to the original input directory would overwrite matching
=.org= files, while leaving =.md= files alone. There is no dedicated undo or
crash-recovery transaction; keep the originals and back up the owned Skg repo.

**** Skg asks for a host-root mapping if it finds absolute links to documents.
Skg runs in a Docker container.
The folder /home/ubuntu/host in that container
corresponds to some folder on the host system.
If the files to be imported contain absolute links
to =.md= or =.org= files,
skg needs to know how those host-system paths
correspond to paths in the docker container.

**** Link syntax in literal text is an example, not a link.
In an Org file, the importer leaves alone any link written inside text
that Org shows literally:
- inline =verbatim= or ~code~, like =[[id:ID][label]]=,
- a fixed-width line, which begins with a colon and a space
  (=: [[id:ID][label]]=), or is a lone colon,
- a =#+begin_...= / =#+end_...= block of any kind, and
- a =```= fence (Markdown syntax, but common in Org files too).
Such links are not resolved or rewritten, and do not produce warnings.
Backticks (=`code`=) are not literal in Org, so a link inside them is a link.
Use =verbatim= or ~code~ instead.
(To insert a block in Emacs, use =C-c C-,=, which is =org-insert-structure-template=.)
The rest of Skg (saving, link statistics, link annotations, export)
treats links in literal text the same way.

**** An Org heading inside a block or fence stops the import.
If a line of an Org file looks like a heading (asterisks at the start of
the line, then a space) but is inside a =#+begin_...= block or a =```= fence,
nothing is imported, and the preview explains which lines are the problem.
Org would read the line as a heading and end the block there,
so Skg cannot tell what was meant.
Often the block was never closed.
If the line belongs inside the block, escape it with a leading comma
(=,* ...=), as Org does. This check applies only to Org files;
in a Markdown file, a =#= line in a code block is ordinary code.

**** Imported Markdown hard breaks become Org's two-backslash hard breaks.
In Markdown you can put a slash or two spaces after a line
to ensure that the next line is shown on a separate line,
rather than smooshed into a single flowing paragraph.
In Org, such a "hard break" is represented by two slashes,
so the importer makes that conversion.

*** importing from org-roam
:PROPERTIES:
:CUSTOM_ID: import-org-roam
:END:
**** import-org-roam : terminal command
This imports Org-roam '.org' files into Skg. It is a Cargo subcommand,
not an Emacs command, and needs no running server. Unlike the additive
interactive importer above, this legacy command replaces its destination.

Run from the repository root, where Cargo and the input files are available:

#+begin_src sh
cargo run --bin skg -- import-org-roam ORG_DIR OUTPUT_DIR REPO_NAME
#+end_src

All three arguments are required. 'ORG_DIR' contains your Org-roam notes;
'OUTPUT_DIR' receives the '.skg' files; 'REPO_NAME' names the destination
Skg Skg repo. For example, using a fresh staging directory:

#+begin_src sh
cargo run --bin skg -- import-org-roam /imports/org-roam /tmp/skg-import-review imported-notes
#+end_src

Paths are relative to the process's working directory unless absolute.
Inside Docker, supply container-visible paths. There is no host-path
mapping argument or interactive prompt.
**** Before running: the destination is replaced
First, if any input file has a line that looks like a heading inside a
'#+begin_' block or a fence, the command stops, naming those lines, and
nothing is deleted or written; see
[[*An Org heading inside a block or fence stops the import.][the same check in the interactive importer]].
Otherwise the importer creates 'OUTPUT_DIR' if necessary, then deletes every
immediate '.skg' file already in it, before importing the input. There is no confirmation,
dry run, merge-with-destination mode, or automatic backup. Other files and
nested directories are left alone. Use a fresh staging directory and inspect
the result before replacing existing data.

An incorrect or unreadable input can leave the destination empty. Traversal
errors are skipped; unreadable files and files without the required file-level
ID silently produce no nodes. The report counts files read, nodes written,
and write errors, but a successful exit does not establish that every input
was imported. Check the output against your originals.
**** What is imported
The scan recurses for the exact extension '.org', skipping '.git' directories.
Each file must begin with a ':PROPERTIES:' drawer containing ':ID:'.
Indentation on that first drawer line is accepted; blank lines before it
are not. Files without this file-level ID are skipped even if headings have IDs.

Each accepted file becomes a node, titled from '#+title:' or, if absent,
the filename without its extension. Each heading becomes a node, with
ordered 'contains' relationships representing the outline. Existing IDs are
retained; headings without IDs get fresh UUIDs on every run. Some skipped
heading levels introduce grouping nodes titled 'These are special!' and
'These are normal.' rather than reproducing the outline literally.

'ROAM_ALIASES' becomes Skg aliases. Nodes with an original ID receive the
'Had ID before import' flag. Duplicate IDs within the input
are merged: children and aliases are combined, and additional titles and
bodies are appended with a separator. Such nodes receive 'Was overloaded
during org-roam import'. This does not compare or merge with existing
nodes in your configured Skg Skg repos.
***** Text and links
Bodies are copied with whitespace normalization. Parsed property drawers
are consumed; properties other than 'ID' and 'ROAM_ALIASES' are not retained
from those drawers. The parser uses line-based heading detection, so this
is not a lossless general-purpose Org conversion.

Existing =[[id:ID][label]]= links retain their targets. File links and heading
search links are not converted to Skg ID links, and attachments are not copied.
Relative file links may no longer resolve after import. The importer does not
validate that linked IDs exist. It creates no subscriptions, hides, or overrides.
**** Making the imported data available in Skg
The command writes one 'ID.skg' file per resulting node. It does not edit
configuration, start the server, or refresh a running server's graph and
search index. 'REPO_NAME' labels the Skg repo during conversion; the permanent
Skg repo association comes from the configured directory, not a Skg repo field
inside each file.

After reviewing the output, place it in the intended owned Skg repo directory
and configure that Skg repo with the intended name and privacy order. See
[[file:api-and-formats.org][the configuration reference]]. Check for ID collisions with existing Skg repos
before loading: the importer itself does not check them.

For a first setup, configure the Skg repo before starting Skg. When replacing
existing data, save and close affected views and stop the server before
changing the files in its Skg repos, then restart it. If files in an already configured
Skg repo changed while the server remained running,
'M-x skg-rebuild-ephemeral-data-stores' reloads them; close stale views and
open fresh ones before editing. Configuration changes require a restart.

The Cargo command prints a reminder to commit the imported files so Git
diff views have a baseline; it does not run Git. Reimporting replaces the
destination and gives ID-less headings new IDs, so it is not an incremental
update workflow. Keep your originals and a backup of Skg edits you want to
retain. [[file:undoing-import.org][Exporting back to Org]] does not restore the original files or all graph
semantics.
**** bash/import-org-roam.sh : host-side Docker and Git wrapper
[[file:../bash/import-org-roam.sh][This script]] accepts 'REPO DEST NICKNAME' and prompts for a Docker
container. Unlike the Cargo command, it offers to remove the destination's
'.git' directory as well as its '.skg' files, then runs the importer,
initializes Git, stages the destination, and opens an editor for a commit.
Declining its cleanup prompt does not prevent the underlying importer from
deleting existing '.skg' files.

It also offers to request a server rebuild, reading the port from 'SKG_CONFIG'
(default 'data/skgconfig.toml'). Its Docker working directory is hard-coded
to '/home/ubuntu', while host-side paths use the shell's working directory.
Check that the mounts and paths identify the intended directories on both
sides. Use the Cargo command directly when you do not want Git operations.
*** skg-export-some-to-org : exporting to org
:PROPERTIES:
:CUSTOM_ID: export-org
:END:
Exports Skg data to plain =.org= files, so the data can be read
(and navigated on GitHub) without running Skg. No keybinding.

It asks two things:
- the most private Skg repo to include. The export includes
  that Skg repo and every Skg repo more public than it.
  Choose all to include every Skg repo.
- which directory to write to (default =org-exports=). This path
  is interpreted *by the server*, relative to the project root the
  server runs from. Because the server may run inside a Docker
  container whose filesystem differs from the host Emacs runs on,
  this prompt has no tab completion. An absolute path is used
  as-is.
  Existing files in the output dir are overwritten in place; other
  files there are left untouched.
  A body line Org would read as a headline (such as a Markdown
  =* item=) is indented two spaces, making it a list item, or inside a
  =#+begin_= block is escaped with a comma, as Org itself does.

**** choosing what to export: export markers
Nothing is exported unless you mark
it. To make node N into an exported file,
make N contain a child node, called an /export marker/, such that:
- The marker's title contains a link to the ID
  =3d9aa9be-d95a-48bc-b362-33f9e7ebdf6f=.
  That ID is a fixed constant that the exporter looks for.
  The node it names only documents this feature.
  The link works even if your Skg repos do not contain that node.
  The link's label is up to you, for example:
  : [[id:3d9aa9be-d95a-48bc-b362-33f9e7ebdf6f][Export to Org]]
- The marker's body contains a line saying where to write the file,
  relative to the output directory and without the =.org= extension:
  : target_filepath = docs/setup
  Quote the path if it contains whitespace
  (=target_filepath = "my notes/setup"=).
  The path cannot be absolute or contain =.= or =..= components.

N is then written to =<output-dir>/<target_filepath>.org= as a
recursive content view: N's title and body,
each of its content nodes' titles and bodies,
each of *their* content nodes' titles and bodies, etc.,
stripped of Skg metadata. The export marker itself is left out of the file.
N's position does not matter; it can be anywhere in the graph.
But N must belong to a Skg repo included in the export;
otherwise it is skipped, with a warning.
If N has several markers, the first one is used, with a warning.
If two nodes claim the same path, only one of them is exported, with a warning.

A node whose title links to that ID but whose body has no =target_filepath=
line is not a marker. It is exported as ordinary content, so you can
mention the feature in your notes without triggering it.
If the =target_filepath= is malformed, the node is dropped from the
export, N is not exported, and you get a warning.

[[#import-md-and-org][skg-import-md-and-org]] adds a marker to each
imported document automatically.

**** links and overlap
Links are rewritten to relative org links. Link syntax that Org shows
literally (in =verbatim= or ~code~, a fixed-width =:= line, or a
=#+begin_...= block or code fence) is an example, and is left alone. A link to another
exported file's root points at that file; a link to a non-root
node points deep, to the relevant headline of the document,
via =[[./file.org::*Heading][label]]=.
Links in headlines are kept. Org cannot find a headline containing
a link by its text, and finds only the first of several headlines
with the same text. So a link to either kind of headline uses its
node's ID instead, =[[./file.org::#ID][label]]=, and that headline
gets a =:CUSTOM_ID: ID= property. Only headlines something links to
get one.

if an exported node contains another export root,
the second root’s contents go in its own file,
and are not duplicated into the first.
The first instead gets a heading linking to the second file.

A link whose dest
is not exported under the chosen set points to a "some links
might be broken" note.
**** privacy
If a restricted export would include overPrivateText telescope text, Skg asks for
approval for each such ID before writing any file. Repo-set =all= exports
it with a warning. The noninteractive form "fails closed" (fails before writing any files) unless passed
=--include-overPrivateText-telescopes=:

: cargo run --bin skg -- export-org [config-path] [repo-set] [output-dir] [--include-overPrivateText-telescopes]
