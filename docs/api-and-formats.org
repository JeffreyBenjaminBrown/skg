* API

Communication between Rust and Emacs is via TCP on port 1730, configurable in any skgconfig.toml. The connection is persistent.

After initialization, every server response is length-prefixed as
=Content-Length: LENGTH\r\n\r\nPAYLOAD=; =LENGTH= is the number of
UTF-8 bytes in =PAYLOAD=. The exceptional busy-initializing signal is
described below.

Many responses carry their main payload in a =(content "...")= field.
That field is just "the payload": it has nothing to do with a node's
=contains= list or the "content view" (though a content-view response
has one too).

A string atom in a response is double-quoted when it is empty, or
holds a double quote, whitespace, or a number; any other string atom
is a bare symbol. So an empty view arrives as =(content "")=.

The shared overPrivateText-telescope release warning is
=OPERATION includes title or body text selected below its node's home
repo for PID P.= (or =PIDs P1, P2, ...=). A restricted request that
needs approval instead receives
=((response-type overPrivateText-telescope-confirmation) (operation OPERATION)
(pids ("P" ...)) (prompt "..."))=; the response itself contains no
protected title or body. Except for search's include/exclude choice,
approval is always the exact request-local list
=(approved-overPrivateText-pids "P" ...)= and is never cached.

So far there are these endpoints:

** Verify connection
  - Request: ((request . "verify connection"))
  - Response: LP =((response-type verify-connection) (content "This is the skg server verifying the connection."))=.

** Text search
  - Request: =((request . "text search") (terms . "SEARCH_TERMS")
    (regex . "BOOL") (body . "BOOL") (operators . "BOOL"))=, plus
    optional =(overPrivateText-telescopes . "include")= or
    =(overPrivateText-telescopes . "exclude")=.
    - Search always returns every match. Prominent nodes (literal roots, cycle-roots, mentioned nodes, and things that had an ID when imported) are ranked higher, via their prominence multiplier.
    - =regex=, =body=, =operators= are optional; each defaults to "false".
      - "regex=true": interpret the query as a per-token regex; a RegexQuery is built directly and the QueryParser is bypassed.
      - "body=true": also search node bodies (titles are always searched).
      - "operators=true": preserve Tantivy phrase and operator syntax (AND / OR / phrase / +foo / -bar / grouping / field:). Intra-word operator chars still get escaped heuristically so C++ etc. remain findable. In regex mode, the query is parsed as a boolean expression over the per-token regexes: AND / OR / NOT / +foo / -bar, conventional precedence (NOT > AND > OR, bare adjacency = OR), and grouping via parens that stand alone between whitespace (a paren attached to a pattern is regex syntax within that piece). Malformed operator syntax is an error; phrase syntax does not apply. Detailed in docs/COMMANDS.org.
    - The skgrepo restriction is applied before grouping, ranking,
      alias/title selection, and display truncation. Restricted-skgrepo
      documents do not influence result order or which title/alias is
      shown for an unrestricted result.
    - =overPrivateText-telescopes= is normally absent on the first request. Under
      a restricted skgrepo-set, if the search index contains any telescope
      whose selected title or body lies below home, the server does no
      query and responds with LP
      =((response-type overPrivateText-telescope-confirmation)
      (operation text-search) (pids ()) (prompt "..."))=. The empty PID
      list is deliberate: a pre-query decision must not disclose which
      overPrivateText node might match. The retry uses ="include"= or ="exclude"=.
      Exclusion is applied inside the Tantivy query, before matching,
      and remains in force through asynchronous enrichment. The choice
      is request-scoped. Skgrepo-set =all= needs no choice and returns a
      warning if the results include overPrivateText telescopes.

  - Phase 1, immediate: Server sends LP =((response-type
    search-results) (content "ORG") (warnings ("..." ...)))=.
    Results are ordinary write-protected occurrences, the roots of the
    search buffer (not special non-vognode kinds). A no-match or error response has the same
    response type and a single =content= field.

  - Every =search-results= is followed by exactly one
    =search-enrichment=, which is what releases the client's stream
    guard. (The overPrivateText challenge above sends neither.) When no
    enrichment is coming, that message omits =content=:
    =((response-type search-enrichment) (terms "TERMS") (warnings (...)))=.
    The client then leaves the search buffer alone and shows any
    warnings. This happens immediately after a no-match or error
    response; when the client closes the search view (=close view= of
    =search:TERMS=) before enrichment arrives, after the close-view
    response; and when the server cannot enrich a buffer snapshot, with the
    reason as a warning.

  - Phase 2, enrichment: A three-message sequence:
    1. Rust sends LP response-type "request-snapshot" with =(("content" "TERMS"))= — asking Emacs for a snapshot of the search buffer matching those terms.
    2. Emacs replies with =((request . "snapshot response") (terms . "TERMS"))\n= followed by =Content-Length: N\r\n\r\n<buffer text>= — the current buffer contents, dirty or not. Emacs sets the buffer to readonly before sending.
    3. Rust parses the buffer snapshot and refreshes it as a stub
       ('enrich_search_viewforest'): each hit, a write-protected
       occurrence, asks for its containers folder ('(folder
       containers)'), and holds an empty overrider and overridden
       folder when it has such relatives; the refresh fills the
       folders and draws each member's containerward chain. Rust then
       sends LP response-type "search-enrichment" with =(("terms"
       "TERMS") ("content" "ORG") ("warnings" (...)))=. Emacs replaces
       the buffer and exits readonly. A refresh shows each hit with
       its node's title, so a hit that matched by an alias shows the
       alias in the first phase and the title in the second.
    - Enrichment uses the same skgrepo restriction as the original
      search. The containerward chain stops before restricted
      containers.
    - Under each result hang, folded, its containers folder, whose
      members carry the containerward chain; its overrider folder,
      the visible nodes that override it; and its overridden folder,
      the visible nodes it overrides. A folder with no member is not
      drawn. The members are write-protected. A matching node
      recursively overridden by an owned result is suppressed at the
      top level; if the owned result overrides it directly, it
      reappears in that result's overridden folder.

** Single-root content view from ID
  - Request: =((request . "single root content view")
    (id . "NODE_ID") (view-id . "VIEW_ID")
    (approved-overPrivateText-pids "PID" ...))=
  - Response: LP =((response-type content-view) (content "...")
    (errors ("..." ...)) (warnings ("..." ...)))=. The document
    structure is detailed below, under =Content view=.
    Under a restricted skgrepo-set, a response involving an overPrivateText
    telescope instead returns LP =overPrivateText-telescope-confirmation= with
    =(operation single-root-view)=, the exact PIDs, and a text-free
    prompt. An approved retry carries those
    exact PIDs in =approved-overPrivateText-pids=; approval is not cached.
    Skgrepo-set =all= returns the ordinary response with a warning.
  - If =NODE_ID= resolves to a restricted skgrepo, the server refuses the
    request with a human-readable message and does not open a buffer.
    Following a link to a restricted-skgrepo node behaves the same way.
  - The requested node opens as itself, shown raw. Because the raw root
    is an overridden node shown raw, its immediate children are also shown
    raw (one level); substitution resumes at the grandchildren. See
    "Override substitution" below. Override facts can be inspected in
    search results' override folders and in explicitly requested
    override folders.

** Save buffer
  - Request: First =((request . "save buffer") (view-id . "VIEW_ID") (point-lines-below-focused-headline . "N") (point-column . "C") (point-screen-lines-below-window-start . "M"))\n=, then one UTF-8 length-prefixed S-expression envelope:
    #+begin_src lisp
    ((saved-buffer "...Org text...")
     (other-views
       (((view-id "...") (dirty false))
        ((view-id "...") (dirty true)
         (baseline (present "...last clean text..."))
         (current "...edited text..."))
        ((view-id "...") (dirty true)
         (baseline unavailable)
         (current "...edited text...")))))
    #+end_src
    =Content-Length= is the envelope's UTF-8 byte length. =other-views=
    is mandatory even when empty and covers every other live client view,
    including views the server has not registered. Clean entries carry no
    buffer snapshots. Dirty entries carry exact current text and either the exact
    clean baseline or explicit =unavailable=. Duplicate view IDs, the saved view ID,
    missing fields, and inconsistent clean/dirty fields are rejected. Raw Org
    in place of the envelope is not a supported legacy form.
    - Two optional fields drive the fork-confirmation round-trip
      (below): =(approved-forks . "true")= marks a re-issued save whose
      forks the user approved, and
      =(fork-repos ((N . REPO) ...))= pairs each forked node's id
      N with the owned skgrepo chosen for its clone. Both are absent on
      an ordinary save.
    - =(strandeds-reviewed . "true")= and =(reset-strandeds ("RELATION"
      "RECORDER" "MEMBER") ...)= are present only on a retry after
      =strandeds-confirmation=: the first says the user reviewed the
      stranded relationships, the second names those to reset to default
      (possibly none).
    - =(approved-hoist-pids "PID" ...)= is present only on a retry
      after =telescope-hoist-confirmation=. It is the exact list the
      user approved for text publication; it is not a boolean and
      does not authorize any other PID or bypass ordinary save
      validation.
    - =(approved-overPrivateText-pids "PID" ...)= is the shared text-release
      approval field. On save it appears only when retrying a
      =save-rerender= =overPrivateText-telescope-confirmation=, and authorizes
      those exact PIDs for that response attempt. It is independent of
      Hoist authority: viewing text and publishing it on disk are
      different decisions.
    - =point-lines-below-focused-headline= is global to the buffer save: the number of text lines from the focused headline to point before save.
    - =point-column= is global to the buffer save: the column of point within its line, echoed back so the client can restore the exact cursor position.
    - =point-screen-lines-below-window-start= is global to the buffer save: the number of screen lines from the window's top line to point before save. The server echoes all three point fields in the final save response so Emacs can restore point and scroll position after replacing the buffer text.
  - Response: Multiple length-prefixed messages, sent sequentially:
    1. Early lock acknowledgement (sent immediately, before reading the envelope):
       =Content-Length: N\r\n\r\n((response-type save-lock) (lock-views ("view ID1" "view ID2" ...)))=
       Both clients lock every local Skg view before taking the request's
       buffer snapshots. This message acknowledges that broad lock; its server-known
       view ID list does not authorize unlocking client-only views.
    2. Save-relax-lock message (sent after preparation and conflict checking, before mutation):
       =Content-Length: N\r\n\r\n((response-type save-relax-lock) (lock-views ("view ID1" "view ID2" ...)))=
       The keep-set contains selected collateral targets and every dirty view
       whose baseline/current buffer snapshots were checked, including unregistered
       views. The saved view is retained implicitly. Only unrelated clean
       views may unlock at this point. A malformed narrowing message leaves
       all locks held until terminal cleanup.
    3. Zero or more collateral-view messages (one per collateral view, streamed as each finishes):
       =Content-Length: N\r\n\r\n((response-type collateral-view) (view-id "VIEW_ID") (content "..."))=
       Emacs unlocks and updates each buffer as it arrives.
    4. Final save response:
       =Content-Length: N\r\n\r\n((response-type save-result) (content "...") (errors ("..." ...)) (warnings ("..." ...)) (corrections (("VIEW_ID" "..." ...) ...)) (point-lines-below-focused-headline N) (point-column C) (point-screen-lines-below-window-start M))=
       =content= is the re-rendered saved buffer (nil on failure). =errors= is a list of failure-explaining strings. =warnings= is a list of nonfatal messages. Both lists are present and empty if none.
       =corrections= holds what the refresh corrected in each view the
       save refreshed, the saved view and the collateral ones: one
       list per view with buffer corrections, its view ID first, then one
       message per buffer correction (see "How a message names a headline"
       below), such as =("content-view:5" "Drew what the graph says
       belongs here.\n*** new child\n- viewnode ID: 0d. ...")=. A
       buffer correction is a headline the refresh changed because the
       buffer contradicted the graph (reinstated, entombstoned, marked
       =noClaim=, joined by a viewnode merge, re-kinded, or an edit
       request dropped). What
       the refresh draws as extent is not one: the content of an
       occurrence it extends first, the members of a folder first
       requested, a fresh view's content. So a reinstatement is
       reported only where a list already drawn lacked a member, and a
       plain save reports nothing. The list is present and empty if
       none; a failed save's response has no =corrections=. A buffer
       of the diff view reports its buffer corrections too, but for its change
       viewnodes, which describe the straddle and are recomputed at
       every refresh. Each client appends them to its
       warnings buffer (see "Server warnings" below), under one level-1
       headline per view naming the view's buffer (or its view ID when
       no buffer shows it).
       Each message names the headlines it concerns as subheadlines
       (see "How a message names a headline" below). A failed save
       sends one error, =NOTHING WAS SAVED=, whose validation errors
       follow as =** Error N= headlines.
       When the saved buffer is one of the diff view's, the response
       ends with =(readiness-summary (ready N) (changed M) (foreign F) (order-only O) (notEditable K))=:
       of the M changed files of the owned skgrepos (O of them changed only
       in order, and so ready), N are commit-ready; F files changed in
       foreign skgrepos; and K changes are not editable in the view: they
       are recorded by nodes whose changes the buffer does not make editable. A
       buffer makes a node's changes editable where it has an editable
       occurrence of it, in content or in a partner folder, or a
       ghost of it in content position: under the buffer
       root or an occurrence, or in the old content of such a
       ghost. The buffer is refreshed over the graph straddle: its
       roots, and every headline it holds editable, stay as saved, and
       its change facts, change viewnodes and removed members are
       recomputed. What it adds anew it adds by its pruned
       change view sets recomputed after the save: a new member in U is editable,
       with its content list, and any other new member is a
       write-protected member shown without its content. It
       makes no occurrence editable and appends no root; the "integrate
       unshown changes" request below does. An editable-view request
       cascades as in any view, and only the extension of a node
       outside U spends =initial_node_limit=; nothing else in the
       buffer spends that budget.
  - Readiness requests (=(ready OBJECTS)= and =(unready OBJECTS)=
    inside a headline's =(editRequest ...)=; see "Metadata of the
    diff view") are
    consumed by a save of any buffer, not only one of the diff view's,
    after its graph edits succeed: each sets or clears the marks of the
    change-forest leaves its headline names, at their current
    fingerprints. A save that stops for a confirmation (strandeds,
    Hoist, forks) or fails consumes none, and leaves them in the
    buffer. A request that names no current change is dropped, with
    the warning =A readiness request names no current change; it was
    dropped.=, which names its headline as a subheadline.
  - A write-protected occurrence saves nothing of its own, so a save is
    refused, before anything is written, if one differs from the graph
    ('errors_for_writeProtected_occurrences' in
    'server/from_text/write_protected_edits.rs'): in its title or home
    skgrepo, or in its alias folder, when present, by lacking or
    reordering one of the node's aliases or by carrying a relRepo
    request. Under a write-protected occurrence no child claims
    membership, so anything else standing there -- an alias the node
    lacks, a child, a folder's members -- is the user's note or the
    diff view's, which the refresh shows unwarranted, and is not
    checked. An ID folder, under any node, is refused only when it
    lacks one of the node's IDs; and a present flags folder, under any
    node, must equal the node's flags.
  - Before mutation, the server computes the update-relevant neighborhood of
    every prepared write/delete identity independently in the before and
    candidate graphs. Other registered views containing an affected unrestricted ID
    are rerendered. For every dirty client view, the server parses and unions
    dependencies from its clean baseline, current text, and registered forest
    when present. Any intersection refuses the save conservatively; malformed
    or missing dirty dependency data also refuses. A refusal returns
    =save-result= with nil content and actionable errors naming view IDs and
    IDs, and performs no filesystem, graph, search index, registry, or collateral
    update. There is no save-anyway path.
  - Moving a node between skgrepos: for each home skgrepo move the server
    finds every relationship touching the moved node, in either
    direction and whether or not a view shows it, that sat at its
    default relRepo and that the sticky-else-default rule would leave
    off its new default ('server/from_text/strandeds.rs'). One left more
    public than its member's new home (an inbound relationship of a
    privatizing move) is raised to the new default, and the save's
    warnings say so. If any other remains and the request lacks
    =(strandeds-reviewed . "true")=, nothing is skgsave-committed and the
    server replies, before any other decision and in place of
    save-result,
    =((response-type strandeds-confirmation) (strandeds (((relation
    "contains") (recorder "R") (member "M") (relRepo "REPO") (default
    "REPO")) ...)) (prompt "..."))=, with IDs but no titles. The
    client re-issues the same save with =(strandeds-reviewed . "true")=
    and the chosen =(reset-strandeds ...)=; the server resets those
    to their new defaults, saving each recorder (outside the view or
    not), so the views that show them rerender as collateral.
  - The first alternative terminal message: after validation, a save
    rereads every telescope it will write. If any currently selects a
    title or body below home and lacks exact approval, nothing is
    skgsave-committed and the server replies, in place of save-result,
    =((response-type telescope-hoist-confirmation) (telescopes
    (((pid "P") (home "REPO")) ...)) (prompt "..."))=.
    This response contains no title or body. The prompt explains that
    Hoist moves the selected title/body text to home and removes lower
    title/body copies while retaining lower relationships and aliases;
    Abort writes nothing and requires manual =.skg= repair. Hoist
    re-issues the same save with =(approved-hoist-pids "P" ...)=.
    The server rereads and reclassifies on that retry, so newly dirty
    PIDs produce another batch confirmation. Each attempt still sends
    =save-lock= first, and the confirmation is terminal for that
    attempt: neither =save-relax-lock=, =collateral-view=, nor
    =save-result= follows it.
  - The second alternative terminal message: a save that detects forks
    (edited foreign nodes, or explicit fork requests) and does not
    carry =(approved-forks . "true")= skgsave-commits nothing and replies, in
    place of save-result,
    =((response-type fork-confirmation) (content "...") (to-minibuffer "..."))=,
    where =content= is the fork-confirmation buffer (an instructions
    headline, then per fork the clone-to-be over the original it
    forks; an unspecified clone skgrepo renders as the PICK-A-REPO
    placeholder under a =# Suggested repo ...= comment). The client
    shows it, collects a skgrepo per placeholder, and on approval
    re-issues the same save with =(approved-forks . "true")= and
    =(fork-repos ...)=. Hoist is decided first: when a save needs
    both decisions, its approved Hoist retry then returns the fork
    confirmation, and neither attempt writes.
  - The third alternative terminal message protects the saved and
    collateral rerenders. After a valid save has updated disk and the
    session-lifetime stores, the server renders the saved view and every collateral view in memory.
    Under a restricted skgrepo-set, if the staged forests contain overPrivateText
    telescopes without exact text-release approval, it changes no
    open-view registry entry, streams no content, and sends
    =((response-type overPrivateText-telescope-confirmation)
    (operation save-rerender) (pids ("P" ...)) (prompt "..."))=.
    The save itself has succeeded; only its updated text is withheld.
    The client may retry the same save with
    =(approved-overPrivateText-pids "P" ...)=. Under skgrepo-set =all=, or on an
    approved retry, the ordinary save-result carries the shared overPrivateText-
    telescope warning. Declining leaves current client buffers and the
    server's open-view registry unchanged.
  - Exactly one of =save-result=, =strandeds-confirmation=,
    =telescope-hoist-confirmation=, =fork-confirmation=, and the save-rerender
    =overPrivateText-telescope-confirmation= is sent as the terminal response to
    one save attempt.
  - If the server errors before sending the early lock message (e.g. malformed request), only one message is sent: the error response in the save-result format.

** Snapshot response (part of search enrichment; see "Text search" above)
  - Request: First =((request . "snapshot response") (terms . "TERMS"))\n=, then =Content-Length: N\r\n\r\n<buffer text>=.
  - Initiated by the client in response to a "request-snapshot" message from the server.
  - Response: LP response-type "search-enrichment" with enriched buffer content and an explicit =warnings= list. If enrichment fails, the response omits =content= and gives the reason in =warnings=.

** Get file path
  - Request: ((request . "get file path") (id . "THE_ID") (repo . "THE_REPO"))
  - Response: LP =((response-type get-file-path) (content "PATH"))=,
    normally with =PATH= relative to the data root. Errors use the same
    shape with human-readable =content= beginning =Error:=.
  - The server deliberately returns the computed path when the file no
    longer exists, so deleted nodes can still be located in a git diff.
  - Does not require the live graph or Tantivy -- only the config.
  - If the requested skgrepo is restricted in the current connection's
    skgrepo restriction, the server refuses to expose the path. Direct
    file visits outside Skg are not intercepted.

** Herald rules
  - Request: ((request . "herald rules"))
  - Response: LP response-type "herald-rules" with
    =((content "RULES_SEXP") (skgrepoLabels ("REPO" "LABEL")...))=.
    =RULES_SEXP= is the herald rule table -- one sexp, rooted at =(skg ...)=,
    in the grammar =elisp/skg-sexpr/skg-lens.el= interprets. Inside it,
    strings are always double-quoted and match atoms are bare symbols;
    the distinction is load-bearing for the lens engine.
    =skgrepoLabels= names each configured skgrepo with its herald label
    (its =abbreviation=, or else its name). A client renders a node's
    =repoBoundary= as "⌂:LABEL", LABEL looked up by the node's
    =nodeRepo= (the =nodeRepo= itself when the table lacks it), so no
    rendered text rides in the metadata.
  - The table in =server/heralds.rs= supplies non-relationship labels,
    colors and placement. Both clients render the semantic =(rels ...)=,
    =(props ...)= and =(birth ...)= facts of =(view ...)= themselves,
    including fractions and per-character styles.
    Each client fetches both at connection setup and re-fetches on reconnect.
    If the fetch fails, its herald display disables after bounded retries;
    there is no client-side fallback table. The user-facing legend is
    [[file:./heralds.org][heralds.org]].
  - A Rust unit test (=herald_rules_cover_the_emittable_vocabulary=)
    pins the table to the metadata vocabulary the server can emit, in
    both directions. It pins atom coverage only, not presentation.

** How a message names a headline
Every message in an =errors=, =warnings= or =corrections= list is Org
text. Its first line is the message's headline text, which both
clients write as a level-2 headline (=** =) under =* errors=, =*
warnings= or the headline naming a corrected view; the lines after
it are its body. A message that concerns a headline of the
buffer names it as a level-3 subheadline, after the message's own
lines:
#+begin_example
** A readiness request names no current change; it was dropped.
*** b
- graphnode ID: b
- viewnode ID: 0z. To find it: C-c g v 0z
#+end_example
The subheadline's text is the headline's title, or =(untitled)= for a
headline without one, such as a folder. Under it comes =- graphnode
ID: X= when the headline carries a graphnode ID, then =- viewnode ID:
X= (see "The metadata headers") with the command that finds it, or =-
not yet saved= for a headline without a viewnode ID: one the user
typed or copied since the last render. No message invents a viewnode
ID. A message about several occurrences of a node names each in
turn. A failed save's validation errors each follow as a =** Error
N= headline of the one =NOTHING WAS SAVED= message, so their
subheadlines nest under them; a parse error ends with the headline it
is in. The command, 'skg-goto-viewnode-id' on =C-c g v= in Emacs and
=<localleader>gv= in Neovim (which the Neovim client writes in place
of =C-c g v=), reads a viewnode ID and moves to the headline carrying
it, while heralds hide it. The subheadline is written by
'HeadlineName::org_subheadline' (=server/types/errors.rs=). A save
refused because another view's metadata is invalid lists that view's
errors on one line, naming each headline by its viewnode ID or title,
since the command searches the current buffer.

** Server warnings
  - Request: ((request . "server warnings"))
  - Response: LP =((response-type server-warnings) (warnings ("WARNING" ...)))=,
    or =(warnings ())= when there are none. The warnings are the ones
    the server raised as it started: one per top-level key of
    skgconfig.toml it does not know (see "skgconfig.toml", below), and
    one per foreign skgrepo whose dependencies manifest orders two
    skgrepos differently than the config does (see
    "OTHER_SKGREPO_DEPENDENCIES.toml", below).
    A reload of the config ("Rebuild session-lifetime stores") does
    not change them.
  - Each client sends this once per connection, as soon as the
    connection is up and before it requests any view
    ('skg-tcp-connect-to-rust', 'client.connect'). A non-empty answer
    is appended to a buffer, keeping what it holds, under a level-1
    headline "Startup warnings", each warning a level-2 headline:
    =*SKG Server Warnings*= in Emacs, =skg://messages/server-warnings=
    in Neovim. An empty answer opens nothing.
  - The same buffer receives the buffer corrections that a =save-result= or
    a =rerender-done= carries: each client appends them, keeping
    what the buffer holds, under one level-1 headline per view,
    "Buffer corrections in" and the view's buffer name, each buffer
    correction a level-2 headline under it.

** Link statuses
  - Request: =((request . "link statuses") (request-id . "TOKEN") (ids "ID" ...))=.
    A client batches and deduplicates literal link target IDs in a view.
  - Response: LP =((response-type link-statuses) (request-id "TOKEN")
    (results (("ID" resolved "PID" "REPO-LABEL")
              ("ID" restricted) ("ID" missing) ...)))=.
    Results follow the requested IDs. =PID= is the resolved primary ID,
    including resolution from an extra ID. =REPO-LABEL= is the visible
    target's home-repo herald label, not the link's relRepo. Restricted
    and missing rows return neither title nor skgrepo. The lookup reads the
    current in-Rust graph snapshot and skgrepo restriction, independently
    of Tantivy title-index commits. =request-id= associates asynchronous
    responses with their requesting buffer and its buffer generation.

** Diff view
  - Request: =((request . "diff view") (buffer . "BUFFER") (view-id . "VIEW_ID"))=,
    where BUFFER is ="all changes"=, ="merges"=, ="skgrepo changes"= or
    ="order-only changes"=. The client sends one request per buffer, in
    that order, each after the previous answer.
  - Response: LP response-type "diff-view", one of:
    - =((content "ORG") (errors ()) (warnings ()))=: the buffer, now
      registered under VIEW_ID as a buffer of the diff view.
    - =((empty . t) (errors ()) (warnings ()))=: the buffer would show
      nothing, so the client does not open it.
    - =((content "") (errors ("REFUSAL")) (warnings ()))=: refused, when
      the skgrepo restriction is not =all=, when an owned skgrepo is
      not a gitrepo or has no HEAD commit, or for an unknown BUFFER. A
      refusal applies to every buffer, so the client stops.
  - What each buffer shows: the "all changes" buffer is the pruned change view over
    every change in the owned skgrepos since HEAD; the merges and
    skgrepo-changes buffers are pruned change views over the nodeMerges and over the
    home skgrepo and relRepo moves; the order-only buffer lists the
    nodes whose only change is the order of a list. Foreign skgrepos
    are excluded. See the glossary's "Terms a user meets in the diff
    view", and "Metadata of the diff view" below.
  - The server compares HEAD with the worktree through a graph straddle it
    keeps per connection, brought up to date at each request, at each
    save of a buffer of the diff view, and at each rerender of
    every view. Closing the last such buffer drops it, as does a
    rebuild of the session-lifetime stores, so the next request reads
    both halves from the disk the rebuilt live graph was read from. Saving such a buffer is ordinary (see "Save
    buffer"), and its response carries the readiness summary.
  - A rerender of such a buffer (after a save, collateral, or after a
    commit) is a refresh in diff-view mode (see
    =docs/data-model_technical.org=, "The refresh: how a view follows
    the graph", and =docs/diff-view.org=, "Rendering a buffer"): every
    headline it holds is kept, with its =folded= and =bodyFolded=, and
    re-kinded and re-tagged in place (a member that loses its
    relationship becomes a removed member, a deleted node its ghost,
    and back); a change viewnode whose change is gone becomes a
    tombstone, pruned once it holds nothing; what the goals name and
    the buffer lacks is drawn.
    The server sets a fold state only on a viewnode it draws: a
    context node's body starts folded. A root stays until the
    buffer is closed. A ghost, a pending change, is shown until it is
    restored or its deletion is committed; a ghost root whose node a
    commit deleted, now in neither graph, becomes a tombstone, pruned
    when it holds nothing.
  - Logic: =server/serve/handlers/diff_view.rs=, =server/diff_view/=
    (=pruned_change_view.rs=, =changes.rs=).

** Stage and commit
  - Request: =((request . "stage and commit") (message . "MESSAGE"))=,
    optionally with =(confirmed . t)=.
  - Response: LP response-type "stage-and-commit", then a rerender
    stream (rerender-lock, rerender-view*, rerender-done). The
    response is one of:
    - =((needs-confirmation . t) (already-staged (("GITREPO" "PATH" ...) ...)) (readiness-summary ...) (errors ()) (warnings ()))=
      when the request is not confirmed and either the readiness
      summary (the save response's form, with =(notEditable 0)=) is
      incomplete or some owned gitrepo has entries already staged.
      =already-staged= is present only in the second case: each such
      gitrepo's worktree path, then its staged paths relative to it,
      read from the git index before anything is staged. Nothing
      changes, and the rerender stream is empty. A resend with
      =(confirmed . t)= covers both reasons.
    - =((commits (("SKGREPO" "COMMIT-ID") ...)) (errors (...)) (warnings ()))=
      otherwise: every owned skgrepo with changes had its =.skg= files
      staged (deletions included; the command stages nothing else) and
      git-committed with MESSAGE, by the gitrepo's configured user. A
      git-commit records the whole git index, so the commit of a
      gitrepo with an already-staged entry includes it. A skgrepo without changes is in
      neither list; one that failed is an error. When something was
      committed, the rerender stream rerenders each open buffer of
      the diff view over the rebuilt graph straddle, as any
      rerender does: its roots and what it holds editable stay, and what
      was committed loses its change facts. The marks of the changes committed are dropped
      from the readiness store.
    - =((errors ("REFUSAL")) (warnings ()))= when the skgrepo
      restriction is not =all=, the message is blank, or the graph
      straddle cannot be built. The rerender stream is empty.
  - Logic: =server/serve/handlers/stage_and_commit.rs=,
    =server/git_ops/stage_and_commit.rs=.

** Integrate unshown changes
  - Request: =((request . "integrate unshown changes") (view-id . "VIEW_ID"))=,
    where VIEW_ID names a buffer of the diff view. The client
    sends it only for a buffer with no unsaved changes, since the
    server works on the viewforest it registered at the last rerender.
  - Response: LP response-type "integrate-unshown-changes", then a rerender
    stream (rerender-lock, rerender-view*, rerender-done). The
    response is one of:
    - =((readiness-summary ...) (errors ()) (warnings ()))=, the save
      response's form, for the buffer as rerendered; the rerender
      stream carries that buffer.
    - =((errors ("REFUSAL")) (warnings ()))= when the skgrepo
      restriction is not =all=, VIEW_ID is not a buffer of the
      diff view, or the rerender fails. The rerender stream is empty.
  - Logic: the graph straddle is brought up to date, and the buffer's
    pruned change view sets recomputed. Each node of U without an editable
    occurrence becomes editable at its first content occurrence in
    level order, its children claiming as the buffer read back would; a
    node shown only as a write-protected folder member counts as shown
    nowhere, since a folder's members stay write-protected. The buffer
    is then refreshed as after a save, which gives each node made
    editable its body and draws its content list. Last, each origin of
    D that the buffer shows nowhere is appended as a root, at the end,
    in ID order, and the buffer refreshed again; R is deduplicated with
    the buffer's roots pinned, so that a changed cycle that already has
    a root gains no second one. What the request draws is what the user
    asked for, so it reports no buffer correction.
    =server/serve/handlers/integrate_unshown_changes.rs=, =server/diff_view/pruned_change_view.rs=
    ('ensure_editableOccurrences_exist',
    'contentOrigins_missing_from_buffer'), and 'rerender_view' in
    =server/update_buffer.rs=.

** Investigate unknown node
  - Request: =((request . "investigate unknown node") (id . "ID"))=.
  - Response: LP response-type "investigate-unknown-node" with
    =((content "ORG") (errors (...)) (warnings (...)))=. The content is:
    - =ID resolves to node TITLE (PID) in SKGREPO= when ID resolves
      (as primary or extra ID) to a node of the live graph;
    - otherwise what git history says, as Org text headed =* ID=: for
      each skgrepo whose first-parent history from HEAD holds the ID's
      file, the most recent commit that held it, the commit it vanished
      at, its title then, its own relation lists then, and every node of
      that tree that referred to it (links included); or
      =** never present in the git history of any skgrepo=.
  - Refused, with the reason as an error, unless the skgrepo
    restriction is =all=: history can hold the text of any skgrepo.
  - Logic: =server/serve/handlers/investigate_unknown_node.rs=,
    =server/git_ops/vanished.rs=.

** Rebuild session-lifetime stores
  - Request: ((request . "rebuild session-lifetime stores"))
  - Response: LP response-type "rebuild-session-lifetime-stores" with =((content "..."))=.
    Content reports that the graph and Tantivy were rebuilt on success,
    or "Rebuild failed: ..." on error.
  - Behavior: Reads the authoritative =.skg= files once, validates a complete
    candidate graph, builds that graph and a fresh Tantivy index from the same
    node vector, then atomically swaps in the new runtime generation. It does
    not rewrite =.skg= files. Failure leaves the old generation live. Success
    closes existing views, drops the graph straddle of the diff
    view, and recomputes context rankings for search.

** relRepo info
  - Request: ((request . "relRepo info") (owner . "ID")
    (member . "ID") (relation . "contains")) — relation is one of
    =contains=, =subscribesTo=, =overrides=: the three
    relations an explicit =(editRequest (relRepo ...))= request can name.
  - Response: LP response-type "relRepo-info" with
    =((default "NAME") (current "NAME"))=. =(current ...)= is absent
    when the graph records no such exact raw relationship (e.g. one typed into a
    buffer and not yet saved). An unresolved member is valid: it uses
    the recorder's home as its default and may still report an exact raw
    stored relRepo. On failure, =((error "..."))= — e.g. a recorder
    the graph does not know.
  - Behavior: between owned endpoints, =default= is the more-private
    home. From an owned recorder to a foreign member, =default= is the
    recorder's home regardless of privacy order; this deliberately
    exposes the member ID and relationship to that owned skgrepo's
    readers, while avoiding any proposed foreign write. =current= is
    the relationship's relRepo.
    =skg-set-relRepo= uses the reply to offer only
    skgrepos the save can accept. Advisory: the save-time floor check
    in =apply_sticky_relRepos_in_graph= stays load-bearing, since buffers go
    stale and the request is plain text.

** Flag state
  - Request: =((request . "flag state") (id . "ID")
    (flag . "noSearchMatching"))=.
  - Response: =((response-type flag-state) (id "CANONICAL-PID")
    (flag "noSearchMatching") (value "true") (repo "REPO")
    (owned "true"))=. Extra IDs resolve to the canonical PID. Unknown IDs
    or flag atoms return =(error "...")= under the same response type.
  - The endpoint is read-only and may report =hadId=, =wasOverloaded=, or
    =noSearchMatching=. Ownership is advisory; save-time validation remains
    authoritative.

** Strip body whitespace
  - Request: ((request . "strip body whitespace"))
  - Response: LP response-type "strip-body-whitespace" with
    =((content "..."))=. Content reports how many files changed and
    a per-repo breakdown, or "Body whitespace strip failed: ...".
  - Behavior: Strips trailing whitespace from every line of every
    body, and trailing blank lines from each body's tail, in every
    owned skgrepo in the config. Foreign skgrepos are never written, so they are
    left untouched (stripping them would make them diverge from
    their upstreams). Rewrites exactly the .skg files whose bodies
    changed (a clean file stays byte-identical); a body that strips
    to nothing is dropped from its file. The graph and Tantivy are refreshed
    to match. The clients suggest
    reviewing the result with =git diff --ignore-all-space=, which
    should show nothing.

** Import Markdown and Org

The Emacs =skg-import-md-and-org= and Neovim =:SkgImportMdAndOrg=
commands use the same length-prefixed S-expression exchange on one persistent
TCP connection:

- Initial preview request: =((request . "import md and org")
  (action . "preview") (input-directory . "/absolute/server/path")
  (destination-repo . "OWNED-REPO"))=.
- If absolute filesystem links to =.md= or =.org= files are found, the
  server responds with
  =response-type= =import-md-and-org-host-mapping-needed= and a =content=
  explanation. The client asks for the absolute host path corresponding to
  the input directory, then retries the same preview with
  =(host-root . "/absolute/host/path")=. An empty string explicitly declines
  mapping. Web URLs and literal code examples do not trigger this prompt.
- A successful or invalid preflight responds with =response-type=
  =import-md-and-org-preview=, =content= containing the resolved arguments,
  counts, export paths, and diagnostics, plus =(errors (...))= and
  =(warnings (...))=. A valid nonempty preview also carries
  =(approval-token "OPAQUE")=. No token means that nothing may be applied
  (including an empty input set).
- Explicit confirmation sends =((request . "import md and org")
  (action . "apply") (approval-token . "OPAQUE"))=. The one-use token refers
  to server-retained preparation, not to client-supplied nodes. The server
  consumes it and revalidates inputs, configuration, identities, export
  claims, and file absence under the mutation gate before writing. A new
  preview replaces the previous approval; closing the connection discards it.
  Stale, unknown, reused, and cross-session tokens cannot apply a batch.
- Declining sends =((request . "import md and org") (action . "cancel"))=,
  clearing retained preparation without writing. Apply/cancel responses have
  =response-type= =import-md-and-org-result= and =content=, =errors=, and
  =warnings= fields. A successful apply additionally has
  =(record-id "ID")=; clients then use the normal rerender protocol with an
  optional =(exclude-view-ids "VIEW_ID" ...)= list naming dirty editor views.
  Those views are not replaced or updated in the server's open-view state;
  clean views refresh normally. An absent list means rerender all views.

The importer only creates new authoritative =.skg= files and then swaps in
the graph and search delta. An ordinary write failure removes files created
by that attempt where possible and reports residual paths; a process crash
is not guaranteed atomic. Source files are never changed. An export marker
under each imported file root prepares a later Org export, but does not run
one automatically.

** Export to org
  - Request: =((request . "export to org") (skgrepo-set . "NAME")
    (output-dir . "PATH") (approved-overPrivateText-pids "PID" ...))=.
    - Both fields are required; a missing or blank =output-dir= is an
      error (the server applies no default -- the client supplies the
      user a default but always sends a value). =output-dir= is
      resolved against the server's working directory (its project
      root): a relative PATH lands under it, an absolute PATH is used
      as-is. The client does not tab-complete it, since the server
      may run in a container whose filesystem differs from the
      client's.
  - Response: LP response-type "export-to-org" with
    =((content "REPORT") (errors ("..." ...)) (warnings ("..." ...)))=.
    =content= is a human-readable report (files written, broken-link
    count, warning count). =errors= is non-empty only on failure
    (bad/unknown skgrepo-set name, unreadable =.skg= files, filesystem
    error). =warnings= are non-fatal (skipped roots,
    broken links).
  - Behavior: Reads all =.skg= files fresh from disk, finds every
    export root, and writes each to
    =<output-dir>/<target_filepath>.org= as a recursive content view
    limited to =NAME=, stripped of skg metadata, with
    =[[id:..][label]]= links rewritten to relative org links. Each
    file begins with three comment lines: a fixed first line, then
    =# ROOT-PID=, then a fixed warning against editing the file. The
    importer ignores exactly this header.
    Existing files are overwritten; others are left untouched. Needs
    neither the live graph nor Tantivy.
    Before writing anything, a restricted export involving overPrivateText
    telescopes returns LP =overPrivateText-telescope-confirmation= with
    =(operation export-to-org)= and the exact PIDs. An approved retry
    carries those PIDs in =approved-overPrivateText-pids=. An =all= export, or
    an approved restricted export, returns the ordinary export response
    with the shared warning.
  - An *export root* is a node one of whose =contains= children has
    a title linking to the instruction node
    =3d9aa9be-d95a-48bc-b362-33f9e7ebdf6f= and a body yielding a
    =target_filepath= (a tolerant ~key = value~ parse; the value may
    be bare or quoted, but a bare value with whitespace is refused).
    The marker child is omitted from output. A nested export root is
    rendered as a link to its own file, not inlined. Links whose
    dest is not exported under =NAME= point to the export of
    =9ff04e25-01e8-4634-8aa5-f5849bc1eb81= ("Some links might be
    broken."); if that note is itself not exported, the link degrades
    to plain label text. A deep link targets =*Heading=, or =#PID=
    when that headline contains a link or repeats an earlier
    headline's text in its file; only headlines targeted by
    =#PID= get a =:CUSTOM_ID: PID= drawer.
  - The same export is available as a CLI subcommand (no running server):
    =cargo run --bin skg -- export-org [config-path] [skgrepo-set]
    [output-dir] [--include-overPrivateText-telescopes]=. Under a restricted set it
    fails closed before writing unless the flag is present; under =all=
    (and on an approved restricted run) it prints the warning.

** Delete references to an absent node

  - Initial request: =((request . "delete references to absent node")
    (id . "RAW-ID"))=. =RAW-ID= must still be absent.
  - If owned title/body links point at the ID, response type
    =delete-references-confirmation= carries =(id ...)=, an opaque
    =(approved-preview ...)=, =(content "ORG WARNING")=, and a prompt,
    followed by an empty rerender stream.  A retry echoes the exact preview.
    The warning ends with a line naming the command that investigates
    the ID ("Investigate unknown node").
  - Success response type =delete-references-result= carries Org =content=,
    =changed-nodes=, and =changed-memberships=, followed by rerender-lock,

  - The mutation removes only exact raw-ID matches in owned =contains=,
    =subscribesTo=, =hidesFromSubs=, and
    =overrides= lists.  It leaves text links and foreign telescopes

** Rerender all views
  - Request: =((request . "rerender all views")
    (approved-overPrivateText-pids "PID" ...))=.
  - Response: Multiple length-prefixed messages, sent sequentially:
    1. Lock message:
       =Content-Length: N\r\n\r\n((response-type rerender-lock) (lock-views ("view ID1" "view ID2" ...)))=
       Lists all view IDs that will be re-rendered. Emacs locks those buffers.
    2. Zero or more per-view messages (one per view, streamed as each finishes):
       =Content-Length: N\r\n\r\n((response-type rerender-view) (view-id "VIEW_ID") (content "..."))=
       Emacs unlocks and updates each buffer as it arrives.
    3. Done message:
       =Content-Length: N\r\n\r\n((response-type rerender-done) (errors ("..." ...)) (warnings ("..." ...)) (corrections (("VIEW_ID" "..." ...) ...)))=
       Emacs removes the rerender-view handler and unlocks any remaining buffers.
       =corrections= holds what the refresh corrected in each view it
       rerendered, as in the save's =save-result= (see "Save buffer"
       above), and is present and empty if none. Every rerender stream
       ends with this message.
  - Behavior: Re-renders every open view from server memory, each a
    refresh of what it holds; a buffer of the diff view is refreshed
    over the graph straddle.
    Does not save or modify the graph. Refreshes all views without
    requiring a save.
  - All view text is prepared in memory before the release decision.
    Under a restricted set, overPrivateText content without exact approval returns
    LP =overPrivateText-telescope-confirmation= with
    =(operation rerender-all-views)= and
    the exact PIDs, followed by an empty rerender stream
    (=rerender-lock= with no view IDs, then clean =rerender-done=). No view
    text is sent and no open-view registry entry changes. A retry adds
    =approved-overPrivateText-pids=; =all= instead adds the shared warning to
    =rerender-done=.
  - =server/serve/rerender_stream.rs= prepares, authorizes and streams
    the rerenders; every request answered by a rerender stream shares
    it.

** skgrepo-sets
  - Skgrepo-sets are the prefixes of the config's privacy order (see
    "skgconfig.toml > skgrepo-sets" below): each skgrepo name denotes
    itself plus everything more public, and =all= means every skgrepo.
  - Request: ((request . "list repo sets"))
  - Response: LP response-type "repo-sets" with
    =((restriction "NAME") (sets ("NAME1" "NAME2" ...)))=. The sets are
    the skgrepo names in privacy order (most public first) followed
    by =all=; order is meaningful (it is the privacy ladder), so
    clients should preserve it.
  - Request: ((request . "skgrepo restriction"))
  - Response: LP response-type "skgrepo-restriction" with
    =((restriction "NAME"))=.
  - Request: =((request . "set skgrepo restriction") (name . "NAME")
    (approved-overPrivateText-pids "PID" ...))=.
  - Response: Multiple length-prefixed messages, sent sequentially:
    1. Skgrepo-set response:
       =Content-Length: N\r\n\r\n(("response-type" "skgrepo-restriction") ("restriction" "NAME") ("content" "Skgrepo restriction: NAME"))=
    2. The rerender stream, as in "rerender all views":
       rerender-lock → rerender-view* → rerender-done. Each open view
       is re-rendered in place under the new set by the refresh alone:
       every occurrence of a node the new set hides becomes a
       tombstone, which keeps its viewchildren; so does an unknown,
       since under a set other than =all= no goal names one; a
       tombstone is pruned unless it holds something; an editable
       folder the new set empties stays, empty, as any empty editable
       folder does; and the refresh fills every folder per the new
       set, so widening the set reveals members and folders, and
       fills an emptied folder again. When the set changed, none of
       this is reported as a buffer correction.
  - Behavior: The skgrepo restriction is per Emacs TCP connection. It
    defaults from =skgconfig.toml=, resets on reconnect, and is not
    written back to the config. Changing it requires confirmation in
    Emacs, re-renders (not closes) all active Skg buffers for that
    connection, and cancels any in-flight search enrichment.
  - Refusal: the endpoint's error paths (missing or unknown set
    name) answer in the normal skgrepo-restriction response-type,
    carrying the explanatory text as =content= and the unchanged set
    as =restriction=, followed by an empty rerender stream (a
    rerender-lock naming no views, then rerender-done), so the
    client's preemptive buffer locks and stream guard unwind.
  - Rerender authorization precedes both the set change and release of
    view text. If the proposed set would render an overPrivateText telescope, the
    first reply is LP =overPrivateText-telescope-confirmation= with
    =(operation repo-set-switch-rerender)= and exact PIDs, followed by an empty
    rerender stream. A retry adds =approved-overPrivateText-pids=; declining
    leaves the skgrepo restriction and open-view registry unchanged.

** Titles by ids

* Content view

Rust sends the entire text document to Emacs, org-bullets and all.
Each org-bullet is followed by a space, some metadata, a space,
and then headline text.

The metadata is an s-expression containing bare values and key-value pairs,
wrapped in "(skg ...)" -- something like
#+begin_example
 (skg (vnid 0a) folded node (gnid long-string) (skgRepos (nodeRepo main)) writeProtected)
#+end_example
Every headline has this one shape: its viewnode ID first, then the
position atoms (=focused=, =folded=, =bodyFolded=), then its kind,
and every part of the headline beside the kind at the top level, in
any order, the derived facts gathered in =(view ...)= and =(diff
...)=, which the parser skips (see "The metadata headers"). The kind
is a bare atom (=node=, =ghost=, =unknown=, =alias=, =id=,
=tombstone=, a folder atom, =bodyDiff=), or, for a kind with a
parameter, a small form naming it (=(flag F)=, =(oldText ASPECT)=,
the two moves, =(changesetMarker KIND)=). A headline naming no kind
is a node. Each kind
takes only its own parts; =(gnid ID)= names the node a node, a
ghost or an unknown stands for, and =(skgRepos (nodeRepo REPO)
[(relRepo REPO)])= its home skgrepo and the skgrepo recording its
relationship to its viewparent, the relRepo written only when it
differs from the default (a ghost has no relRepo; an unknown and an
alias have only one). The parser refuses the retired spellings
listed in "The metadata headers" with a message naming the grammar.

Any such string is valid metadata
(although much of it might be ignored by Emacs),
if and only if it adheres to the following:

- parentheses
  - The metadata starts with "(skg" and ends with ")".
  - Key-value pairs are wrapped in their own parens: "(key value)".
- whitespace
  - Whitespace separates all elements.
  - Extra whitespace is ignored.
  - Keys and bare values should contain no whitespace. A value that contains
    whitespace is represented as a quoted string atom; server-rendered skgrepo
    names and repo-derived herald values use this form automatically.

On a node, the bare atom =noClaim= says the node
takes no part in the membership represented by its viewparent: it is
preserved and displayed but does not alter the parent's membership on
save. A member carries nothing, and so does a view root. The atom is
meaningful only where the save reads the claims of the viewparent's
children: under an editable occurrence, and under an editable folder
(subscribee, overridden, hidden-outside, alias) of one. Under any
other viewparent no child claims, whatever it carries, and the server
writes no =noClaim= there.

The atom =omittedBody= in =(view ...)= accompanies =writeProtected= on a
write-protected node whose graphnode has a body — one the rendering
hides. Herald "B", hugging the ☮. A derived fact: the parser skips
it; the view regenerates it.

A chain node -- a node of the containerward chain under a member of a
partner folder, a container of its viewparent (see "View requests"
below) -- carries =writeProtected=, no =noClaim= (it stands under a
write-protected occurrence, where nothing claims), and, being no
member, no =(birth ...)= in its =(view ...)= (see "Stats metadata"
below). It is known by where it stands, so it is still one after a
save. A chain node carries no change facts.

** View requests: (viewRequests ...)

=(viewRequests ...)= carries client→server requests for viewbranches
(unlike =(view ...)= and the stats below, which are server→client). On save
the refresh fulfills each request and then drops the atom, so a
request is transient (the request rung of the ladder, in
=docs/data-model_technical.org=, "The refresh: how a view follows
the graph"). Request forms:

In a content view, an occurrence that an editable-view request
extends -- a fresh view's roots, and the editable content the request
draws or shows under them -- shows its nonempty =subscribeeFolder=, but
no other top-level relation folder, unasked. This applies both to
ordinary positions and to nodes extended as members of relation
folders. An editable subscribee-as-such additionally includes its
nonempty =hiddenInSubscribeeFolder=; =hiddenOutsideOfSubscribeeFolder=,
when nonempty, is part of the subscriber's =subscribeeFolder=. Use a
folder request for the other relation folders; their potential
contents remain advertised by the node's heralds. The diff view draws
no folder unasked but where something changed.

- =(folder RELNAME)= — build both folders of the relation, populated from the
  graph. RELNAME is =aliases=, =overrides=,
  =hidesFromSubs=, =subscribesTo=, =containers= or =mentioners=.
  The editable folder (=overriddenFolder= / =subscribeeFolder= / =aliasFolder=)
  appears even when empty (its editable "add here" surface); an empty
  write-protected folder is pruned. =containers= and =mentioners= each
  build one write-protected folder (=containerFolder=,
  =mentionerFolder=), pruned when empty: the other side of each is the
  node's content, or its links, shown without a folder.
  Under each member of a partner folder of any kind but the diff
  view's two acquisition folders hangs its containerward chain: the
  member's containers as write-protected occurrences claiming nothing,
  under each of those its containers, breadth-first up to the roots or
  =max_roleTree_depth=; a container met again on the way is drawn once
  more as a leaf. The member's partners in the folder's own role are
  not drawn below it; a folder request on the member draws them.
  Nothing hangs under a ghost member. The refresh draws the chain
  under a member it draws and never reinstates a chain node, so a
  chain that stays keeps its headlines and their fold state, and a
  member the user deletes takes its chain with it. No request
  extends a chain; a =(folder containers)= request on a chain node
  draws a containers folder under it. A fresh content view puts the
  =containers= request on each root. Emitted by the =C-c l= commands.
- =editableView= — on a write-protected occurrence, make it the node's
  editable one (the occurrence that was editable is write-protected,
  keeping its shown content, whose children claim nothing there); on
  an editable node, extend its content editable: each member it shows
  or draws whose node has no editable occurrence becomes editable,
  within =initial_node_limit= extensions, and passes the request on. A
  buffer carries at most one per node.
- =writeProtectedView= — make the occurrence write-protected (its title
  resynced from the graph); its children then claim nothing, and keep
  their own editability and subtrees. The edits the occurrence carries
  in the same save are saved first. On a write-protected occurrence it
  does nothing. Emitted by =C-c s w=.
- =writeProtectedSubtreeView= — the same for the occurrence and every
  occurrence of its content subtree. Emitted by =C-c s W=.
  Either write-protect request together with =editableView= on one
  occurrence is refused; on two occurrences of a node they move
  editability. The children of a write-protected occurrence carry no
  =noClaim=, so when it becomes editable again each claims, and the
  refresh marks =noClaim= on those its content list does not name:
  moving editability back restores the content.
- =flags= — add one write-protected =flagsFolder=, retained even when empty.
  Its true-only viewnodes use =(flag hadId)=, =(flag wasOverloaded)=, and
  =(flag noSearchMatching)= metadata in that order. Viewnodes have no Org title;
  their friendly visible label comes from the herald. Deleting the entire
  folder dismisses this optional viewbranch and has no persistence meaning;
  edits within a retained folder are rejected rather than silently ignored.
- =fork= — the explicit =skg-fork-node= gesture: clone this (owned)
  node into a private fork that overrides it. Consumed on the save path
  at fork detection (the refresh leaves it alone), then dropped. Emitted
  by =skg-fork-node= (=C-c m f=).

A ghost takes no view request; the parser refuses one there.

** Edit requests: (editRequest ...)

=(editRequest ...)= carries a client→server request that the save change
the graph. A save that succeeds consumes every request in the buffer
it saves, after its graph edits; a save that stops for a confirmation
or fails leaves them in the buffer. A headline carries at most one,
beside at most one readiness request, =(ready ...)= or =(unready
...)= (see "Metadata of the diff view"), written after it. The
heralds are nonstandard. The five requests on a node, and the
one on a ghost:

- =delete= — delete the node. Herald "delete". Written by =skg-delete=
  (=C-c <backspace>=). Only an editable occurrence carries it.
- =(merge ID)= — this node, the acquirer, acquires the node ID by a
  nodeMerge (see =docs/merging.org=). Herald "merge:ID". Written by
  =skg-set-merge-request= (=C-c s m=). Only an editable occurrence
  carries it.
- =(relRepo NAME)= — herald "request:~NAME".
  This is the sole explicit relRepo request, written by
  =skg-set-relRepo= (C-c s r) and consumed at save, where
  the server enforces the floor (an offered skgrepo more
  public than the relationship's default is a save error; a skgrepo at the
  default or more private is honored, which is how a stuck relationship's
  privacy is lowered; a legacy or hand-authored relationship whose disk
  skgrepo already sits more public than the default may be held or
  made more private, never made still more public). Absent means the
  relationship sits at its default relRepo. The relationship belongs to the
  view-parent (or a writable folder's viewparent), so a write-protected headline
  may carry this request too; the save refuses it only when nothing editable
  writes that relationship, e.g. under a write-protected parent.
  An alias and an unknown likewise show their relationship's relRepo
  in =(skgRepos (relRepo NAME))=, which the save does not read as a
  request, and carry a request only in =(editRequest ...)=; copying the
  fact is harmless, while copying a request deliberately requests it at
  the destination.
- =(flag noSearchMatching true|false)= — an idempotent
  save-only desired-state request. The provenance flags =hadId= and
  =wasOverloaded= are write-protected and rejected here. A successful save consumes
  the request; a failed save leaves it in the buffer. Herald view presents the
  request as one red semantic state: =request:no search matching= for =true=,
  or =request:search matching= for =false=.
- =restoreRel= — in the diff view, re-add the relationship this headline
  stands for, as HEAD recorded it: on a removed member, its content
  relationship to its viewparent; on a member of a partner folder carrying
  =(rel removed)=, the folder's relationship between it and the folder's
  viewparent. Herald "restore membership". Written by
  =skg-restore-removed-membership= (=C-c s l=). Like the relRepo request it
  concerns that relationship, so a write-protected occurrence carries it
  too. On a ghost it is a parse error, "This node is deleted; restore
  it first (skg-restore-deleted-node)". On a node that stands
  elsewhere than a removed member may, as a member under a vognode, a
  root or a node of the containerward chain, the save refuses it as a
  local structure violation, "Only a removed membership can be
  restored"; one that stands where a removed member may but names no
  relationship HEAD records is dropped with a warning.
- =restoreNode=, on a ghost — in the diff view, write
  back the node this ghost stands for, as HEAD had it.
  Herald "restore node". Written by =skg-restore-deleted-node=
  (=C-c s n=). The only edit request a ghost accepts; =restoreNode= on
  anything else is a parse error.

What the save does with the two restore requests is described in
=docs/diff-view.org=, "Restoring what a change removed".

** Stats metadata: the view facts, =(view ...)=

The derived facts of a headline's position stand in one form,
=(view FACT...)=, after its declared parts and before its =(diff
...)=. The server computes them at every rendering (the stats pass,
=server/update_buffer/viewnodestats.rs=); nobody reads them back:
the parser skips =(view ...)= whole, so editing them changes
nothing. A headline with none carries no =(view ...)=, and =(view)=
is never written. On a node, in the order written:

- =omittedBody= — on a write-protected node whose graphnode has a
  body, one the rendering hides. Herald "B", hugging the ☮.
- =(rels ...)=, =(props ...)=, =(birth ...)= — the relationship
  facts, below.
- =noWarrant= — the graph does not relate the node to its viewparent
  as its position implies: its parent does not contain it, the
  folder's relation does not hold for it, or, on a chain node, it
  does not contain the node above. A root is always warranted.
  Herald "⊥". Independent of =noClaim=.
- =cycle= — this position repeats an ancestor's ID. Herald "⟳".
- =repoBoundary= — the node sits at a skgrepo boundary: a root, or a
  node whose home skgrepo differs from its nearest occurrence
  ancestor's. Written only when the config has more than one skgrepo.
  Herald "⌂".

On an alias, an ID or a flag member, =(view ...)= holds at most one
atom: =noWarrant= when the node above its folder lacks it, or
=ghostWarrant= when HEAD alone warrants it (in the diff view, one
the worktree lost since HEAD, which also carries =(diff (rel
removed))=).

=server/herald_tokens.rs= assembles graph counts and occurrence facts
into the three semantic forms. Clients render them; the wire contains
no assembled glyphs, omitted numerals or colors. For example:

#+begin_example
(view
  (rels
    (contains (in 2 (ancestors 1))
              (out 8 (ancestors 2) (unintegrated 3 (ancestors 2))))
    (linksTo (in 5 (ancestors 1 2)
                   (substantive 2 (ancestors 1)))
             (out 3 (ancestors 2)))
    (overrides (out 1 (ancestors 1))))
  (props (aliases 2) (extraIds 1) (flags 3))
  (birth (contains in 1)))
#+end_example

Each relation side in =(rels ...)= is =(in COUNT (ancestors GEN...))=
or =(out COUNT (ancestors GEN...))=. Empty sides are generally
omitted, and =(rels ...)= is absent when no relation has anything to
say; =COUNT= is the complete distinct visible node count even when
ancestor flags let the client omit its numeral. =GEN= is an ancestor
generation: 1 is the viewparent, 2 the grandparent, counting
non-vognode levels. Relation keys are =contains=, =linksTo=,
=subscribesTo=, =overrides=, and =hidesFromSubs=. The =linksTo=
incoming side adds =(substantive COUNT (ancestors GEN...))= for the
subset whose skgrepo has a nonempty body, visible direct content, or
more than one distinct visible resolved target. Its outgoing side
counts distinct visible resolved targets. An applicable
subscribee-as-such =contains= outgoing side adds =(unintegrated COUNT
(ancestors GEN...))=, including when both counts are zero; absence of
that subform means the role does not apply. The numerator counts
members not already directly contained or hidden by that
occurrence's subscriber. Subset counts cannot exceed their side's
total. The ancestors counted are the viewparent, or, for a folder
member, the vognodes of the folder's required ancestry. A child
claiming nothing under a subscribee-as-such -- content its subscriber
hides, which the refresh keeps there, unwarranted, while it holds a
subtree or the user keeps it -- also counts the subscriber, three
generations up, on its =hidesFromSubs= incoming side, as a
=hiddenInSubscribeeFolder= member does.

=(props (aliases K) (extraIds K) (flags K))= holds the property
counts, each present only when nonzero; =(props ...)= is absent when
all are zero.

=(birth (RELNAME SIDE [GEN])...)= identifies the relation(s) behind
this occurrence, read from where it stands: for each, the side of
this node it is on (=in= or =out=) and the ancestor generation it
accounts for. =GEN= is omitted when no ancestor accounts for it, as
for a node shown in place of a node it overrides, which carries
=(overrides out)=. An occurrence that does not stand as a member of its
viewparent carries none: where the viewparent's claims are read, one
claiming nothing; in a write-protected folder, one the folder's
relation does not warrant; under a write-protected occurrence, every
child ('stands_as_member' in =server/update_buffer/viewnodestats.rs=).

| Birth                            | Facts                                                        |
|----------------------------------+--------------------------------------------------------------|
| ordinary content                 | =(contains in 1)=                                            |
| subscribee-folder member         | =(subscribesTo in 2)=                                       |
| subscriber-folder member         | =(subscribesTo out 2)=                                      |
| overridden-folder member         | =(overrides in 2)=                                   |
| overrider-folder member          | =(overrides out 2)=                                  |
| hidden-folder member             | =(hidesFromSubs in 2)=                        |
| hider-folder member              | =(hidesFromSubs out 2)=                       |
| container-folder member          | =(contains out 2)=                            |
| mentioner-folder member          | =(linksTo out 2)=                             |
| hidden-in-subscribee member      | =(hidesFromSubs in 4) (contains in 2)=        |
| hidden-outside-subscribee member | =(hidesFromSubs in 3)=                        |
| shown overrider (overrides-here) | =(overrides out)=                                    |
A member of an acquisition folder carries none: a nodeMerge is no
relation.
See [[file:./heralds.org][heralds.org]] for the rendered notation and styles.

The graph counts fold into these forms (=overriding= / =subscribing= /
=hiding= become the =O= / =S= / =H= tokens; =aliasing= / =extraIDs= /
true flags become the =Ak= / =Ik= / =Fk= property tokens), and the
per-relation view-position flags are the ancestor-lettered tokens.

Two facts of a headline's relationship to its viewparent are not view
facts. The skgrepo recording it, when its privacy was deliberately
raised above the relationship's default, is the =(relRepo NAME)= of
the headline's =(skgRepos ...)= (the =contains= relationship to a
content child, or the folder's relation for a partner folder member);
ugly herald "~NAME", shown immediately before the ⌂. It is recomputed
at every rendering, and the save never reads it as a request, which
is =(editRequest (relRepo NAME))=. And =(overridesHere N)=, crucial
=ĥ= immediately after the =O= token, is a load-bearing declared part,
documented in "Override substitution and the overridesHere part"
below.

** Node flags

The YAML =flags= list stores =Had_ID_Before_Import=, =Was_Overloaded=, and
=NoSearchMatching= using those exact spellings. Absence means false.
=NoSearchMatching= keeps the node's Tantivy documents for ID/title/repo
lookup but marks every title/alias document with indexed, stored
~no_search_matching=true~; every text query adds a mandatory exclusion. It
therefore blocks direct title, alias, body, regexp, operator, and
field-qualified matches, but is not an access-control boundary and does not
remove graph context.

** Override substitution and the overridesHere part

Where a node N stands as content of an editable occurrence in a
content view, and an owned overrider R of N is visible under the
skgrepo restriction, the refresh shows R instead -- transitively (an
owned chain D overrides C overrides N is legal and resolves to the
last visible link), cycle-guarded, and never in the diff view
('substitute_overriders' in =server/refresh/ladder.rs=). The refresh
substitutes at every refresh, a member already shown raw included,
since it decides from the buffer and the graph as they are now. Only
content substitutes: partner folder members, view roots, search
results, chain nodes and ghosts show the raw node.

The buffer whose approved save creates a fork is the post-save exception. A
root named by one of that save's exact =ForkSpec=s is rewritten from original F
to clone K, and an existing recursive-content occurrence in the saved forest
may likewise be replaced by its newly visible substitute. Both carry
=(overridesHere F)=. The refreshed forest remains under the same view ID, and
the open-view root index is recomputed from it, so that buffer is thereafter
registered as rooted at K. Collateral rerenders do not replace roots;
their content occurrences substitute as any refresh's do. A later
independent single-root request for F still opens raw F.

Moreover, the immediate children of any overridden node shown raw -- a
partner folder member other than a subscribee, a view root, or the
overridden-as-such (a member of an overriddenFolder) -- are also shown
raw: the user is looking at the
original, so its children are the original's, not the overrider's. This is one
level deep -- substitution resumes at the grandchildren -- and it is strict:
a node whose only overrider is invisible under the skgrepo restriction is
"overridden but shown raw" too, so its children are shown raw as well.

A substituted viewnode carries the keyed form
=(overridesHere N)= -- crucial =ĥ= immediately after =O= -- naming the original it
stands for. The part is load-bearing at save: wherever it
appears, extraction collects N rather than the carrying node's own
ID, so a container's contains list round-trips to the original
instead of being rewritten to the overrider. Edits to the shown
node itself (title, body, folders) still save to the shown node.
A buffer whose part the server would not have rendered (the carrier
is not on N's owned override chain -- the ownership-gated,
visibility-ungated walk out of N) aborts the save with an
explanation. With chains the honest carrier may be a middle link
(shown when a later link's mentioner is hidden), so the check accepts
any node on the chain and rejects only off-chain facts. A
skgrepo-set switch that makes a
shown substitute's skgrepo restricted turns it into a tombstone (the
fact does not survive -- a tombstone says nothing of what stood
there); the original it stood for is preserved in its container's
contains by disk supplementation. When the override itself is gone,
the refresh shows the overrider as itself, without the fact,
unwarranted and so claiming nothing, and reinstates the original
beside it.

The server's configuration file. See example-data/ for an example.

** Skgrepos

Each =[[repos]]= entry defines a directory of =.skg= files.
*Order is load-bearing*: skgrepos must be listed in privacy order,
most public first, most private last. That order defines the privacy
levels of the telescope model (see =docs/telescopes.org=) and the
available skgrepo-sets (below).

| Field          | Required | Description |
|----------------+----------+-------------|
| =path=         | yes      | Directory containing =.skg= files. Relative to data root. |
| =name=         | no       | Unique name for this skgrepo (used in metadata, provenance). Defaults to =path=. |
| =abbreviation= | no       | Short label for heralds. Owned skgrepos with defaulted names abbreviate to the path minus the owned folder. |

The skgrepo name =all= is reserved and rejected.

*Ownership is by location, not declaration*: a skgrepo is owned
(writable) iff its path lies under =<data_root>/<owned_folder>=,
where =owned_folder= is a top-level config field defaulting to
="owned"=. Everything else is foreign (never written). The old
=user_owns_it= field is retired and rejected with an error naming
the migration script (=bash/migrate-to-author-folders.sh=).

** skgrepo-sets

Skgrepo-sets are no longer declared; the retired =[[repo_sets]]=
table is rejected with an error. The sets are exactly the
*prefixes of the privacy order*: each skgrepo's name denotes the
set consisting of itself and every more-public skgrepo, and the
reserved name =all= means every skgrepo. Choosing a set is choosing
"the most private skgrepo to make available." =default_repo_set=
(top-level field) names the skgrepo restriction when a client connects.

Example:

#+begin_src toml
default_repo_set = "public"

# Privacy order: most public first.
[[repos]]
name = "public"
path = "owned/public"   # under owned/ => writable

[[repos]]
name = "private"
path = "owned/private"

[[repos]]
name = "Fred"
path = "Fred"           # foreign => write-protected
#+end_src

Here the available skgrepo-sets are =public= = {public},
=private= = {public, private}, =Fred= = =all= = {public, private,
Fred}.

** OTHER_SKGREPO_DEPENDENCIES.toml

At every server start the server writes an =OTHER_SKGREPO_DEPENDENCIES.toml=
manifest into each owned skgrepo directory. Its =dependencies= is a
list of pairs, one per skgrepo that skgrepo may reference — itself and
everything more public, in privacy order, the skgrepo itself last.
Each pair has a =path= (data-root-relative directory) and, unless the
skgrepo is not a gitrepo or has no remote, a =git-remote= (the fetch
URL =git remote -v= prints, =origin= preferred), so a receiver knows
where to fetch each dependency; when the chosen remote is not =origin=
its name is also recorded as =git-remote-name=. skg makes no use of
the =git-remote= values itself. For example:

#+begin_src toml
dependencies = [
  { path = "owned/public", git-remote = "git@github.com:me/public.git" },
  { path = "owned/private", git-remote = "git@github.com:me/private.git" },
]
#+end_src

It is generated output — hand edits are clobbered — and lets someone
who receives one of your skgrepos see what it depends on and where to get
it. When a foreign skgrepo's manifest orders two skgrepos differently
than this config does, the server warns at init, in its log and in
the startup warnings each client shows on connect (see "Server
warnings", above). (The receiver also
still reads the older bare-string =dependencies= shape, so manifests
published before this change keep working.)

** Log files

The server writes to =<data_root>/logs/=:
- =server-to-user.log= — human-readable log (always on).
- =server.jsonl= — structured JSON log (when ~timing_log = true~). Queryable with =jq=.

** Readiness marks file

=<data_root>/readiness-marks.json= holds the commit-readiness marks
of the diff view ('server/diff_view/readiness_store.rs'). The server reads
it at startup and rewrites it after every change; a missing or
unreadable file means no marks. It is a JSON object whose =marks= is a
list of ={"leaf": KEY, "fingerprint": N}= entries. KEY names one
change-forest leaf ('LeafKey' in 'server/diff_view/change_leaves.rs'): a node
aspect ={"Node": {"pid": ..., "aspect": ...}}=, where the aspect is
="Existence"=, ="Text"=, ="Home"=, ={"Alias": TEXT}=, ={"ExtraId": ID}=
or ={"Flag": FLAG}=; or a relationship aspect ={"Relationship":
{"relation": ..., "recorder": ..., "member": ..., "aspect": ...}}=
(the leaf's 'RelationshipKey', flattened, beside its aspect), where
the aspect is ="Existence"= or ="RelRepo"=. N is the fingerprint
of the change the mark approved, a hash of the leaf's before and after
values; a mark whose fingerprint no longer matches the current change
counts as absent.

See =example-data/skgconfig.toml=.

* The .skg file format

It is a specialization of YAML -- every .skg file is valid YAML,
although not vice versa. The definitive source of truth is
=server/types/nodes/fs.rs= (=GraphnodeOnDisk=).

Each file is one *telescope section*: the slice of one node
recorded at one privacy level (see =docs/telescopes.org=). One node =
one ID = same-ID =.skg= files across skgrepos, at most one per
skgrepo; the filename is the node's primary ID followed by =.skg= in
every skgrepo. The node's *home* is its most public section, and
that section carries the =title= — an invariant, not a search rule.
A titleless section more public than the title still loads (the
composition reports it) but cannot be rewritten by a save. A field a
section omits is a field that section has no opinion about.
Pre-telescope single-file nodes parse unchanged (one section, title
present, no anchors).

Fields:

- =title=: A string, no newlines. Present in the home section only.
- =pid=: The node's primary ID. Must equal the filename stem. Present
  in every section.
- =extra_ids=: Optional list of additional IDs (from node merges).
  Home section only, by convention.
- =body=: An optional string, perhaps with newlines. Home only.
- =aliases=: Optional list of strings. Each section may contribute
  aliases; an alias's relRepo is its section's skgrepo.
- =contains=, =subscribesTo=: Ordered relations. One flat YAML
  sequence per relation, one entry per line:
  - =- ID= — a member recorded at this section's skgrepo. Identical
    syntax in every section, so a membership moving between skgrepos
    diffs as a clean one-line delete/add pair.
  - =- anchor: ID= — a placement anchor: the members after it (until
    the next anchor) insert immediately after the anchored ID, which
    lives in a more public section. Members before the first anchor
    prepend to the front of the more public list. Anchors are derived
    on save from the in-memory order; hand-written anchors are
    honored on load (a dangling anchor's run falls back with a
    warning, and duplicate anchors concatenate in file order).
- =hidesFromSubs=, =overrides=: Unordered
  relations; plain lists of IDs. The effective list is the union
  across sections; each entry's relRepo is its section's
  skgrepo.

The composition of all same-pid sections (most public first) yields the
node; saving decomposes the node back into sections, byte-stably, so
untouched sections do not change on disk. An owned section emptied
by a save is deleted; foreign sections are never touched.

* The metadata headers

Most org headlines in the client will have a 'metadata header',
consisting of some bare values and some key-value pairs
separated by whitespace. Each kv pair is wrapped in parens: (key value).
The whole collection is wrapped in (skg ...).
This metadata appears right after the org bullet and a whitespace,
and right before another whitespace and the node's title.

The metadata grammar (which keys are recognized and how they're
parsed) lives in =server/serve/parse_metadata_sexp.rs=. The
in-memory types those keys correspond to are in
=server/types/viewnode.rs= (=Viewnode=, =ViewnodeKind=, =Vognode=,
=Folder=, =PropertyMember=, the diff view's =ChangeViewnode=, and its
=ChangeFacts= and =ReadinessRequest=, which every =Viewnode= carries).

Every headline has one shape:
#+begin_example
(skg (vnid X) [focused] [folded] [bodyFolded]
     KIND DECLARED...
     [(view FACT...)] [(diff FACT...)])
#+end_example
The parts are of two classes. The declared parts are what the client
is responsible for and the save reads: the kind, the viewnode ID, the
position atoms, =(gnid ID)=, =(skgRepos ...)=, =noClaim=,
=writeProtected=, =(overridesHere ID)=, =(viewRequests ...)= and
=(editRequest ...)=. The derived facts are what the server computes
at every rendering and nobody reads back: everything in =(view ...)=
(see "Stats metadata: the view facts" above) and in =(diff ...)=
(see "Metadata of the diff view" below). The parser skips both forms
whole. KIND is a bare atom, but five kinds carry their parameter in a
small form headed by the kind: =(flag F)=, =(oldText ASPECT)=,
=(homeSkgrepoMove ...)=, =(relRepoMove ...)= and =(changesetMarker
KIND)=. A headline whose metadata names no kind is a node: a client
writes =(skg folded)= on a headline that has no metadata yet. Each kind
takes only its own declared parts:
#+begin_example
node [(gnid ID)] [(skgRepos [(nodeRepo R)] [(relRepo R)])]
     [noClaim] [writeProtected] [(overridesHere ID)]
     [(editRequest [REQUEST] [READINESS])] [(viewRequests ...)]
     [(view ...)] [(diff ...)]
ghost (gnid ID) (skgRepos (nodeRepo R)) [noClaim]
      [(editRequest [restoreNode] [READINESS])]
      [(view ...)] [(diff ...)]
unknown (gnid ID) [(skgRepos (relRepo R))] [noClaim]
        [(editRequest [(relRepo R)] [READINESS])] [(diff ...)]
alias [(skgRepos (relRepo R))] [noClaim]
      [(editRequest [(relRepo R)] [READINESS])] [(view ...)] [(diff ...)]
id [noClaim] [(editRequest READINESS)] [(view ...)] [(diff ...)]
(flag F) [(editRequest READINESS)] [(view ...)] [(diff ...)]
(oldText ASPECT), (homeSkgrepoMove ...), (relRepoMove ...),
(changesetMarker KIND): [(editRequest READINESS)] [(diff ...)]
bodyDiff, tombstone, forestRoot, a folder atom
#+end_example
where READINESS is =(ready OBJECT...)= or =(unready OBJECT...)= (see
"Metadata of the diff view"). =(gnid ID)= names the node a node, a
ghost or an unknown stands for, and =(skgRepos (nodeRepo REPO)
[(relRepo REPO)])= its home skgrepo and the skgrepo recording its
relationship to its viewparent, the relRepo written only when it
differs from the default (a ghost has no relRepo; an unknown and an
alias have only one). =noClaim= on a node, a ghost, an alias, an ID
or an unknown says the save does not read it as a member of its
viewparent's list; a claimant carries nothing, and so does every
child of a viewparent whose claims the save does not read. A lost
alias and a dangling partner the worktree lost (an unknown carrying
=(rel removed)=) carry =noClaim= where their viewparent's claims are
read, so that the save, which skips the =(diff ...)= saying they were
lost, leaves them out of the list.
=(editRequest ...)= holds at most two requests: one edit request and
one readiness request, written after it.

Every viewnode's metadata starts with its viewnode ID, =(vnid X)=, where
X is one or more lowercase letters and digits: =(skg (vnid 0a) node
(gnid 1) (skgRepos (nodeRepo main)))=. It identifies the viewnode within its buffer for the
life of the buffer. The server assigns one, from the view's counter in
base 36 (two characters at least, skipping any spelled like a number,
such as =05= or =1e5=), to every viewnode that lacks one at the end of a
refresh, and never reassigns or reuses one: a headline keeps the
viewnode ID it carried through a save and a rerender, through a cut
and paste, and through a skgrepo-set switch that does not hide it. A
headline typed without one gets one; of two headlines carrying one
viewnode ID, the first in buffer order keeps it and the second (a copy)
gets a fresh one; a headline carrying one the view does not know
(typed by hand, or brought back by an old copy of the buffer's text)
gets a fresh one too, and the counter does not move past it. The
clients show nothing for it and save it back untouched. The view's
record of its viewnode IDs, with the counter and the viewnode IDs of
the forest as last rendered, is 'ViewnodeIdRecord' in
=server/types/views_state.rs=.

The parser refuses, with a message naming the grammar, the retired
spellings: =(node ...)=, =(ghost ...)= and =(unknown ...)= as forms,
=(deleted ...)=, =(historical ...)=, =(id ID)=, =(repo REPO)=, a
top-level =(relRepo REPO)=, =(FOLDER changed)=, =(rels ...)=,
=(viewStats ...)=, =omittedBody= or the old home skgrepo herald
outside =(view ...)=, =(readyRequest ...)=, =(unreadyRequest ...)=,
and the old atoms of a child claiming nothing and of a hidden node's
placeholder ('parse_metadata_sexp.rs' names each).

Metadata is not WYSIWYG; its appearance in the client
is determined by =elisp/heralds-minor-mode.el=, whose rule table is
served by Rust (see "Herald rules" above; the table lives in
=server/heralds.rs=).

Partner folders are represented in Rust as
=ViewnodeKind::Folder (Folder)=, but their external metadata
remains the established bare non-vognode atom:
=subscribeeFolder=, =subscriberFolder=, =overriddenFolder=, =overriderFolder=,
=hiderFolder=, =hiddenFolder=, =hiddenInSubscribeeFolder=,
=hiddenOutsideOfSubscribeeFolder=, =containerFolder=, =mentionerFolder=,
or, in the diff view only, =acquiredByFolder= or =acquiredFolder=.

A tombstone is written =(skg (vnid X) tombstone)=: it has
no ID, no change facts and no title (the parser discards text typed on
its line), and holds only what stands below it. The refresh makes one
of a headline that can stand where it is for nothing: an occurrence
whose node a save deleted (in the diff view, its ghost instead, when
HEAD has the node) or the skgrepo restriction hides, a descriptor
whose position its kind forbids, a change viewnode whose change is
gone, an empty folder nothing can be added to, a ghost on request.
The refresh prunes it once it is childless, a view root included, so a
buffer may end with no headlines (the glossary's "tombstone,
entombstone"). Herald "something stood here".

** Metadata of the diff view

The buffers of the diff view (see "Diff view") show changes with
the forms below. The change facts are derived facts, which the
parser skips; the readiness requests and the restore edit requests
are declared parts, which the save consumes. Saving a buffer reads
none of the new viewnodes, which are save-inert, but for a ghost's
restore request and the gnid of a ghost that claims membership (one
its viewparent's worktree list still names), which the save keeps in
the list, as it keeps an unknown's.
The glossary's "Terms a user meets in the diff view" and "Terms of
the diff view's implementation" define the vocabulary.

*** The change facts: =(diff ...)=
A headline's change facts form one list, the last part of its
metadata:
#+begin_example
(diff (node added) (rel removed) (properties changed) (leaves N OBJECT...) (ready OBJECT...) (homeSkgrepoMove (old OLD) (new NEW)) (movedLikeAncestor LETTER))
#+end_example
The first three parts are the three kinds of change, and say only
what is true. The parts come in that order, and a part is absent when
it has nothing to say; a headline with nothing to say carries no
=(diff ...)=, and =(diff)= is never written. A node, a ghost, an
unknown, an alias, id or flag member and the change viewnodes other
than =bodyDiff= may carry it; a folder never does (see "Changed
folders" below).
**** =(node added)=, =(node removed)= -- the node's existence
The node HEAD lacks (=added=) or the worktree lacks (=removed=). On a
member, a removed member, a folder member, a root, and a ghost.
**** =(rel added)=, =(rel removed)= -- the existence of the relationship to the viewparent
The relationship that HEAD lacks (=added=) or the worktree lacks
(=removed=). Under a vognode it is the viewparent's content; in a partner
folder it is the relationship, of the folder's kind, between the
member and the folder's viewparent (the two compound partner folders
carry none). On an alias, id or flag member, the single diff object
is written =(rel added)= or =(rel removed)=: the member's existence
in its list. A lost alias or ID (below) carries =(rel removed)=.
**** =(properties changed)= -- the node's other properties
The node is in both graphs and its file records a change ("modified",
herald =M=), on a member, a removed member, a folder member or a
root. Never beside =(node added)= or =(node removed)=, and never on a ghost.
**** =(leaves N OBJECT...)= -- on every viewnode that names leaves
It gives the OBJECTs a request there may name (=node= and/or =rel= on
a vognode or ghost, each worth one leaf; =all= on a
vognode whose properties changed, beside =rel= when that names a leaf;
=all= on another changed vognode neither of whose objects names a
leaf, or on a changeset marker; none where a bare request names them),
and N, how many distinct leaves a request naming all of them touches.
The clients read it to build their requests and to count the leaves
an unmark touches.
**** =(ready OBJECT...)= -- the diff objects whose change-forest leaves are all marked commit-ready
The objects are =node=, =rel=, and =all= on a headline whose =(leaves
...)= lists it, so a ready changeset marker carries =(ready all)=. A
bare =(ready)= marks a headline that lists no object (one naming a
single leaf). Absent when nothing is ready.
**** =(homeSkgrepoMove (old OLD) (new NEW))=, =(movedLikeAncestor LETTER)= -- a node's home skgrepo moved
In the skgrepo-changes buffer, on a node whose home skgrepo moved
from OLD to NEW since HEAD; herald "-OLD +NEW". Beside it, when the
nearest vognode ancestor whose home moved moved the same way,
=(movedLikeAncestor LETTER)=, LETTER naming that ancestor as the
relationship tokens do (a = the viewparent); herald "Δ⌂=LETTER".

*** The readiness requests: =(editRequest (ready ...))=
=(ready OBJECT...)= and =(unready OBJECT...)= inside =(editRequest
...)= ask the save to set or clear the commit-readiness marks of the
leaves those objects name; the object =all= names every leaf a
vognode's node records, or every leaf of a commit readiness
aggregate, one level down. At most one per headline, written after
the headline's other edit request if it has one: =(editRequest
delete (ready node))=. Any headline that may carry =(diff ...)= may
carry one.

*** Who writes each part, and who acts on it
**** The server writes the change facts
The server writes the =(diff ...)= form (=diff_form= in
=server/org_to_text.rs=), and it sets =(ready ...)= and =(leaves
...)= in the tail of the refresh (=set_ready_facts_in_viewforest=); see
=docs/diff-view.org=, "Change facts on the wire". A rerender of a
buffer of the diff view recomputes each kept viewnode's change facts
in place from the graph straddle, and so does a save of such a
buffer; see "Diff view" and "Save buffer" above. The parser skips
=(diff ...)= whole, so editing a change fact changes nothing. The
clients read =(leaves ...)= to build their requests and to count the
leaves an unmark touches.
**** The client's readiness gestures write the readiness requests
A gesture writes =(ready ...)= or =(unready ...)= into the headline's
=(editRequest ...)=, creating the form if the headline lacks one, and
saves; see =docs/diff-view.org=, "Readiness requests and gestures".
In Emacs the gestures are =C-c r r= (=skg-cycle-commit-ready=), which
toggles the commit-readiness of the change at point, and =C-c r h=
(=skg-toggle-homeSkgrepo-move-commitReady=), which toggles the
commit-readiness of the home-skgrepo move of the node at point. Their
recursive forms take a prefix argument: =C-u C-c r r= marks every
change in the subtree at point, or unmarks them if the headline at
point is ready, and =C-u C-c r h= does the same as =C-c r h= to every
descendant whose home moved between the same two skgrepos; see
=docs/COMMANDS.org=, "C-c r : commit readiness, in the diff view". The
Neovim keys are in =docs/COMMANDS-nvim.org=. A gesture that would
unmark more than one change first asks for a typed "yes".
**** The save of any buffer consumes the requests
A save of any buffer, not only one of the diff view's, consumes the
readiness requests after its graph edits succeed: each sets or clears
the marks of the change-forest leaves its headline names, at their
current fingerprints. A save that stops for a confirmation (strandeds,
Hoist, forks) or fails consumes none, and leaves them in the buffer. A
request that names no current change is dropped, with the warning =A
readiness request names no current change; it was dropped.=, naming its
headline as a subheadline. See "Save buffer" above.
**** One gesture on a modified node marks its file, on a write-protected occurrence too
On a modified node (=(properties changed)=), =C-c r r= names every leaf the node
records, and its relationship when that changed, so one gesture marks
the file; both =C-c r r= and =C-c r h= work on write-protected
occurrences. See =docs/diff-view.org=, "Readiness requests and
gestures", and the glossary's "diff object, diff aspect", which says
that =all= names every leaf a modified node records, so one gesture on
it marks its file.

*** The diff view's viewnodes
**** =alias noClaim (view ghostWarrant)=, =id (view ghostWarrant)= with =(rel removed)= -- in an alias or ID folder: an alias or extra ID that HEAD has and the worktree lacks
Its headline is the alias or the ID: a member with a ghost warrant,
which claims no membership. Saving reads no alias from it, and the
ID folder, whose claims the save never reads, carries no =noClaim=;
the save's check of an ID folder refuses only one lacking an ID of
the node. A dangling partner the worktree lost, an unknown carrying
=(rel removed)=, likewise carries =noClaim= where its folder reads
claims.
**** =ghost (gnid ID) (skgRepos (nodeRepo REPO)) ...= -- a ghost
It is a node HEAD has and the worktree lacks, with HEAD's title and
body, drawn only in the diff view. Its ID is written =(gnid ID)= and
its home skgrepo =(skgRepos (nodeRepo REPO))=, as a node's are. It
claims membership only where its viewparent's worktree list still
names its gnid; elsewhere, where claims are read, it carries
=noClaim=, and where nothing warrants it, =(view noWarrant)= (never
=ghostWarrant=: the kind is its own herald). It may carry
=(editRequest restoreNode)= (see "Edit requests: (editRequest ...)"),
and no view request.
**** =(oldText titleAndBody)=, =(oldText title)=, =(oldText body)= -- the node's text at HEAD
It sits under a node whose text changed; its headline is the old
title, its body the old body.
**** =bodyDiff= -- under an old text: the line diff of the body
Each line is prefixed by a space, =-= or =+=.
**** =(homeSkgrepoMove (old REPO) (new REPO))= -- the node's home skgrepo moved
**** =(relRepoMove (old REPO) (new REPO))= -- under a member: the skgrepo recording its relationship to its viewparent moved
**** =(changesetMarker content)=, =(changesetMarker relRepo)=, =(changesetMarker orderOnly)= -- a changeset marker
**** =acquiredByFolder=, =acquiredFolder= are write-protected and derived
Under a ghost, an =acquiredByFolder= holds the node that acquired it
by a nodeMerge; under an acquirer, an =acquiredFolder= holds the
ghosts of the nodes it acquired. An =acquiredFolder= also accepts a
child the user puts there, which claims nothing.

*** Changed folders
A partner, alias, ID or flags folder is written as its bare atom,
whether or not something in it changed. A folder is shown because of
a change when some member of it carries a change of its relationship
to the folder's viewparent: a =(rel ...)= part, or a =(relRepoMove
...)= under it. The clients compute that from the members, and label
such a folder "its X changed (this file)" or "(other files)" (see the
glossary's "in, out"), with ✓ when every changed membership is ready:
a member's =(rel ...)= is ready when it carries =(ready ...)= naming
=rel= if its =(leaves ...)= lists =rel=, and any =(ready ...)=
otherwise; a relRepo move is ready when it carries =(ready ...)=.
A readiness gesture on such a folder acts on each changed membership.

*** Examples
#+begin_example
(skg node (gnid 7) (skgRepos (nodeRepo main)) (diff (node added) (rel added) (leaves 2 node rel) (ready node)))
(skg node (gnid 8) (skgRepos (nodeRepo main)) writeProtected (diff (rel added) (properties changed) (leaves 3 rel all) (ready all)))
(skg node (gnid 9) (skgRepos (nodeRepo main)) noClaim writeProtected (view noWarrant) (diff (rel removed) (leaves 1 rel)))
(skg alias (editRequest (ready)) (diff (rel added) (leaves 1)))
(skg alias noClaim (view ghostWarrant) (diff (rel removed) (leaves 1) (ready)))
(skg ghost (gnid 4) (skgRepos (nodeRepo main)) (diff (node removed) (rel removed) (leaves 2 node rel)))
(skg (oldText title) (diff (leaves 1) (ready)))
(skg (changesetMarker content) (diff (leaves 3 all) (ready all)))
(skg (changesetMarker content) (editRequest (ready all)) (diff (leaves 3 all)))
(skg node (gnid 5) (skgRepos (nodeRepo pub)) (diff (homeSkgrepoMove (old priv) (new pub)) (movedLikeAncestor a)))
#+end_example

** Restricted-skgrepo nodes: omission, retention, and save preservation

Under a restricted skgrepo-set, rendering omits nodes from restricted
skgrepos (/hidden/ nodes) entirely -- content, subscribees, and every
partner folder's members alike. Omission is recursive: an omitted
container's whole branch is omitted, unrestricted descendants
included (they stay reachable by search or direct visit).

Saving preserves what rendering omitted: an omitted relationship
member cannot be deleted (or even seen), so the save merges the
buffer's visible lists with the disk lists -- order-preserving (the
anchored weave) for =contains= and =subscribesTo=, set-difference
for =overrides=; and the folder of what a subscriber hides outside
its subscribees replaces only the hides it could show, those whose
relRepo and member's home the set both holds. Edits to visible
members, including deletions, are honored. A hidden member needs no headline for this:
the disk supplies it.

When a skgrepo-set switch is applied to an open view (an
already-rendered buffer), every occurrence of a now-hidden node
becomes a tombstone, which keeps the occurrence's viewchildren, so
its visible descendants are not orphaned:

#+begin_example
(skg tombstone)
#+end_example

A tombstone says nothing of what stood there: no id, skgrepo or
title, so nothing the user hid by restricting the skgrepo-set leaks.
A childless one is pruned, as are the property members and change
viewnodes of the node it replaced and the folders that prune empties.
An editable folder whose members the new set hides stays, empty.
It is save-inert: it emits no fieldIntent (a hidden node's membership
in its parent's list is owned entirely by disk supplementation, not
the buffer), and it is not a collateral re-render target. Its
children remain occurrences, claiming nothing. Switching back draws the
hidden node again; the tombstone stays beside it until its children
are gone. A de-novo render under a restricted set never produces
one -- hidden members are omitted and their content is never
extended.

Edits to restricted nodes themselves are /suppressed/ at save, not
fatal: any nodeInstruction that would write a restricted skgrepo is
dropped and the save succeeds with the warning "Restricted nodes
present in saved buffer remain unchanged in graph." An untouched
stale node saves silently (its identical-to-disk nodeInstruction is
discarded as a no-op first).
