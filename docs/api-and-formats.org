* API

Communication between Rust and Emacs is via TCP on port 1730, configurable in any skgconfig.toml. The connection is persistent.

After initialization, every server response is length-prefixed as
=Content-Length: LENGTH\r\n\r\nPAYLOAD=; =LENGTH= is the number of
UTF-8 bytes in =PAYLOAD=. The exceptional busy-initializing signal is
described below.

Many responses carry their main payload in a =(content "...")= field.
That field is just "the payload": it has nothing to do with a node's
=contains= list or the "content view" (though a content-view response
has one too).

A string atom in a response is double-quoted when it is empty, or
holds a double quote, whitespace, or a number; any other string atom
is a bare symbol. So an empty view arrives as =(content "")=.

The shared overPrivateText-telescope release warning is
=OPERATION includes title or body text selected below its node's home
skgrepo for PID P.= (or =PIDs P1, P2, ...=). A restricted request that
needs approval instead receives
=((response-type overPrivateText-telescope-confirmation) (operation OPERATION)
(pids ("P" ...)) (prompt "..."))=; the response itself contains no
protected title or body. Except for search's include/exclude choice,
approval is always the exact request-local list
=(approved-overPrivateText-pids "P" ...)= and is never cached.

So far there are these endpoints:

** Verify connection
  - Request: ((request . "verify connection"))
  - Response: LP =((response-type verify-connection) (content "This is the skg server verifying the connection."))=.

** Text search
  - Request: =((request . "text search") (terms . "SEARCH_TERMS")
    (regex . "BOOL") (body . "BOOL") (operators . "BOOL"))=, plus
    optional =(overPrivateText-telescopes . "include")= or
    =(overPrivateText-telescopes . "exclude")=.
    - Search always returns every match. Prominent nodes (literal roots, cycle-roots, mentioned nodes, and things that had an ID when imported) are ranked higher, via their prominence multiplier.
    - =regex=, =body=, =operators= are optional; each defaults to "false".
      - "regex=true": interpret the query as a per-token regex; a RegexQuery is built directly and the QueryParser is bypassed.
      - "body=true": also search node bodies (titles are always searched).
      - "operators=true": preserve Tantivy phrase and operator syntax (AND / OR / phrase / +foo / -bar / grouping / field:). Intra-word operator chars still get escaped heuristically so C++ etc. remain findable. In regex mode, the query is parsed as a boolean expression over the per-token regexes: AND / OR / NOT / +foo / -bar, conventional precedence (NOT > AND > OR, bare adjacency = OR), and grouping via parens that stand ALONE between whitespace (a paren attached to a pattern is regex syntax within that piece). Malformed operator syntax is an error; phrase syntax does not apply. Detailed in docs/COMMANDS.org.
    - The skgrepo restriction is applied before grouping, ranking,
      alias/title selection, and display truncation. Restricted-skgrepo
      documents do not influence result order or which title/alias is
      shown for an unrestricted result.
    - =overPrivateText-telescopes= is normally absent on the first request. Under
      a restricted skgrepo-set, if the search index contains any telescope
      whose selected title or body lies below home, the server does no
      query and responds with LP
      =((response-type overPrivateText-telescope-confirmation)
      (operation text-search) (pids ()) (prompt "..."))=. The empty PID
      list is deliberate: a pre-query decision must not disclose which
      overPrivateText node might match. The retry uses ="include"= or ="exclude"=.
      Exclusion is applied inside the Tantivy query, before matching,
      and remains in force through asynchronous enrichment. The choice
      is request-scoped. Skgrepo-set =all= needs no choice and returns a
      warning if the results include overPrivateText telescopes.

  - Phase 1, immediate: Server sends LP =((response-type
    search-results) (content "ORG") (warnings ("..." ...)))=.
    Results are ordinary write-protected non-content unrestricted vognodes (not
    special non-vognode types). A no-match or error response has the same
    response type and a single =content= field.

  - Every =search-results= is followed by exactly one
    =search-enrichment=, which is what releases the client's stream
    guard. (The overPrivateText challenge above sends neither.) When no
    enrichment is coming, that message omits =content=:
    =((response-type search-enrichment) (terms "TERMS") (warnings (...)))=.
    The client then leaves the search buffer alone and shows any
    warnings. This happens immediately after a no-match or error
    response; when the client closes the search view (=close view= of
    =search:TERMS=) before enrichment arrives, after the close-view
    response; and when the server cannot enrich a buffer snapshot, with the
    reason as a warning.

  - Phase 2, enrichment: A three-message sequence:
    1. Rust sends LP response-type "request-snapshot" with =(("content" "TERMS"))= — asking Emacs for a snapshot of the search buffer matching those terms.
    2. Emacs replies with =((request . "snapshot response") (terms . "TERMS"))\n= followed by =Content-Length: N\r\n\r\n<buffer text>= — the current buffer contents, dirty or not. Emacs sets the buffer to readonly before sending.
    3. Rust parses the buffer snapshot, inserts containerward role tree,
       overrideward view-subtrees, and graphnodestats, and sends LP
       response-type "search-enrichment" with =(("terms" "TERMS")
       ("content" "ORG") ("warnings" (...)))=. Emacs replaces the
       buffer and exits readonly.
    - Enrichment uses the same skgrepo restriction as the original
      search. Containerward role tree truncates before restricted
      containers.
    - Each result's overrideward view-subtree contains its visible
      override relatives in both directions: what it overrides and what
      overrides it. Each direction is recursive and cycle-guarded. These
      nodes are write-protected non-content descendants. A matching node
      recursively overridden by an owned result is suppressed at the
      top level because it reappears in that result's subtree.

** Single-root content view from ID
  - Request: =((request . "single root content view")
    (id . "NODE_ID") (view-id . "VIEW_ID")
    (approved-overPrivateText-pids "PID" ...))=
  - Response: LP =((response-type content-view) (content "...")
    (errors ("..." ...)) (warnings ("..." ...)))=. The document
    structure is detailed below, under =Content view=.
    Under a restricted skgrepo-set, a response involving an overPrivateText
    telescope instead returns LP =overPrivateText-telescope-confirmation= with
    =(operation single-root-view)=, the exact PIDs, and a text-free
    prompt. An approved retry carries those
    exact PIDs in =approved-overPrivateText-pids=; approval is not cached.
    Skgrepo-set =all= returns the ordinary response with a warning.
  - If =NODE_ID= resolves to a restricted skgrepo, the server refuses the
    request with a human-readable message and does not open a buffer.
    Following a link to a restricted-skgrepo node behaves the same way.
  - The requested node opens as itself, drawn raw. Because the raw root
    is an overridden node drawn raw, its immediate children also draw
    raw (one level); substitution resumes at the grandchildren. See
    "Override substitution" below. Override facts can be inspected in
    search results' overrideward view-subtrees and in explicitly requested
    override folders and role trees.

** Save buffer
  - Request: First =((request . "save buffer") (view-id . "VIEW_ID") (point-lines-below-focused-headline . "N") (point-column . "C") (point-screen-lines-below-window-start . "M"))\n=, then one UTF-8 length-prefixed S-expression envelope:
    #+begin_src lisp
    ((saved-buffer "...Org text...")
     (other-views
       (((view-id "...") (dirty false))
        ((view-id "...") (dirty true)
         (baseline (present "...last clean text..."))
         (current "...edited text..."))
        ((view-id "...") (dirty true)
         (baseline unavailable)
         (current "...edited text...")))))
    #+end_src
    =Content-Length= is the envelope's UTF-8 byte length. =other-views=
    is mandatory even when empty and covers every other live client view,
    including views the server has not registered. Clean entries carry no
    buffer snapshots. Dirty entries carry exact current text and either the exact
    clean baseline or explicit =unavailable=. Duplicate view IDs, the saved view ID,
    missing fields, and inconsistent clean/dirty fields are rejected. Raw Org
    in place of the envelope is not a supported legacy form.
    - Two optional fields drive the fork-confirmation round-trip
      (below): =(approved-forks . "true")= marks a re-issued save whose
      forks the user approved, and
      =(fork-repos ((N . REPO) ...))= pairs each forked node's id
      N with the owned skgrepo chosen for its clone. Both are absent on
      an ordinary save.
    - =(strandeds-reviewed . "true")= and =(reset-strandeds ("RELATION"
      "RECORDER" "MEMBER") ...)= are present only on a retry after
      =strandeds-confirmation=: the first says the user reviewed the
      stranded relationships, the second names those to reset to default
      (possibly none).
    - =(approved-hoist-pids "PID" ...)= is present only on a retry
      after =telescope-hoist-confirmation=. It is the exact list the
      user approved for text publication; it is not a boolean and
      does not authorize any other PID or bypass ordinary save
      validation.
    - =(approved-overPrivateText-pids "PID" ...)= is the shared text-release
      approval field. On save it appears only when retrying a
      =save-rerender= =overPrivateText-telescope-confirmation=, and authorizes
      those exact PIDs for that response attempt. It is independent of
      Hoist authority: viewing text and publishing it on disk are
      different decisions.
    - =point-lines-below-focused-headline= is global to the buffer save: the number of text lines from the focused headline to point before save.
    - =point-column= is global to the buffer save: the column of point within its line, echoed back so the client can restore the exact cursor position.
    - =point-screen-lines-below-window-start= is global to the buffer save: the number of screen lines from the window's top line to point before save. The server echoes all three point fields in the final save response so Emacs can restore point and scroll position after replacing the buffer text.
  - Response: Multiple length-prefixed messages, sent sequentially:
    1. Early lock acknowledgement (sent immediately, before reading the envelope):
       =Content-Length: N\r\n\r\n((response-type save-lock) (lock-views ("view ID1" "view ID2" ...)))=
       Both clients lock every local Skg view before taking the request's
       buffer snapshots. This message acknowledges that broad lock; its server-known
       view ID list does not authorize unlocking client-only views.
    2. Save-relax-lock message (sent after preparation and conflict checking, before mutation):
       =Content-Length: N\r\n\r\n((response-type save-relax-lock) (lock-views ("view ID1" "view ID2" ...)))=
       The keep-set contains selected collateral targets and every dirty view
       whose baseline/current buffer snapshots were checked, including unregistered
       views. The saved view is retained implicitly. Only unrelated clean
       views may unlock at this point. A malformed narrowing message leaves
       all locks held until terminal cleanup.
    3. Zero or more collateral-view messages (one per collateral view, streamed as each finishes):
       =Content-Length: N\r\n\r\n((response-type collateral-view) (view-id "VIEW_ID") (content "..."))=
       Emacs unlocks and updates each buffer as it arrives.
    4. Final save response:
       =Content-Length: N\r\n\r\n((response-type save-result) (content "...") (errors ("..." ...)) (warnings ("..." ...)) (point-lines-below-focused-headline N) (point-column C) (point-screen-lines-below-window-start M))=
       =content= is the re-rendered saved buffer (nil on failure). =errors= is a list of failure-explaining strings. =warnings= is a list of nonfatal messages. Both lists are present and empty if none.
       When the saved buffer is one of the diff view's, the response
       ends with =(readiness-summary (ready N) (changed M) (foreign F) (order-only O) (notEditable K))=:
       of the M changed files of the owned skgrepos (O of them changed only
       in order, and so ready), N are commit-ready; F files changed in
       foreign skgrepos; and K changes are not editable in the view: they
       are owned by nodes whose changes the buffer does not show. A
       buffer shows a node's changes where it has an editable
       occurrence of it, in content or in a partner folder, or a
       historical phantom of it in content position: under the buffer
       root or an unrestricted vognode, or in the old content of such a
       phantom. The buffer is reconciled over the graph straddle, not
       rebuilt: its roots, and every headline it drew editable, stay as
       saved, and its change facts, change folders, markers and removed
       members are redrawn. What it draws anew it draws by its PCSVF
       sets recomputed after the save: a new member in U is editable,
       with its content list, and any other new member is a
       write-protected member drawn without its content. It
       makes no occurrence editable and appends no root; the "integrate
       unshown changes" request below does. An editable-view request
       cascades as in any view, and only the expansion of a node
       outside U spends =initial_node_limit=; nothing else in the
       buffer spends that budget.
  - A write-protected occurrence saves nothing of its own, so a save is
    refused, before anything is written, if one differs from the graph:
    in its title or home skgrepo, in its alias folder or a partner
    folder when present, or by holding a child that affects it. A
    partner folder's members are compared with the node's partners in
    its relation as a set of node IDs, under the save's skgrepo
    restriction, not counting a member the diff view shows as
    removed; a member carrying a relRepo request differs. A present
    flags folder, under any node, must likewise equal the node's flags.
  - Before mutation, the server computes the update-relevant neighborhood of
    every prepared write/delete identity independently in the before and
    candidate graphs. Other registered views containing an affected unrestricted ID
    are rerendered. For every dirty client view, the server parses and unions
    dependencies from its clean baseline, current text, and registered forest
    when present. Any intersection refuses the save conservatively; malformed
    or missing dirty dependency data also refuses. A refusal returns
    =save-result= with nil content and actionable errors naming view IDs and
    IDs, and performs no filesystem, graph, search index, registry, or collateral
    update. There is no save-anyway path.
  - Moving a node between skgrepos: for each home move the server
    finds every relationship touching the moved node, in either
    direction and whether or not a view shows it, that sat at its
    default relRepo and that the sticky-else-default rule would leave
    off its new default ('server/from_text/strandeds.rs'). One left more
    public than its member's new home (an inbound relationship of a
    privatizing move) is raised to the new default, and the save's
    warnings say so. If any other remains and the request lacks
    =(strandeds-reviewed . "true")=, nothing is skgsave-committed and the
    server replies, before any other decision and in place of
    save-result,
    =((response-type strandeds-confirmation) (strandeds (((relation
    "contains") (recorder "R") (member "M") (relRepo "REPO") (default
    "REPO")) ...)) (prompt "..."))=, with IDs but no titles. The
    client re-issues the SAME save with =(strandeds-reviewed . "true")=
    and the chosen =(reset-strandeds ...)=; the server resets those
    to their new defaults, saving each recorder (outside the view or
    not), so the views that show them rerender as collateral.
  - The first ALTERNATIVE terminal message: after validation, a save
    rereads every telescope it will write. If any currently selects a
    title or body below home and lacks exact approval, nothing is
    skgsave-committed and the server replies, in place of save-result,
    =((response-type telescope-hoist-confirmation) (telescopes
    (((pid "P") (home "REPO")) ...)) (prompt "..."))=.
    This response contains no title or body. The prompt explains that
    Hoist moves the selected title/body text to home and removes lower
    title/body copies while retaining lower relationships and aliases;
    Abort writes nothing and requires manual =.skg= repair. Hoist
    re-issues the SAME save with =(approved-hoist-pids "P" ...)=.
    The server rereads and reclassifies on that retry, so newly dirty
    PIDs produce another batch confirmation. Each attempt still sends
    =save-lock= first, and the confirmation is terminal for that
    attempt: neither =save-relax-lock=, =collateral-view=, nor
    =save-result= follows it.
  - The second ALTERNATIVE terminal message: a save that detects forks
    (edited foreign nodes, or explicit fork requests) and does NOT
    carry =(approved-forks . "true")= skgsave-commits nothing and replies, in
    place of save-result,
    =((response-type fork-confirmation) (content "...") (to-minibuffer "..."))=,
    where =content= is the fork-confirmation buffer (an instructions
    headline, then per fork the clone-to-be over the original it
    forks; an unspecified clone skgrepo renders as the PICK-A-REPO
    placeholder under a =# Suggested repo ...= comment). The client
    shows it, collects a skgrepo per placeholder, and on approval
    re-issues the SAME save with =(approved-forks . "true")= and
    =(fork-repos ...)=. Hoist is decided first: when a save needs
    both decisions, its approved Hoist retry then returns the fork
    confirmation, and neither attempt writes.
  - The third ALTERNATIVE terminal message protects the saved and
    collateral rerenders. After a valid save has updated disk and the
    session-lifetime stores, the server renders the saved view and every collateral view in memory.
    Under a restricted skgrepo-set, if the staged forests contain overPrivateText
    telescopes without exact text-release approval, it changes no
    open-view registry entry, streams no content, and sends
    =((response-type overPrivateText-telescope-confirmation)
    (operation save-rerender) (pids ("P" ...)) (prompt "..."))=.
    The save itself has succeeded; only its updated text is withheld.
    The client may retry the SAME save with
    =(approved-overPrivateText-pids "P" ...)=. Under skgrepo-set =all=, or on an
    approved retry, the ordinary save-result carries the shared overPrivateText-
    telescope warning. Declining leaves current client buffers and the
    server's open-view registry unchanged.
  - Exactly one of =save-result=, =strandeds-confirmation=,
    =telescope-hoist-confirmation=, =fork-confirmation=, and the save-rerender
    =overPrivateText-telescope-confirmation= is sent as the terminal response to
    one save attempt.
  - If the server errors before sending the early lock message (e.g. malformed request), only one message is sent: the error response in the save-result format.

** Snapshot response (part of search enrichment; see "Text search" above)
  - Request: First =((request . "snapshot response") (terms . "TERMS"))\n=, then =Content-Length: N\r\n\r\n<buffer text>=.
  - Initiated by the client in response to a "request-snapshot" message from the server.
  - Response: LP response-type "search-enrichment" with enriched buffer content and an explicit =warnings= list. If enrichment fails, the response omits =content= and gives the reason in =warnings=.

** Get file path
  - Request: ((request . "get file path") (id . "THE_ID") (repo . "THE_REPO"))
  - Response: LP =((response-type get-file-path) (content "PATH"))=,
    normally with =PATH= relative to the data root. Errors use the same
    shape with human-readable =content= beginning =Error:=.
  - The server deliberately returns the computed path when the file no
    longer exists, so deleted nodes can still be located in a git diff.
  - Does not require the live graph or Tantivy -- only the config.
  - If the requested skgrepo is restricted in the current connection's
    skgrepo restriction, the server refuses to expose the path. Direct
    file visits outside Skg are not intercepted.

** Herald rules
  - Request: ((request . "herald rules"))
  - Response: LP response-type "herald-rules" with =((content "RULES_SEXP"))=.
    =RULES_SEXP= is the herald rule table -- one sexp, rooted at =(skg ...)=,
    in the grammar =elisp/skg-sexpr/skg-lens.el= interprets. Inside it,
    strings are always double-quoted and match atoms are bare symbols;
    the distinction is load-bearing for the lens engine.
  - The table in =server/heralds.rs= supplies non-relationship labels,
    colors and placement. Both clients render the semantic =(rels ...)=
    facts themselves, including fractions and per-character styles.
    Emacs fetches the table at connection setup and re-fetches on reconnect.
    If the fetch fails, its herald display disables after bounded retries;
    there is no client-side fallback table. The user-facing legend is
    [[file:./heralds.org][heralds.org]].
  - A Rust unit test (=herald_rules_cover_the_emittable_vocabulary=)
    pins the table to the metadata vocabulary the server can emit, in
    both directions. It pins atom coverage only, not presentation.

** Link statuses
  - Request: =((request . "link statuses") (request-id . "TOKEN") (ids "ID" ...))=.
    A client batches and deduplicates literal link target IDs in a view.
  - Response: LP =((response-type link-statuses) (request-id "TOKEN")
    (results (("ID" resolved "PID" "REPO-LABEL")
              ("ID" restricted) ("ID" missing) ...)))=.
    Results follow the requested IDs. =PID= is the resolved primary ID,
    including resolution from an extra ID. =REPO-LABEL= is the visible
    target's home-repo herald label, not the link's relRepo. Restricted
    and missing rows return neither title nor skgrepo. The lookup reads the
    current in-Rust graph snapshot and skgrepo restriction, independently
    of Tantivy title-index commits. =request-id= associates asynchronous
    responses with their requesting buffer and its buffer generation.

** Diff view
  - Request: =((request . "diff view") (buffer . "BUFFER") (view-id . "VIEW_ID"))=,
    where BUFFER is ="all changes"=, ="merges"=, ="skgrepo changes"= or
    ="order-only changes"=. The client sends one request per buffer, in
    that order, each after the previous answer.
  - Response: LP response-type "diff-view", one of:
    - =((content "ORG") (errors ()) (warnings ()))=: the buffer, now
      registered under VIEW_ID as a buffer of the diff view.
    - =((empty . t) (errors ()) (warnings ()))=: the buffer would show
      nothing, so the client does not open it.
    - =((content "") (errors ("REFUSAL")) (warnings ()))=: refused, when
      the skgrepo restriction is not =all=, when an owned skgrepo is
      not a gitrepo or has no HEAD commit, or for an unknown BUFFER. A
      refusal applies to every buffer, so the client stops.
  - What each buffer draws: the "all changes" buffer is the PCSVF over
    every change in the owned skgrepos since HEAD; the merges and
    skgrepo-changes buffers are PCSVFs over the nodeMerges and the home
    moves; the order-only buffer lists the nodes whose only change is
    the order of a list. Foreign skgrepos are excluded. See the
    glossary's "Terms of the diff view", and "Metadata of the
    diff view" below.
  - The server compares HEAD with the worktree through a graph straddle it
    keeps per connection, brought up to date at each request, at each
    save of a buffer of the diff view, and at each rerender of
    every view. Closing the last such buffer drops it, as does a
    rebuild of the session-lifetime stores, so the next request reads
    both halves from the disk the rebuilt live graph was read from. Saving such a buffer is ordinary (see "Save
    buffer"), and its response carries the readiness summary.
  - A rerender of such a buffer (after a save, collateral, or after a
    commit) reconciles what it holds with a fresh drawing from the
    straddle: a viewnode the fresh drawing also produces is kept, with
    its =folded= and =bodyFolded=, its kind and facts updated in place
    (a member that loses its relationship becomes a removed member, a
    deleted node a historical phantom, and back); one it does not is
    removed; the rest is created. The server sets a fold state only on
    a viewnode it creates: a context node's body starts folded. A
    root stays until the buffer is closed; a root whose node a commit
    deleted is drawn as a deleted phantom.
  - Logic: =server/serve/handlers/diff_view.rs=, =server/pcsvf.rs=,
    =server/to_org/render/changes.rs=.

** Stage and commit
  - Request: =((request . "stage and commit") (message . "MESSAGE"))=,
    optionally with =(confirmed . t)=.
  - Response: LP response-type "stage-and-commit", then a rerender
    stream (rerender-lock, rerender-view*, rerender-done). The
    response is one of:
    - =((needs-confirmation . t) (readiness-summary ...) (errors ()) (warnings ()))=
      when the readiness summary (the save response's form, with
      =(notEditable 0)=) is incomplete and the request is not confirmed.
      Nothing changes, and the rerender stream is empty.
    - =((commits (("SKGREPO" "COMMIT-ID") ...)) (errors (...)) (warnings ()))=
      otherwise: every owned skgrepo with changes had its =.skg= files
      staged (deletions included) and git-committed with MESSAGE, by
      the gitrepo's configured user. A skgrepo without changes is in
      neither list; one that failed is an error. When something was
      committed, the rerender stream rerenders each open buffer of
      the diff view over the rebuilt graph straddle, as any
      rerender does: its roots and what it drew editable stay, and what
      was committed loses its change facts. The marks of the changes committed are dropped
      from the readiness store.
    - =((errors ("REFUSAL")) (warnings ()))= when the skgrepo
      restriction is not =all=, the message is blank, or the graph
      pair cannot be built. The rerender stream is empty.
  - Logic: =server/serve/handlers/stage_and_commit.rs=,
    =server/git_ops/stage_and_commit.rs=.

** Integrate unshown changes
  - Request: =((request . "integrate unshown changes") (view-id . "VIEW_ID"))=,
    where VIEW_ID names a buffer of the diff view. The client
    sends it only for a buffer with no unsaved changes, since the
    server works on the viewforest it registered at the last rerender.
  - Response: LP response-type "integrate-unshown-changes", then a rerender
    stream (rerender-lock, rerender-view*, rerender-done). The
    response is one of:
    - =((readiness-summary ...) (errors ()) (warnings ()))=, the save
      response's form, for the buffer as rerendered; the rerender
      stream carries that buffer.
    - =((errors ("REFUSAL")) (warnings ()))= when the skgrepo
      restriction is not =all=, VIEW_ID is not a buffer of the
      diff view, or the rerender fails. The rerender stream is empty.
  - Logic: the graph straddle is brought up to date, and the buffer's
    fresh PCSVF sets computed. Each node of U without an editable
    occurrence becomes editable (its body from the live graph) at its
    first content occurrence in level order, or if it has none at its
    first partner folder occurrence. The buffer is then rerendered as
    after a save, which draws the content list of each node made
    editable. Last, each origin of D that the buffer draws nowhere is
    appended as a root, at the end, in ID order, and completed; R is
    deduplicated with the buffer's roots pinned, so that a changed
    cycle that already has a root gains no second one.
    =server/serve/handlers/integrate_unshown_changes.rs=, =server/pcsvf.rs=
    ('ensure_editableOccurrences_exist',
    'contentOrigins_missing_from_buffer'), and 'rerender_view' in
    =server/update_buffer.rs=.

** Investigate unknown node
  - Request: =((request . "investigate unknown node") (id . "ID"))=.
  - Response: LP response-type "investigate-unknown-node" with
    =((content "ORG") (errors (...)) (warnings (...)))=. The content is:
    - =ID resolves to node TITLE (PID) in SKGREPO= when ID resolves
      (as primary or extra ID) to a node of the live graph;
    - otherwise what git history says, as Org text headed =* ID=: for
      each skgrepo whose first-parent history from HEAD holds the ID's
      file, the most recent commit that held it, the commit it vanished
      at, its title then, its own relation lists then, and every node of
      that tree that referred to it (links included); or
      =** never present in the git history of any skgrepo=.
  - Refused, with the reason as an error, unless the skgrepo
    restriction is =all=: history can hold the text of any skgrepo.
  - Logic: =server/serve/handlers/investigate_unknown_node.rs=,
    =server/git_ops/vanished.rs=.

** Rebuild session-lifetime stores
  - Request: ((request . "rebuild session-lifetime stores"))
  - Response: LP response-type "rebuild-session-lifetime-stores" with =((content "..."))=.
    Content reports that the graph and Tantivy were rebuilt on success,
    or "Rebuild failed: ..." on error.
  - Behavior: Reads the authoritative =.skg= files once, validates a complete
    candidate graph, builds that graph and a fresh Tantivy index from the same
    node vector, then atomically swaps in the new runtime generation. It does
    not rewrite =.skg= files. Failure leaves the old generation live. Success
    closes existing views, drops the graph straddle of the diff
    view, and recomputes context rankings for search.

** relRepo info
  - Request: ((request . "relRepo info") (owner . "ID")
    (member . "ID") (relation . "contains")) — relation is one of
    =contains=, =subscribesTo=, =overrides=: the three

  - Response: LP response-type "relRepo-info" with
    =((default "NAME") (current "NAME"))=. =(current ...)= is absent
    when the graph records no such exact raw relationship (e.g. one typed into a
    buffer and not yet saved). An unresolved member is valid: it uses
    the recorder's home as its default and may still report an exact raw
    stored relRepo. On failure, =((error "..."))= — e.g. a recorder
    the graph does not know.
  - Behavior: between owned endpoints, =default= is the more-private
    home. From an owned recorder to a foreign member, =default= is the
    recorder's home regardless of privacy order; this deliberately
    exposes the member ID and relationship to that owned skgrepo's
    readers, while avoiding any proposed foreign write. =current= is
    the relationship's relRepo.
    =skg-set-relRepo= uses the reply to offer only
    skgrepos the save can accept. Advisory: the save-time floor check
    in =apply_sticky_relRepos= stays load-bearing, since buffers go
    stale and the request is plain text.

** Strip body whitespace
  - Request: ((request . "strip body whitespace"))
  - Response: LP response-type "strip-body-whitespace" with
    =((content "..."))=. Content reports how many files changed and
    a per-repo breakdown, or "Body whitespace strip failed: ...".
  - Behavior: Strips trailing whitespace from every line of every
    body, and trailing blank lines from each body's tail, in every
    OWNED skgrepo in the config. Foreign skgrepos are never written, so they are
    left untouched (stripping them would make them diverge from
    their upstreams). Rewrites exactly the .skg files whose bodies
    changed (a clean file stays byte-identical); a body that strips
    to nothing is dropped from its file. The graph and Tantivy are refreshed
    to match. The clients suggest
    reviewing the result with =git diff --ignore-all-space=, which
    should show nothing.

** Import Markdown and Org

The Emacs =skg-import-md-and-org= and Neovim =:SkgImportMdAndOrg=
commands use the same length-prefixed S-expression exchange on one persistent
TCP connection:

- Initial preview request: =((request . "import md and org")
  (action . "preview") (input-directory . "/absolute/server/path")
  (destination-repo . "OWNED-REPO"))=.
- If absolute filesystem links to =.md= or =.org= files are found, the
  server responds with
  =response-type= =import-md-and-org-host-mapping-needed= and a =content=
  explanation. The client asks for the absolute host path corresponding to
  the input directory, then retries the same preview with
  =(host-root . "/absolute/host/path")=. An empty string explicitly declines
  mapping. Web URLs and literal code examples do not trigger this prompt.
- A successful or invalid preflight responds with =response-type=
  =import-md-and-org-preview=, =content= containing the resolved arguments,
  counts, export paths, and diagnostics, plus =(errors (...))= and
  =(warnings (...))=. A valid nonempty preview also carries
  =(approval-token "OPAQUE")=. No token means that nothing may be applied
  (including an empty input set).
- Explicit confirmation sends =((request . "import md and org")
  (action . "apply") (approval-token . "OPAQUE"))=. The one-use token refers
  to server-retained preparation, not to client-supplied nodes. The server
  consumes it and revalidates inputs, configuration, identities, export
  claims, and file absence under the mutation gate before writing. A new
  preview replaces the previous approval; closing the connection discards it.
  Stale, unknown, reused, and cross-session tokens cannot apply a batch.
- Declining sends =((request . "import md and org") (action . "cancel"))=,
  clearing retained preparation without writing. Apply/cancel responses have
  =response-type= =import-md-and-org-result= and =content=, =errors=, and
  =warnings= fields. A successful apply additionally has
  =(record-id "ID")=; clients then use the normal rerender protocol with an
  optional =(exclude-view-ids "VIEW_ID" ...)= list naming dirty editor views.
  Those views are not replaced or updated in the server's open-view state;
  clean views refresh normally. An absent list means rerender all views.

The importer only creates new authoritative =.skg= files and then swaps in
the graph and search delta. An ordinary write failure removes files created
by that attempt where possible and reports residual paths; a process crash
is not guaranteed atomic. Source files are never changed. An export marker
under each imported file root prepares a later Org export, but does not run
one automatically.

** Export to org
  - Request: =((request . "export to org") (skgrepo-set . "NAME")
    (output-dir . "PATH") (approved-overPrivateText-pids "PID" ...))=.
    - Both fields are required; a missing or blank =output-dir= is an
      error (the server applies no default -- the client supplies the
      user a default but always sends a value). =output-dir= is
      resolved against the server's working directory (its project
      root): a relative PATH lands under it, an absolute PATH is used
      as-is. The client does not tab-complete it, since the server
      may run in a container whose filesystem differs from the
      client's.
  - Response: LP response-type "export-to-org" with
    =((content "REPORT") (errors ("..." ...)) (warnings ("..." ...)))=.
    =content= is a human-readable report (files written, broken-link
    count, warning count). =errors= is non-empty only on failure
    (bad/unknown skgrepo-set name, unreadable =.skg= files, filesystem
    error). =warnings= are non-fatal (skipped roots,
    broken links).
  - Behavior: Reads all =.skg= files fresh from disk, finds every
    export root, and writes each to
    =<output-dir>/<target_filepath>.org= as a recursive content view
    limited to =NAME=, stripped of skg metadata, with
    =[[id:..][label]]= links rewritten to relative org links. Each
    file begins with three comment lines: a fixed first line, then
    =# ROOT-PID=, then a fixed warning against editing the file. The
    importer ignores exactly this header.
    Existing files are overwritten; others are left untouched. Needs
    neither the live graph nor Tantivy.
    Before writing anything, a restricted export involving overPrivateText
    telescopes returns LP =overPrivateText-telescope-confirmation= with
    =(operation export-to-org)= and the exact PIDs. An approved retry
    carries those PIDs in =approved-overPrivateText-pids=. An =all= export, or
    an approved restricted export, returns the ordinary export response
    with the shared warning.
  - An *export root* is a node one of whose =contains= children has
    a title linking to the instruction node
    =3d9aa9be-d95a-48bc-b362-33f9e7ebdf6f= and a body yielding a
    =target_filepath= (a tolerant ~key = value~ parse; the value may
    be bare or quoted, but a bare value with whitespace is refused).
    The marker child is omitted from output. A nested export root is
    rendered as a link to its own file, not inlined. Links whose
    dest is not exported under =NAME= point to the export of
    =9ff04e25-01e8-4634-8aa5-f5849bc1eb81= ("Some links might be
    broken."); if that note is itself not exported, the link degrades
    to plain label text. A deep link targets =*Heading=, or =#PID=
    when that headline contains a link or repeats an earlier
    headline's text in its file; only headlines targeted by
    =#PID= get a =:CUSTOM_ID: PID= drawer.
  - The same export is available as a CLI subcommand (no running server):
    =cargo run --bin skg -- export-org [config-path] [skgrepo-set]
    [output-dir] [--include-overPrivateText-telescopes]=. Under a restricted set it
    fails closed before writing unless the flag is present; under =all=
    (and on an approved restricted run) it prints the warning.

** Delete references to an absent node

  - Initial request: =((request . "delete references to absent node")
    (id . "RAW-ID"))=. =RAW-ID= must still be absent.
  - If owned title/body links point at the ID, response type
    =delete-references-confirmation= carries =(id ...)=, an opaque
    =(approved-preview ...)=, =(content "ORG WARNING")=, and a prompt,
    followed by an empty rerender stream.  A retry echoes the exact preview.
    The warning ends with a line naming the command that investigates
    the ID ("Investigate unknown node").
  - Success response type =delete-references-result= carries Org =content=,
    =changed-nodes=, and =changed-memberships=, followed by rerender-lock,
    rerender-view*, and rerender-done for every open view.
  - The mutation removes only exact raw-ID matches in owned =contains=,
    =subscribesTo=, =hidesFromSubs=, and
    =overrides= lists.  It leaves text links and foreign telescopes
    untouched.

** Rerender all views
  - Request: =((request . "rerender all views")
    (approved-overPrivateText-pids "PID" ...))=.
  - Response: Multiple length-prefixed messages, sent sequentially:
    1. Lock message:
       =Content-Length: N\r\n\r\n((response-type rerender-lock) (lock-views ("view ID1" "view ID2" ...)))=
       Lists all view IDs that will be re-rendered. Emacs locks those buffers.
    2. Zero or more per-view messages (one per view, streamed as each finishes):
       =Content-Length: N\r\n\r\n((response-type rerender-view) (view-id "VIEW_ID") (content "..."))=
       Emacs unlocks and updates each buffer as it arrives.
    3. Done message:
       =Content-Length: N\r\n\r\n((response-type rerender-done) (errors ("..." ...)) (warnings ("..." ...)))=
       Emacs removes the rerender-view handler and unlocks any remaining buffers.
  - Behavior: Re-renders every open view from server memory; a buffer
    of the diff view is reconciled over the graph straddle.
    Does not save or modify the graph. Refreshes all views without
    requiring a save.
  - All view text is prepared in memory before the release decision.
    Under a restricted set, overPrivateText content without exact approval returns
    LP =overPrivateText-telescope-confirmation= with
    =(operation rerender-all-views)= and
    the exact PIDs, followed by an EMPTY rerender stream
    (=rerender-lock= with no view IDs, then clean =rerender-done=). No view
    text is sent and no open-view registry entry changes. A retry adds
    =approved-overPrivateText-pids=; =all= instead adds the shared warning to
    =rerender-done=.

** skgrepo-sets
  - Skgrepo-sets are the prefixes of the config's privacy order (see
    "skgconfig.toml > Repo sets" below): each skgrepo name denotes
    itself plus everything more public, and =all= means every skgrepo.
  - Request: ((request . "list repo sets"))
  - Response: LP response-type "repo-sets" with
    =((restriction "NAME") (sets ("NAME1" "NAME2" ...)))=. The sets are
    the skgrepo names in privacy order (most public first) followed
    by =all=; order is meaningful (it is the privacy ladder), so
    clients should preserve it.
  - Request: ((request . "skgrepo restriction"))
  - Response: LP response-type "skgrepo-restriction" with
    =((restriction "NAME"))=.
  - Request: =((request . "set skgrepo restriction") (name . "NAME")
    (approved-overPrivateText-pids "PID" ...))=.
  - Response: Multiple length-prefixed messages, sent sequentially:
    1. Skgrepo-set response:
       =Content-Length: N\r\n\r\n(("response-type" "skgrepo-restriction") ("restriction" "NAME") ("content" "Skgrepo restriction: NAME"))=
    2. The rerender stream, as in "rerender all views":
       rerender-lock → rerender-view* → rerender-done. Each open view
       is re-rendered in place under the new set: nodes whose skgrepo
       became restricted are converted and pruned (a restricted node
       with unrestricted viewchildren is retained, write-protected), and
       PartnerFolders regenerate per the new set, so widening the set
       reveals members and folders.
  - Behavior: The skgrepo restriction is per Emacs TCP connection. It
    defaults from =skgconfig.toml=, resets on reconnect, and is not
    written back to the config. Changing it requires confirmation in
    Emacs, re-renders (not closes) all active Skg buffers for that
    connection, and cancels any in-flight search enrichment.
  - Refusal: the endpoint's error paths (missing or unknown set
    name) answer in the normal skgrepo-restriction response-type,
    carrying the explanatory text as =content= and the UNCHANGED set
    as =restriction=, followed by an EMPTY rerender stream (a
    rerender-lock naming no views, then rerender-done), so the
    client's preemptive buffer locks and stream guard unwind.
  - Rerender authorization precedes both the set change and release of
    view text. If the proposed set would render an overPrivateText telescope, the
    first reply is LP =overPrivateText-telescope-confirmation= with
    =(operation repo-set-switch-rerender)= and exact PIDs, followed by an EMPTY
    rerender stream. A retry adds =approved-overPrivateText-pids=; declining
    leaves the skgrepo restriction and open-view registry unchanged.

* Content view

Rust sends the entire text document to Emacs, org-bullets and all.
Each org-bullet is followed by a space, some metadata, a space,
and then headline text.

The metadata is an s-expression containing bare values and key-value pairs,
wrapped in "(skg ...)" -- something like
#+begin_example
 (skg (id long-string) repeated (key value) another-value)
#+end_example

Any such string is valid metadata
(although much of it might be ignored by Emacs),
if and only if it adheres to the following:

- parentheses
  - The metadata starts with "(skg" and ends with ")".
  - Key-value pairs are wrapped in their own parens: "(key value)".
- whitespace
  - Whitespace separates all elements.
  - Extra whitespace is ignored.
  - Keys and bare values should contain no whitespace. A value that contains
    whitespace is represented as a quoted string atom; server-rendered skgrepo
    names and repo-derived herald values use this form automatically.

Inside a =(node ...)= form, =(affectsParent ...)= describes whether the
node participates in the membership represented by its viewparent:

- omitted =affectsParent= means =true=;
- =(affectsParent true)= is accepted but normally omitted when rendered;
- =(affectsParent false)= means the node is preserved/displayed but
  does not alter the parent's membership on save;
- =(affectsParent na)= is rendered for view roots.

The bare atom =omittedBody= accompanies =writeProtected= on a write-protected
node whose graphnode HAS a body — one the rendering hides. Herald
"B", hugging the ☮. Display-only: the parser accepts and discards it;
the view regenerates it.

A role graft -- a node a role tree drew, playing a partner role toward
its viewparent (e.g. =container= for a containerward role tree,
=mentioner= for a node that links to it, also =mentioned=, =overrider=,
=overridden=, =hider=, =hidden=, =subscriber=, =subscribee=) -- carries
=(affectsParent false)=, and its =(rels ...)= carries a birth fact naming
its role's relation (see "Stats metadata" below). The roles are the nine
in =PARTNER_ROLE_VOCAB= (=server/dbs/in_rust_graph/relation_accessors.rs=).
A role graft's herald is not a fixed glyph: the clients render its
semantic relation and ancestor facts, e.g. an =overrider= role graft
reads =Oa=, an =overridden= role graft =aO=.

** View requests: (viewRequests ...)

=(viewRequests ...)= carries client→server REQUESTS for viewbranches
(unlike =birth= and the stats below, which are server→client). On save
the server fulfills each request during view completion and then drops
the atom, so a request is transient. Request forms:

An editable node's default presentation includes its nonempty
=subscribeeFolder=, but no other top-level relation folder. This applies both
to ordinary positions and to nodes expanded as members of relation folders.
An editable subscribee-as-such additionally includes its nonempty
=hiddenInSubscribeeFolder=; =hiddenOutsideOfSubscribeeFolder=, when nonempty,
is part of the subscriber's =subscribeeFolder=. Use a folder request for the
other relation folders; their potential contents remain advertised by the
node's heralds.

- =(folder RELNAME)= — build BOTH folders of the relation, populated from the
  graph. RELNAME is =aliases=, =overrides=,
  =hidesFromSubs=, or =subscribesTo=.
  The editable folder (=overriddenFolder= / =subscribeeFolder= / =aliasFolder=)
  appears even when empty (its editable "add here" surface); an empty
  write-protected folder is pruned.
  Emitted by the =C-c l= commands.
- =(roleTree ROLENAME)= — build the role tree for one partner role, grafting
  the partners as inverted write-protected children, the role grafts. ROLENAME
  is one of the nine in =PARTNER_ROLE_VOCAB=. Emitted by the =C-c p= commands.
- =editableView= — on a write-protected occurrence, make it the node's
  editable one (the occurrence that was editable is write-protected,
  keeping its drawn content, each member of which, there and below,
  becomes a non-member); on an editable node, unfold its content
  editable, within =initial_node_limit= expansions. A buffer carries at
  most one per node.
- =writeProtectedView= — make the occurrence write-protected (its title
  resynced from the graph) and each of its direct child vognodes a
  non-member; the children keep their own editability and subtrees. The
  edits the occurrence carries in the same save are saved first. On a
  write-protected occurrence it does nothing. Emitted by =C-c s w=.
- =writeProtectedSubtreeView= — the same for the occurrence and its whole
  content subtree: every node in it becomes write-protected, and every
  child under them a non-member. Emitted by =C-c s W=.
  Either write-protect request together with =editableView= on one
  occurrence is refused; on two occurrences of a node they move
  editability. An editable occurrence adopts a non-member child that
  stands for an entry of its content list, where no member does, as
  that entry's member, so moving editability back restores the content.
- =flags= — add one write-protected =flagsFolder=, retained even when empty.
  Its true-only viewnodes use =(flag hadId)=, =(flag wasOverloaded)=, and
  =(flag noSearchMatching)= metadata in that order. Viewnodes have no Org title;
  their friendly visible label comes from the herald. Deleting the entire
  folder dismisses this optional viewbranch and has no persistence meaning;
  edits within a retained folder are rejected rather than silently ignored.
- =fork= — the explicit =skg-fork-node= gesture: clone this (owned)
  node into a private fork that overrides it. Consumed on the save path
  at fork detection (not during view completion), then dropped. Emitted
  by =skg-fork-node= (=C-c m f=).

** Stats metadata: graphStats and viewStats

Generated display facts decorate a =(node ...)= and are never save input.
=server/herald_tokens.rs= assembles graph counts and occurrence facts into
one semantic =(rels ...)= form. Clients render it; the wire contains no
assembled glyphs, omitted numerals or colors. For example:

#+begin_example
(rels
  (contains (in 2 (ancestors 1))
            (out 8 (ancestors 2) (unintegrated 3 (ancestors 2))))
  (linksTo (in 5 (ancestors 1 2)
                   (substantive 2 (ancestors 1)))
               (out 3 (ancestors 2)))
  (overrides (out 1 (ancestors 1)))
  (aliases 2) (extraIds 1) (flags 3)
  (birth (overrides out 1)))
#+end_example

Each relation side is =(in COUNT (ancestors GEN...))= or
=(out COUNT (ancestors GEN...))=. Empty sides are generally omitted;
=COUNT= is the complete distinct visible node count even when ancestor
flags let the client omit its numeral. =GEN= is an ancestor generation:
1 is the viewparent,
2 the grandparent, counting non-vognode levels. Relation keys are =contains=,
=linksTo=, =subscribesTo=, =overrides=, and
=hidesFromSubs=. The =linksTo=
incoming side adds =(substantive COUNT (ancestors GEN...))= for the subset
whose skgrepo has a nonempty body, visible direct content, or more than one
distinct visible resolved target. Its outgoing side counts distinct visible
resolved targets. An applicable subscribee-as-such =contains= outgoing side
adds =(unintegrated COUNT (ancestors GEN...))=, including when both counts
are zero; absence of that subform means the role does not apply. The
numerator counts members not already directly contained or hidden by that
occurrence's subscriber. Subset counts cannot exceed their side's total.
=(birth (RELNAME SIDE [GEN])...)= identifies the relation(s) behind this
occurrence: for each, the side of this node it is on (=in= or =out=) and
the ancestor generation it accounts for. =GEN= is omitted when no
ancestor accounts for it, as for a node drawn in place of a node it
overrides, which carries =(overrides out)=.

| Birth                            | Facts                                                        |
|----------------------------------+--------------------------------------------------------------|
| ordinary content                 | =(contains in 1)=                                            |
| subscribee-folder member         | =(subscribesTo in 2)=                                       |
| subscriber-folder member         | =(subscribesTo out 2)=                                      |
| overridden-folder member         | =(overrides in 2)=                                   |
| overrider-folder member          | =(overrides out 2)=                                  |
| hidden-folder member             | =(hidesFromSubs in 2)=                        |
| hider-folder member              | =(hidesFromSubs out 2)=                       |
| hidden-in-subscribee member      | =(hidesFromSubs in 4) (contains in 2)=        |
| hidden-outside-subscribee member | =(hidesFromSubs in 3)=                        |
| drawn overrider (overrides-here) | =(overrides out)=                                    |
| role graft                   | its role's relation, =out= for a first role and =in= for a second, =1= |
Nonzero =(aliases K)=, =(extraIds K)= and =(flags K)= are property counts.
See [[file:./heralds.org][heralds.org]] for the rendered notation and styles.

There is no longer a
=(graphStats ...)= sexp on an unrestricted node: its counts fold into the
form above (=overriding= / =subscribing= / =hiding= become the =O= / =S= /
=H= tokens; =aliasing= / =extraIDs=/true flags become the
=Ak= / =Ik= / =Fk= property tokens),
and the per-relation view-position flags (=containsParent=,
=overridesParent= / =parentOverrides=, =subscribesParent= /
=parentSubscribes=, =hidesParent= / =parentHides=, =grandparentOverrides= /
=grandparentSubscribes=) are gone — those facts are the
ancestor-lettered tokens now. (The bare =omittedBody= atom documented
above still rides a write-protected node whose graphnode has an omitted
body.)

=(viewStats ...)= still carries the position facts that are NOT
relationship tokens (the same graphnode can warrant different ones
under different parents):

- =cycle= — this position repeats an ancestor's ID;
- =(homeRepoHerald ⌂:LABEL)= — the node sits at a skgrepo boundary (a
  root, or a skgrepo differing from its nearest unrestricted-vognode ancestor);
- =(homeSkgrepoMove (old OLD) (new NEW))= — in the skgrepo-changes buffer of
  the diff view, the node's home skgrepo moved from OLD to NEW
  since HEAD; herald "-OLD +NEW". A display fact, discarded at save;
- =(movedLikeAncestor LETTER)= — beside =homeSkgrepoMove=, when the nearest
  vognode ancestor whose home moved moved the same way; LETTER names
  that ancestor as the relationship tokens do (a = the viewparent).
  Herald "Δ⌂=LETTER". A display fact, discarded at save;
- =(relRepo NAME)= — ugly herald "~NAME", drawn immediately before
  the ⌂ skgrepo herald; the relRepo of the RELATIONSHIP this
  headline represents (the =contains= relationship to a content child, or
  the folder's relation for a PartnerFolder member), when its privacy was
  deliberately raised above the relationship's default. This is an observed,
  recomputed display fact: save never reads it as input.
- =(editRequest (relRepo NAME))= — nonstandard herald "request:~NAME".
  This is the sole explicit relRepo request, written by
  =skg-set-relRepo= (C-c s r) and consumed at save, where
  the server enforces the floor (an offered skgrepo more
  public than the relationship's default is a save error; a skgrepo at the
  default or more private is honored, which is how a stuck relationship's
  privacy is lowered; a legacy or hand-authored relationship whose DISK
  skgrepo already sits more public than the default may be held or
  made more private, never made still more public). Absent means the
  relationship sits at its default relRepo. The relationship belongs to the
  view-parent (or a writable folder's viewparent), so a write-protected headline
  may carry this request too; the save refuses it only when nothing editable
  writes that relationship, e.g. under a write-protected parent.
  Alias and Unknown headlines likewise
  expose a flat/nested display =relRepo= fact and put write requests only
  under =editRequest=; copying a fact is harmless while copying a request
  deliberately requests it at the destination.
- =(editRequest (flag noSearchMatching true|false))= — an idempotent
  save-only desired-state request. The provenance flags =hadId= and
  =wasOverloaded= are write-protected and rejected here. A successful save consumes
  the request; a failed save leaves it in the buffer. Herald view presents the
  request as one red semantic state: =request:no search matching= for =true=,
  or =request:search matching= for =false=.
- =(overridesHere N)= — crucial =ĥ= immediately after the =O= token; the load-bearing
  substitution fact, documented in the next subsection.

** Node flags

The YAML =flags= list stores =Had_ID_Before_Import=, =Was_Overloaded=, and
=NoSearchMatching= using those exact spellings. Absence means false.
=NoSearchMatching= keeps the node's Tantivy documents for ID/title/repo
lookup but marks every title/alias document with indexed, stored
~no_search_matching=true~; every text query adds a mandatory exclusion. It
therefore blocks direct title, alias, body, regexp, operator, and
field-qualified matches, but is not an access-control boundary and does not
remove graph context.

** Override substitution and the overridesHere fact

When view completion would CREATE a viewnode for node N as
recursive content, and an owned overrider R of N is visible
under the skgrepo restriction, it draws R instead -- transitively (a
owned chain D overrides C overrides N is legal and resolves to
the last visible link), cycle-guarded, and never in the diff view.
Ordinary completion does not rewrite an existing raw viewnode merely because
an overrider is visible (closing and reopening normalizes). In a de-novo
render, only content substitutes: PartnerFolder members, view roots, search
results, role grafts and phantoms begin as the raw node.

The buffer whose approved save creates a fork is the post-save exception. A
root named by one of that save's exact =ForkSpec=s is rewritten from original F
to clone K, and an existing recursive-content occurrence in the saved forest
may likewise be replaced by its newly visible substitute. Both carry
=(overridesHere F)=. The completed forest remains under the same view ID, and
the open-view root index is recomputed from it, so that buffer is thereafter
registered as rooted at K. Collateral rerenders do not perform these
replacements; they retain their existing raw positions. A later independent
single-root request for F still opens raw F.

Moreover, the immediate children of ANY overridden node drawn raw -- a
PartnerFolder member, a view root, or the overridden-as-such (a member
child of an overriddenFolder) -- also draw raw: the user is looking at the
original, so its children are the original's, not the overrider's. This is one
level deep -- substitution resumes at the grandchildren -- and it is strict:
a node whose only overrider is invisible under the skgrepo restriction is
"overridden but drawn raw" too, so its children draw raw as well.

A substituted viewnode carries the keyed viewStats form
=(overridesHere N)= -- crucial =ĥ= immediately after =O= -- naming the original it
stands for. The fact is LOAD-BEARING at save: wherever it
appears, extraction collects N rather than the carrying node's own
ID, so a container's contains list round-trips to the original
instead of being rewritten to the overrider. Edits to the drawn
node itself (title, body, folders) still save to the drawn node.
A buffer whose fact the server would not have drawn (the carrier
is not on N's owned override chain -- the ownership-gated,
visibility-UNGATED walk out of N) aborts the save with an
explanation. With chains the honest carrier may be a MIDDLE link
(drawn when a later link's mentioner is hidden), so the check accepts
any node on the chain and rejects only off-chain facts. A
skgrepo-set switch that makes a
drawn substitute's skgrepo restricted turns it into an anonymous
=restrictedNode= (the fact does not survive -- a restricted node is
dataless); the original it stood for is preserved in its container's
contains by disk supplementation.

** Skgrepos

Each =[[repos]]= entry defines a directory of =.skg= files.
*Order is load-bearing*: skgrepos must be listed in privacy order,
most public first, most private last. That order defines the privacy
levels of the telescope model (see =docs/telescopes.org=) and the
available skgrepo-sets (below).

| Field          | Required | Description |
|----------------+----------+-------------|
| =path=         | yes      | Directory containing =.skg= files. Relative to data root. |
| =name=         | no       | Unique name for this skgrepo (used in metadata, provenance). Defaults to =path=. |
| =abbreviation= | no       | Short label for heralds. Owned skgrepos with defaulted names abbreviate to the path minus the owned folder. |

The skgrepo name =all= is reserved and rejected.

*Ownership is by location, not declaration*: a skgrepo is owned
(writable) iff its path lies under =<data_root>/<owned_folder>=,
where =owned_folder= is a top-level config field defaulting to
="owned"=. Everything else is foreign (never written). The old
=user_owns_it= field is retired and rejected with an error naming
the migration script (=bash/migrate-to-author-folders.sh=).

** skgrepo-sets

Skgrepo-sets are no longer declared; the retired =[[repo_sets]]=
table is rejected with an error. The sets are exactly the
*prefixes of the privacy order*: each skgrepo's name denotes the
set consisting of itself and every more-public skgrepo, and the
reserved name =all= means every skgrepo. Choosing a set is choosing
"the most private skgrepo to make available." =default_repo_set=
(top-level field) names the skgrepo restriction when a client connects.

Example:

#+begin_src toml
default_repo_set = "public"

# Privacy order: most public first.
[[repos]]
name = "public"
path = "owned/public"   # under owned/ => writable

[[repos]]
name = "private"
path = "owned/private"

[[repos]]
name = "Fred"
path = "Fred"           # foreign => write-protected
#+end_src

Here the available skgrepo-sets are =public= = {public},
=private= = {public, private}, =Fred= = =all= = {public, private,
Fred}.

** OTHER_SKGREPO_DEPENDENCIES.toml

At every server start the server writes an =OTHER_SKGREPO_DEPENDENCIES.toml=
manifest into each OWNED skgrepo directory. Its =dependencies= is a
list of pairs, one per skgrepo that skgrepo may reference — itself and
everything more public, in privacy order, the skgrepo itself last.
Each pair has a =path= (data-root-relative directory) and, unless the
skgrepo is not a gitrepo or has no remote, a =git-remote= (the fetch
URL =git remote -v= prints, =origin= preferred), so a receiver knows
where to fetch each dependency; when the chosen remote is not =origin=
its name is also recorded as =git-remote-name=. skg makes no use of
the =git-remote= values itself. For example:

#+begin_src toml
dependencies = [
  { path = "owned/public", git-remote = "git@github.com:me/public.git" },
  { path = "owned/private", git-remote = "git@github.com:me/private.git" },
]
#+end_src

It is generated output — hand edits are clobbered — and lets someone
who receives one of your skgrepos see what it depends on and where to get
it. When a FOREIGN skgrepo's manifest orders two skgrepos differently
than this config does, the server warns at init. (The receiver also
still reads the older bare-string =dependencies= shape, so manifests
published before this change keep working.)

** Log files

- =server-to-user.log= — human-readable log (always on).
- =server.jsonl= — structured JSON log (when ~timing_log = true~). Queryable with =jq=.

** Readiness marks file

=<data_root>/readiness-marks.json= holds the commit-readiness marks
of the diff view ('server/readiness_store.rs'). The server reads
it at startup and rewrites it after every change; a missing or
unreadable file means no marks. It is a JSON object whose =marks= is a
list of ={"leaf": KEY, "fingerprint": N}= entries. KEY names one
change-forest leaf ('LeafKey' in 'server/change_leaves.rs'): a node
aspect ={"Node": {"pid": ..., "aspect": ...}}=, where the aspect is
="Existence"=, ="Text"=, ="Home"=, ={"Alias": TEXT}=, ={"ExtraId": ID}=
or ={"Flag": FLAG}=; or a relationship aspect ={"Relationship":
{"relation": ..., "recorder": ..., "member": ..., "aspect": ...}}=,
where the aspect is ="Existence"= or ="RelRepo"=. N is the fingerprint
of the change the mark approved, a hash of the leaf's before and after
values; a mark whose fingerprint no longer matches the current change
counts as absent.

* The .skg file format

It is a specialization of YAML -- every .skg file is valid YAML,
although not vice versa. The definitive source of truth is
=server/types/nodes/fs.rs= (=GraphnodeOnDisk=).

Each file is one *telescope section*: the slice of one node
recorded at one privacy level (see =docs/telescopes.org=). One node =
one ID = same-ID =.skg= files across skgrepos, at most one per
skgrepo; the filename is the node's primary ID followed by =.skg= in
every skgrepo. The node's *home* is its MOST PUBLIC section, and
that section carries the =title= — an invariant, not a search rule.
A titleless section more public than the title still loads (the
composition reports it) but cannot be rewritten by a save. A field a
section omits is a field that section has no opinion about.
Pre-telescope single-file nodes parse unchanged (one section, title
present, no anchors).

Fields:

- =title=: A string, no newlines. Present in the home section only.
- =pid=: The node's primary ID. Must equal the filename stem. Present
  in every section.
- =extra_ids=: Optional list of additional IDs (from node merges).
  Home section only, by convention.
- =body=: An optional string, perhaps with newlines. Home only.
- =aliases=: Optional list of strings. Each section may contribute
  aliases; an alias's relRepo is its section's skgrepo.
- =contains=, =subscribesTo=: Ordered relations. ONE flat YAML
  sequence per relation, one entry per line:
  - =- ID= — a member recorded at this section's skgrepo. Identical
    syntax in every section, so a membership moving between skgrepos
    diffs as a clean one-line delete/add pair.
  - =- anchor: ID= — a placement anchor: the members after it (until
    the next anchor) insert immediately after the anchored ID, which
    lives in a MORE PUBLIC section. Members before the first anchor
    prepend to the front of the more public list. Anchors are derived
    on save from the in-memory order; hand-written anchors are
    honored on load (a dangling anchor's run falls back with a
    warning, and duplicate anchors concatenate in file order).
- =hidesFromSubs=, =overrides=: Unordered
  relations; plain lists of IDs. The effective list is the union
  across sections; each entry's relRepo is its section's
  skgrepo.

The COMPOSITION of all same-pid sections (most public first) yields the
node; saving DECOMPOSES the node back into sections, byte-stably, so
untouched sections do not change on disk. An owned section emptied
by a save is deleted; foreign sections are never touched.

* The metadata headers

Most org headlines in the client will have a 'metadata header',
consisting of some bare values and some key-value pairs
separated by whitespace. Each kv pair is wrapped in parens: (key value).
The whole collection is wrapped in (skg ...).
This metadata appears right after the org bullet and a whitespace,
and right before another whitespace and the node's title.

The metadata grammar (which keys are recognized and how they're
parsed) lives in =server/serve/parse_metadata_sexp.rs=. The
in-memory types those keys correspond to are in
=server/types/viewnode.rs= (=ViewnodeKind=, =Vognode=, =PropertyFolder=,
=Property=, =PartnerFolder=, =ChangeFacts=, =ReadinessRequest=).

Metadata is not WYSIWYG; its appearance in the client
is determined by =elisp/heralds-minor-mode=, whose rule table is
served by Rust (see "Herald rules" above; the table lives in
=server/heralds.rs=).

PartnerFolders are represented in Rust as
=ViewnodeKind::PartnerFolder (PartnerFolder)=, but their external metadata
remains the established bare non-vognode atom:
=subscribeeFolder=, =subscriberFolder=, =overriddenFolder=, =overriderFolder=,
=hiderFolder=, =hiddenFolder=, =hiddenInSubscribeeFolder=, or
=hiddenOutsideOfSubscribeeFolder=.

** Metadata of the diff view

The buffers of the diff view (see "Diff view") draw
changes with the forms below. All are display facts except the
readiness requests, which the save consumes; saving a buffer reads
none of the new viewnodes, which are save-inert. The glossary's "Terms
of the diff view" defines the vocabulary.

*** Presence: =(diff ATOMS)=
ATOMS are drawn from =node+ node- rel+ rel-=: the node HEAD lacks (=node+=)
or the worktree lacks (=node-=); the relationship to the viewparent
that HEAD lacks (=rel+=) or the worktree lacks (=rel-=). It sits inside
=(node ...)=, =(deleted ...)=, =(unknown ...)= and =(historical ...)=, and
at top level on alias, id and flag leaves, whose single diff object
is written =rel+= or =rel-=. A lost alias or ID is a =removedAlias= or
=removedID= leaf (below), whose =rel-= is display only.

*** Readiness: =(ready OBJECTS)=, =(readyRequest OBJECTS)=, =(unreadyRequest OBJECTS)=
=(ready OBJECTS)= lists the diff objects (=node=, =rel=) whose
change-forest leaves are all marked commit-ready; a bare =(ready)=
marks a single-object leaf, or an aggregate (a folder or changeset
marker) that is ready. It is absent when nothing is ready.
=(readyRequest OBJECTS)= and =(unreadyRequest OBJECTS)= ask the save
to set or clear the marks of those leaves; the object =all= names
every leaf of an aggregate, one level down. These sit where =(diff ...)= sits, and also at top level on the
properties below other than =bodyDiff=.

*** The diff view's viewnodes
- =removedAlias=, =removedID= -- in an alias or ID folder: an alias or
  extra ID that HEAD has and the worktree lacks, its headline the alias
  or the ID, carrying =(diff rel-)=. Saving reads no alias from it and
  does not count it among the node's IDs.
- =(historical (id ID) (repo REPO) ...)= -- a historical phantom: a node
  HEAD has and the worktree lacks, with HEAD's title and body; the
  grammar of =(deleted ...)=.
- =(oldText titleAndBody)=, =(oldText title)=, =(oldText body)= -- the
  node's text at HEAD, under a node whose text changed; its headline is
  the old title, its body the old body.
- =bodyDiff= -- under an old text: the line diff of the body, each line
  prefixed by a space, =-= or =+=.
- =(homeSkgrepoMove (old REPO) (new REPO))= -- the node's home skgrepo moved.
- =(relRepoMove (old REPO) (new REPO))= -- under a member: the skgrepo
  recording its relationship to its viewparent moved.
- =(changesetMarker content)=, =(changesetMarker relRepo)=,
  =(changesetMarker orderOnly)= -- a changeset marker.
- =acquiredByFolder=, =acquiredFolder= -- under a historical phantom, the
  node that acquired it by a nodeMerge; under an acquirer, the
  historical phantoms of the nodes it acquired. Both are write-protected
  and derived.

*** Changed folders
A partner, alias, ID or flags folder drawn because some relationship of
it changed is written =(FOLDER changed)=, e.g. =(containerFolder changed)=,
in place of the bare atom, and is followed by =(ready)= when every
changed member is ready. Its herald reads "its X changed (this file)"
or "(other files)" (see the glossary's "in, out").

*** In view stats
=(homeSkgrepoMove (old OLD) (new NEW))= and =(movedLikeAncestor LETTER)= may sit
in a vognode's =(viewStats ...)= in the skgrepo-changes buffer; see
"Stats metadata" above.

Examples:
#+begin_example
(skg (node (id 7) (repo main) (diff node+ rel+) (ready node)))
(skg (node (id 9) (repo main) (affectsParent false) writeProtected (diff rel-)))
(skg alias (diff rel+) (readyRequest))
(skg removedAlias (diff rel-) (ready))
(skg (historical (id 4) (repo main) (diff node- rel-)))
(skg (oldText title) (ready))
(skg (changesetMarker content) (readyRequest all))
(skg (subscriberFolder changed) (ready))
#+end_example

** Restricted-skgrepo nodes: omission, retention, and save preservation

Under a restricted skgrepo-set, rendering omits nodes from restricted
skgrepos entirely -- content, subscribees, and every PartnerFolder's
members alike. No restricted vognode appears, and omission is recursive: an
omitted container's whole branch is omitted, unrestricted descendants
included (they stay reachable by search or direct visit).

Saving preserves what rendering omitted: an omitted relationship
member cannot be deleted (or even seen), so the save merges the
buffer's visible lists with the disk lists -- order-preserving (the
anchored weave) for =contains= and =subscribesTo=, set-difference
for =overrides=. Edits to visible members, including
deletions, are honored.

The one place a restricted node still appears is retention: when a
skgrepo-set switch is applied to an open view (an already-drawn
buffer), a restricted node with unrestricted viewchildren stays on screen
as an anonymous restricted vognode, so its unrestricted descendants are not
orphaned:

#+begin_example
(skg restrictedNode)
#+end_example

The restricted vognode is dataless by design: a restricted node's id, skgrepo,
and title all describe content the user hid by restricting the
skgrepo-set, so emitting any of it would leak. It carries no id or
skgrepo and renders titleless. It is save-inert: it emits no fieldIntent
(its membership in its parent's list is owned entirely by disk
supplementation, not the buffer), it is not a collateral re-render target, and
editing its (empty) title/body is a buffer validation error. Its
unrestricted children remain fully editable. A de-novo render under a
restricted set never produces one -- restricted members are omitted and
their content is never expanded.

Edits to restricted nodes themselves are /suppressed/ at save, not
fatal: any nodeInstruction that would write a restricted skgrepo is
dropped and the save succeeds with the warning "Restricted nodes
present in saved buffer remain unchanged in graph." An untouched
stale node saves silently (its identical-to-disk nodeInstruction is
discarded as a no-op first).
