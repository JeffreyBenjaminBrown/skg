* Data Model Skg Extensions

Skg grafts a novel sharing model onto a familiar data model older than Rome.
** The familiar part: Trees with links
This is [[file:./data-model-trees-with-links.org][the data model that almost all serious knowledge mapping software seems to use]].

(If 'link' sounds weird, just think 'hyperlink'. If you use the internet, you are used to using these.)

*** What the =contains= relation means, and how it differs from links
Each document is a curated view of data defined by the =contains= relation. Any document that includes the node N also includes every node that descends from N via =contains=.

As described in the [[file:./data-model_technical.org][technical data model]], nodes can
be connected by =contains=, =linksTo=, and several other relationships.
Containment and links differ in two ways:

- Links are defined by the text in a node, whereas containment is defined by nodes' spatial relationships to each other in a tree (the document containing them).
- Following a link requires the user to jump to a different context, whereas following a containment relationship need only require moving your eyes. If A contains B, looking at A means looking at a document that already contains B underneath A.
** Each node of a document is a separate file.
This is unusual -- in most applications, the entire tree of text would be a single document. The one-file model has the advantage that a document can be easily read without special software. But the Skg model makes it possible to share granularly (see [[file:./sharing-model.org][the sharing model]], and [[file:./diffs-are-clearer-in-skg.org][easy to understand changes]].
** The forks relationship
A file F can fork file O. Visiting O directly still opens O itself as the raw root. Fork facts can be inspected in the heralds. Separately, wherever O would appear as recursive /content/ of a node already in view, F can be shown in its place automatically; this is /override substitution/ (see [[file:./sharing-model.org][the sharing model]]).

Forking is useful for both sharing and privacy, as is explained below.

Forking is represented in the graph with the =forks=
relationship.
** Sharing
When you "edit" a note N that you don't own, what actually happens is you gain a new note N', which begins with all of the content from N plus a (deletable) =forks= relationship to N.

Because nodes in Skg are represented as flat files, N' duplicates very little data. For instance, if N consisted of two big branches, then the file representing N would only contain some text and two nodes. If you changed their order, you would have to duplicate N (with its text and its two nodes), but you would not have to duplicate anything inside either branch.

The =forks= relationship is what makes Skg show N' wherever N would appear as recursive content. Opening a fresh view of N (say, by following a link) still opens raw N; its subscriber folder, in search results or requested, exposes N', which forks it.

The same relationship makes new content in N appear in your N' as "unintegrated forked content" (which you can proceed to integrate if you like). If you delete the =forks= relationship, both stop being true. N' can also fork other nodes apart from N.

If the original N contains C, and you delete C from your N', then N' gains a "hidesFromSubs" relationship to C, which prevents C from being shown as "unintegrated forked content" in N'.
** Privacy relies on forking.
The previous section describes how forking is used to integrate foreign content into one's data. Forking is also the mechanism by which private data is added to public data.

Suppose you have a puBlic note B that contains branches X and Y. Suppose you would like to include a third branch Z, but you want Z to be private.

Skg's solution is to fork B into a new priVate note V, which contains X, Y and Z. When you view B in "private mode", your private note V will stand in B's place. But when you are in "public mode", following a link to B will bring you to B.
