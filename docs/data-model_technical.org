* Skg data model: technical reference

This document describes the complete runtime graph model.  The =.skg= files
and =skgconfig.toml= are authoritative.  At startup and explicit rebuild, the
server composes all file sections into =Graphnode= values, validates the whole
set, builds an immutable =InRustGraph= graph snapshot, and builds Tantivy from the
same values.  Tantivy is a derived search index; it is not graph authority.

For a gentler introduction, see [[./data-model_friendly.org][the friendly data-model guide]].  For
privacy-section composing and decomposing, see [[./telescopes.org][telescopes]].

** Node fields

The full composed representation is =Graphnode= in
=server/types/nodes/complete.rs=.  =GraphnodeInRust= is its graph projection and adds
derived text links.

| Field | Type | Meaning and storage |
|-------+------+---------------------|
| =pid= | =ID= | Immutable primary identity.  It determines the home filename and is the key in =InRustGraph.nodes= and Tantivy. |
| =extra_ids= | =Vec<ID>= | Former identities acquired by node merge.  They are normalized in stable first-occurrence order, excluding the node's own PID.  Any primary or extra ID resolves to the node's =pid=. |
| =home_repo= | =RepoName= | The node's home: the most public skgrepo with a retained telescope section.  It is inferred from file location and never serialized inside YAML. |
| =title= | =String= | Composed node title. |
| =body= | =Option<String>= | Composed body text.  Leading and trailing whitespace-only lines are normalized away; a body with no remaining content is =None=. |
| =overPrivateText_telescope= | =bool= | True when the selected title or body came from a section below the home skgrepo.  Release decisions use this conservative folded fact. |
| =aliases= | =MSV<RelPartner<String>>= | Search aliases and the skgrepo at which each is recorded. |
| =contains= | =Vec<RelPartner<ID>>= | Ordered content children and each relationship's relRepo. |
| =forks= | =MSV<RelPartner<ID>>= | Ordered nodes this node forks, with relRepos: their content it does not contain or hide shows under it, and each is its mirror.  Stored under the '.skg' key 'forks'. |
| =hides= | =MSV<RelPartner<ID>>= | Nodes suppressed when reached through what this node forks, with relRepos. |
| =flags= | =Vec<Flag>= | Node flags: import provenance (=Had_ID_Before_Import=, =Was_Overloaded=) and behavior settings such as =NoSearchMatching=. |
| =linksTo= | =Vec<ID>= on =GraphnodeInRust= | Outbound Org =id:= links parsed from title/body text.  Derived rather than serialized as a graph field. |

=MSV<T>= means “maybe specified vector.”  =Unspecified= says a file or edit
has no opinion about the field; =Specified([])= explicitly supplies an empty
value.  This distinction is load-bearing while telescope sections and partial
nodeIntents are combined.  =RelPartner<T>= attaches the privacy
skgrepo where an alias or relationship is recorded.  The order of list-valued fields is
preserved.

** Relationships

All stored relationships are directed from the owning node to a member ID.
Member IDs may be primary IDs or extra IDs; graph indexes canonicalize known
extra IDs to the corresponding primary ID.  A dangling member is retained so
that hand-authored or temporarily incomplete graphs remain representable.

| Relationship | First role | Second role | Semantics |
|--------------+------------+-------------+-----------|
| =contains= | container | contained | Ordered document/content nesting. |
| =forks= | forker | forkee | The forker shows the forkee's content that the forker neither contains nor hides, and the two are mirrors: either may stand in the other's place where mirror substitution acts.  The fork operation's clone forks its original. |
| =hides= | hider | hidden | Suppresses the hidden node only when it would be reached through what the hider forks. |
| =linksTo= | mentioner | mentioned | Plain Org ID links derived from text. |

Home skgrepo and which node carries each extra ID are node properties, not separate runtime
relationship entities.  Relationship relRepo remains part of every stored
=RelPartner= and participates in skgrepo-set/privacy gating.

** Hard validation constraints

=validate_complete_graph= runs before the startup/rebuild swap-in.  Saves
preserve the same constraints incrementally: while holding the mutation gate,
they derive an exact persistent candidate from the current valid graph snapshot,
validate the identities and relationships whose truth can change, and check
the affected recorderward-relmap entries before any file mutation.  A candidate is
rejected when any of these conditions holds:

1. A primary ID identifies more than one composed node.
2. An extra ID belongs to more than one node.
3. An ID is both a primary ID and an extra ID.
4. A node's home skgrepo is absent from the current configuration.
5. An owned note forks itself, contains itself or hides itself.  A link to
   itself is fine.
6. An owned note both forks and contains one note, contains a note that
   forks it, or forks a note that contains it.  A dangling ID, naming no
   note, breaks no such pair.
7. Any stored graph index differs from an independently recomputed
   one.

The complete validator makes one exception to rule 6: a pair in which a
foreign note takes part (a foreign note forking an owned note that
contains it, or an owned note forking a foreign note that contains it)
is a warning there, not an error, since only a hand edit of the owned
note could otherwise mend what the foreign author did.  Startup and
rebuild report it among the startup warnings, naming both notes and
which is foreign ('foreign_note_taking_part' in
'server/dbs/in_rust_graph/override_invariants.rs'), and proceed.  A save
that leaves such a pair is still refused, so a save of the owned note
succeeds only once it ends the pair.

Any number of notes, owned or not, may fork one note, and forks may form
cycles: mirror substitution ([[file:mirrors.org][mirrors.org]], "Mirror
substitution") ranks a note's mirrors and has no cycle case.

Relationship roles are enforced by distinct Rust fields.  A node has exactly
one =home_repo= in its composed representation.  Telescope validation also
checks privacy/provenance rules.  Telescope violations are deterministic
warnings rather than hard graph-construction errors; callers surface them for
repair while retaining readable data.

The incremental proof relies on induction: startup or rebuild establishes a
valid base (but for the warned pairs above, which a save touching their
owned note must end), and each serialized save proves that its delta preserves validity.
Which node carries each ID is evaluated as one simultaneous final-state overlay;
the checks of forks, contents and hides cover the touched notes, the notes
they contain or fork or that contain or fork them, and untouched notes whose
contents or forks name an ID that canonicalization re-keys.  Local graph-index checks compare
only keys that could change.  The complete validator remains an independent
startup/rebuild gate and test oracle.

The shared mutation gate serializes candidate construction, filesystem
mutation, graph swap-in, and Tantivy enqueue so two writers cannot validate
against the same stale graph snapshot.  Filesystem preflight and graph validation
produce tokens tied to that exact graph snapshot; skgsave-commit consumes those prepared
values rather than recomputing them after writes begin.

** Graph indexes

=InRustGraph= stores =GraphnodeInRust= values in a persistent =im::HashMap=.  Its
derived indexes are:

| Index | Key -> value | Purpose |
|-------+--------------+---------|
| =contained_by= | contained pid -> container pids | Inverse =contains= traversal. |
| =forkers_of= | forkee pid -> forker pids | Inverse =forks= traversal, mirror lookup and validation. |
| =hiders_of= | hidden pid -> hider pids | Inverse hiding lookup. |
| =mentioners_of= | destination pid -> linking pids | Incoming text-link traversal. |
| =extra_id_to_pid= | extra ID -> primary ID | Canonical identity resolution. |

Construction is two-pass: first collect every extra-ID mapping, then insert
nodes and build recorderward relmaps.  This makes results independent of file read
order.  Incremental mutation instead installs the batch's complete final
identity state first, then reindexes each touched node and every untouched
recorder whose raw relationship can resolve differently under the final identity
map.  All four recorderward relmaps use that same final resolver.  Deletion is
supported: references to a deleted PID remain raw and surviving recorders are
rekeyed where canonical resolution changed.  Writers clone the persistent
graph and swap in one new =Arc= atomically; readers retain the immutable
generation they captured at operation start.

Managed saves support monotonic acquisition of extra IDs during node merge,
but reject arbitrary extra-ID revocation.  An apparently unused alias may be
how someone else's data links to the node, and Skg cannot infer that even the
most private skgrepo was never shared with a trusted person.  Raw-file editing
and rebuild remain an escape hatch, but spending effort to remove such tiny
identity metadata is usually a poor trade.

Leak-shaped telescope warnings judge only relationships recorded in owned
skgrepos; a foreign skgrepo's file is never a leak.  They use the target's
home as the privacy ceiling when the target exists.  For a dangling relationship there is no target home, so the
extant recorder's home is the conservative ceiling.  Saves recompute warnings for
saved recorders plus untouched inbound recorders affected by identity, existence, or
home changes; startup and rebuild still audit every recorder.

** Runtime generations and rebuilding

An =SkgEnv= family shares one atomic =RuntimeGeneration= swap-in point and
one mutation gate.  A generation contains an =Arc<SkgConfig>=, an
=Arc<InRustGraph>=, the matching =TantivyIndex=, and a monotonically increasing
generation number.  Each request captures exactly one generation and threads
its graph through graph-dependent helpers.  There is no process-global graph
fallback.

Startup and “rebuild session-lifetime stores” both read the filesystem once,
validate the candidate graph, and build graph plus Tantivy from that same node
vector.  A live rebuild swaps in only after the complete candidate succeeds;
failure leaves the prior generation visible.  The operation never rewrites
authoritative =.skg= files.

The generation number starts at the microseconds since the Unix epoch when
the server starts, so that a generation in the server's log places itself in
time, and each swap-in adds one.  It is internal: it names the generation a
reload notice swapped in, the generation a rerender pass refreshes against,
and the search index a rebuild builds, and it dates nothing a client holds.
No view response carries it.  Whether a save is stale is decided by content, not by
generation: the save compares the buffer's baseline, the text the server
last drew for it, with the graph (=docs/api-and-formats.org=, "Save buffer"
and "The baseline of a view").  So a restart, a rebuild or a strip of body
whitespace makes no buffer stale by itself.

*** A batch of files changed on disk becomes a generation

The server also learns of =.skg= files that change on disk without it
(another writer, a =git pull=): the repo watcher (=server/repo_watch/=)
watches every skgrepo directory and gathers the changed paths of a
burst into one batch, once the directories have been quiet for
=repo_watch_quiet_ms=.  The batch is reloaded as a save's
nodeInstructions are, under the mutation gate, but nothing is
written (=reload_changed_skg_files= in
=server/repo_watch/reload.rs=):
- each path names a skgrepo (its directory) and a pid (its file name);
  a path whose file is as the server itself last left it is dropped
  (=server/repo_watch/own_writes.rs=), since every server write of a
  =.skg= file records the path and a hash of its content;
- each pid's telescope is read again from every skgrepo, as a load
  reads it: illegal sections set apart, the rest composed, extra IDs
  resolved through the current graph.  A node the graph has, and disk
  no longer, becomes a Delete; one that differs from the graph's, a
  Save; one that agrees, nothing.  A file that cannot be read leaves
  its node as the graph has it;
- the nodeInstructions go through =prepare_graph_update=, the save's
  incremental validation over the current graph, so a batch costs what
  a save of its nodes costs, not a rebuild.  A batch that fails leaves
  the graph as it was, and its paths are tried again with the next;
- the candidate, with its illegal edits brought up to date, is swapped
  in as the next generation, so a buffer that showed a node of the batch
  before is refused if its save would write it: its copy no longer
  matches the graph.
  The search index is updated in the background, as after a save.
A notice of what the batch did reaches every connection, which tells
its client between requests and names the views to rerender
(=docs/api-and-formats.org=, "Repo files reloaded"); the rerender of
a buffer of the diff view it names also extends it
(=docs/diff-view.org=, "After a reload").

** The refresh: how a view follows the graph

Every buffer the server sends is drawn by one operation, the
*refresh* (=refresh_viewforest= in =server/refresh/mod.rs=). It takes a
viewforest the parse has read and validation accepted (every new
headline already has a gnid and a skgrepo), the *truth* (=Truth=: the
in-Rust graph as the skgrepo restriction lets it be seen, with the
config), the mode (=RefreshMode= in
=server/refresh/mode.rs=: a content view, or a buffer of
the diff view over the graph straddle, with the processed store) and
the node budget (=initial_node_limit=). It
changes the viewforest in place and returns nothing of what it
changed; each caller renders the viewforest once, when it is done
with it. A fresh content view is the refresh of a stub
(=stub_of_fresh_content_view= in =server/update_buffer.rs=: one
editable occurrence per requested node, asking for its containers
folder and to be the node's editable occurrence); a rerender, the
saved view and every collateral view are refreshes of what the
buffer holds (=refresh_view= in =server/rerender_pass.rs=); the search buffer is the refresh of
a stub built from the hits (=build_search_viewforest=, which
=draw_search_buffer= refreshes); the diff
view's buffers are refreshes in diff-view mode (=docs/diff-view.org=,
"Rendering a buffer").

The refresh decides everything from the buffer and the truth as they
are now, never from what either was at an earlier save. So it is a
fixpoint: refreshing its own output changes nothing, up to the
viewnode IDs it assigns. =tests/idempotence.rs=
asserts this over every content-view and diff-view fixture.

*** The kinds a refresh sees
A *vognode* stands for a gnid (=Vognode=): an *occurrence*, of a node
the truth has, editable or write-protected; a *ghost*, in the diff
view only, of a node HEAD has and the worktree lacks; an *unknown
viewnode*, of a gnid its viewparent's list names and no node answers to; a
*restricted viewnode*, of a node the skgrepo restriction keeps out
that a visible record names (a record is a relationship as one
node's file states it, in one skgrepo's section, visible when the
skgrepo restriction holds that skgrepo), showing nothing of the node but the
record's gnid and relRepo. A
*descriptor* describes its viewparent: a folder, a property member
(an alias, an ID or a flag in its property folder) or a change
viewnode. A *tombstone* says only that something stood there, and
holds the children of what it replaced. A tombstone whose only
children are tombstones stays, as after deleting a node and what it
contained: these nested tombstones are by design, and collapsing them
was considered and rejected because it could confuse the user. The
buffer root holds the roots.

*** The ID rule
What a headline standing for a gnid becomes is decided by five
questions, the first yes winning (=id_rule= in
=server/refresh/id_rule.rs=). Does the truth have the node? Then it is
an occurrence of the node's pid. Otherwise, does the truth say the
node is restricted (=Restricted=, =GnidPresence=: the
skgrepo restriction keeps out its home)? Then, if its viewparent's
goal names the gnid (its record is visible), or it is a root
of the view (the view is the user's own request), it is a restricted
viewnode; if not, a tombstone. Either reveals nothing of the node.
Otherwise, in the diff view, does HEAD have it? Then it is the node's
ghost, unless the skgrepo restriction keeps out HEAD's node's home, when it
is answered as a restricted node is: a restricted node is never a
ghost. Otherwise,
does its viewparent's list name the gnid? Then it is an unknown viewnode.
Otherwise it is a tombstone. In a content view an occurrence the
rule answers so does not become one: it *vanishes*, removed with its
subtree, a view root included, for its node is gone or restricted and
its viewparent's list does not name it ('docs/glossary.org',
"vanish"); in the diff view it becomes a tombstone. So an occurrence
of a node a skgrepo narrowing keeps out becomes a restricted viewnode
in place where its record is visible, and an occurrence again after a
skgrepo widening; where its record is not visible it vanishes, and
the skgrepo widening draws it again. When an unknown viewnode or a restricted viewnode
becomes an occurrence, each of its children claims again, as the
text of its view, which writes no =noClaim= under it, would say, and
the claims rung makes those vanish that the truth does not warrant
there. In the diff view, a gnid that HEAD had
as a node and that a nodeMerge has since made an extra ID of another
node stays that node's ghost. The headline is re-kinded where it
stands, keeping its viewnode ID, its fold state, its children and,
for an occurrence, its editability.

*** Claim and warrant
Each child of a vognode or a folder has two flags. It *claims
membership* when the save will read it as a member of its
viewparent's list. That is declared: the bare atom =noClaim= says no,
its absence yes (=claimsMembership= on the occurrence, the ghost, the
unknown viewnode, the restricted viewnode, the alias and the ID). The save reads claims only under an
editable occurrence, and under an editable folder (forks,
hidden-outside, alias) of one
(=parent_reads_claims= in =server/refresh/ancestry.rs=); under any
other viewparent no child claims, whatever it carries, and the
server writes no =noClaim= there. A child *is warranted* when the
truth relates it to its viewparent as its position implies: content
its occurrence contains, a partner of the folder's relation, a
container of the node above it in the containerward chain, a
property of the node in a property folder. In the diff view HEAD
alone may warrant it, a *ghost warrant*. The warrant is derived
(=Warrant { ByGraph, ByHead, No }=), recomputed at every refresh and
written in =(view ...)= as =noWarrant= or =ghostWarrant=, nothing
meaning warranted by the truth; a root carries none, nor does a
tombstone's child, but for an orphan graphnode, which is
unwarranted.

Under an editable parent at rest the two agree: every child that
claims and that the truth does not warrant vanishes at the refresh,
with its subtree, and the next save makes every claim warranted. They differ only for what
the user typed since the last save: a new child claims and is not yet
warranted, and a child the user marked =noClaim= to detach it is
warranted and claims nothing (a *pending detachment*, herald
"detach"). The refresh sets no claim but a root's: the user's claims
are the user's to make, and a claim the truth does not warrant the
refresh does not mark but removes, with the child that made it.

In the forks folder a claim says "the folder's viewparent forks it".
A goal item there may refuse a claim (=GoalItem::claimable= false, a
forker-only member's): a child claiming it is unwarranted
(=warrant_of_child=), and vanishes, and the item is drawn again
claiming nothing (=draw_item=). So a member claims exactly when the
note forks it, and a save of the view never makes the note fork a
forker it only showed.

*** The goal
A parent's *goal* is what the truth says its children should be
(=goal_of_parent= in =server/refresh/goal.rs=): for an occurrence's
content, its =contains= list in file order (for a forkee shown as
such, less what its forker hides or already contains); for a node
of the containerward chain, its containers; for a folder, its
partners in the folder's relation, or the compound folders' derived
lists; for a property folder, the node's aliases, IDs or true flags.
A containers folder's goal leaves out every view-ancestor of the node
it describes: each gnid a vognode above it stands for, folders passed
over, since the view already shows that container
(=Folder::omits_view_ancestors=, =view_ancestor_gnids= in
=server/refresh/ancestry.rs=).
Each item names a gnid, by the pid its list entry resolves to or the
raw ID when nothing answers to it, or a property value. The goal is
ordered where the viewparent's own file records the order (content,
aliases, and the forks, hidden and hidden-outside folders:
=Folder::goal_is_ordered=), and unordered elsewhere. The forks
folder's goal is ordered only in part: its forkees lead, in the
order of the note's 'forks' list, and its forker-only members, which
no list orders, follow them all, in the order the view has them
(=Goal::ordered_then_unordered=, "The forks folder" below). In the diff view the goal is the union
of the parent's lists in the two graphs of the straddle, an item only
HEAD's list holds being warranted by HEAD. A parent whose position
implies no relationship (the buffer root, a tombstone, an unknown
viewnode, a restricted viewnode) has no goal.

Under a skgrepo restriction a goal omits each member whose record is
restricted: the gated accessors of the in-Rust graph leave it out;
an alias folder's goal omits an alias whose record is restricted, and
the stats count it nowhere. The diff view's goal asks the
skgrepo restriction too, though the diff view opens only on an
unrestricted connection: a switch rerenders its open buffers.
It keeps each member whose record is visible: a node the
skgrepo restriction keeps out, which the ID rule, finding the node restricted and the
gnid named by the goal, answers with a restricted viewnode; and a gnid
nothing answers
to, an unknown viewnode, as under no skgrepo restriction. The save is its mirror: it
restores to a list only the members whose records are restricted,
and to a node's aliases only those whose records are restricted,
which the buffer could not show (=preserve_invisible_members= and
=server/from_text/weave.rs=), so a restricted viewnode keeps its member
while it claims, and deleting its line removes the record.

The rule behind the mirror: the skgrepo restriction limits what the
save may write as it limits what the refresh may show. Every decision
of the save that a record's absence from the buffer drives (a member
gone from a list, a hide, an alias, an extra ID, a forks relationship
gone, a relRepo or a home that differs) asks the record's
visibility first, and a record the skgrepo restriction keeps out is
neither removed, moved nor rewritten, whatever the buffer shows in its
place. A write that acts on the skgrepo restriction's silence is a defect.
So the forkee-visibility step, which rewrites a forker's
hides from what an editable forkee as such shows of its content under it
(=resolve_visibility.rs=), reads the forkee's content and the
forker's hides by their visible records: a hide recorded in a
restricted section is neither removed nor moved, though the
forkee's visible record shows the hidden node as its content, and
no hide is written of a member that only a restricted record
explains. The inference of hides from a removal
(=infer_hides_from_contains_removals=) reads the same way: the
forker's visible forks, their content by visible records,
and its visible hides. So does the hiding of a forker deleted from a
forks folder (=resolve_forks_folder_removals=): only a forker whose
record the skgrepo restriction shows was drawn, so only such a one
is hidden for its absence.

The rule has a converse for what the save creates: no record lands in
a section the skgrepo restriction keeps out unless the graph already
holds it there (=refuse_records_landing_restricted= in
=server/from_text/validate.rs=, after the suppression of writes to
restricted nodes, which keys on the graph's home as well as the
buffer's). A new hide's relRepo is at least as private as each record
that explains it, the forks relationship and the contains record
(=hide_skgrepo=), so that a public hide never names a private
membership. The writes built from the graph rather than the buffer
obey the rule apart: a fork's clone copies only the visible records
(=build_fork_clone=); a nodeMerge, like a delete, is refused when
either graphnode has a restricted section; and a delete's propagation
(=apply_delete_propagation_cleanup=) counts the restricted records
naming a deleted graphnode first, and the save stops for the
delete-from confirmation when there are any.

*** The walk and the refresh's rungs
Before the walk, every editable-view request in the text is
fulfilled: its occurrence becomes the node's editable one and any
other editable occurrence of the node is write-protected
(=fulfill_editableView_requests=), the request staying on it for its
visit to consume; and where a nodeMerge made two
editable occurrences stand for one node, the first in level order
stays editable (=keep_the_first_editable_occurrence_of_each_node=).
The input holds at most one editable occurrence per gnid, which
validation guarantees for a saved buffer
(=Multiple_Defining_Viewnodes=); the refresh asserts it and does not
re-check. The walk then holds each node's one editability by the
node's pid, whichever of its IDs the occurrence is written under
(=Walk::editability_key=), so that an occurrence the refresh draws
elsewhere hears that the user's occurrence, written under an extra
ID, holds it. In the diff view an ID that HEAD had as a node of its
own, and that a nodeMerge has since made an extra ID, keys only
itself: the ID rule makes its occurrence that node's ghost, and the
acquirer's own occurrence keeps the acquirer's editability.

The walk then visits every parent in level order from the buffer
root, a parent's own kind settled before its children are visited.
At each parent P (=visit_parent= in =server/refresh/visit.rs=) it
consumes P's editable-view request and charges the node budget
(below), lets the request extend the content P already shows, adds
P's default folders, computes P's
goal, and runs the *refresh's rungs* in order, weakest first (older
text calls them the ladder):
1. re-kind: each vognode child becomes what the ID rule says (in a
   content view, an occurrence it makes a tombstone vanishes); each
   descriptor whose position the ancestry table forbids is
   *unsayable* and becomes a tombstone, and so does a change viewnode
   whose change is gone, and an alias whose record the
   skgrepo restriction keeps out;
2. viewnode merge: duplicate viewnode siblings, standing for one
   gnid, are merged into one viewnode, which stands where the first
   stood and gets a fresh viewnode ID; it is folded (and body-folded)
   only if every sibling was, and focused, editable and claiming if
   any was (but not editable where it stands for another node whose
   editable occurrence is elsewhere in the buffer); it carries the siblings' requests; every sibling's
   children are appended to it in sibling order, for the claims
   rung of its own visit to judge (the glossary's "viewnode merge");
3. warrant: each child's warrant is set from P's goal;
4. claims: under a parent whose claims are read, each child that
   claims and that the truth does not warrant vanishes, with its
   subtree; under any other, no child claims, but an unwarranted
   child of the hides folder whose hide no record names, or of a
   containers folder that stands for a view-ancestor, vanishes;
5. reinstate: each goal item no child stands for is drawn, as far as
   the extent allows (below); what it draws is what the ID rule makes
   of the item, and a member of a folder whose members carry the
   containerward chain gets its chain;
6. reorder: where the goal is ordered, the children it names take its
   order, and every other child rides right after the sibling it
   followed; where it is not, nothing moves, and a drawn item follows
   the last child the goal names (as does a drawn forker-only member
   of a forks folder, all of which share the position after the last
   forkee: =Goal::keeps_the_views_order=);
7. substitution: in a content view, under an editable occurrence, a
   member is shown as the mirror shown for it, with =(inPlaceOf
   N)=, except where P is itself shown raw where another mirror would
   stand (a root, or a member of a folder that is no forkee as such);
   when the original itself becomes the mirror shown, the
   carrier loses the part and the original is reinstated beside it
   (=docs/api-and-formats.org=, "Mirror substitution and the
   inPlaceOf part");
8. requests: each child's view requests are fulfilled and dropped
   (=writeProtectedView=, =writeProtectedSubtreeView=, =(folder
   REL)=, =flags=); =fork= stays for the save. An edit request is carried through untouched unless the
   child's new kind has no slot for it, in which case it is dropped
   and reported.
In the diff view, between rungs 5 and 6, the change viewnodes P
should hold are drawn or kept, and each child is tagged with its
change (=server/refresh/diff_view.rs=). After the rungs, a folder
left with no child is entombstoned, unless the save reads its
membership or it is the flags folder, which stays visible when empty
('folder_goes_when_empty').

A content view draws some folders unasked (=add_default_folders=): an
occurrence that an editable-view request extends, a fresh view's
roots and every occurrence the refresh draws editable among them,
shows its forks folder when it has a fork partner, either way, by a
record the skgrepo restriction shows (=has_a_fork_partner=); an
editable forkee shown as such shows the folder of what its forker
hides in it, when that holds anything. And every forks folder of a
content view holds, last, the folder of what its viewparent hides
outside its fork partners, when it hides something there
(=add_hidden_outside_folder_to_forks_folder=), so that a forker a
save hid stands there.

*** The ancestry table
=required_ancestry= (=server/refresh/ancestry.rs=) gives each kind of
descriptor the ancestors it may stand under, nearest first: a folder
under an occurrence (the acquired-by folder under a ghost; the
hidden-outside folder in a forks folder; the hidden-in folder under
a member of a forks folder); a property member in its
property folder; a change viewnode under an occurrence or a ghost,
and a body diff under an old text. A descriptor whose ancestors are
not those is unsayable. A vognode has no row: an occurrence is never
unsayable.

*** The forks folder
The forks folder ('Folder::Forks', =forksFolder=) under an occurrence
of a note N holds N's fork partners, each once: the notes N forks
(forkees) and those that fork it, by records the skgrepo restriction
shows. A *mutual* both forks N and is forked by it; a *forker-only
member* forks N and is not forked by it.

**** Its goal and its claims
Its goal (=forks_folder_goal= in =server/refresh/goal.rs=) is N's
forkees in the order of N's 'forks' list, each claimable, with the
relRepo of each unknown or restricted one; then its forker-only
members (=forker_only_members=): the notes that fork N, in graph
order, less those N forks or hides, each unclaimable
(=GoalItem::claimable= false). The forkees take the list's order;
the forker-only members keep the order the view has them in, after
the last forkee (=Goal::ordered_then_unordered=). So a member claims
exactly when N forks it: a forkee or a mutual claims, a forker-only
member claims nothing. A member claiming what N no longer forks
(another view's save removed the fork) is unwarranted and vanishes,
and, if it still forks N, is drawn again claiming nothing. A member
claiming nothing that N forks is a pending detachment, as anywhere; a
forker-only member is none.

The folder is editable: it stays when empty, and is drawn unasked
where N has a fork partner either way ('add_default_folders'); a
request for it is '(folder forks)' ('FolderRelation::Forks'). A
forker N hides is not drawn in it: it stands in the folder of what N
hides outside its fork partners, which the forks folder holds last.

**** What each member shows
The birth facts follow the sides on which the member stands
(=forks_folder_member_sides= in =server/refresh/viewnodestats.rs=):
=(forks in 2)= where it claims (where the folder reads no claims,
where the graph says N forks it), =(forks out 2)= where the graph's
warrant and a visible record say it forks N; a mutual carries both,
a detached forkee neither. Its relRepo fact is N's record of the fork
where it claims, else its own record of forking N. A relRepo request
on a member claiming nothing is refused at validation
(=is_forks_folder_member_claiming_nothing= in
=server/from_text/buffer_to_viewnodes/validate_tree.rs=): its record
is in its own file.

**** What a save reads there
The save's traversal (=visit_forks_folder= in
=server/from_text/local_fieldintent_collection/traverse.rs=) reads
the folder's claiming members as N's 'forks', and visits a claiming
member as a forkee as such and one claiming nothing as a member of a
write-protected folder. It also emits a signal,
=FieldIntent::ForksFolderMembers=, listing every vognode the folder
shows, claiming or not, but those marked for deletion. Visibility
resolution then hides in N each note that forks N by a visible
record, that the folder no longer shows, that N does not fork after
the save, and that N does not hide already
(=resolve_forks_folder_removals= in =resolve_visibility.rs=), before
the edits of the hidden-outside folder, which run last. So:
- typing a member there, claiming, makes N fork it;
- deleting a forkee ends N's fork of it;
- deleting a forker-only member hides it in N, and it leaves the
  forks folder for the hidden-outside folder; removing it there
  unhides it, and it is drawn in the forks folder again;
- deleting a mutual ends N's fork of it and hides it;
- detaching a mutual ends N's fork of it only: it stands as a
  forker, claiming nothing;
- attaching a forker-only member makes N fork it: a mutual.
The hidden-outside folder's membership reads N's forkees' content
only; plan 2 ('TODO/every-mirror/2_plan.org', decision 8) makes N's
hides apply to what it shows of its forkers too, and that folder's
membership with them.

*** The extent and the node budget
The *extent* is how much of P's goal the refresh draws
(=server/refresh/extent.rs=): all of it for a folder and for an
editable occurrence's content, and in the diff view for a ghost's old
content where content stands; none of it, beyond what the buffer
already shows, for a write-protected occurrence's content and for the
containerward chain. An occurrence the refresh draws where its
parent's children are editable content is drawn write-protected,
carrying an editable-view request; so is a write-protected child that
claims membership under an occurrence carrying one: the request
passes on to the content it extends, showing or drawing. At the
occurrence's own visit the request is consumed: the occurrence
becomes editable when no other occurrence of its node is and the
budget allows, and stays write-protected otherwise; the request goes
when the visit ends. Each editable occurrence whose content is drawn
charges the budget once, at its visit, whatever made it editable: the
budget need not count exactly, only stop an explosion. The walk keeps
nothing else of editability than where each node's one editable
occurrence stands. The diff view's deviations are in
=docs/diff-view.org=, "Editability in the diff view".

*** The tail
After the walk, once (=server/refresh/tail.rs=): the derived facts are
computed, the stats of each occurrence (its relationship facts,
property counts and birth, =cycle=, =repoBoundary=, =omittedBody=, its
relRepo where it differs from the default), and in the diff view the
'(processed ...)' change facts, from the processed store, and the home
skgrepo moves; every
childless tombstone is pruned, postorder and roots included, so a
buffer may end with no roots, and so is a folder the pruning leaves
empty that goes when empty; an editable folder stays even when
empty, since the user can add to it, so one whose every member's
record the skgrepo restriction keeps out stays, empty, and fills again
after a skgrepo widening; every
viewnode that lacks a viewnode ID gets one. The refresh renders
nothing: each caller renders the viewforest once, when it is done
with it (=viewforest_to_string=), the search after it has folded
what it drew and excluded the overPrivateText nodes.

*** The refresh reports nothing
The refresh changes a view and says nothing of it: no response
carries what it changed, and neither client shows it
('docs/glossary.org', "what the refresh changes silently"). It does
not warn either; the warnings a save or a rerender sends are the
save's and the rerender's own.
