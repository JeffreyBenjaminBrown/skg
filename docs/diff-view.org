#+title: The diff view
* What it is
The diff view shows every change in the owned skgrepos since their
last commits -- how each worktree differs from HEAD -- with the
context needed to understand each change, in buffers that are
ordinary editable views. It lets the user review the changes, mark
each one processed, and commit what is processed (C-c r c) or
everything (C-c r C). C-c v d
('skg-diffView-open'; Neovim '<localleader>vd') opens it.

The vocabulary (graph straddle, the three kinds of change, C, R, U,
D, change-forest leaf, mark, changeset marker, ...) is the
glossary's "Terms a user meets in the diff view" and "Terms of the
diff view's implementation" ('docs/glossary.org'); the refresh's
words (the ID rule, goal, warrant, the refresh's rungs, extent) are among its
"Terms of the implementation", and ghost, tombstone and claims
membership among its "Terms a user meets". A buffer of the diff view
is drawn by the refresh every view uses, whose model is
'docs/data-model_technical.org', "The refresh: how a view follows the
graph"; this document says what its diff-view mode adds. The wire forms are the
API doc's "Diff view", "Stage and commit", "Extend diff view" and
"Metadata of the diff view" ('docs/api-and-formats.org'). The
heralds are 'docs/heralds.org', "Diff heralds". The commands are
both COMMANDS files, under C-c v d and C-c r, and the two restore
requests under C-c s. The server's code is
'server/diff_view/' (its 'mod.rs' lists the files), over the graph
straddle of 'server/graph_straddle/'.

* The four buffers
One command opens up to four buffers, in this order, and skips any
that would be empty. The client sends one "diff view" request per
buffer; the server answers each with a buffer, or with '(empty . t)',
which the client does not open. Each buffer is registered like any
view, under a client-generated view ID, with its buffer kind
('DiffViewBufferKind'), so saves and collateral rerenders reach it.
** "diff-view: all changes"
The pruned change view over all of C.
** "diff-view: merges"
A pruned change view over the nodeMerges since HEAD: its C is each acquiree (a
node only the before-graph has, which an after-graph node lists as an
extra ID) and its acquirer. The acquiree's text preserver is not in
C; it shows as a new member of the acquirer's content.
** "diff-view: skgrepo changes"
A pruned change view over the skgrepo moves
('prunedChangeView_sets_for_skgrepo_changes'):
its C is the recorders of the change-forest leaves whose aspect is
the home skgrepo or the relRepo, that is, the nodes whose home skgrepo
moved and the recorders of the relationships whose relRepo moved. A
node of that C is shown as in any buffer, with all of its changes.
The processed summary counts the whole changeset whatever buffer is open;
only the count of changes not editable in the buffer depends on what
this buffer shows. In this buffer each
moved vognode's own heralds also read "-OLD +NEW", and "Δ⌂=a" when
the nearest moved vognode ancestor (a, the viewparent; b, the
grandparent; ...) moved the same way ('set_homeSkgrepoMove_facts_in_viewforest').
** "diff-view: order-only changes"
A flat list, in ID order, of the nodes whose file changed but which
record no change-forest leaf: only the order of some list changed.
Each is shown with its content in the new order, as write-protected
members shown without their content, and with an order-only changeset
marker, which is always processed. Its sets are empty: it renders no pruned change view.
** Refusals
Every buffer is refused, and the client stops, unless the
connection is unrestricted, and when the graph straddle cannot be built: an
owned skgrepo that is not in a gitrepo or has no HEAD commit, or a
HEAD that fails the whole-graph validation. A merge commit at HEAD is
no reason to refuse.
** Foreign skgrepos
Foreign skgrepos are read at their worktrees in both halves of the
straddle, so they never produce a change: they are outside C, the
change-forest and the processed marks. The processed summary only counts their
changed nodes, by the stems of their changed '.skg' files.
** No stages
The diff view compares HEAD with the worktree. The git index never
enters it: no fact carries a stage, and a commit is built from HEAD's
tree and the worktree, not from the git index ("Stage and commit").

* The graph straddle
The graph straddle ('GraphStraddle', 'server/graph_straddle/') holds
the before-graph (each owned skgrepo read at HEAD, each foreign one at
its worktree) and the after-graph (the live graph), and answers
questions about their union (the "union walk"): each node and each
relationship it reports carries its existence across the straddle
('existence_across_straddle'): 'Existence::Added' when only the
after-graph holds it, 'Existence::Removed' when only the before-graph
does, none when both do. A partner of a node in some role is an
entry of the union of the two graphs' lists, with its existence and
its relRepo in each graph; it changed when the relationship is in one graph only, or
its relRepo differs.

Each connection keeps one straddle. A diff-view request, a save, a
rerender and stage-and-commit bring it up to date: it is rebuilt when
an owned skgrepo's HEAD moved (as a git-commit does), re-paired with
the live graph when that changed, and otherwise reused. The before-graph
is read through a cache keyed by the owned skgrepos' HEAD commits.
Closing the last buffer of the diff view drops the straddle, and so
does a rebuild of the session-lifetime stores, so the next request
reads both halves from the disk the rebuilt live graph was read from.
What the straddle computes from itself -- C, the change-forest, each
buffer's sets -- is computed once per straddle, on first use.

* C, R, U and D
These sets define the pruned change view a buffer renders
('PrunedChangeViewSets').
** C
C is the set of changed graphnodes, read off the change-forest leaves
(see "Change-forest leaves"). It has two halves:
- out-changed: the recorders of leaves, the nodes whose own files
  record a change -- a new or deleted node, a changed title or body,
  alias, extra ID, flag or home skgrepo, an added or removed member of
  its contains, subscribesTo, overrides or hidesFromSubs list, or a
  moved relRepo of one;
- in-changed: the nodes whose set of containers, mentioners,
  subscribers, overriders or hiders changed: every member of a
  relationship leaf whose relationship exists in one graph only, and
  every node a recorder mentions in one graph only (a mention is no
  leaf: it changes with its mentioner's text, the mentioner's leaf),
  when that node exists in either graph.
A relRepo move puts only the recorder in C. A change of order alone
puts nothing in C.
** R and U
From each node of C the containerward walk climbs through the union
of the two graphs, following single containers, until it reaches a
content origin: a node with no container or with several, or the
members of a rootlike cycle. R is the content origins reached. U, the
nodes to extend contentward, is C, R and every node on those walks.
** D
D, the buffer's first roots, is R deduplicated: R is processed in ID
order, and a content origin is discarded when its containerward walk
within U reaches another content origin still kept. Of two origins on
a shared cycle, exactly one is kept. When D is recomputed for a buffer
that already stands (see "Extending the diff view"), the buffer's
standing roots are pinned as kept first, so a change to a cycle's
membership never adds a second root for it.

* Rendering a buffer
** Stub roots
The buffer starts as one stub per root, in D's order: an editable
occurrence, its body folded unless its node is in C (it is
context), or, when the after-graph lacks the node, its ghost. In a
pruned change view, a root with several containers gets a folded
container folder, which the refresh fills with its containers in
either graph and their containerward chains
('stub_viewforest_of_roots' in 'server/diff_view/buffer_rerender.rs').
** The refresh over the straddle
A buffer of the diff view is drawn, and redrawn after every save,
rerender and commit, by the one refresh every view uses
('refresh_viewforest', 'server/refresh/'), in diff-view mode: the
mode is 'RefreshMode::DiffView', which carries the straddle, the
buffer kind and the processed store, from which the refresh reads
the marks ('server/refresh/mode.rs')
('refresh_diffView_viewforest' and
'refresh_diffView_buffer_over_current_straddle' in
'server/diff_view/buffer_rerender.rs').
The diff-view mode ('server/refresh/diff_view.rs') changes the
refresh so:
- a parent's goal is the union of its lists in the two graphs
  ('GraphStraddle::partners', in the order of their interleaved
  diff), so an item only HEAD's list holds is drawn too, warranted
  by HEAD ('Warrant::ByHead', written 'ghostWarrant');
- the ID rule asks, after the truth, whether HEAD has the node: an
  occurrence whose node the worktree lacks becomes its ghost where
  it stands, and a ghost becomes an occurrence again, in place,
  when its node is back;
- a ghost where content stands holds its old content, its content
  at HEAD, drawn as any content is;
- the change viewnodes of each editable occurrence are recomputed in
  place (below), and each child is tagged with its change;
- content is shown without override substitution: the view shows
  raw graph facts;
- no default folder is drawn; a folder appears where something
  changed, or where the buffer holds one;
- what may be editable, and what the node budget may refuse, the
  buffer's sets decide ("Editability in the diff view");
- in the tail, the '(processed ...)' change facts are set from the
  store, and in the skgrepo-changes buffer the home skgrepo moves.
The diff view opens only on an unrestricted connection, but a
switch of the skgrepo restriction rerenders its open buffers under
the new skgrepo restriction, and the refresh asks it there as in a
content view. The goal omits a member whose record is restricted. It
keeps a member whose record is visible and whose node is restricted
(the worktree's node, or HEAD's when the worktree has none). That
member stands as a restricted viewnode, carrying only its
relationship's change fact ('(rel ...)', herald =~+= or =~-=), never
a node's ('∃+', '∃-'), and none of the change viewnodes that would
show its text ('tag_children' in 'server/refresh/diff_view.rs'). A
restricted node is never a ghost.
** Change viewnodes and tags
At each editable occurrence of a node in C, the refresh holds, ahead
of its content, what 'model_of_front_change_viewnodes'
('server/diff_view/changes.rs') says: its old text, its home skgrepo
move, its "it acquired" folder, its alias, ID and flags folders whose
list changed; then its partner folders whose membership changed;
then its changeset markers; and in the order-only buffer, its
order-only changeset marker. Each is kept while its change exists, drawn when
missing (after the one before it, or first), and entombstoned when
its change is gone; the tombstone holds whatever stood under it. A
write-protected occurrence holds none: an earlier one's change
viewnodes are entombstoned.

What a node in C shows, the refresh reads from the leaves that
mention the node (those it records and the relationship leaves naming
it as member), grouped by aspect ('ChangedAspects'); the graphs supply
only what each viewnode shows, such as the old title. A new aspect of
a leaf is added in one place, and C, the extension and the processed marks
follow. The mentioner folder alone reads the nodes whose set of
mentioners changed, since a mention is no leaf.

Each child is tagged with its change ('tag_children'): an occurrence
with its node's existence ('(node added)', '(node removed)'), its
node's other properties ('(properties changed)') and its
relationship's existence ('(rel added)', '(rel removed)'), the last
from the goal item it is; a ghost with its node's removal and its
relationship's; an unknown viewnode, a restricted viewnode or a
property member with its relationship's. A root, and an occurrence the goal does not name, are
tagged as a node only; a node of the containerward chain carries no
change. Under a member whose relationship moved to another skgrepo
stands its relRepo move, first.

A node was added when only the after-graph has it, and removed when
only the before-graph does ('GraphStraddle::node_existence'); its
other properties changed ("modified", herald M) when both graphs have
it and it records at least one leaf
('GraphStraddle::node_properties_changed') that neither its own 'rel'
nor a headline under it shows: the tail of the refresh clears '(properties changed)' where
the object 'node' names no leaf ("Change facts on the wire"), so
that M stands for what a mark of 'node' marks there. A node whose
only changes are its relationships to the members drawn under it
shows no M where it stands with them; its changeset markers and
members show those changes. A ghost never carries
'(properties changed)'.
** What each kind of change looks like
Every label is a herald rule on a metadata atom; 'docs/heralds.org'
lists them, and the API doc's "Metadata of the diff view" the atoms.
*** text
A changed title or body adds an old text under the node, a change
viewnode labelled "old title and body", "old title" or "old body"
(its headline the old title, its body the old body), with a "body
diff" change viewnode under it holding the line diff when the body
changed. The text change is one
leaf, marked on the old-text headline.
*** content
Content has no folder. The members are the node's children, each
tagged ∃+ / ∃- for its node's existence, M for its other properties
and ~+ / ~- for its relationship's existence; a removed member stands
where the interleaved diff of the two lists puts it (below). The
content changeset marker, "its content changed", gathers the
relationship leaves of the content list.
*** the in-folders and out-folders
A changed set of containers, mentioners, subscribers, overriders or
hiders adds a write-protected folder labelled "its other containers changed
(other files)" and so on; a changed set of subscribees, overridden or
hidden nodes adds the existing folder labelled "its subscribees
changed (this file)" and so on. A containers folder is drawn only
when a container not above the node in the view gained or lost it,
and, as in every view, leaves out the node's view-ancestors: the
node's headline under its parent already carries that containment
change ('changed_partner_folder_kinds' in
'server/diff_view/changes.rs'). A folder holds the partners in either
graph, each tagged as a content member is: its node's existence and
other properties, so a modified member shows ☮ M, and 'node' with
'rel' there marks its file, and the existence of its relationship to
the folder's viewparent, of the folder's kind. The two compound partner
folders ("It contains these, but the subscribing ancestor hides them" and
"The subscriber ancestor hides these, but subscribes to nothing that
contains them") show no change and carry no '(rel ...)'. Under each
member of a changed folder hangs its containerward chain, as in every
view, so that the user sees where the member sits: the member's
containers as write-protected occurrences, theirs under them, up to
the roots or to 'max_roleTree_depth', walked over the union of the
two graphs ('ContainerwardChainPartners::GraphStraddle'). The refresh
draws a chain under a member it draws, and never reinstates a chain
node. A ghost member holds no chain. A chain node
carries no change facts and takes no processed marker; only
the folder's members show change. Before the chain, where the
member's relationship moved to another skgrepo, hangs that move.
*** aliases, IDs and flags
The alias, ID and flags folders, drawn when their list changed,
hold the union of the two lists in the order of their interleaved
diff, each member tagged '(rel added)' (+) or '(rel removed)' (-),
its existence in the list. A removed alias or ID is an alias or ID
member with a ghost warrant ('Warrant::ByHead', written
'ghostWarrant'), claiming nothing ('noClaim'), so the save never
reads it. Each is one leaf.

A property folder is matched by its kind among all the children of
its node, so a folder the user requested becomes the changed one
when its list changes. It stays until the user deletes it, filled
from its goal, the union of the two lists: its members tagged while
the lists differ, and untagged after. A member a commit made lost
for good stays, unwarranted and claiming nothing.
*** home skgrepo and relRepo moves
A home skgrepo move is one change viewnode under the node, "⌂ -OLD
+NEW", one leaf. A relRepo move is a change viewnode under the member
whose relationship moved, "relationship moved from X to Y", one leaf
keyed by the relationship, so the same move seen from either end is the
same mark. The relRepo changeset marker, "some content relationships
changed skgrepo", sits under the recorder when a content relationship
moved. Mentions have no relRepo.
*** deleted and new nodes
A deleted node is shown as its ghost, written 'ghost (gnid ID)
(skgRepos (nodeRepo REPO)) ...': write-protected,
with HEAD's title and body, under each former container. Its old
content stands beneath it, recursing into deleted members. Its
existence is one leaf. An acquiree's ghost holds a derived,
save-inert folder "it was acquired by" with its acquirer, and the
acquirer holds "it acquired" with the ghosts of its acquirees. A new
node is an ordinary editable node with ∃+; its existence is one leaf.

A ghost claims membership only where its parent's worktree list
still names its gnid (a dangling reference to a node HEAD has): it
carries no 'noClaim' there, and the save keeps its gnid in the list
as it keeps an unknown viewnode's ('traverse.rs'). Anywhere else under an
editable parent it claims nothing ('noClaim'), and contributes
nothing to the save.
** What the refresh keeps
Nothing that exists is drawn again: the refresh decides everything
from the buffer and the truth as they are now ('server/refresh/mod.rs'),
and every buffer it draws refreshes to itself
('every_diff_view_fixture_is_a_fixpoint_of_the_refresh' in
'tests/idempotence.rs'). A child keeps its vnid, its fold state and
its place; it is re-kinded where it stands, by the ID rule (a member
whose node was deleted becomes its ghost and back); siblings standing
for one gnid are joined by a viewnode merge, so a copy the user pasted
beside a member is joined to it. A child the goal does not name
vanishes, with its subtree, where it claims under an editable
parent; one that claims nothing, or stands where no claim is read,
is kept, unwarranted. A member whose node was deleted is never
removed: it stays as its ghost. A tombstone keeps its children, and is pruned when it holds
nothing; so is a folder the prune leaves empty. The server sets a fold
state only on a viewnode it draws (a context node's body and a
container folder start folded, the rest open).

A root stays until the buffer is closed, whatever becomes of the
changes under it. A ghost is a pending change: it is shown until it
is restored or its deletion is committed. A commit is an ordinary
rerender: the roots
stand as plain context with their change viewnodes entombstoned; a
ghost root whose node the commit deleted, now in neither graph,
becomes a tombstone, which keeps what stood under it, and one whose
gnid the commit left an extra ID of its acquirer becomes an
occurrence of the acquirer, in place.

The goal orders what it warrants where the graph records an order
(content, aliases, the subscribee, overridden and hidden folders);
every other child stays right after the sibling it followed. So a
buffer saves back to itself, and a view other than the one saved
follows a reorder saved elsewhere.
** Removed members
A removed member is a member of the before-graph's list that the
after-graph's lacks: an occurrence whose relationship to its
viewparent HEAD alone has, warranted by HEAD ('ghostWarrant'),
claiming nothing ('noClaim') where claims are read, with the change
fact '(rel removed)'. That is the one encoding of a removed
relationship, wherever it stands: in content, in a partner folder, in
a ghost's old content, and as a node of the containerward chain whose
container relationship only HEAD had. Membership is decided by set
difference, so a reorder shows nothing; the goal's order, the
interleaved diff of the two lists, places it: before the next
surviving member of the old order, or last
('interleaved_diff_without_reorders'). The partner folders place
their removed members the same way; recorders, which no list orders,
come sorted by ID.

A removed dangling ID is not shown in a folder whose membership the
save reads, nor in content when neither graph has the node: its leaf
in content is under the content changeset marker. Elsewhere it is an
unknown viewnode, with '(rel removed)'.

The restore requests read where it stands: 'restoreRel' is accepted
on an occurrence with a ghost warrant in content position or in a
partner folder ('restoreRel_stands_where_it_may'), and a save that
fulfils one leaves the headline claiming the relationship it
restored.

* Editability in the diff view
The diff view follows the rule that decides which occurrence is
editable in any view -- one editable occurrence per node, the first
the refresh draws where its parent is editable content, the
editable-view request and the node budget, described in the module
comment of 'server/refresh/editability.rs' -- with these deviations.
** A node of U is editable, with its whole content list
An occurrence the refresh draws in editable content is editable when
its node is in U and has no editable occurrence yet, and its whole
content list is drawn; a member outside U is a write-protected member
shown without its content. No size cap applies: the node budget never
refuses a node of U, though each one's extension charges it, as every
extension does. A removed member in content position is
an occurrence like any other here: a node whose first drawn
occurrence is a removed member (one its only container dropped, say,
or one first reached through a container that dropped it) is
editable there ("Removed members"). An occurrence the buffer holds
keeps its editability.
** The budget bounds only requests outside U
An editable-view request (C-c s e) behaves as in any view: it makes
its occurrence the editable one, write-protecting the other (whose
content keeps its own editability), and passes on to its content:
each member it shows or draws whose node has no editable occurrence
is editable while the budget allows, and passes it on in turn. Every
extension charges 'initial_node_limit', the nodes of U included, but
the budget refuses only a node outside U that a request reached: a
node of U is editable whether the rule above or a request reached
it. Charging U overcounts, which the budget can afford: it exists to
stop an explosion, not to count. A request adds no default folders,
since the diff view draws none.
** A save makes nothing editable and appends no root
After a save, a buffer's sets are recomputed, and the refresh extends
by the recomputed U wherever it draws something new. Nothing the buffer
holds editable is write-protected again by the server. But the server
makes no occurrence editable and appends no root on its own: a change
recorded by a node the buffer holds no editable occurrence of is not
editable in this view, and the processed summary counts it, until the
buffer is extended (below).
** Extending the diff view
C-c r u ('skg-diffView-extend'; Neovim '<localleader>ru',
':SkgDiffViewExtend'), on a buffer with no unsaved changes, sends
"extend diff view", which extends the buffer to the changes it does
not show. The server brings the straddle up to
date and recomputes the buffer's sets. Every node of U without an
editable occurrence becomes editable at its first content occurrence
in level order, its children claiming as a buffer read back would
('ensure_editableOccurrences_exist'); a node shown only as a
write-protected folder member counts as shown nowhere, since the
extension makes no folder member editable. A folder member the user
made editable with an editable-view request (C-c s e) is an editable
occurrence, and its node counts as shown there.
The walk for content occurrences counts a removed member under an
occurrence or a ghost as a content occurrence, and passes through a
ghost in content position into its old content.
Each content origin of D that the buffer makes editable nowhere is
then appended as a stub root, in ID order, with the standing roots
pinned, and the buffer is refreshed once, as after a save, which
gives each node made editable its body and draws its content list
and the content of each appended root
('refresh_diffView_buffer_over_current_straddle').
The answer
is the processed summary, and the rerender stream carries the buffer.
It does not matter who write-protected an occurrence: the user asked
for every change.
*** After a reload
When the server reloads '.skg' files that changed on disk (another
writer's save, a 'git pull'), its "repo-files-reloaded" message names
every open buffer of the diff view, and the client asks for the
rerender of each that holds no unsaved edits. That rerender extends
the buffer as C-c r u would, so a change made elsewhere appears in it
even where the buffer did not show its node. The server marks each
buffer the message names ('ViewState::extend_at_next_rerender_all')
and the next "rerender all views" that includes the buffer extends it
and clears the mark; any other rerender is a refresh alone. A buffer
with unsaved edits is not rerendered, so it keeps its edits and is not
extended; its save is refused if it would write a node the reload
changed (COMMANDS.org, "Save buffer"). Under a skgrepo restriction,
where C-c r u is refused, no buffer is marked.
** What counts as editable here
A buffer makes a node's changes editable when it holds an editable
occurrence of the node, wherever that sits, or the node's ghost in
content position (under the buffer root, an occurrence, or a ghost
that is itself in content position),
since a deleted node's old content is editable nowhere and shown
there ('nodes_editable_in_diffView'). The change-forest leaves those
nodes record are the changes editable in the buffer.

* Processed marks
** Change-forest leaves
The change-forest ('ChangeLeaves', built from the straddle,
independent of any view) holds every change a user can mark: its
leaves. A leaf's key is a node and an aspect of it (existence, text,
home skgrepo, an alias, an extra ID, a flag), or a relationship (a
relation, its recorder, its member) and an aspect of it (existence,
relRepo). The recorder of a leaf is the node whose file records it; a
relationship's leaf lives under its recorder, and seen from either
end it is the same leaf. A node's existence leaf covers its own
content when it is new or deleted.

The builder compares only the nodes that one graph lacks or holds
unequal, and the nodes that list a member whose ID the two graphs
resolve to different nodes: after a nodeMerge since HEAD, a container
that still lists the acquiree's ID is equal in both graphs, yet the
after-graph resolves that ID to the acquirer. Such IDs are among the
extra-ID differences of the unequal nodes. No other node can record a
change, so neither the leaves nor C cost a comparison of every node.
** Marks, fingerprints and the store
A mark says that one leaf is processed. The processed store
('server/diff_view/processed_store.rs') keeps each mark with the fingerprint of
the change it approved, a hash of the leaf's before and after values.
A mark whose fingerprint no longer matches the change counts as
absent: editing a marked change unmarks it, and nothing signals that
an earlier version was approved. The store lives on the server, is
written to its file after every change, and is read at startup; a
missing or unreadable file is an empty store. The file is the
config's 'processed_marks_file', or else
'<data_root>/processed-marks-STEM.json', STEM the config file's name
without '.toml' (a symlink to a config resolved first), so that
servers over one data root keep their marks apart
('SkgConfig::processed_marks_path').
The file serializes the leaf keys, aspect names included, so their
spelling is kept stable. After a git-commit, the store keeps exactly
the marks whose leaves still exist in the rebuilt straddle.
** Processed aggregates
A processed aggregate -- a folder, a changeset marker, a node,
or the whole changeset -- is processed when every leaf under it
that can be processed is processed. An unchanged membership has no leaf and is
never asked. The content changeset marker gathers the
content relationship leaves of its node; a member's existence leaf
belongs to the member itself. A node is processed when every leaf it
records is: its own aspects and the relationships it records
('ChangeLeaves::node_is_processed'). A node whose only change is order
records no leaf and is processed. A headline's ✓ after ∃ or M says that
the leaves 'node' names there are marked, and after ~ that the one
'rel' names is ("What a request names").
** Change facts on the wire
A headline's change facts form one form, '(diff (node added|removed)
(rel added|removed) (properties changed) (leaves N OBJECT...) (processed
OBJECT...))', and in the skgrepo-changes buffer its home skgrepo move
after them, each part present only when it has something to say, the
first three only when true ('diff_form' in 'server/org_to_text.rs';
the grammar is in 'docs/api-and-formats.org', "Metadata of the diff
view"). Like every part of a headline it stands at the top level of
the metadata, last; the parser skips it whole. A folder carries none:
each client computes a changed folder's label and whether it is processed from its
members ("changed folder" in 'docs/glossary.org'). A processed
request is no change fact; it rides in the headline's '(editRequest
...)' (below).

The part '(processed OBJECT...)' is a derived fact the server sets in the
tail of the refresh ('set_processed_facts_in_viewforest'): the objects
of '(leaves ...)' whose leaves are all marked; a bare '(processed)' on
a headline that names one leaf, which lists no object, and on the
order-only changeset marker, which names none. Nothing reads it at
save.

Before it, a headline that names leaves
carries the part '(leaves N OBJECT...)': N is the number of distinct
leaves a request naming every listed object would touch, and the
OBJECTs are those of 'node' and 'rel' that name some leaf there, 'rel'
alone on a changeset marker; none on a headline that names exactly
one leaf, which a bare request marks. The same tail clears '(properties
changed)' where 'node' names no leaf.
The server's 'leaves_named_at' is the single rule; the change fact
is display-only, and the clients read it instead of keeping tables of
headline kinds.

** What a request names
A mark marks what its headline shows. A headline shows two things
that can change: its node, whose glyph is ∃ or M, and its
relationship to its viewparent, whose glyph is ~. 'node' names the
first and 'rel' the second ('leaves_named_at' in
'server/diff_view/processed_requests.rs'). So 'rel' names the
existence of the relationship by which the headline stands where it
does, and 'node' names every leaf its node records but the
relationships shown on it or under it: its own 'rel', that of each
member drawn under it, in its content or a partner folder, whatever
the aspect (a relRepo move hangs under the member), and the content
relationships a changeset marker under it gathers. On a new or
deleted node that is its existence; on a modified node, its text,
home skgrepo, aliases, extra IDs and flags, and any relationship it
records that no headline under it shows. Where the node stands with
its members, as at its editable occurrence, 'node' leaves their
containment to each member's 'rel'; where it stands alone, as in a
folder, 'node' and 'rel' together name its whole file. Every leaf is
thus named by some headline without a walk; a reordering is no leaf.

A changeset marker gathers relationships: 'rel' names them, and
'node' the own leaves (existence, text, home skgrepo, aliases, extra
IDs, flags) of their members, one level down: the content members
drawn beside it. Its '(leaves ...)' lists only 'rel', what its label
describes; the members show their own leaves under their own glyphs,
so a client cannot count from it how many leaves 'node' there names. A request with no object names what
'(leaves ...)' can list there: 'node' and 'rel' on a vognode, 'rel'
on a changeset marker or an unknown viewnode, the one leaf elsewhere.

The walks, 'newContent' and 'newOutward', name leaves of the new
nodes reached from the headline's node, and the letters beside a walk
filter them: 'node' each new node's existence, 'rel' the
relationships it records that the walk follows, neither both. Each
letter also names its own object on the headline, which the walk
never reaches: '(processed rel newContent)' marks the headline's
relationship to its viewparent and the content relationships of the
new nodes reached. There is no object 'all'; the parser refuses it.

** Processed requests and gestures
A gesture writes processed requests, '(processed OBJECTS)' or '(unprocessed
OBJECTS)', into a headline's '(editRequest ...)' (creating the form if
the headline lacks one) and saves; the save
consumes them after its graph edits succeed (not when it stops for a
confirmation), in any buffer, marking or unmarking the leaves each
headline names at their current fingerprints. A request naming no
current change is dropped with a warning. Validation refuses a save
in which two headlines name one leaf, one processed and the other
unprocessed, naming the leaf and both headlines
('find_contradictory_processed_requests'); requests that agree are
consumed as usual.

A gesture says what it marks and which way: C-c m, then 'n' (the
node), 'r' (its relationship to its viewparent) or 'b' (both), then
'p' (processed) or 'u' (unprocessed); 'skg-mark-node-processed' and
its five siblings ('elisp/skg-processed.el'). On the headline at point
it names the letter's objects among those its '(leaves ...)' lists,
and refuses when that is none. A headline that names one leaf, which
lists no object, gets the bare request from the letter of the leaf's
kind: 'r' for a relRepo move and an unknown or restricted viewnode
(which shows no node, only its relationship), 'n' for an alias, extra
ID, flag, old text or home skgrepo move; 'b' for either. On a changeset marker at
point the letters go as they are, 'n' naming its members' own leaves
(above, "What a request names"). On a changed folder the gesture acts
on its children, one level down, each as above.

With a prefix argument it acts on every headline of the subtree that
names some of the letter's objects, a changeset marker below the
headline at point naming only what it lists, since its members name
their own leaves under their own headlines. At a new node (=(node
added)=) in content position (not in a folder), and at the headline
at point when it is a new node wherever it stands, it names the
letters and =newContent= (with two prefix
arguments, =newOutward=) and skips the rest of the node's subtree: the
server then walks the graph from it through new nodes only, shown or
not, write-protected or not, contentward or along every relationship
each records, the letters naming the node's own objects and filtering
what the walk marks. The letters go there whole, even where the
headline lists fewer, since a walk without a letter names every kind.

C-c m h p and C-c m h u ('skg-mark-homeSkgrepo-move-processed',
'-unprocessed') act on the home skgrepo move of the node at point, and
with a prefix argument on every descendant whose home skgrepo moved
between the same two skgrepos. Every gesture works on write-protected
occurrences. A gesture that would unmark more than one leaf first
asks for a typed "yes". It counts as the server does where it can: N
of '(leaves N ...)' for every listed object, one for 'rel' alone, N
less one for 'node' alone; an object the headline does not list (a
walk, 'node' on a changeset marker) counts two, so that unmarking it
always asks, since the client cannot count what the server will
reach.

Six commands move point between headlines with change facts, the
headlines whose metadata carries a '(leaves ...)' change fact: C-c r n c
('skg-diffView-goto-next-change') to the next, C-c r n u to the next
unprocessed one and C-c r n p to the next processed one, and C-c r p c, C-c r
p u and C-c r p p to the previous ones. A headline with change facts is processed
when its '(processed ...)' names every object its '(leaves ...)' lists.
They do not wrap: at the end they say "No further change" (or "No
earlier change", with "unprocessed" or "processed" for the filtered forms).
They skip a write-protected occurrence (☮; a ghost is not skipped)
standing directly in a folder whose changed label says "(other
files)", the folders 'folder_heralds.other_files' in
'shared/herald-styles.json' lists: its other containers, mentioners,
subscribers, overriders and hiders. Each such member records its
relationship to the folder's viewparent in its own file, so every
change it carries is a leaf it records, and in a buffer extended to
every change its node has an editable occurrence, where the refresh
draws every leaf the node records: its node changes on its headline
or under it, its relationships among its content or in a folder of
its own file. A ghost is visited because a deleted node's ghost
draws no partner folders: a deleted subscriber's subscription stands
only on its ghost in the subscribers folder. A member made editable
inside such a folder (C-c s e) is not skipped, nor is anything under
it, since its changes are then drawn there. So in a buffer extended
to every change, the plain motions reach each change. Under a skipped
member they still visit its relRepo move, a change of the member's
file seen from the other side. The same six keys with a capital last
letter (C-c r n C, ...) skip nothing. When a plain motion finds
nothing but its capital would, it says so and names the capital's key.
** The processed summary
The answer to each "diff view" request for a nonempty buffer, to each
save of a buffer of the diff view, and to C-c r u carries the
processed summary, as does the answer to a commit of everything that
asks first. When a buffer of the diff view opens, after every save of
one, after C-c r u, and before such a commit, the client shows it.
It counts nodes, the unit a commit takes ("Stage and commit"): the
changed nodes, those processed, those of them that changed only in
order (processed, since they record no leaf), and the processed nodes
a commit of the processed would hold back ('waiting'), by the rule
that commit applies ("Which nodes go in"). A node with sections in
two skgrepos counts once. It is computed over the whole
change-forest, whatever buffer is open. It adds the changed nodes of
the foreign skgrepos (the stems of their changed '.skg' files, each
once), and the changes not editable in this view: the leaves whose
recorder the buffer does not make editable (see "What counts as
editable here"), with the command that extends the buffer to them.
The diff view's answer, a save and C-c r u compute it alike
('buffer_processed_summary_for', 'server/diff_view/processed_requests.rs',
over 'buffer_processed_summary', 'server/diff_view/change_leaves.rs').
The waiting count costs no Git and no check: it is the commit's rule
over the straddle the save already has.

* Restoring what a change removed
Two edit requests undo a removal from the diff view's buffers, without
leaving them. Each is written by a command that refuses at once on the
wrong kind of headline, and does not save; the parser refuses each
there too. They are carried, applied and consumed like every edit
request: the save collects them with its graph edits, and consumes them
after the skgsave-commit; a save that stops for a confirmation or fails
leaves them in the buffer.
** '(editRequest restoreNode)': a deleted node
C-c s n ('skg-restore-deleted-node'; Neovim '<localleader>sn',
':SkgRestoreDeletedNode') writes it into a ghost, the only
headline that accepts it (herald "restore node"). The save writes the
node's file from the before-graph's copy of it (title, body, aliases,
extra IDs, flags, home skgrepo, and its four relationship lists with
their relRepos), as it writes any node. An out-link to a node still
deleted is kept as HEAD recorded it, and shows as that node's ghost,
claiming membership, so a later save keeps it.
Then it re-adds the node's in-links, from the before-graph's inbound
indexes: each node that recorded it at HEAD (as content, a
subscription, an override or a hide) gains it in that list, at the
index it had at HEAD, clamped to the list's length, in the skgrepo
that recorded it, unless that recorder is itself deleted (it is
skipped) or lists it already. A recorder the save already writes, as
the buffer's editable occurrence of it, gains it there.
** '(editRequest restoreRel)': a removed membership
C-c s l ('skg-restore-removed-membership'; Neovim '<localleader>sl',
':SkgRestoreRemovedMembership') writes it into an occurrence
carrying '(rel removed)' that stands where it may: a removed member in
content position (a child claiming nothing under a vognode that is no
node of the containerward chain), or a member of a partner folder whose
relationship to the folder's viewparent was removed, editable or
write-protected (herald "restore membership"). The command and the
save both refuse it anywhere else, by where the headline stands, with
"Only a removed membership can be restored". On a ghost it refuses with "This
node is deleted; restore it first (skg-restore-deleted-node)". The save
re-adds the one relationship the headline stands for (the processed
requests' 'relationship_to_viewparent' names it), as HEAD recorded it:
at its index in the recorder's list at HEAD, clamped, in the skgrepo
that recorded it. A request whose headline stands for no relationship
(as under an acquisition folder), whose relationship is a link, has a
deleted node at either end, or is not recorded at HEAD, is dropped with
a warning naming the headline (=docs/api-and-formats.org=, "How a
message names a headline").
** Both in one save
The restored nodes come first, then the relationships, so a
relationship restored in a save may name a node restored in the same
save. A relationship that a restored node records is restored with its
file.
** The rerender
The save's rerender shows the result as any save's does: the
ghost of a restored node becomes the node again, and a
removed member whose relationship returned is warranted again,
claiming it. A change that no longer differs from HEAD leaves the
change view; what the buffer still holds of it is kept as "What the
refresh keeps" describes.

* Stage and commit
C-c r c ('skg-stage-and-commit') opens a buffer for the message, and
C-c C-c there sends "stage and commit". The request commits the
changed nodes of the owned skgrepos, never the foreign ones: with
'(processed-only . t)' the processed ones, less those that must wait,
and asking nothing; without it every changed node, by the same
commit, asking first when some is not processed. The rule a user
holds: "C-c r c commits every node whose changes are all processed,
except one that needs a node whose changes are not." C-c r c sends
'(processed-only . t)'; C-c r C (Neovim '<localleader>rC', the AI
reader's 'commit --all') sends the request without it. The decisions
behind it, and the alternatives rejected, are in Vic's plan "commit
only the processed nodes, each whole" (node
75da3bb2-881a-48cf-94bd-be487db9604c).
It refuses unless the connection is unrestricted, for a blank
message, and when the straddle cannot be built. It never stages
'OTHER_SKGREPO_DEPENDENCIES.toml', which the diff view does not
cover: committing that generated manifest is a deliberate, manual act.
** The unit is the node
A node goes in whole, all its changed files or none: its sections in
every owned skgrepo, so a home skgrepo move, a relRepo move and an
alias moved from one section to another never split. It is processed
when every leaf it records is ("Processed aggregates"); a child's '~'
is its container's.
The changed nodes are the straddle's: every node that records a leaf
in an owned skgrepo, and every order-only node
('ChangeLeaves::changed_nodes'). A foreign node that lists an ID a
merge re-resolved records a leaf, but in a foreign skgrepo, so it is
none: no commit takes it, and it holds nothing back. A container
whose file is unchanged but which lists a member a merge re-resolved
is one, with nothing to stage. Their files are found from Git, not
from the change-forest: every '.skg' path of an owned skgrepo whose
worktree blob differs from HEAD's (new and untracked, changed, or
gone), grouped by the
file's stem, its node's pid ('changed_skg_paths_by_stem',
'server/git_ops/stage_and_commit.rs'). A leaf's 'files' are not exact
enough to stage from: an alias leaf names the home file wherever the
alias is recorded. A stem Git lists that the straddle does not count
changed differs only in bytes the parser does not read; it goes in
with any commit, as a processed order-only node does, and is counted
in 'committed-nodes'. A stem that names no owned node of the graph
(a section of a foreign node in an owned skgrepo, which the graph
sets apart as an illegal edit) never goes in. A path is changed when its contents, as Git
would store them (through the gitrepo's filters, line endings among
them), differ from HEAD's. Only the '.skg' files directly in a
skgrepo's folder count, as only those are read into the graph; a file
the gitrepo ignores counts too, since the graph reads it.
** Which nodes go in
A processed node waits while it needs a node that does not go in, in
one of three ways, each named as the answer names it:
- 'names-new': its worktree names, in one of its four lists, a new node.
- 'still-named': it is deleted, and a node names it at HEAD, in one of
  its four lists, by an ID that node's worktree list lacks.
- 'merge': it is a part of a merge. The acquirer (a node whose extra
  IDs changed) and the acquiree (the node whose pid is such an ID)
  need each other: the acquirer alone would hold one ID as primary
  and extra, and the acquiree's deletion alone would leave the ID
  dangling. A node listing that ID resolves it through whichever is
  committed, so one listing it in both graphs and the two need each
  other; one listing it at HEAD only is needed by the two but needs
  nothing; one listing it in the worktree only needs the two
  ('merge_needs').
The rule is applied in rounds until a round holds nothing back
('hold_back_waiting_nodes', 'server/diff_view/change_leaves.rs'). So
a node needing a waiting node waits too, and every chain of waits
ends at a node that is not processed. Each waiting node names the
first by title of the nodes it needs that do not go in; for a merge,
of those that are not processed, if any is. A new node
whose container waits goes in uncontained, which is valid and is what
was marked. A waiting node keeps its marks: HEAD does not change for
it, so its leaves keep their fingerprints. Mentions hold nothing back:
a link is text.
A commit of everything chooses every changed node, so nothing waits.
** The check before anything is committed
The commits are prepared first, for every owned skgrepo: each one's
tree, and each gitrepo's configured author ('prepare_commits'). A
gitrepo with something to commit and no author refuses the whole
request, naming its skgrepo. Then the graph the commits would leave
is read as the straddle's before-graph is ('read_candidate_graph_snapshot',
each owned skgrepo from its gitrepo's last prepared tree, each foreign
one from its worktree), and must
- pass the whole-graph validation (two owned overriders of one target,
  or an override cycle, can fail here, since no waiting rule holds
  them back: the user marks or unmarks the other override);
- name, in the four lists, no node it lacks unless HEAD or the worktree
  names it so too;
- differ from the worktree by exactly the change-forest leaves of the
  changed nodes left out, keys and fingerprints both, among the leaves
  recorded in owned skgrepos.
A failure commits nothing and says why: "Nothing was committed: the
commit would not validate: ...", or, for either of the last two, that
either a '.skg' file changed on disk and the server has not reloaded
it yet, or this is a bug, since the waiting rule should have prevented
it; the server's log then has the sets compared
('check_candidate', 'server/serve/handlers/stage_and_commit.rs'). A
commit of everything passes the same check, expecting no leaf left.
** The commit
Each owned skgrepo with something to commit gets one git-commit, in
config order, with the message, by its gitrepo's configured user; in
a gitrepo shared by several, each commit's parent is the one before.
So a home skgrepo move between two skgrepos is one node in two
commits. A commit's tree is the tree before it with the skgrepo's
committed paths taken from the worktree (removed, for a deletion), not
the git index: what was staged by hand never goes in. After a commit,
each committed path's git index entry is set to the commit's (removed,
for a deletion), and every other entry is left as it was, so a file
staged by hand stays staged. Nothing in the worktree is written.
Before the first git-commit, every gitrepo's HEAD must still hold the
tree its commit was built on, or nothing is committed. A git failure
after that stops the rest; it is reported, 'committed-nodes' counts
only the nodes each of whose files went in, and the next diff view
shows what is left.
The save's mutation gate is held from the choice of nodes to the last
git-commit, so no save changes the worktree or the graph between them.
A mark rides on a save; the commit reads the marks once, under the
processed store's lock, when it chooses, so a mark lands wholly before
the choice or wholly after it.
** Its confirmation
Only a commit of everything asks. When some changed node is not
processed and the request lacks '(confirmed . t)', the answer is the
processed summary with '(needs-confirmation . t)', and nothing
changes; the client asks for the typed word "yes" and resends
confirmed. A commit of the processed ignores '(confirmed . t)'.
** After the commit
The straddle is rebuilt over the new HEAD, the store keeps only the
marks whose leaves still exist, and each open buffer of the diff view
is refreshed as any rerender is: its roots and what it made editable
stay, and what was committed loses its change viewnodes. The marks of
the nodes left out stay, since the check proved their leaves
unchanged.

* Strandeds
A relationship touching a node whose home skgrepo moves is stranded
when it sat at its default relRepo before the move and the sticky rule
would leave it off its new default. The save finds every stranded
relationship of every relation, in both directions, shown in some view
or not ('server/from_text/strandeds.rs'); only a relationship recorded
in an owned skgrepo can be stranded. An inbound stranded
relationship of a privatizing move would leak its member's ID, so the
save raises it to the new home by itself and says so in its warnings.
The strandeds of a publicizing move are listed in a
strandeds-confirmation; the client asks which to reset to their new
defaults and re-saves with '(strandeds-reviewed . "true")' and the
chosen '(reset-strandeds ...)', after which the server resets them,
rewrites the telescopes of the nodes that record them, and rerenders
the views that show them. Mentions carry no relRepo, so they are
never stranded. The client writes only the new home; the analysis is
the server's.

* Investigating an unknown graphnode
An unknown viewnode stands for an unknown graphnode: an ID nothing
in the graph answers to.
C-c t r ('skg-investigate-unknown-node') asks the server what git
history knows of that unknown graphnode: when it was last present, the commit it vanished
at, its title and relations then, and what referred to it (the API
doc's "Investigate unknown node").
