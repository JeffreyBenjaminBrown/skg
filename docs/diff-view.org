#+title: The diff view
* What it is
The diff view shows every change in the owned skgrepos since their
last commits -- how each worktree differs from HEAD -- with the
context needed to understand each change, in buffers that are
ordinary editable views. It lets the user review the changes, mark
each one commit-ready, and commit everything at once. C-c v d
('skg-diffView-open'; Neovim '<localleader>vd') opens it.

The vocabulary (graph straddle, the three kinds of change, C, R, U,
D, change-forest leaf, mark, changeset marker, ...) is the glossary's "Terms of the
diff view" ('docs/glossary.org'); the reconcilers' words (owner,
key, the one rule, dead viewnode, non-member) are among its terms
specific to Skg. The wire forms are the API doc's
"Diff view", "Stage and commit", "Integrate unshown changes" and
"Metadata of the diff view" ('docs/api-and-formats.org'). The
heralds are 'docs/heralds.org', "Diff heralds". The commands are
both COMMANDS files, under C-c v d and C-c r, and the two restore
requests under C-c s. The server's code is
'server/diff_view/' (its 'mod.rs' lists the files), over the graph
straddle of 'server/graph_straddle/'.

* The four buffers
One command opens up to four buffers, in this order, and skips any
that would be empty. The client sends one "diff view" request per
buffer; the server answers each with a buffer, or with '(empty . t)',
which the client does not open. Each buffer is registered like any
view, under a client-generated view ID, with its buffer kind
('DiffViewBufferKind'), so saves and collateral rerenders reach it.
** "diff-view: all changes"
The pruned change view over all of C.
** "diff-view: merges"
A pruned change view over the nodeMerges since HEAD: its C is each acquiree (a
node only the before-graph has, which an after-graph node lists as an
extra ID) and its acquirer. The acquiree's text preserver is not in
C; it shows as a new member of the acquirer's content.
** "diff-view: skgrepo changes"
A pruned change view over the skgrepo moves
('prunedChangeView_sets_for_skgrepo_changes'):
its C is the recorders of the change-forest leaves whose aspect is
the home skgrepo or the relRepo, that is, the nodes whose home skgrepo
moved and the recorders of the relationships whose relRepo moved. A
node of that C is shown as in any buffer, with all of its changes.
The readiness summary counts every leaf whatever buffer is open;
only the count of changes not editable in the buffer depends on what
this buffer shows. In this buffer each
moved vognode's own heralds also read "-OLD +NEW", and "Δ⌂=a" when
the nearest moved vognode ancestor (a, the viewparent; b, the
grandparent; ...) moved the same way ('set_homeSkgrepoMove_facts_in_viewforest').
** "diff-view: order-only changes"
A flat list, in ID order, of the nodes whose file changed but which
record no change-forest leaf: only the order of some list changed.
Each is shown with its content in the new order, as write-protected
members shown without their content, and with an order-only changeset
marker, which is always ready. Its sets are empty: it renders no pruned change view.
** Refusals
Every buffer is refused, and the client stops, unless the skgrepo
restriction is 'all', and when the graph straddle cannot be built: an
owned skgrepo that is not in a gitrepo or has no HEAD commit, or a
HEAD that fails the whole-graph validation. A merge commit at HEAD is
no reason to refuse.
** Foreign skgrepos
Foreign skgrepos are read at their worktrees in both halves of the
straddle, so they never produce a change: they are outside C, the
change-forest and readiness. The readiness summary only counts their
changed '.skg' files.
** No stages
The diff view compares HEAD with the worktree. The git index never
enters it: no fact carries a stage, and stage-and-commit stages every
change itself.

* The graph straddle
The graph straddle ('GraphStraddle', 'server/graph_straddle/') holds
the before-graph (each owned skgrepo read at HEAD, each foreign one at
its worktree) and the after-graph (the live graph), and answers
questions about their union (the "union walk"): each node and each
relationship it reports carries a presence, 'Both', 'OnlyBefore' or
'OnlyAfter'. A partner of a node in some role is an entry of the
union of the two graphs' lists, with its presence and its relRepo in
each graph; it changed when the relationship is in one graph only, or
its relRepo differs.

Each connection keeps one straddle. A diff-view request, a save, a
rerender and stage-and-commit bring it up to date: it is rebuilt when
an owned skgrepo's HEAD moved (as a git-commit does), re-paired with
the live graph when that changed, and otherwise reused. The before-graph
is read through a cache keyed by the owned skgrepos' HEAD commits.
Closing the last buffer of the diff view drops the straddle, and so
does a rebuild of the session-lifetime stores, so the next request
reads both halves from the disk the rebuilt live graph was read from.
What the straddle computes from itself -- C, the change-forest, each
buffer's sets -- is computed once per straddle, on first use.

* C, R, U and D
These sets define the pruned change view a buffer renders
('PrunedChangeViewSets').
** C
C is the set of changed graphnodes, read off the change-forest leaves
(see "Change-forest leaves"). It has two halves:
- out-changed: the recorders of leaves, the nodes whose own files
  record a change -- a new or deleted node, a changed title or body,
  alias, extra ID, flag or home skgrepo, an added or removed member of
  its contains, subscribesTo, overrides or hidesFromSubs list, or a
  moved relRepo of one;
- in-changed: the nodes whose set of containers, mentioners,
  subscribers, overriders or hiders changed: every member of a
  relationship leaf whose relationship exists in one graph only, and
  every node a recorder mentions in one graph only (a mention is no
  leaf: it changes with its mentioner's text, the mentioner's leaf),
  when that node exists in either graph.
A relRepo move puts only the recorder in C. A change of order alone
puts nothing in C.
** R and U
From each node of C the containerward walk climbs through the union
of the two graphs, following single containers, until it reaches a
content origin: a node with no container or with several, or the
members of a rootlike cycle. R is the content origins reached. U, the
nodes to extend contentward, is C, R and every node on those walks.
** D
D, the buffer's first roots, is R deduplicated: R is processed in ID
order, and a content origin is discarded when its containerward walk
within U reaches another content origin still kept. Of two origins on
a shared cycle, exactly one is kept. When D is recomputed for a buffer
that already stands (see "Integrating unshown changes"), the buffer's
standing roots are pinned as kept first, so a change to a cycle's
membership never adds a second root for it.

* Rendering a buffer
** Stub roots
The buffer starts as one stub per root, in D's order: an editable
vognode, or, when the after-graph lacks the node, its historical
phantom. In a pruned change view, a root with several containers gets a folded
container folder, which completion fills with its containers in
either graph and their containerward forest.
** Completion over the straddle
The stub is completed by the one view completion every view uses
(the level-order BFS of 'complete_viewforest'), with the completion
context's 'straddle' set to the straddle and its
'diffView_buffer_kind' to the buffer kind. 'straddle' is the switch,
and it changes completion so:
- at an editable node's visit, before the content reconciler runs,
  its children are aligned with the straddle, so that the reconciler
  keeps each viewnode instead of creating another;
- content is shown without override substitution: the view shows raw
  graph facts;
- no default partner folders and no hidden-in-subscribee folder are
  created; folders appear only where something changed;
- a property folder (alias, ID, flags) whose list changed is
  reconciled by the per-visit step from the straddle; any other is
  refreshed from the live graph at its own visit, as in every view;
- a partner folder shows the union of the straddle;
- a deleted phantom whose node the before-graph has becomes its
  historical phantom, and a historical phantom in content position
  adds its old content;
- the node budget is charged only as "Editability in the diff view"
  says;
- each editable node's visit ends in the per-visit step;
- after completion, the readiness facts are set from the store.
The skgrepo restriction plays no part, since the diff view requires
'all'.
** The per-visit step
At each editable occurrence's visit, after the content reconciler,
'process_unrestrictedVognode_changes' adds the node's change
viewnodes:
- it tags each content member with the three kinds of change: its
  node's existence ('(node added)', '(node removed)'), its node's
  other properties ('(properties changed)') and its relationship's
  existence ('(rel added)', '(rel removed)'), and shows a
  new member outside U as a write-protected member shown without its
  content (one that was editable when the rerender began stays
  editable);
- it adds the removed content members (below);
- for a node in C, ahead of its content: its old text, its home
  skgrepo move, its "it acquired" folder, the alias, ID and flags
  folders whose list changed, the partner folders whose membership
  changed, and its changeset markers;
- in the order-only buffer, its order-only marker.
What it adds for a node in C, it reads from the leaves that mention
the node (those it records and the relationship leaves naming it as
member), grouped by aspect ('ChangedAspects' in
'server/diff_view/changes.rs'); the graphs supply only what each
viewnode shows, such as the old title. A new aspect of a leaf is
added in one place, and C, the extension and readiness follow. The
mentioner folder alone reads the nodes whose set of mentioners
changed, since a mention is no leaf.
A node in U but not in C is context: when completion creates it, its
body starts folded. A write-protected occurrence gets none of this;
what an earlier visit added under it while it was editable goes, and
its viewparent tags it. A root has no viewparent to tag it, so its
own visit, editable or not, tags its node.

A node was added when only the after-graph has it, and removed when
only the before-graph does ('GraphStraddle::node_existence'); its
other properties changed ("modified", herald M) when both graphs have
it and it records at least one leaf
('GraphStraddle::node_properties_changed'). Every site that tags a
member, a removed member, a folder member or a root asks both
('GraphStraddle::node_change'). A phantom never carries '(properties
changed)'.
** What each kind of change looks like
Every label is a herald rule on a metadata atom; 'docs/heralds.org'
lists them, and the API doc's "Metadata of the diff view" the atoms.
*** text
A changed title or body adds an old-text property under the node,
"old title and body", "old title" or "old body" (its headline the old
title, its body the old body), with a "body diff" property under it
holding the line diff when the body changed. The text change is one
leaf, marked on the old-text headline.
*** content
Content has no folder. The members are the node's children, each
tagged ∃+ / ∃- for its node's existence, M for its other properties
and ~+ / ~- for its relationship's existence; a removed member stands
where it stood (below). The
content changeset marker, "its content changed", gathers the
relationship leaves of the content list.
*** the in-folders and out-folders
A changed set of containers, mentioners, subscribers, overriders or
hiders adds a write-protected folder labelled "its containers changed
(other files)" and so on; a changed set of subscribees, overridden or
hidden nodes adds the existing folder labelled "its subscribees
changed (this file)" and so on. A folder holds the partners in either
graph, each tagged as a content member is: its node's existence and
other properties, so a modified member shows ☮ M and one gesture
there marks its file, and the existence of its relationship to the
folder's viewparent, of the folder's kind. The two filter folders
("It contains these, but the subscribing ancestor hides them" and
"The subscriber ancestor hides these, but subscribes to nothing that
contains them") show no change and carry no '(rel ...)'. Under each
member of a changed folder hangs its member role tree, so that the
user sees where the member sits: under a container, its full
containerward tree; under a mentioner, subscriber, overrider or hider,
the role tree of that role with a containerward tree under each graft.
The role-tree engine walks the union of the two graphs, so a role
graft whose relationship to its viewparent (the one its birth names)
is in the before-graph only carries '(rel removed)', and a gesture on
it names that relationship.
*** aliases, IDs and flags
The alias, ID and flags folders, drawn when their list changed,
hold the union of the two lists in the order of their interleaved
diff, each entry tagged '(rel added)' (+) or '(rel removed)' (-),
its existence in the list. A lost alias or ID is its own kind,
'Property::RemovedAlias' or 'Property::RemovedID', which the save never
reads. Each entry is one leaf.

A property folder is matched by its kind among all the children of
its node, so a folder the user requested becomes the changed one
when its list changes. It stays until the user deletes it: marked
changed while its list differs between the graphs, and unmarked
after ('unmark_property_folders_except' in
'server/diff_view/changes.rs' converts its lost entries and clears
the rest's change facts), when its own visit refreshes it from the
live graph, as in every view. The diff view never converts a
property folder as stale.
*** home skgrepo and relRepo moves
A home skgrepo move is one property under the node, "⌂ -OLD +NEW",
one leaf. A relRepo move is a property under the member whose
relationship moved, "relationship moved from X to Y", one leaf keyed
by the relationship, so the same move seen from either end is the
same mark. The relRepo changeset marker, "some content relationships
changed skgrepo", sits under the recorder when a content relationship
moved. Mentions have no relRepo.
*** deleted and new nodes
A deleted node is shown as its historical phantom: write-protected,
with HEAD's title and body, under each former container. Its old
content stands beneath it, recursing into deleted members. Its
existence is one leaf. An acquiree's phantom holds a derived,
save-inert folder "it was acquired by" with its acquirer, and the
acquirer holds "it acquired" with the phantoms of its acquirees. A new
node is an ordinary editable node with ∃+; its existence is one leaf.
** The shallow model subtree, and what it keeps
Nothing that exists is created again. Each step builds a shallow model
subtree of what a viewnode should hold, in a scratch tree, and
'reconcile_children_with_shallowModelSubtree' matches what the viewnode holds
to it. A child that stands for a graphnode is matched by the ID it
stands for: a member or removed member by the pid the live graph
resolves its ID to (so one shown by an extra ID matches its node), an
unknown phantom by its raw ID, a historical phantom by its ID at HEAD
('skgid_a_folder_child_stands_for', which the partner-folder
reconciler and the save's check of a write-protected occurrence read
too); any other child by its kind (a folder entry by its entry). A
key is matched among all the children of the viewnode, whoever drew
them. A matched child is adopted: kept, with its fold state, and its
kind and facts are updated in place: a member that loses its
relationship becomes a removed member and back, a deleted phantom
becomes a historical phantom and back, a graft or a copy the user
pasted becomes the removed member of its node. A second child of a
matched key is a duplicate: of the copies the editable one is
adopted, else the first in buffer order, and each other is converted
by the one rule, its subtree staying under it. A child the shallow
model subtree lacks is converted, never detached (next section);
what only the shallow model subtree has is created.
"Produced by the shallow model subtree" is defined over the union of the two
graphs, so a viewnode is converted only when what it stands for is in
neither graph. The member role trees under a changed folder's members
are reconciled the same way.

So folding survives saves, rerenders and commits: the server sets a
fold state only on a viewnode it creates (a context node's body and a
container folder start folded, the rest open).

A root stays until the buffer is closed, whatever becomes of the
changes under it. A commit is an ordinary rerender: the roots stand
as plain context with their change viewnodes gone, and a root whose
node the commit deleted is shown as a deleted phantom. A removed
member that held content, or any change viewnode that held
something of the user's, stays as a write-protected non-member or
a dead viewnode holding it.
** What a reconciler keeps
Two reconcilers run at an editable node's visit. The older one,
'complete_managed_children' ('server/update_buffer/util.rs'),
reconciles the content list first, as in every view, and each folder's
members at the folder's own visit; then the per-visit step runs the
diff view's, 'reconcile_children_with_shallowModelSubtree', over the change
viewnodes, the removed members and what the diff view adds below
them. What the user added survives both. Both obey the one rule
('docs/glossary.org', "the one rule: convert, then prune"): neither
detaches, and each converts a child the graph no longer warrants into
a write-protected non-member or a dead viewnode, which the prune
removes once childless.

Neither moves a child it keeps. A child it creates goes right after
the kept or created child that precedes it in its model, or first
when none does ('place_created_children_after_their_model_predecessors'
in 'server/types/tree/moves.rs'; 'KeptChildOrder::Unmoved' in
'complete_managed_children'). So a buffer saves back to itself, and an
order the user gives a role tree or a write-protected folder stands.
There are two exceptions. A list whose order is a graph fact the save
writes -- the content of a node, the alias folder and the editable
partner folders -- follows the graph's order
('KeptChildOrder::FollowsGoal'), so that a view other than the one
saved follows a reorder saved elsewhere; in the view saved the two
orders agree. And a removed member of a content list is moved to its
slot at every visit ("Removed members and the LCS placement"), since
the content reconciler puts non-members ahead of members. The
containerward walk visits a node's containers in ID order, so a first
render is the same every time.

The diff view's reconciler matches a key among all the children of
a node, whoever drew them, and owns every child it adopts; it
converts a stale child only when it owns it ('docs/glossary.org',
"owner"), as the view's record of owners says, so a viewnode the
user typed or pasted that no model wants is nobody's, and stays
where it stands. Under an editable node the content members are the
content reconciler's, and the change viewnodes and removed members
the diff view's reconciler's; a member that the straddle sets aside
becomes the latter's, as does any non-member whose relationship to
the node is only in the before-graph (a graft, or a copy the user
pasted), and so do the former members under a historical phantom,
whose old content adopts them. Before the content reconciler runs,
the first non-member of a node in the after-graph's content list
becomes its member when no member of that node stands there
('align_content_members_with_straddle'). The member role trees
under a changed folder's members are the role-tree attach's; it
matches every child of the member but its members, and converts
only what it owns, so it leaves the member's own visit's viewnodes
alone. A role graft's
birth is written into its metadata as '(birth roleGraft ROLENAME)'
and read back by the parser ('Birth::RoleGraft'), so it survives a
save, and the clients, which rewrite metadata structurally and strip
only what they know, carry the atom through. Since the member role
trees are extended over the union of the straddle, a graft's birth is
validated against either graph of the straddle, not only the live
one.

Both convert a stale child by one function
('convert_unwarranted_child'), as the glossary's statement of the
one rule says. The older reconciler never looks below the
children it manages; the diff view's converts, with the stale
child, what was made below it for the same model
('convert_unwarranted_subtree'), and the prune removes what holds
nothing of the user's (a deleted node's phantom, once the
deletion is committed, is deadened holding the user's note but
not its old content).

So a note the user adds under a member of a changed folder, under a
historical phantom, in the "it acquired" folder or under a removed
member survives every rerender; when the removed member goes stale
(a commit makes the removal part of HEAD, or the relationship
returns), the note stands under a write-protected non-member
occurrence of it.
A new note there that names no skgrepo ('(repo NAME)') inherits that
of its nearest ancestor that is an unrestricted vognode, through the
phantoms and folders between them
('inherit_skgrepo_from_nearest_unrestricted_ancestor_if_possible'), as
a note directly under a vognode inherits its parent's; in a folder it
is a non-member.
** Removed members and the LCS placement
A removed member is a member of the before-graph's list that the
after-graph's lacks. Membership is decided by set difference, so a
reorder shows nothing; the longest common subsequence of the two
lists only places a removed entry: immediately before the next
surviving member of the old order, or last
('phantom_insertion_plan', 'compute_interleaved_diff'). Content and
the alias, ID and flags folders are placed this way. In content each
removed member is moved, not recreated, to its slot at every visit,
after the content reconciler has reordered the children; in a folder
a removed entry is placed in its slot when it is created, and then
stays where it stands, as every kept child does.

The partner folders over the straddle place their removed
members the same way, since 'GraphStraddle::partners' gives the
partners a node records in the order of the interleaved diff of the
two lists ('interleaved_diff_without_reorders'); recorders, which no
list orders, come sorted by ID. So every rendering of the union of the
two graphs places a removed entry by the LCS.
** One encoding of a removed relationship
A removed member whose node survives is an unrestricted vognode, a
non-member, with the fact '(rel removed)': its relationship to its
viewparent exists in the before-graph only. That is the one encoding
of a removed relationship, wherever it stands: in content, in a
partner folder, and in a historical phantom's old content
('mk_removed_member_viewnode', 'FolderGoalShape::Removed').
'is_unrestricted_removed_member' reads it, and tests nothing
about editability; the parser's check of where a restore request
sits reads it too ('check_where_the_edit_request_sits'). Since a removed member is never a member, the
save's check of a write-protected occurrence's folders counts only
members.

Its editability is a member's. In content position (under an
unrestricted vognode or a historical phantom) a removed member is
created editable, its body from the after-graph, when its node is in
U, which it always is (its node is in C), and write-protected
otherwise; the editability rule at its own visit keeps it editable
when its node is unclaimed and write-protects it when another
occurrence claimed the node first. An editable removed member's visit
extends it as any editable occurrence's does, with its content list
and its change viewnodes, among them its container folder listing the
container that dropped it; a write-protected one holds nothing of its
node. A removed member that was editable when a rerender began stays
editable ('adopt_model_facts' only ever write-protects). In a partner
folder a removed member stays as the folder's other members are.

A removed dangling ID is not shown in content or in a folder whose
membership the save reads (an unknown phantom there would read back
as a member); its leaf in content is under the content changeset
marker. In a write-protected-set folder and in a historical phantom's
old content, where nothing reads back, it is an unknown phantom with
'(rel removed)'; the save's check of a write-protected occurrence's
folder skips an unknown phantom with that part, as it skips a removed
member by its non-membership ('partnerFolder_members_in_view'). A
former member is any viewnode standing for a
before-only relationship, historical phantoms included.

* Editability in the diff view
The diff view follows the rule that decides which occurrence is
editable in any view -- the editable map, the editability rule, the cascade
and the node budget, described in the module comment of
'server/to_org/extend/editable.rs' -- with these deviations.
** A node of U is editable, with its whole content list
When a buffer is first rendered, a node of U is editable at its first
occurrence and its whole content list is shown; a member outside U is
a write-protected member shown without its content. No size cap
applies: the node budget is not charged for any of this. A removed
member in content position counts as an occurrence here: a node
whose first occurrence is a removed member (one its only container
dropped, say, or one first reached through a container that dropped
it) is editable there ("One encoding of a removed relationship").
** The budget bounds only requests outside U
An editable-view request (C-c s d) behaves as in any view: it makes
its occurrence the editable one, write-protecting the other with its
content subtree, and cascades to its content children. Only the
extension of a node outside U that a request asked for is charged to
'initial_node_limit'; a node of U is never charged, whether the rule
above or a request made it editable. A request adds no default
folders, since the diff view creates none.
** A save makes nothing editable and appends no root
After a save, a buffer's sets are recomputed, and completion extends by
the recomputed U wherever it adds something new. Nothing the buffer
holds editable is write-protected again by the server. But the server
makes no occurrence editable and appends no root on its own: a change
recorded by a node the buffer holds no editable occurrence of is not
editable in this view, and the readiness summary counts it.
** Integrating unshown changes
C-c r u ('skg-diffView-integrate-unshown-changes'; Neovim
'<localleader>ru'), on a buffer with no unsaved changes, sends
"integrate unshown changes". The server brings the straddle up to
date and recomputes the buffer's sets. Every node of U without an
editable occurrence becomes editable (its body read from the live
graph) at its first content occurrence in level order, else at its
first partner-folder occurrence ('ensure_editableOccurrences_exist').
The walk for content occurrences counts a removed member under an
unrestricted vognode or a historical phantom as a content occurrence,
and passes through a historical phantom in content position into its
old content.
The buffer is then rerendered as after a save, which extends the
content list of each node made editable, and last, each content
origin of D that the buffer shows nowhere is appended as a root, in ID
order, with the standing roots pinned, and completed. The answer is
the readiness summary, and the rerender stream carries the buffer. It
does not matter who write-protected an occurrence: the user asked for
every change.
** What counts as editable here
A buffer makes a node's changes editable when it holds an editable
occurrence of the node, wherever that sits, or the node's historical
phantom in content position (under the buffer root, an unrestricted
vognode, or a historical phantom that is itself in content position),
since a deleted node's old content is editable nowhere and shown
there ('nodes_editable_in_diffView'). The change-forest leaves those
nodes record are the changes editable in the buffer.

* Readiness
** Change-forest leaves
The change-forest ('ChangeLeaves', built from the straddle,
independent of any view) holds every change a user can mark: its
leaves. A leaf's key is a node and an aspect of it (existence, text,
home skgrepo, an alias, an extra ID, a flag), or a relationship (a
relation, its recorder, its member) and an aspect of it (existence,
relRepo). The recorder of a leaf is the node whose file records it; a
relationship's leaf lives under its recorder, and seen from either
end it is the same leaf. A node's existence leaf covers its own
content when it is new or deleted.

The builder compares only the nodes that one graph lacks or holds
unequal, and the nodes that list a member whose ID the two graphs
resolve to different nodes: after a nodeMerge since HEAD, a container
that still lists the acquiree's ID is equal in both graphs, yet the
after-graph resolves that ID to the acquirer. Such IDs are among the
extra-ID differences of the unequal nodes. No other node can record a
change, so neither the leaves nor C cost a comparison of every node.
** Marks, fingerprints and the store
A mark says that one leaf is commit-ready. The readiness store
('server/diff_view/readiness_store.rs') keeps each mark with the fingerprint of
the change it approved, a hash of the leaf's before and after values.
A mark whose fingerprint no longer matches the change counts as
absent: editing a marked change unmarks it, and nothing signals that
an earlier version was approved. The store lives on the server, is
written to '<data_root>/readiness-marks.json' after every change, and
is read at startup; a missing or unreadable file is an empty store.
The file serializes the leaf keys, aspect names included, so their
spelling is kept stable. After a git-commit, the store keeps exactly
the marks whose leaves still exist in the rebuilt straddle.
** Commit readiness aggregates
A commit readiness aggregate -- a folder, a changeset marker, a node,
a file or the whole changeset -- is ready when every leaf under it
that can be ready is ready. An unchanged membership has no leaf and is
never asked. The content changeset marker gathers the
content relationship leaves of its node; a member's existence leaf
belongs to the member's own file. A file whose only change is order
has no leaf and is ready. A modified node stands for every leaf it
records, nearly its file (a home skgrepo move and a relRepo move name
a second file): it shows M✓ when each of those is marked, wherever it
stands.
** Facts on the wire
A headline's facts and its readiness request form one form, '(diff
(node added|removed) (rel added|removed) (properties changed) (leaves
N OBJECT...) (ready OBJECT...) REQUEST)', each part present only when
it has something to say, the first three only when true
('change_fact_forms' in 'server/org_to_text.rs'; the grammar is in
'docs/api-and-formats.org', "Facts and requests"). It sits inside the
node's or phantom's form, or at top level on a property. A changed
folder's '(diff ...)' holds only its readiness, the objectless
'(ready)', which is the folder's aggregate.

The part '(ready OBJECT...)' is a display fact the server writes after
completion ('set_ready_facts_in_viewforest'): the diff objects
('node', 'rel', and on a headline that lists it 'all') whose leaves
are all marked, so a ready changeset marker carries '(ready all)'; a
bare '(ready)' on a headline that names one leaf, which lists no
object. Nothing reads it at save.

Before it, a headline that names leaves
carries the part '(leaves N OBJECT...)': N is the number of distinct
leaves a request naming every listed object would touch, and the
OBJECTs are those a request on this headline may name ('node' and/or
'rel' on a vognode or phantom, each worth one leaf; 'all' on a
modified node, every leaf it records, beside 'rel' when its
relationship changed; 'all' on a commit readiness aggregate, worth N; none on a
headline that names exactly one leaf, which a bare request marks).
The server's 'leaves_named_at' is the one rule; the fact is
display-only, and the clients read it instead of keeping tables of
headline kinds.
** Readiness requests and gestures
A gesture writes readiness requests, '(readyRequest OBJECTS)' or
'(unreadyRequest OBJECTS)', as the last part of a headline's '(diff
...)' (creating the form if the headline lacks one) and saves; the save
consumes them after its graph edits succeed (not when it stops for a
confirmation), in any buffer, marking or unmarking the leaves each
headline names at their current fingerprints. A request naming no
current change is dropped with a warning. 'all' names every leaf a
modified node records, or every leaf of a commit readiness aggregate
one level down.

Every gesture toggles: it unmarks what is ready and marks what is
not, and every headline is ready when its own '(ready ...)' names
every object its '(leaves ...)' lists. C-c r r
('skg-cycle-commit-ready') acts on the headline at point, naming every
object it lists: one leaf; on a new member, its existence and its
relationship; on a modified node, every leaf it records, and its
relationship when that changed, so one gesture marks the file; on a
changed folder, its leaves one level down; with a prefix argument,
every leaf of the subtree. Below the headline it acts on, a gesture
names no 'all': the leaves of a modified node or a commit readiness
aggregate there are named by the headlines under it, or are not
shown there; the other objects such a headline lists are named. C-c r h
('skg-toggle-homeSkgrepo-move-commitReady') acts on the home skgrepo
move of the node at point, and with a prefix argument on every
descendant whose home moved between the same two skgrepos. Both work
on write-protected occurrences. A gesture that would unmark more than
one leaf, counting each request's leaves as '(leaves N ...)' does,
first asks for a typed "yes".

Six commands move point between change headlines, the headlines
whose metadata carries a '(leaves ...)' fact: C-c r n c
('skg-diffView-goto-next-change') to the next, C-c r n u to the next
unready one and C-c r n r to the next ready one, and C-c r p c, C-c r
p u and C-c r p r to the previous ones. A change headline is ready
when its '(ready ...)' names every object its '(leaves ...)' lists.
They do not wrap: at the end they say "No further change" (or "No
earlier change", with "unready" or "ready" for the filtered forms).
** The readiness summary
After every save of a buffer of the diff view, after C-c r u, and
before a stage-and-commit that would leave changes behind, the client
shows the readiness summary: "12 of 14 changed files are ready", or
"Commit ready. All 14 of 14 changed files are ready.". A changed file
is ready when every change it records is marked; order-only files
count as changed and ready. It is computed over every leaf of the
change-forest, whatever buffer is open. It adds the changed files of
the foreign skgrepos, and the changes not editable in this view:
the leaves whose recorder the buffer does not make editable (see
"What counts as editable here"), with the command that integrates
them. A save and C-c r u compute it alike
('buffer_readiness_summary_for', 'server/diff_view/readiness_requests.rs').

* Restoring what a change removed
Two edit requests undo a removal from the diff view's buffers, without
leaving them. Each is written by a command that refuses at once on the
wrong kind of headline, and does not save; the parser refuses each
there too. They are carried, applied and consumed like every edit
request: the save collects them with its graph edits, and consumes them
after the skgsave-commit; a save that stops for a confirmation or fails
leaves them in the buffer.
** '(editRequest restoreNode)': a deleted node
C-c s n ('skg-restore-deleted-node'; Neovim '<localleader>sn',
':SkgRestoreDeletedNode') writes it into a historical phantom, the only
headline that accepts it (herald "restore node"). The save writes the
node's file from the before-graph's copy of it (title, body, aliases,
extra IDs, flags, home skgrepo, and its four relationship lists with
their relRepos), as it writes any node. An out-link to a node still
deleted is kept as HEAD recorded it, and shows as an unknown phantom.
Then it re-adds the node's in-links, from the before-graph's inbound
indexes: each node that recorded it at HEAD (as content, a
subscription, an override or a hide) gains it in that list, at the
index it had at HEAD, clamped to the list's length, in the skgrepo
that recorded it, unless that recorder is itself deleted (it is
skipped) or lists it already. A recorder the save already writes, as
the buffer's editable occurrence of it, gains it there.
** '(editRequest restoreRel)': a removed membership
C-c s l ('skg-restore-removed-membership'; Neovim '<localleader>sl',
':SkgRestoreRemovedMembership') writes it into an unrestricted vognode
carrying '(rel removed)' that is no role graft: a removed member in
content position, or a member of a partner folder whose relationship to
the folder's viewparent was removed, editable or write-protected (herald
"restore membership"). On a historical phantom it refuses with "This
node is deleted; restore it first (skg-restore-deleted-node)". The save
re-adds the one relationship the headline stands for (the readiness
requests' 'relationship_to_viewparent' names it), as HEAD recorded it:
at its index in the recorder's list at HEAD, clamped, in the skgrepo
that recorded it. A request whose headline stands for no relationship
(as under an acquisition folder), whose relationship is a link, has a
deleted node at either end, or is not recorded at HEAD, is dropped with
a warning naming the viewnode ID.
** Both in one save
The restored nodes come first, then the relationships, so a
relationship restored in a save may name a node restored in the same
save. A relationship that a restored node records is restored with its
file.
** The rerender
The save's rerender shows the result as any save's does: the
historical phantom of a restored node becomes the node again, and a
removed member whose relationship returned becomes a member again. A
change that no longer differs from HEAD leaves the change view; what
the buffer still holds of it is kept or converted as "What a
reconciler keeps" describes.

* Stage and commit
C-c r c ('skg-stage-and-commit') prompts once for a message and sends
"stage and commit". The server stages the changed '.skg' files of
every owned skgrepo, deletions included, and git-commits each gitrepo
that has changes with that message, by the gitrepo's configured user.
It refuses unless the skgrepo restriction is 'all', for a blank
message, and when the straddle cannot be built. It commits whole
skgrepos, never less: a partial commit can leave HEAD inconsistent
(referencing nodes it lacks, recording a relationship from one end
only, holding a moved node twice), and the next diff view against it
would report changes that are only that inconsistency.
** Its confirmations
When the readiness summary is incomplete and the request lacks
'(confirmed . t)', the answer is the summary alone with
'(needs-confirmation . t)', and nothing changes; the client asks for
the typed word "yes" and resends confirmed.

Before staging anything, the server also
reads the index of every owned gitrepo. If any has entries already
staged, the answer is the same confirmation with a second reason,
'(already-staged ((GITREPO PATH...) ...))', and nothing is staged or
committed; the client lists those paths and asks the typed "yes".
One confirmed resend covers both reasons, and the commit of such a
gitrepo then includes its already-staged entries, as a git commit
records the whole index.
** After the commit
The straddle is rebuilt over the new HEAD, the store keeps only the
marks whose leaves still exist, and each open buffer of the diff view
is rerendered as any rerender is: its roots and what it made editable
stay, and what was committed loses its change viewnodes.

* Strandeds
A relationship touching a node whose home skgrepo moves is stranded
when it sat at its default relRepo before the move and the sticky rule
would leave it off its new default. The save finds every stranded
relationship of every relation, in both directions, shown in some view
or not ('server/from_text/strandeds.rs'). An inbound stranded
relationship of a privatizing move would leak its member's ID, so the
save raises it to the new home by itself and says so in its warnings.
The strandeds of a publicizing move are listed in a
strandeds-confirmation; the client asks which to reset to their new
defaults and re-saves with '(strandeds-reviewed . "true")' and the
chosen '(reset-strandeds ...)', after which the server resets them,
rewrites the telescopes of the nodes that record them, and rerenders
the views that show them. Mentions carry no relRepo, so they are
never stranded. The client writes only the new home; the analysis is
the server's.

* Investigating an unknown node
An unknown phantom stands for an ID nothing in the graph answers to.
C-c t r ('skg-investigate-unknown-node') asks the server what git
history knows of it: when it was last present, the commit it vanished
at, its title and relations then, and what referred to it (the API
doc's "Investigate unknown node").
