#+TITLE: The Neovim client's deviations from the Emacs client
# Every place the Neovim client behaves differently from the Emacs
# client because Neovim cannot do what Emacs does. Anything not
# listed here is intended to behave
# identically; if it doesn't, that's a bug worth reporting in
# ../TODO/problems.org.
#
# Wire compatibility is total: same protocol, same requests, same
# metadata grammar, zero server changes.

* The two clients' names match
A Neovim module has its Emacs file's name, without 'skg-' or
'skg-request-' and with '_' for '-': 'skg-metadata.el' is
'metadata.lua', 'skg-request-text-search.el' is 'text_search.lua',
'skg-sexpr-edit.el' and 'skg-sexpr-edit/skg-sexpr-cycling.el' are
'sexpr_edit.lua' and 'sexpr_edit/sexpr_cycling.lua'. A function has
its Emacs twin's name, without the 'skg-' or 'skg--' prefix and its
module's own prefix, in the same module. Where an Emacs function acts
at point, its twin takes a line number and says '_at_line' for
'-at-point'; a few that read the whole buffer at once say
'_in_lines' ('pending_detachment_in_lines'). The shared case files in
'tests/shared/' are the oracles both clients are tested against.

Some names stay apart because they name an Emacs mechanism Neovim
does not have: 'heralds-minor-mode.el' is 'heralds.lua' (no minor
modes), 'skg-org-fold.el' is 'folds.lua', 'skg-request-file-path.el'
is 'goto_git.lua' (no magit; see "The git jumps"),
'skg-keymaps-and-aliases.el' is 'keymaps.lua' (no 'M-x' aliases),
'skg-request-save/skg-lock-buffers.el' is 'lock.lua'. Where Emacs
splits a concern over several files that each hold one command
('skg-request-verify-connection.el',
'skg-request-rebuild-session-lifetime-stores.el',
'skg-request-strip-body-whitespace.el'), Neovim keeps the commands in
'misc_requests.lua'. Helpers Emacs gets from its own library
('read', 'prin1-to-string', reading a field of a response) are
'sexpr/parse.lua' and 'payload.lua'. Three Emacs files hold two
concerns each, which Neovim keeps apart: 'skg-id-search.el' is
'id_search.lua' and 'linkstack.lua', 'skg-config.el' is 'config.lua'
and 'picker.lua' (the prompts), 'skg-request-save.el' is 'save.lua'
and 'messages.lua' (the report buffers).

A message has the same words in both clients; Neovim's begins
'skg: ' and in lowercase where Emacs's begins with a capital, and
names Neovim's keys where Emacs's names a chord.

* Input model (necessary: vim is modal, and C-c belongs to the terminal)
- The Emacs 'C-c ...' chords become '<localleader>' plus the same
  mnemonic letters ('C-c s d' -> '<localleader>sd'); where Emacs ended
  a chord with RET the family letter doubles ('C-c g RET' ->
  '<localleader>gg'); capitals stay capitals. 'C-x C-s' becomes ':w'
  (skg buffers are 'acwrite'; ':w' runs the save pipeline). Every
  command is also an ':Skg*' Ex command. The full table lives in
  nvim/lua/skg/keymaps.lua and docs/COMMANDS-nvim.org.
- Extra vim-idiomatic surfaces beyond the Emacs set: ']i' / '[i' as
  id-next/prev motions; '^' plays the C-a title toggle; '<Tab>'
  toggles the fold at point and '<S-Tab>' global visibility.
- TODO-keyword cycling is 'cit' / 'ciT' (wrapping the org plugin so
  metadata survives, as the Emacs org-todo advice did). Vim's fold
  cycling is two-state (open/closed) rather than org's three-state
  cycle.
- The minibuffer linkstack bindings ('C-c o i' etc. in prompts) become
  command-line-mode mappings '<C-x>i', '<C-x>l', '<C-x>I', '<C-x>L'.
  The Emacs shell-mode linkstack bindings have no terminal-mode
  equivalent here; paste the id from a buffer instead.
- Emacs binds a few keys outside its content views: search, go-to-ID
  and the skgrepo-set switch in every buffer, and go-to-node and
  id-next/prev in magit. Neovim binds no key globally and none in
  neogit; every ':Skg*' command works from any buffer instead. Its
  .skg file buffers and report buffers get the same subsets Emacs
  gives them (docs/COMMANDS-nvim.org, "keys outside content views").
- Emacs also binds 'C-c C-o' to skg-goto, in place of org's
  open-at-point; Neovim has only '<localleader>gg'.
- The relationship-kind menu of the recursive relRepo gesture
  ('<localleader>sR') is Neovim's selection menu ('vim.ui.select'),
  one entry per relation role, where Emacs pops up an org buffer of
  the relations and their roles; choosing a role that cannot be set
  says why, as RET on it does in Emacs.
- The skgrepo prompts cycle with S-Left/S-Right and complete with TAB,
  as in Emacs; the 'C-?' show-all-skgrepos helper key inside the prompt
  is dropped (terminals rarely deliver C-?); ':SkgViewRepoList'
  shows the same list.

* Buffer locking (necessary: nvim has no overlay modification hooks)
- A buffer locked during a save/rerender stream rejects edits with
  vim's generic "E21: Cannot make changes, 'modifiable' is off"
  instead of Emacs's custom "skg: buffer locked -- save in progress".
- Consequently a second save attempted mid-stream is refused by the
  lock (E21) rather than by the stream-in-progress guard's message;
  the guard still exists as the second line of defense, exactly as
  in Emacs.

* Read-only text regions (necessary: nvim has no per-range read-only)
- The metadata edit buffer's display-only title group is editable
  while typing; edits to it are discarded at commit (the strip step
  drops the title group whatever it holds). Emacs rejected the edits
  at type time.
- The fork-confirmation buffer similarly relies on commit-time
  validation (the placeholder-skgrepo refusal) rather than type-time
  protection.

* Folding (necessary: vim folds are line ranges on windows)
- A closed fold always displays vim's one-line fold placeholder; org
  hid the text entirely.
- A one-line body cannot be body-folded (vim cannot close a
  single-line fold). A 'bodyFolded' atom on such a body degrades
  gracefully: the body stays visible and the atom is simply not
  re-recorded at the next save. Multi-line bodies body-fold normally.
- Fold state lives on windows, so fold restoration after a save/
  rerender applies to a window showing the buffer; a collateral view
  updated while not displayed anywhere gets its fold atoms stripped but
  has no fold state to restore into, and appears fully open when next
  displayed. (Emacs restored folds even in undisplayed buffers.)
- For the same reason the body toggle ('<localleader>vb', Emacs's
  'C-c v b') leaves a one-line body shown, and says so; org hid it.
  (Closing a one-line fold would also mark it closed, so that the
  next close would close the headline's whole subtree.)
- skg view buffers use skg's own foldexpr (a body gets its own fold
  one level below its headline, which is what makes 'bodyFolded'
  representable) rather than nvim-orgmode's folding; the org plugin
  still provides syntax highlighting.

* The git jumps (necessary: no magit exists for vim)
- 'skg-goto-in-magit' -> ':SkgGotoInGit': opens neogit (the closest
  magit analog, baked into the docker image) on the skgrepo's gitrepo and
  lands on the file's entry by text search, warning when the file
  appears in several sections. Magit's section-object navigation has
  no neogit API equivalent.
- 'skg-goto-in-magit-parent' -> ':SkgGotoInGitParent': opens a plain
  git-diff buffer ('skg://git-diff/FILE', readable-ids enabled) with
  the cursor on the first changed line containing the node's id --
  the same information magit showed, without the status chrome.

* Display details
- Heralds conceal the metadata rather than covering it with a display
  overlay. With 'concealcursor=nc', entering insert mode on a line
  reveals its raw metadata (arguably clearer for editing); Emacs never
  revealed it. Semantics, colors and the server-owned rule table are
  identical.
- Readable-ids shortens UUIDs by concealing the tail to an ellipsis
  and renders titles as inline virtual text; same behavior, same
  server round-trip, different mechanism.
- The buffer corrections a save or a rerender reports are appended to
  'skg://messages/server-warnings', shown in a split, with the cursor
  left where it was; Emacs moves point in '*SKG Server Warnings*' to
  what it appended.
- Server messages name Emacs chords. The client rewrites those it
  has a binding for ('neovim_bindings_of_emacs_chords' in
  nvim/lua/skg/messages.lua: C-c s d, C-c s w, C-c s s, C-c s r,
  C-c g RET, C-c g v). It leaves the others as they are: the
  fork-confirmation buffer's 'C-c C-c' and 'C-c C-k' are
  '<localleader>cc' and '<localleader>ck' here, as the notification
  that opens it says.
- View buffers are named 'skg://TITLE' (search: 'skg://?TERMS');
  Emacs used '*TITLE*'. Message/report buffers live under
  'skg://messages/...', 'skg://unknown-node', 'skg://diff-view: ...',
  etc.

* Small semantic notes
- 'point-column' in the save round-trip is a byte offset here and a
  character offset in Emacs. The server merely echoes it, so each
  client round-trips its own convention; on lines containing
  multibyte characters before point, a buffer saved in one client and
  restored in the other would land point a few cells off. Harmless in
  single-client use.
- The Lua sexp printer renders the empty list as '()' where elisp
  prints 'nil'; the server's parser accepts both, and the reader maps
  both to the same value.
- 'view-without-metadata' takes the visual selection (or the last
  visual marks); Emacs took the active region.
- 'search-interactive''s 'h' option opens docs/COMMANDS-nvim.org
  (falling back to COMMANDS.org).
- The 'M-x' cosmetic machinery (alias names, completion-predicate
  hiding of internal names) has no analog; the ':Skg*' commands are
  the public names.
