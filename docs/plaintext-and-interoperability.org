* Plaintext And Interoperability

** Does it use plaintext? Is it interoperable with Emacs org-mode?

Yes and yes.

I hope to create an isomorphism from Skg into [[https://github.com/CategoricalData/hydra/tree/main][Dragon]], whereupon it can easily be converted back and forth into anything else for which such an isomorphism has been written. Anything expressible in Skg and not the other system, or vice-versa, can (but needn't be) preserved as comments -- that is part of Hydra's magic.

Skg uses Org text to manipulate data, but stores it as YAML in =.skg= files. Skg files are valid YAML, but most YAML is not valid Skg. See the [[file:./api-and-formats.org][file-format reference]] and [[file:../server/types/nodes/fs.rs][on-disk node types]].

Skg can import ordinary Org and Markdown into an existing owned skgrepo after a preview and explicit approval; see the [[file:./COMMANDS.org][command reference]]. It also has a separate Org-roam importer, which replaces existing =.skg= files in its destination; use a fresh staging directory for that older command. Skg exports selected content to plain Org.

Export is for readable documents, not lossless backup or synchronization with Org-roam. It omits identities and relationships needed to reconstruct the graph. See [[file:./undoing-import.org][returning imported data to Org]] for the limitations.

** The =contains= relationship and nesting org-mode headlines

The Skg containment relationship is identical to the org-mode relationship from a headline to one of its subheadlines. (I might rename it "shows" or "presents" or something, to make clear that it is the relationship that defines a "document" or a "view".)

What's different is their representation on disk. Skg represents each node of a document with a separate file in order to  enable sharing. I can't link to one of your nodes unless every node has an ID. And creating a fork of one of your nodes would have a prohibitive memory cost if the node has many descendents.
