#+title: Override relationships, substitution, and navigation
#+date: 2026-09-20

* The relationship

If =R= overrides =N=, =R= is the /overrider/ and =N= is the
/overridden/ node.  The relationship is stored on =R= as an entry in
its =overrides_view_of= list:

#+begin_example
R.overrides_view_of = [N]
#+end_example

The stored value is a =RelPartner<ID>=.  Its =member= is =N= and its
=relSource= says which telescope section records the relationship.
The relSource is independent of either endpoint's home source: two
public nodes can be connected by an override relationship recorded only
in =private=.

An overrider may override any number of nodes.  Owned override data has
two invariants in the opposite direction:

1. A target has at most one user-owned overrider.
2. User-owned override chains are acyclic.

Thus =R -> N1= and =R -> N2= are legal, as is the linear chain
=D -> C -> N=.  Two owned nodes overriding the same target are not
legal.  Foreign data can contain branches or cycles; Skg preserves
those as displayable graph facts, but never uses foreign overriders for
automatic substitution.

* Direct visits are exact

Visiting an ID opens that exact node as the raw root of a content view.
It does not redirect to an overrider and does not stop at a choice
buffer.  Re-visiting an ID that is already a root switches to its open
content view.  A node whose home source is inactive in the current
source-set cannot be visited.

This makes every row used for navigation a stable destination.  In
particular, selecting a node in search results, an override folder, or
an override path opens the selected node itself.

The root's ordinary =O= relationship herald reports its visible
override facts.  The user can then inspect those facts through the
overrideward view-subtree in search results, the two override folders,
or the two override paths.

* Overrideward view-subtrees in search results

Search hits begin as raw, write-protected, non-content roots.  During
search enrichment, each result gains an /overrideward view-subtree/
containing visible override relatives in both directions:

| Direction       | From result N, it shows                 |
|-----------------+------------------------------------------|
| overriddenward  | nodes that N overrides                  |
| overriderward   | nodes that override N                   |

Each direction is recursive and cycle-guarded.  The inserted rows are
write-protected non-content descendants with an override birth reason,
so their highlighted =O= herald explains why they occur at that
position.  Node visibility and the override relationship's relSource
both gate the subtree.

Search also groups matching owned override chains.  If a user-owned
search hit recursively overrides another matching hit, the overridden
hit is suppressed at the top level and reappears under the owned hit.
A foreign overrider never suppresses another top-level result, although
visible foreign override relatives can occur in the subtree.

* Override folders

The folder command =C-c l o= requests both directions for the node at
point.

** =overriddenFolder=: what this node overrides

Under overrider =R=, =overriddenFolder= is the editable projection of
=R.overrides_view_of=.  Adding or deleting a member edits that stored
list.  This is the direct way to create or remove an override
relationship without forking.

The folder is a writable set, so an explicit request creates it even
when it is empty.  Absence means that the buffer expresses no opinion
about the stored list; a present empty folder means to set the visible
list empty.  The folder's members are /overridden-as-such/: they show
the original target rather than a substitute.  The outbound member is
also the surface from which the relationship's relSource can be edited.

** =overriderFolder=: what overrides this node

Under overridden =N=, =overriderFolder= is generated by finding nodes
whose =overrides_view_of= list contains =N=.  Its membership is
read-only because the relationship is stored in each overrider's data.
Deleting a real member is repaired on reconciliation; inserting a
nonmember does not create an override relationship.  An empty
=overriderFolder= is pruned.

The rows are initially write-protected because the folder membership
is an inverse view.  A row can still be visited, or made definitive as
the node itself, without making the inverse membership editable.

** Initial folder presentation

An ordinary definitive node automatically includes only a nonempty
=subscribeeFolder=.  Override folders are never part of its initial
content merely because they would be nonempty; the herald advertises
their existence and the folder command asks for them.

The same narrow rule applies when a hidden-as-such, hider-as-such,
overridden-as-such, or overrider-as-such row becomes definitive.  A
subscribee-as-such is the exception: in addition to its ordinary
content, it automatically includes a nonempty folder for content hidden
there.

Under a restricted source-set, both override folders omit relationships
whose relSource is inactive and partners whose home source is inactive.
Saving the visible subset preserves memberships stored in hidden
telescope sections.

* Override paths

=C-c p O= requests a transitive read-only path through overriders.
=C-c p o= requests a transitive read-only path through overridden
nodes.  These are path grafts rather than folders or recursive content.
Their rows carry an override birth reason and are exact navigation
targets.

* Automatic override substitution

Substitution is a recursive-content rendering rule, not a navigation
rule.  When completion is about to create a content viewnode for =N=,
the resolver walks toward user-owned nodes that override it.  For

#+begin_example
D overrides C overrides N
#+end_example

a full-source content view draws =D= where =N= occurs.  If =D='s home
source is inactive but =C='s is active, it draws =C=.  If no user-owned
overrider is drawable, it draws =N=.  A monogamy violation makes the
resolver refuse to choose a branch; a cycle makes it abandon
substitution and return the originally requested node.

Substitution is disabled in diff mode.  It also does not rewrite
existing viewnodes: closing and reopening a normal view produces the
fresh normalized rendering.

The following positions always begin with the raw node rather than an
automatic substitute:

- content-view roots;
- search-result roots and enrichment grafts;
- PartnerFolder members and requested path rows;
- ancestry rows and diff phantoms.

When a node with a user-owned overrider is deliberately drawn raw, its
immediate content children are also drawn raw.  Substitution resumes at
the grandchildren.  This one-level rule makes the raw node show its own
children rather than its overrider's interpretation of them.

** The =overridesHere= marker

A substituted row carries =(overridesHere N)=, where =N= is the
original node for which the displayed carrier substitutes.  The marker
is load-bearing during save: the row contributes =N= to its parent's
stored relationship list rather than the carrier's ID.  Editing the
carrier's title, body, or folders still edits the carrier itself.

The server rejects a forged or stale marker whose carrier is not on
=N='s user-owned override chain.  The validation walk is intentionally
visibility-ungated so that a marker which was honest when rendered does
not become invalid merely because the active source-set changed.

* Heralds and reasons for placement

An ordinary relationship =O= says that the node participates in a
visible override relationship.  A highlighted birth =O= says that an
override relationship is why this particular row is present beneath
its org parent.

Substituted rows, override-folder members, override-path rows, and
search overrideward descendants carry override birth information.  A
node can have ordinary =O= facts without a highlighted birth =O= when
its placement comes from some other relationship.

* How override relationships are created

** Forking

Editing a definitive foreign node and saving requests an implicit fork.
After confirmation, Skg creates an owned clone which subscribes to and
overrides the foreign original.  It shallow-copies the edited content
IDs and hides original children removed by the edit.  The original is
unchanged.

=skg-fork-node= (=C-c m f=) explicitly forks an owned node, commonly to
add a more-private layer such as =D= over =C=.  Forking a substituted
row forks the carrier on screen and therefore deepens the chain.
Creating a second user-owned overrider for the same target is refused.

The subscription and override are paired by the fork operation, not by
the data model.  Removing either relationship later does not
automatically remove the other.

** Direct editing and imported data

Adding a member to an owned node's =overriddenFolder= creates an
override relationship without creating a subscription.  Raw or
imported =.skg= data can likewise contain existing override facts.

* Merge behavior

When node =A= acquires node =B=, their outbound =overrides_view_of=
lists are combined.  Duplicate partners keep the more-private
relSource, and each relSource is clamped no more public than =A='s
home.  References to =B='s primary or extra IDs resolve canonically to
=A= after the merge.

Merge validates the resulting owned override graph atomically.  If
owned =R1= overrides =A= and owned =R2= overrides =B=, merging =A= and
=B= would make two owned nodes override one canonical target.  The
merge is rejected and identifies the participants so the user can
establish an explicit chain first.  Cycle creation is rejected for the
same reason.  Merge does not create a subscription-and-override pair.

* Deletion and dangling references

Deleting a node removes its primary and extra IDs from the outbound
relationship lists of owned referencers, including
=overrides_view_of=.  Foreign files are not rewritten.  The explicit
absent-reference cleanup can remove an exact dangling override partner
from owned data.

An unknown override target can otherwise remain visible as an unknown
folder member.  It cannot substitute because there is no node to draw.

* Source-set behavior

Override folders, paths, search grouping, search overrideward
view-subtrees, =O= relationship counts, and automatic substitution all
derive their topology from relSource-gated relationship accessors.

For automatic substitution, an override hop is followable only when the
edge's relSource and the overrider node's home source are active and the
overrider is user-owned.  A relationship outside the active source-set
therefore cannot silently select a node which the corresponding folders,
paths, heralds, and search subtree omit.

** Other relationships

Initial construction of the default =subscribeeFolder= also obtains its
members through the generic directional, relSource-gated accessor before
deciding whether the folder would be empty.  A private subscription between
two public nodes therefore creates neither a member nor an empty default
folder in a public-only view.  An explicitly requested writable folder may
still be created empty, as intended.

The other relationship-driven presentation paths do not have the same
problem:

- =contains= memberships are relSource-gated before recursive content is
  reconciled, including the contains-minus-hides treatment of a subscribee;
- =hides_from_its_subscriptions= and the containment memberships used to
  derive =hiddenHere= and hidden-outside folders are gated in both initial and
  reconciliation paths;
- ordinary relationship folders, paths, backpaths, herald counts, and
  ancestor heralds use the generic gated accessors for every stored
  node-to-node relationship;
- =textlinks_to= has no independently movable relationship source: it is
  derived from the source node's title and body, so its effective relSource is
  that node's home source.

Raw relationship reads in save, merge, deletion, and invariant-checking code
are intentionally full-graph operations rather than source-set presentation.

* Org export

Org export follows the stored, source-gated =contains= graph.  It does
not perform interactive override substitution.
