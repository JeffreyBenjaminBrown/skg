What the test checks, phase by phase. 'test-emacs.el' and
'test-nvim.lua' run the same phases, one per client; 'run-test.sh'
resets the five fixtures under 'data/owned/skg-data/', removes any
node a previous run created, and starts a server of its own.

* How the buffers are checked
Each check lists, for every headline that carries metadata, its
depth, its kind and its title ('assert-headline-types-and-titles' in
'../save_collateral_break_cycle/test-helpers.el', and its Lua port in
'test-nvim.lua'). A folder carries no title, so it is checked by
kind and depth. Viewnode IDs and the derived facts
vary from run to run and are not checked.

* Phases 1 and 2: buffer 1
Phase 1 opens the content view of node 1. Phase 2 asks for 11's
alias folder, appends a second root, subee with its child subee-1,
and saves, so that the server registers both roots. The appended
root is editable, so the save writes subee's content as the buffer
shows it; that is why subee-1 is typed in too. The check after the
save:

#+begin_example
  1 node "1"
  2 node "11"
  3 aliasFolder
  4 alias "eleven"
  3 subscribeeFolder
  4 node "subee"
  4 hiddenOutsideOfSubscribeeFolder
  5 node "also-hidden"
  1 node "subee"
  2 node "subee-1"
#+end_example

* Phase 3: buffer 2
A buffer written by hand: 11, write-protected, and subee with
subee-1, both roots. Its save registers it as a view and changes
nothing on disk. The check: the three headlines, as written.

* Phases 4 and 5: the delete
Phase 4 removes 'writeProtected' from 11 in buffer 2, adds
'(editRequest delete)', and saves. 11's file is deleted, and 1's
contents lose 11.

Phase 5 checks both buffers. In buffer 2, 11's root vanished:

#+begin_example
  1 node "subee"
  2 node "subee-1"
#+end_example

Buffer 1 is a collateral view of that save. The occurrence of 11
vanished, and with it everything that stood under it: its alias,
subscribee and hidden-outside folders and what they held
('docs/glossary.org', "vanish"):

#+begin_example
  1 node "1"
  1 node "subee"
  2 node "subee-1"
#+end_example

* Phases 6 and 7: an edit in the buffer the delete changed
Phase 6 adds a headline subee-2, with no metadata, as the last child
of buffer 1's root subee (now the only headline titled subee), and
saves buffer 1. The save creates subee-2 and
adds it to subee's contents. Phase 7 checks that buffer 1 shows it
under its root subee and is otherwise as in phase 5, and that buffer
2, rerendered as a collateral view, shows it too:

#+begin_example
  1 node "subee"
  2 node "subee-1"
  2 node "subee-2"
#+end_example

* Phases 8 and 9: the buffer round-trips
Phase 8 adds a root, new-root, after buffer 1's root subee and its
children, and saves. A root has no viewparent to inherit a skgrepo
from, so the headline carries '(skgRepos (nodeRepo main))'. Phase 9
checks that the save gave new-root an ID and kept the rest of the
buffer as it was: buffer 1 is as in phase 7, with
'1 node "new-root"' last.

* What it does not check
No phase edits where 11 stood: nothing stands there after the
delete.
