#+title: skg-for-ai: reading and writing the skg graph as plain files

* Start here
skg-for-ai lets you read and change a skg graph as plain Org files,
without an editor client. Everything below this page is reference;
this page is the whole working loop. Every command is
'python3 tools/skg-for-ai/skg_for_ai.py COMMAND ...', run against the
server whose port 'SKG_PORT' (or '--port') names. There is no default
port: a command that needs a server and is given none is refused.

First, start a daemon, and leave it running for the session:
'daemon --out-dir DIR &'. It keeps one connection to the server, so
the views you write stay current: when a save, a git-commit or a
teammate's change touches a node a view shows, it rewrites that
view's files, and it notes each such event in 'DIR/skg-for-ai.log'.
Every later command for that server runs through it, wherever it
writes. 'daemon --stop --out-dir DIR' ends it.

To read, view a node: 'view ID --out-dir DIR' writes 'view_ID.full.org'
(the view exactly as the server drew it), 'view_ID.compact.org' (the
same tree, each headline ending in a handle) and a sidecar,
'view_ID.view.json'. Read the compact file. Following a link is
'view' again on the link's ID; 'search WORDS' finds nodes.

A handle is '⟨ID HERALDS⟩'. ID names the headline, not its node; the
heralds are short codes, mostly counts of the notes related to it.
Take '⟨4w ☮B 1C9b 3/L ⌂:claude-public folded⟩': it is write-protected
here (☮) and has a body not shown here (B); one note contains it and
it contains nine, among them 'b', the headline two levels up (1C9b);
three notes link to it, all substantive (3/L); its home skgrepo is
'claude-public'; an editor would show it collapsed. Most common first:
- 'C', 'L', 'K', 'H': contains, links to, forks, hides. A count
  before the letter counts the notes that do it to this one, one after
  it those this one does it to: '2C3', two contain it, it contains
  three; 'C3', nothing contains it. Only a token that would read just
  'aC' (the parent alone contains it, the ordinary case) is left out.
- 'a', 'b', ...: a headline above, 'a' the parent, 'b' its parent,
  and so on; a folder is a headline, so under one 'a' is the folder.
  '2aC', two contain it, the parent one of them; 'Ca', it contains its
  parent; letters without a count are the whole side ('bdC').
- '/': the count before it is the part worth a look, and nothing
  after it means all. '3/7L', seven notes link to it, three of them
  substantive (with a body, content, or links to other notes too);
  '3/L', three, all substantive; '3L', none. On a member of a forks
  folder, 'C2/8', two of eight contents are new to you (neither the
  folder's note nor another of yours holds or hides them); 'C1/', all.
- '☮': write-protected here, whoever owns it (a teammate's note may
  be editable): it is editable elsewhere in the view, or stands under
  a '☮' folder, say. A save refuses an edit to it; 'editable' in its
  handle moves the editing here. 'B': view it to read its body.
  '⌂:REPO': its home skgrepo, on a root and where the voice differs
  from the node above. '⌂:<MINE/THEIRS>': a fork, in MINE, of a note
  of THEIRS; 'THEIRS?' means no loaded skgrepo is known to be the one
  recorded. No '⌂': it says what the node above says, attribution
  included. 'A2 I1 F1': two aliases, an extra ID, a true flag ('no
  search matching', say). 'Kĥ': it stands in the place of a note
  joined to it by forks; its parent contains that note, not this one.
A headline whose handle holds a sentence is a folder. 'These also
contain it.' and 'These link to it.' list notes, each with its own
containers under it, so there nesting reads upward. In 'Its mirrors
are these.', 'bK' marks a note the folder's note
forks, 'Kb' one that forks it. A member there whose title is the
folder's note's carries 'title=b'; one whose body is, 'body=b', and
its body is left out of the compact file: read b's (see "Restated
titles and bodies"). So a count before C beyond 'a' says
the note is filed elsewhere too ('contains ID'), one before L who
cites it ('links-here ID'), 'K' that it forks or is forked ('forest
forks ID'), '1H' that a note hides it, so that its forks folder no
longer shows it. That ID is the node's: the '(gnid ID)' on the line
that 'grep "(vnid 4w)"' finds in the full view. "The heralds in the
handle" explains the rarer heralds, and 'describe VIEW 4w' says in a
sentence each what this handle's heralds mean, its counts and letters
read out.

To change the graph, edit the compact file in place. Change a title
or a body by editing its text. Add a node by writing a new headline,
with no handle, where it belongs. A note that nothing contains is not
made that way: a headline typed without a handle at the top level of
a view, beside its root, is refused. Make it with 'new TITLE REPO',
REPO an owned skgrepo, which writes the new note's view to go on in.
Move a node by moving its line, handle and all, and its subtree with
it. Remove a headline to take
the node out of its parent; write 'delete' in its handle,
'⟨0d aC1 delete⟩', to delete the node itself. To put a node that
already exists here too, write a headline ending in '⟨node:ID⟩', ID
its ID; to fork a teammate's node, edit it where it is editable, and
the save asks before it forks ("Placing an existing node" and
"Forking"). Other words in a handle ask for the clients' other
gestures, 'write-protect', 'detach' or 'repo:NAME' among them ("Words
in a handle").

To mark a mailed item handled, 'receipt ITEM TEXT --yes' writes the
note TEXT under your fork of ITEM and hides ITEM from your fork of its
mailbox, in one write ("Read receipts").

Then save with the report: 'save DIR/view_ID.view.json' prints, line
by line, what the save would do, and changes nothing. Read it. For
each new node it names the parent, "New: 'TITLE', under ...": as in
Org, that is the nearest shallower headline above it, so a headline
appended to the end of the file joins whatever subtree is last there,
which may be a folder or a teammate's note. If the report
says what you meant, run it again with '--yes' to save; the files
are then rewritten with the server's new rendering. If it reports an
error or asks a question, answer it as it says and run it again.

One rule matters more than the rest: never retype a handled headline.
The handle is the only thing that ties a headline to its node. A
headline typed afresh, without the handle, is a new node with a new
ID, and the old node leaves its parent, taking with it the links to
it, its other relationships and its history, to a place the view no
longer shows. So move or reword a headline by editing or moving its
line, never by writing it again; if you must retype one, copy its
handle onto the new line. The save stops at a retyped title it
recognizes, and asks about one that resembles a removed one, but do
not count on it.

When a piece of work is done, review and commit it. 'diff --out-dir
DIR' writes the diff view: every change since the last git-commit,
each handle carrying its change facts. Fix anything wrong by editing
and saving, as above; write 'processed both' in the handles of the
changes you approve ('processed node' or 'processed rel' for one of
the two a headline shows) and save that buffer; then 'commit "MESSAGE"'
git-commits every node whose changes are all processed, except one
that needs a node whose changes are not, and prints what it left and
why. 'commit "MESSAGE" --all --yes' commits every change, marked or
not.

The rest of this file is reference: "Running it" (every command and
option), "The files it writes" (the compact view, every herald, the
summary), "The daemon", "Writing" (the report, the words a handle
takes, retyped headlines, placing and forking), "The skgrepo
restriction and overPrivateText", "Reviewing and committing" and
"What the tool covers of COMMANDS.org". The protocol is in
'docs/api-and-formats.org', and the diff view in 'docs/diff-view.org'.

* What it is for
A client such as Emacs shows a skg view as a tree of headlines, each
with a few short coloured heralds, and hides the long '(skg ...)'
metadata sexp that every headline carries. A program that reads the
same view as text, such as an AI agent, sees all of that metadata,
which outweighs the words. 'skg_for_ai.py' asks a running skg server
for a view and writes it twice: once exactly as the server rendered it,
and once compactly, with the words, the nesting and a short handle per
headline, which carries the heralds a client shows. Nothing is lost,
because each handle is the viewnode ID of the full view's headline,
whose metadata it stands for. An edited compact
view can be saved back: the tool rebuilds the full buffer from it and
saves that through the server (see "Writing"). The diff view, which
shows every change since the last git-commit, is written the same way,
and changes are marked processed and committed through it (see "Reviewing
and committing").

The tool is written for anyone, human or agent, who wants to use the
graph without an editor client. It is a client like any other: it
speaks the server's TCP protocol (see 'docs/api-and-formats.org'),
and like the editor clients it may save and import, which write
through the server to the skgrepos the config owns. It uses nothing
but the Python 3 standard library. It never touches '.skg' files
itself; only the server does.

Each command opens its own connection and closes it when done. A
daemon ('daemon --out-dir DIR') instead keeps one connection open, as
an editor session does: every command for its server runs through
it, and it keeps the files of the views they write current as the
graph changes; see "The daemon".

* Running it
** Commands
Each view command ('view', 'search', 'forest', 'contains',
'links-here', 'diff') writes three files per view into '--out-dir'
(default: the current directory) and prints their paths, one per line.

'python3 tools/skg-for-ai/skg_for_ai.py view ID' writes the recursive
content view of the node ID, as a client opens it. Through a daemon,
where ID is already a root of another view the daemon holds (one
switched to a perspective that put ID in its root's place, say), the
server sends no view, as a client lands in that view's buffer: 'view'
prints that view's paths instead, and says why on standard error.

'search TERMS...' writes the search buffer for the terms: each hit at
the top level, with the containers of each hit beneath it. Its
options are those of the clients' 'skg-search-interactive' ('C-c f
i'): '--regex' reads each term as a regular expression, matched
against the lowercased words ('fre.*'); '--body' searches the bodies
too; '--operators' keeps Tantivy's phrase and operator syntax (quotes,
AND, OR, +word, -word, grouping; 'docs/COMMANDS.org' says more). A
search with no match writes nothing and says so.

'forest KIND ID' writes the node's view with the folder KIND under it,
as the clients' 'C-c l' commands draw it ('docs/COMMANDS.org', "C-c
l"), named 'forest-KIND_ID'. Under each member of a partner folder
hangs its containerward chain: its containers, theirs, and so on up
to the roots; under a member of the forks folder, in a containers
folder of its own, folded (but the view-ancestors). The chain passes
through mirrors: a member, or a note of its chain, that forks or is
forked holds its forks folder first, each mirror there with its own
containers, and so on, a set of mirrors listed once per view; so
'forest containers' says where a note sits in anyone's version of it
('docs/mirrors.org', "Forests through mirrors"). The forks folder
is flat: no member of it shows a forks folder of its own unless one
is asked for there. The kinds:
| KIND          | Emacs   | what it draws                                                                    |
|---------------+---------+----------------------------------------------------------------------------------|
| containers    | C-c l c | the containers folder: what contains the node                                    |
| mentioners    | C-c l m | the mentioners folder: what links to it                                          |
| forks         | C-c l f | the forks folder: every mirror, what it forks, what forks it, then the rest      |
| hides         | C-c l h | the hidden folder (what it hides from its forks) and the hiders folder           |
| aliases       | C-c l a | the aliases folder                                                               |
| flags         | C-c l p | the flags folder: its true flags                                                 |
A write-protected folder (☮) is one whose membership cannot be
changed from there; an empty one is left out, an empty editable one
shown as a place to add members. A fresh content view already carries
the root's containers folder, so 'forest containers' is 'view' under
another name; every other kind is drawn by a save, as the clients do;
see "How 'forest' draws a folder". A view saved under the out
directory keeps the metadata the server drew it with: once the server
no longer knows an atom of it (a folder kind that has gone, say), a
save of that view is refused, and
the view must be fetched again.

'contains ID' is 'forest containers ID', and 'links-here ID' is
'forest mentioners ID', each named after itself ('contains_ID',
'links-here_ID').

'close SIDECAR' sends 'close view' for the view ID a sidecar records,
to the sidecar's server, and marks the sidecar closed. See "Views and
connections" for why it is needed only with a daemon.

'daemon --out-dir DIR' runs until stopped, taking every command for
its server, holding on one connection every view they write, and
rewriting a view's files when the server rerenders it; 'daemon --stop
--out-dir DIR' stops it. See "The daemon".

Following a link is just 'view' on the link's ID.

'diff' writes the diff view: each of its buffers that is not empty, as
a view, named 'diff_all-changes', 'diff_merges', 'diff_skgrepo-changes'
and 'diff_order-only-changes' ('--name BASE' replaces 'diff'). When
nothing changed it writes nothing and says so. See "Reviewing and
committing".

'save SIDECAR' saves an edited compact view; see "Writing".

'extend SIDECAR' extends a buffer of the diff view to the changes it
does not make editable, as the clients' 'C-c r u' does, and writes
the buffer again; see "Reviewing and committing".

'perspective SIDECAR' shows a view from the next perspective,
as the clients' 'skg-cycle-perspective'
('C-c v o' in Emacs) does, and writes the view again;
'perspective SIDECAR PERSPECTIVE' switches to the one named, by the
server's name: 'root homes', or 'skgrepo NAME' for any configured
skgrepo (the words may be given apart or quoted together).
Where a node stands as content and it has mirrors (notes joined to
it by forks, either way: 'docs/mirrors.org', "Mirrors"), the view may
show one of its mirrors in its place, marked 'ĥ' after its 'K'
('⟨0b Kĥ1⟩'). The perspective is one skgrepo, or the root homes, one
per tree; a skgrepo's list (it, then the config's declaration order)
ranks the mirrors: a fresh view
follows each tree's root's home skgrepo, the root homes (a view of
your note, your note's skgrepo; of a teammate's, theirs); the others
follow one skgrepo's in every tree, owned or foreign, whatever the
root's home, so you can choose, say, between a private and a public
fork of one note. The cycle holds the root homes, then each skgrepo
home to a mirror in the view whose perspective would show it
differently, in declaration order; the server computes it afresh at
each switch. It prints the server's name for the perspective,
'Showing the perspective of tracy.' or 'Showing the perspective of
each root's home skgrepo (tracy).', then the paths; the sidecar
records the perspective ('perspective' and 'perspective_name'), the
compact view's summary names it unless it is the root homes, and
every later save of the view names it, as the server needs, whoever
then rewrites the files. Like the clients, it refuses a compact view
with edits, which the switch's rerender would replace: save them
first. The server refuses a buffer of the diff view, 'next' where no
other perspective would show the view differently, and a named
perspective that would show it as the root homes do; the tool prints
its refusal and exits 1. The server
switches a view it holds: through a daemon that holds the view the
request goes on the daemon's connection; otherwise (no daemon, or one
started since the view was written) the tool first saves the full view
back unchanged, naming the choice it was drawn with, which writes
nothing and leaves the server holding it, as 'extend' does. Under a
skgrepo restriction the server may ask before the switched view
releases text from overPrivateText telescopes; '--show-overPrivateText'
approves.

'commit MESSAGE' git-commits, with MESSAGE, every node of the owned
skgrepos whose changes are all processed, except one that needs a node
whose changes are not; 'commit MESSAGE --all' commits every changed
node, asking first when not everything is processed, and '--yes'
(alone, or with '--all') commits everything without asking; see
"Reviewing and committing".

'new TITLE REPO' creates a root node titled TITLE whose home is the
owned skgrepo REPO, and writes its view as 'view' does (named
'view_ID' unless '--name' says otherwise), after printing the save's
answer and 'New node: ID'. A view needs a node to start from, so this
is how an empty skgrepo gets its first one. It saves a buffer holding
only that headline, as an editor client saves a new empty view
('skg-view-new-empty', 'C-c v e' in Emacs), with the empty baseline
of one, and refuses a skgrepo the
server's 'repos' request does not call owned. The new node's body and
children are then written through the view's edit-and-save loop.

'raw REQUEST' sends REQUEST, one sexp, as a request line, and prints
every response, each after a line '--- message N (CHARS chars) ---',
until the server has been quiet for three seconds. With
'--saved-buffer FILE' the request is a 'save buffer', and the tool
sends FILE's text as the saved buffer in the length-prefixed body
after it, then prints every response up to the save's terminal one.
The body also carries the saved buffer's baseline, the text the server
last drew for it: with '--baseline FILE', FILE's text; without it, the
empty baseline, a new empty view's.

'import INPUT_DIR REPO' imports the Markdown and Org files under
INPUT_DIR (a path the server can read) into the owned skgrepo REPO: it
asks for a preview and then applies it, on one connection, since the
server binds the preview's approval token to the connection that
asked. When the server asks for the host root of absolute links (the
input links to Markdown or Org files by absolute path), the tool
answers with '--host-root PATH', the absolute path of INPUT_DIR on the
host whose paths the links name; without it, with the empty one, which
leaves those links unresolved. '--preview-only' cancels instead of
applying. It prints the responses as 'raw' does.

'delete-references ID' removes every owned structured reference to
the node ID, which the graph must lack: ID leaves every 'contains',
'forks' and 'hides' list of the owned
skgrepos that names it, as the clients'
'skg-delete-references-to-absent-node' ('C-c d a', on an unknown
viewnode) does; links in titles and bodies stay. Without '--yes' it
sends nothing. With it, when titles or bodies link to ID, the server
first shows what it would remove and the links it leaves, and the tool
prints that and stops; '--yes --leave-links' approves it. It prints
the server's report. It needs a connection with no skgrepo
restriction, and, like the clients, refuses while a view the daemon
holds has unsaved edits; the daemon rewrites the views that showed a
removed reference.

'receipt ITEM TEXT' writes a read receipt, as the Emacs command
'skg-receipt' ('C-c m a') does; see "Read receipts" under
"Writing".

'restrict' prints the connection's skgrepo restriction and the rungs
it may take, as the clients' 'skg-list-repo-sets' does: 'Skgrepo
restriction: main; available: main, private (no restriction).'.
'restrict NAME' sets it, as their 'skg-restrict-repo-set' ('C-c v l')
does: NAME is the most private owned skgrepo to show;
'--foreign hidden' (or 'shown') hides (or shows) the foreign
skgrepos, apart from the rung. The most private owned skgrepo with the
foreign skgrepos shown is no restriction. The restriction belongs to a
connection, and a command's own connection ends with it, so setting it
needs a daemon: run through one, it sets the daemon's, which every
command run through that daemon then has, and the server rerenders the
views the daemon holds under it, which the daemon rewrites. It is
refused while a held view has unsaved edits, as the clients refuse
it. See "The skgrepo restriction and overPrivateText".

'linkstack ACTION' keeps the clients' linkstack in a file,
'skg-for-ai.linkstack.org' in '--out-dir', which reads as their
'skg-view-linkstack' ('C-c v s') shows it: a headline per entry, its
label the title and its ID the body, the top first; it may be edited
by hand. 'linkstack push ID' ('C-c u') pushes the node ID with its
title, which it asks the server for; 'linkstack push
"[[id:ID][LABEL]]"' pushes the link's ID and label. 'linkstack show'
prints the stack. 'linkstack paste id', 'paste link' and 'paste node'
('C-c o i', 'o l', 'o n') print, from the top entry, its ID, a link
'[[id:ID][LABEL]]', or the text of a headline placing the node,
'LABEL ⟨node:ID⟩' (see "Placing an existing node"); 'linkstack pop
id', 'pop link' and 'pop node' ('C-c O i', 'O l', 'O n') print the
same and remove the entry. The tool has no cursor, so pasting is
writing what it prints into a compact view.

'chain VIEW HANDLE' prints the chain of the headline HANDLE in VIEW
(its sidecar, full or compact view, or a folder holding one view):
a link to each note from the view's top-level one down to it,
folders skipped, joined by the graph edge its metadata records
between each note and the next, as the clients' 'skg-push-ancestry'
('C-c U') pushes it and 'C-c o l' pastes it: '/' contains, '\'
is contained by, '~' forks or is forked by, '->' links to, '<-' is
linked to by, 'hides', 'is hidden by'. So '[[id:A][a]] / [[id:B][b]] ~
[[id:C][c]]' says a contains b, and c is a fork partner of b, in b's
forks folder. The edge is the relation that put the note there (its
'(birth ...)'), else the first of contains, forks, links to and hides
whose '(rels ...)' names the note above among its ancestors. Where no
edge joins a note to the one above (an indirect member of a forks
folder, say), it refuses, naming both. It needs no server, and keeps
no stack: write what it prints where the chain is wanted.

'describe VIEW HANDLE' prints, a sentence a line, what the headline
HANDLE in VIEW is, when it is a folder, and what each of its heralds
means, the most informative first, with its own counts, ancestor
letters and skgrepos read out: '2/5L: 5 notes link to this one; 2 of
them are substantive (...)'. These are the sentences the clients'
'skg-describe-at-point' ('C-c v ?') shows; the server the view's
sidecar names writes them ('docs/api-and-formats.org', "Describe
heralds"), from the headline's metadata in the full view.

Options, after the command: '--port N' for every command ('save',
'extend', 'close' and 'perspective' require the sidecar's; a
command run through a daemon's folder talks to the daemon's server
unless it names one);
'--yes' for
'save', 'commit', 'delete-references' and 'receipt'; '--keep-ids' or '--all-new'
for 'save' (see "Retyped headlines"); '--fork-into REPO' for 'save'
(see "Forking") and 'receipt'; '--title TITLE', '--mailbox ID' and
'--no-hide' for 'receipt' (see "Read receipts"); '--hoist', '--delete-from visible|all' and
'--strandeds reset|keep' for 'save', answering the server's questions
(see "The server's answer"); '--show-overPrivateText' for the view
commands, 'save', 'restrict' and 'perspective' (see "The skgrepo
restriction and overPrivateText"); '--regex', '--body' and '--operators' for
'search'; '--host-root PATH' for 'import'; '--leave-links' for
'delete-references'; '--foreign shown|hidden' for 'restrict'; for the
view commands also '--out-dir DIR', '--name BASE' to name the files
'BASE.full.org' and so on instead of 'COMMAND_ARGUMENT', and
'--no-summary' to leave the summary out of the compact view;
'--out-dir DIR' for 'linkstack' (its file's folder), and for
'delete-references', 'receipt' and 'restrict' (the folder whose daemon to run
through).
Every command that writes a view fetches the server's herald rule
table once, with the 'herald rules' request.
** The port
The tool connects to 127.0.0.1 on the port '--port' names, else on the
one 'SKG_PORT' names. The port of a server is the 'port' of its
'skgconfig.toml'.

There is no default port. There was one, 1730, and it was a live
user's own server: a command whose shell had lost its 'SKG_PORT' (an
agent's shell starts fresh on every call) wrote to that server, and
'commit --all --yes' git-committed his unfinished changes. So a
command that needs a server and is given no port, by '--port',
'SKG_PORT', its sidecar ('save', 'extend', 'close',
'perspective') or a daemon answering in its '--out-dir'
folder, is refused before it connects to anything: it prints one line
saying to name the server with '--port PORT' or 'SKG_PORT', and exits
1. 'daemon' needs a port too. Commands that need no server run
without one: 'linkstack' but 'push', 'chain', 'daemon --stop', and
'delete-references' without '--yes'.

* The files it writes
For a base name such as 'view_ID' the tool writes 'view_ID.full.org',
'view_ID.compact.org' and 'view_ID.view.json'.
** The full view
'BASE.full.org' is the view's text exactly as the server sent it,
metadata and all. It is what a client receives, before heralds hide
the metadata. It is also the view's baseline, the text the server last
drew for it, which every save of the view sends beside the edited
buffer ('docs/api-and-formats.org', "Save buffer").
** The compact view
'BASE.compact.org' has every line of the full view, in the same order,
but the body of a forks-folder member that restates its note's (see
"Restated titles and bodies").
A body line is copied unchanged, except that its links are annotated.
A headline keeps its stars and its title; its '(skg ...)' metadata is
removed, and a handle is added at the end of the line.
*** The handle: the headline's viewnode ID
A handle has the fixed form '⟨ID ...⟩'. ID is the headline's viewnode
ID, the '(vnid ID)' that opens its metadata in the full view: the
server gives one to every headline of a view, and keeps it across that
view's saves ('docs/api-and-formats.org', "The metadata headers").
'grep -n "(vnid ID)" BASE.full.org' finds the headline's metadata, and
the pattern '⟨[0-9a-z]+' finds every handle. A headline that is moved
keeps its handle, so a tool can tell a move from a deletion, and a
headline without a handle is a new one. Body lines have no handle: a
body line belongs to the nearest headline above it. Since a handle's
brackets end a headline, 'save' refuses, before sending anything, a
new headline whose title holds '⟨' or '⟩', and a title edited to hold
one, naming the headline; a title that already held one is left as
it is.
*** The heralds in the handle
After ID come the headline's heralds: every herald a client shows,
in the order it shows them, as plain text, without their styles. A
client renders them from the server's herald rule table, which the
tool fetches too ('docs/heralds.org' explains each). So a node reads
'⟨0d ☮B 1Cb ⟳ M ~+⟩': write-protected (☮), its body omitted (B), its
relationship heralds, a cycle (⟳), then its change facts. A headline
that is not a node occurrence shows its label: a folder its sentence,
'⟨0b ☮ These also contain it.⟩'; an alias 'alias', a flag row '☮ had ID
before import', a tombstone 'something stood here', an unknown
viewnode 'Reference to unknown node.'; a folder has no title, so in a
compact view it is its stars and its handle. An illegal edit to a
foreign node, a section of it in one of your skgrepos, is a folder
labelled '☮ ILLEGAL EDIT TO FOREIGN NODE'. On a node, in the order a
client shows them, the heralds are:
- the position glyphs: 'ᗣ' a ghost, or what HEAD alone warrants;
  '⊥' an unwarranted position; '☮' write-protected, and 'B' riding it
  when the node's body is omitted from the view;
- the relationship heralds (see below), then '⟳', a cycle;
- '~NAME', its relationship to its parent recorded in a skgrepo more
  private than the default, then '⌂:LABEL', the home skgrepo boundary
  (see below);
- the change facts, in the diff view (see below);
- pending requests, which a view the server rendered never shows,
  since a save consumes every request: 'delete', 'detach' (a
  'noClaim' child that leaves an editable parent at the next save),
  'req:...' view requests, 'request:...'.
*** The relationship heralds
The relationship heralds are rendered as the clients render them;
'docs/heralds.org', "Relationship heralds", explains them. In display
order: 'C' contains, 'L' links to, 'K' forks (the K of forK; 'F' is
the flags count), 'H' hides (the hider keeps the hidden node out of
what it shows of the members of its forks folder). A count before a
letter counts the nodes on the relation's in-side ("two nodes contain
this"), a count after it the out-side ("this contains three").
Missing sides and empty relations are left out.

A lowercase letter is an ancestor in this view: 'a' the viewparent,
'b' the grandparent, and so on, each headline above counting as one
generation, a folder included (after 'z', '{27}' and so on). Under a
folder, then, 'a' is the folder and 'b' the node whose folder it is.
Letters replace the count when ancestors make up the whole side, and
follow it when they do not: '2aC' is two containers, the viewparent
one of them; 'Kb', it forks the grandparent and nothing else; 'K2b',
it forks the grandparent and one more. In a forks folder the
grandparent is the note whose folder it is, so a forkee shows 'bK', a
note that forks it 'Kb', a mutual 'bKb', and an indirect member,
joined to it only through other forks, neither 'b'.

A fraction marks a subset, on two sides. Before 'L' the numerator
counts the substantive mentioners: those with a nonblank body, a
visible content, or links to more than one distinct visible target
('mentioner_is_substantive' in 'server/dbs/in_rust_graph/stats.rs').
'1/5L', five nodes link here and one of them is substantive. After
'C', on a member of a forks folder, the numerator counts what the
member shows, its unintegrated content: its contents that the
folder's note neither contains nor hides, and that no owned note but
the member contains ('docs/glossary.org', "what a member shows"); in
the diff view, it counts those an owned note contains too. 'C2/8',
eight contents, two of them unintegrated. A numerator equal to the
whole side drops the denominator: '5/L', five mentioners, all
substantive; 'C1/', one content, unintegrated. A numerator of none
drops the slash: '5L', no mentioner substantive; 'C8', nothing
unintegrated. An ancestor stands once, before the slash
if it is in the subset ('2b/L3'). 'ĥ' after 'K' says this occurrence
stands in the place of one of its mirrors, a node joined to it by
forks, which its parent's list names ('docs/mirrors.org', "The
inPlaceOf part"). The property counts 'A' (aliases), 'I' (extra IDs)
and 'F' (true flags) follow. So '⟨0h 2aC3⟩' has two containers, one
of them the viewparent, and three contents.

One token is left out: a bare 'aC', which says only that the
viewparent contains the node and nothing else does. That is the
ordinary case in a content tree, so most handles would carry it;
'⟨0c aC L1⟩' is written '⟨0c L1⟩', and '⟨0e aC⟩' just '⟨0e⟩'. Every
other form, 'aC10' or '2aC' among them, stays.
*** The skgrepo boundary
A headline whose home skgrepo herald would say something other than
what its nearest node occurrence above it says, or a root, carries
'⌂:LABEL' after its relationship heralds, LABEL the skgrepo's label
from the table the server sends beside its herald rules: '⟨0h ☮ C1
1/L bK ⌂:fred⟩' is a note of the 'fred' skgrepo under a node of
another. A fork that records where it was forked from (an
attribution, see "Forking") says '⌂:<MINE/THEIRS>': its home
skgrepo's label, then the label of the skgrepo it was forked from, or
that skgrepo's recorded name followed by '?' when no loaded skgrepo is
known to be it. The whole herald is compared, so under
'⌂:<MINE/THEIRS>' a plain note of MINE says '⌂:MINE' (the voice is
MINE again), and only a fork from the same THEIRS says nothing. A
headline without '⌂' speaks in the same voice as the node above it.
*** Change facts, in the diff view
A headline of the diff view that shows a change carries, after the
skgrepo boundary, the change facts the clients show ('docs/heralds.org',
"Diff heralds"). On a node or a ghost (a deleted node, shown as HEAD
has it, 'ᗣ☮'): '∃+' a new node, '∃-' a deleted one, 'M' a modified one
(its title, body, properties or lists changed), then '~+' a new
membership in its parent (in a partner folder, its relationship of
the folder's kind to the folder's parent), '~-' a removed one. On an
alias, ID or flag in its folder, '+' or '-'; on an unknown viewnode,
'~+' or '~-'. A '✓' right after a change says it is marked processed:
'∃+✓ ~+' is a new node, approved, in a membership that is not. The
headlines the diff view adds to explain a change show their labels:
'old title' (or 'old body', 'old title and body') and 'body diff',
'its content changed' (a changeset marker), '⌂ -OLD +NEW' (a move to
another skgrepo), 'relationship moved from OLD to NEW', and a node's
other changes in words ('its content was reordered', 'its attribution
changed', joined by '; '); each takes a '✓' when processed. A folder shown because a member's relationship to
the folder's parent changed reads 'its other containers changed (other
files)' and so on, with '✓' when every such change is processed. In the
skgrepo-changes buffer a moved node adds '-OLD +NEW', and 'Δ⌂=a' when
its nearest moved ancestor (here the parent) moved the same way.
*** Restated titles and bodies
A member of a forks folder often says what the folder's note says.
Where its title equals the note's, its handle carries 'title=b'; where
its nonblank body does, 'body=b', and the compact file leaves its body
out: it is b's, the body under the headline two levels up ('b' is the
note's ancestor letter as counted from the member). The full file has
every body. The clients draw the same members with "<b's title,
unchanged>" and "<b's body, unchanged>" over the text
('elisp/skg-fork-dedup.el'). A save of a headline that still says
'body=b' and has no body under it sends the body the full file gave
it, unchanged; text written under it is its new body; to empty the
body, take the word away. The words are the tool's: a save sends
neither, and 'title=b' changes nothing (the title is there to edit).
*** Folded headlines
A headline the server marks 'folded', one a client shows collapsed,
ends its handle with the word 'folded': '⟨0j ☮ cH ⌂:fred folded⟩'.
The lines under it are still in both files; the word tells where a
person reading in a client would see less. It is the tool's; a client
shows no herald for it.
*** How the tool renders them
The tool applies the rule table the server serves ('herald rules',
fetched once per command) to each headline's metadata, as the clients'
lens does ('nvim/lua/skg/sexpr/lens.lua', the port of
'elisp/skg-sexpr/skg-lens.el'), and renders the relationship heralds
from the '(view (rels ...) (props ...) (birth ...))' facts, as
'render_rel_facts' in 'nvim/lua/skg/heralds.lua' does, reading
'shared/relations.json' for the letters and their order. What one
headline's metadata cannot say it reads from the headlines around it,
as a client reads its buffer: a pending detachment from the parent
and grandparent, a changed folder from its members
('shared/herald-styles.json' gives the folder labels and which
folders are write-protected).
*** Link annotations
Every '[[id:ID][label]]' link, in a title or a body, is followed by an
annotation in a fixed form. A link whose target resolves gets '⟦→ TITLE
⌂:LABEL⟧', the target's title and its home skgrepo's label. A link
whose target this server holds no node of gets '⟦not held here⟧': the
node may have been deleted, may never have been written, or may be in
a skgrepo this server does not load, so it need not be a broken link.
A link whose target the skgrepo restriction hides gets
'⟦✗ restricted⟧', and one whose status the server did not give back
gets '⟦✗ lookup failed⟧'. The tool asks the server's 'link statuses'
request, which the clients' link annotations use, and then 'titles by
ids' for the titles of the resolved targets. The annotation is the
tool's; the link itself is unchanged. A '⟦' or
'⟧' in the title or label an annotation quotes is written '⦗' or '⦘',
so that the annotation ends at its own '⟧' and a save removes exactly
it; the annotation is never saved, so the node's title is unchanged.
*** The summary
Unless '--no-summary' is given, the compact view starts with a few Org
comment lines ('# ...') before the tree. They name the full view and
the view ID, say what a handle holds and that "Start here" explains
the heralds, then count, from the same metadata: the headlines, node
occurrences, distinct nodes, folders and other kinds; the node
occurrences in each skgrepo, owned or foreign; the occurrences in
foreign skgrepos, the write-protected and the folded headlines; those
contained elsewhere too (a 'contains' in-side larger than its ancestor
flags, so a container not above it in this view); those forked
("forked N") and those forking ("forking M"); the links, their distinct targets, and how many
of those resolve; and the server's errors and warnings, which the
sidecar lists. A view shown from a perspective other than its root homes
('perspective') names it on the line after the first,
'# Showing the perspective of tracy (each root's home skgrepo is the
default).'; a view shown from the default has no such line.

Whether a skgrepo is owned or foreign comes from the server's 'repos'
request, which lists every configured skgrepo.
*** The ancestry
A view does not summarize the root's ancestry: the containers folder
that the server draws as the root's first child in a fresh content
view (and under each search hit) holds it, each container with its
own containers nested beneath it, so each chain upward reads as a path
of nested headlines. 'contains ID' gives the same view of any node,
to read its ancestry the same way. The folder is absent when nothing
contains the root.

A buffer of the diff view opens its summary with two more lines: the
processed summary the server sends, in nodes, the unit 'commit'
takes ("1 of 4 changed nodes are processed", with how many of those
would wait, how many changes this buffer cannot edit and how many
nodes changed in foreign skgrepos), and how many headlines show a
change, processed and not.
** The sidecar
'BASE.view.json' records the view ID, the command and its request (for
a buffer of the diff view, the buffer's name), the view's perspective
('perspective': "root homes", a
fresh view's, or "skgrepo NAME", after 'perspective'; a sidecar
holding an older name, "user", "owner of NAME" or "root authors",
is read as the root homes; and 'perspective_name', the server's
name for it), the port, the two files' names, the server's errors and warnings, whether
the compact view has a summary, and whether the view is closed: it
is closed unless a daemon holds it (see "The daemon"). 'save' sends
the edited view against this view ID, with the full view as its
baseline, to this port, naming the perspective, '(perspective . "skgrepo main")' say, when
the sidecar's is not the root homes,
and renders the summary again when there was one. A save, a daemon's
rewrite of the files and the daemon's stop keep 'perspective';
a view written afresh into the same files has the default. A sidecar
without it follows the root homes.

* Views and connections
The server keeps a view's state per TCP connection, and forgets every
view of a connection when it ends. Without a daemon, each command
opens one connection, and sends 'close view' for its view before
disconnecting, as a client does when its buffer is killed. A view is
therefore never left open by the command. A save reads the saved
buffer against the graph; the server does not hold its view, and
keeps every handle the buffer carries (see "Handles across saves"). A
save of a buffer of the diff view names its buffer
('(diff-view-buffer . "all changes")', say), so the server re-renders
it as that buffer, with its processed summary. The 'close' command
matters only for a view that a longer-lived connection holds: a
daemon's.

Between its answers, the server may tell a connection that it
reloaded '.skg' files that changed on disk (a teammate's save, a
'git pull'). A command on its own connection prints, on standard
error, a line per skgrepo, as 'skg server: reloaded N files from repo
NAME', and each warning (a file that could not be read, say), as
'skg server: WARNING', and reads on; a view written before it may be
refused on save if it would write a node that changed. A daemon
instead rewrites the views it names and logs the counts and warnings.

* The skgrepo restriction and overPrivateText
A connection starts with the skgrepo restriction the config's
'default_repo_set' names, or none; 'restrict' prints it. Under a
restriction a view, a search and a save show only what the skgrepos
it shows hold (see 'docs/api-and-formats.org', "skgrepo-sets"), the
diff view and a commit are refused, and so are 'delete-references'
and the processed and restore words. A daemon's connection keeps a
restriction 'restrict NAME' sets, for every command run through it;
without a daemon, each command has the config's.

A telescope whose title or body sits below its home has
overPrivateText ('docs/glossary.org'). Under a restriction the server
asks before it releases such text: before a view ('view', 'forest'
and the others), a save's re-rendered view, the rerender of the
held views a new restriction asks for, or that of a view switched by
'perspective', it names the telescopes and
withholds the text. '--show-overPrivateText' approves, and the tool
sends the request again with their IDs (for a save, it asks for the
withheld rerender instead; see "The server's answer"); without it, the tool prints
the question on standard error and writes nothing (a save has then
happened; see "The server's answer"). A search asks whether to
include such telescopes: without the option it excludes them, saying
so on standard error, and with it includes them. With no restriction
the text is shown, and the answer carries a warning. The approval is
for that request only, and does not approve Hoist.

* The daemon
** Why
A command's connection ends with the command, and with it everything
the server would have said to it later. The server rerenders a view
only on the connection that holds it: after a save on that
connection, of any view that shows a node the save changed, and when
it reloads '.skg' files that changed on disk (a teammate's save on
their own server, a 'git pull'), of the views showing a changed node.
It tells only connected clients its warnings. Files written by a
command therefore go stale silently, and nobody hears the warnings.

The daemon is a client that stays connected, as an editor session
does. Every command for its server runs through it; it holds every
view they write, wherever they write it, rewrites a view's files when
the server rerenders it, and logs what happened and why. Nothing
changes for a reader who never starts one.
** Starting and stopping
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py daemon --out-dir DIR --port P &
# ... view, edit, save with '--out-dir DIR' as usual ...
python3 tools/skg-for-ai/skg_for_ai.py daemon --stop --out-dir DIR
#+end_example
The daemon connects to the server ('--port', else 'SKG_PORT'; with
neither it refuses to start, as there is no default port), logs the
server's startup warnings, listens on two Unix sockets,
'DIR/skg-for-ai.sock' and the port's,
'skg-for-ai-PORT.sock' in 'XDG_RUNTIME_DIR' (or in '/tmp' when that
is unset), and prints one line saying so; it runs in the foreground
until stopped. DIR holds its log and its socket; the views it holds
may be anywhere. 'daemon --stop --out-dir DIR', SIGTERM and SIGINT
each stop it: it closes every view it holds (each sidecar then says
'closed'), its connection and its sockets, and exits. A stop signal
is noticed between commands, not during one.

One daemon runs per folder and one per port: starting a second where
one answers, in the same folder or for the same port, is refused,
naming the running one's process, folder and port. A daemon that was
killed outright leaves its sockets behind; commands then run on their
own connections, and the next daemon started there removes each and
makes its own. A daemon whose server goes away (stops, restarts, is
rebuilt) logs it and stops, since the server has forgotten its views.
** Commands run through it
While a daemon runs for a port, every command for that port runs
through it, whatever folder it writes into: a view command ('view',
'search', 'forest', 'contains', 'links-here', 'diff', 'new'), and
'save', 'extend', 'close' and 'perspective', whose port is their
sidecar's, and
'commit', but for 'commit --all' without '--yes'. A command's port is the one its '--port' or
'SKG_PORT' names, or the sidecar's. A command that names no port and
has no sidecar runs through the daemon of its '--out-dir', if one
runs there, on that daemon's server; otherwise it is refused, as
there is no default port ("The port"). The command sends its command
line, its current directory and the port it named over the socket; the daemon
runs it exactly as the command would run, but on the daemon's
connection, writing its files where the command asked, and answers
with what it printed and its exit code, which the command prints and
exits with. So the output and the files are those of the command run
without a daemon, but for the sidecar's 'closed', which is false
while the daemon holds the view.

The daemon runs one command at a time; the others wait their turn.
Between commands it reads what the server sends unprompted; what
arrives while a command waits for its answer is handled after that
command.

'restrict' and 'delete-references' run through it too: the first
sets the restriction of the daemon's connection, which then holds for
every command it runs. 'raw', 'import' and 'linkstack' always run on
their own connection: 'raw' speaks the protocol directly, 'import'
binds its approval to a connection of its own, and 'linkstack' keeps
a file. So does a 'commit --all' without '--yes', since the
typed "yes" it may ask for cannot cross the socket; once it has
committed, it asks the daemon for its port to rerender the buffers
of the diff view it holds, which the server rerenders after a
git-commit only on the committing connection.
** What happens to the views
Every view a command run through the daemon writes stays open on the
daemon's connection, in whatever folder its files are. A save of one is the ordinary case for the
server: a save of a view the connection holds, the case of an editor's
buffer. The rules for a view the server does not hold (the handles
taken from the buffer, the diff-view buffer named in the request; see
"Handles across saves") are not needed. The tool still names the
buffer of the diff view in a save; the server keeps the kind a held
view was registered with, so this changes nothing, and a command
behaves the same with or without a daemon. 'extend' still saves the
full view back unchanged before it extends, which writes nothing.

When the server rerenders a held view, the daemon writes the
rerendered view over its three files, as 'save' does, and logs it.
The server rerenders a held view
- after a save on the daemon's connection (a command run through it)
  that changes a node the view shows: a collateral rerender, which
  arrives with the save's answer, and which the daemon writes before
  the command returns;
- after a git-commit on the daemon's connection ('commit', or
  'commit --yes'), and of the buffers of the diff view after one on
  another ('commit --all' without '--yes', which then asks the daemon);
- after it reloads files that changed on disk, of which it tells
  the connection with a 'repo-files-reloaded' message naming the
  views that show a changed node (and every buffer of the diff view):
  the daemon then asks for their rerender, as the clients do ('Repo
  files reloaded' in 'docs/api-and-formats.org'), and the server
  extends each buffer of the diff view so rerendered to the changes
  it did not show, as 'extend' would.
A rewritten buffer of the diff view has no processed summary, since a
rerender carries none; its next save, or 'diff', gives one.

A compact view with unsaved edits (anything 'save' would report) is
never overwritten. The daemon does not ask for its rerender, keeps its
files as they are, and logs 'kept BASE'. Its save is then refused if
it would write a node that changed since it was rendered; view the
node again under another '--name' to see the change, and redo the edit
there.

Every save through the daemon tells the server about the other views
it holds, as the clients name their other buffers in a save's
'other-views': each held view, and for one whose compact view has
unsaved edits, the full view as its clean text and the buffer its own
save would send as its current one. The server refuses a save that
would change a node such a view shows, naming the view ("this save
conflicts with unsaved dependencies in content-view:ID"); save or undo
that view's edits first. A held view whose handles are in error has
no such buffer, so a save beside it is refused until it is fixed or
closed. A switch of the restriction and 'delete-references' are
likewise refused while a held view has unsaved edits, as the clients
refuse them, since their rerender would replace it.

'restrict' logs the new restriction ('Skgrepo restriction: main'),
and the rerender of each held view under it, as for any rerender of
a command; 'delete-references' logs 'removed the references to ID'.

A view ID names one view per connection, and a held view one set of
files. 'view ID' and 'forest KIND ID' share the view ID
'content-view:ID', so the later of them holds it, and the earlier
files are released: their sidecar says 'closed', the daemon no longer
rewrites them, and a save of them runs on its own connection. Viewing
a node again into the same files replaces the held view with a fresh
one, and a new 'diff' replaces the buffers written under the same
names. 'close SIDECAR' releases one view.
** What it does not see
A save on another connection to the same server (an editor on that
server, or a command that reached no daemon: an 'import', or one run
while the daemon was down) writes files the server knows as its own,
so no message reaches the daemon, and the views it holds that show
those nodes go stale; a save of one is then refused if it would write
a node that changed. Commands for the daemon's port run through it,
so this happens only with another client on the same server. A
change on disk by anything else, another server's save or a 'git
pull', reaches it.
** The log
'DIR/skg-for-ai.log' is appended to, one line per event, each starting
with the local time ('2026-11-01 21:34:33'); a message of several
lines is joined into one with ' | '. The events:
- 'started: process N, server port P', with '; replaced the socket a
  dead daemon left at PATH' for each it replaced; 'stopped: released
  N views'.
- 'holding BASE (view ID ID)' when a command writes a view;
  'released BASE: its view ID now shows OTHER'; 'closed BASE'. BASE
  is the files' base name in the daemon's folder, and their folder's
  real path joined to it elsewhere ('/home/me/notes/view_ID').
- 'saved BASE', 'saved new root TITLE', 'extended BASE', for the
  commands that write to the graph; 'perspective of BASE: NAME' (the
  server's name for it, 'the perspective of main', say) for
  'perspective'.
- 're-rendered BASE because CAUSE; CHANGES': the daemon rewrote a
  view's files. CAUSE is "of 'COMMAND' on the daemon's connection" for
  a collateral rerender or one after a 'commit' through the daemon,
  "of a git-commit on another connection" after a 'commit --all'
  without '--yes', or "files
  changed on disk (COUNTS; WARNINGS)" with the server's notice. CHANGES compares the old full view with the new,
  node by node, by title: "new 'T'", "gone 'T'", "'T' changed: title,
  was 'OLD', body, metadata" (the metadata holds its relationships,
  among other facts), the first six and a count of the rest, or "no
  node changed".
- 'kept BASE: ...', a rerender not written over unsaved edits.
- 'changed on disk: reloaded N files from repo NAME; ...' when the
  server reloaded files that changed on disk.
- 'warning: TEXT' for every warning the server sends the connection:
  its startup warnings, each reload's (a file that could not be read,
  a batch that failed validation, a telescope that leaks text), and
  those of every save and rerender on the connection.
- 'error: ...': a command that failed, with its message; a message the
  server sent unasked that the daemon does not know; the connection
  lost.
For instance:
#+begin_example
2026-11-01 21:34:13 saved view_child-a-id
2026-11-01 21:34:13 re-rendered view_root-id because of 'save view_child-a-id.view.json --yes' on the daemon's connection; 'First child, renamed via daemon' changed: title, was 'First child'
2026-11-01 21:34:32 changed on disk: reloaded 1 file from repo main
2026-11-01 21:34:33 re-rendered view_child-a-id because files changed on disk (reloaded 1 file from repo main); 'First child, renamed on the other server' changed: title, was 'First child, renamed via daemon'
#+end_example
The log is how a reader who was elsewhere learns that the graph moved:
anything that wants waking when it does can follow the file
('tail -f').

* How 'forest' draws a folder
The server has no request that answers "what links here" or "what
forks this". The clients ask for a folder by saving the view
with a view request on the node's headline, '(viewRequests (folder
mentioners))' for 'C-c l m' in Emacs, or '(viewRequests flags)' for
'C-c l p', and the re-rendered buffer the save returns shows the
folder. The tool does the same: it opens the view, adds the kind's
request to the root's metadata, and saves the otherwise unchanged
buffer; 'forest containers' alone needs no save. The tool may save,
as any client may. Since nothing in
the buffer differs from the graph, the save writes no file, but it is
a save, sent through the server's whole save path, so a node that the
server would refuse or ask about on save (a foreign node edited, for
instance) can make it fail or ask a question the tool does not
answer. The tool then reports the server's answer and writes nothing.

* Running a scratch server for it
To try the tool without touching real data, run a second server on a
scratch data root, as the 'verify' skill ('.claude/skills/verify/')
describes. In short: copy 'tools/skg-for-ai/test-fixture/' somewhere
(the server writes its search index and some generated files into the

* Writing
** The loop
To change the graph, edit the compact view in place and save it:
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py view ID --out-dir DIR
# edit DIR/view_ID.compact.org
python3 tools/skg-for-ai/skg_for_ai.py save DIR/view_ID.view.json
# read the report
python3 tools/skg-for-ai/skg_for_ai.py save DIR/view_ID.view.json --yes
#+end_example
'save' takes the sidecar, the compact or full view beside it (it then
uses the sidecar of the same name), or a directory holding only one
sidecar. Without
'--yes' it prints the report and stops; with it, it prints the report,
sends the save, prints the server's answer, and writes the server's
re-rendered view over the three files, so the next edit starts from
them. A headline the edit kept keeps its handle (see "Handles across
saves"), and a new one has a handle now. A save needs the server the
view came from; '--port', if given, must match the sidecar's.

The tool writes nothing to '.skg' files itself. The server's save does,
with every check an editor client's save gets, and it writes only to
skgrepos the server's config owns.
** How the compact view becomes a buffer
The tool rebuilds the buffer an editor client would send, from the
edited compact view and the full view it was written beside. A
headline with a handle '⟨ID ...⟩' gets back the metadata of the full
view's headline whose viewnode ID is ID; its level, title and
position come from the edited compact view. The rest of the handle
(the heralds, 'folded') is display only, and editing it changes
nothing, except for the words that ask for something: 'delete' (see
"A deleted node"), 'processed' and 'unprocessed' with 'node', 'rel'
or 'both' and perhaps 'outward', 'restoreNode' and 'restoreRel' (see
"Reviewing and committing"), 'editable' and 'fork'
(see "Forking"), and those of "Words in a handle": 'merge:ID',
'relRepo:NAME', 'noSearchMatching', 'searchMatching',
'write-protect', 'detach', 'attach', 'repo:NAME' and 'subtree'. No
herald of a view the server rendered is one of these words, since a
save consumes every request; so each such word in a handle was
written there. The rebuild writes the edit requests into the
headline's '(editRequest ...)', which holds one ('delete',
'restoreNode', 'restoreRel', '(merge ID)', '(relRepo NAME)' or
'(flag noSearchMatching true|false)') and one processed request
after it; the view requests into its '(viewRequests ...)', as
'editableView', 'fork', 'writeProtectedView' or
'writeProtectedSubtreeView'; 'detach' and 'attach' as the atom
'noClaim', written or removed; and 'repo:NAME' into its '(skgRepos
(nodeRepo NAME))'. A headline without a handle, or with the handle
'⟨new⟩', is written bare, and the save makes it a new node, with a
new ID (see "Retyped headlines"); '⟨new repo:NAME⟩' makes it in the
owned skgrepo NAME. A headline ending in '⟨node:ID⟩' is written as the
clients paste a node (see "Placing an existing node").

Body lines are taken as edited, and belong to the headline above them.
The link annotations the tool added ('⟦→ ... ⟧', '⟦✗ ... ⟧' or
'⟦not held here⟧' right after a link; '⟦✗ ... ⟧' includes the
'⟦✗ missing⟧' of views written before '⟦not held here⟧') are removed
and the links kept, so a link typed anew needs no annotation. The
summary's comment lines before the first headline are dropped.
** What each change does in skg
*** A changed title or body
The node's title or body changes, wherever else it appears. A
write-protected occurrence (one the full view marks 'writeProtected',
such as each container in a 'containerFolder') saves nothing of its own,
so the server refuses a save that changes its title.
*** A new headline
A headline typed without a handle becomes a new node, contained by its
parent headline, at the position typed. Its home skgrepo is chosen by
the server as for any new headline. The re-rendered view shows it with
a handle, and the full view gives its new ID.
*** A moved headline
A handled headline under a different parent leaves the old parent's
content and joins the new one's, at the position typed. Reordering
headlines under one parent reorders its content.
*** A removed headline
Deleting a headline's line, and the lines under it, takes the node out
of its parent's list (where the parent reads claims: an editable node's
content, an editable folder's members). The node itself stays in the
graph, with its other containers. Under a write-protected occurrence or
a write-protected folder nothing claims, so removing a headline there
only removes it from the view.
*** A deleted node
To delete a node from the graph, write the word 'delete' inside its
handle: '⟨0d delete⟩', or '⟨0d aC1 delete⟩'. The tool writes it into the
headline's metadata as '(editRequest delete)', the request the clients'
'skg-delete' ('C-c <backspace>') writes, and the save deletes the node.
Only an editable node occurrence can carry it; the server refuses it
elsewhere. 'delete subtree' deletes every node occurrence below it too
(see "Words in a handle").
** Words in a handle
Each word below is a gesture of the clients, written into the handle
of the headline it acts on, '⟨0d aC1 write-protect⟩', and saved. The
report says what each asks; the save consumes it.
*** 'detach' and 'attach'
'detach' takes the headline out of its parent's list but keeps it in
the view, as the clients' 'skg-detach' ('C-c s t') does: the save
writes 'noClaim' on it, and the re-rendered view shows it unwarranted
('⊥'). Removing the headline instead also takes it out of the list,
and out of the view. 'attach', their 'skg-attach' ('C-c s a'), puts an
unwarranted headline into its parent's list. Each needs a parent
that reads claims, an editable node or an editable folder under one,
and is refused on a headline that already claims (or does not) what
it asks. When a write-protected parent becomes editable, its
unwarranted children vanish, so attach a child before then.
*** 'write-protect'
'write-protect' makes the occurrence write-protected after the save's
edits, as 'skg-request-write-protected' ('C-c s w') does: its title is
the graph's again, and its children keep their own editability but
no longer claim membership of it. With 'subtree', as 'C-c s W', every
occurrence of its content subtree becomes write-protected too.
'editable' undoes it; the two in one handle are refused. Neither
writes a file.
*** 'merge:ID'
'merge:ID' on a node makes it acquire the node ID by a nodeMerge
('docs/merging.org'), as 'skg-set-merge-request' ('C-c s m') does:
the two become one node, this one, with the relationships of both, and
ID becomes one of its extra IDs. The report names the acquiree by the
title the server gives it, and refuses an ID the graph lacks. The
linkstack ('linkstack push ID', see "Running it") is one place to
keep an ID until it is written here.
*** 'relRepo:NAME'
'relRepo:NAME' records the relationship of the headline to its parent
in the owned skgrepo NAME, as 'skg-set-relRepo' ('C-c s r') does: a
content child's membership of its parent, or a member's relationship
to the viewparent of a writable partner folder (its forks folder,
where the member claims: one claiming nothing forks the viewparent and
records that in its own file, and is refused); on an alias, the
alias's own. The server refuses
NAME when it is more public than the relationship's default
('docs/telescopes.org', "Setting a relationship's skgrepo"); the report
refuses it on a root, under a write-protected parent, and in a
folder whose relationships belong to the other end. A relationship
recorded more privately than its default shows '~NAME' in its handle
from then on.

With 'subtree', as 'C-c s R', it sets every relationship of one kind
in the subtree: written on a node, its content relationships, its
own among them when its parent's list holds it; on a forks folder,
the 'forks' relationships of its claiming members. The walk is the
clients': it does not go below a write-protected node or a member as
such of a forks folder (a forkee or a forker as such).
*** 'noSearchMatching' and 'searchMatching'
'noSearchMatching' keeps the node from matching any search, by its
title, aliases or body, as 'skg-set-flag-search-matching' ('C-c s x')
sets the flag; 'searchMatching' clears it. The node can still be
viewed by its ID, and still shows as context under other hits. Only
an editable occurrence of an owned node takes either. With 'subtree'
(C-u C-c s x) the node and every member occurrence below it take the
word, but a node shown twice, a write-protected occurrence, one with
another edit request, and a foreign node, which a 'Skipped:' line
names.
*** 'repo:NAME'
'repo:NAME' moves the node to the owned skgrepo NAME, as 'skg-set-repo'
('C-c s s') does: its home section, title and body included, goes
there. A write-protected occurrence is refused (the save would refuse
its edit; write it on the editable occurrence), and so is the skgrepo
the node is in already. With 'subtree', as 'C-c s S', the node and
every node below it that was in the same skgrepo move, through member
occurrences; a write-protected one is left, and a 'Not moved:' line
names it, unless the move reaches the node's editable occurrence.
What a move leaves behind is the strandeds question (see "The
server's answer"). On a new headline, '⟨new repo:NAME⟩' makes it in
NAME.
*** 'subtree'
'subtree' asks for the subtree form of the other words of its handle,
as a prefix argument (C-u) does in the clients: 'delete subtree'
deletes the node and every node occurrence below it
('skg-delete-recursive', C-u C-c <backspace>); 'processed both
subtree' and the like mark or unmark the subtree's changes (see
"Marking changes processed"); and 'write-protect', 'relRepo:NAME',
'noSearchMatching', 'searchMatching' and 'repo:NAME' as above. The
words it gives the headlines below show in the report as their own.
Alone, it is refused.
** The report
Before saving, the tool compares the edited compact view with the full
view and prints a line per change, each naming headlines by handle and
title, as in
#+begin_example
Changes in view_root-id.compact.org, against view_root-id.full.org (view ID content-view:root-id):
Moved: ⟨0e⟩ 'Contained twice', from under ⟨0d⟩ 'First child' to under ⟨0f⟩ 'Second child, a forker'.
New: 'A new grandchild', under ⟨0d⟩ 'First child'.
Title: ⟨0d⟩ 'First child' → 'First child, renamed'.
Bodies changed: 1 (⟨0a⟩).
Not saved. Run again with '--yes' to save.
#+end_example
An 'Error:' line names a handle that names no headline of the full
view, or whose request words make no one '(editRequest ...)' (two edit requests, both 'processed' and 'unprocessed', 'processed' without one of 'node', 'rel' and 'both', one of those or 'outward' without 'processed' or 'unprocessed'),
or whose processed words name nothing there (see "Marking changes processed"),
or that carries a word its kind does not take ('editable', 'fork',
'write-protect', 'repo:NAME', 'merge:ID' or a flag word on anything
but a node, say), or a word that cannot stand where it is (see "Words
in a handle"); or a '⟨new⟩' or '⟨node:ID⟩' carrying another word, a
placed node the graph lacks, or one with a body or children (see
"Placing an existing node"); or a new headline retyped with a removed
one's title (see "Retyped headlines"); or an edit of a write-protected
foreign node, a 'fork' beside other edits, or a fork with no owned
skgrepo to go to (see "Forking");
any error stops the save, and the report then lists only the errors.
The report does not guess what the server will refuse: the server's
answer says that.

The changes follow, in this order. 'Delete:', 'Restore node:',
'Restore membership:', 'Merge:', 'relRepo:', 'Search matching:',
'Repo:', 'Editable:', 'Write-protect:', 'Detach:', 'Attach:', 'Processed:'
and 'Unprocessed:' are the requests the handles' words ask for, each with
the form the save sends ('Processed: ⟨0j⟩ 'A new grandchild', as '(processed
node rel)'.'); a 'subtree' gives a line to each headline it gives a
word.
When the 'unprocessed' requests would unmark more than one change, a
'Question:' line asks what a client asks before such a gesture, and
'--yes' answers it. 'Removed:' is a handle the edit no longer has,
with how many headlines below it went with it; a child of a removed
headline that was moved elsewhere is reported as moved. A removed
headline leaves its parent's list, where the parent reads claims; the
node itself stays in the graph. 'Moved:' is a handle under a
different parent, or at a different depth below the same one.
'Reordered:' is a parent whose kept children stand in another order.
'New:' is a headline without a handle, and where it stands.
'Placed:' is a headline ending in '⟨node:ID⟩', with the title the
server gives the node, where it stands, and whether it is placed
write-protected.
'Repeated:' is a handle used twice, which shows the same node twice.
'Title:' gives a changed title, old and new, and 'Bodies changed:'
counts the changed bodies and names their handles. 'Fork:' is a node
the save forks, and 'Fork into:' the skgrepo its clone goes to (see
"Forking"). An edit with none of these prints 'No changes.' and saves
nothing. A 'Question:' line asks whether a new headline is a removed
one reworded (see "Retyped headlines"). Then 'Not moved:' and
'Skipped:' name what a 'subtree' leaves out, and why.

Last, without '--yes', come the hides, which no edit shows: the server
infers them from what left a forker ('docs/forks.org', "Editing
the clone: deletions become hides"). The tool sends the save as a
preview, which writes nothing, and prints each line of the server's
answer, as in
#+begin_example
Hides 'A detail of Fred's' from 'A second container, outside the view', as content of 'Fred's note'.
Hides nothing: 'Contained twice' left 'Second child, a forker', but it is no content of 'Fred's note', nor a mirror of any.
#+end_example
'Hides' and 'Stops hiding' name what the save adds to or takes from
a note's hides, and the member of its forks folder (a note it forks,
or a forker or other mirror it does not hide) whose content holds it. 'Hides nothing:' is a child
that left a note with such a member without hiding anything,
and the rule that kept it from hiding: it is no content of those
members and a mirror of none of it,
or what it stands for was hidden already, or is still contained, or
the same save shows it in the forks folder, or another node you own
keeps it ("but 'Y' keeps it"), so that no member of the forks folder shows it. A removal from a note
that forks nothing prints no line. Every word is the
server's ('docs/api-and-formats.org', "Save buffer"). When the server
would refuse the save, the report says so, with its errors, and the
hides are not printed; a question the save would ask (a fork, Hoist)
is not asked by the preview. A server too old to preview (its answer
to "verify connection" does not name it) is not asked, and the report
says so in their place. The report printed with '--yes' has no such
lines; the save's answer has them instead (see "The server's
answer").
** Retyped headlines
A headline's handle is what ties it to its node. Retyping a headline
instead of moving its line loses that tie: the typed headline becomes
a new node with a new ID, and the old node leaves its parent but stays
in the graph, so links to it, its other relationships and its history
stay with a node the view no longer shows. So the rule is: to move or
reword a headline, keep its handle. Cut and paste the whole line, or
copy the handle onto the headline typed in its place; a handle with
only its ID, '⟨0e⟩', is enough, since the rest of a handle is display.

The tool catches the mistake before saving, by comparing the title of
each new headline (one with no handle) with the title of each headline
the edit removed (a handle of the full view the edited compact view no
longer has).

When the titles are equal, the save is refused. An 'Error:' line names
the new headline and the removed one, and says how to go on: if the
new headline is the removed node, moved or reworded, end it with the
removed one's handle; if it is a different node that happens to share
the title, end it with '⟨new⟩'. That handle has no ID, only the word,
and says "this headline is new on purpose": the tool saves it as a
new node and never compares its title again. It takes no other word.

When the titles differ but probably say the same thing, the report
asks:
#+begin_example
Question: removed ⟨0d⟩ 'Added at the top, retitled' / new 'The headline added at the top, retitled again' (line 10): probably the same statement reworded; keep its ID?
#+end_example
and nothing is saved until it is answered. '--yes' alone does not
answer it: '--yes' says "save", not which of two things to save. The
answers:
- '--keep-ids' answers yes to every question: each new headline takes
  its removed headline's handle, and so its node, its ID and its
  metadata, with the new title. The report then shows the move and
  the retitle instead of a removal and a new headline.
- '--all-new' answers no to every question: each new headline is a
  new node, and each removed one leaves its parent.
- Or answer on each headline: write the removed handle on it (the
  same node), or '⟨new⟩' (a new one). Then that headline asks nothing.
Run the save with the answer and '--yes' to save; without '--yes' the
report shows what the answer would save.

A title "probably says the same thing" by a deliberately loose test.
Each title is lowercased; apostrophes are dropped and other
punctuation splits words; common words are dropped (articles,
prepositions, conjunctions, pronouns and verbs like 'is', 'are',
'was', 'be', 'has', 'have', 'do'); and each word loses one suffix
('-ing', '-ed', '-es', '-ly' or '-s') and then a final 'e', so that
'save', 'saves', 'saved' and 'saving' are one word. Two titles match
when their sets of words share enough, by the Dice coefficient
(twice the shared words over the sum of the two counts) of at least
0.6, or when the remaining texts are alike letter by letter, by
'difflib''s ratio, at least 0.75. The ratio counts only when each
title has at least three words left: on shorter ones a shared word
is most of the text ("budget meeting" and "budget notes" reach
0.76), so two short titles match by the Dice coefficient alone.
The test errs toward asking: a
needless question costs one flag, a missed one costs an ID. When a
new headline resembles several removed ones it is paired with the
closest, and the question names the others; each removed headline is
paired with one new headline at most, closest pairs first.
** Placing an existing node
A headline that ends in '⟨node:ID⟩', ID a node's ID, puts that
existing node there: under an editable parent it joins the parent's
content, so the node gains a container and keeps the ones it had.
This is the clients' 'skg-paste-node' ('C-c o n' in Emacs), which
pastes the top of the linkstack; here the ID is written instead, and
'linkstack paste node' prints such a headline from the tool's
linkstack (see "Running it"). Find an ID in the full view, where each
headline's metadata carries its '(gnid ID)', or in a link.
#+begin_example
** inboxes ⟨0a C1 ⌂:first⟩
*** anything ⟨node:883e7f64-c377-4894-a75b-64c52d1668c4⟩
#+end_example
The title may be anything: the tool asks the server for the node's
title ('link statuses', then 'titles by ids', as the link annotations
do), the report shows it, and the save sends it, since the server
refuses a write-protected occurrence whose title differs from the
graph's. The report reads
#+begin_example
Placed: ⟨node:883e7f64-c377-4894-a75b-64c52d1668c4⟩ 'to Ed', under ⟨0a⟩ 'inboxes'.
#+end_example
The headline is sent as the clients paste it: '(skg node (gnid ID)
writeProtected (viewRequests editableView))', a write-protected
occurrence asking to be made editable. The save fulfils the request,
so the re-rendered view shows the node editable, with its real title,
body and content, and a handle. When the view already holds an
editable occurrence of the node, or a headline asking to become one
(an earlier placement of it, say), the request is left out, since a
view holds at most one editable occurrence of a node; the node is
then placed write-protected, and the report says so: "Placed: ...,
write-protected, since the view already holds an editable occurrence
of it."

Placed in an editable folder of a 'forest' view, a node joins that
folder's relation instead: in the forks folder ('forest forks ID')
the folder's node forks it. Under a forkee as such, the forked node
in that folder, stand its unintegrated children: those the forker
neither contains nor hides, and that you keep in no other node you
own;
those you keep elsewhere stand first, folded, under "☮ It contains
these, and you keep them elsewhere.", each with the folder of its
containers ('docs/forks.org', "What you keep elsewhere"). Removing
one of the others there hides it from the forker, as in the clients,
unless a node you own contains it after the save: moving it into one
of your nodes hides nothing. A
note that forks the folder's node, and that it does not fork, stands
there claiming nothing; removing it hides it in the folder's node.
So does each other mirror of the folder's node, joined to it only
through others (an indirect member): claiming nothing, and removing
it hides it there too. Under either, a forker as such, stands what a
member shows: its content less what the folder's node contains or
hides and what you keep in another node; removing one of those makes the
folder's node fork it, and hides the child unless the node, or another
node you own, contains it after the save.
A node placed under a forkee or forker as such joins that member's
content, after the child it follows, when you own the member; under
a foreign one the save is refused.

A placed node takes no other word in its handle, no body and no
children in the save that places it: it is saved write-protected,
which saves no body, and under which no child claims membership. Edit
it in the view the save writes, where it is editable. The report
stops at a placed ID the graph lacks or the skgrepo restriction
hides.
** Forking
A fork ('docs/forks.org') makes an editable clone, in a skgrepo you
own, of a node: the clone forks the original, so it stands in the
original's place in your views, while the
original's later content reaches you as unintegrated content in the
clone's forks folder. It is how a teammate's node becomes yours
to edit, without changing theirs.
*** Editing a foreign node forks it
A node of a foreign skgrepo forks when you edit it: change its title
or its body, or add, remove or reorder its children, at an editable
occurrence of it. A foreign node in your own node's content is
editable in a fresh view; one placed with '⟨node:ID⟩' is editable
after the save that places it. A write-protected occurrence ('☮')
saves nothing of its own, so editing one forks nothing: the report
stops with an error, and says how to go on. Write 'editable' in its
handle and save, which makes it the view's editable occurrence of the
node, as the clients' 'C-c s e' does; then edit it and save again.
Only an occurrence in content forks, a root of the view or a node's
child: a member of a folder does not. A member as such of a forks
folder, a forkee or a forker as such, is drawn editable under an
editable node, unless the view already shows its node editable (a
repeat); its title and body save when you own it, and a foreign
one's are refused; a child removed from under it is hidden instead,
unless the node, or another node you own, contains it after the save
(moving it into a node of yours hides nothing), and from under a
forker the node also comes to fork it (see "Placing an existing
node"); a headline typed under it, or an existing node
moved there, joins its content when you own it, and is refused under
a foreign one.

The report says what forks, and where the clone goes:
#+begin_example
Bodies changed: 1 (⟨0b⟩).
Fork: ⟨0b⟩ 'to Ed', of the foreign skgrepo 'public', whose body changed: the edit goes to a new clone of it, which forks it; the original stays as it is.
Fork into: 'first', the one skgrepo this server owns, unless the edit settles another. The server asks before forking; '--yes' approves.
Not saved. Run again with '--yes' to save.
#+end_example
The clone needs an owned skgrepo. '--fork-into REPO' names it; without
it, the clone goes to the server's one owned skgrepo, from the 'repos'
request, and when the server owns several the report stops and asks
for '--fork-into'.
*** The fork confirmation
A save that forks writes nothing at first: the server answers with a
fork confirmation, which lists each clone-to-be (the edited title,
its skgrepo, or 'PICK-A-REPO' with a suggestion when the edit did not
settle one) over the original it forks. Without '--yes' the tool sends
nothing, so nothing is forked: that is the decline, as a client's
decline sends nothing either. With '--yes' the tool prints the
confirmation, as the clients show it in their confirmation buffer,
#+begin_example
Server: fork confirmation: the save forks 1 node, and writes nothing until that is approved.
Clone-to-be: 'to Ed', in 'first' (the server suggests 'first').
  It forks 'to Ed' (883e7f64-c377-4894-a75b-64c52d1668c4), of the skgrepo 'public'.
Approved: the save is sent again with the forks approved.
#+end_example
then approves it, as a client's approval does: it sends the same save
again, on the same connection, with '(approved-forks . "true")' and
'(fork-repos (("ID" . "REPO") ...))', each original's ID with its
clone's skgrepo, the placeholder replaced by the '--fork-into' or
default skgrepo. The answer to that save is the ordinary one, and its
re-rendered view, written over the files, shows the clone in the
original's place, marked 'Kĥ'. '--yes' approves only the forks the
report listed: if the server lists another, nothing is saved, and the
tool says which.

The clone copies the original's title, body and content list (the
IDs, not the subtree) with the edit applied, and forks it; a child
the edit removed becomes one the clone hides from its forks. The original is not written. A node may have
one clone you own; forking it again is refused, naming the clone.
The clone also records where it was forked from, its attribution
('docs/forks.org', "Attribution"), so that a reply in a dialog does
not read as the forker's own words: its handle carries
'⌂:<MINE/THEIRS>' wherever the node above does not say the same. 'stripAttribution' in its
handle removes the record, as the clients' 'skg-strip-attribution'
does.
*** Forking a node you own
'fork' in the handle of a node you own forks it, as the clients'
'skg-fork-node' ('C-c m f') does: '⟨0d aC1 fork⟩'. Its clone
forks it, and the original keeps its own
content; a chain of forks deepens this way. As the clients refuse
to fork from a buffer with unsaved changes, so that the clone is the
node as saved, a 'fork' beside any other edit of the compact view is
an error: save the other edits first. The confirmation and its
approval are those of an implicit fork.
** Read receipts
When you have handled an item someone mailed you (a child of their
note addressed to you, which a note of yours forks: your fork of
their mailbox), 'receipt ITEM TEXT' says how, and files the item away,
in one write, as the clients' 'skg-receipt' does
('docs/forks.org', "Read receipts"). It writes a new note, titled
'--title' (default 'Read.'), its body TEXT (one line, which may hold
links '[[id:ID][LABEL]]'; none when TEXT is empty or equals the
title), as the first child of your fork of ITEM: the fork you hold,
or, if you hold none, a new one, which forks ITEM as an edit would
(the receipt asks no fork confirmation: asking for it approves the
fork). An item you own takes the receipt itself. Then it hides ITEM
from your fork of its mailbox, as removing ITEM's headline there would.

Without '--yes' it asks the server what it would do, prints that, and
writes nothing:

: Not written. The receipt would do this; run again with '--yes':
: Forks 'a letter' (letter, of 'fred') into 'mine', and writes the receipt 'Read.' as the first child of the fork.
: Hides 'a letter' from 'my box', as content of 'the box'.

With '--yes' it prints 'Server: wrote the receipt ID under ID.' and
the same lines, and the daemon rewrites the views that show the
item, the notes written, or the mailbox.

The mailbox is the note of another owner that holds ITEM (or a
mirror of it, a reply forked from your note, say: the hide lands on
the member its list names) and that a note of yours forks. When there
is one it is found; when there are several, the receipt is refused,
naming them, and '--mailbox ID' names one (the mailbox, or your fork
of it). When there is none, the receipt is still written, and it says
"Hides nothing:" and why; so it does when the fork of the mailbox
already hides ITEM. '--no-hide' writes the receipt alone.

A new fork goes into '--fork-into REPO'. Without it, it goes where
your fork of the mailbox is, but only when ITEM is homed in the
mailbox's skgrepo: an item from another of its owner's skgrepos may be
more private than the mailbox, so the receipt is refused, naming your
skgrepos, and so it is for an item in no mailbox. With one owned
skgrepo there is no choice. '--fork-into' naming another skgrepo than
the existing fork's is refused.

The writes are one batch, in the order receipt, fork, fork of the
mailbox; a failure says which files were written. Refused while a
view the daemon holds has unsaved edits.
** Handles across saves
The server keeps a view per connection, and without a daemon the
tool's connection ends with each command, so a save names a view the
server does not hold. For such a view the saved buffer's own viewnode
IDs are the view's
(=docs/api-and-formats.org=, on '(vnid X)'): every headline keeps the
one it carries, and a new headline gets one past the highest the
buffer carries. So every handle stays across a save, through adds,
moves, retitles and removals, and a new headline gets a new handle.
A buffer of the diff view keeps its handles the same way. Through a
daemon the server holds the view, and keeps its viewnode IDs across
its saves as it does an editor's.
** Stale views
The save carries the full view ('BASE.full.org') as its baseline: the
text the server last drew. If a node the save would write changed
since (by Jeff in Emacs, say), the server refuses the whole save,
naming the node and saying what changed in it (a changed body comes
with its changed lines), and writes nothing; the tool prints that
refusal as it prints any other, and leaves the files. A node the view
shows as the graph now has it is not written, so it does not stop the
save. View again and redo the edit.
** The server's answer
After the save the tool prints 'Server: saved' or 'Server: nothing was
saved', with the counts of errors and warnings, then each error and
warning as the server wrote it, then each line of what it hid and
stopped hiding, as the report without '--yes' prints them (see "The
report"). When the server refuses, the three files stay as they were,
so the edit can be fixed and saved again.

The server may answer a save with a question instead, having written
nothing. The tool prints it, and answers it as the command line
says, sending the same save again with the answer, and with every
earlier answer, as the clients' retries do; the server may then ask
the next question. '--yes' alone takes the answer that writes nothing
more, and the tool then stops, saying which option answers otherwise.
The questions, in the order the server asks them:
- delete-from: records the skgrepo restriction keeps out name a node
  the save deletes. '--delete-from visible' strips the deleted ID from
  the records the restriction shows only (the others keep naming it,
  shown as an unknown viewnode); '--delete-from all' from every owned
  record. '--yes' alone cancels.
- strandeds: a move to another skgrepo (see "Words in a handle")
  would leave relationships in their old skgrepos, more private than
  their new defaults; the tool lists each ('child-a-id contains
  secret-id: stays at private; its default is now main.').
  '--strandeds reset' moves each to its new default, '--strandeds
  keep' leaves each where it is. '--yes' alone saves nothing.
- Hoist or Abort: a node the save writes is a telescope whose title
  or body sits below its home (overPrivateText, see
  'docs/telescopes.org'). '--hoist' moves the title and body home and
  removes the lower copies, keeping the lower sections' relationships
  and aliases. '--yes' alone aborts, writing nothing.
- the fork confirmation, which "Forking" describes.
One question comes after the save: under a skgrepo restriction the
server may withhold the re-rendered view while it shows text from
overPrivateText telescopes. The save has then happened. With
'--show-overPrivateText' the tool approves the release as the
clients do: it asks the server to rerender the views the question
names (the "rerender views" request), approving those telescopes,
and writes the view; the save is not sent again, since it would
apply a second time (creating a new root of the view again, or refused
because a container it gave a new child would be an edited stale
graphnode). Without the
option it says so, and the files are out of date until the node is
viewed again.

* Reviewing and committing
** The loop
Saving writes '.skg' files and nothing else. When a piece of work is
done, review it in the diff view, mark the changes meant, and commit
what is marked with one message:
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py diff --out-dir DIR
# read DIR/diff_all-changes.compact.org, and any other DIR/diff_*.compact.org
# fix a change by editing any view (this one too) and saving it
# add 'processed both' (or 'processed node', 'processed rel') to the handles meant:
python3 tools/skg-for-ai/skg_for_ai.py save DIR/diff_all-changes.view.json --yes
python3 tools/skg-for-ai/skg_for_ai.py commit "MESSAGE"
#+end_example
The diff view ('docs/diff-view.org') shows how each owned skgrepo's
worktree differs from its HEAD commit, with the context that explains
each change: the changed nodes, the nodes above them up to a root,
and what each change replaced. A deleted node stands as its ghost,
with HEAD's title and body; a changed title or body has its old text
under it ('oldText ...'), a changed body its line diff ('bodyDiff');
a changed content list a 'changesetMarker content', and a removed
member stands where it stood, marked '~-'. What a node's file changed
that none of those shows (its text moved between a private and a
public section, its attribution changed, an alias moved to another
skgrepo, a list was reordered) is one headline under it, just above
its content, its other changes ('otherChanges ...'), whose handle says
them in words; for a reordered list its body shows the old order
against the new, a line a member, '-' at HEAD, '+' now:
#+begin_example
** ⟨0c its content was reordered⟩
The order of its content (- at HEAD, + now):
+Second child, a forker
 First child, renamed
-Second child, a forker
#+end_example
The handles carry the
change facts (see "Change facts, in the diff view"). There are up to
four buffers, written in this order when not empty: all changes, the
nodeMerges, the moves between skgrepos, and the nodes whose only
change is the order of some list (which all changes shows too). Each is a view like any other: it can
be edited and saved, and its save answers with the processed summary.
After any save, 'diff' again for a fresh rendering; a save of a diff
buffer rewrites that buffer's files.
** Marking changes processed
A mark says that one change is approved as it is now; editing a marked
change unmarks it. Marking is a save: write words in a handle, and
'save' turns them into a processed request in the headline's
'(editRequest ...)', as the clients' 'C-c m' gestures do
('docs/diff-view.org', "What a request names").

'processed' or 'unprocessed' says which way, and one of 'node', 'rel'
and 'both' what, as 'C-c m', then 'n', 'r' or 'b', then 'p' or 'u'
does. A headline shows two things that can change: its node ('∃+',
'∃-', 'M') and its relationship to its viewparent ('~+', '~-').
'node' names the first (a new or deleted node's existence; a modified
node's text, home skgrepo, aliases, extra IDs and flags), 'rel' the
second, 'both' both; each among what the headline's change facts
list, so that 'processed rel' on a headline whose relationship did not
change is an error. A headline showing one change (an old text, an
alias, a move, an unknown viewnode) is marked by the letter of its
kind: a relationship moved between skgrepos and an unknown or
restricted viewnode's membership by 'rel' or 'both', any other (a
node's other changes among them) by 'node' or 'both'. A mark covers
the change as it is now: a reorder's mark lapses when the list is
reordered again. On a changed folder the words mark its members one level down;
on a changeset marker ('its content changed') 'rel' marks the changed
relationships it gathers and 'node' its members' own changes.

'subtree' marks the same in the whole subtree, as the clients' C-u
does: each headline that names some of what the letter names, but at
a new node in content position the server walks the graph contentward
from it, through new nodes only, whatever the view shows, and marks
the letter's kinds of change there ('(processed node rel newContent)');
the rest of that node's subtree is skipped. 'outward' does the same
with the walk along every relationship each new node records
('newOutward'), as C-u C-u does. On a home skgrepo move ('⌂ -OLD
+NEW'), 'processed node subtree' instead marks every move between the
same two skgrepos in the moved node's subtree, as 'C-u C-c m h p' does.

A save that unmarks more than one change prints the question a client
asks first, and '--yes' answers it. The server applies the requests
after the save's edits succeed; it drops a request that names no
current change, with a warning, and refuses a save in which two
headlines mark and unmark one change. The save's answer ends with the
processed summary, "N of M changed nodes are processed", which counts
the changed nodes of the owned skgrepos, whatever the buffer shows,
in the unit 'commit' takes; "(W of them wait)" counts the processed
nodes 'commit' would hold back, and "Commit ready" means 'commit'
would take every changed node.
** Restoring what a change removed
Two more words undo a removal, the way the clients' 'C-c s n' and 'C-c
s l' do. 'restoreNode' on a ghost writes the deleted node back as
HEAD has it, and back into each list that named it at HEAD. 'restoreRel' on a
removed membership (a '~-' member) puts it back in its list, where
HEAD had it. The server refuses either anywhere else.
** Extending a buffer to the changes it does not make editable
A buffer of the diff view makes a change editable where it holds an
editable occurrence of the node that records it. A fresh buffer
('diff') makes every change editable, but a save makes nothing
editable and adds no root, so a change made since (by another view's
save, or by this save itself) may not be editable in the buffer the
save writes. The processed summary then says "N changes are not
editable in this buffer".

'extend SIDECAR' extends the buffer to them, as the clients' 'C-c r u'
does: the server makes each changed node editable at its first
occurrence in the buffer (drawing its body and content), and appends
as roots the origins of changes the buffer shows nowhere. It refuses
a compact view with edits (save them first, as a client refuses a
buffer with unsaved changes), prints the processed summary before and
after, and writes the server's rerendered buffer over the three files.
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py extend DIR/diff_all-changes.view.json
#+end_example
The server extends the buffer it holds under the view ID, so the
tool first saves the full view back unchanged under that ID, naming
its buffer of the diff view (which writes nothing, and leaves the
server holding it as that buffer). The server refuses that
save when a node the buffer shows has changed since it was written;
'diff' then gives a fresh buffer, in which every change is editable.
** Committing
'commit MESSAGE' sends "stage and commit" with '(processed-only . t)':
it commits every node whose changes are all processed, except one that
needs a node whose changes are not, and asks nothing. A node goes in
whole, all its '.skg' files in every owned skgrepo, one git-commit per
skgrepo with MESSAGE, by its gitrepo's configured user; foreign
skgrepos are never committed. A processed node waits, uncommitted and
still marked, when it names a new node that does not go in, when it
is deleted and a node that does not go in still names it, or when it
is part of a merge not all of which goes in ('docs/diff-view.org',
"Which nodes go in"). The tool prints what went in and what is left,
and why each processed node left waits:
#+begin_example
Committed 2 nodes, in public (9c1e40d2...), private (41aa07fe...). 2 changed nodes are left; 1 of them is processed but waits: 'Plans for spring' names 'Seed order', which is new and does not go in.
#+end_example
When nothing is processed it prints "Nothing is processed, so nothing
was committed; 'commit --all' commits everything."

A reorder, a Hoist, a stripped attribution and an alias moved to
another skgrepo are each a change to mark like any other (a node's
other changes, above), and 'commit' takes the node once they are
marked. A node one of whose files, at HEAD or now, is not byte for
byte what skg writes (another field order, say; a file only so
changed counts as left too) is not processed, however many of its
marks are set, and 'commit' leaves it out: its file may have changed
in a way the diff view does not show, and no mark covers that
('docs/diff-view.org', "Changes no mark covers"), so such a node goes
in only with 'commit --all', or with Git. The tool names each:
#+begin_example
Nothing was committed. 1 changed node is left; 1 of them changed in a way no mark covers, which 'commit --all' or Git can commit: 'Spring' (its file changed in a way the diff view does not show (formatting, say)).
#+end_example
'commit --all' takes them, and a file that differs from HEAD only in
bytes the parser does not read, which it counts, so it can take more
nodes than the summary counted changed.

'commit MESSAGE --all' commits every changed node, by the same
commit. When some is not processed the server asks first: the tool
prints the processed summary and asks for a typed "yes" on standard
input. Any other answer, or no input, commits nothing. '--yes' answers
yes, and alone it commits everything too, as '--all --yes' does, so
that a 'commit MESSAGE --yes' written before the commit of the
processed existed still commits what it did. No commit takes what was
staged in git by hand, and such an entry stays staged. A blank
message is refused before anything is sent. With a daemon for the
port, the buffers of the diff view it holds are rewritten after the
git-commit (see "The daemon").
** Where it works
The diff view and the commit need a connection with no skgrepo
restriction, and each owned skgrepo in a gitrepo with a HEAD commit;
the server refuses them otherwise, and the tool prints its refusal.
Foreign skgrepos never show a change, and are never committed. So on
Ed's server ('data/ed/skgconfig.toml'), only the
owned repo 'first' can show changes or be committed.
** How it talks to the server
The server keeps the diff view's buffers, and the comparison behind
them, per connection. 'diff' opens one connection (or runs through a daemon),
requests the buffers in the clients' order, and writes each nonempty
one, with the processed summary the server's answer carries. A later
'save' or 'extend' of a diff buffer names its buffer of the diff
view in the save request, so that the server re-renders it as one,
with the processed summary, on a connection that never opened it; the
save keeps every handle the buffer carries (see "Handles across
saves"). Through a daemon the connection holds the buffer already, and
naming it changes nothing.
