#+title: skg-for-ai: reading and writing the skg graph as plain files

* What it is for
A client such as Emacs shows a skg view as a tree of headlines, each
with a few short coloured heralds, and hides the long '(skg ...)'
metadata sexp that every headline carries. A program that reads the
same view as text, such as an AI agent, sees all of that metadata,
which outweighs the words. 'skg_for_ai.py' asks a running skg server
for a view and writes it twice: once exactly as the server rendered it,
and once compactly, with the words, the nesting and a short handle per
headline. Nothing is lost, because each handle points at the line of
the full view that holds the headline's metadata. An edited compact
view can be saved back: the tool rebuilds the full buffer from it and
saves that through the server (see "Writing"). The diff view, which
shows every change since the last git-commit, is written the same way,
and changes are marked ready and committed through it (see "Reviewing
and committing").

The tool is written for anyone, human or agent, who wants to use the
graph without an editor client. It is a client like any other: it
speaks the server's TCP protocol (see 'docs/api-and-formats.org'),
and like the editor clients it may save and import, which write
through the server to the skgrepos the config owns. It uses nothing
but the Python 3 standard library. It never touches '.skg' files
itself; only the server does.

* Running it
** Commands
Each view command ('view', 'search', 'links-here', 'contains', 'diff')
writes three files per view into '--out-dir' (default: the current
directory) and prints their paths, one per line.

'python3 tools/skg-for-ai/skg_for_ai.py view ID' writes the recursive
content view of the node ID, as a client opens it.

'search TERMS...' writes the search buffer for the terms: each hit at
the top level, with the containers of each hit beneath it.

'links-here ID' writes the node's view with its mentioners folder: the
nodes that link to it, each with its containerward chain (its
containers, theirs, and so on up to the roots). It gets that view by
saving, as 'C-c l m' does in Emacs; see "How 'links-here' looks
backward".

'contains ID' writes the node's view, which already shows what contains
it: a fresh content view carries the root's containers folder, with
each container's containerward chain beneath it. The folder is absent
when nothing contains the node.

'close SIDECAR' sends 'close view' for the view ID a sidecar records and
marks the sidecar closed. See "Views and connections" for why it is
rarely needed.

Following a link is just 'view' on the link's ID.

'diff' writes the diff view: each of its buffers that is not empty, as
a view, named 'diff_all-changes', 'diff_merges', 'diff_skgrepo-changes'
and 'diff_order-only-changes' ('--name BASE' replaces 'diff'). When
nothing changed it writes nothing and says so. See "Reviewing and
committing".

'save SIDECAR' saves an edited compact view; see "Writing".

'integrate SIDECAR' makes editable, in a buffer of the diff view, the
changes it does not make editable, as the clients' 'C-c r u' does,
and writes the buffer again; see "Reviewing and committing".

'commit MESSAGE' stages and git-commits every change in the owned
skgrepos with MESSAGE, asking first when not everything is marked
ready; see "Reviewing and committing".

'new TITLE REPO' creates a root node titled TITLE whose home is the
owned skgrepo REPO, and writes its view as 'view' does (named
'view_ID' unless '--name' says otherwise), after printing the save's
answer and 'New node: ID'. A view needs a node to start from, so this
is how an empty skgrepo gets its first one. It saves a buffer holding
only that headline, as an editor client saves a new empty view
('skg-view-new-empty', 'C-c v e' in Emacs), dated like one by the
server's answer to a 'runtime generation' request, and refuses a skgrepo the
server's 'repos' request does not call owned. The new node's body and
children are then written through the view's edit-and-save loop.

'raw REQUEST' sends REQUEST, one sexp, as a request line, and prints
every response, each after a line '--- message N (CHARS chars) ---',
until the server has been quiet for three seconds. With
'--saved-buffer FILE' the request is a 'save buffer', and the tool
sends FILE's text as the saved buffer in the length-prefixed body
after it, then prints every response up to the save's terminal one.
A 'save buffer' request needs its '(rendered-at . "N")', a number;
without it the server refuses the save. 'raw "((request . \"runtime
generation\"))"' gives a current one.

'import INPUT_DIR REPO' imports the Markdown and Org files under
INPUT_DIR (a path the server can read) into the owned skgrepo REPO: it
asks for a preview and then applies it, on one connection, since the
server binds the preview's approval token to the connection that
asked. When the server asks for the host root of absolute links, the
tool answers with the empty one, leaving those links unresolved.
'--preview-only' cancels instead of applying. It prints the responses
as 'raw' does.

Options, after the command: '--port N' for every command ('save' and
'integrate' require the sidecar's); '--yes' for
'save' and 'commit'; for the view commands also '--out-dir DIR', '--name BASE' to name the files
'BASE.full.org' and so on instead of 'COMMAND_ARGUMENT', and
'--no-summary' to leave the summary out of the compact view.
** The port
The tool connects to 127.0.0.1 on the port 'SKG_PORT' names, or 1730
when it is unset; '--port' overrides both. The port of a server is the
'port' of its 'skgconfig.toml'.

* The files it writes
For a base name such as 'view_ID' the tool writes 'view_ID.full.org',
'view_ID.compact.org' and 'view_ID.view.json'.
** The full view
'BASE.full.org' is the view's text exactly as the server sent it,
metadata and all. It is what a client receives, before heralds hide
the metadata.
** The compact view
'BASE.compact.org' has every line of the full view, in the same order.
A body line is copied unchanged, except that its links are annotated.
A headline keeps its stars and its title; its '(skg ...)' metadata is
removed, and a handle is added at the end of the line.
*** The handle, and why it is a line number
A handle has the fixed form '⟨N ...⟩'. N is the 1-based number of the
headline's line in the full view, so line N of 'BASE.full.org' holds
the headline's metadata: 'sed -n Np BASE.full.org' shows it, and the
pattern '⟨[0-9]+' finds every handle. A line number needs no table
beside it and stays meaningful when the compact view is edited: a
headline that is moved keeps its number, so a tool can tell a move
from a deletion, and a headline without a handle is a new one. Body
lines are not numbered: a body line belongs to the nearest headline
above it.

After N, a headline that is not a node occurrence names its kind: '⟨5
containerFolder⟩', '⟨12 alias⟩'. Folders have no title, so in a
compact view such a headline is its stars and its handle.
*** The relationship heralds in the handle
After N come the headline's relationship heralds, rendered as the
clients render them, without their styles; 'docs/heralds.org',
"Relationship heralds", explains them. In display order: 'C' contains,
'L' links to, 'S' subscribes to, 'O' overrides, 'H' hides from its
subscriptions. A count before a letter counts the nodes on the
relation's in-side ("two nodes contain this"), a count after it the
out-side ("this contains three"). A lowercase letter is an ancestor in
this view: 'a' the viewparent, 'b' the grandparent, and so on; it
replaces the count when ancestors make up the whole side. A fraction
marks a subset: '1/5L', five nodes link here and one of them is
substantive; 'C2/8', eight contents, two not yet integrated by the
subscriber above. 'ĥ' after 'O' says this occurrence stands in for a
node it overrides. The property counts 'A' (aliases), 'I' (extra IDs)
and 'F' (true flags) follow. So '⟨17 2aC3⟩' is line 17: two
containers, one of them the viewparent, and three contents.

One token is left out: a bare 'aC', which says only that the
viewparent contains the node and nothing else does. That is the
ordinary case in a content tree, so most handles would carry it;
'⟨3 aC L1⟩' is written '⟨3 L1⟩', and '⟨5 aC⟩' just '⟨5⟩'. Every other
form, 'aC10' or '2aC' among them, stays.
*** The skgrepo boundary
A headline whose home skgrepo differs from its nearest node
occurrence above it, or a root, carries '⌂:LABEL' after its
relationship heralds, LABEL the skgrepo's label, as the clients show
it: '⟨14 C1 1/L bS ⌂:fred⟩' is a note of the 'fred' skgrepo under a
node of another. Every other headline shares its skgrepo with the
nearest node above it.
*** Change facts, in the diff view
A headline of the diff view that shows a change carries, after the
skgrepo boundary, the diff heralds the clients show
('docs/heralds.org', "Diff heralds"), without their styles. On a node
or a ghost (a deleted node, shown as HEAD has it): '∃+' a new node,
'∃-' a deleted one, 'M' a modified one (its title, body, properties or
lists changed), then '~+' a new membership in its parent (in a
partner folder, its relationship of the folder's kind to the folder's
parent), '~-' a removed one. On an alias, ID or flag in its folder,
'+' or '-'; on an unknown viewnode, '~+' or '~-'. A '✓' right after a
change says it is marked ready: '∃+✓ ~+' is a new node, approved, in a
membership that is not. The headlines the diff view adds to explain a
change name their kind: 'oldText title' (the old title; 'oldText
body', 'oldText titleAndBody'), 'bodyDiff', 'changesetMarker content'
(its content changed), 'homeSkgrepoMove' and 'relRepoMove' (moves to
another skgrepo); each takes a '✓' when ready. In the
skgrepo-changes buffer a moved node adds '-OLD +NEW', and 'Δ⌂=a' when
its nearest moved ancestor (here the parent) moved the same way.
*** Folded headlines
A headline the server marks 'folded', one a client shows collapsed,
ends its handle with the token 'folded': '⟨17 C3 folded⟩'. The lines
under it are still in both files; the token tells where a person
reading in a client would see less.

The tool computes these from each headline's '(view (rels ...) (props
...) (birth ...))' facts, mirroring 'render_rel_facts' in
'nvim/lua/skg/heralds.lua' and reading 'shared/relations.json' for the
letters and their order. The other heralds (☮, ⊥, ⌂ and so on) are not
in the handle; the full view's metadata says what they would say.
*** Link annotations
Every '[[id:ID][label]]' link, in a title or a body, is followed by an
annotation in a fixed form. A link whose target resolves gets '⟦→ TITLE
⌂:LABEL⟧', the target's title and its home skgrepo's label. A link
whose target the graph lacks gets '⟦✗ missing⟧'; one whose target the
skgrepo restriction hides gets '⟦✗ restricted⟧'. The tool asks the
server's 'link statuses' request, which the clients' link annotations
use, and then 'titles by ids' for the titles of the resolved targets.
The annotation is the tool's; the link itself is unchanged.
*** The summary
Unless '--no-summary' is given, the compact view starts with a few Org
comment lines ('# ...') before the tree. They name the full view and
the view ID, then count, from the same metadata: the headlines, node
occurrences, distinct nodes, folders and other kinds; the node
occurrences in each skgrepo, owned or foreign; the occurrences in
foreign skgrepos, the write-protected and the folded headlines; those
contained elsewhere too (a 'contains' in-side larger than its ancestor
flags, so a container not above it in this view); those subscribed to
and those subscribing; the links, their distinct targets, and how many
of those resolve; and the server's errors and warnings, which the
sidecar lists.

Whether a skgrepo is owned or foreign comes from the server's 'repos'
request, which lists every configured skgrepo.

A buffer of the diff view opens its summary with two more lines: the
readiness summary the server sends ("1 of 4 changed files are ready",
with how many changes this buffer cannot edit and how many files
changed in foreign skgrepos), and how many headlines show a change,
ready and not.
** The sidecar
'BASE.view.json' records the view ID, the command and its request (for
a buffer of the diff view, the buffer's name), the
port, the two files' names, the runtime generation the server rendered the
view at ('rendered_at'), the server's errors and warnings, whether
the compact view has a summary, and whether the view is closed. 'save'
sends the edited view against this view ID and generation, to this
port, and renders the summary again when there was one.

* Views and connections
The server keeps a view's state per TCP connection, and forgets every
view of a connection when it ends. Each command opens one connection,
and sends 'close view' for its view before disconnecting, as a client
does when its buffer is killed. A view is therefore never left open
by the tool. A save does not need the view to be open: the server
reads the saved buffer against the graph, so the view ID in the
sidecar is enough. The 'close' command matters only for a view that a
longer-lived connection holds.

* How 'links-here' looks backward
The server has no request that answers "what links here". The clients
ask for it by saving the view with a '(viewRequests (folder
mentioners))' on the node's headline ('C-c l m' in Emacs), and the
re-rendered buffer the save returns shows the mentioners folder. The
tool does the same: it opens the view, adds that request to the root's
metadata, and saves the otherwise unchanged buffer. The tool may save,
as any client may. Since nothing in
the buffer differs from the graph, the save writes no file, but it is
a save, sent through the server's whole save path, so a node that the
server would refuse or ask about on save (a foreign node edited, for
instance) can make it fail or ask a question the tool does not
answer. The tool then reports the server's answer and writes nothing.

* Running a scratch server for it
To try the tool without touching real data, run a second server on a
scratch data root, as the 'verify' skill ('.claude/skills/verify/')
describes. In short: copy 'tools/skg-for-ai/test-fixture/' somewhere
(the server writes its search index and some generated files into the
data root), set its 'port' in 'skgconfig.toml' to a free port, build
the server with 'cargo build --bin skg', and start it from the copy:
#+begin_example
cd /path/to/copy
/path/to/repo/target/debug/skg skgconfig.toml > server.log 2>&1 &
SKG_PID=$!
#+end_example
Wait for "Server ready." in 'server.log', then run the tool with
'SKG_PORT' set to that port. Stop the server with 'kill $SKG_PID'.

* Tests
'python3 tools/skg-for-ai/test_skg_for_ai.py' runs them, given a built
server ('cargo build --bin skg'; 'SKG_BINARY' names another binary).
First it checks the relationship heralds against the rendering cases
both clients' tests share, 'tests/shared/herald-rendering-cases.txt',
taking those whose text is only relationship and property tokens. Then
it copies 'test-fixture/' to a temporary data root, starts a server
there on port 1793 ('SKG_FOR_AI_TEST_PORT' changes it), runs 'view',
'search', 'links-here' and 'contains', and compares each compact view
with its file in 'test-expected/'. It also checks that every handle
names its own line and that line is a headline of the full view. Then
it sends a 'repos' request through 'raw' and imports a Markdown file
through 'import', and checks that the runs, the 'links-here' save
among them, left every '.skg' file of the fixture as it was.

Then, on a second server over a fresh copy of the fixture, it edits
compact views and saves them, in order: a title, a body, a new child,
a move to another parent, a removal (the node then still has its other
container), a deletion through 'delete' in a handle, two bad handles
(refused before any save), a retitled write-protected occurrence
(refused by the server, the files left as they were), a stale view
(refused by the server),
and 'new' (refused in the foreign skgrepo; in the owned one a root
whose view then saves a body and a child).
It compares each report with the text expected and reads the '.skg'
files after each save. The stale case renders a view, changes a node
it shows through a second view's save, and saves the first view's
edit of another node: the server refuses, naming the changed node, and
nothing is written; a fresh view then saves the same edit, and the
second save's change stays.

Then, on a third server over a fresh copy of the fixture whose owned
skgrepo is first made a gitrepo with one commit, it saves a retitle, a
new child and a deletion, compares the diff view's compact buffer
with the text expected, marks the new child 'ready' and sees it ready
in a fresh 'diff', checks the question before an 'unready' of two
changes, commits unconfirmed (nothing happens), restores the deleted
node with 'restoreNode', commits with '--yes' and reads 'git log' and
an empty diff view. Then it retitles the root, writes the diff view
(the root's first child write-protected in it), retitles that child's
new child through a content view, runs 'integrate' on the diff buffer
and checks its output, that the child and the grandchild are now
editable there, and that a save of the buffer retitles the grandchild
again. Last, it checks that a blank commit message is refused.

It prints PASS or each failure, and keeps the scratch files when
something fails. '--update-expected' rewrites the expected
files instead of comparing; read the difference before keeping it.

The fixture has two skgrepos, a foreign 'fred' listed first and an
owned 'main'. Its root contains two children and is contained by a
node above it; one child contains a node that a node outside the view
also contains; the other subscribes to a foreign node and hides two
foreign nodes from its subscriptions, one of which the view shows
folded in a hidden-outside-of-subscribee folder. The root's body links
to a node in the view, to a foreign node, and to an ID nobody wrote.

* Writing
** The loop
To change the graph, edit the compact view in place and save it:
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py view ID --out-dir DIR
# edit DIR/view_ID.compact.org
python3 tools/skg-for-ai/skg_for_ai.py save DIR/view_ID.view.json
# read the report
python3 tools/skg-for-ai/skg_for_ai.py save DIR/view_ID.view.json --yes
#+end_example
'save' takes the sidecar, or a directory holding only one. Without
'--yes' it prints the report and stops; with it, it prints the report,
sends the save, prints the server's answer, and writes the server's
re-rendered view over the three files, so the handles are fresh and the
next edit starts from them. A save needs the server the view came from;
'--port', if given, must match the sidecar's.

The tool writes nothing to '.skg' files itself. The server's save does,
with every check an editor client's save gets, and it writes only to
skgrepos the server's config owns.
** How the compact view becomes a buffer
The tool rebuilds the buffer an editor client would send, from the
edited compact view and the full view it was written beside. A
headline with a handle '⟨N ...⟩' gets back the metadata of line N of
the full view; its level, title and position come from the edited
compact view. The rest of the handle (the heralds, the kind, 'folded')
is display only, and editing it changes nothing, except for the
request words: 'delete' (see "A deleted node"), and 'ready',
'unready', 'all', 'restoreNode' and 'restoreRel' (see "Reviewing and
committing"). The rebuild writes them into the headline's
'(editRequest ...)', which holds one edit request ('delete',
'restoreNode' or 'restoreRel') and one readiness request after it. A headline without a handle is
written bare, and the save makes it a new node, with a new ID.

Body lines are taken as edited, and belong to the headline above them.
The link annotations the tool added ('⟦→ ... ⟧' or '⟦✗ ... ⟧' right
after a link) are removed and the links kept, so a link typed anew
needs no annotation. The summary's comment lines before the first
headline are dropped.
** What each change does in skg
*** A changed title or body
The node's title or body changes, wherever else it appears. A
write-protected occurrence (one the full view marks 'writeProtected',
such as each container in a 'containerFolder') saves nothing of its own,
so the server refuses a save that changes its title.
*** A new headline
A headline typed without a handle becomes a new node, contained by its
parent headline, at the position typed. Its home skgrepo is chosen by
the server as for any new headline. The re-rendered view shows it with
a handle, and the full view gives its new ID.
*** A moved headline
A handled headline under a different parent leaves the old parent's
content and joins the new one's, at the position typed. Reordering
headlines under one parent reorders its content.
*** A removed headline
Deleting a headline's line, and the lines under it, takes the node out
of its parent's list (where the parent reads claims: an editable node's
content, an editable folder's members). The node itself stays in the
graph, with its other containers. Under a write-protected occurrence or
a write-protected folder nothing claims, so removing a headline there
only removes it from the view.
*** A deleted node
To delete a node from the graph, write the word 'delete' inside its
handle: '⟨7 delete⟩', or '⟨7 aC1 delete⟩'. The tool writes it into the
headline's metadata as '(editRequest delete)', the request the clients'
'skg-delete' ('C-c <backspace>') writes, and the save deletes the node.
Only an editable node occurrence can carry it; the server refuses it
elsewhere.
** The report
Before saving, the tool compares the edited compact view with the full
view and prints a line per change, each naming headlines by handle and
title, as in
#+begin_example
Changes in view_root-id.compact.org, against view_root-id.full.org (view ID content-view:root-id):
Moved: ⟨9⟩ 'Contained twice', from under ⟨7⟩ 'First child' to under ⟨10⟩ 'Second child, a subscriber'.
New: 'A new grandchild', under ⟨7⟩ 'First child'.
Title: ⟨7⟩ 'First child' → 'First child, renamed'.
Bodies changed: 1 (⟨1⟩).
Not saved. Run again with '--yes' to save.
#+end_example
An 'Error:' line names a handle that names no line of the full view,
or a body line, or whose request words make no one '(editRequest
...)' (two edit requests, both 'ready' and 'unready', 'all' alone);
any error stops the save, and the report then lists only the errors.
The report does not guess what the server will refuse: the server's
answer says that.

The changes follow, in this order. 'Delete:', 'Restore node:',
'Restore membership:', 'Ready:' and 'Unready:' are the requests the
handles' words ask for, a readiness request with the form the save
sends ('Ready: ⟨14⟩ 'A new grandchild', as '(ready node rel)'.').
When the 'unready' requests would unmark more than one change, a
'Question:' line asks what a client asks before such a gesture, and
'--yes' answers it. 'Removed:' is a handle the edit no longer has,
with how many headlines below it went with it; a child of a removed
headline that was moved elsewhere is reported as moved. A removed
headline leaves its parent's list, where the parent reads claims; the
node itself stays in the graph. 'Moved:' is a handle under a
different parent, or at a different depth below the same one.
'Reordered:' is a parent whose kept children stand in another order.
'New:' is a headline without a handle, and where it stands.
'Repeated:' is a handle used twice, which shows the same node twice.
'Title:' gives a changed title, old and new, and 'Bodies changed:'
counts the changed bodies and names their handles. An edit with none
of these prints 'No changes.' and saves nothing.
** Stale views
The save carries the runtime generation the view was rendered at, from the
sidecar. If a node the save would write changed since (by Jeff in
Emacs, say), the server refuses the whole save, naming the node, and
writes nothing; the tool prints that refusal as it prints any other,
and leaves the files. A node the view shows as the graph now has it is
not written, so it does not stop the save. View again and redo the
edit.
** The server's answer
After the save the tool prints 'Server: saved' or 'Server: nothing was
saved', with the counts of errors and warnings, then each error and
warning as the server wrote it. When the server refuses, the three
files stay as they were, so the edit can be fixed and saved again.
When the server answers with a question instead (to fork an edited
foreign node, to delete records the skgrepo restriction hides, to
review stranded relationships, to hoist telescope text), the tool
prints the question and stops: it answers none of them, and nothing is
saved. A client can answer them. One question comes after the save:
under a restricted skgrepo-set the server may withhold the re-rendered
view until over-private text is approved. The save has then happened,
the tool says so, and the files are out of date until the node is
viewed again.

* Reviewing and committing
** The loop
Saving writes '.skg' files and nothing else. When a piece of work is
done, review it in the diff view, mark the changes meant, and commit
them all with one message:
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py diff --out-dir DIR
# read DIR/diff_all-changes.compact.org, and any other DIR/diff_*.compact.org
# fix a change by editing any view (this one too) and saving it
# add 'ready' to the handles of the changes meant:
python3 tools/skg-for-ai/skg_for_ai.py save DIR/diff_all-changes.view.json --yes
python3 tools/skg-for-ai/skg_for_ai.py commit "MESSAGE"
#+end_example
The diff view ('docs/diff-view.org') shows how each owned skgrepo's
worktree differs from its HEAD commit, with the context that explains
each change: the changed nodes, the nodes above them up to a root,
and what each change replaced. A deleted node stands as its ghost,
with HEAD's title and body; a changed title or body has its old text
under it ('oldText ...'), a changed body its line diff ('bodyDiff');
a changed content list a 'changesetMarker content', and a removed
member stands where it stood, marked '~-'. The handles carry the
change facts (see "Change facts, in the diff view"). There are up to
four buffers, written in this order when not empty: all changes, the
nodeMerges, the moves between skgrepos, and the nodes whose only
change is the order of a list. Each is a view like any other: it can
be edited and saved, and its save answers with the readiness summary.
After any save, 'diff' again for a fresh rendering; a save of a diff
buffer rewrites that buffer's files.
** Marking changes ready
A mark says that one change is approved as it is now; editing a marked
change unmarks it. Marking is a save: write a word in a handle, and
'save' turns it into a readiness request in the headline's
'(editRequest ...)', as the clients' 'C-c r r' does.

'ready' marks every change the headline names, as the request '(ready
OBJECT...)' naming each object its change facts list: on a new node
its existence and its membership, on a modified node ('M') every
change its file records and its membership if that changed, on an old
text or a move the one change, on a changeset marker every change
under it. 'unready' unmarks the same. 'ready all' and 'unready all'
name only the object 'all': every change a modified node's file
records, or every change of a changeset marker.

A save that unmarks more than one change prints the question a client
asks first, and '--yes' answers it. The server applies the requests
after the save's edits succeed; it drops a request that names no
current change, with a warning, and refuses a save in which two
headlines mark and unmark one change. The save's answer ends with the
readiness summary, "N of M changed files are ready", which counts
every change of the owned skgrepos, whatever the buffer shows.
** Restoring what a change removed
Two more words undo a removal, the way the clients' 'C-c s n' and 'C-c
s l' do. 'restoreNode' on a ghost writes the deleted node back as
HEAD has it, and back into each list that named it at HEAD. 'restoreRel' on a
removed membership (a '~-' member) puts it back in its list, where
HEAD had it. The server refuses either anywhere else.
** Integrating changes the buffer does not make editable
A buffer of the diff view makes a change editable where it holds an
editable occurrence of the node that records it. A fresh buffer
('diff') makes every change editable, but a save makes nothing
editable and adds no root, so a change made since (by another view's
save, or by this save itself) may not be editable in the buffer the
save writes. The readiness summary then says "N changes are not
editable in this buffer".

'integrate SIDECAR' makes them editable, as the clients' 'C-c r u'
does: the server makes each changed node editable at its first
occurrence in the buffer (drawing its body and content), and appends
as roots the origins of changes the buffer shows nowhere. It refuses
a compact view with edits (save them first, as a client refuses a
buffer with unsaved changes), prints the readiness summary before and
after, and writes the server's rerendered buffer over the three files.
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py integrate DIR/diff_all-changes.view.json
#+end_example
The server integrates the buffer it holds under the view ID, so the
tool first opens the buffer again under that ID and saves the full
view back unchanged (which writes nothing). The server refuses that
save when a node the buffer shows has changed since it was written;
'diff' then gives a fresh buffer, in which every change is editable.
** Committing
'commit MESSAGE' sends "stage and commit". The server stages every
changed '.skg' file of every owned skgrepo, deletions included, and
git-commits each gitrepo that has changes, with MESSAGE, by that
gitrepo's configured user. It commits everything, marked or not: the
marks are a review, not a selection. When not every changed file is
ready, or some owned gitrepo already has staged entries (which the
git-commit would include), the server asks first: the tool prints the
readiness summary and the staged paths, and asks for a typed "yes" on
standard input; '--yes' answers yes. Any other answer, or no input,
commits nothing. Then it prints 'Committed in SKGREPO (COMMIT ID)'
per git-commit, or 'Nothing was committed.', and any error. A blank
message is refused before anything is sent.
** Where it works
The diff view and the commit need a connection with no skgrepo
restriction, and each owned skgrepo in a gitrepo with a HEAD commit;
the server refuses them otherwise, and the tool prints its refusal.
Foreign skgrepos never show a change, and are never committed. So on
User Claude's server ('data/skgconfig-user-claude.toml'), only the
owned repo 'first' can show changes or be committed.
** How it talks to the server
The server keeps the diff view's buffers, and the comparison behind
them, per connection. 'diff' opens one connection, requests the
buffers in the clients' order, and writes each nonempty one, with the
readiness summary the server's answer carries. A later 'save' or
'integrate' of a diff buffer first requests that buffer again under
the sidecar's view ID on its own connection, so that the server
re-renders it as a buffer of the diff view, with the readiness
summary.
