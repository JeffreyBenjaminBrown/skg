#+title: skg-for-ai: reading and writing the skg graph as plain files

* Start here
skg-for-ai lets you read and change a skg graph as plain Org files,
without an editor client. Everything below this page is reference;
this page is the whole working loop. Every command is
'python3 tools/skg-for-ai/skg_for_ai.py COMMAND ...', run against the
server whose port 'SKG_PORT' (or '--port') names.

First, start a daemon, and leave it running for the session:
'daemon --out-dir DIR &'. It keeps one connection to the server, so
the views you write stay current: when a save, a git-commit or a
teammate's change touches a node a view shows, it rewrites that
view's files, and it notes each such event in 'DIR/skg-for-ai.log'.
Every later command for that server runs through it, wherever it
writes. 'daemon --stop --out-dir DIR' ends it.

To read, view a node: 'view ID --out-dir DIR' writes 'view_ID.full.org'
(the view exactly as the server drew it), 'view_ID.compact.org' (the
same tree, each headline ending in a short handle such as '⟨0d aC1⟩')
and a sidecar, 'view_ID.view.json'. Read the compact file. Following
a link is 'view' again on the link's ID; 'search WORDS' finds nodes.

To change the graph, edit the compact file in place. Change a title
or a body by editing its text. Add a node by writing a new headline,
with no handle, where it belongs. Move a node by moving its line,
handle and all, and its subtree with it. Remove a headline to take
the node out of its parent; write 'delete' in its handle,
'⟨0d aC1 delete⟩', to delete the node itself. To put a node that
already exists here too, write a headline ending in '⟨node:ID⟩', ID
its ID; to fork a teammate's node, edit it where it is editable, and
the save asks before it forks ("Placing an existing node" and
"Forking").

Then save with the report: 'save DIR/view_ID.view.json' prints, line
by line, what the save would do, and changes nothing. Read it. If it
says what you meant, run it again with '--yes' to save; the files
are then rewritten with the server's new rendering. If it reports an
error or asks a question, answer it as it says and run it again.

One rule matters more than the rest: never retype a handled headline.
The handle is the only thing that ties a headline to its node. A
headline typed afresh, without the handle, is a new node with a new
ID, and the old node leaves its parent, taking with it the links to
it, its other relationships and its history, to a place the view no
longer shows. So move or reword a headline by editing or moving its
line, never by writing it again; if you must retype one, copy its
handle onto the new line. The save stops at a retyped title it
recognizes, and asks about one that resembles a removed one, but do
not count on it.

When a piece of work is done, review and commit it. 'diff --out-dir
DIR' writes the diff view: every change since the last git-commit,
each handle carrying its change facts. Fix anything wrong by editing
and saving, as above; write 'ready' in the handles of the changes you
approve and save that buffer; then 'commit "MESSAGE" --yes' stages
and git-commits every change in the owned skgrepos.

The rest of this file is reference. "Running it" lists every command
and option; "The files it writes" explains the compact view, its
handles and heralds, and its summary; "The daemon" says what the
daemon does and what its log means; "Writing" covers saving in
detail, the report, "Retyped headlines", placing an existing node
and forking; "Reviewing and committing" covers the diff view,
readiness and the commit; "What the tool covers of COMMANDS.org"
says, command by command, what the tool does of what Emacs does. The
protocol is in 'docs/api-and-formats.org', and the diff view in
'docs/diff-view.org'.

* What it is for
A client such as Emacs shows a skg view as a tree of headlines, each
with a few short coloured heralds, and hides the long '(skg ...)'
metadata sexp that every headline carries. A program that reads the
same view as text, such as an AI agent, sees all of that metadata,
which outweighs the words. 'skg_for_ai.py' asks a running skg server
for a view and writes it twice: once exactly as the server rendered it,
and once compactly, with the words, the nesting and a short handle per
headline, which carries the heralds a client shows. Nothing is lost,
because each handle is the viewnode ID of the full view's headline,
whose metadata it stands for. An edited compact
view can be saved back: the tool rebuilds the full buffer from it and
saves that through the server (see "Writing"). The diff view, which
shows every change since the last git-commit, is written the same way,
and changes are marked ready and committed through it (see "Reviewing
and committing").

The tool is written for anyone, human or agent, who wants to use the
graph without an editor client. It is a client like any other: it
speaks the server's TCP protocol (see 'docs/api-and-formats.org'),
and like the editor clients it may save and import, which write
through the server to the skgrepos the config owns. It uses nothing
but the Python 3 standard library. It never touches '.skg' files
itself; only the server does.

Each command opens its own connection and closes it when done. A
daemon ('daemon --out-dir DIR') instead keeps one connection open, as
an editor session does: every command for its server runs through
it, and it keeps the files of the views they write current as the
graph changes; see "The daemon".

* Running it
** Commands
Each view command ('view', 'search', 'forest', 'contains',
'links-here', 'diff') writes three files per view into '--out-dir'
(default: the current directory) and prints their paths, one per line.

'python3 tools/skg-for-ai/skg_for_ai.py view ID' writes the recursive
content view of the node ID, as a client opens it.

'search TERMS...' writes the search buffer for the terms: each hit at
the top level, with the containers of each hit beneath it.

'forest KIND ID' writes the node's view with the folder KIND under it,
as the clients' 'C-c l' commands draw it ('docs/COMMANDS.org', "C-c
l"), named 'forest-KIND_ID'. Under each member of a partner folder
hangs its containerward chain: its containers, theirs, and so on up
to the roots. The kinds:
| KIND          | Emacs   | what it draws                                                                    |
|---------------+---------+----------------------------------------------------------------------------------|
| containers    | C-c l c | the containers folder: what contains the node                                    |
| mentioners    | C-c l m | the mentioners folder: what links to it                                          |
| subscribesTo  | C-c l s | the subscribees folder (what it subscribes to) and the subscribers folder        |
| overrides     | C-c l o | the overridden folder (what it overrides) and the overriders folder              |
| hidesFromSubs | C-c l h | the hidden folder (what it hides from its subscriptions) and the hiders folder   |
| aliases       | C-c l a | the aliases folder                                                               |
| flags         | C-c l p | the flags folder: its true flags                                                 |
A write-protected folder (☮) is one whose membership cannot be
changed from there; an empty one is left out, an empty editable one
shown as a place to add members. A fresh content view already carries
the root's containers folder, so 'forest containers' is 'view' under
another name; every other kind is drawn by a save, as the clients do;
see "How 'forest' draws a folder".

'contains ID' is 'forest containers ID', and 'links-here ID' is
'forest mentioners ID', each named after itself ('contains_ID',
'links-here_ID').

'close SIDECAR' sends 'close view' for the view ID a sidecar records,
to the sidecar's server, and marks the sidecar closed. See "Views and
connections" for why it is needed only with a daemon.

'daemon --out-dir DIR' runs until stopped, taking every command for
its server, holding on one connection every view they write, and
rewriting a view's files when the server rerenders it; 'daemon --stop
--out-dir DIR' stops it. See "The daemon".

Following a link is just 'view' on the link's ID.

'diff' writes the diff view: each of its buffers that is not empty, as
a view, named 'diff_all-changes', 'diff_merges', 'diff_skgrepo-changes'
and 'diff_order-only-changes' ('--name BASE' replaces 'diff'). When
nothing changed it writes nothing and says so. See "Reviewing and
committing".

'save SIDECAR' saves an edited compact view; see "Writing".

'integrate SIDECAR' makes editable, in a buffer of the diff view, the
changes it does not make editable, as the clients' 'C-c r u' does,
and writes the buffer again; see "Reviewing and committing".

'commit MESSAGE' stages and git-commits every change in the owned
skgrepos with MESSAGE, asking first when not everything is marked
ready; see "Reviewing and committing".

'new TITLE REPO' creates a root node titled TITLE whose home is the
owned skgrepo REPO, and writes its view as 'view' does (named
'view_ID' unless '--name' says otherwise), after printing the save's
answer and 'New node: ID'. A view needs a node to start from, so this
is how an empty skgrepo gets its first one. It saves a buffer holding
only that headline, as an editor client saves a new empty view
('skg-view-new-empty', 'C-c v e' in Emacs), dated like one by the
server's answer to a 'runtime generation' request, and refuses a skgrepo the
server's 'repos' request does not call owned. The new node's body and
children are then written through the view's edit-and-save loop.

'raw REQUEST' sends REQUEST, one sexp, as a request line, and prints
every response, each after a line '--- message N (CHARS chars) ---',
until the server has been quiet for three seconds. With
'--saved-buffer FILE' the request is a 'save buffer', and the tool
sends FILE's text as the saved buffer in the length-prefixed body
after it, then prints every response up to the save's terminal one.
A 'save buffer' request needs its '(rendered-at . "N")', a number;
without it the server refuses the save. 'raw "((request . \"runtime
generation\"))"' gives a current one.

'import INPUT_DIR REPO' imports the Markdown and Org files under
INPUT_DIR (a path the server can read) into the owned skgrepo REPO: it
asks for a preview and then applies it, on one connection, since the
server binds the preview's approval token to the connection that
asked. When the server asks for the host root of absolute links, the
tool answers with the empty one, leaving those links unresolved.
'--preview-only' cancels instead of applying. It prints the responses
as 'raw' does.

Options, after the command: '--port N' for every command ('save',
'integrate' and 'close' require the sidecar's; a command run through
a daemon's folder talks to the daemon's server unless it names one);
'--yes' for
'save' and 'commit'; '--keep-ids' or '--all-new' for 'save' (see
"Retyped headlines"); '--fork-into REPO' for 'save' (see "Forking");
for the view commands also '--out-dir DIR', '--name BASE' to name the files
'BASE.full.org' and so on instead of 'COMMAND_ARGUMENT', and
'--no-summary' to leave the summary out of the compact view.
Every command that writes a view fetches the server's herald rule
table once, with the 'herald rules' request.
** The port
The tool connects to 127.0.0.1 on the port 'SKG_PORT' names, or 1730
when it is unset; '--port' overrides both. The port of a server is the
'port' of its 'skgconfig.toml'.

* The files it writes
For a base name such as 'view_ID' the tool writes 'view_ID.full.org',
'view_ID.compact.org' and 'view_ID.view.json'.
** The full view
'BASE.full.org' is the view's text exactly as the server sent it,
metadata and all. It is what a client receives, before heralds hide
the metadata.
** The compact view
'BASE.compact.org' has every line of the full view, in the same order.
A body line is copied unchanged, except that its links are annotated.
A headline keeps its stars and its title; its '(skg ...)' metadata is
removed, and a handle is added at the end of the line.
*** The handle: the headline's viewnode ID
A handle has the fixed form '⟨ID ...⟩'. ID is the headline's viewnode
ID, the '(vnid ID)' that opens its metadata in the full view: the
server gives one to every headline of a view, and keeps it across that
view's saves ('docs/api-and-formats.org', "The metadata headers").
'grep -n "(vnid ID)" BASE.full.org' finds the headline's metadata, and
the pattern '⟨[0-9a-z]+' finds every handle. A headline that is moved
keeps its handle, so a tool can tell a move from a deletion, and a
headline without a handle is a new one. Body lines have no handle: a
body line belongs to the nearest headline above it.
*** The heralds in the handle
After ID come the headline's heralds: every herald a client shows,
in the order it shows them, as plain text, without their styles. A
client renders them from the server's herald rule table, which the
tool fetches too ('docs/heralds.org' explains each). So a node reads
'⟨0d ☮B 1Cb ⟳ M ~+⟩': write-protected (☮), its body omitted (B), its
relationship heralds, a cycle (⟳), then its change facts. A headline
that is not a node occurrence shows its label: a folder its sentence,
'⟨0b ☮ These contain it.⟩'; an alias 'alias', a flag row '☮ had ID
before import', a tombstone 'something stood here', an unknown
viewnode 'Reference to unknown node.'; a folder has no title, so in a
compact view it is its stars and its handle. An illegal edit to a
foreign node, a section of it in one of your skgrepos, is a folder
labelled '☮ ILLEGAL EDIT TO FOREIGN NODE'. On a node, in the order a
client shows them, the heralds are:
- the position glyphs: 'ᗣ' a ghost, or what HEAD alone warrants;
  '⊥' an unwarranted position; '☮' write-protected, and 'B' riding it
  when the node's body is omitted from the view;
- the relationship heralds (see below), then '⟳', a cycle;
- '~NAME', its relationship to its parent recorded in a skgrepo more
  private than the default, then '⌂:LABEL', the home skgrepo boundary
  (see below);
- the change facts, in the diff view (see below);
- pending requests, which a view the server rendered never shows,
  since a save consumes every request: 'delete', 'detach' (a
  'noClaim' child that leaves an editable parent at the next save),
  'req:...' view requests, 'request:...'.
*** The relationship heralds
The relationship heralds are rendered as the clients render them;
'docs/heralds.org', "Relationship heralds", explains them. In display
order: 'C' contains, 'L' links to, 'S' subscribes to, 'O' overrides,
'H' hides from its subscriptions. A count before a letter counts the
nodes on the relation's in-side ("two nodes contain this"), a count
after it the out-side ("this contains three"). A lowercase letter is
an ancestor in this view: 'a' the viewparent, 'b' the grandparent, and
so on; it replaces the count when ancestors make up the whole side. A
fraction marks a subset: '1/5L', five nodes link here and one of them
is substantive; 'C2/8', eight contents, two not yet integrated by the
subscriber above. 'ĥ' after 'O' says this occurrence stands in for a
node it overrides. The property counts 'A' (aliases), 'I' (extra IDs)
and 'F' (true flags) follow. So '⟨0h 2aC3⟩' has two containers, one
of them the viewparent, and three contents.

One token is left out: a bare 'aC', which says only that the
viewparent contains the node and nothing else does. That is the
ordinary case in a content tree, so most handles would carry it;
'⟨0c aC L1⟩' is written '⟨0c L1⟩', and '⟨0e aC⟩' just '⟨0e⟩'. Every
other form, 'aC10' or '2aC' among them, stays.
*** The skgrepo boundary
A headline whose home skgrepo differs from its nearest node
occurrence above it, or a root, carries '⌂:LABEL' after its
relationship heralds, LABEL the skgrepo's label from the table the
server sends beside its herald rules: '⟨0h ☮ C1 1/L bS ⌂:fred⟩' is a
note of the 'fred' skgrepo under a node of another. Every other
headline shares its skgrepo with the nearest node above it.
*** Change facts, in the diff view
A headline of the diff view that shows a change carries, after the
skgrepo boundary, the change facts the clients show ('docs/heralds.org',
"Diff heralds"). On a node or a ghost (a deleted node, shown as HEAD
has it, 'ᗣ☮'): '∃+' a new node, '∃-' a deleted one, 'M' a modified one
(its title, body, properties or lists changed), then '~+' a new
membership in its parent (in a partner folder, its relationship of
the folder's kind to the folder's parent), '~-' a removed one. On an
alias, ID or flag in its folder, '+' or '-'; on an unknown viewnode,
'~+' or '~-'. A '✓' right after a change says it is marked ready:
'∃+✓ ~+' is a new node, approved, in a membership that is not. The
headlines the diff view adds to explain a change show their labels:
'old title' (or 'old body', 'old title and body') and 'body diff',
'its content changed' (a changeset marker), '⌂ -OLD +NEW' (a move to
another skgrepo) and 'relationship moved from OLD to NEW'; each takes
a '✓' when ready. A folder shown because a member's relationship to
the folder's parent changed reads 'its containers changed (other
files)' and so on, with '✓' when every such change is ready. In the
skgrepo-changes buffer a moved node adds '-OLD +NEW', and 'Δ⌂=a' when
its nearest moved ancestor (here the parent) moved the same way.
*** Folded headlines
A headline the server marks 'folded', one a client shows collapsed,
ends its handle with the word 'folded': '⟨0j ☮ cH ⌂:fred folded⟩'.
The lines under it are still in both files; the word tells where a
person reading in a client would see less. It is the tool's; a client
shows no herald for it.
*** How the tool renders them
The tool applies the rule table the server serves ('herald rules',
fetched once per command) to each headline's metadata, as the clients'
lens does ('nvim/lua/skg/sexpr/lens.lua', the port of
'elisp/skg-sexpr/skg-lens.el'), and renders the relationship heralds
from the '(view (rels ...) (props ...) (birth ...))' facts, as
'render_rel_facts' in 'nvim/lua/skg/heralds.lua' does, reading
'shared/relations.json' for the letters and their order. What one
headline's metadata cannot say it reads from the headlines around it,
as a client reads its buffer: a pending detachment from the parent
and grandparent, a changed folder from its members
('shared/herald-styles.json' gives the folder labels and which
folders are write-protected).
*** Link annotations
Every '[[id:ID][label]]' link, in a title or a body, is followed by an
annotation in a fixed form. A link whose target resolves gets '⟦→ TITLE
⌂:LABEL⟧', the target's title and its home skgrepo's label. A link
whose target the graph lacks gets '⟦✗ missing⟧'; one whose target the
skgrepo restriction hides gets '⟦✗ restricted⟧'. The tool asks the
server's 'link statuses' request, which the clients' link annotations
use, and then 'titles by ids' for the titles of the resolved targets.
The annotation is the tool's; the link itself is unchanged.
*** The summary
Unless '--no-summary' is given, the compact view starts with a few Org
comment lines ('# ...') before the tree. They name the full view and
the view ID, then count, from the same metadata: the headlines, node
occurrences, distinct nodes, folders and other kinds; the node
occurrences in each skgrepo, owned or foreign; the occurrences in
foreign skgrepos, the write-protected and the folded headlines; those
contained elsewhere too (a 'contains' in-side larger than its ancestor
flags, so a container not above it in this view); those subscribed to
and those subscribing; the links, their distinct targets, and how many
of those resolve; and the server's errors and warnings, which the
sidecar lists.

Whether a skgrepo is owned or foreign comes from the server's 'repos'
request, which lists every configured skgrepo.
*** The ancestry
A view does not summarize the root's ancestry: the containers folder
that the server draws as the root's first child in a fresh content
view (and under each search hit) holds it, each container with its
own containers nested beneath it, so each chain upward reads as a path
of nested headlines. 'contains ID' gives the same view of any node,
to read its ancestry the same way. The folder is absent when nothing
contains the root.

A buffer of the diff view opens its summary with two more lines: the
readiness summary the server sends ("1 of 4 changed files are ready",
with how many changes this buffer cannot edit and how many files
changed in foreign skgrepos), and how many headlines show a change,
ready and not.
** The sidecar
'BASE.view.json' records the view ID, the command and its request (for
a buffer of the diff view, the buffer's name), the
port, the two files' names, the runtime generation the server rendered the
view at ('rendered_at'), the server's errors and warnings, whether
the compact view has a summary, and whether the view is closed: it
is closed unless a daemon holds it (see "The daemon"). 'save' sends
the edited view against this view ID and generation, to this port,
and renders the summary again when there was one.

* Views and connections
The server keeps a view's state per TCP connection, and forgets every
view of a connection when it ends. Without a daemon, each command
opens one connection, and sends 'close view' for its view before
disconnecting, as a client does when its buffer is killed. A view is
therefore never left open by the command. A save reads the saved
buffer against the graph; the server does not hold its view, and
keeps every handle the buffer carries (see "Handles across saves"). A
save of a buffer of the diff view names its buffer
('(diff-view-buffer . "all changes")', say), so the server re-renders
it as that buffer, with its readiness summary. The 'close' command
matters only for a view that a longer-lived connection holds: a
daemon's.

Between its answers, the server may tell a connection that it
integrated '.skg' files that changed on disk (a teammate's save, a
'git pull'). A command on its own connection prints, on standard
error, a line per skgrepo, as 'skg server: repo NAME: N files
integrated', and each warning (a file that could not be read, say), as
'skg server: WARNING', and reads on; a view written before it may be
refused on save if it would write a node that changed. A daemon
instead rewrites the views it names and logs the counts and warnings.

* The daemon
** Why
A command's connection ends with the command, and with it everything
the server would have said to it later. The server rerenders a view
only on the connection that holds it: after a save on that
connection, of any view that shows a node the save changed, and when
it integrates '.skg' files that changed on disk (a teammate's save on
their own server, a 'git pull'), of the views showing a changed node.
It tells only connected clients its warnings. Files written by a
command therefore go stale silently, and nobody hears the warnings.

The daemon is a client that stays connected, as an editor session
does. Every command for its server runs through it; it holds every
view they write, wherever they write it, rewrites a view's files when
the server rerenders it, and logs what happened and why. Nothing
changes for a reader who never starts one.
** Starting and stopping
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py daemon --out-dir DIR --port P &
# ... view, edit, save with '--out-dir DIR' as usual ...
python3 tools/skg-for-ai/skg_for_ai.py daemon --stop --out-dir DIR
#+end_example
The daemon connects to the server ('--port', else 'SKG_PORT', else
1730), logs the server's startup warnings, listens on two Unix
sockets, 'DIR/skg-for-ai.sock' and the port's,
'skg-for-ai-PORT.sock' in 'XDG_RUNTIME_DIR' (or in '/tmp' when that
is unset), and prints one line saying so; it runs in the foreground
until stopped. DIR holds its log and its socket; the views it holds
may be anywhere. 'daemon --stop --out-dir DIR', SIGTERM and SIGINT
each stop it: it closes every view it holds (each sidecar then says
'closed'), its connection and its sockets, and exits. A stop signal
is noticed between commands, not during one.

One daemon runs per folder and one per port: starting a second where
one answers, in the same folder or for the same port, is refused,
naming the running one's process, folder and port. A daemon that was
killed outright leaves its sockets behind; commands then run on their
own connections, and the next daemon started there removes each and
makes its own. A daemon whose server goes away (stops, restarts, is
rebuilt) logs it and stops, since the server has forgotten its views.
** Commands run through it
While a daemon runs for a port, every command for that port runs
through it, whatever folder it writes into: a view command ('view',
'search', 'forest', 'contains', 'links-here', 'diff', 'new'), and
'save', 'integrate' and 'close', whose port is their sidecar's, and
'commit --yes'. A command's port is the one its '--port' or
'SKG_PORT' names, or the sidecar's. A command that names no port and
has no sidecar runs through the daemon of its '--out-dir', if one
runs there, on that daemon's server; otherwise through the daemon for
the default port, 1730. The command sends its command line, its
current directory and the port it named over the socket; the daemon
runs it exactly as the command would run, but on the daemon's
connection, writing its files where the command asked, and answers
with what it printed and its exit code, which the command prints and
exits with. So the output and the files are those of the command run
without a daemon, but for the sidecar's 'closed', which is false
while the daemon holds the view.

The daemon runs one command at a time; the others wait their turn.
Between commands it reads what the server sends unprompted; what
arrives while a command waits for its answer is handled after that
command.

'raw' and 'import' always run on their own connection: 'raw' speaks
the protocol directly, and 'import' binds its approval to a
connection of its own. So does a 'commit' without '--yes', since the
typed "yes" it may ask for cannot cross the socket; once it has
committed, it asks the daemon for its port to rerender the buffers
of the diff view it holds, which the server rerenders after a
git-commit only on the committing connection.
** What happens to the views
Every view a command run through the daemon writes stays open on the
daemon's connection, in whatever folder its files are. A save of one is the ordinary case for the
server: a save of a view the connection holds, the case of an editor's
buffer. The rules for a view the server does not hold (the handles
taken from the buffer, the diff-view buffer named in the request; see
"Handles across saves") are not needed. The tool still names the
buffer of the diff view in a save; the server keeps the kind a held
view was registered with, so this changes nothing, and a command
behaves the same with or without a daemon. 'integrate' still saves the
full view back unchanged before it integrates, which writes nothing.

When the server rerenders a held view, the daemon writes the
rerendered view over its three files, as 'save' does, and logs it.
The server rerenders a held view
- after a save on the daemon's connection (a command run through it)
  that changes a node the view shows: a collateral rerender, which
  arrives with the save's answer, and which the daemon writes before
  the command returns;
- after a git-commit on the daemon's connection ('commit --yes'), and
  of the buffers of the diff view after one on another ('commit'
  without '--yes', which then asks the daemon);
- after it integrates files that changed on disk, of which it tells
  the connection with a 'repo-files-integrated' message naming the
  views that show a changed node (and every buffer of the diff view):
  the daemon then asks for their rerender, as the clients do ('Repo
  files integrated' in 'docs/api-and-formats.org').
A rewritten buffer of the diff view has no readiness summary, since a
rerender carries none; its next save, or 'diff', gives one.

A compact view with unsaved edits (anything 'save' would report) is
never overwritten. The daemon does not ask for its rerender, keeps its
files as they are, and logs 'kept BASE'. Its save is then refused if
it would write a node that changed since it was rendered; view the
node again under another '--name' to see the change, and redo the edit
there.

A view ID names one view per connection, and a held view one set of
files. 'view ID' and 'forest KIND ID' share the view ID
'content-view:ID', so the later of them holds it, and the earlier
files are released: their sidecar says 'closed', the daemon no longer
rewrites them, and a save of them runs on its own connection. Viewing
a node again into the same files replaces the held view with a fresh
one, and a new 'diff' replaces the buffers written under the same
names. 'close SIDECAR' releases one view.
** What it does not see
A save on another connection to the same server (an editor on that
server, or a command that reached no daemon: an 'import', or one run
while the daemon was down) writes files the server knows as its own,
so no message reaches the daemon, and the views it holds that show
those nodes go stale; a save of one is then refused if it would write
a node that changed. Commands for the daemon's port run through it,
so this happens only with another client on the same server. A
change on disk by anything else, another server's save or a 'git
pull', reaches it.
** The log
'DIR/skg-for-ai.log' is appended to, one line per event, each starting
with the local time ('2026-11-01 21:34:33'); a message of several
lines is joined into one with ' | '. The events:
- 'started: process N, server port P', with '; replaced the socket a
  dead daemon left at PATH' for each it replaced; 'stopped: released
  N views'.
- 'holding BASE (view ID ID)' when a command writes a view;
  'released BASE: its view ID now shows OTHER'; 'closed BASE'. BASE
  is the files' base name in the daemon's folder, and their folder's
  real path joined to it elsewhere ('/home/me/notes/view_ID').
- 'saved BASE', 'saved new root TITLE', 'integrated BASE', for the
  commands that write to the graph.
- 're-rendered BASE because CAUSE; CHANGES': the daemon rewrote a
  view's files. CAUSE is "of 'COMMAND' on the daemon's connection" for
  a collateral rerender or one after 'commit --yes', "of a git-commit
  on another connection" after a 'commit' without '--yes', or "files
  changed on disk (COUNTS; WARNINGS)" with the server's notice. CHANGES compares the old full view with the new,
  node by node, by title: "new 'T'", "gone 'T'", "'T' changed: title,
  was 'OLD', body, metadata" (the metadata holds its relationships,
  among other facts), the first six and a count of the rest, or "no
  node changed".
- 'kept BASE: ...', a rerender not written over unsaved edits.
- 'changed on disk: repo NAME: N files integrated; ...' when the
  server integrated files that changed on disk.
- 'warning: TEXT' for every warning the server sends the connection:
  its startup warnings, each integration's (a file that could not be read,
  a batch that failed validation, a telescope that leaks text), and
  those of every save and rerender on the connection.
- 'error: ...': a command that failed, with its message; a message the
  server sent unasked that the daemon does not know; the connection
  lost.
For instance:
#+begin_example
2026-11-01 21:34:13 saved view_child-a-id
2026-11-01 21:34:13 re-rendered view_root-id because of 'save view_child-a-id.view.json --yes' on the daemon's connection; 'First child, renamed via daemon' changed: title, was 'First child'
2026-11-01 21:34:32 changed on disk: repo main: 1 file integrated
2026-11-01 21:34:33 re-rendered view_child-a-id because files changed on disk (repo main: 1 file integrated); 'First child, renamed on the other server' changed: title, was 'First child, renamed via daemon'
#+end_example
The log is how a reader who was elsewhere learns that the graph moved:
anything that wants waking when it does can follow the file
('tail -f').

* How 'forest' draws a folder
The server has no request that answers "what links here" or "what
subscribes to this". The clients ask for a folder by saving the view
with a view request on the node's headline, '(viewRequests (folder
mentioners))' for 'C-c l m' in Emacs, or '(viewRequests flags)' for
'C-c l p', and the re-rendered buffer the save returns shows the
folder. The tool does the same: it opens the view, adds the kind's
request to the root's metadata, and saves the otherwise unchanged
buffer; 'forest containers' alone needs no save. The tool may save,
as any client may. Since nothing in
the buffer differs from the graph, the save writes no file, but it is
a save, sent through the server's whole save path, so a node that the
server would refuse or ask about on save (a foreign node edited, for
instance) can make it fail or ask a question the tool does not
answer. The tool then reports the server's answer and writes nothing.

* Writing
** The loop
To change the graph, edit the compact view in place and save it:
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py view ID --out-dir DIR
# edit DIR/view_ID.compact.org
python3 tools/skg-for-ai/skg_for_ai.py save DIR/view_ID.view.json
# read the report
python3 tools/skg-for-ai/skg_for_ai.py save DIR/view_ID.view.json --yes
#+end_example
'save' takes the sidecar, or a directory holding only one. Without
'--yes' it prints the report and stops; with it, it prints the report,
sends the save, prints the server's answer, and writes the server's
re-rendered view over the three files, so the next edit starts from
them. A headline the edit kept keeps its handle (see "Handles across
saves"), and a new one has a handle now. A save needs the server the
view came from; '--port', if given, must match the sidecar's.

The tool writes nothing to '.skg' files itself. The server's save does,
with every check an editor client's save gets, and it writes only to
skgrepos the server's config owns.
** How the compact view becomes a buffer
The tool rebuilds the buffer an editor client would send, from the
edited compact view and the full view it was written beside. A
headline with a handle '⟨ID ...⟩' gets back the metadata of the full
view's headline whose viewnode ID is ID; its level, title and
position come from the edited compact view. The rest of the handle
(the heralds, 'folded') is display only, and editing it changes
nothing, except for the request words: 'delete' (see "A deleted
node"), 'ready', 'unready', 'all', 'restoreNode' and 'restoreRel'
(see "Reviewing and committing"), and 'editable' and 'fork' (see
"Forking"). No herald of a view the server rendered is one of these
words, since a save consumes every request; so each such word in a
handle was written there. The rebuild writes the first six into the
headline's '(editRequest ...)', which holds one edit request
('delete', 'restoreNode' or 'restoreRel') and one readiness request
after it, and the last two into its '(viewRequests ...)', as
'editableView' and 'fork'. A headline without a handle, or with the
handle '⟨new⟩', is written bare, and the save makes it a new node,
with a new ID (see "Retyped headlines"). A headline ending in
'⟨node:ID⟩' is written as the clients paste a node (see "Placing an
existing node").

Body lines are taken as edited, and belong to the headline above them.
The link annotations the tool added ('⟦→ ... ⟧' or '⟦✗ ... ⟧' right
after a link) are removed and the links kept, so a link typed anew
needs no annotation. The summary's comment lines before the first
headline are dropped.
** What each change does in skg
*** A changed title or body
The node's title or body changes, wherever else it appears. A
write-protected occurrence (one the full view marks 'writeProtected',
such as each container in a 'containerFolder') saves nothing of its own,
so the server refuses a save that changes its title.
*** A new headline
A headline typed without a handle becomes a new node, contained by its
parent headline, at the position typed. Its home skgrepo is chosen by
the server as for any new headline. The re-rendered view shows it with
a handle, and the full view gives its new ID.
*** A moved headline
A handled headline under a different parent leaves the old parent's
content and joins the new one's, at the position typed. Reordering
headlines under one parent reorders its content.
*** A removed headline
Deleting a headline's line, and the lines under it, takes the node out
of its parent's list (where the parent reads claims: an editable node's
content, an editable folder's members). The node itself stays in the
graph, with its other containers. Under a write-protected occurrence or
a write-protected folder nothing claims, so removing a headline there
only removes it from the view.
*** A deleted node
To delete a node from the graph, write the word 'delete' inside its
handle: '⟨0d delete⟩', or '⟨0d aC1 delete⟩'. The tool writes it into the
headline's metadata as '(editRequest delete)', the request the clients'
'skg-delete' ('C-c <backspace>') writes, and the save deletes the node.
Only an editable node occurrence can carry it; the server refuses it
elsewhere.
** The report
Before saving, the tool compares the edited compact view with the full
view and prints a line per change, each naming headlines by handle and
title, as in
#+begin_example
Changes in view_root-id.compact.org, against view_root-id.full.org (view ID content-view:root-id):
Moved: ⟨0e⟩ 'Contained twice', from under ⟨0d⟩ 'First child' to under ⟨0f⟩ 'Second child, a subscriber'.
New: 'A new grandchild', under ⟨0d⟩ 'First child'.
Title: ⟨0d⟩ 'First child' → 'First child, renamed'.
Bodies changed: 1 (⟨0a⟩).
Not saved. Run again with '--yes' to save.
#+end_example
An 'Error:' line names a handle that names no headline of the full
view, or whose request words make no one '(editRequest ...)' (two edit requests, both 'ready' and 'unready', 'all' alone),
or that carries 'editable' or 'fork' but is no node;
or a '⟨new⟩' or '⟨node:ID⟩' carrying another word, a placed node the
graph lacks, or one with a body or children (see "Placing an existing
node"); or a new headline retyped with a removed one's title (see
"Retyped headlines"); or an edit of a write-protected foreign node, a
'fork' beside other edits, or a fork with no owned skgrepo to go to
(see "Forking");
any error stops the save, and the report then lists only the errors.
The report does not guess what the server will refuse: the server's
answer says that.

The changes follow, in this order. 'Delete:', 'Restore node:',
'Restore membership:', 'Editable:', 'Ready:' and 'Unready:' are the
requests the handles' words ask for, a readiness request with the form
the save sends ('Ready: ⟨0j⟩ 'A new grandchild', as '(ready node rel)'.').
When the 'unready' requests would unmark more than one change, a
'Question:' line asks what a client asks before such a gesture, and
'--yes' answers it. 'Removed:' is a handle the edit no longer has,
with how many headlines below it went with it; a child of a removed
headline that was moved elsewhere is reported as moved. A removed
headline leaves its parent's list, where the parent reads claims; the
node itself stays in the graph. 'Moved:' is a handle under a
different parent, or at a different depth below the same one.
'Reordered:' is a parent whose kept children stand in another order.
'New:' is a headline without a handle, and where it stands.
'Placed:' is a headline ending in '⟨node:ID⟩', with the title the
server gives the node, where it stands, and whether it is placed
write-protected.
'Repeated:' is a handle used twice, which shows the same node twice.
'Title:' gives a changed title, old and new, and 'Bodies changed:'
counts the changed bodies and names their handles. 'Fork:' is a node
the save forks, and 'Fork into:' the skgrepo its clone goes to (see
"Forking"). An edit with none of these prints 'No changes.' and saves
nothing. Last, a 'Question:' line asks whether a new headline is a
removed one reworded (see "Retyped headlines").
** Retyped headlines
A headline's handle is what ties it to its node. Retyping a headline
instead of moving its line loses that tie: the typed headline becomes
a new node with a new ID, and the old node leaves its parent but stays
in the graph, so links to it, its other relationships and its history
stay with a node the view no longer shows. So the rule is: to move or
reword a headline, keep its handle. Cut and paste the whole line, or
copy the handle onto the headline typed in its place; a handle with
only its ID, '⟨0e⟩', is enough, since the rest of a handle is display.

The tool catches the mistake before saving, by comparing the title of
each new headline (one with no handle) with the title of each headline
the edit removed (a handle of the full view the edited compact view no
longer has).

When the titles are equal, the save is refused. An 'Error:' line names
the new headline and the removed one, and says how to go on: if the
new headline is the removed node, moved or reworded, end it with the
removed one's handle; if it is a different node that happens to share
the title, end it with '⟨new⟩'. That handle has no ID, only the word,
and says "this headline is new on purpose": the tool saves it as a
new node and never compares its title again. It takes no other word.

When the titles differ but probably say the same thing, the report
asks:
#+begin_example
Question: removed ⟨0d⟩ 'Added at the top, retitled' / new 'The headline added at the top, retitled again' (line 10): probably the same statement reworded; keep its ID?
#+end_example
and nothing is saved until it is answered. '--yes' alone does not
answer it: '--yes' says "save", not which of two things to save. The
answers:
- '--keep-ids' answers yes to every question: each new headline takes
  its removed headline's handle, and so its node, its ID and its
  metadata, with the new title. The report then shows the move and
  the retitle instead of a removal and a new headline.
- '--all-new' answers no to every question: each new headline is a
  new node, and each removed one leaves its parent.
- Or answer on each headline: write the removed handle on it (the
  same node), or '⟨new⟩' (a new one). Then that headline asks nothing.
Run the save with the answer and '--yes' to save; without '--yes' the
report shows what the answer would save.

A title "probably says the same thing" by a deliberately loose test.
Each title is lowercased; apostrophes are dropped and other
punctuation splits words; common words are dropped (articles,
prepositions, conjunctions, pronouns and verbs like 'is', 'are',
'was', 'be', 'has', 'have', 'do'); and each word loses one suffix
('-ing', '-ed', '-es', '-ly' or '-s') and then a final 'e', so that
'save', 'saves', 'saved' and 'saving' are one word. Two titles match
when their sets of words share enough, by the Dice coefficient
(twice the shared words over the sum of the two counts) of at least
0.6, or when the remaining texts are alike letter by letter, by
'difflib''s ratio, at least 0.75. The ratio counts only when each
title has at least three words left: on shorter ones a shared word
is most of the text ("budget meeting" and "budget notes" reach
0.76), so two short titles match by the Dice coefficient alone.
The test errs toward asking: a
needless question costs one flag, a missed one costs an ID. When a
new headline resembles several removed ones it is paired with the
closest, and the question names the others; each removed headline is
paired with one new headline at most, closest pairs first.
** Placing an existing node
A headline that ends in '⟨node:ID⟩', ID a node's ID, puts that
existing node there: under an editable parent it joins the parent's
content, so the node gains a container and keeps the ones it had.
This is the clients' 'skg-paste-node' ('C-c o n' in Emacs), which
pastes the top of the linkstack; the tool has no linkstack, and the
ID is written instead. Find an ID in the full view, where each
headline's metadata carries its '(gnid ID)', or in a link.
#+begin_example
** inboxes ⟨0a C1 ⌂:first⟩
*** anything ⟨node:883e7f64-c377-4894-a75b-64c52d1668c4⟩
#+end_example
The title may be anything: the tool asks the server for the node's
title ('link statuses', then 'titles by ids', as the link annotations
do), the report shows it, and the save sends it, since the server
refuses a write-protected occurrence whose title differs from the
graph's. The report reads
#+begin_example
Placed: ⟨node:883e7f64-c377-4894-a75b-64c52d1668c4⟩ 'to Ed', under ⟨0a⟩ 'inboxes'.
#+end_example
The headline is sent as the clients paste it: '(skg node (gnid ID)
writeProtected (viewRequests editableView))', a write-protected
occurrence asking to be made editable. The save fulfils the request,
so the re-rendered view shows the node editable, with its real title,
body and content, and a handle. When the view already holds an
editable occurrence of the node, or a headline asking to become one
(an earlier placement of it, say), the request is left out, since a
view holds at most one editable occurrence of a node; the node is
then placed write-protected, and the report says so: "Placed: ...,
write-protected, since the view already holds an editable occurrence
of it."

Placed in an editable folder of a 'forest' view, a node joins that
folder's relation instead: in the subscribee folder ('forest
subscribesTo ID') the folder's node subscribes to it, and in the
overridden folder ('forest overrides ID') overrides it. Under a
subscribee as such, the subscribed node in that folder, stand its
children the subscriber has not integrated; removing one there hides
it from the subscription, as in the clients.

A placed node takes no other word in its handle, no body and no
children in the save that places it: it is saved write-protected,
which saves no body, and under which no child claims membership. Edit
it in the view the save writes, where it is editable. The report
stops at a placed ID the graph lacks or the skgrepo restriction
hides.
** Forking
A fork ('docs/forks.org') makes an editable clone, in a skgrepo you
own, of a node: the clone subscribes to the original and overrides
it, so it stands in the original's place in your views, while the
original's later content reaches you as unintegrated content in the
clone's subscribee folder. It is how a teammate's node becomes yours
to edit, without changing theirs.
*** Editing a foreign node forks it
A node of a foreign skgrepo forks when you edit it: change its title
or its body, or add, remove or reorder its children, at an editable
occurrence of it. A foreign node in your own node's content is
editable in a fresh view; one placed with '⟨node:ID⟩' is editable
after the save that places it. A write-protected occurrence ('☮')
saves nothing of its own, so editing one forks nothing: the report
stops with an error, and says how to go on. Write 'editable' in its
handle and save, which makes it the view's editable occurrence of the
node, as the clients' 'C-c s d' does; then edit it and save again.
Only an occurrence in content forks, a root of the view or a node's
child: a member of a folder does not, and a subscribee as such, in a
subscribee folder, takes no edit of its title or body, and a child
removed from under it is hidden instead (see "Placing an existing
node").

The report says what forks, and where the clone goes:
#+begin_example
Bodies changed: 1 (⟨0b⟩).
Fork: ⟨0b⟩ 'to Ed', of the foreign skgrepo 'public', whose body changed: the edit goes to a new clone of it, which subscribes to it and overrides it; the original stays as it is.
Fork into: 'first', the one skgrepo this server owns, unless the edit settles another. The server asks before forking; '--yes' approves.
Not saved. Run again with '--yes' to save.
#+end_example
The clone needs an owned skgrepo. '--fork-into REPO' names it; without
it, the clone goes to the server's one owned skgrepo, from the 'repos'
request, and when the server owns several the report stops and asks
for '--fork-into'.
*** The fork confirmation
A save that forks writes nothing at first: the server answers with a
fork confirmation, which lists each clone-to-be (the edited title,
its skgrepo, or 'PICK-A-REPO' with a suggestion when the edit did not
settle one) over the original it forks. Without '--yes' the tool sends
nothing, so nothing is forked: that is the decline, as a client's
decline sends nothing either. With '--yes' the tool prints the
confirmation, as the clients show it in their confirmation buffer,
#+begin_example
Server: fork confirmation: the save forks 1 node, and writes nothing until that is approved.
Clone-to-be: 'to Ed', in 'first' (the server suggests 'first').
  It forks 'to Ed' (883e7f64-c377-4894-a75b-64c52d1668c4), of the skgrepo 'public'.
Approved: the save is sent again with the forks approved.
#+end_example
then approves it, as a client's approval does: it sends the same save
again, on the same connection, with '(approved-forks . "true")' and
'(fork-repos (("ID" . "REPO") ...))', each original's ID with its
clone's skgrepo, the placeholder replaced by the '--fork-into' or
default skgrepo. The answer to that save is the ordinary one, and its
re-rendered view, written over the files, shows the clone in the
original's place, marked 'Oĥ'. '--yes' approves only the forks the
report listed: if the server lists another, nothing is saved, and the
tool says which.

The clone copies the original's title, body and content list (the
IDs, not the subtree) with the edit applied, subscribes to it and
overrides it; a child the edit removed becomes one the clone hides
from its subscription. The original is not written. A node may have
one clone you own; forking it again is refused, naming the clone.
*** Forking a node you own
'fork' in the handle of a node you own forks it, as the clients'
'skg-fork-node' ('C-c m f') does: '⟨0d aC1 fork⟩'. Its clone
subscribes to it and overrides it, and the original keeps its own
content; a chain of overrides deepens this way. As the clients refuse
to fork from a buffer with unsaved changes, so that the clone is the
node as saved, a 'fork' beside any other edit of the compact view is
an error: save the other edits first. The confirmation and its
approval are those of an implicit fork.
** Handles across saves
The server keeps a view per connection, and without a daemon the
tool's connection ends with each command, so a save names a view the
server does not hold. For such a view the saved buffer's own viewnode
IDs are the view's
(=docs/api-and-formats.org=, on '(vnid X)'): every headline keeps the
one it carries, and a new headline gets one past the highest the
buffer carries. So every handle stays across a save, through adds,
moves, retitles and removals, and a new headline gets a new handle.
A buffer of the diff view keeps its handles the same way. Through a
daemon the server holds the view, and keeps its viewnode IDs across
its saves as it does an editor's.
** Stale views
The save carries the runtime generation the view was rendered at, from the
sidecar. If a node the save would write changed since (by Jeff in
Emacs, say), the server refuses the whole save, naming the node, and
writes nothing; the tool prints that refusal as it prints any other,
and leaves the files. A node the view shows as the graph now has it is
not written, so it does not stop the save. View again and redo the
edit.
** The server's answer
After the save the tool prints 'Server: saved' or 'Server: nothing was
saved', with the counts of errors and warnings, then each error and
warning as the server wrote it. When the server refuses, the three
files stay as they were, so the edit can be fixed and saved again.
When the server answers with a fork confirmation, the tool prints it
and approves it, as "Forking" says. When it answers with another
question instead (to delete records the skgrepo restriction hides, to
review stranded relationships, to hoist telescope text), the tool
prints the question and stops: it answers none of them, and nothing is
saved. A client can answer them. One question comes after the save:
under a restricted skgrepo-set the server may withhold the re-rendered
view until over-private text is approved. The save has then happened,
the tool says so, and the files are out of date until the node is
viewed again.

* Reviewing and committing
** The loop
Saving writes '.skg' files and nothing else. When a piece of work is
done, review it in the diff view, mark the changes meant, and commit
them all with one message:
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py diff --out-dir DIR
# read DIR/diff_all-changes.compact.org, and any other DIR/diff_*.compact.org
# fix a change by editing any view (this one too) and saving it
# add 'ready' to the handles of the changes meant:
python3 tools/skg-for-ai/skg_for_ai.py save DIR/diff_all-changes.view.json --yes
python3 tools/skg-for-ai/skg_for_ai.py commit "MESSAGE"
#+end_example
The diff view ('docs/diff-view.org') shows how each owned skgrepo's
worktree differs from its HEAD commit, with the context that explains
each change: the changed nodes, the nodes above them up to a root,
and what each change replaced. A deleted node stands as its ghost,
with HEAD's title and body; a changed title or body has its old text
under it ('oldText ...'), a changed body its line diff ('bodyDiff');
a changed content list a 'changesetMarker content', and a removed
member stands where it stood, marked '~-'. The handles carry the
change facts (see "Change facts, in the diff view"). There are up to
four buffers, written in this order when not empty: all changes, the
nodeMerges, the moves between skgrepos, and the nodes whose only
change is the order of a list. Each is a view like any other: it can
be edited and saved, and its save answers with the readiness summary.
After any save, 'diff' again for a fresh rendering; a save of a diff
buffer rewrites that buffer's files.
** Marking changes ready
A mark says that one change is approved as it is now; editing a marked
change unmarks it. Marking is a save: write a word in a handle, and
'save' turns it into a readiness request in the headline's
'(editRequest ...)', as the clients' 'C-c r r' does.

'ready' marks every change the headline names, as the request '(ready
OBJECT...)' naming each object its change facts list: on a new node
its existence and its membership, on a modified node ('M') every
change its file records and its membership if that changed, on an old
text or a move the one change, on a changeset marker every change
under it. 'unready' unmarks the same. 'ready all' and 'unready all'
name only the object 'all': every change a modified node's file
records, or every change of a changeset marker.

A save that unmarks more than one change prints the question a client
asks first, and '--yes' answers it. The server applies the requests
after the save's edits succeed; it drops a request that names no
current change, with a warning, and refuses a save in which two
headlines mark and unmark one change. The save's answer ends with the
readiness summary, "N of M changed files are ready", which counts
every change of the owned skgrepos, whatever the buffer shows.
** Restoring what a change removed
Two more words undo a removal, the way the clients' 'C-c s n' and 'C-c
s l' do. 'restoreNode' on a ghost writes the deleted node back as
HEAD has it, and back into each list that named it at HEAD. 'restoreRel' on a
removed membership (a '~-' member) puts it back in its list, where
HEAD had it. The server refuses either anywhere else.
** Integrating changes the buffer does not make editable
A buffer of the diff view makes a change editable where it holds an
editable occurrence of the node that records it. A fresh buffer
('diff') makes every change editable, but a save makes nothing
editable and adds no root, so a change made since (by another view's
save, or by this save itself) may not be editable in the buffer the
save writes. The readiness summary then says "N changes are not
editable in this buffer".

'integrate SIDECAR' makes them editable, as the clients' 'C-c r u'
does: the server makes each changed node editable at its first
occurrence in the buffer (drawing its body and content), and appends
as roots the origins of changes the buffer shows nowhere. It refuses
a compact view with edits (save them first, as a client refuses a
buffer with unsaved changes), prints the readiness summary before and
after, and writes the server's rerendered buffer over the three files.
#+begin_example
python3 tools/skg-for-ai/skg_for_ai.py integrate DIR/diff_all-changes.view.json
#+end_example
The server integrates the buffer it holds under the view ID, so the
tool first saves the full view back unchanged under that ID, naming
its buffer of the diff view (which writes nothing, and leaves the
server holding it as that buffer). The server refuses that
save when a node the buffer shows has changed since it was written;
'diff' then gives a fresh buffer, in which every change is editable.
** Committing
'commit MESSAGE' sends "stage and commit". The server stages every
changed '.skg' file of every owned skgrepo, deletions included, and
git-commits each gitrepo that has changes, with MESSAGE, by that
gitrepo's configured user. It commits everything, marked or not: the
marks are a review, not a selection. When not every changed file is
ready, or some owned gitrepo already has staged entries (which the
git-commit would include), the server asks first: the tool prints the
readiness summary and the staged paths, and asks for a typed "yes" on
standard input; '--yes' answers yes. Any other answer, or no input,
commits nothing. Then it prints 'Committed in SKGREPO (COMMIT ID)'
per git-commit, or 'Nothing was committed.', and any error. A blank
message is refused before anything is sent. With a daemon for the
port, the buffers of the diff view it holds are rewritten after the
git-commit (see "The daemon").
** Where it works
The diff view and the commit need a connection with no skgrepo
restriction, and each owned skgrepo in a gitrepo with a HEAD commit;
the server refuses them otherwise, and the tool prints its refusal.
Foreign skgrepos never show a change, and are never committed. So on
Ed's server ('data/skgconfig-ed.toml'), only the
owned repo 'first' can show changes or be committed.
** How it talks to the server
The server keeps the diff view's buffers, and the comparison behind
them, per connection. 'diff' opens one connection (or runs through a daemon),
requests the buffers in the clients' order, and writes each nonempty
one, with the readiness summary the server's answer carries. A later
'save' or 'integrate' of a diff buffer names its buffer of the diff
view in the save request, so that the server re-renders it as one,
with the readiness summary, on a connection that never opened it; the
save keeps every handle the buffer carries (see "Handles across
saves"). Through a daemon the connection holds the buffer already, and
naming it changes nothing.
